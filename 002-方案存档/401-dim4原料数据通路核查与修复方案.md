# 401 — dim4原料数据通路核查与四项修复方案

---

## 一、背景

400号方案实施完成后，对 dim4 引擎的**输入原料数据**通路进行了全面核查。发现 daemon 预计算写入 pre_feat_cache 的数据在扁平化后存在覆盖、缺失和不一致问题，导致 400 号 F-01 修复（get_tags 补全 asr/cyqkl/profit_ratio）虽在采集层正确产出，但到达 dim4 消费端时已被破坏。

---

## 二、问题清单

### P-01（HIGH）：daemon derived.profit_ratio 覆盖 chip.profit_ratio

**位置**：`backend/data_daemon.py:2475`

**现象**：dim4 evaluate() 的 `profit_ratio` 始终为 None，400号 F-01 修复未闭环。

**根因**：daemon 第11步（derived 特征）写入：
```python
_derived['profit_ratio'] = _chip_f.get('chip_position', 0)   # 值='in_peak'（字符串）
```

第8步（chip 特征）已由 get_tags() 正确写入 `chip.profit_ratio = 0.735`（float）。

`_flatten_pre_feat()` 按组顺序遍历（chip → derived），后者覆盖前者。扁平化后 `tags['profit_ratio'] = 'in_peak'`（string）。

dim4 evaluate 第5443行：`float('in_peak')` → ValueError → except 吞掉 → `profit_ratio = None`。

**影响**：`cost_profit_ratio=None` → `cost_structure` 仍显示"筹码数据不足"，dim4 筹码成本结构输出不完整。

**修复方案**：删除 `data_daemon.py:2475` 的赋值语句。

理由：
1. 该行注释为"利润比"但赋的是 `chip_position`（字符串），语义错误
2. chip.profit_ratio 现已由 get_tags() 通过 ChipIndicators.calculate_profit_ratio() 正确计算
3. 删除后 chip.profit_ratio（float）不再被覆盖，dim4 正常消费

**工时**：0.1天

---

### P-02（MEDIUM）：margin_change_5d 不在 pre_feat_cache 中

**位置**：dim4 evaluate() 第5474行读取 `tags.get('margin_change_5d')`；daemon 14 个特征组均未写入此字段。

**现象**：dim4 每次输出 `margin_detail = '融资数据不足'`，融资维度永远缺失。

**根因**：daemon 的预计算管道未包含融资数据变化率的计算。`margin_change_5d` 需要从 `margin_cache` 表读取近 5 个交易日的融资余额，计算变化百分比，写入 pre_feat_cache。

**修复方案**：在 daemon 第13步（chip_fund_ext 特征组）中补充 margin_change_5d 计算。

具体实现：
1. 从 `margin_cache` 表查询近 5 个交易日的 `rzye`（融资余额）
2. 计算 `(latest - 5d_ago) / 5d_ago * 100` 得到变化百分比
3. 写入 `features['chip_fund_ext']['margin_change_5d']`

**前置条件**：确认 `margin_cache` 表有数据且包含 `rzye` 字段。

**工时**：0.5天

---

### P-03（MEDIUM）：两套 PhaseDetectionEngine 并存

**位置**：
- daemon `data_daemon.py:2410`：`from app.opportunity_atlas.phase_detector import PhaseDetectionEngine`
- dim4 `dim4_chip_fund_engine.py:5397`：内部定义的 `PhaseDetectionEngine`（line 325）

**现象**：daemon 预计算的阶段判定（写入 pre_feat_cache.depth）与 dim4 evaluate() 实时计算的阶段判定可能不一致。

**根因**：这是两个不同的类，各自独立计算。dim4 evaluate() 优先使用内部 PDE 的实时结果，daemon 的预计算值仅作 fallback。

**影响**：
- 同一只股票，daemon 判定 `main_force_phase='raising'`，dim4 内部 PDE 可能判定为 `'building'`
- dim4 使用内部 PDE 结果，daemon 的预计算值被忽略
- 两个路径的 `fund_flow`、`phase_confidence` 也可能不同

**风险评估**：当前不是功能性 bug，但存在数据一致性风险。dim4 内部 PDE 实时计算的逻辑与 daemon 的独立 PDE 逻辑可能存在版本差异。

**修复方案**（两个选项，待确认）：

**方案A（推荐）：dim4 evaluate() 优先使用 tags 中 daemon 预计算的值**

修改 dim4 evaluate() 的 PDE 调用逻辑：
1. 先从 tags 读取 daemon 预计算的 `main_force_phase` / `fund_flow` / `phase_confidence`
2. 仅当 tags 中这些字段为空或 unknown 时，才触发内部 PDE 实时计算
3. 好处：消除双重计算，保证全系统阶段判定一致

**方案B：统一 PDE 类，消除两套实现**

将 dim4 内部的 PhaseDetectionEngine（line 325-1101）替换为对 `app.opportunity_atlas.phase_detector.PhaseDetectionEngine` 的引用。需验证两个类的 API 兼容性。

**工时**：方案A 0.5天 / 方案B 1天

### P-04（INFO）：旧SIG信号路径仍在使用

**位置**：`backend/app/routes/strategy_analyze.py:669-714`

**现象**：前端 7 维分析卡片的筹码维度（`dimensions['chip']`）走旧 SIG 信号路径，不经过 dim4 引擎。

**数据流**：
```
旧SIG路径（7维卡片）:
  strategy_signal_detail → _find_signal('筹码') → chip_sig
  tag_extractor(chip_deep) → _deep_tags
  → _build_chip_dimension(chip_sig, tags=_deep_tags)
  → dimensions['chip']

dim4引擎路径（9维灯）:
  pre_feat_cache → StatusEngine → dim_adapter
  → dims['chip_fund']
  → status_verdict['dim_states']
```

**影响**：400 号方案的 F-01~F-03 修复仅通过 dim4 引擎路径到达前端 9 维灯，7 维卡片的筹码数据仍走旧路径。

**评估**：这是架构层面的遗留问题，非本次修复范围。建议在后续统一数据源时处理。
