## 1. 页面结构概览

AI多角色投研页面提供 **6位独立专业分析师并行研判** 的能力。每位分析师拥有自己的System Prompt和结构化数据源，输出各自专业领域的研判报告（数据卡片+分段叙事报告）。当前为 **Phase 0纯原型阶段**，所有数据为硬编码Mock。详见 [#166 §8.1](./166-前端UI原型逐页调整记录.md#81-页面定位)。

### 1.1 区块布局

| 序号 | 区块名称 | DOM | 展示方式 | 数据状态 |
|:----:|:---------|:----|:---------|:---------|

### 1.3 Phase 0 → Phase 1 → Phase 2 架构演进

```

  │   ├─ 6角色定义(ROLES)         → hardcoded 6项
  │   ├─ Mock数据(MOCK_REPORTS)    → 6角色 × structured[6] + report + sources[3]
  │   ├─ 综合决策(SYNTHESIS)       → consensus[3] + conflicts[2] + overall
  │   ├─ 进度模拟(simulateProgress) → setTimeout模拟
  │   ├─ 辩论按钮                  → alert('Phase 2实现')
  │   └─ 导出按钮                  → alert('后续版本实现')
  └─ 完全不依赖后端API

Phase 1（待建设·6角色专业研判）
  ┌─ 前端改造
  │   ├─ 移除setTimeout → 接入真实进度轮询
  │   ├─ 移除MOCK_REPORTS → 从API获取analysis_report
  │   ├─ 移除SYNTHESIS → 从API获取final-report
  │   └─ 保留辩论/导出按钮(占位→Phase 2)
  └─ 后端增强
      ├─ POST /api/v3/ai/analyze → 6角色并行(ThreadPoolExecutor)
      ├─ GET /api/v3/ai/analyst-progress → 6角色独立进度
      ├─ GET /api/v3/ai/analysts → 6角色列表(替换旧5角色)
      └─ GET /api/v3/ai/final-report → 综合方向+6份analysis_report

Phase 2（待建设·辩论+综合决策）
  ┌─ 前端新增
  │   ├─ 辩论模式UI（双轮对抗+中立评估+最终裁决）
  │   └─ 报告导出（PDF/图片）
  └─ 后端新增
      ├─ POST /api/v3/ai/debate → 启动辩论
      ├─ GET /api/v3/ai/debate/progress/<id>
      ├─ GET /api/v3/ai/debate/result/<id>
```

### 2.2 A1: POST /api/v3/ai/analyze — 启动6角色并行分析

#### 当前状态

现有端点 `POST /api/v3/ai/analyze` 已存在但输出旧5角色格式：
```json
{
  "task_id": "xxx",
  "roles": ["technical", "fundamental", "macro", "fund_manager", "risk"],
  "analysis_report": { "technical": "旧narrative文本", ... }
}
```
输出字段为 `narrative`（纯文本），缺少 `structured_data` 和 `sources`。角色数5个（含旧macro和fund_manager）。

#### Phase 1 增强规格

**请求：**
```json
{
  "ts_code": "000762.SZ",
  "roles": ["technical", "fundamental", "chip", "sentiment", "news", "risk"]
}
```
- `ts_code` — 股票代码（必填）
- `roles` — 可选，默认全部6角色。允许子集（如只分析technical+chip）

**响应：**
```json
{
  "success": true,
  "data": {
    "task_id": "ai_task_20260630_001",
    "total_roles": 6,
    "status": "running",
    "created_at": "2026-06-30T10:30:00+08:00"
  }
}
```

**后端处理流程：**
```
POST /api/v3/ai/analyze
  ├→ 1. 校验: ts_code合法性(必须上市状态)
  ├→ 2. 创建 task_id + 写入 _analysis_store
  ├→ 3. ThreadPoolExecutor(max_workers=3) 并行调度6角色
  │   ├→ 每个角色: _build_structured_input(ts_code, role_id)
  │   │   ├→ 查询对应数据源（Tushare/chip/moneyflow/nlp等）
  │   │   └→ 组装为DeepSeek可接收的JSON input
  │   ├→ 调用DeepSeek API（每个角色有独立System Prompt）
  │   │   └→ System Prompt 详见194号§3.3
  │   └→ 解析LLM输出 → analysis_report + structured_data + sources
  ├→ 4. 写入 _analysis_store[task_id]
  └→ 5. 返回 task_id
```

**_analysis_store 内存数据结构：**
```json
{
  "ai_task_20260630_001": {
    "ts_code": "000762.SZ",
    "status": "running",      // running / completed / partial_failed
    "progress": 0.5,          // 0.0 ~ 1.0
    "created_at": "2026-06-30T10:30:00+08:00",
    "completed_at": null,
    "roles": {
      "technical": {
        "status": "completed",  // pending / running / completed / failed
        "analysis_report": "【走势结构判定】...",
        "structured_data": { "direction": "up", "zhongshu_range": [2950, 3100], ... },
        "sources": [{ "type": "strategy", "source": "chanlun_strategy.py", "data_item": "上升笔+中枢" }]
      },
      "fundamental": { ... },
      "chip": { ... },
      "sentiment": { ... },

    }
  }
}
```

**Phase 1 增强：** 6角色独立进度

```
GET /api/v3/ai/analyst-progress?task_id=ai_task_20260630_001
```

```json
{
  "success": true,
  "data": {
    "task_id": "ai_task_20260630_001",
    "status": "running",           // running / completed / failed
    "progress": 0.5,               // 0.0 ~ 1.0（整体进度）
    "roles": {
      "technical":   { "status": "completed", "progress": 1.0 },
      "fundamental": { "status": "completed", "progress": 1.0 },
      "chip":        { "status": "running",   "progress": 0.6 },
      "sentiment":   { "status": "running",   "progress": 0.3 },
      "news":        { "status": "pending",   "progress": 0.0 },
      "risk":        { "status": "pending",   "progress": 0.0 }
    }
  }
}
```

**前端轮询逻辑：**
```javascript
// Phase 1 替换 setTimeout simulateProgress()
function pollProgress(taskId) {
  var interval = setInterval(function() {
    fetch(`/api/v3/ai/analyst-progress?task_id=${taskId}`)
      .then(r => r.json())
      .then(data => {
        updateRoleStrip(data.data.roles);     // 更新角色条状态
        updateProgressBar(data.data.progress); // 更新百分比
        data.data.roles.forEach(function(r) {
          if (r.status === 'completed' && !r.rendered) {
            // 角色完成，报告立即可读
            r.rendered = true;
          }
        });
        if (data.data.status === 'completed') {
          clearInterval(interval);
          fetchFinalReport(taskId);            // 获取综合报告
        }
      });
  }, 1000);
}
```

## 5. 缓存策略

| 端点 | 缓存Key | TTL | 策略 | 备注 |
|:-----|:--------|:----|:-----|:------|
| `GET /ai/analysts` | `ai:analysts:v1` | 24h | long TTL | 6角色固定，仅在系统升级时变更 |
| `GET /ai/analyst-progress` | — | 无 | 不缓存 | 实时进度，每次返回最新状态 |
| `GET /ai/final-report` | `ai:report:{task_id}` | task生命周期 | 按task写入 | 任务完成后长期驻留内存，新查询 = 新task |
| `POST /ai/analyze` | — | 无 | 不缓存 | 写操作+异步结果 |
| `POST /ai/rerun` | — | 无 | 不缓存 | 覆盖已有task结果 |
| `POST /ai/debate` | — | 无 | 不缓存 | 写操作 |
| `GET /ai/debate/progress/<id>` | — | 无 | 不缓存 | 实时进度 |
| `GET /ai/debate/result/<id>` | `ai:debate:{debate_id}` | debate生命周期 | 辩论完成后写入 | 一次辩论一结果 |
| `GET /ai/synthesis` | `ai:synthesis:{task_id}` | task生命周期 | 按task写入 | 同final-report |

**特殊规则：**
- `_analysis_store` 使用内存字典（当前实现），Phase 1需评估是否迁移至Redis
- 单次分析产生约15-30KB JSON数据（6角色×~3KB/角色 + 综合报告~5KB）
- 单次辩论产生约50-80KB数据（2轮辩论文本+裁决）
- 内存驻留时间：task完成后保留2小时（供用户反复切换Tab查看），超时自动清理
- 并发上限：建议 `_analysis_store` 支持同时运行最多10个task（30个角色并发≈3×10线程）

## 6. 错误处理矩阵

| 错误场景 | HTTP状态码 | business_code | severity | 前端行为 | 降级方案 |
|:---------|:----------|:--------------|:---------|:---------|:---------|
| ts_code不存在 | 400 | `INVALID_TS_CODE` | HIGH | 显示"股票代码不存在"提示，[开始分析]保持可用 | — |
| DeepSeek API不可达 | 502 | `DEEPSEEK_UNAVAILABLE` | CRITICAL | 显示"AI服务暂不可用"错误面板，建议稍后重试 | 全部fallback → 使用预置recent_report（最新一次成功的缓存） |
| 单角色DeepSeek调用超时 | 200（partial） | `ROLE_TIMEOUT` | MEDIUM | 该角色显示"分析超时，可重试该角色" | 其余5角色正常展示，该角色显示[重新分析该角色]按钮 |
| 单角色数据源不可用 | 200（partial） | `DATA_SOURCE_UNAVAILABLE` | MEDIUM | 该角色数据卡片显示"--"，报告描述中标注缺失数据项 | 其余数据源正常，该角色以空输入调用DeepSeek |
| 全部5/6角色失败 | 200 | `MASSIVE_FAILURE` | HIGH | 显示"分析失败，请稍后重试" | 彻底失败 → 提示检查数据连接+DeepSeek配置 |
| task_id不合法（过期/不存在） | 404 | `TASK_NOT_FOUND` | MEDIUM | 显示"分析结果已过期，请重新分析" | — |
| debate_id不合法 | 404 | `DEBATE_NOT_FOUND` | MEDIUM | 显示"辩论结果不存在" | — |
| 并发超限（>10个同时task） | 429 | `TOO_MANY_TASKS` | LOW | 显示"当前分析任务过多，请稍后重试" | — |

**DeepSeek LLM调用超时配置：**
- 每角色超时: 30s
- 总轮询超时: 180s（6角色全部完成）
- 若个别角色超时: 标记为 `status: "timeout"`，progress字段推进至0.9但不等于1.0
- 重试机制: 最多3次重试（指数退避：5s → 15s → 45s）

## 7. 已知差异（Discrepancies）

### D1: 后端旧5角色格式 vs 原型6角色格式 [P0]

| 项目 | 当前后端 | 原型要求 |
|:-----|:---------|:---------|
| 角色数 | 5（含旧macro+fund_manager） | 6（technical/fundamental/chip/sentiment/news/risk） |
| 输出格式 | `narrative`纯文本 | `analysis_report`+`structured_data`+`sources`三元组 |
| 综合输出 | `overallRating`/`targetPriceRange` | `synthesis`对象（consensus/conflicts/scenarios/position） |
| 进度接口 | 旧格式 | 6角色独立状态+progress% |

**优先级：** P0 — Phase 1核心任务，所有5→6角色升级

### D2: 进度模拟setTimeout [P1]

原型使用 `setTimeout` 模拟3秒顺序分析（300-700ms/角色）。Phase 1需替换为 `POST /analyze` → 轮询 `analyst-progress`（1秒间隔）。争议：若后端处理时间 > 3秒，是否需要前端先显示缓存动画再展示真实进度。

**优先级：** P1 — Phase 1时替换，后端需配合进度接口

### D3: 辩论按钮占位 [P2]

原型L169: `alert('🗣️ 辩论模式将在Phase 2实现。当前为Phase 0原型阶段。')`

辩论是AI多角色投研的核心差异化功能，包含双轮对抗+中立评估+综合裁决。当前完全没有后端支持。

**优先级：** P2 — Phase 2核心，前端UI+后端全量实现

### D4: 导出报告占位 [P2]

原型L170: `alert('📋 报告导出将在后续版本实现。')`

需要实现6角色报告+综合决策→PDF/PNG导出。当前无任何实现。

**优先级：** P2 — 低优先级

### D5: MOCK_REPORTS全部硬编码 [P0]

`MOCK_REPORTS`对象（L192-264）包含6角色×结构化6项+报告400-800字+3条来源的全部Mock数据。这是页面的核心Mock体量。Phase 1全部替换为从 `GET /api/v3/ai/final-report`获取。

**优先级：** P0 — Phase 1核心

### D6: SYNTHESIS全部硬编码 [P0]

`SYNTHESIS`对象（L266-277）包含consensus[3]+conflicts[2]+overall。情景推演（3个场景卡片）也在 `showSynthesis()` 中硬编码（L504-506）。

**优先级：** P0 — Phase 1核心

### D7: 模型标DeepSeek v4-flash静态 [P1]

原型L137: `<span class="model-badge">模型: DeepSeek v4-flash</span>`

当前为静态字符串。建议Phase 1从 `GET /api/v3/ai/health` 的 `models` 字段获取当前模型并动态渲染。

**优先级：** P1

### D8: 股票选择仅4只Mock [P1]

原型L133-134: `<select>` 仅4个option硬编码（西藏矿业/平安银行/贵州茅台/宁德时代）。

当前 `GET /api/v3/chart/stock-list` 已有后端端点。Phase 1需替换为真实下拉搜索（借鉴watchlist搜索逻辑）。

**优先级：** P1

### D9: arbitrate + uidf/consolidate 代码就绪路由未挂载 [P1]

#171号§2.5.2标注：
- `POST /api/v3/ai/arbitrate` — 代码已编码⏳路由待挂载（用于验证链冲突AI仲裁）
- `POST /api/v3/uidf/consolidate` — 代码已编码⏳路由待挂载（用于三级决策模式融合）

这两个端点与indicator-ide页面的status-interpret V2流水线相关，但与ai-analysis页面的6角色研判是不同能力线。**建议Phase 1时挂载这两个路由**，使indicator-ide的策略分析增强同时受益。

**优先级：** P1
