## 一、背景与问题

**313 号 §4.2「第三层：IC 加权」的设计意图**（方案原文 `313-….md:121`）：

> 维度权重 wᵢ ∝ ICᵢ（该维度对后续 10/20 日收益的截面相关性，滚动月度重估）

即：每隔一段时间，用历史截面数据计算各维度 IC（信息系数，衡量「该维度打分对后续收益的预测力」），据此重估维度权重并落盘，使潜力评分随市场风格变化自适应。

**问题**：这一层**从未运行过**——

- `recompute_ic_weights`（重算）与 `save_ic_weights`（落盘）**全仓零调用点**；
- `data/ic_weights.json`（97 B，**2026-08-04** 创建）是**静态快照**，内容即 `DIM_WEIGHTS` 初始值（val 0.2 / earn 0.15 / sector 0.15 / event 0.1 / fund 0.2 / trend 0.2），之后从未被写侧更新；
- 读侧链路是活的：`data_daemon.py:6368` 启动时注入 `IC_WEIGHTS_FILE`，`PotentialEngine.__init__`（`potential_engine.py:86`）构造时 `load_ic_weights()` 读取并用于潜力评分加权。

**后果**：维度权重永远是出厂值，市场风格变化（价值/成长轮动、资金因子强弱切换）不会反映到评分权重上。属 313 号方案的**既定设计欠账**，非缺陷但长期隐性。

**前置已就绪**：431 批次15（§019）已把 `recompute_ic_weights` 内 7 处查询从总库连接改为分库路由（daily/daily_basic/moneyflow/fina_indicator 四张分库表，实测行数 daily 641 万 / daily_basic 92 万 / moneyflow 21 万 / fina 2.2 万），写侧计算的数据可达性问题已消除。

**v1.1 关键判断**：查询路由只是「数据可达」前提；**「数据可用 + 口径正确」仍缺审计**——`recompute_ic_weights` 的计算对象与评分实际信号存在错配（见 §二 F6-F8），若直接接写侧并自动化，会把错误口径的 IC 升级为主动覆盖权重的机制，**比不做更糟**。故本号实施以 **批次 0 审计**为强制前置。

**口径定稿（4 条）**：

1. **val / trend**：暂停 IC 重估，权重保持配置值（0.20 / 0.20）。**长线方向**：为 `treemap_snapshot` 建立**历史快照留存**（每日落一份 valuation_deviation / trend_alignment 截面），积累 ≥6 个月后直接用评分信号本身算 IC（唯一正确路径）。该留存机制另列建议（见 §四 批次 5）。
2. **earn**：保留重估，但批次 1 须改数据口径——每只取**最新 end_date 的 roe**（单值），并用「end_date + 披露滞后（Q1≤4 月底 / 半年报≤8 月底 / Q3≤10 月底 / 年报≤次年 4 月底）」做截面日可得性近似。
3. **fund**：暂停重估（等待 moneyflow 积累），启动条件 = 覆盖 ≥60 交易日（≈3 截面）且 ≥3 个有效截面。
4. **`recompute_ic_weights` 现状影响**：当前 4 维重算中 3 维（val/trend/fund）不成立 → **批次 1 须按「earn-only」重构重算逻辑**（val/trend/fund 跳过、权重映射只在 earn 维度生效，或整体降级为「earn 监控 + 保留配置权重」——二选一，批次 1 定稿）。**313 第三层「全维度 IC 驱动」在当前数据条件下不可达成**，本号目标修订为「有限维（earn）自适应 + 全维监控」。

## 三、方案设计

### 3.1 频率与触发时点

- **频率**：月度（313 §4.2「滚动月度重估」）。
- **触发时点**：建议**月末最后一个交易日收盘后**（日终采集完成之后），避开盘中采集/日终同步窗口，避免与 daemon 写库争锁。
- **窗口判断**：月度重估前先查 `daily_cache` 最新 `trade_date`；若当月最后交易日数据尚未落库（盘后未发布），顺延至次月首个可算窗口——宁晚勿错。
- **v1.1 补充（口径纪律）**：① 窗口判断**必须用交易日口径**（`daily_cache` MAX(trade_date)，可复用 432 号 R3 `_lag_trading_days()`），**不要用自然日「月末」**；② 数据齐备判断**不要用「最新日期 == 今天」**——Tushare 日线盘后 18:00 才发布，432 号 R4（`_is_today_data_ready`）刚修过此坑，月度钩子须沿用同一纪律。

### 3.2 承载面评估（实施批次前定稿）

候选挂载点（2026-09-14 初查）：

| 候选 | 位置 | 性质 | 适配度 |
|:--:|---|---|:--:|
| A | `data_daemon.py` 主循环/日终流程挂「月初检查」钩子 | 7x24 常驻采集进程，**唯一写者** | **推荐**（431 原判同向）：数据写侧唯一权威，不依赖 Web 应用常驻 |
| B | `app/scheduler_manager.py`（APScheduler 总管理器，932 行） | **应用侧**调度，Flask 启动时初始化 | 次选：仅当 Web 应用长期常驻时可靠；若系统以 daemon 为数据主链路，应用可能不常驻 → 不可靠 |
| C | `app/scheduler.py` | 应用侧调度器 | 同 B |
| D | `app/services/rule_scheduler.py`（307 行） | 规则条件评估调度（盘中扫描/日终批量/休眠检查） | **不适配**：职责是规则评估，与 IC 重估无交集 |

> 定稿原则：重估作业必须与「数据写者」同生命周期（数据齐了才算、算完落盘），故优先 A；若后续部署形态（云主机 7x24）确认应用常驻，可改挂 B。**最终挂载点与 job 注册方式在 433 实施批次 1 定稿**。

**v1.1 补充（承载面纪律）**：

1. **轻钩子原则**：月度钩子只做「判断是否本月已算 + 数据是否齐备 + 触发」，**全市场截面计算（分钟级重活）放独立函数/子进程，不得阻塞 daemon 主循环/采集**。
2. **幂等与重入**：432 号已出现双 daemon 抢写锁教训——落盘必须**原子写**（tmp 文件 + `os.replace`），且 json 内带 **`last_recalc` 时间戳**（或独立 state 文件）作为「本月已算」标记，防止守护重启双实例重复落盘。
3. **云部署适配**（deployment-plan：将来 daemon 迁 systemd）：钩子逻辑做成**纯函数 + 状态文件**，不依赖 daemon 内部状态，迁移时仅换启动器、业务代码零改动。

### 3.3 执行流程与失败语义

```
月度触发 → 检查 daily_cache 最新交易日（当月末交易日已落库？）（交易日口径）
        → 检查 last_recalc 标记（本月已算？→ 跳过）
        → recompute_ic_weights(ecm, lookback_days=180, horizon=20)
        → 结果非 DIM_WEIGHTS 兜底值 → save_ic_weights(new_w)（原子写 + last_recalc 时间戳）
        → 落盘后日志：IC 重估完成 {ic_mean} → {new_w} + 写 ic_report.json
失败语义：
  - 重算异常：recompute_ic_weights 内部已 except → 返回 DIM_WEIGHTS 兜底
    → 作业层检测到「返回值 == 兜底」时**不落盘**（保留旧权重）+ logger.warning 告警
  - 落盘异常：save_ic_weights 内部已 except → logger.warning
    → 下次月度窗口重试，不阻塞其他流程
```

**关键约束**：**绝不能用兜底值覆盖 `ic_weights.json`**——重估失败时应保留上一版有效权重，而不是写回初始值（否则一次失败就让读侧失去历史自适应成果）。

**v1.1 补充（返回语义区分）**：`recompute_ic_weights` 目前三种路径（数据不足 / 合法无正 IC / 异常）均返回 `DIM_WEIGHTS`（F10），作业层无法区分。**批次 1 须先改造返回结构**（携带 `status` 诊断字段：`insufficient_data` / `no_positive_ic` / `error` / `ok`）——「合法无正 IC」应记 info 日志并保留旧权重（不算失败、不告警），仅「异常」与「数据不足」告警。**本约束在批次 1 落地，批次 2 起作业层按 status 分支**。

### 3.4 上线前验证（实施批次 2）

1. 手工以真实分库数据调用 `recompute_ic_weights` 一次（`backend/scripts/` 一次性脚本），确认：IC 结果非退化（各维 IC 与预期量级相符）、`save_ic_weights` 落盘格式正确（6 键齐全、归一化合计 1.0）。
2. 观察新权重对 `PotentialEngine` 评分的影响面（对比新旧权重下同一标的的 `signal_strength` 变化），确认无异常放大。
3. 月度窗口判断逻辑用模拟日期测试（当月末未落库 → 顺延分支）。

**v1.1 补充（验证扩容）**：

4. **耗时实测**：记录全量重算耗时（F11 性能风险）——若 >3 分钟，批次 1 须先做 SQL 优化（一次性拉窗口数据内存切片 / daily_cache 补 `(ts_code, trade_date)` 索引）再继续。
5. **无前视审计**：对批次 0 定稿后的口径，逐一核对每个截面日「当时可得」的数据源（roe 按 `ann_date <= 截面日`、fund 按 `trade_date <= 截面日`、pe/momentum 无未来引用）——**前视偏差是量化系统的静默杀手，必须显式审计**。
6. **回看验证（质量门禁）**：用历史截面对比「新旧权重」下的 IC 均值 / 排名稳定性，作为「权重真的变好了」的证据（产品视角验收依据）。

### 3.5 可观测性（新增，v1.1）

落盘 `ic_weights.json` 只有 6 个数字，无法回答「这个月为什么 val 从 0.2 变 0.15」。**每次重估并行写 `ic_report.json`**（与 `ic_weights.json` 同目录）：

```
{
  "recalc_at": "2026-09-30T18:30:00",
  "window": {"start": "...", "end": "...", "n_sections": 6, "n_stocks_per_section": 5200},
  "ic": {"val": {"mean": 0.031, "std": 0.02, "n_sections": 6, "samples": 31000},
         "trend": {...}, "fund": {...}, "earn": {...}},
  "status": "ok",
  "old_weights": {...}, "new_weights": {...}
}
```
