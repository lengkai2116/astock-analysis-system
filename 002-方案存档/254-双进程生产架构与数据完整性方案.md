# 双进程生产架构与数据完整性方案

## 一、架构总览

```
┌─ start.command ────────────────────────────────────────────────┐
│  1. 检查是否已运行 → 2. 启动数据进程 → 3. 启动 API 进程 → 4. 打开浏览器  │
└──────────────┬──────────────────────────────┬──────────────────┘
               │                              │
               ▼                              ▼
┌────────────────────────┐    ┌────────────────────────────────┐
│ data_daemon.py          │    │ run.py (保持不变)               │
│ 数据进程                 │    │ API 进程                        │
│ 无 Flask/无 SocketIO    │    │ Flask + eventlet               │
│ 纯 Python 轻量守护       │    │ 端口 5001                      │
│                          │    │                                │
│ 盘中: mootdx 5s 采集     │    │ REST API: 所有前端请求          │
│ 盘后: 日终同步(批量API)   │    │ SocketIO: 实时推送             │
│ 空闲: 完整性检查+补采     │    │ 只读 ECM + InMemoryStateStore │
│                          │    │                                │
│ 写入: ECM SQLite         │    │ 用户操作产生的数据 → PostgreSQL │
│       InMemoryStateStore │    │                                │
└──────────────────────────┘    └────────────────────────────────┘
         │                                   ↑
         │        共享 ECM SQLite (WAL)       │
         └───────────────────────────────────┘
```

### 1.1 进程职责边界

| 维度 | API 进程 (run.py) | 数据进程 (data_daemon.py) |
|------|------------------|-------------------------|
| 对外端口 | :5001（用户访问） | 无（内部） |
| 框架 | Flask + SocketIO + eventlet | 纯 Python，零框架 |
| 数据库访问 | 只读 ECM + PG（用户数据） | 读写 ECM |
| 启动时间 | ~3s | ~5s（含 mootdx 初始化） |
| 重启影响 | 前端断连，恢复后立即可用 | 实时数据暂停，缓存数据可用 |

## 二、数据完整性检查与补采机制

### 2.1 设计原则

1. **启动时必检** — 每次 data_daemon 启动，自动检查并补采缺失数据
2. **定时巡检** — 非交易时段每小时巡检一次
3. **分级补采** — 日报表用批量 API（秒级），财务数据用逐只（按需）
4. **不重复劳动** — 已有数据不重采

### 2.2 启动完整性检查 (startup integrity check)

`data_daemon` 启动后按以下顺序执行：

```
Step 1: 检查今日日线完整性  ─── 缺失? ─→  pro.daily(trade_date=今日)     → 0.2s
Step 2: 检查今日基本面完整性 ─── 缺失? ─→  pro.daily_basic(trade_date=今)  → 0.2s
Step 3: 检查今日资金流向 ──── 缺失? ─→  pro.moneyflow(trade_date=今日)    → 0.3s
Step 4: 检查今日涨跌停 ──── 缺失? ─→  pro.stk_limit(trade_date=今日)     → 0.3s
Step 5: 检查最近交易日完整 ─── 缺失? ─→  逐日补采（最多补5天）           → ~2s/天
Step 6: 检查财务数据时效 ──── 过期? ─→  (仅每月1日触发)

总耗时：约 1-5 秒（大部分数据已存在，跳过）
```

### 2.3 每项检查的判定标准

```
日线完整性:
  SELECT COUNT(*) FROM daily_cache WHERE trade_date = 'YYYY-MM-DD'
  → 如果 < 5000 行 → 认为缺失 → 触发 pro.daily(trade_date=...)

基本面完整性:
  SELECT COUNT(*) FROM daily_basic_cache WHERE trade_date = 'YYYY-MM-DD'
  → 如果 < 5000 行 → 缺失 → pro.daily_basic(trade_date=...)

资金流向完整性:
  SELECT COUNT(*) FROM moneyflow_cache WHERE trade_date = 'YYYY-MM-DD'
  → 如果 < 1000 行 → 缺失 → pro.moneyflow(trade_date=...)

复权因子完整性:  // 复权因子很少变化，只在启动时检测最近5天
  SELECT COUNT(*) FROM adj_factor_cache WHERE trade_date >= 'YYYY-MM-DD' - 5
  → 如果 < 5000 行(合计) → 缺失 → 补采过去5天

涨跌停/龙虎榜: (非关键数据)
  SELECT COUNT(*) FROM stk_limit_cache WHERE trade_date = 'YYYY-MM-DD'
  → 如果 = 0 行 → 缺失 → pro.stk_limit(trade_date=...)
```

### 2.4 定时巡检 (hourly patrol)

```
非交易时段每整点执行:
  if 今日是交易日:
    if 今日日线 < 5000 行:
      补采 pro.daily(trade_date=今日)        ← 0.2s
    if 今日基本面 < 5000 行:
      补采 pro.daily_basic(trade_date=今日)   ← 0.2s
    if 今日资金流向 < 1000 行:
      补采 pro.moneyflow(trade_date=今日)     ← 0.3s
  if 指标预计算未完成:
    触发预计算 (30 分钟后台跑)
```

### 2.5 首次部署/全量重建

首次部署或数据目录丢失时的全量重建流程：

```
1. pro.daily(trade_date=最近交易日)  → 5500行    0.2s
2. 逐日回退补采（从最近交易日到最早）
   每次 pro.daily(trade_date=前一日)              0.2s/天
   1210 个交易日 × 0.2s = 242s ≈ 4 分钟

3. pro.daily_basic(trade_date=最近交易日)         0.2s
4. 逐日回退（同上）≈ 4 分钟

5. 财务数据（逐只，非紧急）→ 后台慢慢跑，不影响使用
```

## 三、data_daemon.py 内部调度逻辑

### 3.1 整体结构

```
data_daemon.py
│
├─ main loop (事件驱动 + 定时器)
│   │
│   ├─ 盘中模式 (9:00-15:30)
│   │   ├─ mootdx 采集线程 (5s 固定间隔)
│   │   ├─ 实时写入 InMemoryStateStore + ECM minute_kline_cache
│   │   └─ 从快照自算涨跌榜/板块排行
│   │
│   ├─ 启动检查 (进程启动时只执行一次)
│   │   └─ 完整性检查 → 缺失数据批量补采
│   │
│   ├─ 日终同步 (15:30 触发)
│   │   ├─ 批量 API 采集 5 类数据 (总耗时 <2s)
│   │   ├─ 触发指标预计算 (后台线程, 20-30min)
│   │   └─ 发送完成信号 (写入 cache_metadata)
│   │
│   ├─ 定时巡检 (每整点,非交易时段)
│   │   └─ 数据完整性检查 → 补采
│   │
│   └─ 月/季任务
│       ├─ 每月1日: 复权因子全量刷新
│       ├─ 每季度初: 财务数据同步
│       └─ 每月15日: 概念/指数成分刷新
```

### 3.2 调度时序图

```
时间轴       data_daemon 行为
────────────────────────────────────────────────────────
09:00        mootdx 采集线程启动 (5s周期)
09:30        开盘 → 采集数据写入 InMemoryStore + ECM
            ...
15:00        收盘
15:30        触发日终同步
             ├─ pro.daily(trade_date=2026-07-07)     → 0.2s
             ├─ pro.daily_basic(...)                  → 0.2s
             ├─ pro.moneyflow(...)                    → 0.3s
             ├─ pro.stk_limit(...)                    → 0.3s
             ├─ pro.top_list(...)                     → 0.3s
             └─ 触发指标预计算 (后台)                 → ~20min
16:00        定时巡检 → 检查今日数据完整性 → 全部OK
17:00        定时巡检 → 检查今日数据完整性 → 全部OK
            ...
次日 09:00   mootdx 重新启动采集
```

### 3.3 内部状态管理

```python
# data_daemon 内部状态（非数据库）
state = {
    'mootdx_connected': False,      # mootdx TCP 连接状态
    'initial_snapshot_ts': None,     # 首次快照完成时间
    'last_daily_sync_date': None,    # 最近日终同步日期
    'today_sync_completed': False,   # 今日同步是否完成
    'precompute_running': False,     # 预计算是否正在运行
    'patrol_last_run': None,         # 最近巡检时间
}
```

### 3.4 关键设计决策

**为什么不用 APScheduler？**
- data_daemon 是轻量进程，APScheduler 是 Flask 插件的重型框架
- 用 Python 标准库 `threading.Timer` + 简单循环即可
- 避免 APScheduler 的 `str vs datetime.date` 兼容 bug

**为什么 data_daemon 不需要 Flask？**
- 数据采集不需要 HTTP 服务
- ECM 操作是本地 SQLite，无需 web 框架
- 节省约 300MB 内存（Flask + SocketIO + 蓝图 + ORM）

## 四、start.command 编排脚本

### 4.1 启动逻辑

```bash
start.command
│
├─ 1. 检查端口 :5001 是否已监听（API 进程）
│   ├─ 是 → 打开浏览器直接返回（已在运行）
│   └─ 否 → 继续
│
├─ 2. 检查 ECM 数据库是否有当日数据
│   ├─ sqlite3 stock_cache.db "SELECT COUNT(*) FROM daily_cache WHERE trade_date='今日'"
│   ├─ 有数据(>5000) → 说明数据进程之前已运行过
│   │   └─ 跳过启动数据进程，直接 goto Step 4
│   └─ 无数据 → 继续
│
├─ 3. 启动 data_daemon.py (后台)
│   ├─ data_daemon 启动后自动做完整性检查
│   └─ 等待 mootdx 首次快照采集完成（检查 ECM minute_kline_cache 有今日数据）
│       └─ 超时 30s → 报错退出
│
├─ 4. 启动 run.py --port 5001 (后台)
│
├─ 5. 等待 API 进程就绪
│   ├─ 轮询 /api/v3/health/live (:5001)
│   ├─ 超时 15s → 报错退出
│   └─ 就绪 → 继续
│
└─ 6. 打开浏览器 http://localhost:5001/dashboard
```

### 4.2 停止逻辑

```bash
stop.command
│
├─ kill $(lsof -ti :5001)    # 停 API 进程
├─ kill $(lsof -ti :5002)    # 停数据进程
└─ echo "服务已停止"
```

### 4.3 进程健康检查

API 进程使用已有 `/api/v3/health/live` 端点（:5001）。

数据进程**不开启 HTTP 端口**，健康状态直接通过 ECM 数据库判定：

```bash
# 3 个指标判断数据进程是否正常工作
sqlite3 "$ECM_DB" "
  SELECT 'today_data', COUNT(*) FROM daily_cache WHERE trade_date='$(date +%Y-%m-%d)'
  UNION ALL
  SELECT 'minute_kline', COUNT(*) FROM minute_kline_cache WHERE trade_date='$(date +%Y-%m-%d)'
  UNION ALL
  SELECT 'mootdx_active', COUNT(*) FROM minute_kline_cache
  WHERE trade_time > datetime('now', '-5 minutes');
"
# → today_data > 0 且 minute_kline > 0 且 mootdx_active > 0 → 数据进程正常
```

## 五、前端数据自动推送机制

### 5.1 设计目标

所有面向用户的界面——仪表盘、自选监控、账户管理等——数据变更后**主动推送到前端**，用户无需手动刷新。

### 5.2 推送架构

> ⚠️ 关键设计：mootdx 采集在数据进程，但 SocketIO 在 API 进程。
> **不做跨进程推送通道。** 前端通过定时轮询 REST API 实现准实时更新，SocketIO 推送作为锦上添花的增强手段。

```
数据进程 (data_daemon)
  └─ mootdx 5s → 写入 ECM + InMemoryStateStore
       (API 进程通过 SQLite 读到最新数据)

API 进程 (run.py) 内部:
  ┌─ WsBridge (每 5s/15s 轮询 InMemoryStateStore) ──────┐
  │  ├─ 检测到指数数据变化 → socketio.emit('market:indices') │
  │  ├─ 检测到涨跌榜变化  → socketio.emit('market:top_stocks')│
  │  └─ 检测到板块变化    → socketio.emit('market:sectors')   │
  └──────────────────────────────────────────────────────┘
                   ↓ SocketIO WebSocket
              浏览器前端
              ┌─ 仪表盘: 指数/涨跌榜/板块实时更新
              ├─ 自选监控: 个股行情自动刷新
              └─ 账户管理: 持仓市值自动更新
```

### 5.3 分层刷新策略

```
┌─ 第一层：SocketIO 实时推送 ──────────────────────────┐
│  适用于：频繁变化的数据                                │
│                                                       │
│  指数行情       → 变化即推（mootdx 每5秒采集）          │
│  涨跌榜         → 变化即推（同上）                     │
│  板块排行       → 每30秒推送一次                       │
│  个股实时行情    → 订阅模式（前端请求 ts_code 后推送）   │
└───────────────────────────────────────────────────────┘

┌─ 第二层：定时轮询 (setInterval) ────────────────────┐
│  适用于：变化频率低但需要自动更新的数据                 │
│                                                       │
│  资金流向       → 每5分钟轮询一次                      │
│  板块资金流向    → 每5分钟轮询一次                      │
│  AI 雷达/信号   → 每15分钟轮询一次（策略计算开销大）   │
│  账户持仓/盈亏  → 每30秒轮询一次（常驻页面时）         │
└───────────────────────────────────────────────────────┘

┌─ 第三层：事件驱动重载 ──────────────────────────────┐
│  适用于：用户操作后立即更新的数据                       │
│                                                       │
│  用户登录/登出  → 立即刷新                             │
│  用户提交订单   → 立即刷新持仓                          │
│  日终同步完成   → SocketIO 推送通知 → 前端重载         │
└───────────────────────────────────────────────────────┘
```

### 5.4 现有 SocketIO 事件的复用

当前前端 `dashboard.html` 已定义 SocketIO 事件处理：

| SocketIO 事件 | 已实现 | 目前状态 |
|---------------|--------|---------|
| `market:indices` | ✅ 四大指数实时更新 | 需 WsBridge 激活 |
| `market:top_stocks` | ✅ 涨跌榜自动切换 | 需 WsBridge 激活 |
| `market:sectors` | ✅ 板块排行更新 | 需 WsBridge 激活 |
| `market:news` | ✅ 新闻推送预留 | 尚未使用 |

WsBridge 已经在 API 进程中存在（`backend/app/data/ws_bridge.py`），它的工作方式是每 5-15 秒检查 InMemoryStateStore 是否有新数据，有则通过 SocketIO 推送到前端。

**双进程下 WsBridge 仍然在 API 进程中运行**，从 ECM SQLite 读取数据后推送。数据进程的 mootdx 每分钟写入 ECM，WsBridge 检测到新数据后推送——这个延迟最多 15 秒，用户无感知。

### 5.5 前端代码改动原则

SocketIO 事件处理已在 `dashboard.html` 中存在，但大部分处于**被动接收状态**——需要数据推送才能触发更新。

在实施阶段需要补充：

1. 为未覆盖的页面（账户管理、自选监控等）添加 SocketIO 订阅逻辑
2. 对没有 SocketIO 支持的数据类型（资金流向、板块资金流向等），用 `setInterval` 加定时轮询
3. 所有定时器在页面隐藏时自动暂停（`IntersectionObserver` 或 `visibilitychange`），节省资源

## 七、已确认的决策

以下决策已在方案评审中确认：

| 决策 | 结论 | 原因 |
|------|------|------|
| 数据进程状态端口 | **不使用 :5002** | 直接用 ECM 数据库 SQL 查询判断状态，零网络开销 |
| 跨进程推送通道 | **不做** | 前端通过定时轮询 REST + SocketIO（API 进程内自检）实现自动更新 |
| 数据进程框架 | **零框架、无 HTTP** | 减少 300MB 内存，避免依赖冲突 |
| 前端自动更新 | **SocketIO + 定时轮询** | WsBridge 在 API 进程中运行，读取 ECM 后推送。无 SocketIO 覆盖的数据用 `setInterval` |
| API 进程代码 | **保持现有 run.py 不变** | 已验证 eventlet + socketio 稳定运行 |
| 前端刷新策略 | **三层：SocketIO 推送 / 定时轮询 / 事件驱动** | 见 §5.3 |
| 仪表盘/自选监控/账户管理 | **全部自动更新** | 用户无需手动刷新 |
