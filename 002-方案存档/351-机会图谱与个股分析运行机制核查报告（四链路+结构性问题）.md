# 351 — 机会图谱与个股策略分析运行机制核查报告

## 一、背景

用户发现兴齐眼药（300573.SZ）弹窗显示"回避"但 L4 共识率 100%，要求对机会图谱和个股策略分析的整体运行机制进行全面核查。

## 二、系统整体架构

### 2.1 四层数据流

```
数据生产层（data_daemon P1→P2→P3→P4→S1）
  ├─ P2: 6策略引擎 → strategy_signal_detail
  └─ P4: 50+标签引擎 → opportunity_tags_cache
            ├→ 判定引擎（StatusEngine L1 + arbiter P0-P7）
            ├→ 建议引擎（advice_builder 五维/L1九维）
            └→ 展示层（diagnose 弹窗 / analyze 个股页）
```

### 2.2 三套共识口径并存

| # | 口径 | 计算位置 | 维度/标签数 | 公式 | 消费方 |
|---|------|---------|-----------|------|--------|
| A | 标签投票 | cross_validate._compute_consensus() :801-891 | 12+标签 | 加权强度比 | arbiter P3/P6 门槛判定 |
| B | 五维推导 | advice_builder._dim_directions() + _consensus_from_dirs() | 5维 | 方向票计数比 | diagnose 回退路径（现不用于主路径） |
| C | L1九维 | StatusEngine._aggregate() :391-400 | 11维 | max(bull,bear)/(bull+bear) | **弹窗/个股页展示主路径** |

**矛盾**：口径 A（标签投票）和口径 C（L1九维）独立计算。arbiter 内部用 A 的 consensus_rate 做 P3/P6 门槛，展示层用 C 的 consensus_rate。两者可能不一致。

### 2.3 两个展示入口的数据流对比

#### 弹窗 diagnose() 全链路

```
diagnose(ts_code, tags)
  ├─ ① _evaluate_gate()                           → 估值/风险门禁
  ├─ ② _compute_consensus(tags, adjusted_votes)   → 口径A（标签投票）
  ├─ ③ arbitrate(tags, gate, consensus=A)         → P0-P7 → avoid/light/enter/wait
  ├─ ④ build_operation_advice(ts_code, _dims)     → 操作建议
  │      ⚠️ 未传 consensus/dirs → 内部用五维推导
  ├─ ⑤ _get_status_verdict(ts_code)              → StatusEngine → consensus_display（口径C）
  ├─ ⑥ _build_verdict(consensus_display, tags, final_state=④降级后state)
  │      └─ 若 arb=avoid → "🚫 回避：{reason}"
  └─ ⑦ 若 ④.state ≠ ③.state → ④覆盖③
```

#### 个股页 analyze() 全链路

```
analyze(ts_code)
  ├─ ① 策略信号读取（P2缓存 → 回退实时计算）
  ├─ ② 五维维度构造（_build_*_dimension × 5）
  ├─ ③ StatusEngine().evaluate(ts_code)            → L1九维
  ├─ ④ 构建 _l1_consensus + _l1_dirs（11维）
  ├─ ⑤ build_operation_advice(..., consensus=④, dirs=④)
  │      ✅ 显式传入 L1 九维
  ├─ ⑥ 第二次 StatusEngine().evaluate()            → status_verdict 展示
  └─ ⑦ 返回
```

#### 关键差异汇总

| 对比项 | 弹窗 diagnose | 个股页 analyze |
|--------|-------------|--------------|
| consensus 展示 | 口径C（L1九维） | 口径C（L1九维） |
| operation_advice 的 consensus | **五维推导**（回退） | **L1九维**（显式传入） |
| operation_advice 的 dirs | **5元素**（五维） | **11元素**（L1九维） |
| 仓位触发 | 5维中1维反向=0.3 | 11维中1维反向=0.3（更易触发） |
| confidence | 五维consensus_rate + conflict_items | L1九维consensus_rate + conflict_items |

## 三、兴齐眼药矛盾根因

### 3.1 数据追踪

```
P4 预计算:
  buy_sell_point = first_sell（缠论一卖）
  → _check_right_side_confirm(): first_sell → right_side_confirm = '否决'
  → arbitrate(tags): P0 否决 → opportunity_state = 'avoid'

L1 九维判定:
  structure = 上升（trend.direction='up'，卖点≠趋势反转）
  vp = 中性（交叉矩阵路径，不读volume_price_fit回退）
  其余 9 维 = 看多/中性
  → bull=7, bear=0, consensus_rate=100%

P0 否决:
  right_side_confirm='否决' → avoid（覆盖 consensus）
```

### 3.2 根因

**`right_side_confirm` 标签触发 P0 否决的判定因子不全部映射到 L1 九维的 11 个维度中**：

| 触发 P0 否决的标签 | L1 九维对应 | 是否参与共识投票 |
|-------------------|------------|----------------|
| `buy_sell_point=first_sell` | 无（structure 看 trend.direction，不看买卖点） | **否** |
| `volume_price_fit=diverging` | vp 维优先从 P2/交叉矩阵推导 | **可能不触发** |
| `pattern_signal 含"预跌"` | 无（event 维只读 catalyst_event） | **否** |

**结论**：P0 否决（标签级旁路）比 L1 共识（维度级投票）更灵敏，两者存在结构性信息差。

## 四、结构性问题清单

### P0：共识率 vs avoid 矛盾

- **现象**：consensus_rate=100% 但 opportunity_state=avoid
- **根因**：right_side_confirm 标签触发 P0 否决，但其判定因子不在 11 维中
- **影响面**：所有 right_side_confirm=否决 但 11 维无看空的股票

### P1：弹窗与个股页 operation_advice 用不同共识口径

- **现象**：弹窗用五维推导（5 dirs），个股页用 L1 九维（11 dirs）
- **根因**：diagnose() 调用 build_operation_advice 未传 consensus/dirs 参数
- **影响**：同一股票仓位可能不同（0.6 vs 0.3），confidence 不同

### P2：三套共识口径并存

- 口径 A（标签投票 12+标签加权）→ arbiter 内部用
- 口径 C（L1 九维 11维计数）→ 展示层用
- 两者可能不一致

### P3：七维画像与 L1 九维方向不一致

- 兴齐眼药：七维"趋势=出货🔴/资金=流出🔴" vs L1 "structure=上升🟢/chip_fund=中性🟡"
- 根因：七维画像用 P2 信号的 status_recognition（更细粒度），L1 用不同数据源

### 5.3 兴齐眼药矛盾在332-337中已有预设

332号§5.5 原文：
> "闸门2（right_side_confirm）→ 成为 L1'信号确认'维度核心输入；否决在 L2 仲裁表按 P0 级一票降级单独裁决——**不允许参与九维平均**（防被高潜力稀释）"

当前实现中 right_side_confirm 未纳入 L1 维度，仅由 arbiter P0 直接消费标签，导致 P0 否决与 L1 共识脱节——**这正是兴齐眼药"100%看多+回避"矛盾的根因**，332号已预见并给出解决方案。

### 5.4 需补齐的实施项

按332号S1→S2→S3渐进步骤，当前需补齐：

1. **S2 补齐**：right_side_confirm 纳入 L1 维度（信号确认维），但不参与九维平均计票（P0 级单独裁决）
2. **S2 补齐**：diagnose() 改为消费成品仓（status_snapshot），不再自行组装 consensus/verdict
3. **S2 补齐**：diagnose() 的 operation_advice 调用传入 L1 共识+dirs（与 analyze 对齐）
4. **S3 实施**：呈现层对齐（状态条/七维模板/verdict 由生产环节统一生成）
