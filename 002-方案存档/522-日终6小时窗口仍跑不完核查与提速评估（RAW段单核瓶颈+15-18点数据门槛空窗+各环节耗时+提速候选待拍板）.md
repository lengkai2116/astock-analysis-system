## 〇、结论摘要

**不是"6 小时被耗光了"，而是"能用的窗口只有约 3 小时"**——日终被一道 **18:00 数据门槛**挡在前面（15:00~18:00 空窗），而 RAW 预计算段本身要 **3h19m**。18:00 放行 → 关机（≈21:00）只有 ~3h < 3h19m ⇒ **跑不完是结构性必然**，RAW-3 首当其冲。质量/完成度本身没问题（10-14 全环节 100%、QA 27 项全过），**问题在吞吐，不在正确性**。

> **v1.1 profiling 修正（结论翻转）**：实测（只读）证明 **RAW-3 单股耗时 99.3% 耗在 `_batch_cache_factor_series` 的逐行建 record**（热点=`_normalize_trade_date` 逐行 `pd.to_datetime`，占该函数 98.5%），拆分为 **读 9ms / 算 4ms / 建 record 1974ms**；且 `factor_cache` **6670 万行**表明**每日把全市场每只股票整条历史序列重写一遍**。⇒ **瓶颈是算法冗余，不是并行度**；**多进程（原 A 档）不是首选**，首选 **E1（日期归一向量化）+ E2（只写增量/最新日）**（详见 §十）。

## 三、瓶颈定位：RAW 预计算段 + 基本单核（代码 + 运行态实证）

**① 时间维度**：RAW 三步是唯一慢段（10-14 合计 3h19m）；下游 SIG(50m)+JUD(15m) 为固定成本；采集 COL 仅 33m。

**② 并发维度（代码实证）**：
- RAW 三步提交到 `ThreadPoolExecutor(max_workers=3)`（`:6961`）——**每步 1 线程**，三步并行。
- **RAW-1 `_precompute_indicators`（`:7275`）是纯串行 `for code in codes` 循环**——无内部并行。
- **RAW-3 `_precompute_preset_combos`（`:3043`）同样是纯串行 `for code in codes` 循环**——无内部并行。
- 仅 RAW-2 内部 `ThreadPoolExecutor(max_workers=4)`（`:4587`）、SIG 内部 `max_workers=4`。
- 实测 `ps`：daemon **%CPU 117%**（三步并行）/**74.9%**（仅 RAW-3）⇒ **10 核机器只用约 0.75~1.2 核**（表层＝单线程 Python 逐股处理）。

**③ I/O 维度**：`sample` 于 SIG 段（07:53）栈顶排序＝`__psynch_cvwait` 67911（线程等 GIL/锁/空闲）／**`pread` 1432（SQLite 读盘）**／`_PyEval_EvalFrameDefault` 1132（Python 求值）⇒ SIG ≈ 一半磁盘 I/O、一半 Python CPU。每只股票各自 `get_cached_daily(code)`（分库往返数千次）。

**④ 10-15 比 10-14 更慢的成因**：三维度步骤（1+4+1 线程）抢同一个 GIL 核、互相拖慢，RAW-1 从 47m 拉长到 1h43m。

## 四、为什么"15:00~21:00 六小时"仍不够

- **硬门槛**：`data_daemon.py:6456` `_is_today_data_ready()` = `_is_market_day() and datetime.now().hour >= 18`——**硬等 Tushare 日线系（龙虎榜/指数等）18:00 后发布**，15:00~18:00 **不可用**（空窗 ≈3h）。
- **有效窗口**：18:00 放行 → 关机（≈21:00，与 10-14 同款跨夜分段）≈ **3h**。
- **结构性需求**：EOD 需 ≈ **5h**，其中 **RAW 单段就 3h19m**。
- ⇒ 3h < 3h19m，**跑不完是必然**；10-15 RAW-3 首当其冲（关机时 4581/5565）。

## 十、profiling 补充记录（v1.1，2026-10-16，全只读）

**目的**：量化 RAW 三步「读盘 vs 计算 vs 建 record」占比，验证"并行度不足"假设。

**① 实时采样（`sample 1165 8`，07:53＝SIG 段）**——栈顶排序：
`__psynch_cvwait` 67911（线程等 GIL/锁/空闲）／`pread` **1432**（SQLite 读盘 I/O）／`_PyEval_EvalFrameDefault` 1132（Python 求值）。

**② RAW-3 单股拆分（`/tmp` 探针，复用真实代码路径、写库换 no-op）**：

| 环节 | 单股耗时 | 占比 |
|---|---|---|
| READ `get_cached_daily` | **9.2 ms** | 0.5% |
| CALC（8 因子 `calculate_single_factor`） | **4.1 ms**（0.5ms/因子） | 0.2% |
| **RECBLD `_batch_cache_factor_series`（逐行建 record）** | **1973.9 ms**（246.7ms/因子） | **99.3%** |

> 写出行数 ≈ **25,240 行/只**（8 因子 × 全部历史交易日）。

**③ 热点函数（cProfile：单股 000001.SZ、单因子 QLIB_ROC_20、6001 行）**：
`_batch_cache_factor_series` = **1.064s**，其中 **`_normalize_trade_date` cumtime 1.048s（98.5%）**——**对每一行本已是 `YYYY-MM-DD` 的字符串再调一次 `pd.to_datetime`**（内部 `_guess_datetime_format_for_array` + `re.search` **502,404 次** + `re.compile` **532,312 次**，≈177 µs/行）。

**④ 写放大（规模实证）**：
- `factor_cache`：**66,706,944 行**（5554 只 × 7547 日，1995-08-30→2026-10-15）；单股 `000001.SZ` **47,916 行 / 6001 个交易日**。
- `indicator_ma` / `indicator_macd` / `indicator_other`：各 **8,403,944 行**（5529/5533 只 × 7547 日）。
⇒ **每日日终把全市场每只股票的整条历史因子/指标序列逐行重写一遍**。

**⑤ 结论**：RAW 慢＝**算法冗余**（逐行标量日期归一 + 全历史重复写），**非并行度**。故优先 **E1（向量化日期归一，消除 ~98% 的 RECBLD）** + **E2（只写增量/最新日）**。

## 十一、E1 实施记录（v1.2，2026-10-16）

用户「并入 522 号升 v1.1，先开 E1 实施批次」→ **E1 已实施并验证**。

### 改动（`backend/app/data/factor_precompute.py`）
- `_normalize_trade_date`（`:55`）新增**快速路径**：严格形态 `YYYY-MM-DD`（正则 `_CANONICAL_DATE_RE` + `datetime.strptime` 兼校日历合法性）**直接返回原串**；`YYYYMMDD` 加连字符；`datetime`/`pd.Timestamp` 走 `strftime`。**其余格式仍回落 `pd.to_datetime` 严格解析**。
- 新增模块级 `_CANONICAL_DATE_RE`/`_COMPACT_DATE_RE`（`import re`）。
- **语义零变化**：「无法识别/非法 → None」保持（`2026-13-45`/`2026-02-30` 仍返回 None）；未改动 `_batch_cache_factor_series` 逻辑与写库路径（属 E2）。

### 依据（微基准，`/tmp`）
`pd.to_datetime` 标量 **72µs/行** vs 正则 **0.11µs** + `strptime` **1.5µs**——取「正则（严格形态）+ `strptime`（校日历）」兼顾**语义等价**与 ~25–45× 单次提速（裸正则仅 0.11µs 但会漏判非法日历日期，故不用）。
