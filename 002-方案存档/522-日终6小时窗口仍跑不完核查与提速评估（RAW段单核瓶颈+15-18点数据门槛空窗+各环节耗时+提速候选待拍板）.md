## 三、瓶颈定位：RAW 预计算段 + 基本单核（代码 + 运行态实证）

**① 时间维度**：RAW 三步是唯一慢段（10-14 合计 3h19m）；下游 SIG(50m)+JUD(15m) 为固定成本；采集 COL 仅 33m。

**② 并发维度（代码实证）**：
- RAW 三步提交到 `ThreadPoolExecutor(max_workers=3)`（`:6961`）——**每步 1 线程**，三步并行。
- **RAW-1 `_precompute_indicators`（`:7275`）是纯串行 `for code in codes` 循环**——无内部并行。
- **RAW-3 `_precompute_preset_combos`（`:3043`）同样是纯串行 `for code in codes` 循环**——无内部并行。
- 仅 RAW-2 内部 `ThreadPoolExecutor(max_workers=4)`（`:4587`）、SIG 内部 `max_workers=4`。
- 实测 `ps`：daemon **%CPU 117%**（三步并行）/**74.9%**（今晨仅 RAW-3，RSS 361MB）⇒ **10 核机器只用约 0.75~1.2 核**。
- 根因：Python **GIL**——逐股计算是 Python 级运算，线程无法跨核；叠加 RAW-1/3 本就是单线程。

**③ I/O 维度**：RAW-3 单线程独占时仍占 ~75% CPU ⇒ 约 3/4 为 CPU 计算、1/4 为 DB 等待；每只股票各自 `get_cached_daily(code)`（`data/duckdb/*` 分库往返数千次）。

**④ 10-15 比 10-14 更慢的成因**：三维度步骤（1+4+1 线程）抢同一个 GIL 核、互相拖慢，RAW-1 从 47m 拉长到 1h43m。

> **口径澄清**：daemon 进程 CPU 上限 ~1 核是**实测**（`ps %CPU` 117%/74.9%）；「GIL vs I/O vs 池未吃满」的**占比仍需 profiling 才能定论**（`project/raw-segment-single-core-throughput.md` 亦标注为未确认假设）。

## 四、为什么"15:00~21:00 六小时"仍不够

- **硬门槛**：`data_daemon.py:6456` `_is_today_data_ready()` = `_is_market_day() and datetime.now().hour >= 18`——**硬等 Tushare 日线系（龙虎榜/指数等）18:00 后发布**，15:00~18:00 **不可用**（空窗 ≈3h）。
- **有效窗口**：18:00 放行 → 关机（≈21:00，与 10-14 同款跨夜分段）≈ **3h**。
- **结构性需求**：EOD 需 ≈ **5h**，其中 **RAW 单段就 3h19m**。
- ⇒ 3h < 3h19m，**跑不完是必然**；10-15 RAW-3 首当其冲（关机时 4581/5565）。

## 五、提速候选（按收益/风险分档，均**未实施**）

| 档 | 措施 | 预期收益 | 风险 / 前置 |
|---|---|---|---|
| **A（收益最大）** | RAW 逐股计算**改进程池（multiprocessing）**，吃满 10 核 | RAW 3h19m → 理论 **~30~45min** | macOS spawn；每进程独立只读连接；结果回传（每股 1 行，量小）；**写回仍留主进程**（保持 505 写模型）；须充分测试不回归 505/506/518 |
| **B（低风险）** | RAW-1 / RAW-3 加内部线程池（对齐 RAW-2 的 4 worker） | 有限（GIL 上限，约 1→2 核） | 改动小；受 GIL 限制 |
| **C（低风险）** | 批量预取全市场日线到内存，替代逐股 DB 往返 | 削掉 ~25% I/O 等待 | 内存占用可控（5565 只 × 60~250 日） |
| **D（中等）** | RAW 三步合并为单一任务队列，消除互相争抢 GIL | 中等 | 结构性改动 |
| **E（缩小空窗）** | 实测 Tushare 日线系最早可获取时点，评估把门槛 18:00 前移 | 上限 ~1h | **质量风险**：数据未齐会算错；须实测发布时点 |
| **F（错峰）** | 把不依赖当日 18:00 数据的步骤（如 COL-7 财务、形态评分）提前到 15:30 做 | 腾挪 ~30m | 需逐项核查数据依赖 |
| **G（根治完成度）** | 云主机 7×24（`project/deployment-plan.md`） | 消除关机中断（不漏算） | 非"耗时"，是"完成度" |

**推荐组合**：先 **C + B**（低风险、快速见效）→ 再上 **A**（收益最大，独立号 + 充分测试）→ 之后评估 **E/F**（涉及数据质量，须实测 + 用户拍板）。
