# 404号 — dim6风险边界引擎输入数据源核查与修复方案

---

## 一、核查范围

本方案核查 dim6 引擎的**输入数据源**（不含输出项），追溯数据从采集层→存储层→计算层→调用层的完整管道，评估数据源获取是否正常、数据是否精准、是否存在遗漏和错误。

dim6 输入分三层：
- **ECM 数据库表**（13个）：通过 `ecm.get_cached_xxx()` 或 `dm.get_cached_xxx()` 读取
- **DataManager 方法**（6个）：`dm.get_stock_info()` 等
- **tags 标签名**（10个）：从 `pre_feat_cache` 扁平化后读取

### 问题标签（3项）

#### DATA-01（HIGH）：`_detect_longhubang` 行867 变量名错误 — 403号BUG-03修复引入的回归

**位置**：dim6_risk_engine.py 行867

**根因**：403号方案 BUG-03 修复（统一 EventMonitor 数据访问路径）将 `_detect_longhubang` 行841的 `cache` 改为 `ecm`，但行867的 `cache.get_cached_lhb_detail()` **未同步修改**，`cache` 变量在当前作用域未定义。

**影响**：当 `_detect_longhubang` 主路径（lhb_cache）未检测到时，进入降级路径调用 `cache.get_cached_lhb_detail()`，抛出 `NameError`，被行879的 `except Exception` 静默吞掉。龙虎榜机构席位明细检测永远不执行。

**修复方案**：将行867的 `cache.get_cached_lhb_detail(ts_code=ts_code)` 改为 `ecm.get_cached_lhb_detail(ts_code=ts_code)`。同时建议在 403 号方案中追加此回归修复记录。

**工时**：0.1天

#### DATA-03（MEDIUM）：`right_side_confirm` 永远不等于 '否决' — 失效条件中右侧否决检查为死代码

**位置**：data_daemon.py 行2467

**现象**：
```python
_derived['right_side_confirm'] = 'strong_confirm' if _cl.get('buy_sell_point', '') in ('first_buy', 'second_buy') and _vp_f.get('volume_price_fit') == 'healthy' else 'unconfirmed'
```

pre_feat_cache 管道中 `right_side_confirm` 只产出两个值：`'strong_confirm'` 或 `'unconfirmed'`。

dim6 `_build_invalidation` 行370 的检查：
```python
if str(tags.get('right_side_confirm', '')) == '否决':
    conditions.append({'source': '右侧', 'condition': '右侧确认转否决', 'priority': 3})
```
永远不会触发。`'否决'` 值只由 `_check_right_side_confirm()`（data_daemon.py 行3159-3254）产出，该函数仅在 treemap 快照管道（行3519+）中被调用，**不在 pre_feat_cache 管道中**。

**影响**：dim6 的失效条件列表（invalidation）中"右侧确认转否决"条件永远不出现，用户无法通过 dim6 看到右侧技术面恶化的警告。

**修复方案**：

方案A —— 在 pre_feat_cache 管道（daemon 行2467附近）中调用 `_check_right_side_confirm()`，将结果写入 `_derived['right_side_confirm']`，使 '否决' 值能流入 tags。

方案B（推荐）—— 标记为已知限制，右侧否决由 treemap 快照管道单独处理，dim6 不覆盖。

**方案A可行性说明**：`_check_right_side_confirm(opportunity_type, tags, df)` 需要三个参数。在 RAW-2 管道中 `df` 可用（`all_data[code]`），但 `opportunity_type` 需要额外确定（可用默认值）。该函数内部执行实时分析（量价背离/预跌形态检测），在 RAW-2 预计算管道中执行分析类逻辑，与353号"RAW层做纯计算"的原则有争议。建议采用方案B。

**工时**：0.5天（方案A）/ 0.1天（方案B，推荐）

## 四、`dims['l0']` 始终为空 — 已知设计限制

### DATA-04（LOW）：hard_veto 检测为死代码

**位置**：dim6_risk_engine.py 行1985

**现象**：
```python
l0 = dims.get('l0', {}) if isinstance(dims.get('l0'), dict) else {}
```

`dims` 由 `dim_adapter.convert_to_dims_format()`（dim_adapter.py 行86）生成，只产出 `structure/vp/chip_fund/emotion/risk/valuation/signal` 七个 key，**无 `l0`**。`l0` 由 `StatusEngine._apply_l0()` 在维度引擎运行**之后**才计算。

**影响**：
- `_assess_risk_level` 行271：`l0.get('hard_veto')` → 永远 False
- `_list_risk_factors` 行324：`l0.get('hard_veto')` → 永远不触发
- `_list_risk_factors` 行340：`l0.get('soft_risks', [])` → 永远空

**性质**：T42 修复的已知设计（消除循环依赖：dim6 输出 feeds StatusEngine l0，l0 不能反向 feed dim6）。hard_veto 由 StatusEngine 在维度引擎运行后独立判定。

**建议**：不做修改，在 dim6 的 `_assess_risk_level` 注释中标注此为已知限制。

**工时**：0.05天（仅加注释）
