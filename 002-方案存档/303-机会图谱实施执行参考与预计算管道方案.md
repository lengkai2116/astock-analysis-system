## 二、P0.4 预计算管道扩展方案评估

### 2.1 现有管道结构分析

`data_daemon.py` 的 `_run_precompute()` 函数（第 1346-1408 行）当前结构为三个独立顺序块：

```
顺序执行，每块均自带 try/except：
  ① 指标预计算（逐只循环，~4800只×30ms ≈ 2.4min）
     使用 PrecomputeIndicatorManager.precompute_all_indicators()
     
  ② 策略信号预计算（批量并行，max_workers=4）
     使用 UnifiedStrategyCore.compute_batch()
     失败回退 _write_factor_signals()
     
  ③ 因子预计算（逐只循环，4800只×20ms ≈ 1.6min）
     使用 FactorPrecomputeManager.precompute_factor()
```

所有块共享同一份 `codes` 列表（当日有日线数据的活跃股票）。每块之间无数据传递（各自独立读取 ECM 缓存）。此结构的优点是**各块独立、互不影响、错误隔离**。

### 2.2 推荐方案：新增 `_precompute_l2_labels()` 块

在③之后、函数返回之前插入新的执行块。不修改现有三个块的任何代码，保持向后兼容。

```python
def _run_precompute():
    # ── 现有代码① 指标预计算（不变） ──
    # ... (lines 1372-1383) ...

    # ── 现有代码② 策略信号预计算（不变） ──
    # ... (lines 1385-1402) ...

    # ── 现有代码③ 因子预计算（不变） ──
    # ... (lines 1404-1408) ...

    # ── 新增代码④ L2 标签预计算 ──
    try:
        _precompute_l2_labels(codes)
    except Exception as e:
        logger.warning(f"L2标签预计算失败: {e}")
```

**设计原则**：
- 不修改已有代码，只新增一个函数和一个调用点
- 遵循现有错误隔离模式（`try/except` + `logger.warning`）
- 与现有块共享相同的 `codes` 列表

### 2.3 `_precompute_l2_labels()` 内部结构

```python
def _precompute_l2_labels(codes):
    """L2标签预计算：读取各引擎产出，聚合写入 opportunity_tags_cache
    
    执行顺序（对所有活跃股）：
      1. 估值标签（ValuationEngine）→ 写入 tags 字典
      2. 阶段判定标签（PhaseDetectionEngine）→ 写入 tags 字典  
      3. 情绪标签（MarketSentimentService）→ 写入 tags 字典
      4. 板块标签（SectorRotationModel）→ 写入 tags 字典
      5. 聚合衍生：计算 signal_strength → 写入 tags 字典
      6. 批量写入 opportunity_tags_cache
    """
    _ensure_pd()
    
    # 延迟导入各引擎（只在 precompute 时加载，不占用主循环内存）
    from app.opportunity_atlas.valuation_estimator import ValuationEngine
    from app.opportunity_atlas.phase_detector import PhaseDetectionEngine
    from app.services.market_sentiment_service import MarketSentimentService
    from app.engine.framework.sector_rotation_model import SectorRotationModel
    
    # 各引擎的延迟初始化（单件模式）
    ve = ValuationEngine(_ecm)
    pd = PhaseDetectionEngine(_ecm)  
    ms = MarketSentimentService(_ecm)
    sr = SectorRotationModel()
    
    import time
    t0 = time.time()
    succeeded = 0
    
    for code in codes:
        try:
            tags = {}
            
            # 1. 估值引擎产出 → 5 个标签（P0.1）
            valuation_tags = ve.compute_tags(code)
            tags.update(valuation_tags)  # valuation_level, valuation_deviation, pe_percentile_5y 等
            
            # 2. 阶段判定引擎产出 → 5 个标签（P0.2）
            phase_tags = pd.compute_tags(code)
            tags.update(phase_tags)  # main_force_phase, phase_confidence 等
            
            # 3. 情绪引擎产出 → 1 个标签（P0.5）
            sentiment = ms.get_sentiment_phase()
            tags['sentiment_phase'] = sentiment['phase']
            
            # 4. 板块引擎产出 → 1 个标签（P0.6）
            sector = sr.evaluate(code, df)  # df 需从 ECM 获取
            tags['sector_heat'] = sector.get('sector_heat', 'none')
            
            # 5. 聚合衍生 → signal_strength（约30行）
            tags['signal_strength'] = _compute_signal_strength(tags)
            
            # 6. 写入数据库（用批量 insert or replace）
            _ecm.write_tags(code, tags)
            succeeded += 1
            
        except Exception:
            continue
    
    elapsed = time.time() - t0
    logger.info(f"L2标签预计算完成: {succeeded}/{len(codes)} 只, 耗时 {elapsed:.1f}s")
```

### 2.4 效率评估

| 维度 | 评估 | 说明 |
|------|------|------|
| 单只耗时 | ~50ms | 4 个引擎计算 + 1 次衍生 + 1 次写入 |
| 4800 只总耗时 | ~4 分钟 | 50ms × 4800 = 240s ≈ 4min |
| 非交易时段窗口 | **15:35~次日9:00 ≈ 17.4h** | 数据充足 |
| 磁盘 IO | ≈9.6MB | 4800 只 × 30 个标签 × ~64byte ≈ 9.6MB |
| 与现有块的关系 | 无冲突，无锁竞争 | 各块写入不同表 |

4 分钟的单次执行时间在 17.4 小时的窗口内完全可以接受，不需要并行优化。如果后续回测发现 4 分钟过长（例如数据量扩展到全历史），最直接的优化是将逐只循环改为批量写入（每 500 只 commit 一次）。

### 2.5 稳定性设计

| 故障场景 | 处理方式 |
|---------|---------|
| 某个引擎 import 失败 | 延迟导入只在此函数内捕获，不影响主循环 |
| 某个引擎对单只股票计算失败 | 该股票不写入该引擎的标签，其他引擎正常写入 |
| 5 个引擎全部失败 | 异常被外围 try/except 捕获，仅日志记录 |
| `opportunity_tags_cache` 表不存在 | 在 `_ensure_cache_tables()` 中增加该表的自动建表 |
| 写入性能问题 | 每 500 只 commit 一次，避免长事务 |

### 2.6 对比方案评估（不采纳的替代方案）

| 替代方案 | 不采纳理由 |
|---------|-----------|
| 改为独立线程异步执行 | 预计算之间有数据依赖（signal_strength 依赖前 4 个引擎），异步后需要同步等待，复杂度增加但无收益 |
| 使用消息队列调度 | 过度工程——当前串行执行 4 分钟，独立队列调度只会增加复杂度 |
| 改写为纯 SQL 聚合（不用 Python 引擎）| 估值和阶段判定引擎包含复杂的 Python 逻辑（ASR 判断、四锚加权等），无法用纯 SQL 表达 |
| 每个引擎单独一个定时任务 | 需要协调 5 个定时任务的执行顺序，且故障恢复复杂 |

## 五、实施通用约定（含审阅补充）

以下约定在 294号 §五 的基础上，增加了本轮审阅发现的关键补充项。

### 5.1 延迟导入原则（不变）

所有引擎模块在 `_run_precompute()` 延迟导入，不在 `data_daemon.py` 顶层 import。已存在的 PrecomputeIndicatorManager、UnifiedStrategyCore 均使用此模式，L2 标签预计算延续同样的方式。

### 5.2 单只失败不阻断全量（不变）

每个引擎对单只股票的计算失败时，仅跳过该股票该标签，继续下一只。9 个新引擎均通过各自的 `try/except` 包裹。

### 5.3 数据不存在回退（不变）

当某个引擎依赖的 ECM 表为空时（如 margin_cache 已知为空），该引擎自动输出 `unknown`/`none` 而不阻断流程。不影响 signal_strength 计算（signal_strength 只对非空标签做聚合）。

### 5.4 批量写入优化（不变）

`opportunity_tags_cache` 使用 `INSERT OR REPLACE` 逐日覆盖策略。每 500 只股票 commit 一次，避免长事务对 SQLite WAL 的锁定压力。

### 5.5 不重复实现收益分解引擎（不变）

`upward_driver` 标签在 **P2.1 事件监控器**中实现（302号§三），不在 P2.5 中重复实现。在 P2.5 实施时跳过此项。

### 5.6 Red Line 5 治理前置化（审阅补充）

**P0.6**（SectorRotation 重写）时**必须同步**实现 DataManager 封装方法 `get_stock_industry()` / `get_stock_industry_batch()`，使引擎的行业数据获取走 DataManager 网关。具体方案见 302号§2.3 更新版。**不可留到 Phase 3 再整革**——因为本轮重写就是最佳的插入点。

### 5.7 signal_strength 事件维度补偿协议（审阅补充）

因 `signal_strength` 在 P0.4（早于 P2.1 事件监控）预计算，**不包含 `catalyst_event` 维度**。P2.2（L4 仲裁层）应输出 `signal_strength_adjusted` 字段用于前端弹窗展示：
```
signal_strength_adjusted = signal_strength × (1 + catalyst_event_adjustment)
catalyst_event_adjustment:
  catalyst_event in (earnings/lhb/buyback/breakout) → +0.15
  catalyst_event = none → 0
  catalyst_event in (pledge/float/reduce/fraud_sign/regulatory) → -0.15
```
仅用于前端机会地图弹窗的"信号强度"展示行，**不回写 `opportunity_tags_cache` 表**。

### 5.8 财报空窗期处理规范（审阅补充）

依赖季频财务数据的标签（`fina_health`/`composite_rating`/`roce_pass`）在财报空窗期**不会每日变化**，这不是故障。处理方式：
- 前端展示处标注"财务数据季频更新"
- L4 变更检测（300号§2.3）在连续多日无变化时，推送分级降至 `none`（不推送无效通知）
- `valuation_level` 中基于 PE/PB 百分位的部分不受影响（daily_basic 日频数据）

### 5.9 P0.4 完成前的前端 fallback 协议（审阅补充）

P0.4 完成之前（第一~二梯队阶段），Treemap 后端 API 应返回：
```json
{
  "treemap_data": [...],
  "signal_strength_fallback": true,
  "data_status": "pre_compute"
}
```
前端据此在机会地图标题栏显示"⚠ 信号强度 Fallback"提示。P0.4 完成后，`fallback` 标识移除，角度消除。

### 5.10 P2.1 分步实施策略（审阅补充）

P2.1 的 2 周周期内需同时完成采集层和计算层，建议按以下优先级分步实施，降低阻塞风险：

| 步骤 | 实施事件 | 数据依赖 | 说明 |
|:----:|---------|:-------:|------|
| 第一步(第1周) | A1/A2/A5/D1/D2/E1/E2 | ECM 已有数据 | 无需等待新增采集，立即可用 |
| 第二步(第2周) | B1~B6 + A3/A4 + 新闻快讯 | 新增 4 类 Tushare 采集 + AKShare | 依赖采集层就绪 |

如果新增 4 类采集受阻（权限/积分问题），优先确保第一步 7 类事件上线，第二步在第六梯队间隙中补齐。
