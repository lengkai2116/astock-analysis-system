## 二、系统整体架构

```
前端 screener.html
       │ POST /api/v3/screener/run
       ▼
路由 screener.py · compute_screening()
       │
       ├── L1: DarwinRiskFilter (风险剔除)
       │    ├── 过滤ST/退市
       │    ├── 过滤低流动性 (换手率<1%)
       │    ├── 过滤极高估值 (PE>300, 金融豁免)
       │    └── 过滤亏损微盘 (PE=NULL + 市值<30亿 + 换手<3%)
       │
       ├── L2: MainForceFilter (主力关注度评分)
       │    ├── A: 资金流向 (moneyflow_cache)
       │    ├── B: 价量主力信号 (OHLCV)
       │    ├── C: 筹码集中度 (stk_holder_cache)
       │    ├── D: 散户反向指标 (moneyflow + margin)
       │    ├── E: 龙虎榜席位 (lhb_cache)
       │    └── F: 筹码分布 (ChipDistributionService)
       │
       └── L3: screen_l3_candidates (多策略验证)
            ├── 缠论策略评分 (chanlun_strategy.py)
            ├── 量价策略评分 (volume_price_strategy.py)
            └── 因子组合评分 (factors 模块)

后台预计算流程 (data_daemon.py):
   日终同步(15:30) ─→ _run_precompute()
       ├── PrecomputeIndicatorManager → indicator_* 宽表
       ├── UnifiedStrategyCore.compute_batch() → strategy_signal_detail 表
       └── _precompute_preset_combos() → factor_cache 表

   开机自检: _check_precompute_status() 在15:30后检查完整性
```

## 三、分层筛选机制详解

### L1 — 达尔文风险过滤 (DarwinRiskFilter)

位于 `screener.py`，四道过滤规则依次应用，任一条不通过即一票否决：

| 规则 | 条件 | 数据来源 |
|------|------|---------|
| ST/退市 | 名称含 `*ST`/`ST`/`退市`/`SST` | Stock ORM → `get_stock_list()` 缓存 |
| 低流动性 | 20日日均换手率<1% 或 成交额<1000万 | `daily_basic_cache` (ECM) |
| 极高估值 | PE_TTM>300（金融行业豁免） | `daily_basic_cache` |
| 亏损微盘 | PE=NULL + 流通市值<30亿 + 换手<3% 三重同时满足 | `daily_basic_cache` |

### L2 — 主力关注度筛选 (MainForceFilter)

`MainForceScorer` 六维评分 0-10 分，阈值 ≥6.4 分视为有主力关注，top_k=20 兜底：

| 维度 | 分值 | 数据源 | 核心逻辑 |
|------|------|--------|---------|
| A: 资金流向 | 0-3 | `moneyflow_cache` | 5日大单净额 + 资金连续性 + 大单占比 |
| B: 价量主力信号 | 0-3 | OHLCV | 四阶段识别(建仓/洗盘/拉升/出货) |
| C: 筹码集中度 | 0-2 | `stk_holder_cache` / OHLCV | 股东户数变化 / 波动率评估 |
| D: 散户反向指标 | 0-2 | `moneyflow_cache` + `margin_cache` | 散户净买入低位/高位判断 + 融资反向信号 |
| E: 龙虎榜席位 | -0.5~1.0 | `lhb_cache` + `lhb_detail_cache` | 真机构加分，假机构识别扣分 |
| F: 筹码分布 | 0-1.5 | ChipDistributionService | ASR + SSRP + CYQKL 真实筹码指标 |

### L3 — 多策略验证

三个正交策略的融合评分：
- **缠论策略** (`chanlun_strategy.py`): ChanlunScorer 11 维度（买卖点/背离/中枢/趋势等）
- **量价策略** (`volume_price_strategy.py`): 量价形态识别
- **因子组合** (`factors` 模块): 用户可选 PRESET_COMBOS + 自定义组合

## 四、后台预计算与数据流

`data_daemon.py` 日终同步后自动触发 `_run_precompute()`：

1. 查询当日有日线数据的全部活跃股票
2. `PrecomputeIndicatorManager.precompute_all_indicators()` → 指标宽表写入
3. `UnifiedStrategyCore.compute_batch()` → `strategy_signal_detail` 表写入（所有策略信号）
4. `_precompute_preset_combos()` → `factor_cache` 表写入（因子预计算值）

开机自检流程 (`_check_precompute_status`):
- 非交易日跳过
- 9:30 前跳过
- 9:30~15:30: 检查自选股，缺失则发起增量请求
- 15:30 后: 全市场检查 `strategy_signal_detail` 是否存在当日数据，缺失则全量预计算

## 五、问题清单

### [P1] L3 策略引擎与选股流程「伪分离」— 重复计算

**影响**: 性能 · **严重程度**: 高

L3 的 `screen_l3_candidates` 对每只候选股独立调用 `analyze_chanlun()` + `VolumePriceStrategy.analyze()` + 因子计算——这些与 `UnifiedStrategyCore` 后台预计算的计算**完全重复**。

后台预计算的结果 (`strategy_signal_detail` 表) **没有被选股 L3 复用**，而是又重新算了一遍。每次执行选股相当于对候选股（通常 20-100 只）额外跑了一遍缠论和量价分析。

**建议**: L3 优先从 `strategy_signal_detail` 表读取预计算结果，仅在数据不足时回退到在线计算。

### [P2] 全量数据加载效率低

**影响**: 性能/内存 · **严重程度**: 高

`load_stock_data_batch()` 先调用 `dm.cache.preload_all()` 全量预加载，再调用 `dm.get_cached_daily_batch(ts_codes)`。对于 5000 只股票的选股，这意味着读取全量日线数据（数年 × 约 5000 只）到内存，即使 L1 过滤后 L2 只处理几百只。

**建议**: 改为按需加载——L1 阶段只需 daily_basic 数据（换手率/PE/市值），L2/L3 阶段才加载日线 OHLCV。

### [P3] ~~sync_requests 异步队列机制未完整实现~~ ✅ 已修复

**影响**: 数据就绪 · **严重程度**: 高 · **状态**: ✅ **data_daemon.py:1771-1808 已实现完整消费**

`data_daemon.py` 主循环 30s 轮询（`_ecm.consume_pending_requests()`），支持全部 12 种 `task_type` 的同步分发。详见 `data_daemon.py:1771-1808`。

**修复后状态**：调用层写入 sync_requests → daemon 30s 内消费 → 全市场批量补采 → 标记完成。机制完整可用。

### [P4] `MultiLayerStockScreener._apply_strategy_validation` 空壳实现

**影响**: 代码质量 · **严重程度**: 中

该方法的 L3 验证仅检查 `len(data) >= 60` 就标为 validated：
```python
if len(data) >= 60:
    candidate['validated'] = True
    candidate['data_points'] = len(data)
    validated.append(candidate)
```

实际上有意义的 L3 实现在 `screener.py` 的 `compute_screening()` 中通过 `screen_l3_candidates` 完成。`MultiLayerStockScreener` 类本身在 API 路由中从未被调用，属于**已废弃但未清理**的代码。

**建议**: 删除 `MultiLayerStockScreener` 和 `SignalFusion` 类，或将 `compute_screening()` 中的 L3 调用整合回该类以保证设计一致性。

### [P5] 存在不可达代码（Dead Code）

**影响**: 代码质量 · **严重程度**: 中

`screener.py` 的 `load_stock_data_batch()` 中有一段 `continue` 前的补采代码后紧跟逻辑块永远不会执行：
```python
dm.request_data('per_stock', ts_code)
except Exception:
    pass
continue  # ← 后续代码永远无法到达
# ... 永远不会执行 if df.empty ... result[ts_code] = ...
```

此外 `DarwinRiskFilter.__init__` 接受 `data_manager` 参数，但 `MultiLayerStockScreener` 无参构造它，该参数从未被利用。

**建议**: 清理不可达代码段；移除 `DarwinRiskFilter` 未使用的构造参数。

### [P6] 评分体系混乱——多套评分并存且未统一

**影响**: 结果一致性 · **严重程度**: 中

| 评分器 | 范围 | 用途 |
|--------|------|------|
| `ChipScorer.score()` | 0-10 | 原 L2 评分（已逐步被 MainForce 替代） |
| `MainForceScorer.score()` | 0-10 | L2 主力关注度 |
| `_compute_chanlun_score()` | 0-10 | L3 缠论评分 |
| `_compute_volume_price_score()` | 0-10 | L3 量价评分 |
| `_score_to_grade()` | S/A/B/C/D | L3 输出映射 |
| `_get_grade_info()` | S/A/B/C/D | 另一套映射（评分标准不同） |

L3 综合评分用 `_compute_combined_score()` 基于 `chanlun_score` + `vp_score` 加权，**不包括主力资金（L2）和因子（选配）的分数**。如果用户同时选了因子组合，因子分量不参与综合分计算。

**建议**: 统一评分体系到 0-10 分，明确各维度的权重关系并在综合评分中全部纳入。

### [P7] 前端 UI 与后端 API 不匹配——Vibe 策略落地浅

**影响**: 功能完整性 · **严重程度**: 中

前端 `screener.html` 展示 Vibe Coding 策略面板，从 `/api/v3/screener/strategies/vibe` 获取策略列表。后端提供了策略列表 API，但 L3 的 `screen_l3_candidates` 对 `vibe_strategies` 参数的处理深度不够——Vibe 信号在 `UnifiedStrategyCore` 中的 `vibe` 类型是否能被 `SignalComputationService` 实际计算需要确认。

**建议**: 审计 Vibe 策略在 L3 中的实际计算逻辑，确认 `SignalComputationService` 已覆盖 Vibe 策略；或在前端隐藏未实现的策略选项。

### [P8] L3 降级路径自恢复机制脆弱

**影响**: 可靠性 · **严重程度**: 中

`compute_screening()` 中 `screen_l3_candidates` 失败后会进入个票逐一调用（兜底降级路径），每个候选股上独立 import `VolumePriceStrategy` 和 `analyze_chanlun`，且完全忽略 `_L3_ENGINE_HEALTH` 健康度数据——健康度数据只被记录和报告，从未触发任何自动恢复动作。

**建议**: 当 L3 错误率超过 20% 时触发自动降级（跳过L3，仅返回 L2 结果）并记录告警。

### [P9] 缺乏筛选过程监控

**影响**: 可观测性 · **严重程度**: 低

`_screener_cache` 有 1h TTL，但缺少对以下指标的跟踪：
- 各层筛选率（L1 通过率、L2 通过率）的历史趋势
- L2 MainForceScorer 各维度评分的分布
- L3 各策略引擎的错误率（虽有记录但无自动阈值告警）
- `daily_basic_cache` 数据缺失率对筛选准确性的影响

**建议**: 增加筛选过程的结构化日志，记录各层筛选率及关键指标分布。

### [P10] 因子预计算与选股因子评分断连

**影响**: 性能 · **严重程度**: 低

`_precompute_preset_combos` 将因子值写入 `factor_cache`，但 `screen_l3_candidates` 在计算因子组合评分时**不是直接从 `factor_cache` 读取**，而是对每只候选股重新调用因子计算逻辑。

**建议**: L3 因子评分改为优先从 `factor_cache` 读取预计算值，仅在数据缺失时重新计算。
