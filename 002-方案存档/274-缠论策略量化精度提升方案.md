# 缠论策略量化精度提升方案

> **背景**：271号方案对中枢延伸算法进行了修复（`_evolve_zhongshu` 三态判断、`_expand_zhongshu` 子中枢保存），但实测301042.SZ安联锐视仍出现中枢吞没全价格范围 [19.17, 113.72] 的异常。经全面复查，发现在数据层、结构层、工程层存在多处与知识库定义不符的实现偏差。
>
> **⚠️ 版本更新**：本版(v5)全量实施完成。P-1(数据架构统一) + 批次0(线段层)+批次1(数据层)+批次2(核心结构修复)+批次3(多级别联立)+批次4(信号层增强)+批次5/6(中短线扩展) 全部实现并端到端验证通过。

## 一、问题全景：偏差集中度评估

基于 LLM Wiki 知识库"缠论走势结构的量化精准识别——系统化设置方案"（以下称"系统化方案"）与当前代码的逐项对比，共发现 **10项偏差**，按严重程度分级：

| 严重度 | 问题 | 当前状态 | 所属层面 | 直接影响 |
|--------|------|---------|---------|---------|
| 🔴 致命 | `_evolve_zhongshu` 的 `'expand'` 分支 | 线段部分超出即扩展区间 | 结构层 | 中枢吞没全价格范围 |
| 🔴 致命 | 多级别联立未接入 | T8 占位，仅日线单级别 | 工程层 | 无跨级别验证约束 |
| 🔴 致命 | **SegmentAnalyzer 特征序列包含处理缺失** | 仅简化版"反向笔突破前低/前高"检查，无真正的特征序列包含关系处理 | 结构层 | 线段划分精度不足，影响后续所有中枢和买卖点 |
| 🔴 致命 | **SegmentAnalyzer 缺少终止高点>起始高点检查** | `_is_valid_segment` 未检查此条件 | 结构层 | 无效线段被计入，中枢区间失真 |
| 🟡 严重 | K线复权用前复权 | `adj='qfq'` | 数据层 | 除权跳空误判为走势结构 |
| 🟡 严重 | 涨跌停K线无特殊处理 | 完全未过滤 | 数据层 | 无量涨停生成虚假笔/中枢 |
| 🟡 严重 | K线包含处理无递归 | 单次包含合并，未递归至无包含 | 数据层 | 分形精度不足 |
| 🟢 中等 | 笔算法固定为严格笔 | `min_klines=4`，无场景切换 | 结构层 | 日线适用但无法下放短线 |
| 🟢 中等 | 背驰单一面积法 | 仅 `macd_algo='area'` | 信号层 | 无辅助验证 |
| ⚪ 提示 | 未使用后复权用于分析 | 分析与执行共用前复权 | 数据层 | 历史结构时间错位 |

## 二、逐项分析与修复方向

### 2.1 数据层偏差

#### D1: K线复权方式（🟡 严重）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 分析用后复权（避免前复权导致历史结构时间错位）；交易用前复权（符合实际成本） |
| **当前状态** | `tushare_provider.py:164` 使用 `adj='qfq'`（前复权），全链路统一使用前复权 |
| **影响** | 前复权会持续修正历史K线的价格，导致过去确认的笔/中枢结构因复权因子更新而产生时间错位。已经完成的走势结构不应因除权除息而"变形" |
| **修复方向** | 分析管道（`compute_for_stock` → `ChanlunAnalyzer`）使用后复权数据；仅在前端展示和交易建议时使用前复权 |

#### D2: 涨跌停K线处理（🟡 严重）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 涨跌停日的"无量涨跌停"标记为特殊K线，量化时应主动过滤，不应按实体阳/阴线纳入笔的生成 |
| **当前状态** | `chanlun_strategy.py` 全文件搜索"涨停/跌停/limit"—0结果，完全无处理 |
| **影响** | 涨停/跌停K线的"有价无量"特性被当作正常K线参与包含处理、分形识别和笔的生成，产生大量不符合真实结构的虚假信号。A股特有的涨跌停制度使得这个问题尤其严重——连续涨停期间MACD失真、分形错位 |
| **修复方向** | 在 `StrokeBuilder`（或上游预处理）中加入涨跌停检测：当日收盘价=涨停价且成交量显著萎缩（<5日均量30%）→ 标记为特殊K线。笔生成时跳过这类K线的分形检测，或将其合并为单方向延续 |

#### D3: K线包含处理无递归上限（🟡 严重）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 包含处理需要递归进行直到不再包含，递归上限10次。不跳过前两根K线 |
| **当前状态** | `KLineMerger.merge()`（line 224-263）仅单次遍历合并，合并后的K线与更前一根K线的潜在再包含未被检查。实际递归深度=1 |
| **影响** | 连续包含关系未被彻底处理，导致残留的包含K线影响分识的精度。在密集震荡行情中，一次合并不够，分形识别会遗漏或产生虚假分形 |
| **修复方向** | 将 `merge()` 改为循环递归：每轮合并后重新从头扫描，直到无包含或达到递归上限（max_iter=10）。参考czsc标准实现 |

### 2.2 结构层偏差

#### S1: 中枢'expand'分支违反缠论定义（🔴 致命）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 中枢区间固定不变（由最初的三段确定）。**中枢延续**：线段在区间内震荡 → 延伸不改变区间。**中枢扩张**：两个同级别中枢区间重叠 → 形成更高级别中枢。**中枢新生**：离开后形成新同级别中枢 |
| **当前状态** | `_evolve_zhongshu`（line 915-934）返回 `'expand'` 当线段部分超出。`_expand_zhongshu` 执行 `min/max` 扩展边界（line 951-952）：`zs.low = min(zs.low, seg_r['low']); zs.high = max(zs.high, seg_r['high'])` |
| **影响** | 单个中枢随每次部分超出持续扩展，最终吞没全部价格范围。301042.SZ 从初始区间 → [19.17, 113.72]。子中枢链 `sub_zhongshu_list` 虽然保存，但输出层从未读取 |
| **修复方向** | 移除 `'expand'` 分支。线段部分超出应归入 `'extend'`（中枢延续，区间不变）。线段完全脱离且不回 → `'detach'`（中枢破坏）。真正的中枢扩张仅在 `_merge_zhongshu` 中发生——两个完整独立中枢区间重叠。修复后，输出层 `latest_zhongshu` 使用最近一个 `type='normal'` 的子中枢（或直接使用最近一个 `zhongshu_list[-1]`） |

#### S2: 笔算法缺乏场景切换（🟢 中等）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 中长线（30分钟/日线）用严格笔（5K线，方向严格）。短线（5分钟及以下）用宽笔（3K线，方向宽松）+ 确认过滤 |
| **当前状态** | `BiConfig.min_klines=4` 固定为中位数，`bi_strict=True`。不分场景统一使用一种笔算法 |
| **影响** | 日线级别4根K线成笔比5根宽松，可能多生成一些笔，但总体影响有限。问题在于向下扩展到60分钟级别时无法灵活切换。但由于目前只有日线单级别，此问题暂未暴露 |
| **修复方向** | 保持当前`min_klines=4`作为默认值。待多级别联立实施后，为各级别配置独立的笔参数（日线严格笔=5K线，60分钟宽笔=3K线+确认过滤） |

#### S3: SegmentAnalyzer 底层逻辑缺陷（🔴 致命）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 线段定义：**三笔方向一致，且终止高点 > 起始高点**（向上线段）或终止低点 < 起始低点（向下线段）。特征序列需要做包含处理（与K线包含处理类似，但针对笔的"侧面"） |
| **当前状态** | `_is_valid_segment`（line 752-756）只检查方向交替和重叠，**未检查"终止高点 > 起始高点"**。特征序列破坏逻辑仅检查反向笔是否突破前低/前高，**没有特征序列元素之间的包含关系处理** |
| **影响** | ① 缺少终止高点检查 → 一个"向上笔+向下笔+向上笔"但第三笔未创新高的无效结构可能被当作有效线段。② 缺少特征序列包含处理 → 复杂笔序列中的包含关系未被消除，线段划分的边界不精确。这两个问题叠加后，上游的中枢区间计算建立在不精确的线段之上 |
| **修复方向** | ① `_is_valid_segment` 增加方向条件：向上线段要求 s3.end_price > s1.start_price，向下线段要求 s3.end_price < s1.start_price。② 增加特征序列元素包含处理：将特征序列（上升段中的下跌笔、下降段中的上涨笔）按K线包含处理的逻辑进行合并，再判断终结。参考czsc标准实现 |

### 2.3 工程层偏差

#### E1: 多级别联立未实施（🔴 致命）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 三级联立 + 正确级别匹配。知识库明确：**短线(T+1/T+2)用5分钟，中线(3-10天)用30分钟，长线用日线。避免混用**。不同策略周期对应的三级组合应为： |
| | **超短线**: 背景5分钟 / 决策1分钟 / 执行tick |
| | **短线(T+1/T+2)**: 背景30分钟 / 决策5分钟 / 执行1分钟 |
| | **中线(3-10天)**: 背景日线 / 决策30分钟 / 执行5分钟 |
| | **长线(1-3月)**: 背景周线 / 决策日线 / 执行60分钟 |
| | 级别递归：1分钟→5分钟→30分钟→日线（或固定周期近似） |
| **当前状态** | `MultiLevelChanlunAnalyzer` 已实现但从未调用。`SignalComputationService` 仅获取日线数据。T8验证器为占位。274号方案v1版原规划 周线/日线/60分钟——**经审查，这个组合仅覆盖长线（1-3月），无法覆盖用户需求的短线(T+1/T+2)和中线(3-10天)** |
| **影响** | ① 只有日线单级别 → 中枢跨级别验证缺失。② 原规划 周线/日线/60分钟 仅对应长线，上线后策略输出会变成超长期（数月到数年），无法用于短线和中线操作。 **要覆盖短线和中线，必须引入分钟级K线数据管道** |
| **修复方向** | **数据源前提已就绪**：系统已有 mootdx（通达信TCP协议）数据通道，实测可免费获取全部所需K线数据——日线(`bars(freq=9)`)、周线(`bars(freq=5)`)、5分钟(`bars(freq=2)`)、沪深300指数(`index_bars`)、复权因子(`xdxr`)。60分钟/30分钟可从5分钟数据聚合（代码中已有 `MinuteDataManager._resample_minute()`）。所有请求0.0-0.1s完成。<br><br>**实施分三阶段**：第一阶段（长线先行）：新增 `DataManager` mootdx 数据管道，接入日线+周线+60分钟数据，启用 `MultiLevelChanlunAnalyzer`。第二阶段（中线扩展）：接入30分钟+5分钟K线数据，新增"中线分析"模式（背景=日线、决策=30分钟、执行=5分钟）。第三阶段（短线扩展）：接入1分钟K线数据，新增"短线分析"模式（背景=30分钟、决策=5分钟、执行=1分钟）。各级别独立配置笔参数（长线严格笔=5K线、中线宽笔=3K线+确认） |

### 2.4 信号层偏差

#### C1: 背驰方法缺少辅助验证（🟢 中等）

| 项目 | 内容 |
|------|------|
| **知识库要求** | 面积法为主（`A2 < A1 * 0.8`）、力度法为辅（`H2 < H1 * 0.75`）。两者同时确认为强信号。MACD参数短线可加快（6,13,5） |
| **当前状态** | `DivergenceConfig.macd_algo='area'` 仅面积法。`divergence_rate=0.9` 背驰阈值偏高。MACD固定(12,26,9) |
| **影响** | 单方法判断背驰，无法交叉验证。误判率高于"面积+力度"双确认 |
| **修复方向** | 增加力度法作为辅助验证。当两种方法同时确认时，背驰置信度×1.3。当面积法确认但力度法不确认时，置信度×0.7 |

### 3.2 详细任务清单

#### 批次P-1: 数据架构统一——全局数据体系

**架构原则**（严格执行）：
1. 所有K线数据**只能通过** `DataManager.get_kline_data()` 获取，策略和前端**不允许直接连接**数据源（mootdx/Tushare/AKShare）
2. 获取流程固定：**ECM缓存优先** → 未命中则从数据源获取 → 写入ECM持久化 → 返回
3. `DataManager` 是唯一的K线数据网关，`MinuteDataManager` 降级为DataManager内部的数据源适配器

**按需缓存（Cache-on-Demand）策略**：
- 不预采全市场分钟数据（5000只×15个月≈6亿行，不现实）
- 首次访问某只股票的某频率时，通过 mootdx `bars()` 获取约15个月历史数据，写入ECM持久化
- 同一股票的第二次及后续访问直接命中ECM缓存，**不再调用任何数据源**
- 每只股票首次加载仅需约0.1秒，后续0.00秒

```
首次访问:  DataManager.get_kline_data(ts_code, period='60m')
              → ECM查询: minute_kline_cache WHERE ts_code=? freq='60m'
              → ❌ 未命中
              → mootdx bars(freq=2) 获取5min数据 (0.05s)
              → _resample_minute() 聚合为60min
              → 写入 ECM minute_kline_cache

二次访问:  DataManager.get_kline_data(ts_code, period='60m')
              → ECM查询: minute_kline_cache WHERE ts_code=? freq='60m'
              → ✅ 命中 → 直接返回 (0.00s)
```

**当前问题**：
- `DataManager._get_minute_data()` 直调 Tushare 不经过 ECM 缓存 ❌
- `MinuteDataManager` 作为独立通道，与 `DataManager` 平级 ❌
- 前端 `routes/minute_data.py` 直接实例化 `MinuteDataManager` ❌
- 前端 `routes/chart.py` 分钟K线路径也走 `MinuteDataManager`，ECM未命中时直接回退到日线，**不触发按需采集** ❌
- 个股缠论分析 `_compute_chanlun_signal` 仅支持日线，不支持分钟级分析 ❌

| 编号 | 任务 | 文件 | 工作量 | 风险 | 前置 |
|------|------|------|--------|------|------|
| **P-1a** | `DataManager._get_mootdx_bars()` 封装 mootdx `bars()`/`k()`/`index_bars()`/`xdxr()`，统一返回标准化 DataFrame（列: ts_code, trade_date/trade_time, open, high, low, close, vol, amount）。**仅限DataManager内部调用，不允许外部直接使用** | `data/__init__.py` 新增私有方法 | 小(~30行) | 低 | 无 |
