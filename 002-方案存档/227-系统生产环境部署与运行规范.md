## 1. 系统定位

### 1.1 核心假设

| 假设 | 说明 |
|:-----|:------|
| 用户规模 | 自有团队数人，每人在各自单机独立运行，**不串联、不共享数据** |
| 使用场景 | 个人研究型 A 股分析工具，日常行情浏览 + 策略分析 + AI 投研 |
| 安装方式 | macOS: Platypus .app 封装 / Windows: Inno Setup .exe 安装程序 |
| 网络依赖 | 需要互联网（Tushare 数据源 / DeepSeek API），离线时使用本地缓存 + Mock |
| 数据量级 | 应用数据（交易/报告/规则）< 100MB/年，市场数据缓存 ~180MB（DuckDB）|
| 并发模型 | 单用户操作，无多用户并发场景 |


## 3. 存储层设计

### 3.1 数据目录选择

#### 原则

生产环境中，数据目录**不能放在应用安装目录下**，原因：
- macOS: `.app` 放在 `/Applications/` → 无权写入（SIP 保护）
- Windows: 安装到 `C:\Program Files\` → 无权写入（UAC 保护）
- 重装/升级应用时数据必须保留

#### 平台标准路径

| 平台 | 数据目录 | 说明 |
|:-----|:---------|:------|
| **macOS** | `~/Library/Application Support/Astock/` | macOS 标准应用数据目录，Time Machine 自动备份 |
| **Windows** | `%APPDATA%/Astock/` (即 `C:\Users\<用户名>\AppData\Roaming\Astock\`) | Windows 标准应用数据目录，Roaming 属性支持漫游 |

#### 目录结构

```
<DATA_DIR>/
├── app.db                   # SQLite 应用数据库（仅用于数据迁移中间状态，生产已迁移至 PG）
├── auth_token.txt           # 访问令牌持久化
├── duckdb/
│   ├── stock_cache.db       # DuckDB 市场数据缓存 (~180MB)
│   └── temp/                # DuckDB 临时目录
├── logs/
│   └── app.log              # 应用日志 (30天轮转)
└── (PostgreSQL 数据由 `brew install postgresql@16` 管理，默认在 `/opt/homebrew/var/postgresql@16/`)
```

> **重要：** 当前生产环境已迁移至 PostgreSQL，`app.db` 不再作为主数据库存储。SQLite 仅在数据迁移过渡期存在。

#### 自定义覆盖

用户可在 `.env` 中添加 `DATA_DIR=/path/to/custom/data` 覆盖默认路径。

#### 开发环境

开发时直接使用项目根目录下的 `data/` 文件夹。启动脚本在检测到开发模式时自动使用相对路径。

### 3.2 PostgreSQL — 业务数据库 + 盘中实时持久化

#### 变更背景

227 号原方案选择 SQLite 作为业务数据库，原因包括零依赖、零运维。但在实施过程中，以下因素促使恢复 PostgreSQL：

| 因素 | 说明 |
|:-----|:------|
| **Gunicorn 多 worker** | SQLite 单写入者在多 worker 场景下会频繁报错（database is locked）|
| **AkshareCollector 并发写入** | 采集器 5 线程与 Flask worker 同时写库，SQLite 无法处理 |
| **盘中实时数据** | 需要同时供多个 worker 读取一致的盘中快照 |
| **数据安全性** | PG 的 WAL + crash recovery 远强于 SQLite 的 rollback journal |

#### 当前 PostgreSQL 数据布局

| 类别 | 表数量 | 说明 |
|:-----|:-------|:------|
| 业务表（SQLAlchemy models） | 30+ | stocks, daily_data, strategies, notification_rules, accounts, playback 等 |
| 盘中实时表（纯 SQL upsert） | 8 张 | snapshot, top_stocks, sectors, concepts, limit_pool, minute_kline, lhb, news |
| 合计 | **38** | |

#### 盘中实时表详情

| 表名 | 写入频率 | 保留策略 |
|:-----|:---------|:---------|
| `realtime_snapshot` | 每 15s 全量覆盖 | 当天 |
| `realtime_top_stocks` | 每 30s 全量覆盖 | 当天 |
| `realtime_sectors` | 每 5min 全量覆盖 | 当天 |
| `realtime_concepts` | 每 5min 全量覆盖 | 当天 |
| `realtime_limit_pool` | 每 5min 全量覆盖 | 当天 |
| `realtime_minute_kline` | 每 5min 追加 | 30 天 |
| `realtime_lhb` | 每 30min 全量覆盖 | 当天 |
| `realtime_news` | 每 30min 全量覆盖 | 当天 |

#### PostgreSQL 连接配置

```
DATABASE_URL=postgresql:///stock_analysis
```
- 连接方式：本地 socket（无需密码）
- 连接池：`psycopg2.pool.ThreadedConnectionPool` 最小 2、最大 10
- 多 worker 隔离：每个 Gunicorn worker 独立创建 Flask-SQLAlchemy 引擎

### 3.3 DuckDB — 市场数据缓存

#### 现状

| 指标 | 值 |
|:-----|:----|
| 当前大小 | ~180 MB |
| 数据内容 | OHLCV 611万条、资金流向、日线基本面 |
| 更新模式 | Tushare 增量同步 (sync_stocks.py) |
| 写入来源 | EnhancedCacheManager |
| 读取来源 | 策略引擎 (strategies)、REST API 路由 |

#### 定位

- **OLAP 数据仓库**：专为时间序列分析优化（列式存储、向量化执行）
- **不可变数据**：Tushare 历史数据写入后只读，不会修改
- **不需要索引**：DuckDB 全表扫描 + 列式过滤的性能已足够（单用户毫秒级）

### 3.4 内存缓存 — 二级缓存架构（原 3.4 版已变更）

#### 变更背景

227 号原方案使用 TTLCache 完全替代 Redis，但在多 worker 场景下暴露出两个问题：
1. 每个 Gunicorn worker 拥有独立的 TTLCache 实例，数据不一致
2. 无法跨 worker 广播实时数据

当前实施采用 **二级缓存 + Redis pub/sub** 架构：

#### 架构

| 层级 | 组件 | 存储位置 | 跨 worker？ | TTL | 用途 |
|:-----|:-----|:---------|:------------|:----|:------|
| L1 热缓存 | **InMemoryStateStore** | 每个 worker 进程内 | ❌ 各自独立 | 直到下一次推送 | 盘中实时快照、WS 推送（O(1)读取）|
| L2 方法缓存 | **TTLCache** | 每个 worker 进程内 | ❌ 各自独立 | 1h | 热点 API 结果缓存 |
| L3 跨 worker | **Redis pub/sub** | 独立 Redis 服务 | ✅ 所有 worker | — | WebSocket 广播、APScheduler 锁 |

#### InMemoryStateStore

```python
# 纯 dict 存储，O(1) 读写
class InMemoryStateStore:
    def __init__(self):
        self._snapshot = {}       # 全市场快照
        self._top_stocks = {}     # 涨跌榜
        self._sectors = []        # 行业板块
        self._concepts = []       # 概念板块
        # ...
```

- AkShareCollector 每 15s-30min 更新 InMemoryStateStore
- WsBridge 每 15s 从 InMemoryStateStore 读取数据推送 WebSocket
- Gunicorn 启动时（`on_starting` hook）采集器写 L1 cache，worker 的 L1 从 PG 热启动

#### TTLCache（方法级缓存）

```python
from cachetools import TTLCache

class MemoryCache:
    def __init__(self, maxsize=1000, ttl=3600):
        self.cache = TTLCache(maxsize=maxsize, ttl=ttl)
```

保留为方法级缓存用途，减少重复计算和数据库查询。

#### Redis 定位

- **SocketIO message_queue**：多 worker 间 WebSocket 消息广播
- **APScheduler 锁**：防止多 worker 重复执行定时任务
- **不作为数据存储**：所有业务数据在 PostgreSQL + DuckDB 中持久化
- **不存储实时数据**：实时数据通过采集器直接写入 InMemoryStateStore + PG

## 4. macOS 启动方案

> ⚠️ **227 号原方案采用 Platypus .app 封装，已被 launchd 替代。**
> 当前生产环境使用 **launchd** (macOS 原生进程管理) 启动 Gunicorn 服务，
> 开机自启 + 崩溃自动重启。详见 `com.stock.analyzer.backend.plist`。

### 4.1 启动流程

```
机器开机 / launchctl load
  ↓
launchd 启动 Gunicorn (1-4 workers × gevent)
  ├─ on_starting hook:
  │   ├─ AkshareCollector 5 线程采集器启动
  │   └─ PostgreSQL 实时连接池初始化
  ├─ Worker 1-4 fork:
  │   ├─ 各自加载 Flask app + 路由注册
  │   ├─ 各自连接 PostgreSQL + Redis
  │   └─ 各自初始化 InMemoryStateStore（从 PG 冷启动）
  └─ when_ready:
      └─ 日志：服务就绪
  ↓
健康检查: http://localhost:5001/api/v3/health
  ↓
打开浏览器: http://localhost:5001
```

## 6. 进程管理

### 6.1 架构决策（2026-07-09）

系统由两个独立进程组成，分工不同，启动策略也不同：

| 进程 | 文件 | 职责 | 启动策略 | 原因 |
|:-----|:-----|:-----|:---------|:-----|
| **数据进程** | `data_daemon.py` | mootdx TCP 采集(5s)、日终同步(15:30)、分钟K线回填、完整性检查 | **launchd 开机自启** | 轻量(~50MB)，需交易时段全天采集，关闭系统时也在后台运行 |
| **API 进程** | `run.py` | Flask REST API、SocketIO 推送、前端SPA托管、策略分析 | **start.command 手动启动** | 较重(~200MB)，仅在用户查看系统时需要，不用时释放资源 |

### 6.2 用户使用流程

```
开机 → 数据进程 launchd 自动启动 → 后台静默采集
                                   ↓
用户双击 start.command → API 进程启动 → 浏览器自动打开
                                   ↓
用户完成使用 → Ctrl+C 关闭 API 进程 → 数据进程继续在后台采集
                                   ↓
下一交易日 → 数据进程已经采集好数据 → 双击 start.command 即可看到最新数据
```

### 6.3 macOS 实现

**数据进程 launchd plist**（新增，与API进程分离）：

```xml
<!-- ~/Library/LaunchAgents/com.stock.analyzer.datadaemon.plist -->
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.stock.analyzer.datadaemon</string>
    <key>ProgramArguments</key>
    <array>
        <string>/path/to/backend/.venv/bin/python</string>
        <string>data_daemon.py</string>
    </array>
    <key>WorkingDirectory</key>
    <string>/path/to/backend</string>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <true/>
    <key>StandardOutPath</key>
    <string>/path/to/backend/logs/data_daemon.log</string>
    <key>StandardErrorPath</key>
    <string>/path/to/backend/logs/data_daemon.log</string>
</dict>
</plist>
```

安装：
```bash
cp com.stock.analyzer.datadaemon.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.stock.analyzer.datadaemon.plist
```

**API 进程 start.command**（精简版，仅启动 API + 打开浏览器）：

```bash
DATA_DAEMON_RUNNING=1 .venv/bin/python run.py --port 5001 &

open http://localhost:5001/dashboard

```

## 8. 开发约束（开发者必须遵守）

> ⚠️ **227 号原方案假设数据库引擎为 SQLite，当前已变更。**
> 以下约束已更新以反映 PostgreSQL + Redis + Gunicorn 的生产要求。
> 开发环境仍然可以使用 SQLite（设置 `DATABASE_URL=sqlite:///instance/test.db`），
> 但盘中实时功能（realtime_* 表 + 采集器）需要 PG。

### 8.1 数据库引擎兼容性

> **生产环境数据库引擎：PostgreSQL 16（必选）+ DuckDB（盘后分析）**
> **开发环境可选：SQLite（需开启开发模式 `FLASK_ENV=development`）**

| 规则 | 说明 | 禁止项 |
|:-----|:------|:-------|
| 使用通用 SQLAlchemy ORM | 所有模型必须使用 SQLAlchemy 跨数据库通用的数据类型 | ❌ ARRAY、TSVECTOR、`func.now()`（SQLite 不兼容）|
| JSON 列使用 `db.Column(JSON)` | SQLAlchemy 自动适配 | ❌ `postgresql.JSON` |
| 布尔值使用 `db.Boolean` | SQLAlchemy 自动映射 | ✅ 兼容 PG & SQLite |
| 自增值使用 `db.Integer` + primary_key | SQLAlchemy 自动处理 | ❌ `SERIAL` |
| 时间戳使用 `db.DateTime` | 通用 | ❌ `TIMESTAMP WITH TIMEZONE` |
| 唯一约束使用 `UniqueConstraint` | 标准 | ✅ 通用 |

**当前代码状态**：✅ 所有模型文件使用通用 SQLAlchemy 类型，无需修改。

### 8.2 生产环境必需的外部服务

| 服务 | 状态 | 用途 | 替代方案（开发环境）|
|:-----|:------|:------|:-------------------|
| **PostgreSQL** | ✅ 生产必需 | 业务数据库 + 盘中实时持久化 | SQLite（但 realtime 功能不可用）|
| **Redis** | ✅ 生产必需 | SocketIO pub/sub、APScheduler 锁 | 单 worker 模式可跳过 |
| **Gunicorn** | ✅ 生产必需 | 1-4 workers × gevent 生产部署 | Flask dev server（开发调试）|
| **Nginx** | ❌ 不使用 | — | Gunicorn 直连 |
| **Docker Desktop** | ❌ 不使用 | — | 裸跑 |
