# 全局数据体系违规审计与架构整改方案

## 一、背景

选股系统在生产环境中出现"筛选超时，请重试"错误。经排查，根因是 `routes/screener.py` 中的
`load_stock_data_batch()` 使用 `use_cache=False` 参数逐只调用 Tushare API，绕过存储层直接访问采集层，
在开机后数据不充分时与 Data Daemon 竞争 API 配额，导致 5000 次 Tushare 调用远超前端 60s 超时阈值。

进一步全系统审计发现，该违规并非个案——`routes/` 和 `services/` 中共计 **10 个文件、20+ 处位置**
存在类似违反《全局数据体系架构红线》的代码。

## 三、系统性质因分析

违规非偶然，是三层系统性原因所致：

### 原因 1：无数据就绪保障机制的架构缺陷

```
Data Daemon 异步启动 → 完整性检查(3-5min) → API 进程已接受请求
  (数据尚未就绪)                                (缓存为空→违规降级)
```

调用层不知道"数据是否就绪"，也没有等待机制，因此每个端点自我兜底。

### 原因 2："先查缓存，查不到直调"的双路径反模式

```python
# 当前反模式（出现于 7+ 个端点）
ecm = get_ecm_instance()
df = ecm.get_cached_xxx(ts_code)
if df.empty:
    tp = TushareProvider()           # ← 违规：绕过三层直调
    raw = tp.get_xxx(ts_code)
```

### 原因 3：红线规则无执行机制

AGENTS.md 规则是纯文档——无 linter 规则、无代码审查 check-list、无运行时防护。
`new TushareProvider()` 在路由中编译和运行都不会产生任何告警。

## 四、整改方案

### 4.1 新架构：异步队列驱动的数据就绪机制

```
┌────────────────────────────────────────────────────────┐
│                    前端 (Frontend)                       │
│  60s 超时 → 改为轮询 + 进度提示                          │
└─────────────────────┬──────────────────────────────────┘
                      │ REST API (只读存储层)
                      ▼
┌────────────────────────────────────────────────────────┐
│        调用层 (Call Layer) — routes/ + services/         │
│  ┌──────────────────────────────────────────────────┐   │
│  │ DataManager (唯一网关)                            │   │
│  │  .get_*() → 有数据直接返回                          │   │
│  │  .request_data() → 写 sync_requests 表，返回空      │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────┬──────────────────────────────────┘
                      │ 存储层
                      ▼
┌────────────────────────────────────────────────────────┐
│    存储层 (Storage Layer) — SQLite WAL + 内存            │
│  sync_requests 表:                                      │
│  id | task_type | ts_code | status | requested_at       │
└─────────────────────┬──────────────────────────────────┘
                      │ daemon 30s 轮询
                      ▼
┌────────────────────────────────────────────────────────┐
│    采集层 (Collection Layer) — data_daemon.py            │
│  30s 主循环:                                            │
│  1. SELECT * FROM sync_requests WHERE status='pending'  │
│  2. 执行 _batch_daily() / _batch_moneyflow() / ...      │
│  3. UPDATE status='done'                                │
│  4. 自动触发计算层预计算                                  │
└─────────────────────┬──────────────────────────────────┘
                      │ 写入
                      ▼
┌────────────────────────────────────────────────────────┐
│    存储层 → 计算层 (自动预计算) → 存储层                    │
└─────────────────────┬──────────────────────────────────┘
                      │ 调用层轮询到 done → 重新读取 → 返回
```

### 4.2 分层整改计划

#### P0 (即刻修复 — screener.py 超时问题)

| 改动项 | 文件 | 内容 |
|--------|------|------|
| 去 `use_cache=False` | `routes/screener.py:102` | 改为 `use_cache=True` |
| 去 `sync_stock_list()` | `routes/screener.py:414-417` | 依赖 daemon 先行完成 |
| 前端超时提升 | `_ui-prototype/screener.html:554` | 60s → 120s + 数据预热提示 |

#### P1 (核心违规 — routes/ 中直调 Provider)

| 文件 | 违规路径 | 整改策略 |
|------|----------|----------|
| `market.py quote` | TushareProvider 降级 | 去降级，返回 ECM cache；无数据则返回 503 + DataUnavailable |
| `market.py moneyflow` | TushareProvider 降级 | 同上 |
| `realtime.py` | 3 个 Provider 实例 | 去 Provider，依赖 data_daemon 推送 InMemoryStateStore |
| `backtest.py` | TushareProvider.test_connection() | 改为检查 ECM 健康状态 |

#### P2 (服务层违规 — services/ 中直调 Provider)

| 文件 | 违规路径 | 整改策略 |
|------|----------|----------|
| `backtest_service.py` | 2 处 TushareProvider | 改为 DataManager 只读，数据由 daemon 预加载 |
| `ai_context_builder.py` | TushareProvider | 改为 DataManager 只读 |
| `research_pipeline.py` | TushareProvider | 改为 DataManager 只读 |
| `market_service.py` | AkshareProvider | 由 daemon 指数数据推送替代 |

#### P3 (基础设施 — sync_requests 队列机制)

| 改动项 | 说明 |
|--------|------|
| 新增 `sync_requests` SQLite 表 | task_type, ts_code, status, requested_at, completed_at |
| DataManager `.request_data()` 方法 | 写 pending 记录 |
| DataManager `.poll_data_ready()` 方法 | 检查 status=done |
| data_daemon 30s 循环消费 | `SELECT * FROM sync_requests WHERE status='pending'` → 批量同步 → 标记完成 |
| 前端异步任务轮询 | 对重任务返回 task_id，前端轮询状态 |

### 4.3 降级策略规范（修订 §13 规则）

**生产环境数据缺失时的降级优先级（修订后）：**

```
1. 缓存数据（ECM 最近一次成功数据，返回 cached_at）  ✅ 允许
2. 空结构（空列表/空对象，前端展示空状态）             ✅ 允许
3. HTTP 503 + DataUnavailable 错误信息               ✅ 允许
4. Queue sync_requests → daemon 异步补 → 下次请求成功 ✅ 新增
-----------------------------------------------------
❌ 禁止：直调 TushareProvider/AkshareProvider/mootdx
❌ 禁止：use_cache=False
❌ 禁止：任何在调用层/服务层实例化数据源 Provider 的行为
```

## 六、AGENTS.md 修订要点

同步修订 AGENTS.md 的以下部分：

1. **红线规则 1**：扩大适用范围——"**所有非采集层代码**（包括 routes/ 和 services/）禁止..."
2. **新增红线规则 7**：禁止 `use_cache=False` 参数在非采集层代码中使用
3. **新增红线规则 8**：数据缺失时禁止任何形式的"直调外部数据源"降级，必须走 sync_requests 队列
4. **§13 数据完整性**：更新降级优先级，加入 sync_requests 异步补采路径
