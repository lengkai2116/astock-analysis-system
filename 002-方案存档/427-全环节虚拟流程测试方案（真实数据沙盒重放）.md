# 427 — 全环节虚拟流程测试方案（真实数据沙盒重放）

> **性质**：本方案为**测试方案**（纯核查/模拟运行）。**不改方案、不改代码、不触碰生产数据**——
> 在完全隔离的沙盒数据副本上，用真实数据（2026-09-11 交易日为基准）驱动
> COL→RAW→(STG 分库写入+QA)→SIG→JUD→OUT 全环节重放，检验 426 修复后的管道
> 各环节是否仍存在问题。
>
> **背景**：426 号方案五阶段已全部实施并验证（代码改动全部在工作区未提交），
> 但**收尾后的"全链路当日回归"因 daemon 未恢复而尚未执行**（426 遗留待办）。
> 本方案利用周六非交易日 + daemon 停运的空窗，以**虚拟重放**替代真实日终运行，
> 提前暴露管道现存问题，为 daemon 恢复后的真实回归提供预检与基线。

**① 采集函数可直接调用（接受 trade_date 参数，单次 API 全市场）**

**② 幂等性表级实测（避免重复存储的关键保障）**——全部 COL 目标表具 PK/唯一约束，写路径 `INSERT OR REPLACE`：

| 表 | 约束（DDL 实测） | 幂等性 |
|---|---|---|
| daily_cache | `PRIMARY KEY (ts_code, trade_date)` | ✅ REPLACE |
| stk_limit_cache / margin_cache / lhb_cache | 同上 PK | ✅ REPLACE |
| concept_cache | `PRIMARY KEY (ts_code, concept_code)` | ✅ REPLACE |
| daily_basic_cache / moneyflow_cache | 唯一 autoindex（隐式 PK） | ✅ REPLACE |

写路径 `_insert_from_df` 统一 `INSERT OR REPLACE`（enhanced_cache_manager.py:271-288）→ **重采 = 覆盖更新，不产生重复行**。
> 对照：426 报告中的重复存储问题（factor_cache / adj_factor_cache_2026 14×）恰发生在**无主键**表——COL 六表无此风险。
> 实测佐证：09-11 当日 daily_cache 稳定 5,553 行，历史上反复采集未翻倍。

**③ 网络与凭据前提成立**

| 项 | 核查结果 |
|---|---|
| Token | tushare 库缓存有效（实测 `ts.pro_api()` 就绪）；`.env` 亦含 TUSHARE_TOKEN |
| 网络保障 | `_ts()` 带速率限制（≤5 次/秒）+ 网络超时保护（`_TS_CALL_TIMEOUT`，超时跳过不阻塞主循环，429 号根治） |

## 4. 测试设计（沙盒重放方案）

### 4.1 设计核心

```
┌─ 生产 data/（25G，只读基线）─┐      ┌─ 沙盒 data_virtual_test_20260912/（cp -c 零拷贝克隆）
```

### 4.2 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **克隆后启动完整 daemon**（而非脚本跳步） | 状态机自然推进 = 真实调度逻辑验证；每环节触发条件/依赖判定/重试/QA 门禁全走真路径 |
| D2 | 沙盒内重置 09-11 管道状态为 pending | `_drive_pipeline` 数据驱动：09-11 已全 done 则不会重跑；重置模拟"日终待处理" |
| D3 | **COL 环节先真实联网采集（沙盒内），再走完整性判定** | v1.1：COL 分两步验证——①步骤 2.5 直接调用 `_batch_*('2026-09-11')` 真实联网采集，验证采集有效性（§4.4）；②步骤 3 管道重放时 COL-1~6 对已采完整数据走"数据已完整→done/跳过"，验证完整性判定逻辑。两者互补、不冲突 |
| D4 | 全程不新增脚本、不改代码 | 完全复用现有 daemon；沙盒内仅执行 SQL 状态重置（对沙盒数据，非生产） |
| D5 | 基线先于重放采集（只读） | 所有对比以"重放前生产快照"为锚，判定矩阵数值与基线对齐 |

### 4.4 COL 真实联网采集设计（v1.1 新增，对应步骤 2.5）

**目的**：用真实网络请求采集上一个交易日（2026-09-11）日终数据到**沙盒分库**，验证 COL 采集环节有效性，
并判别 E1/E2 已知缺口（stk_limit 42%、margin 缺 09-11）是"数据源延迟"还是"采集逻辑缺陷"。

**执行方式**（沙盒内一次性 Python 调用，复用现有函数，不新增采集代码）：

```python
# 一次性驱动（临时脚本或 python -c，仅用于测试，非系统代码）
import os
os.environ['DATA_DIR'] = '<项目根>/data_virtual_test_20260912'   # 沙盒
import data_daemon as dd
dd._ensure_ecm()                                   # 初始化 ECM（读沙盒配置）
results = {}
for name, fn, arg in [
    ('COL-1 daily',    dd._batch_daily,        '2026-09-11'),
    ('COL-2 basic',    dd._batch_daily_basic,  '2026-09-11'),
    ('COL-3 moneyflow', dd._batch_moneyflow,   '2026-09-11'),
    ('COL-4 stk_limit', dd._batch_stk_limit,   '2026-09-11'),
    ('COL-5 lhb',      dd._batch_lhb,          '2026-09-11'),
    ('COL-6 concept',  dd._batch_concept,      None),
]:
    try:
        results[name] = fn(arg) if arg is not None else fn()
        print(f'{name}: 返回 {results[name]} 行')
    except Exception as e:
        print(f'{name}: FAILED {e}')
```

**关键设计约束**：
1. **DATA_DIR 必须在 import data_daemon 之前设置**（`data_daemon.py:22` setdefault 在模块加载时执行）——确保 ECM/分库管理器指向沙盒；
2. **绕过管道跳过逻辑**：直接调用 `_batch_*` 而非 `_drive_pipeline`（后者对完整数据标记 done 跳过）；
3. **幂等保障**：写路径 `INSERT OR REPLACE` + 表级 PK（§2.4-②）→ 重采覆盖更新，无重复行；
4. **采集后立即核验**（§5.2 C-5~C-8），确认落库行数 == 基线（无重复）且 stk_limit/margin 缺口变化；
5. **不采 COL-7 财务**（`_batch_fina_indicator` 等逐只调用、耗时 6,308s/日，非本次验证目标；财务数据 end_date 06-30 已存在，仅验证存在性 C-3）。

**执行顺序**：步骤 2（沙盒克隆+重置）之后、步骤 3（管道重放）之前。
**失败处理**：任一表采集异常（网络/API）→ 记录 FAIL 原因，**不阻断**后续重放（重放时 COL 走"数据已完整→跳过"，用沙盒内既有数据继续）。
