# 333 — P2 分析单元原料供给与双渠道稳定性方案

> **分档定位**：本方案是 **332 号总纲（现状判定引擎统一方案 v3.0）的补充分档**，聚焦总纲中"P2 归位为分析单元（消费端）、标签=原料仓（原料双层）"定位下的落地问题——**① P2 各策略引擎的原料供给核查（消费标签免重复计算、哪些必须原始数据）② 标签+原始数据双渠道调用的稳定性评估与处理 ③ P2 引擎合理性评判 ④ 标签引擎与 P2 引擎的输出整合**。332 号总纲的判定流水线（原料仓→生产环节→成品仓→双模块）以此方案为 P2 环节的落地依据。
>
> **v2.0 修订（08-14，沟通纪要 013-014，用户确认）**：Vibe 引擎从 P2 完全剔除（P2 收敛为 6 引擎，Vibe 后续在机会图谱板块单独建设"个性地图搜索"模块）；整合 4 问深度评估结论。
>
> **v3.0 修订（08-14，沟通纪要 016，用户确认——P2 定位方向修正）**：
> ① **P2 是消费端，不是生产端**：P2 并入生产环节、与现状判定同一维度，**消费标签（主原料）+ 原始数据（深度计算补充）**——不生产标签；
> ② **标签是底层计算的归属方**：P4 标签引擎把缠论/筹码/量价等初加工算好落成标签，P2 消费其结果，避免同算法双算；
> ③ **"共享计算内核"正确含义**：底层计算组件由 P4 统一执行，P2 消费其结果——而非"P2 先算、标签派生"（v2.0 表述错误，已修正）；
> ④ **时序问题靠管道顺序调整**（P4 标签先算当日 → P2 后算消费当日标签），而非反转上下游。

## 一、背景与定位

### 1.1 背景

332 号总纲 v3.0 确定：**P2 为分析单元（消费端）并入生产环节、构成 L1 实现；标签体系为原料仓（原料双层：标签库 + 原始数据表）**。由此产生必须落实的问题：

1. **原料供给**：P2 的 6 个策略引擎（v2.0 剔除 Vibe）消费哪些标签原料可避免重复计算与数据偏差？哪些深度计算必须用原始采集数据（标签无法还原）？
2. **双渠道稳定性**：P2 从标签体系和原始数据双渠道调取原料，是否影响系统稳定运行？存在哪些风险与处理点？
3. **引擎合理性**：P2 引擎的分析逻辑对照 LLM Wiki 知识库是否合理？提升空间在哪？
4. **输出整合**：标签引擎与 P2 引擎输出是否存在重复/精度差异？如何整合提升质量？

### 1.2 定位

- **归属**：332 号总纲的分档实施细节（总纲管"流水线架构"，本方案管"P2 环节的原料、稳定性与整合"）；
- **P2 定位（v3.0 确认）**：P2 = **分析单元（消费端）**，并入生产环节与现状判定同一维度；**消费标签（主原料）+ 原始数据（深度计算补充）**，**不生产标签**；
- **前置**：与 332 号 P0（生产引擎健康修复：`signal_computation_service.py:945/:2461`）配套——P0 修复引擎健康，本方案确定引擎原料供给与整合；
- **范围**：仅 P2 分析单元（6 策略引擎 + 共享 market_context），不涉及 P4 标签管道本身；
- **Vibe 剔除**（v2.0）：Vibe 引擎（AI 模板执行，知识库无对应、合理性最弱）**完全移出 P2**；其"个性地图搜索"能力后续在机会图谱板块单独建设，本方案不再涉及。

## 二、P2 六引擎原料供给核查（explore 子代理逐引擎审计，2026-08-14）

### 2.1 消费标签可避免重复计算（3/6 引擎——v3.0：P4 统一计算落标签，P2 消费）

| 引擎 | P2 当前计算 | 标签侧已独立算过的结论（329 号/P4 实证） | 处理建议（v3.0：P2 消费标签） |
|---|---|---|---|
| **筹码引擎**（全系统最重） | 重算 120 日筹码分布 + 财务六大禁区 + 假机构 + 龙虎榜战法（约 10 类数据源） | 筹码深度组 17（chip_peak/asr/cyqkl/profit_ratio/ssrp，ChipIndicators 已算）+ 阶段主力组 8 + 资金风险组 2 + fina_health + fake_institution | **P2 消费标签结论，不重算筹码分布**（P4 标签引擎统一计算落标签；P2 仅对标签未覆盖的深度派生用原始数据补充；消除最重引擎重复计算，P2 管道 1.6h 历史耗时主要削减点） |
| **量价引擎** | VolumePriceStrategy 完整 analyze 四段链（Stage+量态+9 类 VP 关系+MACD 背离） | 量价方向组 8（volume_price_fit/pattern_signal 等，**get_tags 仅粗启发式 5 条 + _add_vp_simple_tags 再算——全系统 3 处量价逻辑并存**） | **统一量价判定到单一权威**：P4 标签量价标签由 P2 量价引擎完整 analyze 派生（或共用同一组件），get_tags/_add_vp_simple_tags 两处粗逻辑废弃——P2 消费量价标签结论 |
| **情绪引擎（BOCIASI 快线）** | 快线指标（量比/动量/振幅） | 情绪板块组 sentiment_phase（MarketSentimentService 全市场情绪周期，涨停池视角） | 情绪维度双视角保留（涨停池 vs 指数趋势）作交叉验证；快线结论与标签情绪周期对齐，P2 消费标签情绪结论 |

### 2.2 必须用原始采集数据（标签无法还原计算）

| 引擎/输入 | 原因 |
|---|---|
| **缠论引擎（深度部分）** | 中枢/背驰/三级别笔线段计算**必须原始 K 线序列**（含多周期 W/60m/30m/5m）——标签只有结论枚举（state_label/support_resistance），**无法还原计算**；但**买卖点结论可直接消费标签 buy_sell_point**，仅深度计算（背驰置信度/中枢区间细节）用原始数据 |
| **BOCIASI 慢线** | ERP 计算需**指数数据**（benchmark index）+ PE_TTM（国债收益率现硬编码 2.85，建议接真实源）——指数不在标签里 |
| **因子引擎** | factor_cache 为共享源（标签聚合与 P2 同用）——本身已非重复计算，读缓存即可 |
| **market_context（共享）** | daily_basic（换手/市值/PE/PB）+ 指数 + moneyflow 明细——标签只有汇总，明细不在标签 |
| **量价形态细节** | 若需 active_pattern 增强形态细节，pattern_signal 标签仅主形态——需原始 K 线 |

### 2.3 原料供给结论（v3.0）

- **P2 消费标签（主原料）：筹码/量价/情绪 3 引擎**——筹码收益最大（省 120 日筹码分布重算）；
- **P2 用原始数据（深度补充）：缠论深度（中枢/背驰/多周期 K 线）/指数/BOCIASI 慢线/market_context 明细**；
- **定位（v3.0 核心）**：P2 = 消费端，**消费标签结论为主 + 原始数据补深度**，**不生产标签**；底层计算由 P4 标签引擎统一执行落标签，P2 复用其结果避免同算法双算；
- **时序保障**：靠**管道顺序调整（P4 标签先算当日 → P2 后算消费当日标签）**，杜绝"P2 消费昨日标签"（详见 3.1）。

## 三、双渠道调用稳定性评估（4 风险 + 3 处理点）

### 风险 1（最重要）：管道时序错位——P2 消费标签可能拿到"昨日标签"

- **实证**：daemon `_run_precompute` 中 **P2 策略信号（data_daemon.py:1531）在 P4 标签（:1556）之前执行**——若 P2 消费标签作原料，拿到的是**前一日盘后**标签（当日 P4 未算），而原始数据是**当日**的 → 混合输入时序错位（"标签昨日说上升、今日 K 线已跌破"），是"数据偏差"的核心来源。
- **处理（v3.0 方向）**：**调整管道顺序——P4 标签先算（当日）→ P2 后算（消费当日标签）**；同时保留"标签日期 ≥ 数据日期"校验兜底（日期不一致的标签降级为辅助参考）。**不再采用"P2 先算、标签派生"方案（v2.0 表述错误，已废弃）**。

### 风险 2：SQLite 跨进程锁竞争（已知历史问题）

- 历史记录：**"daemon 指数回填 database is locked（历史性，07-24 起存在；API+daemon 共享 stock_cache.db 锁冲突）"**。
- **项目锁处理现状（实测）**：WAL 模式（读不阻塞写）+ **读写分离连接**（read_conn，2026-08-11 根治 daemon 内部多线程写）+ **busy_timeout=30s**（2026-08-12 从 5s 提升）+ checkpoint 机制（PASSIVE/TRUNCATE，wal_maintenance L2）+ 写批量化（500/commit）。
- **处理（轻量预调）**：① daemon 内部写串行化（单写队列，根治剩余并发写）② P2 引擎计算缓存扩展（analysis_cache 已有 chanlun/vp 雏形 → 扩到全部引擎），**API 实时计算回退（4.5-6s）改为读预计算缓存** ③ **不做只读副本库**（双库同步成本高，收益边际递减）。

### 风险 3：双渠道结论打架（标签 vs 原始数据不同步）

- **处理**：统一"原料日期基线"——管道顺序调整后 P2 消费当日标签 + 当日原始数据，天然一致；判定引擎对日期不一致的原料标注或降级。

### 风险 4：性能（净收益为负）

- 每引擎多一次标签读取（毫秒级、可缓存），全市场影响可控；
- **P2 消费标签（省 120 日筹码重算等）收益远大于多读开销**——双渠道不是负担，反而提速。
- **处理**：标签读取走 DataManager 网关缓存（现有 TTL 缓存），不做逐只直查。

### 4.2 标签引擎与 P2 引擎的关系（explore 逐引擎比对 10 个标签引擎）

| 关系类型 | 标签引擎 | 处理原则（v3.0：P4 统一计算，P2 消费） |
|---|---|---|
| **同算法重复计算**（3 个） | PhaseDetectionEngine / ChipDistributionEstimator / ChanlunAnalyzer（组件级复用 TradingPhaseDetector/StageDetector/ChipIndicators/ChanlunAnalyzer 内核） | **P4 标签引擎统一执行底层计算落标签，P2 消费其结论**——消除双算；P2 仅对标签未覆盖的深度计算用原始数据补充 |
| **同主题不同算法**（2 个） | VolumePriceStrategy.get_tags / TimeRhythmEngine | **统一高精度权威**——量价以 P2 完整 analyze 为权威（标签量价标签由它派生），粗启发式废弃 |
| **异源同主题**（1 个） | MarketSentimentService（涨停池 vs P2 指数趋势） | **保留双视角交叉验证**（知识库"多维交叉验证"原则） |
| **部分同源**（2 个） | SectorRotationModel / EventMonitor | 算法不同，保留 |
| **无重叠**（2 个） | ValuationEngine / PotentialEngine | **保持独立**（P2 没有的维度，不归入 P2） |

**结论**：标签引擎**不"归入 P2"**，按上述三类处理——同算法由 P4 统一计算落标签（P2 消费）、同主题统一精度、异源保留交叉验证、独立维度保持。

### 4.3 输出整合三原则（提升精确性与质量，v3.0 方向修正）

1. **P4 统一底层计算、P2 消费（消灭双算与精度分裂）**：缠论/筹码/阶段/量价的底层计算由 **P4 标签引擎统一执行落标签**，P2 引擎**消费标签结论**（免重复计算），仅对标签未覆盖的深度计算（背驰置信度/中枢细节/多周期 K 线）用原始数据补充——单次计算、双端消费、精度分层；
2. **异源视角保留（交叉验证）**：情绪（涨停池 vs 指数趋势）保留双视角，知识库"多维交叉验证"——不整合；
3. **标签升级证据引用（提升输出质量）**：标签从"粗枚举"升级为"**枚举 + 证据引用**"（引用底层计算的 evidence），使标签消费方（treemap/diagnose/P2）都能展示证据链。
