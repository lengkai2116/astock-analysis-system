## 1. 页面结构概览

复盘中心是虚拟实盘跟踪模块，对从 indicator-ide 加入复盘池的策略信号进行**多股票×多日期×多策略**的持续模拟跟踪和复盘分析。

### 1.1 布局结构

```
┌─ header-bar ───────────────────────────────────────────────────────────┐
│ ⏪ 复盘中心          [📊 深度分析] [生成总览报告]                        │
├─ fund-bar (7项) ────────────────────────────────────────────────────────┤
```

### 1.3 数据流

```
indicator-ide (个股策略分析)
  │ 用户点击"加入复盘池"
  │
  ├─ review_pool_entries_v2 [localStorage]
  │    = [{ meta, strategy_config, dimension_outputs, ... }]
  │
  ▼
playback (复盘中心)
  │
  ├─ initPlaybackPage() → 加载localStorage数据
  │   ├─ loadPoolData() → review_pool_data_v2 (已持久化池)
  │   ├─ autoAdvance() → 模拟推进日期 (simulateDay循环)
  │   ├─ readNewEntries() → review_pool_entries_v2 (新条目)
  │   └─ mergeNewEntries() → 合并入 _reviewPool 数组
  │
  ├─ 三阶段模拟执行引擎 (全量Mock)
  │   └─ simulateDay(currentDate)
  │       ├─ pending→holding: allocatePosition()
  │       ├─ holding→completed: closePosition() (stop_loss/take_profit/circuit_breaker/signal_reversal/time_stop)
  │       └─ 账户更新: _accountState 实时计算
  │
  ├─ 九维诊断 (模拟)
  │   └─ generateRealAnalysis(unit)
  │       ├─ Layer1: dimScore + conflictScore
  │       ├─ Layer2: verifyScore
  │       ├─ Layer3: arbScore + scenarioScore
  │       ├─ Layer4: entryScore + exitScore
  │       └─ Layer5: slScore + capScore → totalScore + root_layer
  │
  ├─ 报告存储 → localStorage
  │   ├─ review_reports (元数据数组)
  │   ├─ review_report_data_{id} (完整报告)
  │   └─ report_diagnosis_collection (诊断汇总)
  │
  └─ 报告下载 → JSON Blob
       ├─ downloadReport(reportId) → 单份
       └─ downloadAllDiagnoses() → 全量
```

### 1.4 跨页通信协议（localStorage）

| Key | 类型 | 生产者 | 消费者 | 说明 |
|:----|:-----|:-------|:-------|:------|
| `review_pool_entries_v2` | entry[] | indicator-ide | playback | 新加入的复盘条目列表（含完整 v2 结构） |
| `review_pool_data_v2` | {units[], account, nextId, simDate, _version:'v2.1', last_updated} | playback | playback | 完整池状态持久化 |
| `review_badge_count` | number | indicator-ide | playback + indicator-ide | 新条目计数（侧栏badge） |
| `review_reports` | report[] | playback | playback + reports-center | 已生成报告元数据 |
| `review_report_data_{reportId}` | report object | playback | playback | 完整报告诊断数据 |
| `report_diagnosis_collection` | diagnosis_summary[] | playback | playback | 全量报告的diagnostic_summary聚合 |

### 4.3 模拟执行引擎核心逻辑

原型中整个模拟执行引擎在浏览器端实现，需后端化：

```python
# 每日模拟推进
def simulate_day(pool: List[ReviewUnit], account: AccountState, market_data: Dict[str, DailyBar]) -> ExecutionResult:
    for unit in pool:
        if unit.stage == 'pending':
            days_since = days_between(unit.meta.snapshot_date, current_date)
            if days_since > 30:
                mark_expired(unit)  # 30日未触发 → 标记废弃
            else:
                dd = market_data.get(unit.meta.ts_code)
                if dd and check_entry_condition(unit, dd):
                    allocate_position(unit, account, current_date)

        elif unit.stage == 'holding':
            unit.holding_days += 1
            dd = market_data.get(unit.meta.ts_code)
            if not dd: continue
            unit.current_price = dd.close
            unit.unrealized_pnl_pct = (dd.close / unit.entry_price - 1) * 100

            # 触发条件（按优先级）
            if check_circuit_breaker(account):       # 最高：熔断
                close_position(unit, account, dd.close, 'circuit_breaker')
            elif check_stop_loss(unit, dd):          # 止损
                close_position(unit, account, dd.low, 'stop_loss_hit')
            elif check_take_profit(unit, dd):        # 止盈
                close_position(unit, account, tp_price, tp_name)
            elif check_signal_reversal(unit, dd):    # 信号反转
                close_position(unit, account, dd.close, 'signal_reversal')
            elif unit.holding_days >= 60:            # 超时平仓
                close_position(unit, account, dd.close, 'time_stop')
    update_account(account, pool)
```

止损/止盈/熔断判断规则（203号§6.2-6.3）：
- **止损**：当日最低价 ≤ 止损价 → 止损价平仓
- **止盈**：当日最高价 ≥ 止盈价 → 止盈价平仓（两档：Tier1半仓/Tier2全仓）
- **ATR调整**：止损距 < ATR×1.5 → 仓位减半
- **熔断**：账户回撤 ≥ 2% → 强制平仓所有持仓

## 跨模块依赖与数据约束

| 方向 | 模块 | 依赖说明 |
|:-----|:-----|:---------|
| ⬇️ 依赖上游 | 个股策略 #215 | 复盘池来源：indicator-ide「加入复盘池」按钮写入 `ReviewUnit` |
| ⬇️ 依赖上游 | 策略引擎 | 九维诊断分析依赖策略引擎的真实信号输出（非 Math.random）|
| ⬇️ 依赖上游 | DuckDB 缓存 | 模拟引擎 `simulateDay()` 需真实 OHLCV 数据驱动 |
| ⬇️ 依赖上游 | 账户管理 #226 | review-link 需从 account 模块查询同股票交易记录 |
| ⬆️ 下游消费 | 报告中心 #223 | 复盘生成的诊断报告需写入 reports 模块 |
| ⬆️ 下游消费 | 账户管理 #226 | RV-xxx 诊断结论被账户管理六维复盘引用作为策略执行维度的依据 |

**数据约束：**
- **后端就绪度全站最低（~0%）**：v1 playbook.py 服务于完全不同的概念（单股时间轴回放），不可直接复用
- 模拟引擎应读取 DuckDB 真实 OHLCV，不可复用前端的 `Math.random()`
- 九维诊断的根因层（root_layer）需与 `StatusOutputService.aggregate()` 的输出结构一致
- 报告下载格式：JSON 结构（供开发平台审阅），MD 格式（供周期报告）

### 数据定时获取

参见 [229号方案 §3.1](229-系统定时机制全面分析报告.md) 数据获取定时需求表。

- **核心定时依赖**：模拟引擎 `simulateDay()` 需要**日终事件驱动**——每次 `daily_close_sync` 完成后触发模拟引擎推进一个交易日
- **数据类型**：日线 OHLCV（日终）、复权因子（日终）、ATR 指标（日终重算）
- **事件链路**：daily_close_sync → 模拟引擎日推进 → 仓位损益计算 → 止盈止损触发 → 通知
- **缓存策略**：详见本文 §6 缓存策略表（10s/30s/1h 三级 TTL），日终事件后全量失效
