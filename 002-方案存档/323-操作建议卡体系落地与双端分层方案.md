# 323 — 操作建议卡体系落地与双端分层方案

> **背景**：2026-08-09 基于 LLM Wiki《量化系统面向非量化分析师的操作建议设计》（建议卡 10 字段体系）评估操作建议输出优化。经评估确认用户定位：**机会图谱弹窗=快速浏览入口（精简），个股策略分析=深度分析页（承载完整建议卡）**。
>
> **前置**：322 号已实现 `operation_advice` 基础结构（state/七维红绿灯/几何/情景概率/executable），且已修复两套引擎结论统一（真实标签优先）+ signal_strength 满分 bug。
>
> **架构演进（2026-08-09 多轮讨论，全量记录）**：
> - **一轮**：双端分层定位（弹窗精简 + 个股页完整卡）；
> - **二轮**：双引擎统一——深度字段（约 20 个）从 strategy_signal_detail 迁移至 opportunity_tags_cache，实现"单一标签库 + 两引擎差异化取用"，根治 P4/P2 管道分叉（000975 实证）；
> - **三轮**：① 核实**引擎B 几何 K线读 daily_cache 日终数据（08-07），非盘中实时**——与全量预计算无冲突；② 核查**双操作建议输出存在 3 处执行层冲突**（止损/仓位/入场），提出**执行层统一（方案A）**；③ 明确 **S0 定位 = 执行层统一 + 深度字段预计算**；
> - **四轮（方案审查修订）**：补齐 6 处遗漏——① `tag_group` 列已存在且现有值域为 derived/direction/environment/position/quality/unknown（非设想 screen）；② `time_rhythm` 实际值域（unknown/approaching_turn/early_consolidation/mid_consolidation）与映射表不符，已校准；③ `evidence_count` 值域 0-5（峰值 3），置信度阈值 ≥5→≥4 校准；④ **方案A 影响机会库（advice_generator/opportunity_library 消费 operation_advice）**，需同步格式切换；⑤ 弹窗本地近似保留（初屏秒开）；⑥ `_build_trade_plan` 标记废弃而非直接删除（机会库迁移完成后删）。

## 〇、双引擎数据底座与计算时机澄清（三轮核实结论）

### 0.1 两引擎的计算时机（实证）

| 数据 | 表 | 计算时机 | 是否全量 |
|------|-----|---------|:---:|
| K线 | `daily_cache` | **日终批量采集**（最新 08-07，631 万行） | ✅ |
| 五维信号 | `strategy_signal_detail` | 日终预计算（20260807） | ✅ |
| 标签 | `opportunity_tags_cache` | 日终预计算（内容基于 08-07） | ✅ |
| 盘中实时 | `as_market_snapshot` | 盘中 5s 采集（当前 0 行） | ⏱ 盘中 |
| 机会图谱地图 | `treemap_snapshot` 快照 | S1 日终预计算（5566 只，46 列） | ✅ 全量 |
| 弹窗/个股页操作建议 | diagnose/analyze 组装 | **点击时组装**（读预计算数据） | ⏱ 按需 |

### 0.2 关键澄清：引擎B"实时"= 组装动作，非实时数据

**引擎B 几何指标**（advice_builder → `get_cached_daily_data` → `daily_cache`）**读的是日终 K线**（08-07），**不是盘中实时**。所谓"实时"仅指**点击时组装**（读预计算数据 → 算几何 → 拼建议卡），毫秒级，**无任何实时采集/重算**。

**结论：引擎B 与机会图谱全量预计算无冲突**——所有底层数据都是日终预计算，两引擎数据同源（daily_cache + 标签库），仅组装时机不同（地图=日终全量，建议卡=点击组装）。

### 0.3 机会图谱"全量展示"不依赖引擎B

- 地图方块（颜色/大小/类型）：读快照 46 列（全量预计算），**与引擎B 无关**；
- 弹窗基础数据：快照初始 + 异步 diagnose；
- 弹窗操作建议：异步 diagnose（现为引擎A，改后为引擎B）——**本来就是点击时算**，不涉及全量。

## 二、双引擎统一：深度标签库落地（本方案核心架构决策）

### 2.1 问题：两套引擎的管道分叉

```
引擎A（弹窗/图谱）：opportunity_tags_cache（P4 预计算 61 标签）→ L4/321
引擎B（个股页）：    strategy_signal_detail（P2 预计算 五维信号）→ 五维构建 → 321
                     ↑ 两管道独立预计算、独立存储 → 可能结论不一致（000975 实证）
```

### 2.2 解决：单一标签库 + 差异化取用

将引擎B 五维构建所需的**深度字段从信号迁移至标签库**，形成统一底座：

```
opportunity_tags_cache（扩展后 ~81 标签，tag_group 分组）
  ├─ 现有 6 组（derived/direction/environment/position/quality/unknown，61 标签）← 引擎A + 引擎B
  └─ 新增 3 组（structure/chip_deep/fund_risk，20 标签）                       ← 引擎B 专属深度
```

**tag_group 现状澄清（2026-08-09 实证）**：`opportunity_tags_cache` 的 `tag_group` 列**已存在**，现有值域为 `derived(19)/direction(7)/environment(7)/position(10)/quality(7)/unknown(11)`——**非本方案设想的 screen 组**。方案采用**新增 3 组（structure/chip_deep/fund_risk）+ 复用现有组**，不改变现有 6 组语义（引擎A 消费现有组，引擎B 消费现有组+新增组）。

**两引擎从同一张表读、各取所需子集**——输入同源，顶层状态天然一致，管道分叉根治。

### 2.3 深度标签清单（20 个，产出引擎 + 存储）

### 2.4 差异化取用接口（DataManager 网关）

```python
# 现有（引擎A 用，返回全量标签——现状已含全部 tag_group）
get_tags(ts_code) -> dict

    # groups=['derived','direction','environment','position','quality','structure','chip_deep','fund_risk']
    # WHERE tag_group IN (...) → {tag_name: value}
```

**说明**：引擎A 现状 `get_tags` 已返回全量（含新增深度组，因其不属于筛选逻辑影响小）；引擎B 用 `get_tags_by_group` 精确取所需组（现有 5 组 + 深度 3 组），避免冗余拉取。

### 2.5 引擎B 五维构建改造（读标签库为主，信号回退）

```
_build_chanlun_dimension:  读 tags['structure']（support_resistance/zhongshu_strength…）
                          → 缺失回退 strategy_signal_detail 信号
_build_chip_dimension:     读 tags['chip_deep']（chip_peak/main_force_cost…）
                          → 缺失回退信号
_build_volume_price_dim:   读 tags['screen']（volume_price_fit/buy_sell_point）
                          → 缺失回退信号
```

**渐进式迁移**：标签库为权威，P2 信号降为深度回退——不破坏现有，管道分叉逐步消除。

### 2.6 统一性/精确度收益

| 维度 | 收益 |
|------|------|
| **统一性** | 两引擎同库同源，顶层状态天然一致（无需单向引用压制）；000975 类矛盾结构性根治 |
| **精确度** | 引擎B 深度输入完整（七维/几何不再"虚胖"，fund 维"中性"缓解）；标签集中管理便于审计修正 |
| **性能** | 引擎B 读标签库（毫秒级）替代信号解析，P2 回退仅缺字段时触发 |

## 三、双引擎执行层冲突核查与统一（三轮新增，关键决策）

### 3.1 实证：双操作建议输出存在 3 处实质冲突（4 只股票全样本）

状态层已统一（enter/avoid 等一致），但**执行层（仓位/止损/入场）两套独立实现**：

| 冲突 | 引擎A（弹窗 diagnose `_build_trade_plan`） | 引擎B（个股页 advice_builder） | 差异 |
|------|------|------|------|
| **止损位** | `max(MA20, 前低)×0.98`（000426=31.48 / 603201=15.52） | `60日低点`（000426=26.3 / 603201=13.13） | **-15%** |
| **仓位上限** | L4 共识率映射+强确认提升（0.7） | state 固定档（enter=0.6） | 0.7 vs 0.6 |
| **入场规则** | 三档（回踩MA10/突破前高/回踩MA20） | 单档（close≤60日低点） | 策略逻辑不同 |

**根因**：两套独立实现的操作建议生成器（309/316 号 `_build_trade_plan` vs 322 号 advice_builder）——此前统一只覆盖状态层，**执行层（仓位/止损/入场）从未统一**。

**后果**：用户弹窗看到"止损 31.48"、个股页看到"止损 26.3"——同一股票两个止损价，直接关系实际盈亏，最危险冲突。

### 3.2 解决方案：执行层统一（方案A，推荐）

**让引擎B（advice_builder）成为唯一操作建议生成器，引擎A 弹窗改读其输出**：

```
统一生成：advice_builder.build_operation_advice（唯一仓位/止损/入场来源）
  ├─ 引擎B（个股页）：读完整 operation_advice（现状）
  └─ 引擎A（弹窗）：弹窗 diagnose 改读 advice_builder 输出（仓位/止损/入场统一）
      （或弹窗直接读统一 operation_advice 的前 4 字段）
```

- **止损统一**：统一用 60日低点防守位（B 的 `_geometric`，已实证更合理——A 的 MA20×0.98 在 600519 曾致"止损立即触发"bug）；
- **仓位统一**：统一用 state→档位映射（B 的规则，已与 309/316 对齐）；
- **入场统一**：统一用 advice_builder 的 entry_rules（S6 扩展为区间）；
- **删除 `_build_trade_plan` 重复实现**（cross_validate.py 中旧模板）。

**备选方案**：
- 方案B：共享执行规则常量（仓位映射/止损算法/入场模板提取为共享函数，两引擎引用）——改动小但逻辑仍分两处；
- 方案C：仅前端分层展示（弹窗只显示 B 的仓位/止损）——**治标不治本，不推荐**。

### 3.3 与全量预计算的关系（三轮核实，无冲突）

- 机会图谱**全量展示**（地图）用快照预计算（46 列），**不依赖引擎B**；
- 弹窗操作建议**本就是点击时算**（现 diagnose、改后 advice_builder）——方案A 不引入全量计算；
- 引擎B 几何 K线读 `daily_cache` 日终数据（08-07），**非盘中实时**，与预计算无冲突；
- **S0 的真实价值** = ①执行层统一（消除止损/仓位/入场双套逻辑）②深度字段预计算落库（点击纯读）——**非"解决全量实时矛盾"**（该矛盾不存在）。

### 3.4 方案A 的消费方影响核查（2026-08-09 实证，重大遗漏补充）

**`_build_trade_plan` 与 `operation_advice` 除弹窗 diagnose 外，还有 3 个消费方**——方案A 删除/改造必须一并评估：

| 消费方 | 现状 | 方案A 影响 |
|--------|------|-----------|
| **机会库**（`advice_generator.py:54,153`）| 调 `l4.diagnose` → 存 `operation_advice` JSON 到 `opportunity_library.operation_advice` 列 | ⚠️ **格式变化**：旧格式（action/label/max_position_ratio）→ 新格式（state/executable）——机会库页展示需适配 |
| **机会库 API**（`opportunity_library.py:30`）| 透出 `operation_advice` 字段 | ⚠️ 同上，前端消费方需确认 |
| **弹窗本地近似**（`opportunity-treemap.html:1783`）| 初始渲染用 state 本地近似，异步 diagnose 覆盖 | ✅ 方案A 后弹窗初始仍用快照 state，异步改读 advice_builder 输出——本地近似逻辑可保留（初屏秒开）|

**处理原则**：方案A 不删除 `_build_trade_plan` 本体，而是**将弹窗 diagnose 的 `operation_advice` 改为引用 advice_builder 输出**；`_build_trade_plan` 标记废弃（机会库迁移完成后删除）。**机会库操作建议随方案A 一并切换为新格式**，需同步适配前端展示（避免旧格式解析错误）。

### 3.2 状态→5档操作动作映射（`_map_action_label` 辅助函数）

```
def _map_action_label(state: str, signal_strength: float) -> str:
    if state == 'enter' and signal_strength >= 80: return '重仓买入'
    if state == 'enter':                            return '买入/建仓'
    if state == 'light':                            return '轻仓试探'
    if state == 'wait':                             return '持有/观望'
    return '清仓回避'   # avoid
```

**注意**：`action_label` 是**给人看的**（前端展示）；`executable.action_type`（BUY/HOLD/SELL）**保留机器可执行**（虚拟实盘用）——动作标签细分由前端呈现，执行动作保持 3 态机器语义，两者不冲突。

### 3.3 失效条件派生（`_build_invalidation` 辅助函数）

```
def _build_invalidation(state, support, sentiment_phase, rsc) -> list[str]:
    conditions = []
    if support is not None:
        conditions.append(f'收盘跌破止损位 {support}')
    if sentiment_phase in ('ebb', 'climax'):
        conditions.append('大盘进入退潮/高潮期，追涨风险大')
    if rsc == '否决':
        conditions.append('右侧确认已转为否决（卖出/背离/预跌信号）')
    return conditions   # 有 support 时至少含止损条件
```

### 3.4 置信度合成（`_calc_confidence` 辅助函数）

```
def _calc_confidence(consensus_rate: float, evidence_count: int,
                     conflict_count: int) -> str:
    if conflict_count >= 3 or evidence_count == 0:
        return '低'
    if consensus_rate >= 0.75 and evidence_count >= 4 and conflict_count <= 1:
        return '高'    # 证据阈值已校准：>=4（实测923只，原>=5仅850只）
    if consensus_rate >= 0.55 or conflict_count == 2:
        return '中'
    return '低'
```

**数据来源**：
- `consensus_rate`：现有 `_consensus_from_dirs(dirs)` 已算；
- `evidence_count`：`tags.get('evidence_count')`（真实标签，**实测值域 0-5：3=2434/2=1230/5=850/0=797/1=132/4=74**）；
- `conflict_count`：`len(dimensions['factor'].get('conflict_items', []))`（ConflictArbiter 输出）。

**阈值校准（2026-08-09 实证）**：`evidence_count` 峰值在 3（2434 只）、中位约 2-3，**原阈值 `>=5` 过于严苛**（仅 850 只达标）。校准为 `>=4`（923 只）保留高置信度稀缺性，`>=2` 作为中等门槛，与值域分布匹配。

**低置信度降级**（建议卡 §3.2）：`confidence=='低'` 时 `action_label` 强制为 `'轻仓试探'`（禁止重仓买入），`max_pct` 上限 0.3。

### 3.5 目标位派生（`_build_target_levels` 辅助函数）

```
def _build_target_levels(df) -> list[dict]:
    if df is None or df.empty or 'high' not in df.columns or len(df) < 60:
        return []
    price = float(df['close'].iloc[-1])
    hi60 = float(df['high'].tail(60).max())
    levels = [{'price': round(hi60, 2), 'reason': '60日高点压力位'}]
    levels.append({'price': round(hi60 * 1.15, 2), 'reason': '保守扩展目标'})
    return levels
```

**语义边界**：目标位标注为"参考压力位/扩展参考"，**非"预测必到"**（LLM Wiki 框架妥协，见方案 §八）。

### 3.6 预期持有派生（`_build_expected_holding` 辅助函数）

```
def _build_expected_holding(tags: dict) -> str:
    tr = str((tags or {}).get('time_rhythm') or '')
    holding_map = {
        'early_consolidation': '筑底/建仓初期，波段 20-30 个交易日',
        'mid_consolidation':   '箱体整理中段，短线 10-20 个交易日',
        'approaching_turn':    '临近变盘，等待方向选择（5-10 个交易日）',
    }
    return holding_map.get(tr, '日线波段 20-30 个交易日')
```

**实测值域校准（2026-08-09 实证）**：`time_rhythm` 实际值域为 `unknown(5070)/approaching_turn(232)/early_consolidation(184)/mid_consolidation(76)`——**原方案臆造的 rising/consolidation/bottoming/distribution 与实际不符，已按实证值域重写**。映射表覆盖全部 4 个实际值，unknown 落默认。
