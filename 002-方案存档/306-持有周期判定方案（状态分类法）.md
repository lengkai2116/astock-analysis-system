# 持有周期判定方案（状态分类法）

> **范式转变**：从"分数映射"到"状态分类与应对"——持有周期不是通过加权评分算出来的，而是根据股票当前所处的**多维状态类型**，由规则引擎直接判定得出。
>
> **知识库基础**：本方案设计基于 `data/knowledge/concepts/` 中 790+ 篇资料中的以下核心概念：UIDF（统一投资决策框架）、三层信号结构、多周期层级决策框架、状态依赖的动态周期、信号冲突处理机制、周期错配、情绪周期四阶段模型、因子衰减、状态识别与动态调制（HMM+）。

---

## 一、现状诊断

### 1.1 当前持有周期判定的问题

当前 `hold_period`（持有周期）的判定逻辑位于前端 `opportunity-treemap.html` 第 599-609 行，是一个完全由前端 JavaScript 执行的硬编码映射规则：

```javascript
holdPeriod: s.hold_period || (function() {
    const mfp = s.main_force_phase || '';
    const pos = (s.tags && s.tags.price_position) || '';
    if (mfp === 'building' && pos === 'low_zone') return '长线机会';
    if (mfp === 'building') return '中线机会';
    if (mfp === 'washing') return '中线机会';
    if (mfp === 'lifting') return '短线机会';
    if (mfp === 'distributing') return '超短机会';
    return ss >= 7 ? '长线机会' : ... : '无明确信号';
})()
```

**问题清单：**

| # | 问题 | 严重度 | 说明 |
|---|------|:------:|------|
| **P1** | **仅使用一个标签** | 🔴 | 只用了 `main_force_phase`，`price_position` 仅在 building+low_zone 组合中生效。系统已有 30+ 标签，仅有 1 个被用于周期判定 |
| **P2** | **趋势周期与持有周期混淆** | 🔴 | `main_force_phase` 是趋势周期指标（日线），用来直接决定"6个月长线"——这是知识库中定义的 **周期错配** |
| **P3** | **前端伪计算** | 🟡 | 逻辑在浏览器 JS 中，刷新即丢失；修改需要改前端代码 |
| **P4** | **无量化时间指引** | 🟡 | "长线"是多久？无法给出 6个月 / 1-6月 / 1-4周 / 3-7天 等量化区间 |
| **P5** | **无安全边际考量** | 🔴 | 完全不考虑 `fina_health`（财务健康）、`dividend_yield`（股息率）、`valuation_level`（估值水平）等标的质量因素。一只主力在建仓的造假股也会被判定为"中线机会" |

### 1.2 数据库确认

数据库查询确认 `opportunity_tags_cache` 中不存在 `hold_period` 标签，`TAG_META` 映射表中也无此条目。持有周期实际上是**前端凭空合成的展示字段**，没有任何服务端引擎或数据支撑。

## 二、知识库研究基础

### 2.1 核心理论依据

本方案的设计基础来自系统本地知识库（`data/knowledge/concepts/`）的以下核心概念：

| 知识库概念 | 核心观点 | 对本方案的指导 |
|-----------|---------|--------------|
| **UIDF（统一投资决策框架）** | 从"预测"到"分类与应对"——根据多维数据对当前状态进行完全分类，每类预设操作规则 | `hold_period` 不应是预测分数，而是**当前状态分类下的规则输出** |
| **三层信号结构** | 确认层（方向）→ 执行层（时机）→ 过滤层（噪声），分工明确 | 持有周期判定也应分层：趋势方向→状态分类→时间修正 |
| **多周期层级决策框架** | 背景周期决定方向，决策周期决定买卖，执行周期优化入场 | `main_force_phase` 属于背景周期，不直接等于持有周期 |
| **状态依赖的动态周期** | 不同市场状态下，不同周期信号的权重应动态调整 | 同一 `main_force_phase` 值在不同状态组合下可输出不同的持有周期 |
| **周期错配** | 策略目标周期与分析周期不一致是信号冲突的首要来源 | 日线的 `main_force_phase` 不应直接决定月线的"长线"结论 |
| **情绪周期四阶段模型** | 冰点→复苏→高潮→退潮，不同阶段对应不同操作策略 | `sentiment_phase` 应作为持有周期的**环境修正因子** |
| **因子衰减** | 不同因子有不同半衰期，IC 衰减曲线决定有效持有窗口 | `fina_health` 半衰期长→长线；`catalyst_event` 半衰期短→短线 |

### 2.2 核心范式转变

```
传统加权评分思路（当前方案的问题）：
  输入: 多个标签 → 加权求和 → 分数 → 映射为持有周期
  问题: 矛盾标签相互中和，分数失去可解释性
        无法处理"主力建仓但估值已高"这类矛盾组合

状态分类思路（本方案采用）：
  输入: 多个标签 → 状态联合判定 → 状态类型 → 规则输出持有周期
  优势: 矛盾标签共同定义一种风险状态
        每种状态类型的逻辑独立、可解释
        新增一种状态类型不影响已有类型
```

## 三、三层次状态分类框架

### 3.1 框架总览

```
┌─ 第一层：背景判定（趋势方向）─────────────────────────────────────┐
│  输入: main_force_phase（主力阶段）                                │
│  输出: 趋势方向约束（可持有/仅短线/不持有）                        │
│  依据: 多周期层级决策框架——背景周期决定大方向                      │
│  位置: 服务端 _compute_hold_period() 中第一段逻辑                  │
└───────────────────────────────────────────────────────────────────┘
                              ↓
┌─ 第二层：状态分类（联合判定）──────────────────────────────────────┐
│  输入: 6-8 个现状标签的联合判定                                    │
│  输出: 状态类型（如"价值底部区"、"主升浪"、"危险区"等）           │
│         + 对应的基础持有周期                                       │
│  依据: UIDF分类与应对——多种状态类型各有独立的判定规则             │
│  位置: 服务端 _compute_hold_period() 中核心逻辑（if-elif 树）      │
└───────────────────────────────────────────────────────────────────┘
                              ↓
┌─ 第三层：时间修正（执行细节）──────────────────────────────────────┐
│  输入: time_rhythm（变盘窗口）+ catalyst_event（催化剂到期日）      │
│  输出: 量化持有周期（具体天数）                                    │
│  依据: 状态依赖的动态周期——根据状态信号修正持有长度               │
│  位置: 服务端 _compute_hold_period() 中最后一段                    │
└───────────────────────────────────────────────────────────────────┘
```

### 3.2 第一层：背景判定

背景层不输出最终的持有周期，而是输出**方向约束**。这是对 **多周期层级决策框架** 中"背景周期决定大方向"原则的实现。

```python
def _compute_background_constraint(tags: dict) -> dict:
    """根据主力阶段确定背景方向约束"""
    mfp = tags.get('main_force_phase', 'unknown')

    # 背景层规则表
    constraints = {
        'building':    {'direction': 'bullish', 'max_hold': 'long_term',  'reason': '主力建仓期，蓄势阶段'},
        'washing':     {'direction': 'bullish', 'max_hold': 'mid_term',   'reason': '洗盘整理，清洗浮筹'},
        'lifting':     {'direction': 'bullish', 'max_hold': 'short_term', 'reason': '拉升阶段，不宜长持'},
        'distributing':{'direction': 'bearish', 'max_hold': 'ultra_short','reason': '出货阶段，尽快离场'},
        'unknown':     {'direction': 'neutral', 'max_hold': 'unknown',    'reason': '阶段不明，靠其他维度'},
    }
    return constraints.get(mfp, constraints['unknown'])
```

| `main_force_phase` | 方向约束 | 最长持有限制 | 说明 |
|-------------------|---------|-------------|------|
| `building`（建仓） | 看多 | 长线（6月+） | 蓄势阶段，允许最长持有 |
| `washing`（洗盘） | 看多 | 中线（1-6月） | 洗盘需要时间消化 |
| `lifting`（拉升） | 看多 | 短线（1-4周） | 拉升阶段不宜恋战 |
| `distributing`（出货） | 看空 | 超短（3-7天） | 出货须快进快出 |
| `unknown`（不明） | 中性 | 不限 | 无方向约束，靠其他维度 |

### 3.3 第二层：状态分类（核心）

状态分类是本方案的核心创新。它不是一个加权公式，而是一个 **if-elif 规则树**。每种状态类型的判定条件是多标签的联合判定（AND 逻辑），相互独立。

```python
def _classify_status(tags: dict) -> dict:
    """根据多标签联合判定当前状态类型"""

    mfp   = tags.get('main_force_phase')
    fina  = tags.get('fina_health')
    val   = tags.get('valuation_level')
    sp    = tags.get('sentiment_phase')
    sh    = tags.get('sector_heat')
    vl    = tags.get('volatility_level')
    dy    = tags.get('dividend_yield')
    ce    = tags.get('catalyst_event')

    # 规则树：优先级从高到低，每个规则独立判定
    # 规则之间是 OR 关系——命中第一条即返回

    # ── 危险区（最高优先级）──
    if mfp == 'distributing' and fina == 'fail':
        return {'type': 'danger_zone',        'hold': '不持有',        'days': 0}
    if mfp == 'distributing' and val in ('high', 'extreme_high'):
        return {'type': 'danger_zone',        'hold': '超短机会',      'days': '3-7'}

    # ── 价值底部区 ──
    if mfp == 'building' and fina == 'pass' and val in ('extreme_low', 'low'):
        return {'type': 'value_bottom',       'hold': '长线机会',      'days': '6月+'}

    # ── 建仓在高位（矛盾信号）──
    if mfp == 'building' and val in ('high', 'extreme_high'):
        return {'type': 'build_high',         'hold': '短线机会',      'days': '1-4周'}

    # ── 主力建仓观察区 ──
    if mfp == 'building':
        return {'type': 'building_watch',     'hold': '中线机会',      'days': '1-6月'}

    # ── 主升浪 ──
    if mfp == 'lifting' and sp == 'climax' and sh in ('top_10', 'top_20'):
        return {'type': 'main_upsurge',       'hold': '短线机会',      'days': '1-4周'}
    if mfp == 'lifting' and sh in ('none', 'normal'):
        return {'type': 'steady_rise',        'hold': '中线机会',      'days': '1-3月'}
    if mfp == 'lifting':
        return {'type': 'lifting_general',    'hold': '短线机会',      'days': '1-4周'}

    # ── 洗盘期 ──
    if mfp == 'washing' and sh in ('top_10', 'top_20'):
        return {'type': 'wash_hot',           'hold': '中线观察',      'days': '1-3月'}
    if mfp == 'washing':
        return {'type': 'wash_general',       'hold': '中线机会',      'days': '1-6月'}

    # ── 主线不明，靠基本面判定 ──
    if mfp == 'unknown' and fina == 'pass' and val in ('extreme_low', 'low'):
        return {'type': 'quality_unknown',    'hold': '中线机会',      'days': '1-3月'}
    if mfp == 'unknown' and dy and float(dy) > 3:
        return {'type': 'dividend_play',      'hold': '长线机会',      'days': '6月+'}

    # ── 情绪驱动（事件催化）──
    if ce and ce != 'none' and vl == 'high':
        return {'type': 'event_driven',       'hold': '超短机会',      'days': '3-7天'}
    if ce and ce != 'none':
        return {'type': 'event_watch',        'hold': '短线观察',      'days': '1-4周'}

    # ── 冷门价值（高股息低关注度）──
    if fina == 'pass' and dy and float(dy) > 3 and sh in ('none', 'normal'):
        return {'type': 'cold_value',         'hold': '长线机会',      'days': '6月+'}

    # ── 兜底 ──
    if mfp == 'unknown' or not mfp:
        return {'type': 'no_signal',          'hold': '无明确信号',    'days': '观望'}

    return {'type': 'default',               'hold': '短线观察',      'days': '1-4周'}
```

### 3.4 第三层：时间修正

在第二层输出基础持有周期后，根据时间相关标签进行修正：

```python
def _apply_time_adjustment(base: dict, tags: dict) -> dict:
    """根据时间节奏和催化剂修正持有周期"""
    tr = tags.get('time_rhythm', 'none')
    ce = tags.get('catalyst_event', 'none')

    # 如果存在变盘信号，持有周期缩短到变盘前
    if tr and tr != 'none' and base.get('days') not in (0, '观望'):
        base['days'] = f'≤{tr}'  # time_rhythm 输出具体天数

    # 如果存在近期催化剂事件，持有到事件兑现前
    if ce and ce != 'none' and 'catalyst_date' in tags:
        base['days'] = f'至{tags["catalyst_date"]}前'

    # 情绪修正：高潮期缩短，冰点期延长
    sp = tags.get('sentiment_phase', '')
    if sp == 'climax' and '月' in str(base.get('days', '')):
        base['days'] = base['days'].replace('6月+', '3月').replace('1-6月', '1-3月')
        base['note'] = '情绪高潮，缩短持有周期'
    if sp == 'ice' and '短' in base.get('hold', ''):
        base['hold'] = base['hold'].replace('超短', '短线')
        base['days'] = '1-4周'
        base['note'] = '情绪冰点，适当延长'

    return base
```

## 六、风险与应对

| 风险 | 级别 | 应对 |
|------|:----:|------|
| 规则树优先级不合理，某类型过度捕获 | 🟡 中 | 第一阶段先输出分布统计，调优后再部署到前端 |
| `time_rhythm` 或 `catalyst_event` 数据为空 | 🟢 低 | 第三层时间修正会自动跳过空值，不影响基础判定 |
| 贡献的 3 个新增标签增加存储开销 | 🟢 低 | 3 个 TEXT 字段 × 4800 行 ≈ 非常小 |
| 前端的 tooltip 颜色映射可能需要适配新的 `hold_period` 值 | 🟡 中 | 目前 5 个值（长线/中线/短线/超短/无明确信号）不变，不影响颜色映射。新增的状态类型仅用于详情面板展示 |
| 状态类型判定与 `L4CrossValidator` 的诊断结果冲突 | 🟢 低 | 持有周期是策略建议维度，L4 诊断是信号验证维度，两者不冲突 |
