### 🔴 缺口-2：daily_close_sync 日终同步事件总线

**当前状态：** 3 个手动 CLI 脚本存在，但**无事件信号机制**。

**7 个模块等待 `daily_close_sync` 完成事件：**

| 模块 | 事件触发后的动作 |
|:-----|:----------------|
| 213 仪表盘 | 刷新 DuckDB 缓存 + 重算涨跌榜 |
| 215 个股策略 | 增量更新日线/基本面/复权因子 |
| 216 自选监控 | 重算策略评分 |
| 218 回测 | 更新历史 K 线 |
| 221 复盘中心 | **模拟引擎推进一日**（核心循环） |
| 224 监控通知 | 触发日终批量评估（15:30） |
| 226 账户管理 | 更新持仓市价 |

**缺口本质：** 缺少一个 `signals` 或 `blinker` 事件总线——同步完成后发出 `daily_sync_completed` 信号，各模块订阅该信号并执行回调。

**实施方案：** 可用 Python `blinker` 库（~50 行）或 Flask 内置 `signals`：
1. 定义 `daily_sync_completed = blinker.signal('daily_sync_completed')`
2. 同步脚本/定时任务完成时 `daily_sync_completed.send(date=today, stats={...})`
3. 各模块在 Blueprint 注册时订阅该信号

### 🔴 缺口-3：Config 类未接入 App Factory

**当前状态：** `config.py` 定义了 `Config` 类（54 行），但 `create_app()` **从未导入或使用它**。

| 问题 | 详情 |
|:-----|:-----|
| Config 类 | 定义了 SECRET_KEY / DATABASE_URI / TUSHARE_TOKEN / LLM config / QMT config |
| create_app() | 直接从 `os.getenv()` 读取配置，不使用 Config 类 |
| 后果 | Config 类为死代码；无法实现系统管理 Tab① 的热更新 |

**实施方案：**
1. `create_app()` 改为 `app.config.from_object(Config)`
2. 各模块通过 `current_app.config['KEY']` 读取
3. RuntimeConfigManager 热更新时写入 `app.config` + DB

### 🟡 缺口-4：RuntimeConfigManager 运行时配置管理

**当前状态：** 不存在。系统管理 Tab① 的 config/save + config/load 端点为 P0 待建。

**4 个模块显式依赖：**
- 213 仪表盘：指数列表配置
- 214 选股系统：权重配置持久化
- 217 AI 投研：LLM 模型状态 / API Key
- 225 系统管理：**自身就是配置中心**，需实现 config/save（写入 DB + 更新内存）+ config/load

**设计方案：**
```
RuntimeConfigManager:
  - load() → 从 DB system_config 表加载到内存 dict
  - get(key, default) → 读内存
  - set(key, value) → 写内存 + 写 DB + 发信号
  - 配置域：llm / data_source / notification / system
  - 热更新：set() 后各模块通过信号或轮询获取新值
```

**DB 表：** `system_config`（key TEXT PK / value JSON / domain TEXT / updated_at DATETIME）

**实施方案：** 创建 `LLMPipeline` 类统一入口：
```

  - 超时：默认 15s，可配置
  - 重试：2 次，指数退避
  - Token 计量：记录每次调用消耗
```

## 七、关键架构发现

1. **229 号方案是全系统定时机制圣经** — 全部 14 份规格书引用了 229 号 §3.1，定时基础设施是唯一的 14/14 全依赖底盘。

2. **daily_close_sync 是最关键的事件锚点** — 7 个模块直接等待该事件完成来触发下游逻辑（复盘引擎日推进、监控日终评估、仪表盘缓存刷新等），当前缺事件总线。

3. **225 系统管理 = 底盘的 UI 面** — 它自身就是配置中心、缓存管理、数据源管理、同步控制的入口，其他模块通过 API 消费它管理的资源。**系统管理应最先开发。**

4. **224 监控通知是底盘依赖最重的业务模块** — 唯一同时需要 WebSocket 推送 + APScheduler 多粒度定时 + 6 张新表 + 策略引擎信号 + DuckDB 实时数据 + AI 管道的页面。

5. **Config 类是隐性死代码** — 定义了完整配置结构但 create_app() 完全不使用，是 RuntimeConfigManager 热更新的前置阻塞项。

6. **策略引擎是最大资产** — 16,295 行 + 500+ 因子库，已实现 LEAN 风格框架 + 5 种策略 + UPF/UIDF/CSCV 完整链路，是系统的核心竞争力。
