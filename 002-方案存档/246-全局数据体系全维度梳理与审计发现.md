## 一、数据获取渠道

全局数据体系目前使用 **三大实时数据源 + 一个预留升级路径**。

### 1.1 Tushare Pro（主数据源）

| 属性 | 值 |
|:-----|:---|
| **定位** | 持久历史数据的权威来源 |
| **获取内容** | 日线OHLCV、每日基本面(turnover/PE/PB/总市值)、资金流向、复权因子、财务指标、股票名录、行业分类、概念分类等 |
| **覆盖周期** | 默认5年（日线/周线），10年（月线），持续每日追加 |
| **API频次** | 200次/分钟，5000分/日配额 |
| **网络依赖** | 需外网访问 tushare.pro |
| **代码位置** | `backend/app/data/tushare_provider.py` |
| **拥有方法** | `get_stock_list`, `get_daily_data`, `get_daily_basic`, `get_moneyflow`, `get_adj_factor`, `get_fina_indicator`, `get_income`, `get_balancesheet`, `get_cashflow`, `get_top10_holders`, `get_stk_holdernumber`, `get_margin`, `get_forecast`, `get_industry`, `get_concept`, `get_index_member`, `get_minute`, `get_weekly`, `get_monthly`, `get_top_list`, `get_stk_limit`, `get_news` 等 20+ 方法 |

### 1.2 AKShare / 东方财富（盘中数据源）

| 属性 | 值 |
|:-----|:---|
| **定位** | 盘中实时数据的采集来源 |
| **获取内容** | 全市场实时快照、板块/概念排行、涨跌停池、分钟K线、龙虎榜、个股盘口、新闻 |
| **覆盖周期** | 盘中实时（30日DuckDB归档），**不负责持久历史数据** |
| **API频次** | 无官方限制，实际约 1-3次/秒/接口 |
| **网络依赖** | 需外网访问东方财富接口（`push2.eastmoney.com` 等） |
| **代理问题** | 曾出现 `HTTP_PROXY` 环境变量导致连接失败（240号方案已修复：采集器启动时 `os.environ.pop(_k, None)` 清除代理环境变量） |
| **代码位置** | `backend/app/data/akshare_provider.py`（原始封装）→ `backend/app/data/akshare_collector.py`（后台采集器） |

### 1.3 DataSourceManager 时间感知路由

| **使用场景** | Route 层通过 `data_source_manager.get_data_time_aware()` 获取某只股票的当前行情 |

### 1.4 QMT（预留升级路径）

| 属性 | 值 |
|:-----|:---|
| **定位** | 券商直连的 L2 实时行情升级路径 |

## 二、获取方式

全局数据体系定义了三类获取方式：**定时批量同步**（盘后）、**定时采集推送**（盘中）、**按需查询降级**（运行时）。

### 2.1 定时批量同步（Tushare → DuckDB）

**调度器：** `SchedulerManager`（`backend/app/scheduler_manager.py`），基于 APScheduler BackgroundScheduler

**每日同步流程：**

```
15:30 触发 → daily_close_sync()
  ├── sync_daily_data()        → Tushare → daily_cache（OHLCV）
  ├── sync_daily_basic()       → Tushare → daily_basic_cache
  ├── sync_moneyflow()         → Tushare → moneyflow_cache
  ├── sync_index_data()        → Tushare → DuckDB index 表
  ├── sync_adj_factor()        → Tushare → adj_factor_cache
  └── sync_stock_list()        → Tushare → PG Stock（股票名录）
```

**启动补采：** `catch_up_if_needed()` 在应用启动时执行：
- 查询 `SELECT DISTINCT trade_date FROM daily_cache ORDER BY 1 DESC LIMIT 1`
- 若最近日期 < 今天 → 执行增量同步
- 若 daily_cache 为空 → 全量同步

**定时参数：** 由 `RuntimeConfigManager` 管理，用户可在系统管理页面配置（`trigger_time`、`data_types`、`mode` 等）

### 2.2 定时采集推送（AKShare → InMemory + DuckDB + PG）

**采集器：** `AkshareCollector`（`backend/app/data/akshare_collector.py`），5 个独立守护线程

| 线程 | 采集内容 | 间隔 | 写入策略 | 数据量/次 |
|:-----|:---------|:-----|:---------|:----------|
| ① 全市场快照 | 个股实时行情（~5000只） | 15s | 覆盖 | ~5000 rows |
| ② 板块排行 | 行业/概念板块涨跌 | 30s | 覆盖 | ~200 rows |
| ③ 涨跌停池 | 涨停/跌停股票 | 30s | 覆盖 | ~100 rows |
| ④ 分钟K线 | 当日分钟K线（增量） | 5min | 追加 | ~5000 rows |
| ⑤ 龙虎榜+新闻 | 龙虎榜/财经新闻 | 10min | 覆盖+按需 | ~100 rows |

**每次采集的写入路径（三级）：**

```
mem_store.update_xxx(records)         # L1 内存（O(1) 读取，WS 推送源）
_get_ecm().write_as_xxx(records)     # L2 DuckDB 归档（30日保留）
_get_pg().get('xxx')(records)        # L3 PG 持久化（盘中持久，盘后清理）
```

**交易时段判断：** `_is_trading_time()` 在 9:25-11:30 和 13:00-15:00 运行，节假日自动跳过

### 2.3 按需查询降级（运行时路由）

**DataManager**（`backend/app/data/__init__.py`）提供按需查询接口：

```
get_cached_daily_data(ts_code, start_date, end_date)
  → 查询 DuckDB daily_cache
  → 若不存在 → DataSourceManager.get_data_time_aware() 降级到 Tushare/AKShare

get_cached_daily_basic(ts_code, start_date, end_date)
  → 查询 DuckDB daily_basic_cache
  → 若不存在 → 降级到 Tushare

get_cached_moneyflow(ts_code, start_date, end_date)
  → 查询 DuckDB moneyflow_cache
  → 若不存在 → 降级到 Tushare
```

**AkshareDataReader**（`backend/app/data/akshare_reader.py`）提供盘中数据按需读取接口：

```
get_market_snapshot()
  → InMemoryStateStore（盘中，O(1)）
  → DuckDB as_market_snapshot（盘后归档）
```

## 三、不同数据渠道的功能定位

### 3.1 定位总表

| 数据渠道 | 服务时段 | 数据范围 | 持久性 | 延迟 | 主要消费方 |
|:---------|:---------|:---------|:-------|:-----|:-----------|
| **Tushare Pro** | 盘后 15:30+ | 5年+ 历史日线/基本面/资金流 | ✅ 永久（DuckDB） | 日级 | 选股系统、回测、复盘、策略模板 |
| **AKShare 采集** | 盘中 9:25-15:00 | 当日实时快照/排行/分钟K线 | ⚠️ 30日（DuckDB） | 秒级 | Dashboard、实时监控、个股页 |
| **InMemoryStateStore** | 盘中 9:25-15:00 | 当日实时快照/排行/分钟K线 | ❌ 日终清理 | 毫秒级 | WebSocket推送、REST轮询 |
| **DataSourceManager** | 全天 | 按需路由到Tushare/AKShare | N/A | 秒~分级 | 路由层、无法命中缓存的查询 |
| **QMT（预留）** | 盘中 | L2 逐笔成交/K线 | ✅ | 毫秒级 | 条件满足后替代 AKShare |

### 3.2 关键约束与边界

**Tushare 的约束：**
- 每天 5000 分配额，每次 API 调用消耗 2~10 分
- 一轮全量 daily 同步 ≈ 5000 只股票 × 1 API/只 = 5000 次调用，消耗 ≈ 10000~15000 分
- **这意味着一轮全量同步消耗 2~3 天的配额**——增量同步（仅当天的数据）是唯一可行的日常模式

**AKShare 的约束：**
- 免注册、无配额，但数据来源是东方财富，不受官方 API SLA 保障
- 盘中高频采集可能被东方财富限流（偶发空响应）
- 代理环境变量曾导致采集完全不可用（240号方案已修复）

**InMemoryStateStore 的约束：**
- 单进程内内存存储，多 worker（Gunicorn）模式下不可共享
- 243号方案通过 Redis pub/sub + PG 双写解决了多 worker 场景

**QMT 的约束：**
- 需券商开户 + 开通 QMT 权限 + 本地安装 QMT 客户端
- 不满足条件的系统默认视为"QMT 不可用"，全部走 AKShare 路径

### 3.3 功能重叠与互补

| 场景 | 正确路径 | 不应走的路径 |
|:-----|:---------|:-------------|
| 查看某股票5年历史走势 | DuckDB daily_cache（Tushare同步） | AKShare 当日快照 |
| 盘中看当前涨跌榜 | InMemoryStateStore（AKShare 采集） | Tushare 盘后数据 |
| 筛选成交活跃的股票 | DuckDB daily_basic_cache（turnover/volume_ratio） | 直接调 Tushare API |
| 策略代码中获取 OHLCV | DataManager.get_cached_daily_data() | 直接调 `ak.stock_zh_a_hist()` |
| 回测需要完整日线 | DuckDB daily_cache（5年数据） | AKShare 30日归档(数据不够) |

## 四、数据管理

### 4.1 盘后清理链（Post-Market Cleanup）

每日同步完成后执行的后处理流程（`scheduler_manager.py`）：

```
daily_close_sync() 完成后 →
  cleanup_intraday_data():
    ├── 清空 InMemoryStateStore（所有盘中数据）
    ├── 删除 DuckDB as_minute_kline（30日前数据）
    ├── 清空 PG realtime_* 表（快照/排行/涨跌停/新闻）
    │   └── 保留 realtime_minute_kline 1-3天（复盘用）
    ├── 清理 AkshareCollector watchlist
    └── 清理 TieredMemoryCache
```

### 4.2 启动数据完整性检查

`catch_up_if_needed()` 在应用启动时执行：

```python
# 当前实现（简化版）：
date_df = ecm.conn.execute(
    "SELECT DISTINCT trade_date FROM daily_cache ORDER BY trade_date DESC LIMIT 1"
).fetchdf()
max_date = date_df['trade_date'].iloc[0]
if max_date is None → 全量同步
elif max_date < today → 增量同步
```

**⚠️ 当前仅检查全局最新交易日，不检查单只股票的数据完整性。**

### 4.3 健康监控

**DataSourceManager 健康检查：**

| 指标 | 阈值 | 动作 |
|:-----|:-----|:-----|
| 延迟 > 5s | DEGRADED | 记录降级状态 |
| 连续失败 3 次 | FALLBACK | 自动切到备用数据源 |
| 连续失败 6 次 | UNAVAILABLE | 标记不可用 |
| 连续成功 3 次 | → NORMAL | 自动恢复 |

**L3 引擎健康指标（`screener_strategy_integration.py`）：**

```python
_L3_ENGINE_HEALTH = {
    'total_runs', 'total_stocks_processed', 'total_errors',
    'chanlun_errors', 'vp_errors', 'last_run_status', ...
}
# 错误率 > 20% 时自动告警
```

### 4.4 异常场景降级保障

| 场景 | 降级路径 | 影响范围 |
|:-----|:---------|:---------|
| Tushare API 不可用 | 使用 DuckDB 已有缓存 | 新数据不可用，历史数据可读 |
| Tushare 配额耗尽（5000分/天） | 跳过当日同步，次日重试 | 当日增量数据缺失 |
| AKShare 采集器崩溃 | 使用 DuckDB as_* 归档（最多30日前） | 盘中实时数据不可用 |
| AKShare 单接口失败 | 不影响其他线程 | 仅对应数据缺失 |
| DuckDB 文件损坏 | 自动备份恢复 | 少量数据丢失（最多保留3个备份） |
| PG 连接失败 | 跳过 PG 写入，只写内存 + DuckDB | 盘中 PG 持久缺失 |
| 网络断开 | 所有外网调用失败 | 无新数据，仅缓存可用 |

### 4.5 代理环境变量免疫（240号方案）

AkshareCollector 在模块加载时清除代理环境变量：

```python
for _k in ['HTTP_PROXY', 'HTTPS_PROXY', 'ALL_PROXY', 'http_proxy', 'https_proxy', 'all_proxy']:
    os.environ.pop(_k, None)
```

**原因：** 东方财富 API 是内部 HTTP 接口，走系统代理会连接失败。这是用户本地开发环境有代理配置时的常见问题。

## 五、数据处理

### 5.1 三种写入策略

| 策略 | 适用场景 | DuckDB 操作 | 说明 |
|:-----|:---------|:------------|:------|
| **覆盖（overwrite）** | 快照/板块排行/涨跌停池 | `DELETE + INSERT` | 数据是瞬间状态，旧值无保留价值 |
| **追加（append）** | 分钟K线 | `INSERT` | 时间序列数据，需要累积 |
| **按需（on-demand）** | 龙虎榜/新闻/个股盘口 | `INSERT OR REPLACE` | 有则更新，无则插入 |

### 5.2 日期格式统一

全局数据体系强制使用 `YYYY-MM-DD` 格式存储：

| 来源格式 | 存储格式 | 转换位置 |
|:---------|:---------|:---------|
| Tushare: `20260107` | `2026-01-07` | `tushare_provider.py` 各方法内 |
| AKShare: `2026-01-07` | `2026-01-07` | 直接一致 |
| 前端查询参数 | → 统一转换 | `utils/date_utils.py` |

### 5.3 资金流向数据计算

`get_cached_moneyflow()` 返回的 `net_lg_amount`（主力净流入）是对原始 `buy_lg_amount - sell_lg_amount` 的聚合计算，按股票+日期汇总。

### 5.4 复权因子处理

`adj_factor_cache` 存储 Tushare 的 `adj_factor` 数据，用于策略中前复权/后复权计算。当前策略层（Chanlun/VolumePrice）**均未使用复权数据**，直接使用原始 OHLCV。

### 5.5 财务数据状态

TushareProvider 暴露了 `fina_indicator/income/balancesheet/cashflow/top10_holders/holdernumber/margin/forecast` 等财务数据 API，但 **DuckDB 中没有对应的持久缓存表**。每次调用直接请求 Tushare API，消耗 Token 配额。

**影响：** 当前无任何策略依赖财务数据，但若未来需引入基本面策略，需先建立 DuckDB 缓存层。

## 六、数据存储

### 6.1 存储全景

```
┌─────────────────────────────────────────────────────────┐
│                   数据存储全景                             │
├─────────────┬─────────────┬──────────┬───────────────┤
│ 存储层      │ 存储引擎    │ 数据范围 │ 生命周期       │
├─────────────┼─────────────┼──────────┼───────────────┤
│ L1 热缓存   │ InMemory    │ 盘中实时 │ 日终清理       │
│ L2 归档     │ DuckDB      │ 盘后+盘中│ 永久/30日      │
│ L3 业务数据 │ PG/SQLite   │ 业务表   │ 永久           │
│ L4 原始API  │ Tushare/AK  │ 按需获取 │ 调用时获取     │
└─────────────┴─────────────┴──────────┴───────────────┘
```

### 6.2 DuckDB 表清单

#### ★ cache 表（Tushare 盘后同步，永久存储）

| 表名 | 主键 | 核心字段 | 数据来源 | 五大约束 |
|:-----|:-----|:---------|:---------|:---------|
| **daily_cache** | (ts_code, trade_date) | open/high/low/close/vol/amount/pct_chg | Tushare get_daily | **历史K线⏺** |
| **daily_basic_cache** | (ts_code, trade_date) | turnover_rate/volume_ratio/pe/pb/total_mv/circ_mv/dv_ratio | Tushare get_daily_basic | **基本面⏺** |
| **moneyflow_cache** | (ts_code, trade_date) | buy_lg/sell_lg/buy_elg/sell_elg/buy_mg/sell_mg/... | Tushare get_moneyflow | **资金流⏺** |
| **adj_factor_cache** | (ts_code, trade_date) | adj_factor | Tushare get_adj_factor | **复权⏺** |
| **chip_distribution_cache** | (ts_code, trade_date) | asr_5d/asr_10d/concentration_1d/concentration_5d/phase | ECM计算 | **筹码分布⏺** |
| **indicator_cache** | (ts_code, trade_date, indicator_name) | value | 策略计算结果 | **指标⏺** |
| **win_rate_cache** | (signal_type) | 胜率统计 | 回测结果 | **胜率⏺** |

| **as_sector_ranking** | 覆盖 | sector_name/change_pct/total_mv/up_count/down_count | AKShare 板块排行 |
| **as_concept_ranking** | 覆盖 | concept_name/change_pct/up_count/down_count | AKShare 概念排行 |
| **as_limit_pool** | 覆盖 | ts_code/name/price/limit_type/change_pct | AKShare 涨跌停 |
| **as_minute_kline** | 追加 | ts_code/trade_date/time/open/close/high/low/vol | AKShare 分钟K线 |
| **as_lhb_detail** | 覆盖 | ts_code/name/trade_date/buy_amount/sell_amount/net_amount | AKShare 龙虎榜 |
| **as_news** | 按需 | title/content/publish_time/source | AKShare 新闻 |
| **as_quote_cache** | 按需 | ts_code/bid/ask/last_close/quote_time | AKShare 盘口 |

## 八、红线规则与合规检查

### 8.1 244号方案 §2.3 四红线

| 规则编号 | 规则内容 | 检查结果 |
|:---------|:---------|:---------|
| **R1** | Route 层不能直接调 Tushare/AKShare API | ✅ 所有路由通过 DataManager 或 DataSourceManager |
| **R2** | Service 层不能直接调 Tushare/AKShare API | ⚠️ 部分 Service 有间接违规（见 8.2） |
| **R3** | Engine 层不能直接调 Tushare/AKShare API | ❌ **DarwinRiskFilter 直接调 Tushare HTTP（P0 违规）** |
| **R4** | 所有数据写操作必须通过 ECM（DuckDB）或 DataManager | ✅ DataManager 统一管理写路径 |

### 8.2 当前违规项详述

#### P0 违规：DarwinRiskFilter 直接调 Tushare HTTP

**文件：** `backend/app/engine/framework/screener.py`

**违规代码：**

```python
# 1. 直接 HTTP 调用 Tushare API（_tushare_pro 方法）
def _tushare_pro():
    import tushare as ts
    ts.set_token(token)
    return ts.pro_api()

# 2. 使用 @lru_cache DIY 缓存（绕过 EnhancedCacheManager）
@lru_cache(maxsize=5000)
def _fetch_stock_name(ts_code: str) -> str: ...

# 3. DarwinRiskFilter._filter_low_liquidity() 中有 Tushare fallback
# 4. DarwinRiskFilter._filter_st() 三阶回退中最后一级调 Tushare
```

**影响：** 违反 244 号方案 §2.3 红线 R3。Engine 层直接调用 Tushare API 绕过 DataManager 缓存层，无法利用 DuckDB 缓存、无法统计调用量、消耗 Tushare 配额且绕过了数据质量检查。

**修复方向：** 替换为 `DataManager.get_cached_daily_basic()` + `DataManager.get_stock_list()`。所有需要的信息在 `daily_basic_cache`（turnover_rate/volume_ratio）和 `Stock` 表（name/industry/list_status）中已存在。

### 8.3 合规路径对照表

| 需求场景 | 合规路径 | 当前违规路径 |
|:---------|:---------|:-------------|
| 获取股票名称 | `Stock.query.filter_by(ts_code=...).first()` | `_fetch_stock_name()` → Tushare HTTP |
| 获取股票行业 | `Stock.query` → `DataManager.get_cached_daily_basic()` | `_get_stock_industry()` → ORM + DataManager（ORM 访问违规但已有相关字段） |
| 判断 ST 股票 | `daily_basic_cache` 的 `name` 字段含 `*ST` / `ST` 前缀 | `_filter_st()` → Stock ORM → Tushare HTTP |
| 获取换手率/量比 | `DataManager.get_cached_daily_basic()` | `_filter_low_liquidity()` → Tushare fallback |

## 九、已发现的问题清单

### 9.1 数据基础设施问题

#### P0-1: sync_all_daily_data() 无断点续传机制

**位置：** `backend/app/data/__init__.py`

**现象：** `sync_all_daily_data()` 遍历 `Stock.query.all()`（约 5000 只股票），逐一调用 Tushare API，不设 checkpoint。中间失败后：
- 已同步的股票数据已写入
- 未同步的股票数据缺失
- 无法判断哪些已同步、哪些未同步
- 再次执行时从头开始，消耗 5000 API 调用

**影响：** 首次部署 / 数据重建时，中途失败导致不一致状态，修复耗时需重新消费 2-3 天 Tushare 配额。

**修复方向：** 在 daily_cache 中记录每只股票的 `max(trade_date)`，分批同步，失败时从断点恢复。

#### P0-2: catch_up_if_needed() 仅检查全局最新日期

**位置：** `backend/app/scheduler_manager.py`

**现象：** `catch_up_if_needed()` 仅执行以下查询判断是否需要补采：

```python
SELECT DISTINCT trade_date FROM daily_cache ORDER BY trade_date DESC LIMIT 1
```

而非按股票检查数据连续性。

**场景举例：** 新上市股票（如 2026-06 IPO）不会自动触发数据同步，只有当该股票被选股系统查询时，`get_cached_daily_data()` 的缓存未命中才触发回退到 Tushare。

**影响：** 新上市公司股票在选股系统中数据量不足（只有几天），永远无法通过 L2/L3 的 60 日/120 日最低数据要求。

**修复方向：** `catch_up_if_needed()` 增加按 `(ts_code, max_trade_date)` 的检查，对数据不足 120 日的股票发起增量同步。

#### P1-3: load_stock_data_batch() 静默跳过数据不足股票

**位置：** `backend/app/routes/screener.py`

**现象：** 选股系统批量获取数据时，`get_cached_daily_data()` 返回空或不足 120 行的股票被静默跳过，不触发按需补采。

**影响：** 新股票 / 数据不全的股票永远无法进入选股范围。

**修复方向：** `load_stock_data_batch()` 检测数据不足 120 行的股票 → 触发 `DataManager.sync_daily_data(ts_code)` 按需补采 → 重试读取。

### 9.2 数据消费问题

#### P2-4: moneyflow_cache 数据未被策略消费

**现象：** `moneyflow_cache` 在 DuckDB 中正常同步，包含 5000 只股票的逐日 `buy_lg/sell_lg/net_lg_amount` 等资金流向字段，但当前没有任何策略使用这些数据。

**未消费的数据字段：**

| 字段 | 含义 | 可使用策略 |
|:-----|:------|:-----------|
| `net_lg_amount` | 主力净流入 | ChipStrategy / 选股 L2 增强 |
| `buy_lg_amount` | 超大单买入 | 资金面策略 |
| `sell_lg_amount` | 超大单卖出 | 资金面策略 |
| `net_mg_amount` | 中单净流入 | 跟庄策略 |

**影响：** 每日常规同步消耗 Tushare 配额的 20%（约 2000 分），但数据零消耗，纯浪费。

**修复方向：**
1. ChipScorer V3 集成 `net_lg_amount` 作为第五维度（资金流向维度）—— `moneyflow_cache` 已有完整的 `(ts_code, trade_date, net_lg_amount)` 数据
2. 或在新策略中引入资金面评分

#### P2-5: daily_basic_cache 大量字段未被消费

**现象：** `daily_basic_cache` 同步了丰富的每日基本面数据，但当前策略仅使用 `turnover_rate`（DarwinRiskFilter 换手率过滤）和 `volume_ratio`（备选）。

| 字段 | 当前状态 |
|:-----|:---------|
| `turnover_rate` | ✅ DarwinRiskFilter 用于低流动性过滤 |
| `volume_ratio` | ✅ 备选字段 |
| `pe` (市盈率) | ❌ 未使用 |
| `pb` (市净率) | ❌ 未使用 |
| `total_mv` (总市值) | ❌ 未使用 |
| `circ_mv` (流通市值) | ❌ 未使用 |
| `dv_ratio` (股息率) | ❌ 未使用 |
| `ps` (市销率) | ❌ 未使用 |

**影响：** 基础面数据同步消耗配额但零价值回报。注意这是"未利用"而非"不该同步"——未来基本面策略可能需要这些数据。需要决策：是否暂停低价值字段的同步，或在基本面策略开发后再恢复。

#### P2-6: market_context 参数未从调用方传递

**位置：** `backend/app/engine/framework/screener_strategy_integration.py:255` -> `screen_l3_candidates()`

**现象：** 缠论和量价策略的 `analyze()` 方法支持可选的 `market_context` 参数（含 `turnover_rate`、`net_lg_amount`、`index_condition` 等市场环境信息），但 `screen_l3_candidates()` 在调用时始终传 `None`。

这些数据在 DuckDB 中存在（`moneyflow_cache`、`daily_basic_cache`），但管道未连接。

**影响：** L3 评分缺少市场环境上下文，个股评分在市场极端行情下可能出现误判。

### 9.3 财经数据缓存缺失

#### P3-7: 财务数据无 DuckDB 缓存

**现象：** TushareProvider 暴露了 `fina_indicator/income/balancesheet/cashflow` 等财务 API，但 DuckDB 中无对应的缓存表。每次调用直接请求 Tushare API，按次消耗额度。

**当前状态：** 无任何策略依赖财务数据，所以这一缺失尚未造成直接影响。

**修复建议：** 在引入基本面策略前，先在 DuckDB 中创建 `fina_indicator_cache` 等表，并完成首次全量数据同步。
