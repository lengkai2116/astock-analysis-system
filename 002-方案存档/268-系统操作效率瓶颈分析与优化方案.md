# 系统操作效率瓶颈分析与优化方案

## 一、问题概述

现阶段系统启动后台后（双进程独立模式），弹出浏览器窗口后操作层面的耗时较长，与常规 A 股证券软件（如同花顺、通达信、东方财富等）的响应感知存在明显差异。用户每次页面操作、数据加载的等待时间超出可接受范围。

## 二、当前系统架构梳理

### 2.1 双进程架构

```
数据进程 (data_daemon.py)          API 进程 (run.py)
  ┌──────────────────────┐          ┌──────────────────────┐
  │ mootdx TCP (5s)      │          │ Flask REST :5001     │
  │ AKShare 补充 (30min)  │  ──→──   │ SocketIO WebSocket    │
  │ 完整性检查/补采       │  读写     │ APScheduler           │
  │ 指标预计算            │  ECM      │ 读 ECM + 写 PG       │
  │ 分钟K线回填           │  SQLite   │                      │
  └──────────┬───────────┘          └──────────┬───────────┘
             │                                 │
             └──── ECM SQLite (WAL) ───────────┘
                           ↓
                 PostgreSQL (业务数据)
```

### 2.2 前端架构

- 前端为 **HTML 原型**（`_ui-prototype/`），非 SPA/Vue 构建产物
- 每个页面是独立 HTML，页面切换为全量加载
- 使用 ECharts CDN（`cdn.jsdelivr.net`）、Socket.IO CDN（`cdn.socket.io`）——依赖外部网络
- 仪表盘页面首次加载发起 **7 个并行 REST 请求**

### 2.3 数据缓存体系

| 层级 | 实现 | 容量 | 说明 |
|------|------|------|------|
| 内存缓存 | `TieredMemoryCache` (cachetools.TTLCache) | realtime: 100条/3s, intraday: 200条/5min, analysis: 100条/30min | **容量太小，几乎无命中率** |
| 盘后缓存 | `EnhancedCacheManager` (SQLite WAL) | **16GB** (stock_cache.db) | 主存储，读延迟高 |
| 盘中内存 | `InMemoryStateStore` | 全量快照 | 仅盘中有效 |

## 三、核心性能瓶颈（按严重程度排序）

### 🔴 P0 — ECM SQLite 数据库 16GB，查询极慢

**现状：**
- `stock_cache.db` = **16GB**（单文件 SQLite）
- `indicator_cache`：~**8,500 万行**
- `factor_cache`：~**3,700 万行**
- `daily_cache`：~**575 万行**
- 简单的 `SELECT COUNT(*)` 查询 **超时 >10s**

**根因：**
1. SQLite 适用于 MB~低GB 级数据，16GB 已远超其设计适用区间
2. `indicator_cache` 85M 行 + `factor_cache` 37M 行= 122M 行指标数据，占总数据量绝大部分
3. 表索引仅 primary key，无针对 `trade_date` 等查询列的辅助索引
4. `get_cached_daily_batch()` 执行 `SELECT * FROM daily_cache` **全表扫描 + 全量加载到内存**

**影响：**
- 仪表盘每次加载：4 次 `get_index_daily` + 资金流向 + 板块数据 → 多次 16GB DB 查询
- `screener/run` POST → 全量数据扫描
- 用户等待 3-10s 才能看到页面数据

### 🟠 P1 — API 进程启动开销大

**现状：**
- `create_app()` 执行：db init → model 导入 → blueprint 注册(33个) → 前端挂载 → RuntimeConfig → APScheduler init → catch_up_if_needed → collector检查
- `catch_up_if_needed()` 启动线程：`_catch_up_daily_basic` + 可能触发 `run_daily_sync()`
- 虽有 `DATA_DAEMON_RUNNING=1` 跳过采集器，但整体启动仍在 5-10s+ 级别

### 🟠 P2 — 前端非 SPA，每次导航全量加载

**现状：**
- 从 `dashboard.html` 跳转到 `screener.html` → 全新 HTML 加载 + CSS 重载 + CDN 资源下载
- 无前端路由缓存，无数据状态保持
- 依赖外部 CDN（若网络慢，JS/CSS 加载延迟）

**影响：**
- 页面切换 1-3s（CDN 资源下载）
- 每次进入页面重新发 5-7 个 API 请求

### 🟡 P3 — 仪表盘 7 个并行请求缺乏聚合

**现状：**
- 首次加载：`market/overview` + `market/index-daily` + `dashboard/summary` + `market/moneyflow-summary` + `market/sector-sector` + `market/sector-moneyflow` + `market/daily-top` + `screener/run`
- 每个请求独立查询 16GB SQLite
- 无批量 API 合并

### 🟡 P4 — APScheduler 和后台任务在 API 进程中运行

- APScheduler 的 `catch_up_if_needed()` 在 API 进程启动时运行
- 数据同步、指标预计算等后台任务与前端请求争抢 ECM SQLite 连接
- SQLite WAL 模式下写操作虽不阻塞读，但大量写入仍会争夺 I/O

### 🟡 P5 — 无 CDN 资源本地化

- ECharts 5.4.3 (~1MB) 和 Socket.IO 4.7.5 (~60KB) 需从 CDN 下载
- 若网络不佳，首次加载延迟明显
- 可本地化或使用 importmap 缓存

### 🔵 P6 — 未使用 HTTP 缓存策略

- 所有 API 响应无 `Cache-Control` / `ETag` 头
- 前端无客户端缓存（localStorage/IndexedDB）
- 同一页面的相同数据每次重新请求

## 四、与同类证券软件的对比分析

| 维度 | 同花顺/通达信 | 本系统 |
|------|--------------|--------|
| 启动时间 | 2-5s（本地客户端） | 5-15s（后端启动+浏览器） |
| 页面切换 | 即时（桌面原生） | 1-3s（HTML全量加载） |
| 数据刷新 | 推送式（TCP/P2P 行情） | 轮询式（REST + 部分SocketIO） |
| 首次加载 | 毫秒级（本地数据文件） | 3-10s（16GB SQLite查询） |
| 行情延迟 | <1s（TCP直连交易所） | 5s（mootdx TCP采集周期） |
| 数据量 | 本地数据文件按需加载 | 16GB 单文件 SQLite |

**关键差异：** 商业证券软件使用 C++ 原生客户端 + 内存数据库 + 推送式行情管道；本系统使用 Python Web 应用 + 单文件 SQLite + REST 轮询模式。架构定位不同，但用户体验差距需要通过分层缓存和查询优化来弥合。

## 五、优化方案（按优先级）

### 方案 A：ECM SQLite 性能优化（P0，最高优先级）

**目标：** 将 16GB SQLite 的平均查询延迟从 >3s 降低到 <200ms

| 子项 | 措施 | 预期效果 |
|------|------|---------|
| A1 | **添加缺失的数据库索引**：`daily_cache` 加 `(trade_date)` 索引，`indicator_cache` 加 `(ts_code, trade_date)` 辅助索引，`factor_cache` 加 `(ts_code, factor_name)` 索引 | 过滤查询提速 10-100x |
| A2 | **数据归档/分区**：将 `indicator_cache`（85M行）按时间分区，仅保留最近 120 交易日数据到主表，更早数据归档到归档表 | 主表缩小 ~70% |
| A3 | **VACUUM**：添加索引和删除数据后执行 `VACUUM` 回收空间 | 文件缩小、查询加速 |
| A4 | **SQLite WAL 检查点收缩**：定期执行 `PRAGMA wal_checkpoint(TRUNCATE)` | 减少 WAL 文件大小 |
| A5 | **查询语句优化**：避免 `SELECT *`，改为仅查询需要的列 | 减少 I/O |

### 方案 B：API 响应缓存层（P1）

**目标：** 仪表盘 / 市场总览等高频接口添加内存缓存，避免重复查询 16GB DB

| 子项 | 措施 | 预期效果 |
|------|------|---------|
| B1 | **扩展 TieredMemoryCache**：从 200 条上限提升到 2000+ 条，增加 `dashboard` 级别的 TTL（60s-300s） | 高频调用命中率从 ~5% → ~80% |
| B2 | **API 响应缓存装饰器**：对 `market/overview`、`market/index-daily`、`market/sector-sector` 等添加短 TTL 缓存（同 3-5s 数据无需重复查 DB） | 同一 T 内重复请求即时返回 |
| B3 | **前端数据缓存**：仪表盘页面加载后，前端缓存最近 30s 的响应，避免页面最小化/切换回时重复请求 | 提升交互连贯性 |

### 方案 C：前端 SPA 改造（P2）

**目标：** 页面切换从 1-3s 降低到 <300ms

| 子项 | 措施 | 预期效果 |
|------|------|---------|
| C1 | **前端构建**：完成 `frontend/vue-project/` 的 Vue SPA 构建，替换 HTML 原型 | 页面切换无需全量加载 |
| C2 | **CDN 本地化**：ECharts、Socket.IO 等依赖下载到本地静态目录，或使用 `npm` 打包 | 消除 CDN 网络延迟 |
| C3 | **路由级代码分割**：Vue Router 懒加载 | 首屏体积减小 60% |

### 方案 D：仪表盘数据聚合 API（P3）

**目标：** 7 个请求合并为 1-2 个，减少 HTTP 往返和 DB 查询次数

| 子项 | 措施 | 预期效果 |
|------|------|---------|
| D1 | **新增 `GET /api/v3/dashboard/full`**：返回仪表盘所需的全部数据（指数、成交额、雷达、资金流、板块、涨跌榜、信号汇总） | 7请求 → 1请求 |
| D2 | **服务层批量查询**：在后端一次查询 16GB DB 获取全部所需数据，避免多次 I/O | DB 查询次数减少 80% |

### 方案 E：数据进程与 API 进程职责优化（P4）

| 子项 | 措施 | 预期效果 |
|------|------|---------|
| E1 | **API 进程 APScheduler 延迟初始化**：将 `catch_up_if_needed()` 延迟到 API 进程启动 30s 后执行 | 前端加载不受后台任务干扰 |
| E2 | **DB 连接隔离**：数据进程和 API 进程使用独立的 SQLite 连接（当前已通过 `get_ecm_instance()` 共享） | — |

## 六、建议优先级路线图

### 第一阶段（立竿见影，1-2 天完成）

| # | 措施 | 预期提速 | 风险 |
|---|------|---------|------|
| 1 | 添加 DB 索引（A1） | 仪表盘加载 10x | 低，CREATE INDEX 仅首次慢 |
| 2 | API 响应缓存装饰器（B2） | 重复请求 0ms | 低，cachetools 已依赖 |
| 3 | CDN 本地化（C2） | 加载快 0.5-2s | 低，下载到本地即可 |
| 4 | VACUUM + WAL 收缩（A3/A4） | 查询 1.5-2x | 低，需磁盘空间 |

### 第二阶段（1 周内完成）

| # | 措施 | 预期提速 | 风险 |
|---|------|---------|------|
| 5 | 仪表盘聚合 API（D1/D2） | 仪表盘 3x | 中，需重构前端调用 |
| 6 | 扩展内存缓存（B1） | 高频查询 10x | 低 |
| 7 | 指标数据归档（A2） | 全库查询 3-5x | 中，需迁移脚本 |
| 8 | APScheduler 延迟初始化（E1） | 启动 3-5s 快 | 低 |

### 第三阶段（选做，长期优化）

| # | 措施 | 预期效果 |
|---|------|---------|
| 9 | 前端 SPA 构建（C1/C3） | 页面切换即时 |
| 10 | PostgreSQL 替代 SQLite 作为缓存层 | 查询能力提升 50x，但需评估新依赖 |

**建议当前优先实施第一阶段的 4 项措施**，可以在 1-2 天内显著提升操作感知，且改动风险最低。

## 七、关键风险提示

1. **16GB SQLite 的极限**：即使添加索引，SQLite 在 16GB 级别的查询性能依然有限。如果用户量增长或数据持续积累，建议在第二阶段考虑将高频查询表迁移到 PostgreSQL（系统已配置 PG 连接）。
2. **指标数据库膨胀**：`indicator_cache`（85M行）和 `factor_cache`（37M行）是最大的两个表，需要设计数据保留策略（如仅保留最近 120 个交易日）。
3. **ECM 全局单例锁**：`get_ecm_instance()` 使用 `threading.Lock` 确保单例，多线程访问时虽不阻塞读，但写入串行化。数据进程的写入窗和 API 进程的查询窗应尽量错峰。
