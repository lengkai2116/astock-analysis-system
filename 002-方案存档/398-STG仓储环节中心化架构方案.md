# 398 — STG仓储环节中心化架构方案

> **背景**：396/397号方案核查dim2及SIG管道时发现多个系统级问题：compute_cache.db连接竞态（44个fd泄漏）、indicator写入因锁竞争静默失败、SIG预计算无质量自检、管道失败无自动恢复。根因是当前架构中各环节直接操作数据库，缺乏统一的写入协调和数据质量校验。本方案将STG（存储环节）从被动网关升级为主动仓储管理器，作为全管道的中心调度节点。

---

## 一、问题诊断

### 1.1 当前架构缺陷

| 缺陷 | 表现 | 根因 |
|------|------|------|
| 写入竞态 | compute_cache.db 44个fd泄漏（396号已修） | 各环节直连DB，无统一写入协调 |
| 数据静默失败 | indicator写入`database is locked`后静默丢弃 | 写入失败无重试/告警机制 |
| 无质量自检 | SIG预计算结果无验证，缺失/错误数据直接传递 | 各环节无写入后校验 |
| 管道不可恢复 | SIG失败后需重启daemon | 无断点恢复机制 |
| 数据审计缺失 | 数据质量问题无追踪记录 | 无校验日志 |
| 降级兜底掩盖问题 | dim8空字段静默降级到"数据不足" | 空字段未区分数据管道故障/正常分析结论 |

### 1.2 数据库写入现状

| 写入者 | 目标库 | 写入方式 | 问题 |
|--------|--------|---------|------|
| COL采集 | market_cache.db | 实时逐条写入 | 正常 |
| RAW-1/2/3 | compute_cache.db | 批量写入 | 已修复竞态 |
| SIG | snapshot_cache.db | 独立短连接批量写入 | 路由不一致（sharding指向stock_cache.db） |
| JUD | snapshot_cache.db | ecm.conn直连写入 | 未走sharding_manager |
| OUT | snapshot_cache.db | ecm.conn直连写入 | 未走sharding_manager |

### 1.3 SIG管道时序问题

| 问题 | 影响 |
|------|------|
| 管道只处理最新数据日期 | 历史日期的SIG失败不会被自动修复 |
| 无计算结果质量验证 | signal_json/dim_results_json缺失或异常不会被捕获 |
| 无seven_dim_json生成验证 | dim8失败时降级到旧函数，但降级结果无质量校验 |

## 二、架构设计

### 2.1 STG定位升级

```
当前：STG = 被动数据网关（只存储，不校验）
    COL ──写入──→ market_cache.db ←── 读取── RAW
    RAW ──写入──→ compute_cache.db ←── 读取── SIG
    SIG ──写入──→ snapshot_cache.db ←── 读取── JUD
    JUD ──写入──→ snapshot_cache.db ←── 读取── OUT

升级后：STG = 主动仓储管理器（存储+校验+调度）
    COL ──写入──→ STG网关 ──校验──→ market_cache.db
    RAW ──写入──→ STG网关 ──校验──→ compute_cache.db
    SIG ──写入──→ STG网关 ──校验──→ snapshot_cache.db
    JUD ──读取──→ STG网关 ──校验──→ snapshot_cache.db
    OUT ──写入──→ STG网关 ──校验──→ snapshot_cache.db
                      │
                 ┌────┴────┐
                 │ 核查调度器 │
                 │ 问题→补算 │
                 └─────────┘
```

### 2.2 核心组件

#### 组件1：STG写入网关（WriteGateway）

```python
class WriteGateway:
    """统一写入网关——所有环节通过此入口写入数据库"""
    
    def write_batch(self, table: str, rows: list, pipeline_date: str) -> WriteResult:
        """
        批量写入流程：
        1. 路由到正确的分库
        2. 获取写入锁（同库串行）
        3. 写入前校验（数据格式/非空）
        4. 执行写入（INSERT OR REPLACE）
        5. 写入后校验（行数/日期对齐）
        6. 记录写入日志
        """
    
    def validate_before_write(self, table: str, rows: list) -> ValidationResult:
        """写入前校验：数据格式、必填字段、类型检查"""
    
    def validate_after_write(self, table: str, pipeline_date: str, expected_count: int) -> ValidationResult:
        """写入后校验：行数匹配、日期对齐、关键字段非空"""
```

#### 组件2：数据质量校验器（QualityChecker）

```python
class QualityChecker:
    """数据质量校验——每张表的完整性标准"""
    
    # 校验规则定义
    RULES = {
        'daily_cache': {
            'min_rows': 4000,           # 最少行数
            'date_alignment': True,     # 日期对齐
            'required_fields': ['open', 'high', 'low', 'close', 'vol'],
        },
        'indicator_ma': {
            'min_rows': 4000,
            'date_alignment': True,     # 与daily_cache日期对齐
            'required_fields': ['ma5', 'ma20'],
            'source_table': 'daily_cache',  # 对齐基准
        },
        'strategy_signal_detail': {
            'min_rows': 4000,
            'required_fields': ['signal_json', 'dim_results_json'],
            'json_validity': True,      # JSON格式校验
        },
        'status_snapshot': {
            'min_rows': 4000,
            'required_fields': ['dim_states', 'status_bar'],
        },
    }
    
    def check_table(self, table: str, pipeline_date: str) -> CheckResult:
        """执行单表校验，返回缺失/错误详情"""
    
    def check_cross_table(self, pipeline_date: str) -> CrossCheckResult:
        """跨表校验：indicator与daily_cache日期对齐等"""
    
    def multi_round_check(self, pipeline_date: str, max_rounds: int = 3) -> list:
        """多轮核查：每轮校验→补算→再校验，直到通过或达到上限"""
```

#### 组件3：补算调度器（RecomputeScheduler）

```python
class RecomputeScheduler:
    """数据问题→责任环节的映射和调度"""
    
    # 数据问题→责任环节映射
    RECOMPUTE_MAP = {
        'daily_cache缺失':        ('COL', '_batch_daily'),
        'indicator_ma缺失':       ('RAW', '_precompute_indicators'),
        'indicator_ma日期不对齐':  ('RAW', '_precompute_indicators'),
        'pre_feat_cache缺失':     ('RAW', '_precompute_raw_features'),
        'factor_cache缺失':       ('RAW', '_precompute_preset_combos'),
        'signal_json缺失':        ('SIG', '_precompute_strategy_signals'),
        'dim_results_json缺失':   ('SIG', '_precompute_strategy_signals'),
        'status_snapshot缺失':    ('JUD', '_build_status_snapshot'),
    }
    
    def schedule_recompute(self, issue: str, pipeline_date: str) -> bool:
        """根据问题类型调度对应环节补算"""
    
    def check_recompute_needed(self, check_result: CheckResult) -> list:
        """从校验结果中提取需要补算的问题列表"""
```

#### 组件4：输出语义化控制器（OutputSemanticController）

解决dim8降级兜底问题——空字段不再静默降级，而是区分两种情况：

| 空字段类型 | 处理方式 | 示例 |
|-----------|---------|------|
| 数据管道故障 | STG触发补算，不输出 | indicator_ma缺失→触发RAW-1补算 |
| 正常分析结论 | 输出有意义的"无"文本 | 无背驰→"无背驰信号" |
| 无买卖点 | 输出"无明显买卖点信号" | buy_sell_points=[]→有意义的空结论 |

```python
class OutputSemanticController:
    """输出语义化控制器——替代dim8的plain降级兜底"""
    
    # 空字段语义化映射
    EMPTY_SEMANTICS = {
        'buy_sell_points': '无明显买卖点信号',
        'divergence_type': '无背驰信号',
        'chanlun_direction': '缠论方向未确定',
        'vs_ma': '均线数据不足',
        'vs_indicator': '技术指标数据不足',
    }
    
    def semanticize_empty(self, dim_key: str, field: str, value) -> str:
        """空字段语义化：正常空→有意义文本；故障空→触发补算"""
        if value is None or value == '' or value == [] or value == {}:
            # 检查是否为数据管道故障
            if self._is_data_pipe_failure(dim_key, field):
                raise DataPipeFailureError(f'{dim_key}.{field} 数据管道故障')
            # 正常空→语义化文本
            return self.EMPTY_SEMANTICS.get(f'{dim_key}.{field}', '数据不足')
        return value
```

### 2.3 写入时序模型

```
Round 1（写入后立即校验）：
  STG.write_batch(table, rows)
    → validate_before_write()   # 格式校验
    → INSERT OR REPLACE          # 写入
    → validate_after_write()     # 行数校验
    → if 失败 → schedule_recompute()

Round 2（全管道完成后校验）：
  Pipeline.all_steps_done()
    → QualityChecker.check_cross_table()  # 跨表对齐校验
    → if 缺失 → schedule_recompute() + 多轮核查

Round 3（次日开盘前兜底）：
  _is_market_hours() 前
    → QualityChecker.multi_round_check(max_rounds=3)
    → 告警升级（邮件/日志）
```

### 3.3 Phase 3：实现校验逻辑

```python
# 写入后校验示例
def validate_after_write(self, table, pipeline_date, expected_count):
    actual_count = self._query_count(table, pipeline_date)
    if actual_count < expected_count * 0.95:
        return ValidationResult(
            passed=False,
            issue=f'{table}行数不足: 期望{expected_count}, 实际{actual_count}',
            severity='HIGH'
        )
    return ValidationResult(passed=True)

# 跨表校验示例
def check_indicator_alignment(self, pipeline_date):
    dc_count = self._query_count('daily_cache', pipeline_date)
    for table in ['indicator_ma', 'indicator_other', 'indicator_macd']:
        im_count = self._query_count(table, pipeline_date)
        if im_count < dc_count * 0.95:
            return CrossCheckResult(
                passed=False,
                issue=f'{table}与daily_cache日期不对齐: daily={dc_count}, {table}={im_count}',
                recompute_key=f'{table}日期不对齐'
            )
    return CrossCheckResult(passed=True)
```

### 3.4 Phase 4：实现补算调度

```python
# 补算调度示例
def schedule_recompute(self, issue, pipeline_date):
    recompute_func = self.RECOMPUTE_MAP.get(issue)
    if not recompute_func:
        logger.warning(f"无对应补算函数: {issue}")
        return False
    
    step_name, func_name = recompute_func
    logger.info(f"触发补算: {issue} → {step_name}.{func_name}")
    
    # 更新pipeline_status为pending
    self._ecm.conn.execute(
        "UPDATE pipeline_status SET status='pending' "
        "WHERE pipeline_date=? AND step_id=?",
        [pipeline_date, step_name]
    )
    self._ecm.conn.commit()
    
    return True
```

### 3.5 Phase 5：多轮核查+告警

```python
def multi_round_check(self, pipeline_date, max_rounds=3):
    results = []
    for round_num in range(1, max_rounds + 1):
        check_result = self.check_cross_table(pipeline_date)
        results.append(check_result)
        
        if check_result.passed:
            logger.info(f"第{round_num}轮校验通过")
            break
        
        # 触发补算
        for issue in check_result.issues:
            self.scheduler.schedule_recompute(issue, pipeline_date)
        
        # 等待补算完成（最多5分钟）
        time.sleep(300)
    
    if not results[-1].passed:
        # 告警升级
        self._alert(f"数据校验{max_rounds}轮未通过: {results[-1].issues}")
    
    return results
```

## 四、数据库综合管理

### 4.1 写入顺序规范

```
写入优先级（从高到低）：
  1. COL实时采集（market_cache.db）—— 用户体验依赖
  2. STG校验写入（各库的pipeline_status）—— 管道状态
  3. RAW预计算（compute_cache.db）—— 分析数据基础
  4. SIG策略分析（snapshot_cache.db）—— 策略结果
  5. JUD/OUT成品（snapshot_cache.db）—— 最终输出

写入隔离规则：
  - 同库写入：串行（通过STG写入锁）
  - 异库写入：并行（无锁竞争）
  - SIG/JUD/OUT同属snapshot_cache.db：严格串行
```

### 4.2 数据库健康监控

| 监控项 | 阈值 | 动作 |
|--------|------|------|
| WAL文件大小 | >500MB | 触发checkpoint |
| 连接池使用率 | >80% | 告警 |
| 写入队列深度 | >100 | 告警 |
| 校验失败率 | >5% | 告警+暂停写入 |
| 补算重试次数 | >3 | 告警升级 |

### 4.3 数据一致性保障

| 保障机制 | 实现方式 |
|---------|---------|
| 写入原子性 | 单批commit，失败不提交 |
| 写入幂等性 | INSERT OR REPLACE，重复写入不产生重复数据 |
| 日期一致性 | 写入后校验trade_date与daily_cache对齐 |
| 跨表一致性 | indicator与daily_cache行数差异<5% |
| JSON完整性 | signal_json/dim_results_json格式校验 |
