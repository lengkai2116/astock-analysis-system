# 357 — PRE预计算层拆分实施方案

## 一、背景与范围

### 1.1 问题来源

PRE预计算层（P1-P4）当前存在结构性问题：P4（L2标签）混合了**原料加工**（11个特征提取操作）和**分析判定**（7个判定操作），导致层级职责不清，违反四层架构的单向数据流原则。

### 1.2 核心定位

PRE = **原料加工环节**，非分析环节。100%基于前一交易日日终数据，不使用盘中数据。

### 1.3 目标结构

```
当前（4步混合）                    目标（4步纯原料）
═════════════════                ═════════════════
P1: 技术指标        ─────→        PRE-IND: 技术指标（不变）
P4: L2标签(大杂烩)  ─────→        PRE-FEAT: 特征提取（拆分，仅保留原料部分）
P2: 策略信号        ─────→        PRE-SIG: 策略信号（精简）
P3: 因子值          ─────→        PRE-FAC: 量化因子（不变）
S1: 快照(成品)      ─────→        判定层（独立层级）
```

### 1.4 PRE-FEAT 10个特征组（保留的原料加工部分）

估值特征 / 情绪特征 / 板块特征 / 风格特征 / 时间特征 / 量价特征 / 缠论特征 / 筹码特征 / 事件特征 / 深度字段

### 1.5 移到判定层的7个操作

阶段判定 / 机会潜力 / 机会类型 / 七维画像 / 闸门2 / 跨维仲裁 / avoid降级

## 二、7项决策与实施方案

### 决策1：深度字段解耦

**现状**：`tag_extractor.py` 中的深度字段（筹码集中度、浮筹比例等）依赖 `phase_detector._last_chip_indicators`——阶段判定引擎的副产品。形成反向依赖（原料加工依赖分析判定）。

**方案**：在PRE-FEAT中独立调用 `ChipDistributionEstimator.calculate_all_indicators()`，不再从阶段判定引擎间接获取。

**涉及文件**：
- `backend/app/opportunity_atlas/phase_detector.py` — 移除 `_last_chip_indicators` 的外部暴露
- `backend/app/data/tag_extractor.py` — 改为独立调用 ChipDistributionEstimator

**工作量**：约2-4小时

### 决策2：PRE-FEAT vs 策略层不重复（确认结论）

**核查结论**：4个引擎均不重复——

| 引擎 | PRE-FEAT（原料） | 策略层（判定） | 依据 |
|------|-----------------|---------------|------|
| 缠论 | ChanlunAnalyzer（单周期结构） | MultiLevelChanlunAnalyzer（多周期+评分） | 不同类 |
| 量价 | get_tags()仅12行（K线形态检测） | VolumePriceStrategy完整信号计算 | 极轻量 vs 完整 |
| 筹码 | ChipDistributionEstimator（分布特征） | ChipDistributionStrategy（买卖信号） | 不同类 |
| 情绪 | MarketSentimentService（四阶段） | Bociasi快慢线（资金情绪） | 不同体系 |

**待办事项**：后续单独审核策略引擎原料层计算的逻辑和精确度。

**量价命名优化**：`get_tags()` 重命名为 `_detect_kline_patterns()` 消除与策略层的命名混淆。

### 决策3：strategy_signal_detail 分库（成品数据逻辑）

**方案**：迁移到 `snapshot_cache.db`（快照分库），与 status_snapshot/treemap_snapshot 等成品数据统一存放。

**理由**：strategy_signal_detail 是P2策略信号预计算的**输出产物**（已加工完成的策略信号），属于成品数据，应与同类成品放在一起。

**分库路由更新**：sharding_manager.py 中 strategy_signal_detail 的路由从 compute_cache.db 改为 snapshot_cache.db。

### 决策4：PRE-FEAT 存储粒度（JSON方案）

**方案**：采用JSON存储，按维度分组规范化schema。

**Schema设计**：
```json
{
  "ts_code": "000001.SZ",
  "trade_date": "2026-08-18",
  "features": {
    "valuation": {"pe_percentile": 0.75, "pb_percentile": 0.6, "ps_percentile": 0.5},
    "sentiment": {"phase": "cautious", "bociasi_signal": "neutral", "sentiment_score": 0.45},
    "sector": {"sector_momentum": 0.3, "sector_rank": 15, "is_sector_leader": false},
    "style": {"style_bias": "value", "size_factor": "large_cap"},
    "timing": {"cycle_position": "mid_cycle", "turnover_signal": "normal"},
    "volume_price": {"kline_pattern": "doji", "ma_alignment": "neutral", "vol_price_fit": "healthy"},
    "chanlun": {"trend_direction": "up", "zhongshu_count": 2, "buy_sell_point": "none"},
    "chip": {"chip_position": 0.65, "chip_concentration": 0.4, "main_force_phase": "accumulating"},
    "event": {"catalyst_type": "none", "event_sentiment": "neutral"},
    "depth": {"hold_float_ratio": 0.35, "turnover_rate": 2.1}
  },
  "computed_at": "2026-08-18T16:00:00"
}
```

**存储表**：`pre_feat_cache`（新建）

**理由**：
1. PRE-FEAT特征会持续增减，JSON灵活性更好
2. 消费方（判定层）按维度读取，JSON天然分组
3. 参考 opportunity_tags_cache 的成功模式

### 决策5：判定层执行机制（双模式）

**方案**：日终后台自动 + 用户触发按需

**模式A：日终后台自动**
- PRE层完成后自动触发判定层
- 产出当日 status_snapshot + treemap_snapshot
- 保持现有机制（data_daemon 主循环驱动）

**模式B：用户触发按需**
- 用户在个股页点击"重新分析"时触发
- 仅重算该股的判定层
- 返回即时结果，不写入快照表

**理由**：
1. 日终自动保证 treemap 每日更新
2. 用户按需支持"调参后即时验证"
3. 两者不冲突

### 决策6：opportunity_tags_cache 迁移

**方案**：直接切换到 compute_cache.db

**理由**：
- 当前数据量：0行（从未被填充实际数据）
- 迁移无成本
- 保留表结构以备后续标签缓存需求
- 若后续确认完全废弃，可删除

### 决策7：旧表 strategy_signals 清理

**方案**：彻底删除

**理由**：
- 功能已被 strategy_signal_detail 完全替代
- 仅3处引用（data_daemon.py 写入/读取/删除逻辑）
- 清理成本极低
- 避免后续开发者误用旧表

## 三、PRE层新架构总览

### 3.1 四个独立模块

| 模块 | 职责 | 输入 | 输出 | 触发时机 |
|------|------|------|------|---------|
| PRE-IND | 技术指标计算 | daily_cache | indicator_ma/macd/other | 数据到达时 |
| PRE-FEAT | 特征提取（10组原料） | daily_cache + daily_basic + moneyflow + ... | pre_feat_cache（JSON） | 数据到达时 |
| PRE-SIG | 策略信号生成 | daily_cache + pre_feat_cache + indicator_* | strategy_signal_detail | 数据到达时 |
| PRE-FAC | 量化因子计算 | daily_cache | factor_cache | 数据到达时 |

### 3.2 数据流

```
COL采集层 → STG存储层
                ↓
    ┌───────────┼───────────┐
    ↓           ↓           ↓
PRE-IND    PRE-FEAT    PRE-FAC
    ↓           ↓           ↓
    └─────→ PRE-SIG ←─────┘
                ↓
            判定层（独立）
                ↓
    status_snapshot / treemap_snapshot
```

### 3.3 管道顺序

P1(IND) → P4(FEAT) → P3(FAC) → P2(SIG) → 判定层

（与332号方案一致：P4标签先算→P2后算消费标签）
