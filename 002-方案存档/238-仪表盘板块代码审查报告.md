## 一、Bug 清单（按严重度排列）

### B0 — [严重] Tushare `moneyflow` 金额单位误处理（万元→元）

**位置**: `backend/app/services/dashboard_service.py:531-532, 953-954, 1007, 1011`
**问题**: Tushare `moneyflow` API 返回的金额字段（buy_lg_amount、sell_lg_amount 等）单位是**万元**，但代码全部按**元**处理，除以 `1e8` 试图转为"亿元"。正确除数为 `1e4`（万元→亿）。

**触发路径**:
1. `get_moneyflow_summary()` 直接 Tushare 路径：`total_main / 1e8`（应为 `/ 1e4`）
2. `_aggregate_moneyflow_by_date()` DuckDB 缓存路径：`daily[d]['main'] / 1e8`（应为 `/ 1e4`）
3. `_aggregate_sector_moneyflow()` 板块资金流向：`s['net'] / 1e8` 和 `data['net'] / 1e8`（均应为 `/ 1e4`）

**影响**: 全市场资金流向所有数值被缩小 10,000 倍。例如实际 `-3,000 亿` 变成 `-0.3`。板块资金流向同样失真。3个数据路径共 6 处全量受影响。

**根因**: Tushare 官方文档中 moneyflow API 金额字段单位为"万元"，常见误解。所有 Tushare 资金流向相关功能都需要检查单位换算。

**修复**: 全部 6 处 `/ 1e8` → `/ 1e4`。验证后 API 返回 `main_force_net_inflow` 范围 `-1046.2亿 ~ +459.6亿`，20日数据全部非零。

### B1 — [严重] 板块资金流向 `net_inflow` vs `net_flow` 字段名不匹配

**位置**: `_ui-prototype/dashboard.html:390, 395, 406, 424`
**问题**: 前端读取 `v.net_flow`，后端写入 `v.net_inflow`（`dashboard_service.py:1008`）。四个位置全部使用 `net_flow`，但 API 返回字段是 `net_inflow`。

**触发路径**:
1. 后端 `get_sector_moneyflow()` → `_aggregate_sector_moneyflow()` → 返回 `{'sectors': [{..., 'net_inflow': 值}]}`
2. 前端 `loadSectorMoneyflow()` → `v.net_flow` → `undefined` → `+(undefined||0).toFixed(1)` → `0`

**影响**: 所有板块资金流向柱状图显示为 0，流入/流出排行卡片为空。属于完全不可见的数据面板。

**根因**: 后端从旧格式迁移到 `_aggregate_sector_moneyflow` 时使用了 `net_inflow` 作为聚合计算的字段名，但前端代码未同步更新。

### B2 — [严重] `_aggregate_sector_moneyflow` 中 `ts_code` 字段被填入中文名

**位置**: `backend/app/services/dashboard_service.py:1002`
**问题**: `top_stocks.append({'ts_code': s['name'], 'name': s['name'], ...})` — `ts_code` 字段的值引用的是 `s['name']`，而不是真正的股票代码。

**触发路径**:
1. `sector_agg[ind]['stocks'][code]` 初始化时 `ts_code` 为 `code`（正确）
2. 行 990 更新 `name = name_map[code]`（正确）
3. 行 1002 构造输出时 `ts_code` 错误地使用 `s['name']`（应为 `code` 或 `s.get('ts_code', code)`）

**影响**: 任何前端逻辑依赖 `ts_code` 做跳转、查询或图表加载的地方都会收到一个中文名称而非股票代码，导致链接断裂或查询失败。

**修复**: 将 `'ts_code': s['name']` 改为 `'ts_code': code`（外层循环变量可用，或从字典取原始 key）。

### B3 — [中] `_safe_float` 未覆盖 `close` / `prev_close` 字段

**位置**: `backend/app/services/dashboard_service.py:105-106`
**问题**: `float(close)` 和 `float(prev_close)` 使用原生 `float()`，而同一函数中 `float(amount)` 已迁移到 `_safe_float`。虽然 `close`/`prev_close` 来自 SQLAlchemy ORM 列（NOT NULL），但上游数据源（Tushare/index_daily）可能返回 `NaN` 或 `None`。

**触发假设**: 当数据源某日指数的 `close` 值因数据异常返回 `NaN`：
- `float(NaN)` → `nan`
- `change = nan - float(prev_close)` → `nan`
- `change_pct = nan / float(prev_close)` → `nan`
- 前端收到 `NaN` → 展示为 `"NaN%"` 或空白

**根因**: 同样的数据源（`index_daily` JSON），`amount` 被保护了但 `close`/`prev_close` 没有。应该使用 `_safe_float` 包裹全部 3 个 `float()` 调用。

### B4 — [低] 零涨幅时的颜色判定偏差（涨红跌绿边界）

**位置**: `_ui-prototype/dashboard.html:105, 112, 137, 300` + `backend/app/services/dashboard_service.py:205`
**涉及行**:
- `chg>=0` → 行 105（颜色 class）、行 112（涨跌箭头符号）
- `cp>=0` → 行 137（板块柱状图颜色）
- `pct_chg>=0` → 行 300（成交额柱状图颜色）、py:205（板块颜色）
- `nf>=0` → 行 390（资金流向柱状图颜色）

**问题**: 当涨跌幅 = 0% 时，`>= 0` 判定为 true，即零涨幅被视为"涨"。按设计意图"涨红跌绿"，零涨幅应为中性（绿色或灰色），不应视为上涨。

**影响**:
- 0% 涨幅的指数/板块显示 ↑ 红色（实际上无变动）
- 成交额柱状图某日 `pct_chg=0` 时柱体为红色
- 资金流向柱状图净额为 0 时显示红色

**建议**: 改为 `> 0`（或 `> 0.01` 容忍极小波动）使零涨幅归入"不涨"阵营。

### B5 — [低] 雷达股 `stocks.concat(stocks)` 导致卡片数量翻倍

**位置**: `_ui-prototype/dashboard.html:318`
**问题**: `var allCards = stocks.concat(stocks)` 将雷达股票数组翻倍，每只股票渲染 2 张完全相同的卡片。

**触发假设**: 该行在旧代码中已经存在（本 diff 未修改），但 `loadRadar` 函数被改动过，属于"被触及但未修复的预存问题"。

**影响**:
- DOM 创建成本翻倍
- 视觉上出现完全重复的股票卡片
- SSR / scroller 模式下可能导致重复的导航声音

## 二、可优化项

### O1 — [重复] 三次独立的 `last_date` 查询

**位置**: `dashboard_service.py:265, 338, 412`
**描述**: `db.session.query(func.max(DailyData.trade_date)).scalar()` 在 `get_daily_top`, `get_sector_changes`, `get_dashboard_summary` 三个 fallback 中重复。单次 /dashboard/overview 请求执行 3 次。

**建议**: 抽取为 `_get_last_trade_date()` 方法并在类级别缓存（或至少提取为单次调用传入）。

---

### O2 — [重复] 三次相同的 import 块

**位置**: `dashboard_service.py:262-264, 335-337, 409-411`
**描述**: `from app import db; from sqlalchemy import func; from app.models import DailyData, Stock` 在三处 fallback 中完全一致。

**建议**: 提升到模块级别，利用 Python 模块缓存的特性避免重复 import 和解析。

---

### O3 — [性能] `import pandas as pd` 在方法内部

**位置**: `dashboard_service.py:619`
**描述**: `_build_db_top_list` 方法内部引入 pandas，在每次 Tushare 查询数据时触发完整的 pandas 加载开销。

**建议**: 
1. 将 `import pandas as pd` 移到模块顶部
2. 或直接用原生 Python 排序：`sorted(records, key=lambda r: float(r.get('pct_chg', 0)), reverse=True)[:limit]`

---

### O4 — [设计] 前端字段名归一化未提取公共层

**位置**: `dashboard.html:260(change_pct), 290(days/daily_flow), 315(stocks/radar_stocks), 317(ts_code/code), 353(main_force/net_main), 354(retail_net_outflow/net_retail), 365(sectors), 370(change_pct/pct_chg)`
**描述**: 约 7 个前端回调函数各自独立地执行字段名匹配，模式为 `a || b || c`。如果后端改名，需要逐一排查。

**建议**: 引入 `normalize()` 辅助函数，在 fetch 获取 json 后直接转换数据结构，消除散落的 `||` 模式。

---

### O5 — [设计] `_safe_float` 应上提到 DataManager 层

**位置**: `dashboard_service.py:606`
**描述**: 当前每个数据消费端都需要调用 `_safe_float`，跨 6+ 个方法。如果后续增加新的数据面板，新人容易遗漏。

**建议**: 在数据写入 DataManager 缓存时即对 NaN 字段进行清洗，下游取到的数据默认不需要 `_safe_float`。

---

### O6 — [维护] 无统一日期格式化器

**位置**: 后端 `dashboard_service.py:248` vs 前端 `dashboard.html:293, 347`
**描述**: 后端通过 `f"{dk[4:6]}/{dk[6:8]}"` 生成 MM/DD 格式，前端多处通过 `.slice(5)` 解析。如果日期格式变更，两个端需同时修改。

**建议**: 前端直接使用 `v.date`（后端已格式化的字符串），无需 `.slice(5)`。
