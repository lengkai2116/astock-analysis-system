# 通达信积分核算配置设计（轻享包试水版）

> 目标：用 ¥88/5 万积分的轻享包，建立一套**可追溯、可估算、可对账、可熔断**的 TdxAiData 积分核算体系；先回答“每次调用到底扣多少分”，再决定是否扩大采购。
> 前提：`tdxaidata` 是闭源动态库，调用返回体不含“本次扣了多少分”，因此必须做**外部计量 + 余额/流水对账**，不能只靠库内日志。

---

## 一、设计原则

1. **三层核算**：调用量台账（免费、即时）→ 积分估算（费率模型）→ 实际扣分对账（余额快照/流水导入）。
2. **先量后价**：费率未知时，先按“调用次数/标的数/字段数/行数”记账，用保守上界做预算闸门；拿到 Key 后再标定真实费率。
3. **不侵入业务**：核算层只放在采集层/独立脚本，不进入 routes/services；不写业务库（只写独立的 `data/tdx_points.db`）。
4. **专用账号/专用 Key**：积分是账号级共享池，若同账号还跑 MCP/词元/Skills，余额差分会混入其他产品消耗，标定会被污染。**标定期必须用只开“数据服务”权限的专用 Key，最好专用账号**。
5. **配置即账单**：费率、预算、口径全部版本化，任何一次核算都能复现。

## 三、台账数据模型（`data/tdx_points.db`，SQLite WAL）

```sql
-- 每一次调用（无论成败）
CREATE TABLE calls (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,                 -- 2026-11-11T09:30:00+08:00
  session_id TEXT,                  -- 标定/试跑批次
  endpoint TEXT NOT NULL,           -- get_market_data / get_zdt_data ...
  params_hash TEXT,                 -- 归一化参数哈希（去重/复现）
  symbols_n INTEGER DEFAULT 1,
  fields_n INTEGER DEFAULT 0,
  period TEXT,
  rows_returned INTEGER DEFAULT 0,
  elapsed_ms INTEGER,
  ok INTEGER NOT NULL,
  error TEXT,
  est_points REAL,                  -- 模型估算
  est_points_high REAL,             -- 保守上界（闸门用）
  rate_version TEXT,
  note TEXT
);

-- 余额快照（手动/网页/流水导入）
CREATE TABLE balance_snapshots (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,
  source TEXT NOT NULL,             -- manual | web_session | flow_csv
  total_points REAL,
  used_points REAL,
  left_points REAL,
  raw_json TEXT
);

-- 流水导入（Key 使用流水）
CREATE TABLE flow_imports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  add_val REAL,
  increment_value REAL,
  remark TEXT,                      -- 签到/用户购买/订阅/系统调整
  update_time TEXT,
  source_file TEXT,
  matched_call_id INTEGER           -- 时间窗匹配到的调用
);

-- 费率模型版本（标定结果）
CREATE TABLE rate_models (
  version TEXT PRIMARY KEY,
  endpoint TEXT,
  mode TEXT,                        -- fixed | per_symbol | per_field | per_row | tiered
  base_points REAL DEFAULT 0,
  per_symbol REAL DEFAULT 0,
  per_field REAL DEFAULT 0,
  per_row REAL DEFAULT 0,
  tiers_json TEXT,
  min_points REAL DEFAULT 0,
  max_points REAL,
  sample_n INTEGER,
  variance_pct REAL,
  calibrated_at TEXT
);

-- 预算
CREATE TABLE budgets (
  month TEXT PRIMARY KEY,           -- 2026-11
  cap_points REAL,
  used_points REAL DEFAULT 0,
  warn_ratio REAL DEFAULT 0.8,
  hard_stop INTEGER DEFAULT 1
);
```

## 四、费率模型与估算公式

### 4.1 支持四种计费形态

| mode | 公式 | 适用 |
|---|---|---|
| fixed | `points = base` | 按次计费 |
| per_symbol | `base + per_symbol × n` | 按股票数 |
| per_field | `base + per_field × fields` | 按字段数 |
| per_row | `base + per_row × rows` | 按返回行数 |
| tiered | `tiers_json` 阶梯 | 批量折扣/分段 |

### 4.2 未标定时的保守估算

```text
est_points      = 1.0 × 调用次数
est_points_high = est_points × 10
```

闸门用 `est_points_high`，避免“以为很便宜、实际很贵”。

### 4.3 标定后的估算

```text
est = max(min_points, base + per_symbol×n + per_field×f + per_row×r)
```

每次调用写 `rate_version`，保证历史可复现。

## 五、标定协议（拿到轻享包后执行）

> 总预算控制在 **2,000–3,000 积分**（轻享包的 4%–6%），每组实验 3 次取中位数。

| # | 实验 | 目的 | 预计消耗 |
|---|---|---|---|
| 1 | 单次 `get_stock_info`（1 只） | 测“按次”底价 | 个位数 |
| 2 | 同一调用重复 10 次 | 验证是否线性按次 | 10× |
| 3 | `get_market_data` 1 / 10 / 100 只 | 测 per_symbol | 百级 |
| 4 | 同一批 1 字段 vs 10 字段 | 测 per_field | 百级 |
| 5 | 1 次 batch vs 100 次单只 | 验证批量折扣 | 百级 |
| 6 | 非法代码/空参数 | 验证失败是否扣分 | 0 或个位数 |
| 7 | 1m vs 1d 周期 | 验证周期系数 | 百级 |
| 8 | `subscribe` 10 只 × 60s | 测订阅按时间/按条 | 百级 |

**每次实验流程**：
1. 读余额快照（手动填 Key 页“账户可用积分”或网页接口）；
2. 执行**单一**调用/单批调用；
3. 等待 `settle_seconds`（先测一次扣分落账延迟，再定 30/60/90s）；
4. 再读余额快照；
5. `actual_delta = left_before − left_after`；
6. 写入 `calls` + `balance_snapshots`，拟合 `rate_models`；
7. 方差 >20% 或 R²<0.8 → 回退到“最大观测值”做保守闸门。

**关键干扰项**：同账号其他产品（MCP/词元/Skills）也在扣分。标定窗口内必须停用其他产品，或用专用账号。

## 六、预算闸门与熔断

```text
调用前：
  est_high = estimate(endpoint, n_symbols, fields, rows) × guard_factor
  if today_used + est_high > daily_cap: 拒绝（BudgetExceeded）
  if month_used + est_high > monthly_cap: 拒绝
调用后：
  calls.est_points / est_points_high 落库
  budgets.used_points += est_points（估算）
对账后：
  budgets.used_points = 实际扣分（以余额/流水为准）
  variance = (actual - est) / actual
```

- `hard_stop=true`：拒绝调用并告警（写日志 + 可选 SocketIO/邮件）。
- 每日 08:00 生成前一日报表；每周一生成周报。
- 预警阈值：日 80%、月 80%、单接口占比 >50%。

## 七、报表（`points_report.py`）

### 7.1 日报字段

| 指标 | 说明 |
|---|---|
| 调用次数 / 成功 / 失败 | 按接口分组 |
| 标的数 / 字段数 / 行数 | 批量效率 |
| 估算积分 / 实际扣分 / 偏差 | 对账核心 |
| 单位成本 | 元/万积分、元/千次调用 |
| Top 5 消耗接口 | 优化重点 |
| 月末预测 | 按当前日均线性外推 |
| 未匹配流水 | 可能来自其他 Key/产品，需排查 |

### 7.2 决策门（试水期结束）

| 全市场日终成本（估算） | 结论 |
|---|---|
| ≤500 积分/日（≈¥0.75/日） | 可作为主源候选，进入等价性验收 |
| 500–2,000 积分/日 | 仅批量接口 + 缺口补采，先小规模试跑 |
| >2,000 积分/日（≈¥3/日） | 不作为全市场主源；只用于涨停/两融/ETF 等缺口 |
| >5,000 积分/日 | 放弃，继续用 Tushare + AKShare |

> 5 万积分若按 2,000/日，仅够 25 个交易日；因此“日成本”必须在试水期第一周就测出来。

## 八、Phase 0 / 1 / 2 落地顺序

### Phase 0（现在，不需 Key，1–2 天）

- `tdx_points.yaml` + `points_ledger.py` + `tdx_metered_client.py`（dry-run 模式，只记账不真调）。
- `points_report.py` 生成空报表模板。
- 用假调用回放 1,000 条，验证：台账写入、预算闸门、报表口径、SQLite WAL 并发。
- **不改业务代码、不写业务库**。

### Phase 1（开通轻享包后，1 天）

- 安装 `tdxaidata` 到独立 venv（不改项目主依赖）。
- 执行 §五 标定协议，填 `rate_models`。
- 用 1–2 个真实接口做 100 次试跑，核对“估算 vs 实际”偏差 <15%。
- 设 `monthly_cap=20000`、`daily_cap=1500`。

### Phase 2（试跑 3–5 个交易日）

- 只跑“缺口补采”场景（涨停明细/两融/ETF/北向），不全市场铺开。
- 每日对账 + 周报；确认单位成本与稳定性。
- 通过决策门后再评估是否扩大。

## 九、必须提前知道的坑

1. **扣分可能延迟**：余额不是实时刷新；先测落账延迟，再定 `settle_seconds`。
2. **共享池污染**：同账号跑 MCP/词元会让余额差分包住其他消耗；标定必须专用 Key/账号。
3. **费率可能按“接口+参数”分档**：不要假设全局 1 分/次；用实验矩阵而非单点外推。
4. **失败扣分口径不明**：MCP 明确“失败不扣”，数据服务未说明；必须用实验 6 验证。
5. **批量接口可能有单次上限**：配置 `max_symbols_per_call`，避免一次传全市场被拒绝或按超限计费。
6. **合规**：协议禁止“批量抓取”；台账同时可作为“正常调用量”的证据，但采购前仍须书面确认全市场日终用法。
7. **Key/Token 安全**：配置文件不落 Key；`store_raw_params=false`；日志脱敏。

## 十、轻享包 5 万积分的建议分配

| 用途 | 积分 | 说明 |
|---|---:|---|
| 标定实验 | 2,000–3,000 | 8 组实验 × 3 次 |
| 首月缺口补采试跑 | 15,000–20,000 | 只跑涨停/两融/ETF/北向 |
| 安全余量 | ≥25,000 | 防费率高于预期/重跑 |
| 日预算 | 1,500 | 月 20,000 上限 |

> 若标定发现“全市场日终 >2,000 分/日”，立即停在上表“缺口补采”范围，不扩大。
