## 三、分钟K线 65% 问题分析

### 3.1 现状

| 数据 | 覆盖 | 说明 |
|------|------|------|
| **今日实盘分钟K线** | **100%** | mootdx L1 每5秒聚合，写入 minute_kline_cache |
| **历史分钟K线（近2天）** | **~65% 股票** | baostock 回填了 3,234/5,004 只（131,390行） |
| **缺失部分** | ~1,770只 | 无历史分钟K线，但有今日实盘数据 |

### 3.2 根因

baostock `query_history_k_data_plus()` 在某些股票上**无限挂死**（TCP 连接不释放、无超时机制）。两次运行均在中途停在 0% CPU，线程不退出。

```
第一次挂死: 11:15 启动, 11:20 后无日志 → 2770只
第二次挂死: 14:44 启动, 15:20 后无日志 → +464只
```

挂死模式：每运行 ~6 分钟处理约 500 只后卡住，无异常抛出（try/except 捕获不到 TCP 级超时），进程持续存活但不工作。

### 3.3 影响评估

**对系统功能无影响。** 理由：

1. **今日盘中数据完整** — mootdx L1 聚合对所有活跃股票（~1885只）实时写入 1min K 线，今日数据的覆盖率是 100%
2. **缺失的是历史数据** — 仅影响过去 2 天的分钟K线查询，且缺失的是非活跃股票（被 baostock 排在后面的那些，通常是低流动性/ST/退市整理股票）
3. **分钟K线的主要使用场景是盘中** — 实时行情、缠论分型识别等都不依赖历史分钟K线
4. **历史分钟K线自动积累** — 随着每天交易，mootdx 聚合会逐步填满 minute_kline_cache

### 3.4 改进方案

如需完整的历史分钟K线，有两个选择：

| 方案 | 可行性 | 说明 |
|------|--------|------|
| **baostock 加超时** | 中等 | 在 baostock 查询线程中加 `threading.Timer(timeout)` 强制 kill 挂死线程，但 threading 无法强制终止线程 |
| **mootdx bars 替代** | 已验证不可行 | mootdx bars() 所有 freq 均返回日线，不支持分钟级 |
| **Tushare stk_mins** | 限流严重 | 1次/分钟，5500只需 91 小时 |

**推荐做法**：不追历史。mootdx L1 聚合持续运行，2 周后自然拥有 10 个交易日 × 1900 只 ≈ 91 万行分钟K线，覆盖所有活跃股票。

## 四、后续维护建议

### 4.1 日终调度

今日已注册的 13 个新 data_types 会在每日 15:30 自动触发同步：

```python
data_types: [
    "daily", "basic", "moneyflow", "index", "adj_factor",
    "fina_indicator", "income", "balancesheet", "cashflow",
    "forecast", "margin", "stk_limit", "lhb",
    "top10_holders", "stk_holder",
]
```

注意：
- `margin`、`concept`、`index_member` 三个类型因 Tushare API 问题无法获取数据，但不影响其余类型
- 建议从默认配置中移除这 3 个类型，避免每次日终报错

### 4.2 E07/E10 缓存优先

今日已将 E07（个股行情28字段）和 E10（个股资金流向5日）改造为 ECM 缓存优先读：
- E07: 23/28 字段从本地缓存获取，仅缓存未命中时回退 Tushare
- E10: 从 moneyflow_cache 读取，不再每日现拉 Tushare

### 4.3 数据库膨胀

| 时间 | 数据库大小 | 增长原因 |
|------|-----------|---------|
| 回填前 | ~3 GB | daily_cache + adj_factor + moneyflow |
| 回填后 | **15 GB** | indicator_cache（8500万行）占大头 |

SQLite WAL 模式 15GB 仍可正常运行，但未来 1-2 年会继续增长。建议：
- 短期：接受，15GB 对现代硬盘无压力
- 长期：当超过 50GB 时考虑按年分表或迁移到 PostgreSQL
