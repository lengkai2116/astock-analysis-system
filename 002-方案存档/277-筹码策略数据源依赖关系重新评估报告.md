> 基于全局数据体系（251号方案）的 5 层流水线架构和 19 张活跃数据表的实际状态，

## 一、评估方法

### 1.1 数据源就绪度分级

| 等级 | 定义 | 判断标准 |
|------|------|---------|
| ✅ **已就绪** | 数据已采集、有足够行数、可通过 DataManager 直接访问 | 查 251 号方案 → ECM 表清单确认表存在 + 行数 > 0 |
| ⚠️ **有条件就绪** | 数据存在但需额外处理（聚合/计算/跨字段推导） | 数据存在，但所需字段不完全匹配 |
| ❌ **未就绪** | 该数据源无采集管道或管道不可用 | 251 号方案未列入、或空表、或已知故障 |

### 1.2 全局数据体系五层架构视角

```
采集层 (mootdx TCP / Tushare Pro / AKShare)
  → 存储层 (ECM SQLite WAL / InMemoryStateStore)
    → 计算层 (chip_strategy / ChipDistributionService)
      → 调用层 (signal_computation_service)
        → 使用层 (前端 / API)
```

每层只与相邻层通信。筹码策略位于**计算层**，通过 DataManager 读取存储层数据，不直接触碰采集层。

**原 276 号提升方向：** "机构席位 vs 营业部席位的买卖方向 + 金额对比"

**全局数据体系实际情况：**

| 潜在数据源 | 可用性 | 说明 |
|-----------|:------:|------|
| `lhb_cache`（Tushare `top_list`） | ❌ 无席位字段 | 只有 `name`(股票名)、`buy_amount`、`sell_amount`，无席位名称 |
| `as_lhb_detail`（AKShare `stock_lhb_detail_em`） | ❌ 无席位字段 | 同样只有聚合的买入额/卖出额，无席位明细 |

| AKShare 席位级 API | ❌ 未调研 | 如 `stock_lhb_jgmm_tj_em`（机构买卖统计）或 `stock_lhb_hyyyb_em`（营业部统计）需验证 |

**根本原因：** 当前系统采集的龙虎榜数据（包括 Tushare 和 AKShare 两条管道）均为**个股级聚合数据**（按股票汇总的买入额/卖出额），不含席位维度。知识库定义的"真机构 vs 假机构"席位名称判别法需要**交易席位级数据**（每笔交易的买卖方席位名称、金额）。

| 评估维度 | 结论 | 依据 |
|---------|:----:|------|
| 数据就绪度 | ❌ 未就绪 | 系统中无任何表存储席位级数据 |
| 采集管道 | ❌ 不存在 | 需新增 AKShare `stock_lhb_jgmm_tj_em` 或 Tushare `lhb_detail` 采集 |
| 接入成本 | 🔴 中 | 新增采集管道 + 新表定义 + cache 读写方法 |
| 全局影响 | 🟡 低 | 独立表，不影响现有逻辑 |

**重新评估结果：** ❌ 该依赖**不成立**——需要新增数据源（席位级 LHB 数据），非现有管道的扩展。建议在采集管道就绪后重新评估。

### 3.5 P2-1：筹码集中度因子

**原 276 号方案定义：** "大股东持仓比例变化率 = 过去 N 日的持仓比例变化"

**实际数据源状态：**

| 可用数据表 | 数据结构 | 是否可用于因子计算 |
|-----------|---------|:----------------:|
| `stk_holder_cache`（96k行） | `ts_code`, `end_date`, `holder_number`（股东户数） | ⚠️ **有条件**：只有股东户数（`holder_number`），无持仓比例 |
| `top10_holders_cache`（1.28M行） | `ts_code`, `end_date`, `holder_name`, `hold_amount`（持股数量） | ⚠️ **有条件**：有每个股东的具体持股量，但缺少总股本信息 |
| `daily_basic_cache`（681k行） | 含 `total_mv`（总市值） | ✅ 可推算总股数 |
| `daily_cache` | OHLCV + `amount` / `vol` | ⚠️ 可通过收盘价+总市值推算总股本 |

**精确计算路径**（需要 2 张表联合）：
```
top10_holders_cache.hold_amount  /  (daily_basic_cache.total_mv / daily_cache.close)
= 前十大股东合计持仓比例 → 计算 N 期变化率
```

| 评估维度 | 结论 | 依据 |
|---------|:----:|------|
| 数据就绪度 | ⚠️ 有条件就绪 | 需 `top10_holders` + `daily_basic` + `daily` 三表联合计算，非直接字段 |
| 字段匹配度 | ⚠️ 间接 | 无现成"持仓比例变化率"字段，需多表计算 |
| 采集可靠性 | ✅ `top10_holders` 1.28M 行 | 季度更新，历史数据充足 |
| 实施后精度 | 🟡 中等 | 股东户数变化（`holder_number`）只能反映"集中/分散"的大趋势，个股精确比例需 top10_holders |

**原 276 号方案判断修正：**

| 原判断 | 当前评估 | 修正理由 |
|--------|---------|---------|
| "stk_holder需确认" | ✅ 已确认有 96k 行 | `stk_holder_cache` 可用 |
| "stk_holder未用于变化率计算" | ⚠️ 部分正确 | `holder_number` 可计算变化率，但只能作为**代理指标**（proxy），非精确的持仓比例 |
| 未提及 `top10_holders_cache` | ⚠️ 应使用此表 | `top10_holders_cache` 有 1.28M 行，包含每个股东的持股量，更接近因子定义 |

**重新评估结果：** ⚠️ 有条件就绪。变更计算策略即可实现：使用 `stk_holder_cache.holder_number` 计算 **股东户数变化率**（更易实现，数据稳定），或使用 `top10_holders_cache` 联合 `daily_basic_cache` 计算 **持仓比例变化率**（更精确但需多表联查）。**无需新增数据源。**

## 六、结论

### 6.1 已纠正的依赖误解

| 原误解 | 实际情况 | 影响 |
|--------|---------|------|
| "stk_holder需确认" | ✅ 已有 96k 行数据，可用于股东户数变化率 | 非阻塞，已澄清 |
| "lhb 数据可支持席位识别" | ❌ `lhb_cache` 只有股票级聚合，无席位字段 | 需要新数据源，非现有管道扩展 |
| "margin_cache 有空表风险" | ✅ 194k 行，历史 D1 修复后持续同步 | 已稳定，修复过 |

### 6.2 真正需要新增数据源的事项

仅有 **1 项**：

> **席位级龙虎榜数据（lhb_detail）**：用于假机构识别的"机构专用 vs 营业部"席位名称判别。
> 建议考察 AKShare `stock_lhb_jgmm_tj_em`（机构买卖统计）作为最低成本方案。

### 6.3 无需新增数据源、但需计算逻辑增强的事项

> **筹码集中度因子（P2-1）**：使用 `stk_holder_cache.holder_number` 计算股东户数变化率，或联合 `top10_holders_cache` + `daily_basic_cache` 计算持仓比例变化率。数据已有，只需计算逻辑。

### 6.4 全局视角的评估修正

276 号方案最大的评估偏差在于将**假机构席位识别**归类为"数据已就绪"的改进项，而全局数据体系审计揭示：席位级 LHB 数据根本不在当前的 19 张活跃表中，这是一个需要从采集层开始的新建管道，与 `lhb_cache` 的现有采集无关。
