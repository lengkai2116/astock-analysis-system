# 334 — L1 维度判定细则与信号注册表

> **分档定位**：332 号总纲（现状判定引擎统一方案 v3.0）的**分档二**，聚焦总纲 §5.2（L1 维度判定层）的落地细则。332 号管"流水线架构与统一口径"，本方案管"L1 怎么判、输出什么形态、信号怎么注册与验证、阈值怎么管理与校准"。
>
> **讨论背景（08-15，沟通纪要 001-003）**：组2 讨论确认三点范式——①**维度数量不纠结**（9/10/20 维都行），判定层是内部实现细节，用户关心的是"把现状讲清楚、用右侧信号识别机会"；②**判定层与输出层分离**：机会弹窗=亮灯简述版，个股策略分析=七维现状描述详述版（体检报告式），两者读同一判定源、只允许展示粒度差异；③**信号注册表一步到位**（方案 2），阈值管理提前考虑独立运行需求（yaml 配置化 + 历史数据回算验证）。
>
> 本方案仅存档细则，不修改任何代码。

## 一、范式：判定层与输出层分离（用户 08-15 确认）

```
L1 判定层（内部）——维度数量不纠结（9/10/20 均可），
  目标唯一：每个维度产出「状态 + 证据 + 一句话结论 + 大白话 + 红绿灯」
        ↓
L3 输出层（两种形态，同一判定源，不允许口径分裂）
  ├─ 机会弹窗（简述版）：亮灯组合 —— 维度红绿灯 + 综合状态条 + 建议卡，一眼扫完
  └─ 个股策略分析（详述版）：七维现状描述模板 ——
     每个维度「✅ 一句话结论 + 数字证据 + 大白话」，围绕信号做体检报告
```

**核心目标**（用户原话直白化）：把股票的现状讲清楚，从右侧信号帮助用户识别机会；输出遵循"只描述不预测"——用距离/百分比/天数/盈亏比等**几何化指标**让用户自行衡量风险收益（知识库《现状描述型输出》《七维现状描述模板》）。

## 二、L1 维度池与输出协议

### 2.1 维度池（判定层内部，数量不纠结）

| # | 维度 | 判定实现 | 输入（现有标签/数据） | 状态值域 |
|:-:|---|---|---|---|
| 1 | 估值 | 标签原料 | 估值组 17（valuation_level/composite_rating/pe_pb_ps 分位/fcf_yield） | 低估🟢/合理🟡/高估🔴 |
| 2 | 结构 | **P2 缠论引擎** | 缠论结构组 10（state_label/buy_sell_point/zhongshu_strength/multi_level）+ 原始 K 线补深度 | 上升🟢/盘整🟡/下降🔴 |
| 2b | **量价**（08-15 修订补入） | **P2 量价引擎** | P2 量价信号 trend.direction（回退 volume_price_fit 标签）——**332 §5.2 修订③"量价→量价维"在本表 v1.0 遗漏，全面核查后补入**（同时是七维模板"量价健康度"段数据源） | 健康🟢/中性🟡/背离🔴 |
| 3 | 位置 | 标签原料 | price_position/chip_position/support_resistance/near_levels_filtered | 站上防守位🟢/中位🟡/跌破🔴 |
| 4 | 筹码资金 | **P2 筹码引擎** | 筹码深度组 17 + 阶段主力组 8 + 资金风险组 2（消费标签不重算） | 流入🟢/中性🟡/流出🔴 |
| 5 | 情绪 | **P2 BOCIASI 引擎** | 情绪板块组 5（sentiment_phase/sector_heat/upward_driver）+ 指数补深度 | 复苏🟢/正常🟡/退潮·高潮🔴 |
| 6 | 财务 | 标签原料 | fina_health/roce_pass/roe/revenue_growth（物理在估值组，归属财务维） | 健康🟢/关注🟡/风险🔴 |
| 7 | 事件 | 标签原料 | 事件组 5（catalyst_event/catalyst_impact/event_composite_score） | 正向🟢/中性🟡/负面🔴 |
| 8 | 时间 | 标签原料 + **信号生命周期** | time_rhythm + active_signal（date/price）+ 当前价 | 初期🟢/中期🟡/已延伸🔴 |
| 9 | 风险 | 标签原料 + **PIERS 聚合** | risk_level/volatility_level + 财务风险 + 事件负面 | 低🟢/中🟡/高🔴 |
| 10 | 因子（校验维） | **P2 因子引擎** | 因子信号 + factor_cache 截面 | 看多🟢/中性🟡/看空🔴（辅助灯） |

> **说明**：维度数量不构成用户可见口径；因子作为校验维参与 L2 共识计票（与 322 五维口径一致，603897 五维共识 67% 含 factor），展示时标注"辅助"。筹码资金维合并知识库"筹码分布+资金博弈"两维（系统标签交织在阶段主力组），判定时拆"筹码结构+资金动向"两个子项合并为一个维度状态。

### 2.2 每维输出协议（判定素材，弹窗/个股页共用）

每个维度产出结构化素材，供输出层两种形态取用：

```json
{
  "dim": "结构",
  "state": "上升",                    // 维度状态（值域见 2.1）
  "light": "green",                   // 红绿灯 green/yellow/red
  "evidence": ["state_label=上升", "buy_sell_point=第三类买点(一类前)"],  // 命中的标签/引擎证据
  "conclusion": "上升趋势，日线级别出现第三类买点（一类前）",  // 一句话结论（个股页展示）
  "plain": "趋势向上，刚出现买点信号，离成本区不远",            // 大白话（个股页展示）
  "confidence": 0.85                  // 置信度（引擎置信度或标签 confidence）
}
```

## 五、信号注册表（方案 2 一步到位，用户 08-15 确认）

### 5.1 注册表定义（每类信号注册 5 项）

```
signal_type  信号类型枚举
触发条件    引用现有标签/引擎输出的规则（全部系统已具备）
验证条件    突破后 N 日收盘站稳/不破（用 daily_cache 后续 K 线判定，杜绝人工目测）
生命周期    初期/中期/已延伸 的距离+天数阈值（每类可不同）
介入贵贱    由生命周期阶段派生的一句话提示
```

### 5.2 初始注册 5 类信号（用户确认：5 类先够用，龙虎榜标记待扩展）

| signal_type | 触发条件（现有数据） | 验证条件（建议初值） | 生命周期阈值（初始值，待校准） |
|---|---|---|---|
| `chan_third_buy` 缠论三买 | buy_sell_point=third_buy / active_signal | 信号后 3 日收盘不破信号价 | dist≤+5%→初期；+5~12%→中期；>+12%→已延伸（天数 3/10 兜底） |
| `volume_breakout` 放量突破 | pattern_signal=突破 + vol_ratio≥1.5 + 突破前高 | 3 日收盘站稳突破位 | 同上 |
| `ma_bullish` 均线多头 | ma_alignment=多头 + trend_alignment=up_aligned | 5 日维持多头排列 | 同上 |
| `platform_breakout` 平台突破 | 中枢内横盘（time_rhythm）后向上突破 zs_high | 3 日收盘站稳中枢上沿 | 同上 |
| `pattern_up` 量价强势形态 | pattern_signal 预涨型 + volume_price_fit≠diverging | 3 日不破形态起点 | 同上 |

> **龙虎榜标记**（`lhb`/龙虎榜战法类信号）列入**待扩展**清单（用户确认），后续在注册表追加。
> **信号注册表为个股页七维模板第①维"信号确认状态"的数据基础**（知识库《信号注册表》《信号生命周期》要求）。

### 5.3 信号生命周期算法（时间维 + 七维模板①共用）

```
输入：active_signal = {type, date, price}（缠论结构组已有）+ 当前交易日 + 当前价
计算：days_since = 当前日期 − 信号日期（交易日）
      dist_pct   = (现价 − 信号价) / 信号价 × 100
阶段映射（距离优先、天数兜底）：
  初期   ：dist_pct ≤ +5%   或 days_since ≤ 3    → 🟢 刚脱离成本区
  中期   ：+5% < dist_pct ≤ +12% 或 days_since 4-10 → 🟡
  已延伸 ：dist_pct > +12%  或 days_since > 10   → 🔴 追高风险大
```

> **阈值性质**：+5%/+12%/3 天/10 天为**初始值**（取自知识库示例 +4% 初期/+18% 已延伸的取整），**未经全市场分布验证**，是"先跑起来"的初值；**正式定标交由第六章阈值管理机制的校准脚本**（离线重放 + 在线积累双轨）。active_signal 过时判定沿用现有规则（>3 月且价偏 >20% 判 historical），生命周期只在有效信号上计算。

## 六、阈值管理机制（面向独立运行，用户 08-15 确认：yaml 配置化、版本化可回滚）

### 6.1 历史数据回算验证可行性评估（实测核查结论：可行，双轨）

| 数据资产 | 实测现状 | 用途 |
|---|---|---|
| `signal_records`（app.db，330 改进2 验证环） | **1081 条**，2026-07-09~08-13；含 return_t5/10/20、hit_target/stop、is_win_5d/10d/20d、max_drawdown_t20 | **在线积累（主）**：随运行自然积累"信号→结果"样本，持续校准阈值 |
| `strategy_signal_detail`（stock_cache） | **13 个交易日**历史（20260722~0813，日均 ~5557 只 = 7.2 万条） | 信号历史可回溯 |
| `daily_cache` | **634 万行**，2021-07 至今（5 年） | **离线重放（补）**：重放信号判定 → 统计 dist_pct/days_since 收益分布，一次性定标初始阈值（样本量万级） |
| `factor_cache` | 113499 行 | 因子判定输入 |
| `opportunity_status_history/advice_history/library` | 表已建、0 行 | 332 号 5.6 成品仓落库载体候选（组4 讨论） |

**局限（直白）**：signal_records 当前记的是"策略方向"（缠论 watch/bearish 等），**尚未挂接右侧信号类型**——实施时需为 signal_records 增加右侧信号类型字段（signal_type 细分），验证环接上信号注册表（§5.2 的 5 类）。

### 6.2 阈值管理架构

```
config/signal_registry.yaml        ← 每类信号的触发/验证/生命周期阈值（带版本号）
        ↓ 写入
signal_records（在线积累样本）      ← 每类信号一条记录 + T+5/10/20 结果
        ↓ 校准脚本（scripts/calibrate_signal_thresholds.py）
输出建议阈值：按样本分布分位点（如 dist_pct 的 P50/P80 → 中期/已延伸边界）
        ↓ 人工确认 → 更新 yaml（版本+1，可回滚）
```

- **阈值全部配置化**：不硬编码、不手工拍脑袋；yaml 文件带版本号（version 字段），更新可回滚
- **校准触发条件**：该类信号样本量 ≥ 100 条时脚本给出校准建议（防小样本抖动）
- **初始定标**：上线时用离线重放（daily_cache 5 年）一次性算好初始阈值；之后由在线样本（signal_records）持续校准
- **独立运行安全网**：阈值缺失/异常时回退默认档，不阻塞系统
