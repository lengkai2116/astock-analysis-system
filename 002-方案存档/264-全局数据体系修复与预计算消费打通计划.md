## 二、架构红线

### 2.1 全局数据架构要求（AGENTS.md §三）

```
数据采集层（data_daemon + collectors）
    ↓ ECM 缓存写入
存储层（SQLite WAL: stock_cache.db）
    ↓ ECM 缓存查询
服务层（DataManager / SignalComputationService）
    ↓
路由层（Flask REST API）
```

**红线规则：**
- Route/Service 层只读 ECM 缓存，**不许直接调外部 API**
- DataManager 是所有数据访问的统一入口
- 数据采集走 `data_daemon` + `mootdx_collector`，不许在路由层初始化

### 2.2 CQRS 约束

| 操作 | 进程 | 写入方式 |
|:-----|:-----|:---------|
| 实时写入 | mootdx TCP 采集线程 | 直接 ECM `_insert_from_df()` |
| 日终批量写入 | data_daemon | `_batch_*` 函数 → ECM 缓存方法 |
| 只读查询 | Flask API 进程 | ECM `get_cached_*()` + DataManager |

## 三、修复计划

### 3.1 D1：修复 margin_detail API（🔴 P0，0.5天）

**问题分析：**
- `_batch_margin()` 调用 `pro.margin(trade_date=trade_date)` — 返回3行（SSE/SZSE/BSE交易所汇总）
- `margin_cache` 表schema按个股设计（PRIMARY KEY ts_code, trade_date），API与表结构不匹配
- 正确API：`pro.margin_detail(trade_date=trade_date)` — 返回所有沪深个股融资融券明细

**Tushare margin_detail 返回字段：**
| 字段 | 含义 | margin_cache 列 |
|:-----|:-----|:----------------|
| trade_date | 交易日期 | trade_date ✅ |
| ts_code | 股票代码 | ts_code ✅ |
| rzye | 融资余额 | rzye ✅ |
| rzmje | 融资买入额 | rzmje ✅ |
| rqyl | 融券余量 | rqyl ✅ |
| rqchl | 融券偿还量 | rqchl ✅ |
| rqmcl | 融券卖出量 | rqmcl ✅ |
| rzrqye | 融资融券余额 | rzrqye ✅ |

**实施步骤：**

**Step 1 — `data_daemon.py` 修复 `_batch_margin()`：**
```python
def _batch_margin(trade_date: str) -> int:
    """全市场融资融券个股明细 — 1 次 API 调用"""
    _ensure_pd()
    import tushare as ts
    pro = ts.pro_api()
    raw = pro.margin_detail(trade_date=trade_date)  # ← 改这里
    if raw is None or raw.empty:
        return 0
    df = raw.copy()
    if 'trade_date' in df.columns:
        df['trade_date'] = pd.to_datetime(df['trade_date']).dt.date
    _ecm.cache_margin_data(df)
    return len(df)
```

**Step 2 — `__init__.py` 修复 `sync_margin_data()`（API进程备用路径）：**
- 同上，`pro.margin(` → `pro.margin_detail(`
- 删除行801-804的 `get_margin('000001.SZ')` 死代码

**Step 3 — 历史数据回填（一次性）：**
- 手动补采最近120个交易日的 margin_detail 数据
- 脚本：逐日调用 `pro.margin_detail()` → `cache_margin_data()`
- 预计单日数据~5000行，120天约60万行，耗时约2分钟

**验证标准：** `margin_cache` 行数 > 0，且 `SELECT COUNT(DISTINCT ts_code) FROM margin_cache` > 3000

def _batch_balancesheet(trade_date: str = None) -> int:
    """全市场资产负债表（最近一期）"""
    _ensure_pd()
    import tushare as ts
    pro = ts.pro_api()
    total = 0
    codes = _ecm.conn.execute("SELECT DISTINCT ts_code FROM daily_cache").fetchall()
    codes = [r[0] for r in codes[:500]]
    for code in codes:
        try:
            raw = pro.balancesheet(ts_code=code, start_date=None, end_date=None)
            if raw is not None and not raw.empty:
                if 'end_date' in raw.columns:
                    raw['end_date'] = pd.to_datetime(raw['end_date']).dt.date
                if 'ann_date' in raw.columns:
                    raw['ann_date'] = pd.to_datetime(raw['ann_date']).dt.date
                _ecm.cache_balancesheet_data(raw)
                total += len(raw)
        except Exception:
            continue
    logger.info(f"  [资产负债表] 同步 {total} 条")
    return total

# 同理 _batch_cashflow、_batch_forecast

### 3.3 D3：分钟K线周末全量补齐 — 基于 Tushare 5000 积分（🟡 P1，单次周末任务 + 持续增量）

#### 现状与问题

- `minute_kline_cache` 现有 1,571,194 行，覆盖 ~1885 只热门股
- 剩余 ~3100 只股票分钟数据**完全缺失**或严重不全
- 现有 `_batch_backfill_minute_kline()` 在 data_daemon 日终回填，限 500 只/天，速度不足以补齐全部
- 现有代码存在 **bug**：`pro_bar` 返回字段为 `trade_time`（如 `2026-07-10 14:59`），但回填代码错误地引用 `raw['trade_date']`（第610行），导致该函数从未正确执行过分钟数据回填

#### Tushare pro_bar 分钟数据能力实测

| 指标 | 值 |
|:-----|:----|
| 接口 | `ts.pro_bar(ts_code=X, freq='1min', adj='qfq')`（底层调用 `stk_mins`） |
| 返回字段 | `ts_code, trade_time, close, open, high, low, vol, amount` |
| 单次调用行数 | ~210行/交易日，30天 ≈ 6300行/次 |
| 单次调用耗时 | **~233ms**（实测） |
| 限流 | 500 次/分钟（5000积分级别） |
| 单只股票需调用次数 | 1-4次（取决于需要回填的天数，每次最多30天） |

#### 全量补齐方案

**采用独立脚本 `scripts/backfill_minute_kline.py`，周末运行：**

```
Step 1: 查询 daily_cache 获取全部股票列表 (~5000只)
Step 2: 查询 minute_kline_cache 获取已有数据股票列表
Step 3: 计算缺失集合，按"从未同步"和"部分同步"分组
Step 4: 逐只调用 pro_bar(freq='1min')，带 120ms 间隔限流
Step 5: 数据转换并写入 ECM
```

**耗时估算：**

| 项目 | 计算 | 耗时 |
|:-----|:-----|:----:|
| 全市场股票数 | — | ~5000只 |
| 已有数据股票 | minute_kline_cache 已有 | ~1885只 |
| 完全缺失需首发 | 3100只 × 1次调用 | 3100次 |
| 部分缺失需增量 | 1885只 × 1次调用（最近30天） | 1885次 |
| API 总调用量 | 3100 + 1885 ≈ **5000次** | — |
| 网络传输时间 | 5000 × 0.233s | **~19分钟** |
| 限流等待（500次/分） | 5000次 × 0.12s 间隔 | +10分钟 |
| 数据写入ECM | 5000 × 6300行 ≈ 31.5M行 × ~2μs/行 | +1分钟 |
| **总计** | — | **~30分钟** |

**数据量影响：** 新增 ~31.5M 行，ECM 增长约 8-10%（当前16GB → ~17.5GB），可接受。

#### ECM 分钟K线表结构与 pro_bar 列映射

| minute_kline_cache 列 | pro_bar 返回列 | 转换方式 |
|:----------------------|:---------------|:---------|
| ts_code | ts_code | 直接映射 |
| trade_date | trade_time | `pd.to_datetime(raw['trade_time']).dt.date` 提取日期 |
| trade_time | trade_time | 保留原值（如 `2026-07-10 14:59`） |
| freq | — | 固定设为 `'1min'` |
| open | open | 直接映射 |
| high | high | 直接映射 |
| low | low | 直接映射 |
| close | close | 直接映射 |
| volume | vol | `vol` → `volume` 列重命名 |
| amount | amount | 直接映射 |

> ⚠️ **现有代码 Bug 修复：** `_batch_backfill_minute_kline()` 第610行 `raw['trade_date'] = pd.to_datetime(raw['trade_date']).dt.date` 中 `trade_date` 应为 `trade_time`。第612-613行 `volume`→`vol` 判断逻辑相反（pro_bar 返回 `vol` 而非 `volume`）。这两个 bug 需要同步修复。

#### 增量维护

周末全量补齐后，工作日由 data_daemon 的 `_batch_backfill_minute_kline()` 做增量回填（仅补齐当日缺失的股票）：

| 时段 | 覆盖方式 | 覆盖量 |
|:-----|:---------|:------:|
| 周末 | 独立脚本全量补齐 | ~5000只 × 30天 |
| 每日盘中 | mootdx `minutes()` + 聚合 | ~1885只热门股持续更新 |
| 每日日终 | data_daemon `_batch_backfill_minute_kline()` | 当日新增的 500-1000只 |

**验证标准：** 周末补齐后 `minute_kline_cache` 行数增加 ~31.5M 行，覆盖股票数从 ~1885 提升到 ~5000 只。后续每个交易日增量更新。

### 3.4 D4：预计算数据消费打通（🟡 P1，2天）

**问题分析（260号方案审计确认）：**
- `indicator_cache`（85M行）和 `factor_cache`（37M行）已在日终预计算完成，但路由/服务层仍实时计算
- `strategy_signals` 表已建但0行——预计算任务在 `_run_precompute()` 中写入但代码异常

**实施步骤：**

**Step 1 — 修复 `_run_precompute()` 的策略信号预计算写入：**
- 当前 `_run_precompute()` 末尾对5000+只股票逐一调用 `scs.compute_for_stock()` → 耗时过长（单只~75ms×5000≈6分钟）
- 改为仅对当日有日线数据的股票（约500-1000只）执行

**Step 2 — `indicator-ide.html` 引入 indicator_cache 读取：**
- `chart.py` 的K线API路由：先查 `indicator_cache`，有缓存则直接返回，无则实时计算
- 缓存键：`ts_code + period + indicator_name`

**Step 3 — SignalComputationService 引入 factor_cache：**
- 在 `_compute_factor_score()` 中：先查 `factor_cache`，有则使用预计算值
- 大幅减少因子计算耗时（预计算值 vs 实时计算 ~1ms vs ~15ms/因子）

**验证标准：** K线页面加载指标渲染从实时计算切换到缓存读取，耗时降低50%以上

## 六、与263号方案中P0/P1改进的依赖关系

| 改进项 | 策略 | 依赖的数据修复 | 说明 |
|:-------|:-----|:--------------|:-----|
| P0-①级别递归 | 缠论 | D3（分钟补齐） | 30min/60min级别需要分钟K线覆盖 |
| P0-②BOCIASI四象限 | 因子组合 | **D1（margin）** + D2（财务） | 慢线需要融资余额+ERP |
| P1-①因子覆盖率 | 因子组合 | **D2（财务同步）** | 质量/估值因子需要财务数据 |
| P1-②融资融券反向信号 | L2主力筹码 | **D1（margin）** | 直接依赖margin_detail个股数据 |
| P1-③情绪→权重映射 | 框架协同 | D1 + D2（同BOCIASI） | 四象限前置依赖 |
| P2-①背驰→买卖点联动 | 缠论 | 无新增依赖 | 纯算法变更 |
| P3-①ROCE硬性门槛 | L1风控 | **D2（财务同步）** | 需利润表+资产负债表 |

> **结论：D1（margin_detail）和 D2（财务同步）是两个"闸门式"修复，它们解锁了P0-②和P1-①两个高优先级策略改进的数据支撑。建议在推进任何P0/P1策略改进之前，先完成I1的数据修复。**
