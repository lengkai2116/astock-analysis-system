# 328 — 非24h开机场景下数据体系架构评估与整改方案

> **背景**：2026-08-12 用户提出生产场景关键约束——**未来部署电脑非24h开机、使用时间无法强制**（不能要求"15:30前不关机""交易日9点前开机"）。因此必然出现：**前一日未开机日终数据未到位，当日交易时段（如10:00）开机后需使用系统**——交易时段不可避免需同时进行采集与预计算。要求全面核查数据体系各环节（采集/存储/预计算/调用/快照）合理性、排查隐性链接问题。
>
> **关联**：292（全局数据体系权威架构）、327（预计算自愈，已实施）、305（管道驱动）、方案B（写入者唯一化，已实施）、226（Windows迁移）

## 一、架构合理性核查结论（逐环节）

### 1.1 现有架构（292号设计）与实际

```
data_daemon（单进程）：
  采集线程（mootdx 5s快照/300s分钟线 + AKShare 30min低频）   → InMemoryStateStore（盘中实时）+ ECM
  管道驱动（C1~C6采集 → P1~P4预计算 → S1快照）               → ECM SQLite WAL
  sync_requests 消费（30s轮询）
API 进程（run.py）：DataManager 只读 + 盘中推送
```

**结论：单进程承载采集+预计算是 292 既定设计，架构模式本身合理**——但本次核查发现若干**隐性链接问题**（详见 §二）。

### 1.2 进程内并发写安全性（决定性验证）

**实测**：进程内 `_write_lock` + 单连接多线程写 = **160 成功 0 冲突**（0.5s）

→ **daemon 进程内，采集线程与预计算线程共享 `_write_lock`，天然串行化，无锁冲突**

### 1.3 写入量对比（冲突面量化）

| 写入源 | 日写入量 | 场景 |
|--------|---------|------|
| 分钟线（mootdx 盘中 + 回填）| **75-92 万行/日**（08-12: 92.4万）| 开机日 |
| 预计算 strategy_signal_detail | 6.6 万 | 日终 |
| 预计算 indicator 宽表 | 633 万（全量重建）| 日终 |
| 预计算 tags | 45 万 | 日终 |

**结论**：分钟线是盘中最大持续写入源，但进程内锁保护安全；**真实冲突只发生在跨连接/跨进程**（API 写、测试、手动重算、WAL checkpoint）。

## 二、隐性链接问题清单（本次会话实证）

### 🔴 问题 1：minute_full 非交易时段也采集（check_trading_time=False）

- `minute_full` 线程（300s）`check_trading_time=False`——**非交易时段（如 10:00 开机）也在写 ECM 分钟线**
- 与预计算**抢 CPU/连接**；跨进程（API 读分钟线）时是潜在冲突源
- **修复**：加交易时段限制（与 snapshot 一致），非交易时段停 mootdx 分钟采集；完整性由 Tushare 回填兜底（见 §三）

### 🔴 问题 2：WAL checkpoint 无法收缩（WAL 膨胀 7.6G）

- checkpoint 158 次全失败（busy=1）→ WAL 只增不减
- 根因：API 持续读（5s 快照推送）与 daemon PASSIVE checkpoint 竞争
- **修复**：checkpoint 避开 API 读高峰（如非交易时段/空闲），失败延迟重试

### 🟡 问题 3：申万指数永久缺失致回填死循环（已修复 0b78fdd）

- 801020.SI 在 Tushare 返回 0 行（永久缺失）→ 完整性检查每 tick 触发 60 天回填 → 死循环阻塞主循环
- **已修复**：cache_metadata 记录当日已尝试，次日自动重试

### 🟡 问题 4：管道状态与进程状态耦合（已修复 327 阶段1）

- daemon 重启不重置 pipeline_status → running 卡死（已修 running 超时恢复）

### 🟢 问题 5：sync_requests 依赖 daemon 在线（已修复 327 阶段5）

- API 写队列，daemon 停机无人消费（已修启动即消费）

## 三、分钟线完整性机制（用户核心疑问）

### 3.1 分钟线有【三层保障】，非仅 mootdx 盘中采集

| 机制 | 触发 | 数据源 | 保障 |
|------|------|--------|------|
| 1. mootdx 盘中采集 | 交易时段每 5s/5min | mootdx TCP | 实时分钟线 |
| 2. `_batch_backfill_minute_kline`（日终回填）| 日终后后台线程 | **Tushare pro_bar 1min** | **补齐当日缺分钟线的股票**（前500只/轮）|
| 3. `_check_watchlist_minute` + `run_backfill_all` | 完整性检查 + 闲时 | mootdx minutes() | 自选股分钟补采 |
| 4. `minute_backfill.aggregate_minute` | 补采后 | 1min→5m/15m/30m/60m 聚合 | 生成各周期分钟线 |

### 3.2 关键答案：非交易时段未开机，分钟线如何完整？

**机制 2（`_batch_backfill_minute_kline`）是关键**：
```
日终后（任意时间开机，只要 daemon 运行）：
  → 查"今日有日线但缺分钟线的股票"
  → 用 Tushare pro_bar 补齐 1min 数据（当日完整分钟线）
  → 聚合出 5m/15m/30m/60m
```

**含义**：
- ✅ **即使盘中未开机**（10:00 才开），**日终后用 Tushare 补齐当日分钟线**（Tushare 有完整当日分钟数据）
- ✅ **完整性由"日线为基准"校验**（有日线 → 缺分钟则补）——自动保障
- ⚠️ **限制**：回填**每次限 500 只**（防拖慢）——未开机日全市场缺分钟需**多轮回填**

## 四、整改方案（基于完整核查）

### 4.1 优先级排序

| 优先级 | 整改项 | 解决 |
|:---:|--------|------|
| **P0** | minute_full 加交易时段限制 | 非交易时段停 mootdx 分钟采集（完整性由 Tushare 回填兜底）|
| **P0** | WAL checkpoint 时机优化 | 避开 API 读高峰，解决 7.6G 膨胀 |
| **P1** | 开机回填增强（多轮覆盖全市场）| 未开机日分钟线完整性保障 |
| **P1** | 预计算切片（可选）| 跨进程场景（API 读分钟线期间）减少长事务窗口 |

### 4.2 关键设计（针对非24h开机）

```
开机（任意时间）→ 数据审计（327 阶段2）
  ├─ 昨日数据完整 → 全量补算（P1-P4，后台低优）
  └─ 昨日缺失 → 先补采昨日 → 全量补算
交易时段：只做 L1 单只即时预计算（自选股，秒级）；全市场延后收盘后
收盘后：全量预计算（P1-P4，切片批处理）
分钟线：盘中 mootdx 采集（交易时段）；日终 Tushare 回填兜底（非交易时段）
```

## 五、结论

1. **架构模式合理**（单进程承载采集+日终预计算），非24h开机场景**核心担忧已有解**——分钟线完整性由 Tushare 回填保障
2. **进程内采集+预计算不冲突**（锁串行化实测安全）；真实冲突在跨进程（API 写/测试/checkpoint）
3. **需整改**：minute_full 交易时段限制 + WAL checkpoint 时机（P0 两项）
4. **292 总稿需同步**：5.3 管道驱动机制（running 超时/数据驱动/C1-C6 跳过）、7.4 分钟数据（Tushare 回填兜底）已与实现存在差异
