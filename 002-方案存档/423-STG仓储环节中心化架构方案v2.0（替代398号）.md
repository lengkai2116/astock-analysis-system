> **替代原因**：398 号问题诊断基线已被 421/422 号方案部分修复（写入路由/失败暴露/读写分叉已闭环）；5 个设计缺陷需修正（阻塞式多轮核查、双补算通道、硬编码阈值、门禁放错层、告警通道不适配）；Phase A（dim 梳理）已完成，工期可压缩。v2.0 仅保留真实缺口（8 项）作为实施目标。

## 2. 架构设计（关键修订）

### 2.1 修订原则

```
STG 网关 = sharding_manager（路由+锁+幂等，既有）
         + WriteGateway（薄封装：校验+日志，新增）
         + QualityChecker（质量规则，新增）
         + RecomputeScheduler（定向补算，复用既有执行通道）
         + 语义化门禁（daemon 侧判定管道故障；OUT 侧输出语义文本）
```

**分层边界（v2.0 核心修正）**：
- **数据门禁层（daemon/STG）**：校验不通过 → 补算/标记 failed → **不产出**。抛出/记录的是"管道故障"，不落 snapshot 成品。
- **语义化层（OUT/dim8）**：只处理"校验已通过"的数据，把正常空值（无背驰/无买卖点）转为有意义文本。
- v1.0 把 `DataPipeFailureError` 放在 dim8 内部不合理——API 进程无法触发 daemon 补算，且会污染前端异常。**v2.0 上移门禁到写入前**。

### 2.2 组件 1：WriteGateway（薄封装）

```python
class WriteGateway:
    """统一写入网关——sharding_manager 之上的薄封装
    职责：写前格式校验 → 委托 sharding_manager 执行（锁/事务/幂等）
         → 写后行数校验 → 写入审计日志
    不持有锁、不建连接池；全部委托既有 sharding_manager。
    """
    def write_batch(self, table: str, rows: list,
                    pipeline_date: str, expected_ratio: float = 0.95) -> WriteResult:
        # 1) 写前校验：validate_before_write()（行非空、必填字段、JSON 可解析）
        # 2) 委托 sharding_manager.execute_batch_insert(table, sql, rows)
        #    —— 复用 _write_locks 串行化 + INSERT OR REPLACE 幂等
        # 3) 写后校验：count(table, pipeline_date) >= daily_base * expected_ratio
        # 4) 审计：写入 qa_audit_log（pipeline_date/table/rows/校验结果）
```

### 2.3 组件 2：QualityChecker（动态覆盖率）

**v2.0 修正 v1.0 的两个规则缺陷**：
1. 全表 `min_rows` 阈值错误：`factor_cache`（3715 万行累积）/`pre_feat_cache`/`daily_cache` 均为**累积表**，总行数阈值无意义。改为**按目标日期当日行数**校验。
2. 4000 行硬编码含义不清（≈全市场 73%）。改为**覆盖率基准**：以 `daily_cache` 目标日期行数 N 为锚，其他表行数 ≥ N×ratio。

```python
RULES = {
  # 每表校验维度：rows_ratio（对 N 的覆盖率）/ date_align / required_fields / json_fields
  'daily_cache':        {'rows_ratio': 1.00, 'date_align': True},
  'indicator_ma':       {'rows_ratio': 0.95, 'date_align': True, 'required_fields': ['ma5','ma20'],
                          'src': 'daily_cache'},
  'indicator_macd':     {'rows_ratio': 0.95, 'date_align': True, 'required_fields': ['macd_dif']},
  'indicator_other':    {'rows_ratio': 0.95, 'date_align': True, 'required_fields': ['rsi14']},
  'pre_feat_cache':     {'rows_ratio': 0.95, 'date_align': True, 'json_fields': ['features_json']},
  'factor_cache':       {'rows_ratio': 0.95, 'date_align': True},  # 按当日批次，非总行数
  'strategy_signal_detail': {'rows_ratio': 0.95, 'date_align': True,
                          'required_fields': ['signal_json','dim_results_json'],
                          'json_fields': ['signal_json','dim_results_json','seven_dim_json'],
                          'seven_dim_keys': 7},   # seven_dim_json 须含 7 个 dim 键（G3）
  'status_snapshot':    {'rows_ratio': 0.95, 'date_align': True,
                          'required_fields': ['dim_states','status_bar']},
  'treemap_snapshot':   {'rows_ratio': 0.95, 'date_align': True},
}
```

**G3 专项（SIG 质量自检，v2.0 新增）**：在 `_precompute_strategy_signals` 批量写库前，对每条 record 校验 `signal_json`/`dim_results_json` 可 `json.loads` 且非空、`seven_dim_json` 含 7 个 dim 键；任一条不合法 → 整批标记 failed（复用 421R3 的 `SignalWriteError` 重试路径），杜绝"计算出来但内容是坏的"。

## 3. 时序模型（v2.0 修订：去阻塞）

| Round | 触发时机 | 内容 | 执行方式 |
|---|---|---|---|
| R1 | 每写入点完成后 | `write_batch` 内写后行数/日期校验（轻量） | 同步，毫秒级 |
| R2 | 全管道步骤 done 后 | 跨表对齐校验（indicator↔daily 等） | daemon 主循环下一 tick 触发（不 sleep） |
| R3 | 次日开盘前 / 定时巡检 | 多轮核查 + 历史日期巡检（G8） | 事件驱动：失败→打 QA-CHECK pending→下轮再校验 |

**事件驱动多轮核查（替代 v1.0 `time.sleep(300)`）**：

```
主循环 tick（30s）：
  若存在 QA-CHECK pending 或管道全部 done：
    QualityChecker.multi_round_once(pipeline_date)   # 单轮，非阻塞
      → passed：QA-CHECK 标 done
      → failed：schedule_recompute() → QA-CHECK retry_count+1
                 → retry_count > 3 → 告警升级（L2/L3）
  主循环照常继续（采集/补采不受影响）
```

QA-CHECK 复用 `pipeline_status` 的一个 step_id【D3 已确认 2026-09-10】，天然复用幂等锁 + retry_count + timeout 机制，不新增状态表；问题明细写入 detail 字段（JSON 序列化）。
