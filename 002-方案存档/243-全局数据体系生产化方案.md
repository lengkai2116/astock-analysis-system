# 全局数据体系生产化方案（243号方案）

## 概述

本方案围绕用户提出的三个生产化问题展开设计：

1. **AKShare 快速启动/开机自运行** — 采集器集成到 Flask 进程，launchd 保活
2. **PostgreSQL 替换 SQLite** — 持久化运营稳定性提升，**盘中实时数据也用 PG**
3. **数据读写瓶颈预判** — 随策略和监控规则增长，读写量对 PG 的压力评估

### 关键沟通过程

| 轮次 | 用户观点 | 结论 |
|:-----|:---------|:------|
| 第一稿 | 用户说"切换到性能更好的PostgreSQL" | 我以为只替换 SQLite |
| 第一次纠正 | "DuckDB不迁移，保留为盘后" | DuckDB 保留不动 |
| 第二次纠正 | **"盘中用 PostgreSQL"** | 盘中实时也用 PG，不只是业务数据 |
| 最终澄清 | "每人独立使用，独立单机程序" | 非多租户，每人本地装 PG |

## 最终架构

```
分层              存储                         角色
─────────────────────────────────────────────────────────
① 盘中实时  →  InMemoryStateStore + PostgreSQL    双写
② 盘后归档  →  DuckDB（不变）                    保留
③ 业务数据  →  PostgreSQL（替换 SQLite）          迁移
```

### InMemoryStateStore 保留为 L1 热缓存

**不是二选一（InMemoryStateStore vs PG），是两级存储：**

| 层 | 读延迟 | 持久化 | 跨 worker | 用途 |
|:---|:-------|:-------|:----------|:------|
| InMemoryStateStore | ~0.001ms O(1) | ❌ | ❌ | WS 推送 + 高频读 |
| PostgreSQL | ~1-3ms 带索引 | ✅ | ✅ | REST API + 重启恢复 |

### PG 盘中数据保存策略

PG 盘中数据**不需要长期存档**：

| PG 表 | 盘中完后 | 原因 |
|:------|:---------|:------|
| `realtime_snapshot` | 清空 | 3分钟前的快照无价值 |
| `realtime_top_stocks` | 清空 | 盘中排名历史无意义 |
| `realtime_sectors/concepts` | 清空 | 同上 |
| `realtime_limit_pool` | 清空 | 涨停/跌停是瞬间状态 |
| `realtime_minute_kline` | 保留1-3天 | 复盘分析，之后由 DuckDB 接管 |
| `realtime_lhb` | 保留当日 | Tushare 版更权威 |
| `realtime_news` | 清空 | 过时新闻无存档价值 |

### 步骤 3：PG 双写（代码已修改）

**新建文件：`backend/app/data/realtime_pg.py`**
- PostgreSQL 连接池（`ThreadedConnectionPool`, 2~10 连接）
- 8 张盘中实时表（`CREATE TABLE IF NOT EXISTS` 幂等创建）
- 批量 UPSERT（`INSERT ... ON CONFLICT DO UPDATE`）

**修改文件：`backend/app/data/akshare_collector.py`**
- 5 个采集线程各加一行 PG upsert 调用（非阻塞）
- 惰性导入 `_get_pg()` 避免循环依赖

写入路径变为三级：

```
mem_store.update_xxx(records)        # L1 热缓存
_get_ecm().write_as_xxx(records)     # DuckDB 归档
_get_pg().get('xxx')(records)        # PG 持久化（新增）
```

## 架构决策总结

| 决策点 | 方案 | 理由 |
|:-------|:-----|:------|
| 盘中实时主存储 | **PostgreSQL** | Gunicorn 多 worker 共享，进程重启不丢 |
| L1 热缓存 | **InMemoryStateStore 保留** | O(1) 读取、WebSocket 推送零延迟 |
| 盘后归档 | **DuckDB 不变** | 分析查询性能好，不增加 PG 负担 |
| 采集器位置 | **Gunicorn master 进程**（on_starting hook） | 仅一个进程运行，所有 worker 共享 PG 数据 |
| 多 worker WS 广播 | **Redis pub/sub**（message_queue） | Gunicorn 多 worker 间 WS 通信的必需要素 |
| 进程保活 | **launchd** | macOS 原生，开机自启 + 崩溃重启 |
| 部署模式 | **每人独立单机** | 非多租户，每人本地装 PG |
| PG 盘中数据存档 | **不长期保存** | 盘中快照盘后清空，分钟K线保留 1-3 天 |
