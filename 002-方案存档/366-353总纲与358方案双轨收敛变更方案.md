# 366 — 353总纲与358方案双轨收敛变更方案

> **背景**：系统当前存在两套并行的判定体系——353总纲定义的12维内联路径（旧）和358方案定义的7维引擎路径（新）。本方案分析具体问题并制定收敛变更计划。
>
> **v2.0更新**：基于对358-361号方案系统实际配置的全面检查，补充缺失组件清单、pre_feat_cache字段缺口、维度引擎整合状态、旧体系退役计划，并更新变更步骤和验证标准。

---

## 一、问题全景

### 1.1 双轨并行现状

```
路径A（353体系·生产主路径）：
  evaluate() 
    → _build_dimensions()    ← 10维内联判定（353总纲§3.5定义）
    → _aggregate()           ← 共识率+冲突暴露
    → _assemble()            ← 输出status_snapshot
  
  数据流：pre_feat_cache → tags → 内联计算 → dims → dim_states
  
  影响范围：5541只股票日终批量运行，全市场快照由此路径产出

路径B（358体系·七维体检报告）：
  build_seven_dim_report()
    → build_signal_confirm()     ← signal_attribute_classifier.py
    → build_structure()          ← structure_builder.py
    → build_volume_price()       ← vp_health_builder.py
    → build_fund_chip()          ← fund_chip_builder.py
    → build_emotion()            ← emotion_builder.py
    → build_risk_boundary()      ← risk_boundary_builder.py
  
  数据流：tags + dims + geo → builder → {status_description, judgment, audit, plain}

路径C（365号新增·引擎并行路径）：
  _build_dim_engine_results()
    → dim1~dim6_engine.evaluate(dims, tags, signals, lifecycle)
  
  数据流：dims + tags → dim引擎 → dim_engine_results（附加到status_snapshot）
```

**三条路径同时运行，产出三套不同格式的结果。**

### 1.2 核心矛盾

| 矛盾 | 具体表现 | 影响 |
|------|---------|------|
| **数据源分裂** | 路径A的判定从 `dims` 读取，路径B的现状描述从 `tags` 读取 | 同一股票的"判定"和"现状描述"可能不一致 |
| **key不匹配** | builder需要 `position_vs_zs`/`RSI_14`/`KDJ_J` 等key，tags中不存在 | 结构/量价/风险维度现状描述大量"数据不足" |
| **geo参数缺失** | `build_seven_dim_report(geo=None)` 导致支撑阻力全空 | 风险维度无法输出防守位和盈亏比 |
| **旧体系未退役** | `_build_dimensions()` 仍生成旧10维，`_aggregate()` 仍用旧投票逻辑 | 新维度引擎的输出未被仲裁层消费 |
| **353总纲未更新** | 353号v2.1仍定义"12维度状态判定"，从未反映358的7维架构 | 架构文档与代码实现脱节 |

## 二、根因分析

### 2.1 353总纲的时效性问题

353号总纲最后更新于2026-08-19（v2.1），定义环节5 JUD = 12维度体系。358号方案在2天后（2026-08-21）提出7维架构升级。但353总纲从未同步更新。

**结果**：代码正确执行了353总纲的定义（旧路径），而358方案的新体系作为附加层叠加（新路径），两个总纲之间缺少一次合并更新。

### 2.2 358号方案的过渡说明

358号§10.2（line 638）有明确的过渡声明：

> "当前StatusEngine仍基于12维判定体系（DIM-1~11投票），正逐步向七维框架迁移。以下为现有实现，七维框架的最终实现将替代此流水线。"

但**未指定移除时间点**。364号Phase 8定义了"删除冗余代码"步骤，但依赖所有前置Phase完成。

### 2.3 builder数据通路设计缺陷

`build_structure(dims, tags, geo)` 中：

| 子函数 | 数据来源 | tags中是否有 | 结果 |
|--------|---------|:----------:|------|
| `_assess_vs_zhongshu` | `tags['position_vs_zs']` | ❌ 不存在 | "中枢位置数据不足" |
| `_assess_vs_zhongshu` | `tags['pct_from_zs']` | ❌ 不存在 | 无百分比 |
| `_assess_vs_ma` | `tags['ma_alignment']` | ✅ 'mixed' | "均线mixed" |
| `_assess_vs_support_resistance` | `geo['support_price']` | ❌ geo={} | "支撑阻力数据不足" |
| `_assess_vs_chip` | `tags['chip_concentration']` | ✅ 'concentrating' | "筹码concentrating" |
| `_assess_vs_indicator` | `tags['RSI_14']` | ❌ 不存在 | "指标数据不足" |

**根因**：builder从 `tags`（pre_feat_cache扁平化）读数据，但pre_feat_cache中没有写入这些key。同时 `geo` 参数从未被传入有效值（默认None→{}）。

### 2.4 全量数据缺口清单

经逐函数追踪，builder需要但tags中不存在的key共7个，类型不匹配1个，参数传递问题4个。

**缺失key（7个）**：

| builder | 缺失key | 影响 | 修复方向 |
|---------|---------|------|---------|
| structure_builder | `position_vs_zs` | 中枢位置→"数据不足" | 从dims.evidence提取或新增到pre_feat_cache |
| structure_builder | `pct_from_zs` | 距中枢百分比→缺失 | 同上 |
| structure_builder | `RSI_14` | 指标→"数据不足" | 从daily_basic_cache计算或新增到pre_feat_cache |
| structure_builder | `KDJ_J` | 指标→"数据不足" | 同上 |
| vp_health_builder | `volume_ratio` | 量比→缺失（实际存储为`vol_price_ratio`，key名不匹配） | 统一key名或增加映射 |
| fund_chip_builder | `margin_change_5d` | 融资变化→缺失 | 新增到pre_feat_cache |
| risk_boundary_builder | `exit_conditions` | 失效条件→缺失 | 新增到pre_feat_cache |

**类型不匹配（1个）**：

| builder | key | 实际类型 | 期望类型 | 影响 |
|---------|-----|---------|---------|------|
| emotion_builder | `sector_heat` | 数值（如`0`） | 字符串枚举（`'top_10'`/`'top_20'`等） | `str(0)`→`'0'`匹配不到枚举，始终返回`'normal'` |

**参数传递问题（4个）**：

| 参数 | 调用方传入 | builder期望 | 影响 |
|------|----------|-----------|------|
| `geo` | `{}`（build_seven_dim_report默认None→{}） | 含support_price/resistance_price的dict | 支撑阻力→全空 |
| `sub_scores` | `{}`（_build_fund_chip_segment硬编码） | MainForceScorer输出 | 资金强度→始终为0 |
| `df` | 可能为None | daily DataFrame | 波动率ATR计算→失败 |
| `l0` | 从闭包获取 | 含hard_veto/soft_risks的dict | 风险门禁→可能缺失 |

**365号已新增但builder未读取的key**：

| key | 所在group | 可替代的缺失key |
|-----|----------|---------------|
| `vol_price_ratio` | volume_price | 可替代`volume_ratio`（需key映射） |
| `volatility_percentile` | risk_ext | 可用于波动率分位 |
| `fund_flow_strength` | chip_fund_ext | 可用于资金强度 |
| `emotion_temperature` | emotion_ext | 可用于情绪温度 |
| `support_price` | structure_ext | 可替代geo中的支撑位 |
| `resistance_price` | structure_ext | 可替代geo中的阻力位 |

### 2.5 judgment数据通路

`build_structure()` 的judgment部分（line 45-49）读取 `dims`：

```python
struct_state = dims.get('structure', {}).get('state', '盘整')  # 默认'盘整'
pos_state = dims.get('position', {}).get('state', '中位')       # 默认'中位'
```

`dims` 来自 `_build_dimensions()` 的旧10维内联逻辑，始终有值。所以judgment永远有结论，而status_description可能"数据不足"。

## 三、变更方案

### 3.1 变更目标

**消除双轨并行，统一为单一数据通路**：

```
目标架构（单一路径）：
  evaluate()
    → 6个维度引擎(dims, tags, signals, lifecycle)
    → 兼容层(转为旧dims格式供下游消费)
    → _aggregate() + _assemble()
    → status_snapshot（含七维体检报告）
  
  数据流：pre_feat_cache + strategy_signal_detail → 维度引擎 → 统一输出
```

### 3.2 变更范围

| 类别 | 文件 | 变更类型 | 说明 |
|------|------|---------|------|
| **总纲更新** | 353号总纲 | 文档修订 | 环节5 JUD从12维更新为7维 |
| **核心重构** | status_engine.py | 代码重构 | evaluate()改为调用6维度引擎 |
| **数据通路** | status_engine.py | 代码修复 | builder统一从dims读取，不单独从tags读 |
| **参数补全** | status_engine.py | 代码修复 | 计算geo并传入build_seven_dim_report |
| **兼容层** | status_engine.py | 新增代码 | _convert_to_dims_format() |
| **下游适配** | arbiter.py | 代码适配 | 消费新维度引擎输出 |
| **下游适配** | cross_validate.py | 代码适配 | 消费新维度引擎输出 |
| **旧代码退役** | status_engine.py | 代码删除 | _build_dimensions()标记废弃 |

### 3.3 详细变更步骤

#### 步骤1：统一builder数据读取 + 修复数据缺口（5h）

**问题**：builder从tags读数据，但tags中缺少7个key、1个类型不匹配、4个参数传递问题。

**方案A：tags注入**（status_engine.py `build_seven_dim_report`）

将dims中的关键信息和365号已新增的扩展字段注入tags：


#### 步骤3：evaluate()重构 — 调用维度引擎替代_build_dimensions（8h）

**问题**：evaluate()仍用旧10维内联逻辑，维度引擎输出未被主路径消费。

**方案**：重构evaluate()，用6维度引擎调用替代_build_dimensions()，通过兼容层保持下游兼容。

**具体变更**（status_engine.py）：

```python
def evaluate(self, ts_code):
    tags = self._load_tags(ts_code)
    signals = self._load_signals(ts_code)
    if not tags and not signals:
        return None
    
    lifecycle = self._signal_lifecycle(ts_code, tags, signals)
    
    # 366号步骤3：用维度引擎替代_build_dimensions()
    dim_engine_results = self._build_dim_engine_results(tags, signals, {}, lifecycle)
    
    # 兼容层：将维度引擎输出转为旧dims格式
    dims = self._convert_to_dims_format(dim_engine_results, tags)
    
    l0 = self._apply_l0(ts_code, tags, dims, lifecycle)
    l2 = self._aggregate(tags, dims, l0, lifecycle)
    hits = self._detect_registered_signals(tags, signals)
    
    return self._assemble(ts_code, dims, lifecycle, l0, l2, hits, dim_engine_results)
```

## 六、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| evaluate()重构导致判定结果变化 | 用户可见的股票排序/状态变化 | 兼容层保持旧格式输出，新旧路径diff验证 |

| **缺失分析器开发复杂度高** | **开发周期延长** | **分阶段实施，先核心后增强** |
| **pre_feat_cache字段补全影响性能** | **日终批量耗时增加** | **增量写入，避免全量重算** |
| **维度引擎整合引入回归** | **现有功能受损** | **新旧路径并行运行1周，全市场diff验证** |
| **旧体系退役导致功能缺失** | **关键功能不可用** | **保留兼容层回退，确保降级可用** |
