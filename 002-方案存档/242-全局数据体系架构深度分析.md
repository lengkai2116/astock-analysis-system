# 全局数据体系架构深度分析

## 概述

本报告围绕用户提出的三大核心问题进行深度分析：

1. **AKShare 盘中数据获取** — 当前是否最优？真正的堵点是什么？
2. **DuckDB 方案适配性** — 是否不适配？更好的方案？僵尸锁如何根治？
3. **同类项目架构调研** — 业界量化项目如何做盘中实时数据？

分析基于代码走读、运行时日志审查、AKShare 真实环境测试（沙箱内外）、DuckDB 文件状态核查、以及业界竞品调研。

## 一、AKShare 盘中数据获取深度分析

### 1.1 当前架构

```
AkshareProvider (__init__.py 注册, priority=-1)
    │
    ├─ AkshareCollector (5 daemon 线程, 盘中主动采集)
    │    ├─ Thread 1: market_snapshot  / 15s  → InMemoryStateStore + DuckDB
    │    ├─ Thread 2: top_stocks       / 30s  → InMemoryStateStore + DuckDB
    │    ├─ Thread 3: sector+limit     / 5min → InMemoryStateStore + DuckDB
    │    ├─ Thread 4: minute_kline     / 5min → InMemoryStateStore + DuckDB
    │    └─ Thread 5: lhb+news        / 30min→ InMemoryStateStore + DuckDB
    │
    └─ DataSourceManager (按需查询, 降级路由)
         └─ get_data_time_aware()
              ├─ 交易时段 → AKShare
              └─ 盘后 → Tushare
```

### 1.2 AKShare 真实可用性测试

**结论：AKShare 在当前环境中 import 成功（v1.18.64），但存在网络隔离问题。**

沙箱内测试结果：
```
❌ DNS: push2.eastmoney.com → nodename nor servname provided
❌ HTTP: stock_zh_a_spot_em() → NameResolutionError
```

**根因：Claude Code 沙箱的 DNS 仅限于 `127.0.0.1` 和 `api.anthropic.com`，所有 BastMoney 域名均无法解析。** 这不是系统或 AKShare 的问题，而是 Claude Code 会话环境的固有限制。

**关键区分**：Flask 后端通过 `launch.json` 启动时是**本机原生进程**，不受沙箱 DNS 限制。但 Bash 工具测试全部在沙箱内执行，故 AKShare 网络调用从本对话内直接测试**必然失败**。

当后端实际运行（非在 Claude 对话中测试）时：
- AKShare 模块已安装、已注册、已设置代理免疫
- `DataSourceManager` 日志显示 `活跃数据源切换: tushare → akshare`，说明注册成功且健康检查通过
- 缺少后端运行时的 AKShare 实际调用成功日志（日志文件中只有注册事件，无实际调用结果）

### 1.3 代理环境变量

当前 shell 残留代理变量：
```
HTTP_PROXY   = http://srt:a454995ed...@localhost:62516
HTTPS_PROXY  = http://srt:a454995ed...@localhost:62516
ALL_PROXY    = socks5h://srt:a454995ed...@localhost:62519
```

这些代理变量来自 Claude Code 沙箱，端口 62516/62519 是沙箱内部代理。`akshare_provider.py` 和 `akshare_collector.py` 均已实现模块级 `os.environ.pop()` 清除，`_diagnose_network.sh` 也已硬编码代理免疫。**此问题已在 240号方案中解决。**

### 1.4 当前架构评价

| 维度 | 评价 | 改进方向 |
|:-----|:-----|:---------|
| 采集频次 | 15s~30min，远低于东方财富接口承载能力 | 合理，无需调整 |
| 写入策略 | 先写内存(O(1)) → 再写DuckDB(非阻塞) | 正确，盘中核心路径无IO瓶颈 |
| WebSocket 推送 | WsBridge → socketio.emit | 架构正确，但当前尚未接入前端 `useRealtimeData` |
| DataSourceManager 路由 | 交易时段→AKShare，盘后→Tushare | 正确，但时间判断依赖 `trading_hours.py` |
| 健康检查 | `health_check` 端点仅返回 `{'status': 'ok'}`，**不验证实际网络连通性** | ⚠️ 健康检查流于形式 |
| 降级机制 | 3次失败→fallback，再6次→unavailable | 逻辑正确，但未验证实际触发 |

### 1.5 真正堵点

1. **健康检查是伪检查**：`health_check` 端点直接返回 `{'status': 'ok'}`，不发起任何实际网络调用。如果 AKShare 实际 DNS 被阻断（如沙箱环境启动），健康检查不会发现，`DataSourceManager` 会误认为 AKShare 处于正常状态，路由到它但在实际调用时失败。

2. **AkshareCollector 从未真正启动**：
   - `akshare_collector.start()` 在 `__init__.py` 中**没有被调用**（搜索不到启动代码）
   - 5个采集线程从未创建 → InMemoryStateStore 始终为空 → WsBridge 永远不会 emit
   - 前端 `useRealtimeData` 组件接收到的是空数据

3. **前端未真正对接 WebSocket 推送**：
   - `useRealtimeData.js` composable 存在但仪表盘 `dashboard.html`（原型页面）仍使用 REST API 轮询
   - Vue 组件可能已接入，但原型页面未更新

> **结论**：AKShare 的"不可用"不是 AKShare 本身的问题，而是**集成缺失**——采集器未启动 + 前端未实际对接 WS。

## 二、DuckDB 方案适配性评估

### 2.1 当前状态

#### 双库双路径（严重问题）

存在 **两个独立的 DuckDB 数据库文件**：

| 位置 | 大小 | 状态 | 来源 |
|:-----|:-----|:-----|:-----|
| `data/duckdb/stock_cache.db` | 252MB | ✅ 主库，被旧 PID 25816 锁定 | Config.DATA_DIR 默认值 |
| `backend/instance/duckdb/stock_cache.db` | 12MB | ⏳ 次要库，同步滞后 | 旧版代码/instance_path |

**根因**：`enhanced_cache_manager.py:62` 中：
```python
data_dir = os.getenv('DATA_DIR', '/data')  # 默认 /data
```
但 `config.py:18` 中：
```python
DATA_DIR = os.getenv('DATA_DIR', _get_default_data_dir())  # 默认 project_root/data/
```

两者默认值不同：ECM 默认 `/data`（根目录），Config 默认 `/Users/kalence/.../data`。当 `DATA_DIR` 未设置时（当前情况），ECM 试图连接 `/data/duckdb/`，但实际数据存在 `project_root/data/duckdb/`。

#### corrupted 文件膨胀

数据库目录中共有 **14 个 corrupted 备份文件**：

| 目录 | 文件数 | 总大小 |
|:-----|:-------|:-------|
| `data/duckdb/` | 10 个 | ~2.5GB |
| `backend/instance/duckdb/` | 4 个 | ~620MB |
| **合计** | **14 个** | **~3.6GB** |

**产生过程**：
1. 首次启动 → PID 25816 连接主库，获得文件锁
2. Flask `debug=True` 启用热重载 → 文件变更触发进程重启
3. 新进程执行 `EnhancedCacheManager.__init__()` → 尝试连接 `stock_cache.db` → **旧 PID 25816 仍持有锁**
4. 连接失败 → 尝试连接 `stock_cache.db.backup` → **旧 PID 25842 持有备份锁**
5. `shutil.copy2(db_path, rotated_path)` → 创建 `stock_cache.db.corrupted.{timestamp}`（252MB）
6. 创建空库也失败 → 回退到 `:memory:` 模式
7. 进程再次热重载 → **重复步骤 3-6** → 每个 restart 产生一个新的 corrupted 文件

每次 Flask 热重载（约 2-3 秒）就产生一个 252MB 的 corrupted 文件，10 次 restart 即产生 ~2.5GB。

#### DuckDB 文件锁机制

DuckDB 使用 SQLite 兼容的文件锁（`dotlock` 风格），锁信息记录在文件系统的 advisory lock 上，包含持有 PID。即使 `stock_cache.db.wal` 和 `.tmp` 被清理（ECM 启动时的 `_clean_stale_duckdb_locks`），**主库文件 `stock_cache.db` 本身的文件锁不受影响**。

```
IO Error: Could not set lock on file ".../stock_cache.db":
  Conflicting lock is held in .../python3.11 (PID 25816) by user kalence.
```

### 2.2 DuckDB 适配性评价

| 维度 | 评价 | 说明 |
|:-----|:-----|:------|
| **盘后日线批量写入** | ✅ 非常适合 | 单次写入，大量 DataFrame 操作，OLAP 性能佳 |
| **分钟K线追加** | ✅ 适合 | 追加写入性能好，分析查询快 |
| **因子计算** | ✅ 非常适合 | 窗口函数、SQL 聚合等效高 |
| **跨表关联查询** | ✅ 适合 | SQL JOIN 能力完整 |
| **盘中高并发读写** | ❌ **不擅长** | 单进程单写者，文件锁争抢 |
| **多进程部署** | ❌ **不擅长** | 文件锁天然屏障 |
| **热重载/频繁重启** | ❌ **不擅长** | 僵尸锁清理机制不完善 |
| **作为实时数据管道** | ❌ **不合适** | InMemoryStateStore 已是正确选择 |

**总体判断**：DuckDB 作为**盘后归档数据库**是合适的，但**不该作为盘中高频读写的中心存储**。当前架构中 InMemoryStateStore 处理盘中实时数据是正确的分层。

### 2.3 替代方案对比

| 方案 | 盘中实时 | 盘后归档 | 多进程 | 部署复杂度 | 推荐度 |
|:-----|:---------|:---------|:-------|:----------|:-------|
| **DuckDB** (当前) | ❌ | ✅✅ | ❌ | 低 | ⭐⭐⭐盘后/⭐⭐盘中 |
| **SQLite WAL 模式** | ⚠️ 单写者 | ✅ | ❌ | 极低 | ⭐⭐ |
| **PostgreSQL** | ✅ | ✅✅ | ✅✅ | 中 | ⭐⭐⭐⭐ |
| **SQLite + 内存混合** | ✅ (内存) | ✅ (SQLite) | ❌ | 极低 | ⭐⭐⭐ |
| **纯 InMemoryStateStore** | ✅✅ | ❌ 无持久化 | N/A | 极低 | ⭐⭐⭐ 盘中 |
| **Parquet 文件** | ❌ | ✅✅ | ✅✅ | 低 | ⭐⭐⭐ 归档 |
| **TimescaleDB** | ✅ | ✅✅ | ✅✅ | 高 | ⭐⭐⭐ |

**不建议迁移**的理由：
- 当前分层架构（InMemoryStateStore 盘中 + DuckDB 盘后）**设计是正确的**
- 核心问题不在于 DuckDB 本身，而在于**集成缺陷**（双库路径 + corrupted 膨胀）
- 迁移到 PostgreSQL 增加运维复杂度，与当前轻量部署矛盾

### 2.4 僵尸锁根治方案

**当前方案**（不足）：
- 清理 `.wal`/`.tmp` 文件（60s 过期）→ 不解决主库文件锁
- corrupted 文件创建后永不清理 → 无限膨胀

**推荐改进方案**：

**Phase A（立即修复）**：

1. **修正 ECM 默认路径**：使用 `Config.DATA_DIR` 而不是 `/data`
   ```python
   # enhanced_cache_manager.py:62
   # 改为：
   from flask import current_app
   data_dir = os.getenv('DATA_DIR') or (
       current_app.config.get('DATA_DIR') if current_app else None
   ) or '/data'
   ```

2. **启动时 kill 旧 PID**：
   ```python
   def _kill_stale_duckdb_pids(db_path: str):
       """在连接前检查并 kill 持有 locks 的旧 PID"""
       import fcntl, struct
       # 读取 DuckDB 锁文件中的 PID（使用 lsof 替代 DuckDB API）
       import subprocess
       result = subprocess.run(
           ['lsof', '-F', 'p', db_path],
           capture_output=True, text=True, timeout=5
       )
       pids = [int(line[1:]) for line in result.stdout.splitlines() 
               if line.startswith('p') and int(line[1:]) != os.getpid()]
       for pid in pids:
           try:
               os.kill(pid, 9)
               logger.warning(f"已 kill 旧 DuckDB 进程 PID {pid}")
           except (OSError, ProcessLookupError):
               pass
   ```

3. **限制 corrupted 文件数量**：创建时清理超过 N 个的旧文件
   ```python
   def _rotate_corrupted_backup(db_path: str, max_backups: int = 3):
       """创建 corrupted 备份时限制最大数量，超过则删除最旧的"""
       dir_name = os.path.dirname(db_path)
       pattern = os.path.basename(db_path) + '.corrupted.*'
       backups = sorted(glob.glob(os.path.join(dir_name, pattern)))
       while len(backups) >= max_backups:
           os.remove(backups.pop(0))
   ```

4. **重试机制 + 指数退避**：连接失败后重试 3 次，每次等待 1s→2s→4s
   ```python
   for attempt in range(3):
       try:
           self.conn = duckdb.connect(self.db_path, config=duckdb_config)
           break
       except Exception as e:
           if attempt < 2:
               time.sleep(2 ** attempt)  # 1s, 2s
               continue
           raise
   ```

**Phase B（中期改进）**：

5. **生产环境禁用 debug 模式**：`export FLASK_ENV=production`，热重载在开发环境之外不应启用
6. **引入健康检查 endpoint**：`GET /api/v3/duckdb/health` 验证连接、查询、锁定状态
7. **定期清理策略**：APScheduler 每天凌晨 3:00 清理 7 天前的 corrupted 文件

**Phase C（长期方案）**：

8. **如果确需多写者**：使用 PostgreSQL/TimescaleDB 替代 DuckDB 的盘中写入角色

## 三、同类量化项目实时数据架构调研

### 3.1 调研项目

| 项目 | 类型 | 主要数据获取方式 |
|:-----|:-----|:----------------|
| **VNPY** | Python CTA 交易框架 | 事件驱动引擎，CTP API 直连（WebSocket），自定义数据源 |
| **Microsoft Qlib** | AI 量化研究平台 | 离线本地数据（类 daily 级别），**无实时** |
| **Backtrader** | 回测框架 | Data Feed 抽象层，支持实时 Live Feed（IB, OANDA） |
| **FreqTrade** | 加密币交易机器人 | REST API 轮询 + WebSocket（交易所原生），SQLite 存储 |
| **JoinQuant (聚宽)** | 在线量化平台 | 远程 API（HTTP），本地/云端双存储 |
| **Zipline** | 回测引擎 | Bundle ingestion（离线），无盘中实时 |
| **掘金量化** | 本地量化终端 | C++ SDK WebSocket 直连交易所，本地 MongoDB |
| **RiceQuant (米筐)** | 在线量化平台 | 远程 API + 本地缓存 |

### 3.2 实时数据获取模式

| 模式 | 代表项目 | 适用场景 | 延迟 | 优缺点 |
|:-----|:---------|:---------|:-----|:-------|
| **WebSocket 订阅** | VNPY/掘金/FreqTrade | L2 实时逐笔 | <1s | 最优，但需要券商/交易所接口 |
| **REST 轮询** | FreqTrade(降级) | 轻量级盘口 | 1-15s | 实现简单，延迟可接受 |
| **采集器拉取** | 本系统 (AkshareCollector) | 免费数据源 | 15s-30s | 成本低，无硬件要求 |
| **远程 API 调用** | JoinQuant/Tushare Pro | 盘后/分钟 | T+1/分钟级 | 依赖第三方稳定性 |

**关键发现**：
- **纯离线回测框架**（Qlib/Zipline/Backtrader）都**不处理盘中实时数据**，它们的设计假设是"数据已存在"
- **真正的量化交易系统**（VNPY/掘金）都使用**事件驱动架构 + WebSocket 直连**，数据不经过 REST API 层
- **加密币项目**（FreqTrade）天然 WebSocket 友好，交易所原生支持
- **A 股免费方案**（AKShare/东方财富）只能通过 HTTP 拉取，WebSocket 通道不公开

### 3.3 数据管理模式

| 项目 | 盘中存储 | 盘后存储 | 特点 |
|:-----|:---------|:---------|:-----|
| **VNPY** | 内存 KLine 缓存 | MongoDB / SQLite | 事件驱动，Tick → Bar 聚合 |
| **FreqTrade** | 内存 DataFrame | SQLite | 数据库极简，ORM 层 |
| **掘金量化** | 内存 | MongoDB + 本地文件 | 分库分表，Tick 级存储 |
| **JoinQuant** | 远程缓存 | 云端数据库 | 用户无感知 |
| **本系统 (当前)** | InMemoryStateStore | DuckDB | 分层正确，集成未完成 |

**业界共识**：
- **盘中实时数据原则上只存内存不落盘**——Tick/秒级变化频繁落盘反成性能瓶颈
- **日终数据批量写入归档库**——一次写入大量行，分析型 DB 效率高
- InMemoryStateStore 的设计方向正确，VNPY 也使用类似的内存 KLine 缓存

### 3.4 前后端实时刷新机制

| 项目 | 推送方式 | 前端框架 | 特点 |
|:-----|:---------|:---------|:-----|
| **FreqTrade** | REST 轮询 (5s) | Vue.js | 简单，延迟可接受 |
| **VNPY** | WebSocket | PyQt/React | 原生桌面应用，RPC Push 广播 |
| **掘金量化** | WebSocket | React | C++ SDK → WS → 前端 |
| **JoinQuant** | REST + SSE | React | 混合模式 |
| **OpenAlgo** | SocketIO + REST 5s 降级 | React | 引用计数管理单 WS 连接，3次失败后降级 |
| **Homalos** | SSE + WS 混合 | React | SSE 流式日志(CPU <1%)，WS 账户/仓位(5s) |
| **ai-hedge-fund** | StreamingResponse (ReadableStream) | React | NodeContext 状态机 |
| **本系统 (当前)** | SocketIO WS + REST 降级 | Vue.js | 架构正确，前端未实际对接 |

**关键业界模式——20秒陈旧检测**：每个 Widget 维护 `lastUpdate` 时间戳，每 1-2s 检查一次。若 `Date.now() - lastUpdate > 20000` 则标记为陈旧——变灰、冻结动画、阻止操作。这是防止"连接正常但数据不流动"假象的关键手段。

**可见性感知连接管理**：`document.hidden` / `visibilitychange` 事件触发：
- 标签页隐藏时暂停 WS 连接（减少资源浪费）
- 恢复时自动重连 + 快速填充
- Homalos 实测 CPU 从 2-5% 降至 <1%

**实时刷新最佳实践**：

```
后端                             前端
─────────────────────────────────────────────────────
采集器/数据源                     useRealtimeData composable
   │                                    │
   ▼                                    ▼
内存状态 ← 写入                WebSocket on('market:summary')
   │                                    │
   ▼                                    ▼
WsBridge ──→ socketio.emit    watch → 增量更新 DOM
   │                                    │
   ▼                                    ▼
(降级) REST API               setInterval → REST fallback
```

本系统当前架构完全符合这一最佳实践，只是**两端未实际联通**：
- 采集器未启动 → InMemoryStateStore 为空 → WsBridge 无数据可推
- 前端 `useRealtimeData.js` 存在但 `dashboard.html` 未引用

### 3.5 可借鉴的经验

#### 正面模式

1. **事件驱动总线**（VNPY EventEngine）：数据、订单、状态都通过统一事件总线分发，松耦合
2. **Store-Data 分离**（Backtrader）：连接管理(Store) 和数据生成(DataFeed) 责任分离
3. **同一代码跑回测和实盘**（QuantConnect, Backtrader）：只需换 DataFeed 源，回测代码直接上实盘
4. **数据分层铁律**：盘中只操作内存，盘后才落盘——VNPY/掘金全员遵循
5. **多层 TTL 缓存**（FreqTrade）：不同类型数据用不同 TTL（tickers 10min, OHLCV 持久），平衡新鲜度和 API 效率
6. **降级透明度**：FreqTrade 的 REST 降级对前端完全透明，用户无感知
7. **自动重连 + 断线回填**（VNpy, FreqTrade, Backtrader）：断线后自动恢复并补缺
8. **Tick→Bar 聚合**：VNPY 的内存聚合器（1min/5min K线实时合成），比本系统更精细
9. **可见性感知连接**（Homalos）：标签页隐藏时暂停 WS 连接，恢复时重置；实测 CPU 从 2-5% 降至 <1%
10. **20 秒陈旧检测**：每个 Widget 维护 `lastUpdate`，超 20s 标记为陈旧——变灰、冻结动画、阻止操作
11. **全链路健康检查**（掘金量化）：数据源→内存→推送→前端渲染，定期走通

#### 常见反模式（避免踩坑）

1. **数据污染**：上游变化值不可成交时未做掩码处理，导致指标失真。Factor ML 未对价格变动设可交易掩码 → IC 虚增 18%、实盘 Sharpe 下降 0.44
2. **Fail-open 安全检查**：配置获取失败后降级为"允许全部"→ 安全机制形同虚设。本系统当前健康检查也是伪实现
3. **NaN 传播**：MACD 返回 NaN 而非 None → 悄悄破坏下游计算。本系统存在类似问题（Tushare 空回返回后处理不当）
4. **阻塞 I/O 混入异步循环**：同步 HTTP 调用放在 async event loop 里，阻塞所有协程
5. **冗余计算**：每轮全量重算 O(n²) 指标——应考虑增量计算

## 五、结论

### Q1: AKShare 是否最优？

**当前使用方式合理但不完整**。分层架构（Collector→InMemoryStateStore→WsBridge）设计正确，但与 Tushare 的分工策略也正确（盘中 AKShare、盘后 Tushare）。关键是**采集器未启动**导致整套管道空转，另外健康检查是伪实现，无法发现真实的网络问题。

### Q2: DuckDB 是否不适配？

**DuckDB 作为盘后归档库完全适配**，但**当前不是 DuckDB 的问题，而是集成方式的问题**：
- 双库路径导致数据不一致
- corrupted 文件无限膨胀是错误恢复逻辑缺陷
- 热重载和 DuckDB 单写者模式冲突

不需要换数据库，需要在**现有分层架构上修正集成缺陷**。真正需要的是**启动前锁清理 + 重试 + corrupted 文件上限 + 修复默认路径**。

### Q3: 业界怎么做的？

业界量化系统（VNPY、掘金、FreqTrade）与本系统的架构设计**高度一致**：
- 盘中：**InMemory + WebSocket 推送**
- 盘后：**归档数据库批量写入**
- 降级：**REST API 轮询作为保底**

本系统的方向完全正确，只是**管道的两端没有联通**——采集器未启动、前端未对接。不是一个架构问题，而是一个**集成遗漏**问题。
