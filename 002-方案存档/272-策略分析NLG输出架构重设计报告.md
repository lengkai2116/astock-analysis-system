# 策略分析 NLG 输出架构重设计报告（修订版 v2）

> **修订说明**：本版 v2 是基于 LLM Wiki 桌面 App 真实检索结果对 272 方案进行的全面补充和修正。关键变化：(1) 废弃"定调句"设计，改为完整的九层股票现状描述框架；(2) 补充量价形态系统可提供的具体命名形态；(3) 增加资金博弈与收益驱动两维度的系统数据可行性评估；(4) 新增"股票现状描述规范"概念文件的定义。

---

## 1. 背景与触发

### 1.1 触发事件

实测宏德股份(301163)和杭州园林(300649)的策略分析走势结构输出，发现 NLG 自然语言描述存在多处问题：

- **宏德股份**：输出"日线级别上升趋势、强劲，下降笔延续中"（趋势方向矛盾）、同时展示两个中枢均标"daily"（无法区分）、支撑距离百分比费解
- **杭州园林**：输出"买点:第三类买点(一类前)；卖点:第三类卖点(一类后)"（买卖点同时列出，时序不分）、中枢距当前+78.8%/43.0%（价格已大幅远离，历史中枢参考价值低）

### 1.2 修复过程回顾

前两轮修复集中在模板 NLG 的 patch 层面：

| 轮次 | 修复内容 | 文件 |
|------|---------|------|
| 第1轮 | 方向矛盾括号子句、中枢中文名、距离已跌破/已突破措辞、near_levels去重 | `trend_renderer.py`、`signal_computation_service.py` |
| 第2轮 | dict拷贝防污染、背驰方向严格判断、中枢时段展示、_dedupe倒序修正 | `strategy_analyze.py`、`trend_renderer.py`、`signal_computation_service.py` |

每轮修复都能解决具体问题，但模式暴露了**模板 NLG 的本质缺陷**：遇到一个新场景就需要改一次代码，永远修不完。

---

## 2. 问题诊断

### 2.1 核心矛盾

模板化 NLG（`trend_renderer.py`）试图用有限的分支逻辑穷举无限的市场状态。股市描述没有"标准文本"，同一只股票在震荡市和趋势市中的解读逻辑完全不同。每补一个分支，只是扩大了覆盖盲区，而不是解决了泛化问题。

### 2.2 三个具体病灶

| # | 问题 | 表现 | 根因 |
|---|------|------|------|
| 1 | **历史信号与当前状态混为一谈** | "买点:A；卖点:B"同时列出，先跌出三卖后涨出三买，三卖对当前决策已无用反而误导 | NLG 把"一段时段内发生过的全部事件"做平面的罗列，没有时序和有效性过滤 |
| 2 | **远期中枢与当前中枢同等展示** | 距当前78.8%的中枢与近期中枢并列，用户无法区分哪个是当前参考区间 | `near_levels` 的筛选逻辑缺失，历史中枢没有被降级 |
| 3 | **传递链信息层层丢失** | 策略原始数据 → NLG模板渲染(丢弃精度) → 拼接到prompt喂给DeepSeek(再理解一次) | 两道传递损失信息，DeepSeek 本可理解原始数据却被 NLG 碎片化文本限制 |

### 2.3 反复修 NLG 的原因

当前流程：

```
策略原始数据(结构化)
   ↓ ① 模板NLG渲染（trend_renderer.py, 200-400字中文文本）
中文文本
   ↓ ② 拼接到 prompt
DeepSeek → 解读已有文本（信息已丢失一层）
```

每次遇到新的输出场景 → 改 `trend_renderer.py` → 加分支 → 测试 → 下个场景又需要改。**维护成本随着分支数量线性增长。**

## 3. 整体架构评估

### 3.1 现有四个工作环节

| 环节 | 内容 | 当前状态 |
|------|------|---------|
| 环节1 | 多策略独立分析（缠论/量价/筹码/情绪/因子） | 各策略独立运行，输出结构化数据 |
| 环节2 | 现状描述整理 | **当前由NLG模板做→用户直接看**（问题最大） |
| 环节3 | DeepSeek + 知识库解读分析，给建议+风险提示 | 依赖环节2的NLG文本作为输入 |
| 环节4 | 实操建议 | 当前建议固定模板，几乎未变 |

### 3.2 现有五维框架的局限

现行五维（缠论/量价/筹码/情绪/因子）存在两个问题：

1. **假等权**：五个维度设计为并列，但实际大部分时候只有缠论和因子有输出，量价/筹码经常空
2. **孤立无关联**：五个维度各自输出，缺少"主趋势→当前状态→辅助验证"的层级关系

### 3.3 内嵌知识库体系（已在运行）

系统已有完善的**内嵌知识库**，不需要外接 LLM Wiki：

- 文件位置：`data/knowledge/concepts/`（30+ 概念 markdown 文件）
- 索引引擎：`KnowledgeReader`（SQLite FTS5，`knowledge_reader.py`）
- 已集成方：`deepseek_analysis_service.py`（`_build_knowledge_context`）、`ai_context_builder.py`（`LlmWikiMatcher`）、`strategy_ai_interpretation_service.py`（`_search_llm_wiki`）

生产环节**不需要**依赖外部 LLM Wiki 桌面 App。

## 4. 建议方案：结构化快照 + DeepSeek 合一处理

### 4.1 改动后的数据流（v2修订版）

```
环节1(策略输出, 结构化数据)
     │
     ▼
环节2b: 结构化快照(JSON, 含: 趋势/中枢/笔/信号/量价/筹码/情绪/因子/资金)
     │
     ├──→ 环节2a(用户面完整现状描述, 由DeepSeek按九层框架生成)
     │    走势结构 + 筹码成本 + 价格位置 + 量价关系 + 资金博弈
     │    + 收益驱动 + 时间节奏 + 情绪周期 + 多因子评分 + 财务排雷
     │    （有数据则显，无数据不占位）
     │
     ├──→ 环节3(DeepSeek + 内嵌知识库, 分析解读)
     │    结合知识库概念, 给出分析+建议+风险提示
     │
     └──→ 环节4(实操建议, 由DeepSeek动态生成)
          条件化建议, 非固定模板
```

**核心变化**：
1. 不再用 `trend_renderer.py` 做模板拼接，而是把原始结构化 JSON 直接给 DeepSeek
2. 废弃 v1 版本的"一句话定调"设计（见4.2），改为完整的九层股票现状描述框架
3. 由模型同时产出面向用户的描述和分析解读

### 4.2 关于"定调句"设计的废弃说明

v1 版本（2026-07-15）中的"一句话定调"设计（§4.1：`一句话定调 + 当前价位 + 一个有效信号`）是 272 草案阶段为了简化完整描述而设计的过渡方案。在对接 LLM Wiki 知识库系统性梳理后，已由更完善的"股票现状描述规范"替代——即下面第7章定义的九层描述框架。

**废弃原因**：
- 定调句的本质是"完整描述的简化版"，而非独立输出物
- 用户需要的是完整的、多维交叉验证后的系统性描述，而非一句话概括
- DeepSeek 有能力直接理解完整数据生成完整描述，不需要先摘要再扩展的两步走

### 4.3 信息不再丢失

```
旧: 策略数据 → NLG模板(精度丢失) → DeepSeek(重新理解)
新: 策略数据 → 结构化JSON → DeepSeek(原始精度) + 知识库
```

DeepSeek 能看到完整的数据全貌（价格位置、中枢区间、买卖点时序、量价关系、资金数据），自己判断：
- 哪些信号是"历史发生过但已无效"的
- 哪些价位是"当前仍有参考意义"的
- 如何用自然语言把"当前状态"按规范框架说清楚

### 4.4 Token 消费评估

按 `deepseek-v4-flash` 模型估算：

| 项目 | 当前(模板NLG+DeepSeek) | 建议(结构化直给+九层规范) |
|------|----------------------|-------------------------|
| 输入(含知识库+规范) | ~2500 tokens | ~3500 tokens |
| 输出(完整描述+解读+建议) | ~400 tokens | ~800 tokens |
| 单次总消耗 | ~2900 tokens | ~4300 tokens |
| 增量 | — | +48% |
| 成本(¥1/百万输入) | ~¥0.0029/次 | ~¥0.0043/次 |

日均1000次分析成本约 ¥4.3，可接受。

### 4.5 风险应对

| 风险 | 应对 |
|------|------|
| 模型输出措辞不一致 | system prompt 给九层框架+各层描述示例，不需要逐字一致 |
| 推理延迟300-500ms | 可接受，策略分析非实时报价 |
| API 不可用无描述降级 | 保留极简规则fallback（结构+价位+信号） |
| 幻觉编造数据 | 结构化数据+system prompt约束只基于已有数据说话 |

## 5. 知识库驱动描述风格

当前描述规范写在 `trend_renderer.py` 的代码里，改风格就要改代码。

建议方向：将描述规范迁移到内嵌知识库的概念文件中（`data/knowledge/concepts/`），注入 system prompt 让 DeepSeek 遵循：

```
data/knowledge/concepts/
 ├── 股票现状描述规范.md    ← 本文件定义输出框架（九层描述规范）
 ├── 走势结构描述规范.md   ← 级别/中枢/背驰的描述规则
 ├── 量价关系描述规范.md   ← 量价形态命名+量价关系的自然语言描述
 ├── 筹码资金描述规范.md   ← 筹码分布+资金博弈的描述规则
 ├── 策略建议模板.md       ← 建议的输出格式和约束
 └── ...                  ← 已有30+概念文件
```

这样调整描述风格时，**改 wiki 一篇文章即可，不碰 Python 代码**。"规范即配置"。

## 7. 股票现状描述框架（LLM Wiki 知识库综合产出）

> 以下框架来源于对 LLM Wiki 桌面 App "A股研究"项目中概念文件的系统性检索与综合。核心来源包括：
> - `wiki/concepts/多维度股票现状分析.md` — 七步分析法
> - `wiki/concepts/三层分析框架（走势结构）.md` — 结构确认→位置定位→时间研判
> - `wiki/sources/要系统性地判断一只股票的走势结构...md` — 系统化判断源文档
> - `wiki/sources/think我们被问到两个问题...md` — 五维特征与七步法源文档
> - `wiki/sources/research--2026-06-04.md` — 量化策略全流程融合框架
> - `wiki/queries/research-457-2026-06-05.md` — 统一实战框架（UIDF）
> - `wiki/queries/research-463-2026-06-05.md` — 统一投资决策框架

### 7.1 总体框架

股票现状描述应按以下**三层输出结构**组织，从环境到个体再到验证，层次清晰、主次分明：

```
┌────────────────────────────────────────────────────┐
│    第一层：环境定位                                 │
│    大盘状态 · 板块定位 · 个股相对强弱               │
├────────────────────────────────────────────────────┤
│    第二层：个股全息（核心）                          │
│    ┌─ 走势结构 —— 级别/中枢/背驰/买卖点            │
│    ├─ 筹码成本 —— 筹码峰/主力集中价/偏离度          │
│    ├─ 价格位置 —— 均线乖离/历史分位/支撑阻力        │
│    ├─ 量价关系 —— 成交量分位/近期变化/形态匹配      │
│    ├─ 资金博弈 —— 主导资金/龙虎榜/融资数据          │
│    ├─ 收益驱动 —— 极端收益占比/驱动力定性           │
│    └─ 时间节奏 —— 持续时长/变盘窗口/级别跨度经验    │
├────────────────────────────────────────────────────┤
│    第三层：辅助验证                                 │
│    情绪周期阶段 · 多因子评分 · 财务排雷结论          │
└────────────────────────────────────────────────────┘
```

**核心原则**：
- **结构先行，位置确认，时间验证**（引自 `wiki/concepts/三层分析框架（走势结构）.md`）
- **有数据则显，无数据不占位**（消除假等权）
- **时序过滤**：只展示当前有效的信号，历史信号降级或省略

### 7.2 第一层：环境定位

| 子项 | 数据来源 | 系统支持状态 |
|------|---------|-------------|
| **大盘状态** | 大盘指数(沪深300/上证)趋势方向+阶段 | ⚠️ 需大盘分析数据 |
| **板块定位** | 个股所属板块当前主线/冷门+轮动阶段 | ⚠️ 板块数据来自概念板块缓存(concept_cache) |
| **个股相对强弱** | RPS相对强弱指标/近20/60日跑赢大盘幅度 | ✅ 已在`screener_strategy_integration.py`中有因子计算 |

**有数据则显**：大盘数据可用时才输出首句。示例：
> "上证处于日线级别震荡整理。该股所属半导体板块为当前主线（板块指数+8.2%），个股近20日跑赢大盘4.3%，板块内强度排名前15%。"

### 7.3 第二层-①：走势结构

**核心工具**：缠论级别递归 + 经典形态学

#### 缠论三要素（LLM Wiki概念页核心定义）

| 要素 | 分析内容 | 描述意义 |
|------|---------|---------|
| **级别** | 从周线向下逐级确定当前最高级别中枢 | 界定该股走势的"规模"——是日线级别调整还是周线级别反转 |
| **中枢** | 中枢区间[下沿,上沿]及价格相对位置 | 精确描述"价格处于中枢内还是中枢外" |
| **背驰** | 比较当前段与前一段的力度（MACD面积/高度） | 判断当前趋势是否衰竭，是否临近转折 |

#### 系统数据支持状态

| 状态 | 说明 |
|------|------|
| ✅ **级别** | `MultiLevelChanlunAnalyzer` 支持周线/日线/60分钟多级别递归 |
| ✅ **中枢** | `Zhongshu` 类含 level/duration/low/high 字段，`near_levels` 列表携带全级别中枢 |
| ✅ **背驰** | `DivergenceDetector` 支持7种 macd_algo，含力度比较 |

**描述示例**：
> "该股处于日线级别下降趋势末端，已在60分钟级别形成底背驰，但周线中枢下沿未有效突破，属底部反转初期的结构形态。"

### 7.4 第二层-②：筹码成本

**核心工具**：筹码分布分析、主力集中价

| 指标 | 数据来源 | 系统支持状态 |
|------|---------|-------------|
| **筹码主峰位置** | `ChipDistributionService` 返回 chip_bins + chip_peak | ✅ 已在 pipeline 中有完整实现 |
| **主力集中价** | `_calc_main_force_cost()` 从 moneyflow_cache 计算 | ⚠️ 方法已实现但 `_compute_chip_signal()` 未调用（见 MEMORY §168） |
| **当前价偏离度** | 当前价 vs 主力集中价 | ⚠️ 同上，需修复调用链路 |
| **ASR指标** | 筹码分布中的浮筹比例 | ✅ 已在 chip_strategy_impl.py 中有计算 |
| **融资成本价** | margin_cache 数据 | ✅ margin_cache 已存储，但融资成本价计算未实现 |

**描述示例**：
> "当前价格处于筹码主峰下方且远离主力集中价，偏离-7.7%，主力处于浮亏状态。上方套牢盘密集，需长时间横盘才能消化。"

### 7.5 第二层-③：价格位置

**核心工具**：均线系统、技术指标、支撑阻力位

| 指标 | 数据来源 | 系统支持状态 |
|------|---------|-------------|
| **均线排列** | 5/10/20/60日均线关系 | ✅ `volume_price_strategy.py` 含 _is_ma_tuo_pailie 等方法 |
| **乖离率** | 价格与均线偏离百分比 | ⚠️ 可计算但未提取为独立描述字段 |
| **历史分位** | 近250日价格百分位 | ⚠️ 未实现 |
| **支撑/阻力** | 中枢边界、筹码峰、前高前低、趋势线 | ✅ `near_levels` 已在缠论输出中，需扩展更多来源 |
| **BOLL位置** | 价格相对上下轨位置 | ⚠️ 系统有BOLL指标计算但未输出为描述字段 |

**描述示例**：
> "收盘价22.34跌破20日均线(-4.8%)，接近60日线(21.80)支撑。处于近250日价格区间25%分位（低位区域）。5/10/20日均线已形成空头排列。"

### 7.6 第二层-④：量价关系（LLM Wiki 知识库综合研究）

**C1：主力集中价 vs 融资成本价 "夹层区间"**

知识库定义了两个关键价位之间的博弈区间：

| 价格位置关系 | 含义 | 操作意义 |
|-------------|------|---------|
| 股价 < 两者（均低于） | 主力与散户均亏损 | 绝对低位，但需等待主力自救信号 |
| **主力集中价 < 股价 < 融资成本价** | **主力盈利，散户被套** | **最佳做多区间**——主力有动力拉升到融资成本价去"解放"散户套牢盘 |
| 两者 < 股价 | 主力与散户均盈利 | 需警惕主力出货动机 |

当前系统已计算 `distance_pct`（当前价 vs 主力集中价），只需补充融资成本价估算（基于 `margin_cache`），即可生成这个"夹层区间"判断。

**C2：散户反向指标（大小单对比）**

当前 `moneyflow_cache` 已有 `net_sm_amount`（小单净额，代表散户资金）和 `net_lg_amount + net_elg_amount`（大单+超大单净额，代表主力资金）。两者**从未关联分析**。

应补充的关联判断逻辑：

| net_sm（散户） | net_lg+elg（主力） | 含义 |
|---------------|-------------------|------|
| 净流出 | 净流入 | 💚 **健康**——散户卖主力买，筹码在集中 |
| 净流入 | 净流出 | ❤️ **危险**——主力在出货给散户 |
| 净流入 | 净流入 | ⚠️ **过热**——一致性做多，需警惕见顶 |
| 净流出 | 净流出 | ⚠️ **恐慌**——都在跑，需等待企稳 |

**C3：情绪拥挤度因子**

定义：`融资余额增长率 - 股价涨幅`。正值且过大=情绪过热危险信号。

数据完全就绪（`margin_cache` + 日K线），实现方式：
1. 计算近N日融资余额增长率（如5日/20日）
2. 计算同期股价涨幅
3. 两者之差 > 阈值 → 标记为"情绪拥挤"
4. 可在量价描述和信息输出中附加"资金结构预警"

**C4：主力操盘阶段→量价策略权重联动**

将 `chip_strategy` 的 `phase_info`（建仓/洗盘/拉升/出货）作为量价描述的状态过滤器：

| 主力阶段 | 量价特征 | 对量价描述的影响 |
|---------|---------|----------------|
| 建仓 | 价平量增，底部放量 | 预涨形态置信度上调 |
| 洗盘 | 价跌量减，缩量回调 | 关注缩量止跌信号 |
| 拉升 | 价涨量增，放量突破 | 趋势类信号优先输出 |
| 出货 | 价涨量减/放量滞涨 | 预跌形态置信度上调 |

实现方式：在 `VolumePriceRelationResult` 的 `resonance_score` 计算中加入 `phase_info` 权重因子。

## 9. 与现有系统架构的关系

### 9.1 对现有NLG的影响

本方案**不是完全废弃 NLG**，而是改变 NLG 的定位：

| 现有 | 新定位 |
|------|--------|
| `trend_renderer.py` 作为用户可见的最终输出 | 降级为 **fallback 渲染器**（DeepSeek 不可用时使用） |
| 渲染器试图穷举所有场景 | 保留最简单的分支（结构+价位+信号三要素） |
| 所有维度都用模板渲染 | 只保留走势结构维度的 fallback，其他维度跳过 |

### 9.2 对结构化快照Schema的要求

传递给 DeepSeek 的 JSON 快照必须包含：

##### 1.2 System Prompt 结构

分为三段：角色定义 + 数据说明 + 输出约束

```
【角色定义】
你是一名A股技术分析师。你的任务是基于提供的结构化数据，按九层框架
生成这只股票的现状描述。你的输出将直接展示给用户，请用专业、清晰、
客观的中文撰写。

【数据说明】
以下数据是系统实测的结构化快照，格式为JSON。每个字段含义：
- environment: 大盘环境（大盘趋势/板块强度/个股相对强弱）
- structure: 走势结构（缠论级别/中枢区间/背驰/买卖点）
- chip: 筹码分布（筹码峰/主力集中价/ASR/偏离度）
- price: 价格位置（均线排列/乖离率/历史分位/支撑阻力）
- volume_price: 量价关系（八种基本形态/确认或异常/命名形态）
- capital: 资金博弈（大单净额/龙虎榜/换手率/主力阶段）
- sentiment: 情绪周期（BOCIASI快慢线信号/四阶段）
- time_rhythm: 时间节奏（中枢持续时间/级别上限/变盘条件）
- risk: 风险底线（财务检查/仓位参考）
数据中有 null 的字段表示该维度数据暂不可用，请跳过不写。

【九层描述输出规范】
请按以下顺序和格式输出（有数据的维度写，无数据的维度跳过）：

1.【环境定位】一句话描述大盘趋势、板块位置、个股相对强弱（如有）。
2.【走势结构】什么级别什么趋势，价格在中枢什么位置，是否背驰。
   例："处于日线级别上升趋势，当前笔向下延续。价格位于最近日线中枢
       (26.21-31.98)下方(-15.1%)。周线无背驰，中期趋势尚未衰竭。"
3.【筹码成本】（如有数据）筹码主峰位置，主力集中价，当前偏离度。
4.【价格位置】均线排列状态、乖离率、历史分位、关键支撑阻力。
5.【量价关系】（如有数据）当前量价形态、成交量变化趋势、确认或异常。
6.【资金博弈】（如有数据）大单净额方向、龙虎榜机构情况、换手率。
   例："近5日大单净流入+1.2亿，机构席位净买入2300万，换手率3.2%
       处于历史中位，资金结构健康。"
7.【情绪周期】（如有数据）市场所处情绪阶段。
8.【时间节奏】（如有数据）当前状态持续时间、变盘条件是否成熟。
9.【风险底线】（如有数据）排雷结果、仓位参考。

【格式约束】
- 用客观事实描述，每一句都有数据支撑
- 先事实后判断，先主要后次要
- 有数据则写，无数据跳过，不要编造
- 遇到矛盾信号（如买点与卖点同时存在），说明矛盾原因而非隐藏
- 不预测未来，只描述现状
```

#### G2 解决方案：Fallback 策略具体设计

##### 2.1 Fallback 触发条件

| 条件 | 处理 |
|------|------|
| DeepSeek API 返回错误/超时 | 立即 fallback |
| API Key 未配置 | 永久 fallback |
| 网络不可达 | 立即 fallback |
| 返回内容解析失败 | 重试1次后 fallback |

##### 2.2 Fallback 输出格式

仅走势结构三维度，其余维度不输出。直接从 `status_recognition` 读取：

```
{级别}趋势{方向}，价格处于中枢{上/下/内}方。
{买卖点信号}。{当前笔状态}。
```

生成逻辑（不依赖 NLG renderer，直接从结构化字段拼接）：

```python
def fallback_description(sr: dict) -> str:
    """当DeepSeek不可用时，从 status_recognition 生成简略描述"""
    trend = sr.get('trend', {})
    level = trend.get('stage', '--').replace('日线', '日线级别').replace('30min', '30分钟级别')
    direction = {'up': '上升', 'down': '下降', '': '震荡'}.get(trend.get('direction', ''), '震荡')
    pos = sr.get('position_vs_zs', '未知')
    bp = sr.get('buy_sell_point', {})
    buys = bp.get('buy', [])
    sells = bp.get('sell', [])
    signal = ''
    if buys:
        signal = f'买点:{",".join(buys[:1])}'  # 只取最新一个
    elif sells:
        signal = f'卖点:{",".join(sells[:1])}'
    return f'{level}{direction}趋势，价格处于中枢{pos}方。{signal}。' if signal else \
           f'{level}{direction}趋势，价格处于中枢{pos}方。'
```

**输出示例**：
> "日线级别上升趋势，价格处于中枢上方。买点:第三类买点。"

##### 2.3 与现有 NLG renderer 的关系

| | 现有 NLG (trend_renderer.py) | 新 Fallback |
|--|------------------------------|-------------|
| 覆盖维度 | 缠论+量价+筹码+情绪 | 仅缠论（走势结构） |
| 代码量 | ~300 行复杂分支 | ~20 行拼接逻辑 |
| 维护成本 | 每个新场景需加分支 | 固定不变 |
| 何时使用 | **计划完全废弃** | 仅 DeepSeek 不可用时 |

**实施路径**：不修改现有 `trend_renderer.py`，在新代码中直接实现 `fallback_description()`。待 DeepSeek 链路稳定运行一段时间后，再清理 `trend_renderer.py`。

### 10.2 进一步提升 DeepSeek 分析输出的关键措施

当前 DeepSeek 分析存在三个可优化的结构性问题：

#### 10.2.1 数据输入：从文本片段升级为结构化 JSON

**现状**：`ai_context_builder.build_context()` 返回的上下文极其薄弱（股票名、行业、大盘环境三行文本）。

**改进**：将 `build_context()` 的输出升级为完整的结构化快照 JSON（§9.2 Schema），包括所有 10 个维度。这样 DeepSeek 看到的是结构化的全量数据，而非碎片化文本。

#### 10.2.2 Prompt 设计：从角色分立升级为统一框架

**现状**：6 角色并行分析（技术/基本面/筹码/情绪/消息/风控），每个角色收到不同的 role_prompt，输出不同格式的分析报告。存在三个问题：

1. **角色间信息孤岛**——技术分析师不知道筹码数据，情绪分析师不知道基本面数据
2. **输出碎片化**——6 段独立的分析报告，缺少统一的"这只股票当前是什么状态"的结论
3. **Token 浪费**——每个角色都重复接收基本信息（股票代码、日期等）

**改进建议**：

将 6 角色分析改为 `1 + N` 模式：

```
主分析（1个）: 按九层框架输出完整现状描述（统一输出）
  + 
专项分析（N个，可选）: 在完整描述基础上，按需补充特定角色的深度解读
```

主分析的 system prompt 直接嵌入九层框架模板：

```
请你按以下九层框架描述这只股票的现状：
（有数据则写，无数据跳过，不要编造）

1.【环境定位】大盘趋势/板块定位/个股相对强弱
2.【走势结构】级别/中枢/背驰/买卖点
3.【筹码成本】筹码峰/主力成本/偏离度
4.【价格位置】均线排列/乖离率/历史分位/支撑阻力
5.【量价关系】八种基本形态/确认或异常/具体形态
6.【资金博弈】主力资金方向/游资机构识别/换手率
7.【情绪周期】四阶段定位/快慢线状态
8.【时间节奏】持续时长/变盘条件
9.【风险底线】排雷结果/仓位建议/止损参考
```

#### 10.2.3 知识库注入：从固定概念升级为状态驱动

**现状**：`knowledge_reader.py` 有概念索引但未在 DeepSeek 分析中被系统性地使用。

**改进**：根据股票的当前状态（如"正在背驰段"或"底部放量"），自动检索 `data/knowledge/concepts/` 中相关的概念说明，注入到 system prompt 中。例如：


#### 10.3.2 关键发现：`status_recognition` 是核心数据契约

**`status_recognition` 字典被 6 个不同模块同时消费**，是策略层与展示层/分析层之间的唯一数据契约。任何对该字典结构的修改都会波纹式影响所有下游。

#### 10.3.3 逐模块影响评估

| 模块 | 当前消费方式 | 272 方案影响 | 风险等级 |
|------|------------|-------------|---------|
| **`strategy_analyze.py`** | 读取 `status_recognition.trend.*` 构建 dimension；`status_text` 作为前端直接展示 | **影响较大**。`status_text` 将被 DeepSeek 生成文本替代，但 dimension 结构不变 | 🟡 中 |
| **`screener_strategy_integration.py`** | 读取 `signal_output.status_recognition` 用于评分/分级算法 | **基本无影响**。screener 不依赖 `status_text`，只依赖结构化字段 | 🟢 低 |
| **`status_output_service.py`** | 读取 `status_recognition.state/trend/momentum` 等聚合 | **基本无影响**。聚合逻辑只依赖结构化字段 | 🟢 低 |
| **`deepseek_analysis_service.py`** | 通过 `ai_context_builder.build_context()` 获取简单行情 | **影响较大**。需要大幅扩展 `build_context()` 输出完整结构化快照 | 🟡 中 |
| **NLG renderers** | 读取 `status_recognition.trend.*` 生成中文文本 | **影响较大**。从主要输出降级为 fallback | 🟠 较大 |
| **`StrategyOutput` 持久化** | 存储 `status_recognition` JSON | **基本无影响**。存储格式不变 | 🟢 低 |

**核心结论：272 方案对现有系统的侵入性很低。** 原因是：

1. 方案改动的是**输出层**（如何展示描述），而非**计算层**（如何计算信号）
2. `status_recognition` 结构不变，所有已有消费者不受影响
3. 新增加的 DeepSeek 分析是**旁路**而非**替代**——现有 `status_text` 流可以保留直到新链路成熟
4. **只有在 DeepSeek 完全稳定后**才逐步切换前端展示，在此之前 NLG 渲染器作为 fallback 继续运行

#### 10.3.4 选股系统特别评估

选股流水线架构（`screener.py`）：

```
L1: DarwinRiskFilter（风险剔除）
    └── 不依赖 status_recognition
L2: MainForceScorer（筹码/主力评分）
    └── 从 moneyflow_cache + daily_cache 独立计算
        └── 输出 phase → status_recognition 映射（chip_strategy.py:830）
L3: 多策略验证（缠论+量价+因子）
    └── 读取 signal_output.status_recognition 但不依赖 status_text
L4: 综合评分与排序
    └── 使用 L2+L3 的评分合并
```

**选股系统完全不依赖 `status_text`**，它使用 `status_recognition` 内的结构化字段和独立计算的评分。因此 272 方案的改动（`status_text` → DeepSeek 生成）对选股系统的影响为 **零**。

#### 10.3.5 渐进切换路径

```
Phase 1（当前状态）: 
  status_text = NLG renderer（问题多，但功能完整）

Phase 2（并行运行）:
  status_text = NLG renderer（对外展示不变）
  + 后台实验: 结构化快照 → DeepSeek 生成九层描述（观察质量）

Phase 3（切换默认）:
  status_text = DeepSeek 生成文本（默认展示）
  NLG renderer 作为 fallback（DeepSeek 不可用时）

Phase 4（废弃）:
  确认 DeepSeek 稳定运行后，删除 trend_renderer.py 冗余分支
```

这个渐进路径确保**在任何阶段回滚都不会影响选股系统和个股策略分析的正常运行**。
