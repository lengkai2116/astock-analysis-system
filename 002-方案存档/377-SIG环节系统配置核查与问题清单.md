## 二、353号方案设计 vs 实际实现对比

### 2.1 环节定位

## 三、signal_json 内部结构问题

### 3.1 问题P1：存在空键名信号

**现象**：signal_json的signals字典中存在一个键名为空字符串`""`的信号：

```json
{
  "量价分析策略": {...},
  "筹码主力分析": {...},
  "BOCIASI快线": {...},
  "": {...}          ← 空键名，包含dim_results
}
```

**根因**：`compute_via_engines()`中dim1（Dim1SignalEngine）产出的信号 `strategy_name` 为空字符串。dim1代码路径：

```python
# signal_computation_service.py:96-104
signals.append({
    'strategy_name': '信号确认',  # 设计值
    ...
})
```

但dim1在部分股票上evaluate()返回的judgment中 `attribute.code` 为 `neutral`，导致跳过signals.append（L95条件不满足），而dim1的dim_results仍被写入dim_results字典。后续批量写入时，dim_results被错误地附加到一个空键名信号的 `raw_detail._dim_results` 中。

**影响**：
- signal_json中多一个空键名信号，消费方解析时可能异常
- dim_results在signal_json内部冗余存储（与dim_results_json列重复）

**修复方向**：dim1引擎在neutral时不产出信号（已正确），但dim_results不应嵌套到空键名信号中。需调整 `_precompute_strategy_signals` 中dim_results的组装逻辑。

### 3.2 问题P2：部分引擎信号缺失

**现象**：抽样000002.SZ的signals键：

| 引擎 | 是否产出 | 说明 |
|------|---------|------|
| 量价分析策略（Dim3VPEngine） | ✅ 有 | 正常 |
| 筹码主力分析（Dim4ChipFundEngine） | ✅ 有 | 正常 |
| BOCIASI快线（Dim5EmotionEngine） | ✅ 有 | 正常 |
| 缠论走势分析（Dim2StructureEngine） | ❌ **缺失** | evaluate()返回chanlun_direction='未知'，被L115条件过滤 |
| 信号确认（Dim1SignalEngine） | ⚠️ 以空键名存在 | attribute.code='neutral'，被L95条件过滤 |
| 风险警示（Dim6RiskEngine） | ❌ 缺失 | 仅level='高'/'极高'时产出，000002.SZ为'低'，正常不产出 |
| 因子引擎 | ❌ **完全未实现** | compute_via_engines中无factor引擎调用 |

**说明**：缠论引擎缺失是因为000002.SZ的缠论数据不足（chanlun_direction='未知'），被过滤是正确行为。但全市场统计需确认缠论引擎的实际产出率。

### 3.3 问题P3：status_recognition 全部为空

**现象**：所有引擎产出的信号中 `status_recognition` 字段为空字典 `{}`：

```json
{
  "strategy_name": "量价分析策略",
  "confidence": 0.62376,
  "status_recognition": {},  ← 空
  ...
}
```

**358号方案设计**：status_recognition应包含阶段/趋势/强度等结构化状态信息，供JUD消费。

**实际状态**：369号方案重构后，引擎输出改为 `status_description` + `judgment` + `audit` 三段结构，但signal_computation_service在组装信号时未将status_description写入status_recognition字段。

**影响**：
- 旧消费方（如策略分析页面的九维解读）读不到结构化状态
- 新消费方（JUD步骤）通过dim_results_json读取，不受影响

### 3.4 问题P4：dim_results_json 嵌套位置错误

**现象**：dim_results在两处存储：
1. **正确位置**：`strategy_signal_detail.dim_results_json` 列（独立JSON）
2. **冗余位置**：signal_json内部空键名信号的 `raw_detail._dim_results`

**根因**：`_precompute_strategy_signals` 中组装rows时，dim_results既写入了dim_results_json列（L4740），又被错误地附加到了某个信号的raw_detail中（可能是UnifiedStrategyCore的compute_batch内部逻辑）。

**影响**：数据冗余，signal_json体积膨胀（单只股票signal_json可达数十KB）。

## 七、确认的8维度架构（2026-08-29 用户确认）

### 7.1 架构定义

用户确认SIG环节的策略分析系统采用**8维度架构**：

| # | 维度名称 | 归属环节 | 引擎文件 | dim_results键名 | 产出位置 |
|---|---------|---------|---------|----------------|---------|
| 1 | 信号确认 | **JUD**（SIG预计算，JUD消费） | `dim1_signal_engine.py` | `signal` | dim_results_json |
| 2 | 结构位置 | SIG | `dim2_structure_engine.py` | `structure` | dim_results_json |
| 3 | 量价健康度 | SIG | `dim3_vp_engine.py` | `volume_price` | dim_results_json |
| 4 | 资金与筹码 | SIG | `dim4_chip_fund_engine.py` | `chip_fund` | dim_results_json |
| 5 | 情绪环境 | SIG | `dim5_emotion_engine.py` | `emotion` | dim_results_json |
| 6 | 风险边界状态 | SIG | `dim6_risk_engine.py` | `risk` | dim_results_json |
| 7 | 估值 | SIG | `dim7_valuation_engine.py` | `valuation` | dim_results_json |
| 8 | 状态总结 | SIG | `dim8_summary_engine.py` | `summary`（待定义） | dim_results_json（待实现） |

> **关键决策**：维度1（信号确认）的实际归属为JUD环节 — SIG预计算dim_results，JUD步骤消费dim_results中的信号确认数据进行最终判定。

### 7.2 数据流架构

```
SIG环节（_precompute_strategy_signals）
  │
  ├─ 维度2-7 引擎 evaluate() → dim_results  → 写入 dim_results_json
  ├─ 维度1 引擎 evaluate()  → dim_results  → 写入 dim_results_json（归属JUD消费）
  ├─ 维度8 引擎 evaluate()  → dim_results  → 写入 dim_results_json（待接入）
  ├─ 5引擎信号 → signal_json
  └─ generate_seven_dim_from_signals() → seven_dim_json（直透OUT）
          │
          ▼
JUD环节（_build_status_snapshot）
  │
  ├─ 读取 dim_results_json → 提取维度1（信号确认）进行最终判定
  ├─ 读取 dim_results_json → 提取维度2-7 辅助判定
  ├─ StatusEngine.evaluate(dim_results=cached) → dim_states
  └─ → 写入 status_snapshot
          │
          ▼
OUT环节 → treemap_snapshot / one_liner_detail → 前端消费
```

### 7.4 维度7（估值）现状详情

- **引擎文件**：`dim7_valuation_engine.py` 已存在
- **dim_results_json中已有数据**：抽样000001.SH/000002.SZ均包含完整valuation判定（valuation_level/fpe_percentile/pb_percentile/fina_health/potential_score等）
- **数据来源**：valuation数据由StatusEngine._build_dim_engine_results()中的独立逻辑产出，非通过compute_via_engines()调用Dim7ValuationEngine
- **接入方案**：将Dim7ValuationEngine加入compute_via_engines()的引擎调用链，替换当前的独立逻辑

### 7.5 维度8（状态总结）现状详情

- **引擎文件**：`dim8_summary_engine.py` 已存在
- **dim_results_json中无summary键**：当前无独立的状态总结产出
- **当前实现**：状态总结由StatusEngine.evaluate()内部完成（汇总前7维的灯色/方向/置信度），产出status_bar/consensus_rate/direction等字段
- **待定义**：summary维度的输入（前7维结果）、输出格式（灯色+一句话+证据）、与StatusEngine内部汇总的关系

### 10.6 执行原则（贯穿全流程）

| 原则 | 说明 |
|------|------|
| **现状描述≠信号判定** | SIG输出"这只股票现在的结构是什么样的"，判定结论在JUD环节 |
| **数据消费不自行计算** | 从RAW-1预计算表（indicator_ma/macd/other）读取，不自行计算MA/RSI/KDJ/MACD |
| **真实数据验证** | 每次修改必须用真实股票数据运行验证，禁止mock/模拟 |
| **serena MCP工具** | 代码修改必须通过serena工具真实执行，禁止简单/糊弄式实施 |
| **逐项核对** | 方案中的每个字段必须逐一对照代码确认实现，不允许"应该实现了" |
| **知识库对标** | 每个能力的规则必须有知识库理论依据支撑 |
| **用户参与合理性审核** | 输出规则是否符合A股实际运用场景，需用户确认 |
| **日期必须真实** | 所有文档的编制日期必须使用`date +%Y-%m-%d`获取的真实日期，禁止编造日期 |
| **同一编号不重复建文件** | 378号等统一编号文档只维护一个文件，新维度内容追加为新章节（如§三维度3），禁止创建`378-dim3.md`等分离文件 |
| **修改记录必须同步** | 每次代码修改后必须同步更新380号修改记录，不允许只改代码不更新记录 |
