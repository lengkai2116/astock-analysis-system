### 2.2 【P0，已铁证】RAW-1 MA 组"全有全无"守卫 → 116 支股票 MA 整组不写入（滞后 4~10 日）

**现象（数据实证，快照 20:04:09）**

| 指标 | 实测 |
|---|---|
| `indicator_ma` 总行数 | 6,415,515 |
| `indicator_macd` 总行数 | 6,416,164 |
| `indicator_other` 总行数 | 6,416,164 |
| `indicator_ma@09-11` | **5,388** |
| `indicator_macd@09-11` | **5,504** |
| `indicator_other@09-11` | 5,504 |
| `daily_cache@09-11`（锚 N） | 5,553 |

`daily_cache` 各股 K 线根数分布：**≥250 → 5412 支；120-249 → 72 支；60-119 → 44 支；<60 → 78 支（合计 5606 支）**。

对处于 **[60,249] 根区间的 116 支**（72+44）股票，其 `indicator_ma` 最新日期 vs `indicator_macd` 最新日期之差（julianday 实测）：

| 滞后天数 | 支数 |
|---|---|
| 4 天（ma 停在 09-07，macd 到 09-11） | 110 |
| 10 天 | 6 |

**根因（代码铁证）**

```
enhanced_cache_manager.py:1241
    ma_cols = {'trade_date','ma5','ma10','ma20','ma30','ma60','ma120','ma250','vol_ma5','vol_ma10'}
    if ma_cols.issubset(set(df.columns)):      # ← 全有全无
        self._insert_from_df('indicator_ma', ma_df)
```

```
app/indicators/__init__.py
    if len(result) >= 120: result['ma120'] = ...   # 仅 len>=120 才建列
    if len(result) >= 250: result['ma250'] = ...   # 仅 len>=250 才建列
```

`precompute_all_indicators` 的 df 来自 `engine.calculate_all_indicators(df)`，**未回填历史指标列**，因此当 `len(df)<250` 时 `df.columns` 不含 `ma250` → 守卫为假 → **MA 组整体不写**；而 `macd_cols`/`other_cols` 守卫通过 → macd/other 正常写。**同一 df、同一函数调用内，MA 被单独丢弃。**

**守卫行为实证**（实际执行引擎）：

| df 长度 | `ma_cols` 守卫 | `ma250` 是否在列 |
|---|---|---|
| 59 / 60 / 100 / **249** | **False** | 否 |
| 250 | True | 是 |

**即 `len=249` 也被判失败** —— 缺陷区间精确为 `[60, 249]`（daemon 放行阈值为 `len>=60`，见 `data_daemon.py:5439`）。

**为何这些股票"曾经有 MA 行"**：库中这 116 支确有 MA 行（`has_ma = 116/116`），但最新日期滞后。全仓库 `indicator_ma` 的写入点**仅两处**：生产路径 `cache_indicators_wide`（唯一）与一次性迁移脚本 `backend/scripts/migrate_indicator_to_wide.py`（其 `wide` DataFrame 含全部列 → 守卫通过）。故**现存 MA 行为迁移遗留，RAW-1 自守卫收紧以来从未为 <250 根股票写过 MA**。

**影响**：116 支股票（占全市场约 2.1%）的 MA5/MA10/MA20/MA30/MA60/BBI/ENE 等 **MA 系因子永久滞后 4~10 日**，且随日期推移持续扩大；下游任何取 `ma*` 的判定/回测均受影响。

## 8. 分库设计与存储管理复审（v1.3 补录）

> **来源**：本节为 §0.1 所引复审的完整论证，对应提问"结合此次核查，STG 的分库设计是否还存在问题？存储管理是否合理？"。
> **方法**：将 356 号设计文档与 `sharding_manager.py` / `init_sharding.py` / `enhanced_cache_manager.py` 实现逐条比对，并对 9 个 STG 库执行**只读** SQL 实测（快照 2026-09-11 20:04:09，daemon 运行态）。本节仅为论证补录，**未修改任何代码**。
> **总判**：分库**切分骨架**（按数据域分 6 库 + 总库）**合理**；但**落地为"半迁移"**——设计与实现系统性背离，并保留了会吞掉读写的空壳表。故结论为：**分库设计仍有问题，存储管理不合理**。

### 8.1 设计层面问题

#### 8.1.1 总库归属系统性背离设计（D4）

356 号 §2 定义**总库 = `system_cache.db`**（承载 stocks、pipeline_status、sync_requests、cache_metadata、concept_cache、lhb_cache、lhb_detail_cache、index_member_cache、sentiment_pool_cache 共 9 表）。实现却是：

| 维度 | 356 设计 | 实际实现 |
|---|---|---|
| 总库文件 | `system_cache.db`（9 表） | **`stock_cache.db`**（44 张用户表）——即 ECM 主库 `self.db_path` |
| `system_cache.db` | 总库本体 | 退化为**普通分库**，仅 4 表：`cache_metadata` 3 / `concept_cache` 5,568 / `index_member_cache` 10,450 / `lhb_cache` 964 |
| `stocks` | 在总库 | 实际在 **`data/app.db`**；STG 各库**均无** `stocks` 表 |
| `cache_metadata` | 单一权威于总库 | **双份且不一致**：`stock_cache.db` 29 行 / `system_cache.db` 3 行 |

→ 这是**结构层根因**：迁移把"应留总库的表"与"应迁分库的表"搅在一起，且总库本身换名，导致任何按 356 语义编写的读代码都读不到真数据。

#### 8.1.2 路由 API 的 `None` 二义性（D8，最深层结构缺陷）

`sharding_manager.get_db_for_table()` 的约定是"返回 `None` = 表留在总库"。但实现中 `None` 有两个**语义不同**的来源：

1. **显式登记为主库表**（`_table_to_db` 中值恰为 `None`，实测共 **9 项**）：`stocks`、`pipeline_status`、`sync_requests`、`lhb_detail_cache`、`sentiment_pool_cache`、`conditional_win_rate_cache`、`opportunity_advice_history`、`opportunity_library`、`opportunity_status_history`；
2. **完全未登记的表**（精确与前缀匹配均不命中 → 落到末行 `return None`）。

调用方**无法区分二者**，一律按"主库"处理。后果：

- `execute_insert` / `execute_batch_insert` / `create_table`：`if db_name is None: return` → **裸 return，无异常无日志**（静默丢写）；
- `execute_query`：返回 `[]`；`table_exists`：`False`；`get_table_row_count`：`0`（静默假值）；
- ECM 的 `_query_shard` / `_exec_shard`：`db_name` 为假值时**降级到 `self.conn`（总库）**，形成"静默落空读 / 落空写"。

> 实测**未登记**（`_table_to_db` 零命中）且实际有数据/有用途的表：`market_stats_cache`、`sector_heat_cache`、`pattern_score_cache`、`qa_audit_log`、`as_sector_ranking`、`as_market_snapshot`、`watchlist_status_diff`，以及测试垃圾表 `test_sharding`。其中 **`pattern_score_cache` 在 compute_cache.db 实有 11,071 行**，却因未登记而在 ECM 读路径降级总库——主库无此表 → **返回空的"活体静默空读"**（现网正在发生）。

#### 8.1.3 第 7 个库逃逸设计与路由（D5）

`market_snapshot.db`（`data/duckdb/`，1.1 MB，`as_market_snapshot` **5,211 行**）由 ECM `snapshot_conn` 直连，**既不在 356 六库设计，也不在 `_table_to_db`**。它比"总库换名"更彻底地脱离分库治理（无 PRAGMA 策略、无 WAL 监控、无质量规则）。故 STG 实际库数为 **9**（6 分库 + `stock_cache.db` 总库 + `system_cache.db` 次库 + `market_snapshot.db` 逃逸库），而非设计文档的"6 + 总库"。

#### 8.1.4 主库沦为"空壳回收站"（D4 证据）

`stock_cache.db` 快照：`sqlite_master` 中 **`type='table'` 共 45 条**（含内部表 `sqlite_sequence`；另有 85 条索引），即 **44 张用户表，其中 36 张 0 行**。非空仅 8 张：`sync_requests` 75,965 / `lhb_detail_cache` 4,704 / `pipeline_status` 210 / `sector_heat_cache` 66 / `cache_metadata` 29 / `qa_audit_log` 10 / `market_stats_cache` 4 / `sentiment_pool_cache` 2。

**关键危害**：迁移后的 market/compute 类源表**并未删除**（`daily_cache`、`daily_basic_cache`、`stk_limit_cache`、`margin_cache`、`indicator_ma/macd/other`、`factor_cache`、`pre_feat_cache`、`opportunity_tags_cache`、`win_rate_cache`、`adj_factor_cache`、`adj_factor_cache_2026` 等均以 **0 行空壳**留存，已逐一实测确认）。它们使"读错库"**不抛异常而返回空结果**，正是 **P0-1 假数据**的直因（§4.2）。

#### 8.1.5 大表拆分半成品 + 数据损坏（D3）

356 号 §4 要求对大表按"主键约束 + 年份/月份拆分 + 统一视图"处理。实际：

| 设计要求 | 实际实现 |
|---|---|
| `daily_cache` / `indicator_*` 按年拆分 | **未拆**（单表 641 万行） |
| `minute_kline_cache` 按月拆分 | **未拆**（单表 1,777 万行） |
| `adj_factor_cache` 拆 `adj_factor_cache_YYYY` | **已拆**（2001–2026 共 26 张年表） |
| 年表 `PRIMARY KEY (ts_code, trade_date)` | **无主键**（仅 2 个普通索引：`idx_*_date`、`idx_*_ts`） |
| `adj_factor REAL` | **`adj_factor TEXT`**（实测 `typeof='text'`） |
| `adj_factor_cache` 统一 UNION 视图 | **无**；仅有 `adj_factor_view`，其 DDL 为 `SELECT * FROM adj_factor_cache_2026`，**只覆盖 2026 单年** |
| 无重复 | **严重重复**：`adj_factor_cache_2026` 2,333,970 行 / 164,356 去重键 = **14.2×**（`2026-01-05`→`2026-09-10`）；对照 `adj_factor_cache_2025` 118,742/118,742（正常），可见 2026 为脏写 |

→ 拆分只做到"表名对了"，**约束、类型、视图、去重四项全缺**，且 2026 年表已被重复写入污染（存储浪费 14 倍，聚合口径会失真）。此外 `history_cache.db.adj_factor_cache`（5,559 行）与主库同名空壳（0 行）并存，同名/近名对象语义混乱。

#### 8.1.6 死表残留引用（并入 P2-1 / P1-2）

`init_sharding.SHARDING_CONFIG` 仍列 `chip_distribution_cache`（compute）与 `tag_history`（snapshot），但**两张表在全部 9 库中均不存在**（幻影表）；`backfill_all` 亦残留同名引用。

#### 8.1.7 设计文档与实现不自洽

356 号已把 `cache_metadata`、`lhb_detail_cache` 等划入"总库"，但实现未落实总库实体；§3.2.5 的 snapshot 索引要到 424 号才由 `_ensure_snapshot_indexes` 补齐；§3 的每库 PRAGMA（见 8.2.2）至今未实现。即：**设计是"目标态"，代码停在"过渡态"，而过渡态没有任何一致性守卫**。

### 8.2 存储管理层面问题

#### 8.2.1 保留期规则（规则10）基本未生效（D1）

原始层 `_run_data_cleanup()`（`data_daemon.py:5853`）调用 5 个 `clean_*`，但**路由不一致**：

| 清理方法 | 调用方式 | 目标表实际所在库 | 效果 |
|---|---|---|---|
| `clean_factor_cache` | **`_exec_shard('factor_cache', …)`** | compute_cache.db | ✅ **生效** |
| `clean_stk_limit_cache` | `_execute(…)` + `self.conn.commit()` | market_cache.db | ❌ 打在主库空壳 → **no-op** |
| `clean_fina_indicator_cache` | `_execute(…)` | financial_cache.db | ❌ **no-op** |
| `clean_minute_cache` | `_execute(…)` | market_cache.db | ❌ **no-op** |
| `clean_lhb_cache` | `_execute('lhb_cache'…)` + `_execute('lhb_detail_cache'…)` | `lhb_cache`→system_cache.db（主库为壳）；`lhb_detail_cache`→主库（真数据） | ⚠️ **半失效**：`lhb_cache` 打空、`lhb_detail_cache`"歪打正着"生效 |

根源是 `_execute()` 无表名参数、**恒定使用 `self.conn`（主库）**；而 5 个方法中只有 `clean_factor_cache` 用了会路由的 `_exec_shard()`。

实测后果（规则10 规定：日线 3 年 / 分钟 6 月 / 预计算 1 年 / 复权因子全年份）：

| 表 | 实测 | 规则 | 超出 |
|---|---|---|---|
| `minute_kline_cache` | 17,771,040 行，**2021-07-09 → 2026-09-11**（约 5 年 2 月） | 6 个月 | **约 10 倍** |
| `daily_cache` | 6,414,667 行，**2021-07-07 → 2026-09-11**（约 5 年 2 月） | 3 年 | 约 1.7 倍 |
| `fina_indicator_cache` | 22,407 行，2020-03-31 → 2026-06-30 | 规则未单列 | 长期未清 |

→ 保留期**形同虚设**，直接造成 market/compute 库持续膨胀。

#### 8.2.2 每库 PRAGMA 规则（规则14）未落地（D2，P1-4 根因）

356 号 §3 为每库设定不同缓存与日志上限（market 32MB cache + `journal_size_limit` 256MB、compute 16MB、其余 8MB、`busy_timeout` 多为 10s）。实际 `ShardingManager.get_connection()` **对所有分库统一**：

```
PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;
PRAGMA cache_size=-8192;          # 一律 8MB（market/compute 偏小）
PRAGMA busy_timeout=30000;        # 一律 30s（设计多为 10s）
# 未设 journal_size_limit → WAL 无上限
```

> **v1.5 修正**：总库 ECM 主连接**有** `journal_size_limit=1048576`（`enhanced_cache_manager.py:117`）；缺失的是**全部分库连接**（`ShardingManager.get_connection` + ECM 的 `compute_conn`/`snapshot_conn`/`read_conn`）——初稿"所有库统一无 journal_size_limit"应限定为分库范围。

→ 直接导致 **8.2.3 的 WAL 失控**：`journal_size_limit` 缺失使 WAL 可无限增长；`cache_size` 过小使大库（compute 9.3 GiB）频繁落盘。

#### 8.2.3 WAL 失控，且 checkpoint 只作用于主库

| 库 | 主文件 | WAL |
|---|---|---|
| `compute_cache.db` | 9.32 GiB | **5.66 GiB** |
| `market_cache.db` | 5.34 GiB | 50.7 MiB |
| `snapshot_cache.db` | 1.41 GiB | 0 |
| `history_cache.db` | 370.6 MiB | 39.9 MiB |
