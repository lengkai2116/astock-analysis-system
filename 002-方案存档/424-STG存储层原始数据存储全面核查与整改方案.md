# 424 — STG 存储层原始数据存储全面核查与整改方案

> **性质**：本方案为 **核查存档 + 整改实施计划**。核查部分（§1-§7）记录 2026-09-10 对存储层 STG 全部 COL 原始数据存储情况的只读核查结论；整改部分（§8）为后续实施的可行计划（本方案创建时**未修改任何代码**，仅存档核查报告）。

## 3. 问题 2：分库数据表不足——4 处实质缺口 + 2 处结构缺陷

### 3.1 margin_cache（融资融券）严重停更 ⛔ P0
- 数据停在 **08-26**（仅 08-21/08-26 两个交易日），09-09 当日 0 行，滞后 10 交易日。
- **根因（确定性 bug）**：`run_integrity_check` 中 `today = datetime.now().strftime('%Y%m%d')`（data_daemon.py:1366，如 `'20260910'`），传给 `_batch_margin_range(start_date, today)`（data_daemon.py:565-583）后 `_dt.strptime('20260910', '%Y-%m-%d')` 抛 `ValueError` → 外层 except 吞掉 → **范围补采每次触发但永不执行**。日志实证：09-10 09:01 起 13 次 `融资融券检查失败: time data '20260910' does not match format '%Y-%m-%d'`。
- 叠加：`_batch_margin`（data_daemon.py:533-562）非交易日降级读 `_ecm.conn` 主库 daily_cache（已分库→空）→ 降级失效；margin 不在管道 COL 步骤、不在 QA QUALITY_RULES 9 表内 → **停更无告警**。

### 3.2 win_rate_cache / conditional_win_rate_cache 从未落库

## 6. 问题 5：COL 入库合规与锁风险——合规达标，1 处 P0 锁风险

### 6.1 合规红线检查 ✅（总体达标）
采集主路径 `_insert_from_df`（ECM:184-277）统一按 `sharding_manager.get_db_for_table` 单写分库 + `INSERT OR REPLACE` 幂等 + 自动建表；分库连接 `journal_mode=WAL` / `synchronous=NORMAL` / **busy_timeout=30s** / 每分库独立 RLock 串行写（sharding_manager:110-113/155-202）；快照成品原子替换（新表+DROP+RENAME）；`request_data` 短连接 busy_timeout=2s 防阻塞。当前 daemon 日志 0 次 "database is locked"（旧 daemon.log 91 次均在 08-06 前，属历史）。

### 6.2 P0 锁风险：compute_cache.db-WAL 达 5.26GB，处于监控盲区 ⛔
- **WAL checkpoint 与大小监控只覆盖总库 stock_cache.db**：`_ecm.wal_checkpoint('PASSIVE')`（data_daemon:5802）与 423 B3 的 `sqlite3.connect(...duckdb/stock_cache.db)`（:5849）只处理总库；WAL 大小检测 `os.path.getsize(...stock_cache.db-wal)`（:5818）只统计总库。
- **sharding_manager 分库连接无任何 checkpoint 入口**；`wal_autocheckpoint=1000`（~4MB）本应自动收缩，5.26GB 说明存在长写事务/读连接持续阻止 checkpoint（RAW-1/3 批量写 indicator/factor 1044 万行场景）。
- 后果：读性能下降、占 5.26GB 磁盘、`wal_checkpoint(TRUNCATE)` 深收缩时短暂阻塞写；market_cache.db-wal 105MB、snapshot_cache.db-wal 145MB 同样不受管理。

### 6.3 其他隐患
- 双进程（daemon 21801 + API 22912）共享 8 分库，WAL 下并发靠 busy_timeout 兜底，无锁冲突记录但理论竞争存在；
- `_precompute_sector_heat`（data_daemon:2172-2197）裸连写库绕过 sharding_manager 网关（有意为之，属架构违规）；
- `_compute_volume_ratio`（data_daemon:260）主库 UPDATE daily_basic_cache → 分库权威副本更新不到；
- **`cache_pattern_score`（ECM:2585-2600）持有总库 `_write_lock` 去写 compute 分库**——跨库写共享同一把锁，存在串行阻塞（安全但降低并发，且该表不在 `_table_to_db` 映射致读回退主库，见 §2.1 E4）；
- DATA_DIR 路径分叉：ShardingManager 不读 `DATA_DIR`（固定 `__file__/../../../data`）、ECM 读 `DATA_DIR`——当前靠 daemon 硬编码一致，非 daemon 方式启动且设 DATA_DIR 到别处会拆目录。

**决策**：`chip_distribution_cache` **不接入缓存消费**。理由：
1. 聚合指标已由 SIG 预计算覆盖（RAW-2 → pre_feat_cache → dim1 → data_context → dim4），满足 dim4 主路径需求；
2. 完整分布（chip_bins，150 个 price_bin）仅在 chart.py `/chip-distribution/<ts_code>` 路由按需实时计算（用户查看图表时触发），属"策略核算按需触发"，符合 292 红线；
3. `chip_distribution_cache` 表 0 行、无生产调用方，是**死表**；`scripts/compute_chip_distribution.py` 是遗留脚本（用 `ecm.conn` 主库 + `DATABASE_URL=test.db`，与分库体系不符）。

**附带根治（重复计算）**：RAW-2 预计算（data_daemon:2723）调用 `MainForceScorer.get_sub_scores`，其内部 `_score_chip_distribution`（chip_strategy.py:915）**又实时调用 `ChipDistributionService.calculate_chip_distribution` 重新计算完整分布**——而 RAW-2 在 2732 行已用 `cde.estimate(df)` 算过一次 chip_bins。**同一只股票在 RAW-2 中完整分布被算两次**，全市场 5500 只 × 2 次，是显著重复计算/性能浪费。`_score_chip_distribution` 需要的 asr/ssrp/cyqkl 正是 `chip_fund_ext` 已预计算的聚合指标，应改为**消费 chip_fund_ext**（从 data_context 或 pre_feat_cache 读取），不再实时重算完整分布。

### 10.3 决策点③：finance_report/income 双写收敛方向 —— 保留分库权威，清理总库残留

**核查结论（2026-09-10 复核）**：这是**迁移复制残留，不是双写**。
- sharding 映射：`finance_report_cache` → **history_cache.db**，`income_cache` → **financial_cache.db**；
- 写入主路径 `_insert_from_df` 按映射**单写分库**，不存在同一数据同时写总库+分库的双写逻辑；
- 总库残留（finance_report 25,241 vs history 25,549 差 308 行；income 全量双份）是 **356 号分库迁移前的旧副本残留**，差异是迁移后分库继续更新、总库停更所致。

**决策**：收敛方向 = **保留分库权威**（`finance_report_cache` → history_cache.db；`income_cache` → financial_cache.db，与 sharding 映射一致），**清理总库残留**（归入 P0-3 Step B 残留清理：备份 → 删除 → VACUUM）。**无需改代码**（写入路径已单写分库），只需 grep 复核无读路径命中总库残留。

### 10.4 决策点④：`_batch_*` 是否接入数据源适配层 —— 一次性收敛到 TushareProvider

**核查结论（2026-09-10 复核）**：
- `_batch_*`（`_batch_finance_report`/`_batch_income_recent`/`_batch_balancesheet`/`_batch_cashflow`/`_batch_forecast`/`_batch_margin`）全部直接 `import tushare as ts; pro = ts.pro_api()` **原语调用**，未走 TushareProvider 适配层（424 §5.5）；
- **TushareProvider 已存在且方法完整**（tushare_provider.py）：`get_fina_indicator_extended`（对应 _batch_finance_report 的 FINA_FIELDS_EXTENDED）、`get_income`、`get_balancesheet`、`get_cashflow`、`get_forecast`、`get_margin`，且内部统一走 `_ts()` 限流；
- data_daemon 的 `_ts()` 限流封装（0.2s/5次每秒）与 TushareProvider 的 `_ts()` 是**两套重复实现**。

**决策**：**一次性收敛** `_batch_*` 的 Tushare 调用到 TushareProvider 对应方法（复用其 `_ts()` 限流），消除 data_daemon 内重复的 `import tushare` 原语调用。这样：数据源连接统一收敛到 Provider 层（符合 292 号"数据源适配层"设计）、限流逻辑单一化（消除两套 `_ts()` 重复实现）、异常处理统一（Provider 方法已封装 try/except + warning）。**不建议**引入 DataSourceManager 的自动降级切换（`_batch_*` 是批量全量 API，非逐只实时，降级收益低、复杂度高）——收敛到 TushareProvider 已满足"适配层"要求。
