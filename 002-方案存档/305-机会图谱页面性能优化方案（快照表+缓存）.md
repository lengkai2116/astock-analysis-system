# 机会图谱页面性能优化方案（快照表 + 多级缓存）

> **问题**：机会图谱 Treemap 页面点击打开后耗时 6~12 秒，根源在于后端每请求从 `daily_cache`（580 万行）、`daily_basic_cache`（75 万行）、`opportunity_tags_cache`（21 万行）三张大表进行全量/大范围扫描，而前端实际只需要每只股票的**最新一条日线数据**（4800 行）。
>
> **总则**：本方案不修改原有架构设计，不违反四层架构红线规则，所有新增操作均在现有的 `data_daemon` 流程和 DataManager 网关框架下完成。

---

## 一、瓶颈回顾

### 1.1 当前数据读取量（每请求）

| 数据源 | 当前读取行数 | 实际需要行数 | 倍率 |
|--------|:----------:|:----------:|:----:|
| `daily_cache` | 5,824,958 | 4,800（每只最新 1 条） | 1,213× |
| `daily_basic_cache` | 747,813 | 4,800（每只最新 1 条） | 156× |
| `opportunity_tags_cache` | 205,567 | 205,567（全部标签） | 1×（实际需要全部） |
| **合计** | **~6,778,338** | **~215,167** | **~31×** |

### 1.2 全请求时间线分解

```
前端 renderChart()
  → loadMarketData()
    → fetch('/api/v3/opportunity-atlas/treemap?mode=market')
      ┌────────────────────────────────────────┬──────────┐
      │ 步骤                                 │ 耗时估算  │
      ├────────────────────────────────────────┼──────────┤
      │ ① get_all_ts_codes() — ORM 5000 股   │ < 0.1s   │
      │ ② get_stock_meta_batch() — ORM 批查  │ < 0.1s   │
      │ ③ get_cached_daily_batch() — 5.8M 行 │ 2-8s     │
      │ ④ get_cached_daily_basic() — 747K 行 │ 0.5-2s   │
      │ ⑤ get_all_market_snapshots()         │ < 0.1s   │
      │ ⑥ get_tags_batch() — 205K 行        │ 0.3-1s   │
      │ ⑦ Python 4800 循环组装              │ 0.1-0.3s │
      │ ⑧ JSON 序列化 + 网络传输             │ 0.3-1s   │
      │ ⑨ ECharts 渲染 4800 treemap 节点     │ 0.5-2s   │
      ├────────────────────────────────────────┼──────────┤
      │ 合计                                  │ 4-12s    │
      └────────────────────────────────────────┴──────────┘
```

**核心瓶颈**：步骤 ③④⑥ 串行读取三张大表，且每步都在 SQLite 中全表/大半表扫描。③ 的 `SELECT * FROM daily_cache` 从 21GB 的 SQLite 文件读取 580 万行是绝对主因。

## 二、解决方案：三层递进优化

### 2.1 总体架构

```
                     data_daemon 数据管道（链条驱动，取代定时窗口）
┌─────────────────────────────────────────────────────────────────────┐
│ _drive_pipeline() 每 30s tick 检查 pipeline_status 自动推进          │
│                                                                      │
│ 采集阶段（数据到达驱动，非时间驱动）：                                  │
│   C1 日线采集 → C2 基本面采集 → C3~C6 其余采集                        │
│   (C1~C6 全部 done 后进入预计算，C7~C8 后台低优不阻塞)                │
│    ↓                                                                 │
│ 预计算阶段（C1~C6 done 后自动触发）：                                  │
│   P1 指标预计算 → P2 策略信号 → P3 因子 → P4 L2标签                  │
│    ↓                                                                 │
│ 快照构建阶段（P1~P4 全部 done 后自动触发）：                           │
│   S1 构建 treemap_snapshot → 管道 complete                            │
└─────────────────────────────────────────────────────────────────────┘
                                │
                                ▼
                     ECM SQLite 存储层
          ┌───────────────────────────────────┐
          │ daily_cache (580万行, 不变)       │  ← 全量日线历史，保持不动
          │ daily_basic_cache (75万行, 不变)  │  ← 全量基本面历史，保持不动
          │ opportunity_tags_cache (21万行)   │  ← 标签池，预计算写入
          │ treemap_snapshot (4800行 ★ 新增) │  ← 每日替换的轻量快照
          │ as_market_snapshot (盘中实时)    │  ← 盘中 5s 更新
          └───────────────────────────────────┘
                                │
                                ▼
                     API 进程（run.py）
          ┌───────────────────────────────────┐
          │ TieredMemoryCache                 │  ← 新增 treemap 级别 (3600s)
          │   ├─ treemap:opportunity          │  ← 机会地图全量缓存
          │   ├─ treemap:value               │  ← 价值地图全量缓存
          │   └─ treemap:market_meta         │  ← 市场地图非实时字段
          └───────────────────────────────────┘
                                │
                                ▼
                     Flask REST API → 前端
          HTTP Cache-Control: public, max-age=3600 (非 market 模式)
```

### 2.2 第一层：快照表（日终预提取）— 根本方案

#### 2.2.1 新增表结构

```sql
-- 在 stock_cache.db (ECM) 中新增
CREATE TABLE IF NOT EXISTS treemap_snapshot (
    ts_code            TEXT PRIMARY KEY,
    name               TEXT,              -- 股票名称（编码归一化）
    industry           TEXT,              -- 申万一级行业
    close              REAL,              -- 最新收盘价
    pct_chg            REAL,              -- 最新涨跌幅（%）
    total_mv           REAL,              -- 总市值（元）
    trade_date         TEXT,              -- 数据日期 (YYYYMMDD)

    -- L2 标签平铺（约 15 个核心字段）
    signal_strength        REAL,
    valuation_level        TEXT,
    valuation_deviation    REAL,
    main_force_phase       TEXT,
    phase_confidence       REAL,
    sentiment_phase        TEXT,
    sector_heat            TEXT,
    fina_health            TEXT,
    hold_period            TEXT,
    trend_alignment        TEXT,
    price_position         TEXT,
    fund_flow              TEXT,
    capital_nature         TEXT,
    chip_concentration     TEXT,
    volatility_level       TEXT,
    dividend_yield         REAL,
    composite_rating       REAL,

    -- 元信息
    snapshot_date        TEXT DEFAULT (date('now')),  -- 快照构建日期
    build_version        INTEGER DEFAULT 1,           -- 快照格式版本
    UNIQUE(ts_code, snapshot_date)
);

CREATE INDEX IF NOT EXISTS idx_snapshot_industry ON treemap_snapshot(industry);
```

**设计说明**：
- **平铺而非 EAV**：4800 行 × ~25 列 ≈ 120K 个字段值，约 2-3 MB，远低于常规表的规模。平铺结构让 SQLite 单行 I/O 即可读出全字段，无需 `GROUP BY` 或 `JOIN`
- **不保留历史**：每次构建是全量替换（非交易日不替换），因为快照的目的是提供"最新可用的一幅市场快照"
- **行业索引**：`idx_snapshot_industry` 供前端按行业筛选过滤使用

#### 2.2.2 构建函数（data_daemon 新增）

```python
def _build_treemap_snapshot(codes: list[str]):
    """日终预计算完成后，构建 treemap_snapshot 快照表

    执行时机：在 _run_precompute() 全部完成后调用（L2标签已就绪）
    执行周期：每个交易日日终预计算完成后执行一次
    数据来源：仅从 ECM 存储层读取，不涉及外部数据源
    """
    from app.data import DataManager
    dm = DataManager()
    ecm = dm.cache

    # 1. 获取活跃股票列表（当日有日线数据的股票）
    codes = dm.get_all_ts_codes()

    # 2. 获取元数据（名称 + 行业）
    meta = dm.get_stock_meta_batch(codes)

    # 3. 获取最新日线（仅最新一条，用 SQL 聚合而非全表扫描）
    daily_latest = ecm._query_df("""
        SELECT ts_code, close, pct_chg, trade_date FROM daily_cache
        WHERE (ts_code, trade_date) IN (
            SELECT ts_code, MAX(trade_date) FROM daily_cache
            WHERE ts_code IN ({placeholders})
            GROUP BY ts_code
        )
    """, codes)

    # 4. 获取最新基本面（仅 latest total_mv）
    basic_latest = ecm._query_df("""
        SELECT ts_code, total_mv FROM daily_basic_cache
        WHERE (ts_code, trade_date) IN (
            SELECT ts_code, MAX(trade_date) FROM daily_basic_cache
            WHERE ts_code IN ({placeholders})
            GROUP BY ts_code
        )
    """, codes)

    # 5. 获取 L2 标签（扁平化，每只一行）
    tags_df = ecm._query_df("""
        SELECT ts_code,
               MAX(CASE WHEN tag_name='signal_strength'     THEN tag_value END) as signal_strength,
               MAX(CASE WHEN tag_name='valuation_level'     THEN tag_value END) as valuation_level,
               -- ... 其余 20+ 标签同理
        FROM opportunity_tags_cache
        WHERE ts_code IN ({placeholders})
        GROUP BY ts_code
    """, codes)

    # 6. 合并写入 treemap_snapshot（用 INSERT OR REPLACE + 逐条提交）
    for code in codes:
        ecm.conn.execute("""
            INSERT OR REPLACE INTO treemap_snapshot
            (ts_code, name, industry, close, pct_chg, total_mv, trade_date,
             signal_strength, valuation_level, ...)
            VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ...)
        """, (code, ...))
    ecm.conn.commit()
```

**关键设计决策**：

| 决策 | 选择 | 理由 |
|------|------|------|
| 写入方式 | 逐条 `INSERT OR REPLACE` | 4800 条 × 1ms ≈ 4.8s，可接受且避免长事务锁 |
| 查询方式 | SQL 子查询 `MAX(trade_date)` | 避免全表扫描，利用 `(ts_code, trade_date)` 主键索引 |
| 标签平铺 | SQL `MAX(CASE WHEN ...)` + `GROUP BY` | 比 pandas 逐只循环快 10 倍以上，充分利用 SQLite 引擎 |
| 数据源 | 全部从 ECM 存储层读取 | 完全遵守四层架构红线，不涉及外部数据源 |

#### 2.2.3 触发时机

S1（`_build_treemap_snapshot`）作为管道驱动模式中的一个独立环节运行，**不由 `_run_precompute()` 内部触发**，而是由 `_drive_pipeline()` 在 P1~P4 全部 `done` 后自动推进（详见 §9.4）：

```
_drive_pipeline()
  → C1~C6 done? → P1~P4 done? → S1 pending? → 执行 _build_treemap_snapshot()
```

因此 `_build_treemap_snapshot()` **不追加到 `_run_precompute()` 末尾**，而是作为一个独立函数（签名见 §2.2.2）供 `_run_step()` 调度器调用。

**节假日处理**：data_daemon 的 `_drive_pipeline()` 在非交易日不会开始管道，因此 S1 不会执行。快照表保持最近一个交易日的状态，API 读取时语义为"最近可用交易日的数据"。

#### 2.2.4 预期效果

| 指标 | 优化前 | 优化后 | 提升 |
|------|:-----:|:-----:|:----:|
| 单次 API 扫描行数 | ~6,778,338 行 | ~4,800 行 | **99.93% 减少** |
| 后端响应时间 | 3-10s | **0.2-0.5s** | **15-20 倍** |
| 数据库 IO 压力 | 2-3 张大表全扫 | 1 张小表主键查 | 极低 |
| DB 内存驻留 | pandas 580 万行 DataFrame | 无 | 无 |

### 2.3 第二层：内存缓存（TieredMemoryCache + API 进程内）

#### 2.3.1 新增缓存级别

在 `memory_cache.py` 新增 `treemap` 级别：

```python
CACHE_LEVELS = {
    # ... 现有 4 个级别不变 ...
    'treemap': {'ttl': 3600, 'maxsize': 50},   # 新增：treemap 全量响应缓存（1h TTL）
}
```

#### 2.3.2 缓存策略

```python
def get_treemap_cache_key(mode: str, tags: str = '', industry: str = '') -> str:
    """生成缓存键，含筛选参数"""
    if mode == 'market':
        return f'treemap:market'  # 仅缓存非实时字段
    return f'treemap:{mode}:{tags}:{industry}'
```

| 地图模式 | 缓存行为 | 说明 |
|---------|---------|------|
| `market`（市场地图） | **非实时字段**缓存（名称/行业/市值/标签） | `pct_change` 依然每 30s 从 `as_market_snapshot` 实时读取 |
| `opportunity`（机会地图） | **全响应**缓存 3600s | 数据仅日终变化，盘中无需更新 |
| `value`（价值地图） | **全响应**缓存 3600s | 同上 |

#### 2.3.3 日终缓存失效机制

日终快照构建完成后，API 进程需要感知并清除旧缓存。有两种方案：

**推荐方案：缓存 TTL 自然过期**
- TTL 设为 3600s，日终预计算完成后 T+1 日 9:30 开盘前，缓存最多过期 18 小时
- 次日首次请求触发缓存重建 → 命中快照表
- 优点：零协调，零耦合，绝对稳定

**替代方案（可选增量）：日终后主动失效**
- `data_daemon` 在 `_build_treemap_snapshot()` 完成后写入一个共享状态（如 `cache_metadata` 表）：`last_treemap_update = 20260729`
- API 进程每请求检查该时间戳，若晚于当前缓存时间则清除缓存
- 优点：缓存更及时
- 劣势：增加了跨进程协调复杂度

**建议**：先实施推荐方案，若用户在交易日切换时感受到延迟再追加替代方案。

        # ── opportunity/value 模式：仅快照表 ──

## 四、故障模式与安全护栏

### 4.1 快照表缺失（首次部署 / DB 重建）

```python
def get_treemap_snapshot(self, ts_codes):
    try:
        df = self._query_df(...)
        if df.empty:
            raise ValueError("snapshot empty")
        return df
    except Exception:
        # 兜底：回退到旧路径（逐个查询，返回 cached_at 标志）
        logger.warning("treemap_snapshot 不可用，回退到逐表查询")
        return self._fallback_legacy_query(ts_codes)
```

| 场景 | 行为 | 对用户影响 |
|------|------|-----------|
| data_daemon 尚未完成首次构建 | API 回退到旧路径 | 恢复当前速度（慢但可用） |
| 快照表构建进行中（`_write_lock` 被持） | SQLite `busy_timeout=5000ms` 后失败 → 回退 | 最多等待 5s |
| 快照构建失败（某只股票数据缺失） | 该股票在快照表中不存在 | 该股票不显示在 treemap 中（非严重错误，不影响其他 4799 只）|
| 某日无交易（节假日） | 快照表未被替换 | 仍显示最近交易日数据，语义正确 |

### 4.2 多副本/多进程安全

由于 `treemap_snapshot` 需要全量替换，写入期间的读写一致性问题必须处理。

**推荐方案：原子表替换**。核心思路是写入新表后再通过 DDL 切换，确保查询不读到半截数据：

```python
# 原子表替换（写入全程旧表仍可读）
NEW_TABLE = 'treemap_snapshot_new'

# 1. 创建新表（空结构，与目标表一致）
_ecm.conn.execute(f"""
    CREATE TABLE IF NOT EXISTS {NEW_TABLE} (
        ts_code TEXT PRIMARY KEY, name TEXT, industry TEXT,
        close REAL, pct_chg REAL, total_mv REAL, trade_date TEXT,
        signal_strength REAL, valuation_level TEXT, ...
    )
""")

# 2. 写入新表（旧表不受影响，查询仍命中旧表）
for code in codes:
    _ecm.conn.execute(f"INSERT OR REPLACE INTO {NEW_TABLE} ...")
_ecm.conn.commit()

# 3. 一次性切换（事务内完成，对查询原子可见）
_ecm.conn.execute("DROP TABLE treemap_snapshot")
_ecm.conn.execute(f"ALTER TABLE {NEW_TABLE} RENAME TO treemap_snapshot")
_ecm.conn.commit()
# 至此，后续查询原子性地命中新表
```

| 阶段 | 查询行为 | 正确性 |
|------|---------|:------:|
| 写入新表中（步骤 1-2） | 查询命中旧表 | ✅ |
| DROP 旧表 → ALTER 新表（步骤 3） | 短窗口内表名不存在 → SQLite 报错 → 回退到旧路径 | ✅ 回退安全 |
| 切换完成后 | 查询命中新表 | ✅ |

> 注意：`DROP` + `ALTER` 是两条单独的 DDL 语句，严格来说不是单事务。但 `ALTER TABLE ... RENAME` 在 SQLite 中是原子操作，写入立刻对新查询可见。`DROP` 失败的概率极低（仅在磁盘已满等极端场景），此时 `_build_treemap_snapshot` 的外层 `try/except` 会捕获异常，旧表可用，下次重试即可。

**不推荐的方案：先 DELETE 再 INSERT**。删除后插入前存在空窗期，此时查询返回空结果或部分数据，会触发回退路径，不必要地降级到旧查询。

### 4.3 market 模式实时数据与快照的合并

market 模式的 `pct_change` 从 `as_market_snapshot` 实时读取：
- 盘中：`pct_change = realtime.pct_change`（覆盖快照的 pct_chg）
- 盘后收盘后：`as_market_snapshot` 可能为空 → 使用快照的 `pct_chg`
- 非交易时段：同上

```python
def _merge_snapshot_with_realtime(snapshot_items, realtime_dict):
    for item in snapshot_items:
        rt = realtime_dict.get(item['ts_code'])
        if rt and 0.01 < float(rt.get('price', 0)) < 10000:
            item['pct_change'] = float(rt['change_pct'])
            item['price'] = float(rt['price'])
            item['snapshot'] = True
    return snapshot_items
```

### 8.2 现有触发机制的问题

当前 `_run_precompute()` 的触发链路：

```
data_daemon 主循环 (30s tick)
  │
  ├─ ① 15:30-15:35 窗口触发 → run_daily_sync()
  │     └─ 最后 → threading.Thread(target=_run_precompute).start()
  │
  ├─ ② sync_requests 队列消费（30s轮询）
  │
  ├─ ③ 整点巡检（非交易时段）
  │
  └─ 开机时（独立于主循环）：
       ├─ run_integrity_check(backfill_days=3)
       ├─ _check_daily_sync_backfill()    ← 日终兜底
       └─ _check_precompute_status(today) ← 预计算自检
```

**缺陷清单**：

| # | 缺陷 | 技术表现 |
|---|------|---------|
| **D1** | **定时触发而非数据驱动** | 15:30-15:35 的 5 分钟窗口是硬编码的。若电脑在 15:35 之后才开机，`_daily_sync_triggered` 离开窗口后重置为 `False` 但窗口已错过。兜底逻辑 `_check_daily_sync_backfill()` 虽能补，但判断条件过于粗放 |
| **D2** | **环节之间无完成信号传递** | `run_daily_sync()` 在第 1213 行启动 `_run_precompute` 后台线程时，采集本身**尚未全部完成**——`_run_financial_sync()` 和 `_run_minute_backfill()` 也在同一点作为后台线程启动。三者并行。预计算依赖的 `daily_cache` 数据虽已就绪（因为主采集线程已串行完成），但财务数据的缺失会导致估值引擎部分标签不完整 |

| **D4** | **缺少持久化环节状态** | 所有完成状态是内存变量（`_SYNCED_TODAY`、`_daily_sync_triggered`），重启后丢失。开机时的兜底逻辑只能通过"表有没有数据"间接推断，无法精确知道哪些环节已完成、哪些需重做 |
| **D5** | **快照构建未纳入管道** | `_run_precompute()` 完成四步后没有第五步，快照表从未构建 |

## 九、管道状态表与链条驱动机制

> 本方案在快照表之上，进一步提出将 data_daemon 的日终处理从**定时+兜底**模式改造为**数据驱动管道**模式。核心是新增 `pipeline_status` 持久化状态表，每个环节显式记录完成状态，主循环根据前置环节的完成状态决定下一步。

### 9.1 核心逻辑

两个关键变更：

1. **新增 `pipeline_status` 表**，持久化记录每个交易日每个环节的执行状态（pending/running/done/failed/skipped）
2. **新增 `_drive_pipeline()` 函数**，替代 `run_daily_sync()` 的定时窗口触发。每 30s tick 检查管道状态，找到下一个可以执行的环节并推进

### 9.2 pipeline_status 表

```sql
CREATE TABLE IF NOT EXISTS pipeline_status (
    pipeline_date  TEXT,           -- 交易日 (YYYYMMDD)
    step_id        TEXT,           -- 环节标识符，如 'C1', 'P1', 'S1'
    step_name      TEXT,           -- 环节名称（中文说明）
    status         TEXT            -- pending | running | done | failed | skipped
        DEFAULT 'pending',
    started_at     TIMESTAMP,      -- 该环节开始执行的时间
    completed_at   TIMESTAMP,      -- 该环节完成的时间
    detail         TEXT,           -- 执行结果摘要（行数/耗时/错误信息等）
    retry_count    INTEGER DEFAULT 0,  -- 重试次数
    PRIMARY KEY (pipeline_date, step_id)
);
```

**设计要点**：
- **`pipeline_date` 天然区分不同交易日**——多日状态共存（T 日管道进行中，T-1 日已完成），重启后也能读到最后状态
- **`retry_count`** 控制重试次数上限（默认 3 次后标记 `failed`），避免单环节无限重试
- **`started_at`** 用于超时判断——若状态为 `running` 但 `started_at` 超过 30 分钟前，视为 `failed` 并允许重试

### 9.3 完整的全局数据处理链条

区别于当前 `run_daily_sync()` 将所有采集步骤捆成一个整体、后台线程并行启动预计算，管道模式将每一类数据处理定义为**独立环节**，每个环节有明确的**前置依赖**：

```
 链条 ID: daily_pipeline_{YYYYMMDD}

 ┌─ 采集阶段（C 系列）────────────────────────────────────────────────
 │  前置条件：交易日判断通过（周一至周五，且 ≥15:00 或日线数据已到达）
 │
 │  C1: 日线采集       _batch_daily()         → daily_cache
 │  C2: 基本面采集     _batch_daily_basic()    → daily_basic_cache
 │  C3: 资金流采集     _batch_moneyflow()      → moneyflow_cache
 │  C4: 涨跌停采集     _batch_stk_limit()      → stk_limit_cache
 │  C5: 龙虎榜采集     _batch_lhb()            → lhb_cache
 │  C6: 概念板块采集   _batch_concept()        → concept_cache
 │  C7: 财务数据同步   _run_financial_sync()   → fina/income/balance/cashflow
 │  C8: 日终补充       adj_factor/top10/...    → 对应 cache 表
 │
 │  依赖图：C1~C6 在 C7~C8 之前（财务数据非日更，不影响预计算主体）
 │          C1~C6 之间无依赖（可并行，但管道模式串行推进更稳定）
 │  完成条件：C1~C6 全部 done → 进入 P 阶段
 │            C7~C8 为后台低优，不阻塞 P 阶段
 │
 ├─ 预计算阶段（P 系列）──────────────────────────────────────────────
 │  前置条件：C1~C6 全部 done
 │
 │  P1: 指标预计算     precompute_all_indicators()  → indicator_ma/macd/other
 │  P2: 策略信号预计算 UnifiedStrategyCore()        → strategy_signal_detail
 │  P3: 因子预计算     precompute_preset_combos()   → factor_cache
 │  P4: L2 标签预计算  precompute_l2_labels()       → opportunity_tags_cache
 │
 │  依赖图：P1→P2→P3→P4 串行（P4 依赖前序产出）
 │  完成条件：P1~P4 全部 done → 进入 S 阶段
 │
 └─ 快照构建阶段（S 系列）────────────────────────────────────────────
   前置条件：P1~P4 全部 done
   
   S1: Treemap 快照  _build_treemap_snapshot()  → treemap_snapshot
   
   完成条件：S1 done → 管道 complete
```

### 9.4 链条驱动逻辑

```python
def _drive_pipeline():
    """管道驱动：检查当前状态，推进到下一个可执行的环节

    每 30s tick 由 data_daemon 主循环调用一次。
    每次只推进一个环节，避免单 tick 过长。
    """
    today = datetime.now().strftime('%Y%m%d')

    # ── Guard 1: 非交易日跳过 ──
    if not _is_market_day():
        return

    # ── Guard 2: 今日管道是否已完成 ──
    if _is_pipeline_complete(today):
        return

    # ── 交易日判断 ──
    # 判断依据：daily_cache 已有当日数据且 ≥ 5000 行（即日终数据已到达）
    # 不是根据时间判断，而是根据**数据是否存在**判断
    has_today_data = _ecm.conn.execute(
        "SELECT COUNT(*) FROM daily_cache WHERE trade_date=?", [today]
    ).fetchone()[0] >= 5000

    if not has_today_data:
        # ① 如果是交易日下午 15:30 之后仍无数据 → 可能是非交易日（调休），跳过
        # ② 如果 <15:30 → 等数据，不处理
        return  # 下一 tick 再检查

    # ── 读取当前管道状态 ──
    status = _load_pipeline_status(today)

    # ════════════════════════════════════════════
    # 采集阶段 C1→C6（串行推进）
    # ════════════════════════════════════════════
    if not _step_done(status, 'C1'):
        _run_step(today, 'C1', '日线采集', _batch_daily, today)
        return
    if not _step_done(status, 'C2'):
        _run_step(today, 'C2', '基本面采集', _batch_daily_basic, today)
        return
    # ... C3~C6 同样模式 ...

    # ── 采集阶段检查：C1~C6 全部 done 才进入 P 阶段 ──
    if not _all_done(status, ['C1','C2','C3','C4','C5','C6']):
        # 若有 failed 的环节 → 触发重试（上限 3 次）
        _retry_failed_steps(today, status, ['C1','C2','C3','C4','C5','C6'])
        return

    # ════════════════════════════════════════════
    # 预计算阶段 P1→P4（串行推进）
    # ════════════════════════════════════════════
    codes = _get_active_codes(today)

    if not _step_done(status, 'P1'):
        _run_step(today, 'P1', '指标预计算', _precompute_all_indicators, codes)
        return
    if not _step_done(status, 'P2'):
        _run_step(today, 'P2', '策略信号预计算', _compute_strategy_signals, codes)
        return
    if not _step_done(status, 'P3'):
        _run_step(today, 'P3', '因子预计算', _precompute_preset_combos, codes)
        return
    if not _step_done(status, 'P4'):
        _run_step(today, 'P4', 'L2标签预计算', _precompute_l2_labels, codes)
        return

    # ════════════════════════════════════════════
    # 快照构建阶段 S1
    # ════════════════════════════════════════════
    if not _step_done(status, 'S1'):
        _run_step(today, 'S1', 'Treemap快照', _build_treemap_snapshot, codes)
        return

    # ════════════════════════════════════════════
    # 全管道完成
    # ════════════════════════════════════════════
    _mark_pipeline_complete(today)
    logger.info(f"  [管道] 今日全链路完成 ✅")


def _run_step(today, step_id, step_name, func, *args):
    """执行单个管道环节，记录状态

    原子性保证：通过 UPDATE ... SET status='running' WHERE status='pending'
    确保同一环节不会被多个 tick 同时执行（幂等锁）
    """
    # 抢锁：只有将 pending→running 成功的 tick 才执行
    rowcount = _ecm.conn.execute(
        "UPDATE pipeline_status SET status='running', started_at=CURRENT_TIMESTAMP "
        "WHERE pipeline_date=? AND step_id=? AND status='pending'",
        [today, step_id]
    ).rowcount
    if rowcount == 0:
        return  # 另一个 tick 已抢到锁，本 tick 跳过

    # 执行
    t0 = time.time()
    try:
        result = func(*args)
        detail = f"OK ({result}行, {time.time()-t0:.1f}s)" if result else f"OK ({time.time()-t0:.1f}s)"
        _ecm.conn.execute(
            "UPDATE pipeline_status SET status='done', completed_at=CURRENT_TIMESTAMP, detail=? "
            "WHERE pipeline_date=? AND step_id=?",
            [detail, today, step_id]
        )
    except Exception as e:
        _ecm.conn.execute(
            "UPDATE pipeline_status SET status='failed', completed_at=CURRENT_TIMESTAMP, detail=? "
            "WHERE pipeline_date=? AND step_id=?",
            [f"ERROR: {e}", today, step_id]
        )
    _ecm.conn.commit()
```

每个 tick 的流程图：

```
_drive_pipeline() 入口
  │
  ├─ 非交易日？→ 跳过，return
  ├─ 本日管道已完成？→ return
  ├─ 今日数据未到达？→ return（等下一 tick）
  │
  ├─ C1 pending？→ 执行 C1，return
  ├─ C2 pending？→ 执行 C2，return
  ├─ ...（C3~C6）
  ├─ C1~C6 全部 done？→ 继续；否则→ 处理 failed 重试后 return
  │
  ├─ P1 pending？→ 执行 P1，return
  ├─ P2 pending？→ 执行 P2，return
  ├─ P3 pending？→ 执行 P3，return
  ├─ P4 pending？→ 执行 P4，return
  │
  ├─ S1 pending？→ 执行 S1，return
  │
  └─ 全部 done → 标记 complete
```

### 9.5 节假日与跨日处理逻辑

```
交易日判断链（每个 tick 执行）：

  ① today 是周一到周五？
     否 → 跳过（周末/法定假日）
     是 → 继续
  ② daily_cache 有 trade_date=today 且 ≥5000 行？
     是 → 交易日且数据已到达 → 驱动管道
     否 → 
       如果当前时间 < 15:00 → 等数据（盘中尚未收盘）
       如果当前时间 ≥ 15:30 → 非交易日（如调休、长假）→ 跳过
       如果 15:00~15:30 → 等数据（收盘后数据尚未到达）
```

**跨日处理**：`pipeline_status` 表以 `(pipeline_date, step_id)` 为主键，天然支持多日状态共存。T 日管道在进行中，T-1 日的完成状态仍可查询。data_daemon 重启后读取 `pipeline_status` 中 `pipeline_date=today` 的记录，从上次断点恢复。

**开盘自检的简化**：现有 `_check_precompute_status()` 和 `_check_daily_sync_backfill()` 可以被 `_drive_pipeline()` 替代——开机后首次 tick 就会检查管道状态并推进，无需单独的开机检查函数。

### 9.7 风险评估

| 风险 | 级别 | 缓解措施 |
|------|:----:|---------|
| `pipeline_status` 表写入失败导致重复执行 | 🟡 中 | 幂等锁：`UPDATE ... WHERE status='pending'` 确保同一环节只被一个 tick 执行一次 |
| 长环节（P4 L2 标签 ~4 分钟）执行中被中断 | 🟡 中 | `started_at` 时间戳 + 超时阈值（30 分钟），重启时若读到 `running` 且超时，标记为 `failed` |
| 不同 tick 之间的原子性问题 | 🟢 低 | 每 tick 只推进一个环节，不跨 tick。`_run_step` 中的 SQL UPDATE 是原子操作 |
| 与 sync_requests 的交互冲突 | 🟢 低 | sync_requests 作为采集补充信号，独立于管道状态。两者写入不同表 |
| 财务数据 C7 与预计算 P 阶段的时序问题 | 🟢 低 | C7（财务数据同步）标记为"后台低优，不阻塞 P 阶段"。因为估值引擎在缺失财务数据时会自动兜底 |
| 与现有 `run_daily_sync()` 的并行冲突 | 🟡 中 | 改造完成后应移除 `run_daily_sync()` 的定时窗口调用，确保新旧两套逻辑不会同时执行 |
