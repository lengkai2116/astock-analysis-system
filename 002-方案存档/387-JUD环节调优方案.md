# 387 — JUD环节调优方案

> **背景**：基于JUD环节完整架构梳理（status_engine.py 967行 + arbiter.py 267行 + cross_validate.py 1872行），对照LLM Wiki知识库中多策略融合、量化仲裁、风险预算、信号冲突处理等理论框架，识别系统实际配置与理论最佳实践之间的差距，编制分层调优路径。
>
> **核心原则**：
> - **理论对照实践**：每项调优均有知识库理论依据+系统现状差距分析
> - **分层递进**：P1(低复杂度立即可做) → P2(中等复杂度近期) → P3(高复杂度中期)
> - **最小侵入**：优先调整配置/参数，避免大规模重构

## 一、JUD架构现状摘要

### 1.1 管道定位

```
COL → RAW → SIG → JUD → OUT
                  ↑
            本方案调优目标
```

JUD包含3个子步骤（data_daemon.py L4559-4567）：
1. `_build_status_snapshot` — StatusEngine.evaluate() 核心判定
2. `_jud_enrich_with_meta` — 机会分类+潜力评分+右侧确认
3. `_build_treemap_snapshot` — treemap快照生成

### 1.2 核心判定链

```
原料加载(pre_feat_cache + signal_json)
  → L1 维度判定（7+1维度引擎 → {state, light, confidence, evidence}）
  → L0 风险分级（硬否决/软约束/持有期）
  → L2 聚合（动态权重共识率 + conflict_evidence + arbiter仲裁）
  → opportunity_state（enter/light/wait/avoid）
  → status_snapshot 行输出
```

### 1.3 关键配置项

| 配置项 | 当前值 | 位置 |
|--------|--------|------|
| 动态权重矩阵 | 4种市场状态 × 7维度（静态经验值） | status_engine.py L554-558 |
| 共识阈值 | bearish_strong=0.67, enter_threshold=0.67 | arbiter.py L57-59 |
| L0软风险系数 | fina_fail=0.5, distributing=0.7, deep_valuation=0.3等 | status_engine.py L520-540 |
| 仓位基数 | enter=0.6, light=0.6, wait=0.2, avoid=0.0 | status_engine.py L722 |
| 状态条阈值 | green≥6强趋势, green≥4趋势确认, red≥4趋势转弱 | status_engine.py L691-715 |

## 二、知识库理论对照与差距分析

### 2.1 权重体系

**知识库来源**：
- `wiki/sources/主动投资组合管理.md`：IC（信息系数）驱动权重，权重 ∝ IC × 预测值 / 残差波动率
- `wiki/concepts/信号冲突处理机制.md`：市场状态依赖加权法，"没有任何一个因子在所有市场状态下都有效"

**系统现状**：4种市场状态 × 7维度的静态权重矩阵（trending_up/ranging/trending_down/extreme_panic）

**差距**：
- 权重为**固定经验值**，未基于历史IC值校准
- 市场状态识别依赖标签推导（status_bar关键词匹配），非量化指标
- 未引入因子有效性衰减机制

### 2.2 仲裁状态机

**知识库来源**：
- `wiki/concepts/标签化与仲裁机制.md`："标签化的可组合性"——标签之间可逻辑组合（AND/OR）
- `wiki/concepts/信号冲突处理机制.md`："多指标共识机制"——归一化后≥2/3方向一致才执行

**系统现状**：P0-P7八级优先级，逐级判定命中即止

**差距**：
- P0/P1/P2/P4/P5**无置信度门槛**——单标签值即触发状态转换
- P6的0.67阈值为**全局固定值**，未考虑波动率影响
- 缺少**信号衰减机制**——知识库指出"信号预测能力随时间流逝而衰减"

### 2.3 仓位管理

**知识库来源**：
- `wiki/concepts/风险预算驱动仓位.md`：2%风险规则，仓位 = (账户资金×2%) / (入场价-止损价)
- `wiki/concepts/情绪周期-仓位联动.md`：五阶段仓位参数表（萌芽30%/发酵60%/高潮80%/退潮30%/冰点10%）
- `wiki/concepts/凯利公式（仓位管理）.md`：f = (b×p-q)/b，半凯利辅助校准

**系统现状**：固定基数（enter=0.6）× L0软风险系数连乘

**差距**：
- 仓位基于**固定基数**，未接入风险预算
- L0系数为**静态经验值**，未与止损距离挂钩
- 缺少情绪周期-仓位联动（dim5已有sentiment_phase输出）
- 缺少月度风险预算（无累计亏损上限）

### 2.4 冲突处理

**知识库来源**：
- `wiki/concepts/信号冲突处理机制.md`——多周期层级决策框架：
  - 背景周期（周线）：判断大方向
  - 决策周期（日线）：唯一买卖决策来源
  - 执行周期（小时）：优化入场位置
  - "**三灯全绿才进场**"

**系统现状**：conflict_evidence为平面列表（最多8条），仅展示不参与仲裁

**差距**：
- 冲突无层级区分（致命vs警告）
- dim2已有多级别分析但JUD未显式使用
- 冲突暴露给前端但不直接影响opportunity_state

### 2.5 过拟合防控

**知识库来源**：
- `wiki/concepts/组合对称交叉验证cscv.md`：PBO < 30%稳健，30-60%中等风险，> 60%不可信
- `wiki/concepts/过拟合检测贯穿全流程.md`："每增加一个维度都消耗研究员自由度"

**系统现状**：CSCVValidator在dim6中已实现但标记为独立工具类，未接入JUD管道

**差距**：
- arbiter阈值（0.67）未验证在不同市场周期的稳定性
- L0系数为经验值，无回测验证
- 缺少Walk-Forward参数稳定性检查

## 三、双视角审查与修正（量化分析师+系统架构师）

> v3.0新增：基于专业量化分析师和系统架构师两个视角对v2.0方案的全面审查，识别遗漏、风险、隐性BUG和可升级空间，所有高/中风险问题已在本版修正。

### 3.1 高风险问题（已修正）

#### H1：冲突降级规则1条件语义不一致（v2.0-§3.2 已修正）

**问题**：v2.0的致命冲突规则1写的是"缠论趋势下降 vs 多周期趋势向上（方向分歧）"，但触发条件是`state_label含"下降" AND trend_alignment="down_aligned"`——这是**缠论和趋势都看空**（同向），不是"分歧"。如果是同向看空，已被P3（强看空consensus≥67%→avoid）捕获，无需额外致命冲突规则。

**修正**：将规则1的条件改为真正的分歧场景：
| 原规则 | 修正后 |
|--------|--------|
| state_label含"下降" AND trend_alignment="down_aligned" | state_label含"下降" AND trend_alignment="**up_aligned**"（缠论空+趋势多=真正分歧） |

#### H2：日终管道与实时诊断双路径一致性（v2.0-§5.2 补充说明）

**问题**：方案的调优修改`_convert_to_dims_format()`和`_aggregate()`会同时影响两条路径：日终批量（`_build_status_snapshot`→status_snapshot表）和实时诊断（`cross_validate.diagnose`→`_get_status_verdict`→`StatusEngine().evaluate(ts_code)`）。实时诊断路径不传入dim_results，会重新计算8引擎，性能可能恶化。

**修正**：在§八验证策略中新增"双路径验证"要求，并在§六风险中明确标注性能影响评估为P2前置条件。

#### H3：回测验证框架缺失（v2.0-§四 新增P1.0）

**问题**：P2的IC动态权重和P3的CSCV验证都依赖"历史回测框架"，但方案将其标记为"需建立"而未给出建设计划。没有回测框架就无法量化调优效果。

**修正**：在P1层最前面新增"P1.0 回测框架最小可行性版本"作为所有后续调优的前置依赖。详见§四-P1层。

#### H4：验证策略仅3只蓝筹股（v2.0-§6.3 重写）

**问题**：000001.SZ/600519.SH/000002.SZ都是大盘蓝筹，无法覆盖中小盘、ST股、北交所、次新股、高波动股等场景。

**修正**：验证集扩展到20只覆盖全场景，详见§6.3验证策略。

### 3.2 中风险问题（已修正）

#### M1：IC动态权重样本量不足（v2.0-§四-3.5 修正）

**问题**：30日lookback窗口内只有6个独立的5日收益数据点（30/5=6），统计功效极低。IC值的置信区间极宽，权重分配本质是噪声驱动。

**修正**：
- lookback从30日改为**60日**（12个数据点，统计功效提升一倍）
- 新增**显著性检验**：IC的t检验p值<0.1才采信，否则回退到静态权重
- 新增**失败回退逻辑**：IC计算异常时自动回退到MARKET_REGIME_WEIGHTS静态矩阵

#### M2：共识率忽略维度相关性（v2.0-§四-新增说明）

**问题**：dim2（结构）和dim3（量价）都依赖OHLCV数据，高度相关。两个正相关维度同时看多时，权重被重复计算，consensus_rate虚高。

**修正**：在§六风险中明确标注此限制，作为P3级别的后续优化方向（引入方差膨胀因子VIF降权），不在本方案P1-P2中实施（避免复杂度过高）。

#### M3：status_engine.py即将过载（v2.0-§四 新增拆分计划）

**问题**：当前967行，方案新增约335行后膨胀到约1300行，超出单文件合理维护边界。

**修正**：在§四实施路径中新增模块拆分计划：
- `_convert_to_dims_format` → `dim_adapter.py`（维度格式适配器）
- `_compute_dynamic_weights` → `weight_engine.py`（权重计算引擎）
- `_aggregate`中的冲突检测 → `conflict_detector.py`（冲突检测器）

#### M4：advice_params新增字段的下游适配（v2.0-§四-路径D 补充）

**问题**：路径D新增7个字段到advice_params，但未说明advice_builder.py和前端Vue是否需要适配。

**修正**：在§四-路径D后新增"下游适配清单"：

| 下游组件 | 适配要求 | 优先级 |
|---------|---------|--------|
| advice_builder.py | 读取stop_loss_price/target_price替代自行计算 | P2 |

| 前端Vue（操作建议卡） | 新增止损价/目标位展示 | P3 |
| status_snapshot_history | 归档时包含新字段（JSON格式向前兼容） | P1 |

#### M5：P6阈值动态调整的方向假设可能反转（v2.0-§四-3.6 修正）

**问题**：方案假设"低波动→信号更可靠→降低阈值"。但A股实证中低波动率环境下假突破率更高（市场缺乏方向性时突破多为噪声）。

**修正**：将低波动阈值从0.60（降低）改为**0.70（微升）**——低波动不意味着信号更可靠，反而需要更谨慎：

| ATR百分位 | 原P6阈值 | 修正后 | 逻辑 |
|-----------|---------|--------|------|
| < 30%（低波动） | 0.60（降低） | **0.70（微升）** | 低波动≠高可靠，假突破率可能更高 |
| 30%-70%（正常） | 0.67（不变） | 0.67（不变） | 标准阈值 |
| > 70%（高波动） | 0.75（提高） | 0.75（不变） | 高波动需更强确认 |

#### M6：情绪周期参数表的经验值性质（v2.0-§四-3.4 标注）

**问题**：方案直接引用知识库五阶段参数表（冰点10%/退潮30%/...），但知识库自身已标注"具体百分比为经验值，缺乏历史回测数据支撑"。

**修正**：在§四-3.4中新增醒目提示：

> ⚠️ **经验值警告**：以下仓位参数（10%/30%/60%/80%）来自知识库经验总结，未经历史回测验证。实施后需通过P1.0回测框架验证参数合理性，并在实盘中持续监控效果。参数应可在status_engine.yaml中配置调整。

#### M7：dim1/dim8输出未纳入利用率审计（v2.0-§三 补充）

**问题**：审计覆盖dim2-dim7但完全未提及dim1和dim8。

**修正**：在§三汇总表中补充：

#### 5.7 2%风险规则接入

**数据依赖**：

- 止损价：dim6的support_price（已输出）
- 账户资金：需新增接口（或使用默认值100万）

**改动范围**：status_engine.py advice_params计算 + advice_builder.py

**约束叠加**（知识库约束条件）：
- 单只股票 ≤ 30%
- 同一行业 ≤ 40%
- 总持仓 3-8只
- 情绪阶段总仓位 10%-80%（与3.4联动）
- 月度风险预算 ≤ 6%

#### 5.8 背景周期过滤

**目标**：在_aggregate中引入dim2多级别分析结果

**知识库依据**：`wiki/concepts/信号冲突处理机制.md` 多周期层级决策框架

**改动范围**：status_engine.py _aggregate()

**规则**：

# 背景周期过滤（周线方向）
weekly_direction = dim_results.get('structure', {}).get('judgment', {}).get('weekly_direction', '')
if weekly_direction == 'down' and direction == 'bullish':

## 七、风险与注意事项

### 7.1 过拟合风险

- **P2的IC动态权重**：即使lookback从30日改为60日，IC在A股的时变性仍然很高，需严格通过显著性检验
- **P3的CSCV验证**：PBO应逐层计算（L0/L2/arbiter各自独立），而非整体计算（v3.0-L1修正）
- **知识库警告**："每增加一个维度都消耗研究员自由度"——本方案新增约83个消费字段，需通过回测验证未引入过拟合

### 7.2 向后兼容

- P0层为新增工具，不影响现有逻辑
- P1层改动为**纯增量**（新增字段+配置），不影响现有opportunity_state输出
- P2层的5.4情绪联动为**新增约束**（max_position_cap），不改变现有仲裁逻辑
- P3层的5.8背景周期过滤为**降级机制**（仅在周线空头时降级），不改变正常路径
- **路径D下游适配**（v3.0-M4修正）：advice_params新增字段需同步适配advice_builder.py和前端Vue

### 7.3 维度相关性限制（v3.0-M2标注）

当前共识率计算假设7个维度相互独立，但dim2/dim3共用OHLCV数据，dim4/dim5共用部分pre_feat_cache标签。高相关维度的权重被重复计算，可能导致consensus_rate虚高。此问题的根治（引入VIF降权）超出本方案范围，作为P3后续优化方向。

### 7.4 性能影响（v3.0-H2标注）

- 日终管道：新增字段提取增加约335行代码，5500只股票的全市场评估耗时需实测
- 实时诊断：`_get_status_verdict()`调用`StatusEngine().evaluate()`不传dim_results，会重新计算8引擎——新增字段提取可能进一步恶化实时响应时间
- **建议**：P2实施后进行性能基准测试（目标：实时诊断<500ms/只）
