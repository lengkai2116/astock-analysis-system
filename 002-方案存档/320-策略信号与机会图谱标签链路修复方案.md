# 机会弹窗与个股策略分析页整合 + 策略信号链路修复方案

> **背景**：2026-08-07 围绕"机会弹窗简述版 + 个股策略分析页详细版面"及其数据链路进行了多轮沟通与实证评估（详见 `001-沟通记录/26-08-07沟通纪要.md` 018/019/020/021）：
> - **展示层**（018）：机会弹窗改为精简简述版，与个股策略分析页（indicator-ide.html，上半K线+下半策略详解）整合，弹窗"策略分析"按钮跳转个股页，两板块 ts_code 双向往返；
> - **链路层**（019-021）：评估确认 ①九层解读**无需另搭预计算体系**（daemon P2 管道已存在）；②两条链**共用同一数据基础**（daily_cache K 线），"部分 vs 全面数据"实为数据采集问题；③**无需统一引擎**（本就同源），但需修复数据层与消费层的 3 个具体问题。
> 本方案整合两部分制定完整修复计划。**本方案仅存档，不修改任何代码。**

## 第二部分：链路层修复（策略信号与机会图谱标签链路统一）

## 二、评估结论回顾（方案依据）

### 2.1 两条链的机制对比（021 实证）

| 维度 | 机会图谱标签 | DeepSeek 九层解读 |
|------|------------|------------------|
| 预计算环节 | daemon **P4** `_precompute_l2_labels`（日终流水线） | daemon **P2** `_precompute_strategy_signals`（日终流水线，**已存在**） |
| 落表 | opportunity_tags_cache / treemap_snapshot | **strategy_signal_detail**（08-06 正常，5533 只） |
| 核心引擎 | 估值/阶段判定/量价/缠论/筹码/情绪/事件 | 缠论/量价/筹码/BOCIASI/因子（量价与筹码**同源**，缠论双封装） |
| 产出 | 结构化标签（枚举+红绿灯+评分） | 叙事信号（evidence/status_text） |
| 触发 | 日终自动 | 日终自动（P2）+ 用户触发（页面运行分析） |

### 2.2 三个待修复问题（评估结论）

| # | 问题 | 根因 | 影响 |
|---|------|------|------|
| **P1** | 553 只股票 K 线 <30 根（含 600519 仅 1 行），两条链的 K 线依赖维度同时失效 | daily_cache 历史 K 线缺失，日终回填/完整性检查未覆盖 | 600519 策略信号 signals={}；机会图谱 buy_sell_point/volume_price_fit/chip_position 标签缺失；九层解读 snapshot 多维度空 |
| **P2** | 策略信号双表并存：strategy_signals（07-22 停更旧表）vs strategy_signal_detail（08-06 正常新表） | P2 管道切换落表后旧表未清理 | 数据混乱、九层解读可能读错表 |
| **P3** | 九层解读走实时 compute_for_stock，未消费 P2 预计算产物 | `_get_deepseek_status_text` 调 `ai_context_builder.build_context` → 实时计算 | 与标签链数据时点不一致、重复计算（E12/E13/E14 三处重复） |

## 二、修复方案（P1-P4）

### P1：K 线缺失补采（数据采集层，最高优先级）

**目标**：全市场 5582 只均满足策略引擎 K 线门槛（≥130 根）。

**方案**：利用 daemon 已有的日终回填机制（`_batch_daily` + 完整性检查），对 K 线不足的股票补采历史日线。

```
补采范围判定（SQL）：
  SELECT ts_code, COUNT(*) cnt FROM daily_cache GROUP BY ts_code HAVING cnt < 130
  → 约 602 只（553 只 <30 根 + 49 只 30-129 根）

补采方式（复用现有 _batch_daily 逻辑）：
  对上述 ts_code 调用 Tushare daily（start_date=上市日/近5年, end_date=今日）
  写入 daily_cache（已有 cache_daily_data 方法）

触发时机：daemon 日终同步后，若完整性检查发现 K 线不足股 → 后台补采（复用 sync_requests 队列或独立循环）
```

**验收**：全市场 K 线 ≥130 根的股票占比 89% → ≥99%；600519 等样本股策略信号 signals 非空、机会图谱 buy_sell_point 等标签恢复。

### P2：策略信号双表清理（存储层）

**目标**：统一策略信号存储，消除旧表残留。

**方案**：
```
1. 确认 P2 管道唯一写入表 = strategy_signal_detail（_precompute_strategy_signals 已用 cache_signal_detail）
2. 停用/废弃 strategy_signals 旧表写入路径（_precompute_strategy_signals 中已无引用，确认无其他写入方）
3. 全系统检索 strategy_signals 读取方（SignalComputationService/路由/NLG 渲染器）→ 迁移到 strategy_signal_detail
4. 数据迁移完成后 DROP strategy_signals（或保留为只读备份 30 天）
```

**验收**：全系统无 strategy_signals 读取引用；strategy_signal_detail 为唯一策略信号源。

### P3：九层解读改消费 P2 产物（消费层）

**目标**：九层解读从 strategy_signal_detail（P2 预计算产物）读取，与标签链同源同数据时点。

**方案**：
```
改造 _get_deepseek_status_text（strategy_analyze.py:50-104）：
  原：ai_context_builder.build_context → SignalComputationService.compute_for_stock（实时重算）
  改：从 strategy_signal_detail 读取 P2 预计算信号 JSON（复用 SnapshotAssembler 组装）
     → strategy_signal_detail 无该股数据时，回退到实时计算（兜底，保持功能可用）

配套：SnapshotAssembler 直接消费 strategy_signal_detail 的 signal_json（而非 compute_for_stock 返回值）
```

**验收**：九层解读不再触发实时 compute_for_stock；600519 等 K 线补齐后九层解读与机会图谱标签数据时点一致；页面性能提升（消除 E12/E13/E14 重复计算）。

### P4：九层解读注入机会图谱标签基线（结论对齐，低风险增强）

**目标**：九层解读以机会图谱标签为权威基线，消除两套结论冲突。

**方案**：
```
stock_status_description.txt 的 user prompt 增加标签基线段：
  【标签基线（系统权威结论）】
  - tags_summary: 方向=趋势向上,均线交叉 / 位置=估值偏低 / 质量=主力洗盘 / 环境=情绪高潮
  - opportunity_profile: 🟢低估 🟢财务健康 🟢量价健康 🟡主力洗盘 🔴情绪高潮
  要求：九层描述与标签基线一致；不一致时标注差异原因（数据时点/算法差异），不隐藏

数据来源：opportunity_tags_cache（P4 产物），零新计算，仅 prompt 注入
```

**验收**：九层解读输出与机会图谱弹窗标签结论一致；冲突场景有差异标注。

## 四、风险与说明

**展示层（S1-S4）**：
1. **弹窗简述化信息取舍**：精简可能丢失细节，原则=结论与关键风险保留、细节下沉个股页；红绿灯画像数据全部已有（opportunity_profile 七维）
2. **跳转参数**：indicator-ide.html 需支持 `?ts_code=` URL 参数自动加载（当前可能未实现，S2/S4 需确认）
3. **科技感样式**：仅 CSS 增强，不影响功能；浏览器兼容性需验证

**链路层（F1-F5）**：
4. **K 线补采量**：约 602 只 × 5 年日线 ≈ 70-80 万行，单次 Tushare 批量补采耗时约 10-20 分钟（复用 _batch_daily 全量逻辑，有完整性检查节流），建议日终后台低优执行；
5. **双表迁移风险**：strategy_signals 的读取方需逐一检索确认（可能含历史报表/回测），迁移后旧表保留 30 天只读备份，回滚=恢复读取路径；
6. **九层兜底**：strategy_signal_detail 无数据时回退实时计算（保持功能可用），避免引入新故障；
7. **标签基线注入影响**：prompt 增强仅约束 LLM 输出对齐，不改引擎计算；若 LLM 判断标签与自身分析冲突，要求标注差异而非强制覆盖（保留叙事价值）。

本方案整合两部分：**展示层（S1-S4）**按 018 规划将机会弹窗简述化、打通"策略分析"按钮跳转、个股页新增现状诊断卡（七维红绿灯+信号生命周期+几何化指标+风险边界）、实现两板块 ts_code 双向往返；**链路层（F1-F5）**按 019-021 评估结论修复：F1 K 线补采（解决 553 只缺数据股两链失效）、F2 策略信号双表清理（strategy_signal_detail 唯一化）、F3 九层解读消费 P2 产物（与标签同源同数据时点）、F4 标签基线注入（结论对齐）。核心原则：**无需统一引擎/另搭预计算**——复用既有 P2/P4 管道，统一数据消费层与输出对齐层；展示层与链路层共同实现"简述发现→详解决策"闭环。**本方案仅为存档，未修改任何代码。**
