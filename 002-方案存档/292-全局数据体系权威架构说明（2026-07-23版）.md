### 1.2 数据流路径

```
采集层 → 存储层 → 计算层(数据计算) → 存储层 → 调用层 → 前端     [标准路径]
采集层 → 存储层 → 调用层 → 前端                             [原始数据无需计算]
采集层 → 存储层 → 计算层(策略核算,用户触发) → 返回前端       [策略分析路径]
调用层 → sync_requests → 采集层 → 存储层 → 调用层            [数据缺失补采路径]
采集层(pipeline驱动) → 存储层(pipeline_status) → 计算层      [管道驱动路径]
  C1~C6采集done → P1~P4预计算done → S1快照done                [日终全链路]
```

### 1.3 进程分工

| 进程 | 文件 | 职责 | 启动方式 | 资源 |
|------|------|------|---------|------|
| **数据进程** | `backend/data_daemon.py` | 实时采集、管道驱动日终（C1~C6采集→P1~P4预计算→S1快照）、完整性检查、sync_requests消费 | launchd 开机自启，后台静默运行 | ~50MB |
| **API 进程** | `backend/run.py` | Flask REST API、SocketIO 推送、前端SPA托管 | `start.command` 手动启动 + 打开浏览器 | ~200MB |

## 第二部分：四层架构红线标准

### 2.1 四层定义

```
┌─────────────────────────────────────────────────────────────┐
│ 采集层 (Collection Layer)                                    │
│   代码位置: backend/data_daemon.py + backend/app/data/       │
│   进程: data_daemon (独立进程)                                │
│   职责: 从外部数据源获取原始数据，写入存储层                    │
│   约束: 不关心谁消费数据，只做采集+写入                         │
│   数据源: 东财HTTP / 新浪HTTP / Tushare / AKShare / mootdx   │
│                                                             │
│   采集频率由 data_daemon 主循环统一管理                       │
│   禁止在 API 进程中触发任何采集操作                            │
│                                                             │
│ 存储层 (Storage Layer)                                       │
│   入口: DataManager (data/__init__.py) — 唯一数据访问网关     │
│   组件: ECM SQLite WAL (盘后) + InMemoryStateStore (盘中)     │
│         + TieredMemoryCache (方法级TTL缓存)                   │
│   约束: 采集层写、计算层读写、调用层只读                        │
│                                                             │
│ 计算层 (Computation Layer)                                   │
│   入口: data_daemon 后台线程                                  │
│   类型1: 数据计算 — 数据到达时自动触发 (MA/MACD/RSI/分钟聚合) │
│   类型2: 策略核算 — 用户触发执行 (缠论/量价/筹码策略分析)      │
│   约束: 只读存储层，不得直连数据源                              │
│                                                             │
│ 调用层 (Call Layer)                                          │
│   代码位置: backend/app/routes/ + backend/app/services/      │
│   职责: 接收前端请求，从存储层读取数据返回                      │
│   约束: 只读存储层，不得直调数据源，不得 use_cache=False       │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 红线规则

**红线 1** — 所有非采集层代码禁止实例化数据源 Provider：
```python
# ❌ 禁止
TushareProvider()
AkshareProvider()
mootdx.Quotes.factory()
```

**红线 2** — 禁止调用 `DataManager.sync_*()` 系列方法（`sync_daily_data`、`sync_stock_list`、`sync_all_daily_data` 等）

**红线 3** — 禁止 `use_cache=False` 参数出现在非采集层代码中

**红线 4** — API 路由中禁止实时计算技术指标。策略核算可按用户操作触发

**红线 5** — 所有数据读取必经 DataManager 只读方法（`get_*`），禁止绕过

**红线 6** — 禁止使用 Mock/随机数据作为数据降级方案

**红线 7** — 分钟K线数据必须持久化到 `minute_kline_cache` 表，禁止直调不落缓存

**红线 8** — 数据缺失时禁止直调数据源降级，必须走 `sync_requests` 异步队列

### 2.3 sync_requests 数据就绪保障机制

```
调用层发现数据缺失
  → DataManager.request_data(task_type, ts_code?)
  → 写入 SQLite sync_requests 表 (status='pending')
  → 返回空结果 / HTTP 503
  → data_daemon 30s 轮询消费
  → 批量同步 (全市场API, 非逐只)
  → 写入存储层 + 标记 status='done'
  → 计算层自动触发预计算
  → 调用层下次请求命中缓存
```

| task_type | 触发的采集函数 | 说明 |
|-----------|---------------|------|
| `full_daily` | `_batch_daily` + `_batch_daily_basic` | 全市场日线+基本面 |
| `full_moneyflow` | `_batch_moneyflow` | 全市场资金流向 |
| `full_basic` | `_batch_daily_basic` | 全市场基本面 |
| `full_stock_list` | `_batch_stock_list` | 股票列表 |
| `per_stock` | `_batch_daily` + 数据补采请求 | 单只股票数据 |
| `adj_factor` | `_batch_adj_factor` | 复权因子 |
| `top10_holders` | `_batch_top10_holders` | 前十大股东 |
| `stk_holder` | `_batch_stk_holder` | 股东人数 |
| `finance_report` | `_batch_finance_report` | 扩展财务 |
| `margin` | `_batch_margin` | 融资融券 |
| `concept` | `_batch_concept` | 概念板块 |

## 第三部分：采集层

### 3.1 实时行情数据源（5s 快照）

#### 主源：东方财富 HTTP API

| 端点 | 方法 | 参数 |
|------|------|------|
| `https://push2.eastmoney.com/api/qt/ulist.np/get` | GET | `fltt=2`, `fields=f2,f3,f4,f5,f6,f7,f8,f9,f10,f12,f14,f15,f16,f17,f18,f20,f21,f37,f38,f39,f40,f41,f45,f46,f48,f50,f57,f58,f60,f61,f62`, `secids=市场.代码` |

- **批量大小**：60只/请求，URL 长度可控
- **并行度**：4~8 线程，全市场 5000 只约 2.6~5.2s
- **字段缩放**：`fltt=2` 返回正确缩放的值（价格直接可用）
- **状态**：✅ 200次连续测试100%成功率，P95=97ms
- **覆盖**：🟡 批量端点不含五档盘口（个股五档走新浪）

**字段映射（东财 → 内部列名）：**

| 字段码 | 标准化列名 | 说明 |
|--------|-----------|------|
| f2 | price | 最新价 |
| f3 | change_pct | 涨跌幅% |
| f4 | change | 涨跌额 |
| f5 | volume | 成交量(手) |
| f6 | amount | 成交额 |
| f7 | amplitude | 振幅% |
| f8 | turnover_rate | 换手率% |
| f10 | volume_ratio | 量比 |
| f12/f57 | code/ts_code | 代码 |
| f14/f58 | name | 名称 |
| f15 | high | 最高价 |
| f16 | low | 最低价 |
| f17 | open | 开盘价 |
| f18 | prev_close | 昨收价 |
| f20 | market_cap | 总市值 |
| f21 | circ_market_cap | 流通市值 |

#### 备源：新浪 HTTP API

```
GET http://hq.sinajs.cn/list=sh600036,sz000001
```

- CSV 格式，按索引位置解析
- 字段[3]=最新价, [4]=最高, [5]=最低
- 字段[10-19]=买五档(vol/price交替), [20-29]=卖五档(vol/price交替)
- 支持五档盘口（全市场快照不需要，个股详情按需查）
- 时效性：与东财完全一致

#### 备源：腾讯 HTTP API

```
GET http://qt.gtimg.cn/q=sh600036,sz000001
```

- `~` 分隔的 CSV，字段丰富
- 含五档盘口字段[7-26]
- 偶有 ~2s 延迟

#### 降级链策略

```
正常状态: 东财(评分>0.9) → 新浪 → 腾讯 → 缓存
降级状态: 新浪(评分0.5~0.9) → 腾讯 → 缓存
紧急状态: 缓存(评分<0.5) → 空DataFrame(前端显示数据延迟)
```

自动降级依据 HealthScorer 每周期评分：
- **评分 0.9~1.0**：正常，继续使用当前源
- **评分 0.6~0.9**：有异常但可用，记录日志
- **评分 < 0.6**：自动切换备源+告警

**L2 标签预计算的执行顺序**（插入在因子预计算之后，为全量日终计算的最后一步）：

```
日终同步 → 指标预计算 → 策略信号预计算 → 因子预计算

### 5.3 数据管道驱动机制（305号§九）

> 取代原有的"定时窗口 + 兜底"模式。data_daemon 主循环每 30s 调用一次 `_drive_pipeline()`，根据 `pipeline_status` 表判断各环节完成情况，自动推进到下一个可执行的环节。

#### 5.3.1 pipeline_status 表

详见 §4.1 的 `pipeline_status` 表定义。每 tick 的状态判断流程：

```
_drive_pipeline() 入口
  │
  ├─ 非交易日？→ 跳过，return
  ├─ 本日管道已完成？→ return
  ├─ 今日数据未到达（daily_cache 行数 < 5000）？→ return
  │
  ├─ C1 pending？→ 执行 C1（日线采集），return
  ├─ C2 pending？→ 执行 C2（基本面采集），return
  ├─ C3~C6 同理...
  ├─ C1~C6 全部 done？→ 继续；否则→ 处理失败重试后 return
  │
  ├─ P1 pending？→ 执行 P1（指标预计算），return
  ├─ P2 pending？→ 执行 P2（策略信号预计算），return
  ├─ P3 pending？→ 执行 P3（因子预计算），return
  ├─ P4 pending？→ 执行 P4（L2标签预计算），return
  │
  ├─ S1 pending？→ 执行 S1（Treemap快照），return
  │
  └─ 全部 done → 标记管道完成
```

#### 5.3.2 完整数据链条

```
链条 ID: daily_pipeline_{YYYYMMDD}

 采集阶段（C 系列）
 ┌─────────────────────────────────────────────────────────────────┐
 │ C1: 日线采集       _batch_daily()         → daily_cache         │
 │ C2: 基本面采集     _batch_daily_basic()    → daily_basic_cache   │

 │ C6: 概念板块采集   _batch_concept()        → concept_cache       │
 │ C7: 财务数据同步   _run_financial_sync()   → fina/income/...     │（后台低优）
 │ C8: 日终补充       adj_factor/top10/...    → 对应 cache 表       │（后台低优）
 │                                                                    │
 │ 完成条件：C1~C6 done → 进入预计算阶段                              │

 └─────────────────────────────────────────────────────────────────┘

#### 5.3.3 幂等性保证

每 tick 执行 `UPDATE pipeline_status SET status='running' WHERE status='pending'`，只抢到锁的 tick 才执行该环节。保证不重复执行。

#### 5.3.4 超时与重试（2026-08-12 更新，327阶段1）

| 条件 | 行为 |
|------|------|
| 环节 `running` 超过 **4 小时**（`mark_step_running` 超时自动重置）| **自动重置为 `pending`**（327阶段1：daemon 重启/崩溃后旧 running 不再永久阻塞管道）|
| `_recover_stale_running()`（每 tick）| 全表扫描清理超时 running → pending + "stale running 重置"标注 |
| `failed` 重试次数 < 3 | 重置为 `pending`，下一 tick 重试 |
| `failed` 重试次数 ≥ 3 | 保持 `failed`，记录日志告警 |
| 某环节 `failed` 且重试耗尽 | 管道在此环节阻塞，**不影响已完成的环节** |

> 原设计"running 超过 30 分钟标记 failed"已废弃——P2 最长 1.6h 会误判；改为 4 小时超时自动重置（远大于最长环节）。

#### 5.3.5 数据驱动日终（2026-08-12 更新，327阶段2）

原 `_drive_pipeline()` 用**当前日期**驱动（今日数据未到达则等待）——非24h开机/错过15:30/隔日启动时永不推进。327阶段2 改为**数据日期驱动**：

```
_drive_pipeline() 入口（327阶段2）
  ├─ _recover_stale_running() 清理超时 running
  ├─ 确定 data_date = daily_cache 最新完整交易日（非当前日期）
  ├─ 无数据 → return（等采集）
  ├─ 该数据日期管道已完成 → return
  ├─ 该日期数据完整（≥4000行）→ 进入环节推进
  │
  ├─ C1~C6：数据完整时标记 done 跳过（"数据已完整，采集跳过"，C6概念独立采集）
  ├─ P1~P4：串行推进预计算
  └─ S1：快照构建
```

**关键**：数据驱动实现**任意时间开机自动补算**（含错过15:30、隔日启动），用最新数据日期而非等待"今天"。

#### 5.3.6 与现有机制的兼容

| 原机制 | 新机制 |
|--------|--------|
| 15:30-15:35 定时窗口触发 `run_daily_sync()` | `_drive_pipeline()` 数据驱动，不再依赖时间窗口 |
| `_daily_sync_triggered` 内存标志 | `pipeline_status` 持久化状态替代 |
| `_SYNCED_TODAY` 内存标志 | `pipeline_date=complete` 替代 |
| `_check_precompute_status()` 开机自检 | `_drive_pipeline()` 开机首次 tick 自动恢复（死代码已删）|
| `_check_daily_sync_backfill()` 兜底 | 由 `_drive_pipeline()` 的"数据日期驱动"自动覆盖 |

`run_integrity_check()` 和 sync_requests 队列保持不变，与管道机制正交运行。

#### 5.3.7 SQLite 并发写锁治理（2026-08-12 新增，方案B + 328号）

**问题**：SQLite WAL 单写者模型——一个连接未提交事务，另一连接写入在 busy_timeout 后报 `database is locked`。历史多次冲突（API 直写、测试并发、WAL checkpoint）。

**实证**：
- 进程内 `_write_lock` + 单连接多线程写 = **160 成功 0 冲突**（采集线程与预计算线程天然串行安全）
- 真实冲突在**跨连接/跨进程**：API 写、测试、手动重算、WAL checkpoint

**治理措施（已实施）**：
1. **方案B（写入者唯一化）**：API 进程移除全部 stock_cache.db 直写（strategy_analyze 缓存 miss 改走 sync_requests）；daemon 为唯一业务写者；用户数据（factors/strategy_templates）独立 db
2. **busy_timeout 5s→30s**：三连接（conn/read_conn/snapshot_conn），覆盖 P4 批量长事务窗口

**剩余（P0 待实施，见 328号 §四）**：minute_full 交易时段限制、WAL checkpoint 时机优化。

#### 5.3.8 非24h开机适配（2026-08-12 新增，328号评估结论）

**场景**：部署电脑非24h开机、使用时间无法强制——前一日未开机日终数据未到位，当日交易时段开机需使用系统。

**结论**：
1. **分钟线完整性有保障**：mootdx 盘中采集（交易时段）+ **Tushare pro_bar 日终回填兜底**（`_batch_backfill_minute_kline`：以日线为基准，缺分钟线的股票用 Tushare 补齐）
2. **进程内采集+预计算不冲突**（锁串行化实测安全）
3. **需整改**：minute_full 加交易时段限制；WAL checkpoint 时机优化（详见 328号方案）

### 7.4 分钟数据覆盖能力

mootdx TCP 协议断裂（2026-07-20）后，`quotes()` 和 `bars()` 返回空，但 **`minutes()` 和 `transactions()` 仍可用**。两者组合可覆盖全天分钟数据：

| 数据源 | 覆盖时段 | 数据类型 | 状态 |
|--------|---------|---------|------|
| mootdx `minutes()` | **09:30~13:29** | 分钟级累计数据 (240点) | ✅ 可用 |
| mootdx `transactions()` | **11:25~15:29** | 逐笔成交明细 (2000笔) | ✅ 可用 |
| 两者合并 | **09:30~15:00 全天** | 1min OHLC | ✅ 实现中 |
| **Tushare pro_bar**（2026-08-12 补充）| **全天任意日** | 1min OHLC（回填）| ✅ 日终回填兜底 |

合并方式：`minutes()` 提供上午骨架，`transactions()` 提供下午逐笔聚合，重叠区以 `minutes()` 为准。最终通过 `_resample_minute()` 聚合为 5/15/30/60 分钟 K 线。

#### 7.4.1 非交易时段分钟线完整性（2026-08-12 补充，328号）

**关键保障**：`_batch_backfill_minute_kline()`（data_daemon）——**日终后任意时间，以日线为基准补齐缺分钟线的股票**：
```
1. 查"今日有日线"的股票列表
2. 查"今日已有分钟线"的股票
3. 缺失股票 → Tushare pro_bar(1min) 补齐（每次限500只，后台低优）
4. 聚合生成 5m/15m/30m/60m
```

**含义**：即使盘中未开机（10:00 才开），**日终后用 Tushare 补齐当日分钟线**——分钟线完整性不依赖开机时段。限制：全市场缺分钟时需多轮回填（500只/轮）。

### A.3 全局速率限制器规范

所有 Tushare API 调用必须通过 `_ts()` 包装器进行，确保 ≤5次/秒的频率：

```python
# 在 data_daemon.py 和 tushare_provider.py 中均需实现
import time as _time
_ts_last_call = 0.0
_TS_MIN_INTERVAL = 0.2  # 5次/秒 → 200ms间隔

def _ts(pro_func, *args, **kwargs):
    global _ts_last_call
    elapsed = _time.time() - _ts_last_call
    if elapsed < _TS_MIN_INTERVAL:
        _time.sleep(_TS_MIN_INTERVAL - elapsed)
    _ts_last_call = _time.time()
    return pro_func(*args, **kwargs)
```

### C.8 交易日/非交易日差异化规则

**交易日判断规则**：
- 使用 `trading_hours.py` 的 `is_holiday()` 函数
- 判断条件：周末（周六/周日）+ 法定节假日

**非交易日采集策略**：

| 采集器 | 交易日 | 非交易日 |
|--------|--------|----------|
| mootdx 快照 | 运行 | 停止 |
| mootdx 分钟线 | 运行 | 停止 |
| AKShare 板块/分钟线/龙虎榜 | 运行 | 停止 |
| Tushare 日终同步 | 运行 | 不运行 |
| 完整性检查 | 运行 | 可选运行（仅数据审查） |

### C.9 交易日分时段采集规则

**时段划分**：

| 时段 | 时间范围 | 时段类型 | 采集活动 |
|------|----------|----------|----------|
| 开盘前 | 09:00-09:15 | 非交易时段 | 数据准备、系统检查 |
| 集合竞价 | 09:15-09:25 | 交易时段 | 盘中实时采集启动 |
| 上午盘 | 09:30-11:30 | 交易时段 | 盘中实时采集 |
| 中午休市 | 11:30-13:00 | 非交易时段 | 数据同步、完整性检查 |
| 下午盘 | 13:00-15:00 | 交易时段 | 盘中实时采集 |
| 收盘处理 | 15:00-15:30 | 非交易时段 | 日终数据采集 |
| 日终处理 | 15:30-16:00 | 非交易时段 | 日终同步、预计算 |
| 夜间维护 | 16:00-09:00 | 非交易时段 | 数据维护、备份 |

### C.10 盘中/日终采集规则

**盘中数据采集**（支撑盘中数据提取和处理）：
- 实时行情：全市场快照（5s）
- 分钟K线：盘中分钟级数据（300s）
- 板块排行：行业板块实时排行（1800s）
- 龙虎榜：当日龙虎榜数据（1800s）
- 舆情新闻：实时舆情信息（1800s）
- 存储：InMemoryStateStore（内存，日终清理）+ minute_kline_cache（持久化）

**日终数据采集**（满足存档后续使用需求）：
- 日线数据：全市场日线OHLCV（15:30批量采集）
- 基本面数据：PE/PB/换手率等（15:30批量采集）
- 资金流向：大单/超大单资金流向（15:30批量采集）
- 补充数据：融资融券/复权因子/股东信息等（非交易时段）
- 存储：ECM SQLite WAL（持久化）
