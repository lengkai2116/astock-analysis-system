# 550｜机会图谱「机会地图」判定链路核查

## 一、摘要

2026-10-26 07:38 对「机会图谱 → 机会地图」做只读核查（API 5001 + SQLite 只读），数据成品日为 **2026-10-23**，共 **5,570 只 / 111 个行业组**。

**结论：状态机内核基本正常，但“机会地图对外呈现的判定”不是单一源，当前不能判定为完全正确。**

- 方块颜色读 `opportunity_state`；浮窗「时机」、时机筛选、「只看重点」、侧栏徽标读 `right_side_confirm`；点击方块进入弹窗时 `opportunity_state` 又被 ECharts 树对象裁掉，回退到 `right_side_confirm`。
- 按「右侧确认→状态」映射后，与真实状态不一致 **4,068 / 5,570 = 73.0%**。
- 状态判定使用的 RSC 与地图展示的 RSC 不一致 **329 只（6.4%）**。
- 5,568 条 `status_snapshot` 中 **299 条** `final_score` 与 `opportunity_state` 不满足阈值映射（287 条为致命冲突 `wait + 30.0`）。

**性质：P1 三项（展示多源、点击字段裁剪、RSC 双源）+ P2 五项（分数/状态冲突、图例漏 reduce、统计卡口径、`mode=opportunity` 空接口、徽标语义）+ P3 两项（stale/2 只空行）。**

## 六、问题清单

### P1-1 浮窗/筛选/侧栏用 RSC，方块颜色用 state（73% 不一致）

**事实**

- 浮窗 `:1208`：`● 时机：${d.rightSideConfirm}`，颜色也用 `timingColor(d.rightSideConfirm, ...)`。
- 筛选 `:1017`：`filtered.filter(s => s.rightSideConfirm === timingFilter)`。
- 只看重点 `:1023`：`nonRejected = filtered.filter(s => s.rightSideConfirm !== '否决')`。
- 侧栏 `:1475`：`CONFIRM_BADGE[s.rightSideConfirm]`。

**量化**

将 RSC 映射为 `强确认→enter / 基础确认→light / 未确认→wait / 否决→avoid`，与真实 `opportunity_state` 对比：**4,068 / 5,570 = 73.0% 不一致**。

| 按钮 | 命中数 | 实际颜色分布 |
|---|---:|---|
| 🟦 可入场（强确认） | 138 | enter 3；wait 113、avoid 10、reduce 6、light 6 |
| 🟨 可轻仓（基础确认） | 509 | light 5；avoid 243、wait 197、reduce 45、enter 19 |
| ⬜ 等待（未确认） | 3,801 | avoid 2,892、reduce 506、wait 382、enter 14、light 7 |
| 🟫 回避（否决） | 1,120 | avoid 1,110、wait 10 |

「只看重点」截取潜力前 20% 共 **890** 只：**avoid 402（45.2%）**、wait 261、reduce 185、enter 33、light 9。

**影响**：用户按“可入场”筛选，得到 138 只，其中只有 3 只是蓝色可入场；悬停“时机：未确认”的方块可能是棕色回避。这是当前最直接的用户可见判定矛盾。

### P1-2 点击方块进入弹窗时，state 等字段被裁掉

**事实**

- `buildTreeData` 返回对象（`:1100-1125`）只有 `rightSideConfirm/confirmEvidence/...`，**没有** `opportunityState`、`consensusRate`、`stateEvidence`、`pePercentile5y`、`pbPercentile5y`、`_raw`。
- 点击处理器 `:1264` 直接 `showDetail(params.data)`。
- `showDetail` 依赖这些字段：`:1891` L4 共识、`:1892` 仲裁标识、`:1902` 高潜力+回避提示、`:1942-1943` 估值分位、`:1970` 本地建议。
- 搜索与 URL 路径（`:926` / `:2275`）传的是完整 `stockItem`。

**结果**

- 点方块进入：`data.opportunityState` 为空 → 时机行回退 `right_side_confirm`；异步 `/diagnose` 只覆盖价位/建议，**不回写时机行**。
- 搜索/URL 进入：同一只股票显示 state 口径。
- **同一股票两种入口两套判定**，且点击入口缺少 L4 共识、估值分位、state 依据。

### P1-3 判定用的 RSC 与展示用的 RSC 是两个源

**事实链**

1. `status_engine._aggregate/_aggregate_v390` 用 `pre_feat` 的 `right_side_confirm` 计算 `opportunity_state`（`status_engine.py:1019-1075`）。
2. `_jud_enrich_with_meta` 之后又用日线执行 `_check_right_side_confirm`，写回 `_jud_meta_cache.right_side_confirm`（`data_daemon.py:5990-6000`、`:6017-6024`）。
3. `_build_treemap_snapshot` 用 `_jud_meta_cache` 覆盖 `treemap_snapshot.right_side_confirm`（`data_daemon.py:6247-6258`）。
4. 状态（`status_snapshot`）不回写，仍保留第 1 步的判定。

**量化**

- 从 `state_evidence` 解析判定用 RSC，与 `treemap_snapshot.right_side_confirm` 对比：可解析 5,176 只，**实际不一致 329 只（6.4%）**。
- 剔除 1,093 条「否决（出现卖出/背离/预跌信号）」与「否决」的文案差异后，实质差异为：
  - 判定“未确认” vs 展示“基础确认”：202
  - 判定“基础确认” vs 展示“未确认”：119
  - 强确认↔未确认：8

**样例（state=enter，evidence 写基础确认，地图显示未确认）**

- `600085.SH 同仁堂`：`right_side_confirm=基础确认 → ×0.8 → 92.0 → enter`；地图 `未确认`。
- `002475.SZ 立讯精密`：同上。
- `920156.BJ 海昌智能`：evidence 基础确认；地图未确认；state=enter。

**交叉影响**

- 33 只 enter 的展示 RSC 不是“强确认”（19 基础 + 14 未确认）。
- 253 只 avoid 的展示 RSC 是“强确认/基础确认”（243 基础 + 10 强）。
- 10 只 avoid 展示“强确认”、6 只 reduce 展示“强确认”。

### P2-1 `final_score` 与 `opportunity_state` 299 行不一致

| 类型 | 数量 | 成因 |
|---|---:|---|
| `wait` + `final_score=30.0` | 287 | `_aggregate_v390` 致命冲突分支 `_v390_result('wait', ..., 30.0)`（`status_engine.py:1142-1144`）；30 分按阈值应落 `reduce` |
| `wait` + 70~92 分 | 11 | 周线向下“丢弃买点→wait”，分数未同步下调（494 号设计） |
| `avoid` + 29.95（显示 30.0） | 1 | 展示四舍五入，实际 <30，非逻辑错 |

**影响**：地图颜色只看 state，不受影响；但 `status_snapshot.final_score`、建议卡、外部消费者会读到“30 分却等待”的成品。

### P2-2 图例/说明漏 `reduce`，可入场门槛文案与实现不符

- `STATE_COLORS.reduce` 橙色，实测 **557 只（10.0%）**。
- `updateLegend`（`:1637`）与 `showLegendHelp` 只列蓝/黄/灰/棕，**没有“减仓”**；筛选按钮也没有 reduce 档。
- 帮助文案“可入场门槛 = 维度共识 ≥67%”，实际 `final_score ≥80`；实测 enter 最小共识 **75.5%**，全部 enter 落深蓝，文案里的“浅蓝 67-70%”无样本。

### P2-3 顶部统计卡两只口径错误

`:354` / `:2225-2231`：

- **“机会信号 (评分≥7)”**：代码统计 `signal_strength >= 70`，实测 **989**；标签仍是旧 0-10 分制“≥7”。
- **“建仓期标的”**：代码按 `s.phase === '建仓期'` 统计，但 `phase` 实际是 `s.main_force_phase`（`building/washing/...`）或旧阈值 `ss >= 7 ? '拉升' : '震荡'`（`:762`），永远不等于“建仓期”，实测 **0**；真实 `main_force_phase=building` 有 **2,589** 只。
- “低估标的” 1,095，口径正确。

### P2-4 `/treemap?mode=opportunity` 实际不可用

实测：

```text
HTTP 200，146 字节
{"code":0,"data":{"mode":"opportunity","groups":[],"data_status":"no_data",...}}
```

原因：`_collect_ts_codes`（`routes/opportunity_atlas.py:155-156`）在 `mode=opportunity` 且无 `tags` 参数时直接 `return explicit`，`explicit` 为空。页面从不调用该接口，而是拉 `mode=market`（9.83 MB）后前端重着色，导致接口契约与页面行为脱节。

### P2-5 “信号缺失”徽标/`pre_compute` 被 2 只股票放大成全局状态

- 5,570 只中仅 2 只 `signal_strength=null`；
- `_build_response` 的 `_missing_ss = any(...)` → `signal_strength_fallback=true`；前端 `checkFallback`（`:1358`）对全部股票读到 true，机会地图全局显示「⚠ 信号缺失」；
- `data_status` 变 `pre_compute`；
- `signal_strength_coverage=0.4257` 实际是 `strength > 0` 的占比（2,371/5,570），不是“非空覆盖率”，易被误读为 57% 未计算。

### P3 其他

- `panel_stale` 用 `snapshot_date < 今天` 判断，10-23 对 10-26 会置 `true`，但中间是周末；页面未消费该字段，暂不影响展示，API 语义不准确。
- `301718.SZ` 名称/行业/信号全空，地图归“其他”，属元数据缺口。

- **推荐 A**：判定与展示同源；代价是需要重跑一次状态成品，影响面大于纯前端。
- **复跑**：`SELECT` 对比 `status_snapshot.state_evidence` 解析 RSC 与 `treemap_snapshot.right_side_confirm`，目标差异 0。
