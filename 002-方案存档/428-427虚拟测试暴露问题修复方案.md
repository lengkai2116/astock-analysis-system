## 2. 问题清单与根因

### D-1 【已修正✅】Tushare daily 系接口"外部不可用"实为日期格式未归一

> 427 判定 C-5 `daily系=0行（Tushare 外部不可用）→ FAIL(外部)`，428 v1.0 据此列为外部问题、排除出方案（原 §5.3）。
> **2026-09-13 实测推翻该归因**——同一 token 对照调用：
> ```
> trade_date='2026-09-11'  → 0 行  （系统实际传的格式）
> trade_date='20260911'    → 1 行  （Tushare 要求的紧凑格式）
> ```

**根因（系统缺陷，非外部）**：Tushare daily 官方要求 8 位紧凑 `YYYYMMDD`，收到横杠 `YYYY-MM-DD` **静默返回空 DataFrame（不抛异常、无权限码）**。系统主通道 `_drive_pipeline` 把 `_get_latest_data_date()`（返回横杠）作为 `today_fmt` 传入 `_batch_*`，再原样透传 Tushare → 0 行；而 `_consume_sync_requests_batch` 用 `datetime.now().strftime('%Y%m%d')`（紧凑）能采到 → 解释开发基准库 daily_cache 09-11=5553 行、COL 主通道却 0 行的矛盾。token/积分（5000+）与对接方式（官方 Python SDK，`ts.set_token`+`pro_api()`）均正常。

**修复（已实施并验证）**：
- **阶段 A（写侧入口归一）**：在统一 Tushare 调用收敛点 `_ts()`（data_daemon.py 与 tushare_provider.py 两处同版）新增 `_to_tushare_date()`，调用前对 `trade_date/start_date/end_date` 做 `YYYY-MM-DD → YYYYMMDD`（仅 str 含横杠才剥，datetime/date 原样）；并加"显式日期却空返回 → WARNING 附参数"告警。沙盒双切实测：横杠日期 `daily` 0→5550 行、落库横杠且幂等无重复；**开发基准数据目录零写入**。
- **阶段 B（读取侧错配）**：存储层全库横杠 `YYYY-MM-DD` 已统一（355号方案规则1），但 `EnhancedCacheManager.get_cached_stk_limit` 与 `get_cached_sentiment_pool` 把紧凑 `trade_date` 原样入 `WHERE trade_date=?`（调用方 quote 端点 market.py:239、market_sentiment_service:55），查库内横杠列 → 0 命中。已在两处读取入口加"查询前紧凑→横杠"归一（幂等，与既有 `get_cached_daily` 惯例一致）。开发基准库只读验证：`stk_limit_cache` 紧凑 `20260911` 命中 5641 行（修复前 0）。
- **核查排除**：`strategy_signal_detail` 开发基准库全横杠无混写（`_write_factor_signals` 用横杠 `today_fmt`；`cache_signal_detail` compact 默认仅缺键才触发）；`app/data/__init__.py sync_daily_data` 透传已被阶段A `_ts` 覆盖，均无需改。
- **原则**：只在 Tushare 调用入口 / 读取查询入口做单向归一，**不改存储层、不改对外 API 返回格式、不触碰前端展示**，最小侵入。

**验证**：ruff 通过（改动文件）、归一逻辑离线自测通过、开发基准库只读命中、既有 `test_273a`（传横杠）不受影响。完整 `make test` 因含数据/网络依赖用例在非沙盒环境天然超时，需沙盒双切后执行（见 §5.4 遗留）。

### P0-1 【高✅已实施】fina_indicator_cache Series 绑参 + 虚报完成（426 P2-2 根治未完成）

**427 测试现象**：COL-7 期间每批 `[财务指标] 逐只获取 100 只股票` 后持续报
`分库写入失败: fina_indicator_cache on financial_cache.db, ProgrammingError: Error binding parameter 29: type 'Series' is not supported`（50+ 次/批），
随后仍输出 `[财务指标] 逐只同步完成，共 100 条`（**虚报**）。真实 daemon 恢复后遇 sync_requests 积压同样发生。

**代码实证（2026-09-13 核查）**：
| 层 | 现状 | 位置 |
|---|---|---|
| ① 写路径值归一化 | `_insert_from_df` rows 构造 `rows = [tuple(r[c] for c in cols) for _, r in df.iterrows()]`——**无标量检查**，Tushare fina_indicator 嵌套对象列（实测 parameter 29=ebitda 列，表 54 列）渗入为 `pd.Series` → sqlite 绑参失败 | enhanced_cache_manager.py:225 |
| ② 异常传播 | `_insert_from_df` 分库写 `except Exception as e: logger.warning(...)`——**自身吞掉不向上抛** → 调用方 `cache_fina_indicator_data` try 不触发、返回 True | enhanced_cache_manager.py:270-276 / 1873-1932 |
| ③ 单表展平 | `cache_fina_indicator_data` 内部有 Series/DataFrame 展平（`s.apply(lambda x: x.iloc[0] ...)`）但**仅本表、仅 object 列**，对 latest 单行 df 的嵌套值不彻底 | enhanced_cache_manager.py:1912-1926 |
| ④ 计数 | `_batch_fina_indicator` `if _ecm.cache_fina_indicator_data(latest): total += 1 else: fail += 1`——因②返回 True → 虚报 | data_daemon.py:1006-1008 |

**修复动作**：
1. `_insert_from_df` rows 构造处**统一值类型归一化**（426 §5.3 动作①落地）：
   ```python
   def _to_scalar(v):
       if isinstance(v, (pd.Series, pd.DataFrame)):
           return v.iloc[0] if hasattr(v, 'iloc') and len(v) else None
       if isinstance(v, (pd.Timestamp, datetime.date, datetime.datetime)):
           return v.strftime('%Y-%m-%d') if isinstance(v, (datetime.datetime,)) else str(v)
       return v
   rows = [tuple(_to_scalar(r[c]) for c in cols) for _, r in df.iterrows()]
   ```
2. `_insert_from_df` **返回写入行数**（成功返回实际 `INSERT OR REPLACE` 行数，失败返回 0，保留 warning 日志）——不影响现有调用（None→int 兼容）。
   > **实现注意**：分库路径存在"列过滤（keep 子集）"分支——分库列是总库子集时部分列被过滤。
   > 返回行数应取**实际写入的 `len(shard_rows)`**（而非过滤前的 `len(rows)`），否则在过滤分支会把
   > 有效行数误判为虚报。总库路径（无过滤）取 `len(rows)` 即可。
3. `cache_fina_indicator_data` 改为：`n = self._insert_from_df(...); return n > 0`（写失败不再返回 True）。
   > **现状校准**：ecm:1873-1935 的 `cache_fina_indicator_data` **已返回 bool，但该 bool 恒为 True**——
   > 它调用的 `_insert_from_df` 写失败只吞异常不返回行数，故 bool 并未真正感知写失败，虚报未根除。
   > 本动作(2)+(3)正是堵住这个盲点，别被"已返回 bool"误判为已修复。
4. 全表统一受益（其他含嵌套值表同样防绑参失败）。

**检验标准**：
- 触发 fina 同步：日志零 `type 'Series'` 错误；
- 写失败场景：`_batch_fina_indicator` 输出 `写入失败 N 条`（不再虚报"共 N 条"）；
- `SELECT COUNT(*) FROM fina_indicator_cache`（financial_cache.db）随同步增长；
- 回归：`make lint` / 既有测试通过。

### P1-1 【中✅已实施】COL-7 财务全量同步 81min（增量缺失）

**427 测试现象**：COL-7 实际执行 4879.9s（81min），每批 500 只 × 4 表全量重拉；本地实测
income/balancesheet/cashflow/fina_indicator 均已覆盖 5,552-5,555 只、MAX end_date=2026-06-30（最新半年报完整）→ **99.9% API 调用为重复**。

**代码实证**：`_batch_income_recent/_batch_balancesheet/_batch_cashflow/_batch_forecast/_batch_fina_indicator`
（data_daemon.py:946/1342/1372/1401/1430）逐只调用 `provider.get_income(code)` 等（每只拉全历史），**无本地最新期检查**；
逐只成本 ~0.3s（`_TS_MIN_INTERVAL=0.2` 限流 + ~0.09s 网络，实测）→ 5,500×4 ≈ 110min 理论下限。
> 注：period 批量接口已实测**不可行**（`EXC: 必填参数, ts_code`，当前 token 权限须逐只）；forecast 虽支持 ann_date 但单日返回 0 行。故**增量跳过为现实路径**。

**修复动作**：
1. 各 `_batch_*` 拉取前查本地该股最新报告期：
   ```sql
   SELECT MAX(end_date) FROM <表> WHERE ts_code=?   -- financial_cache.db
   ```
   `== 目标报告期`（当前 2026-06-30）即跳过（不入 API 队列）；
2. **目标报告期推导**：由 `daily_cache` 最新交易日所在季度末（如 09-11 → 2026-06-30）或 `stocks` 表维护；提供函数 `_target_fin_period()`；
3. 仅对"无本地数据或 MAX(end_date) < 目标期"的股票调用 API（次新股/新披露补采）；
   > **实现注意（forecast 豁免）**：`_batch_forecast` 的 `forecast_cache` 用 `ann_date`（披露日）而非
   > `end_date`（报告期），且该表单日接口返回 0 行（见上文"period 批量接口不可行"注）。若用
   > `MAX(end_date)==目标期` 判定，forecast 因按 ann_date 组织、且常无当期数据，会被**反复判定需拉取**。
   > **建议 forecast 排除在增量跳过外**（或按 `stock_basic` 更新），仅对 income/balancesheet/cashflow/fina_indicator 四表启用
   > `MAX(end_date)` 跳过，避免 forecast 白拉与跳过判定失真。
4. 增量逻辑复用现有 `_ts` 限流（总量自然下降 90%+）。

**检验标准**：
- 二次运行 COL-7（沙盒复测或开发基准触发）：耗时 **<10min**（基线 81min）；
- 日志 API 调用量下降 ≥90%（可加"跳过 N 只（已有最新期）"日志）；
- 数据完整性：`MAX(end_date)` 与行数不变（幂等回归）；
- fina_indicator 同步不再全失败（依赖 P0-1）。

### P1-2 【中✅已实施】RAW 并行超时强制 done（静默标记不完整数据）

**427 测试现象**：RAW-2 原料加工 1714.6s（开发基准 815s 的 2.1 倍）触发 `RAW-2 并行执行超过1800s未完成`，
随后 `mark_step_done` **无条件执行**（"记录全部完成"），RAW-1/2/3 全标 done——若超时线程数据不全也会被静默标记。

**代码实证**：data_daemon.py:5197-5211——`fut.result(timeout=1800)` 超时仅记 warning，`finally` 后
`for s in unfinished_raw: _ecm.mark_step_done(...)` **无条件执行**（426 P0-4 续算机制语义缺陷场景）。

**修复动作**：
1. **超时步骤不标 done**：跟踪 `{s: 是否超时}`，超时步骤标 `failed`（detail=`RAW超时未完成: <s>`）
   或保 `pending`——由下 tick `_drive_pipeline` 续算（426 续算机制：未完成步骤保 pending 续算，写路径幂等）；
2. **进度日志**：RAW-2 主循环每 500 只输出 `RAW-2 进度: N/5553`（诊断慢股票）；
3. **单股超时**：循环内单股计算包 `_run_with_timeout`（如 60s，与 RAW-1 一致）防单股 hang 拖垮全批；
4. **RAW-2 hang 根因专项**（后续定位，可并列）：疑似同库 compute 写锁竞争（RAW-1/2/3 三线程同写 compute_cache.db，
   `_insert_from_df` 单 `_write_lock` 串行）或单股引擎计算卡顿——加日志后复测定位。

**检验标准**：
- 注入"RAW 步骤超时"场景（构造慢步骤）：步骤**不标 done**，下 tick 自动续算，最终仍收敛 15/15；
- RAW-2 运行日志含进度输出；
- 正常场景（无超时）行为不变。
