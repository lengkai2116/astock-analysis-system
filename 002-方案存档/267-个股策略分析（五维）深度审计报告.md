## 二、设计意图澄清

### 2.1 五维策略分析的设计定位

根据方案 215 号（§2.4）和 180 号（§1-2）的定义，五维策略分析的**核心目标**是：

> **对一只股票在任何时刻 t，通过多策略分析生成五维现状特征向量，每个维度输出当前状态的描述性文本，不输出评分和建议。**

它与选股系统的根本区别在于：

| 维度 | 选股系统（screener） | 个股策略分析（indicator-ide） |
|:-----|:--------------------|:----------------------------|
| 目的 | 批量筛选、打分排名 | 个股深度现状识别 |
| 输出 | 数字评分 + 排名 | `direction` + `status_text` + 维度间关系 |
| 用户 | 寻找"哪只股票有机会" | 了解"这只股票当前状态如何" |
| 后续 | 直接推荐 | AI 解读 → 客户自行决策 |

### 2.2 三层架构

```
┌─ Layer 1: 策略现状识别 (E12) ──────────────────────────────┐
│  输入：K线数据 + 可选策略列表                                │
│  处理：SignalComputationService → 5维度独立现状识别          │
│  输出：{direction, status_text, 维特异化字段}                │
│  约束：不输出评分，仅输出状态描述                             │
├─ Layer 2: 交叉验证 (E13) ──────────────────────────────────┤
│  输入：E12 的信号 + status_recognition                       │
│  处理：StatusOutputService.aggregate_v2() → 4条验证链       │
│  输出：verification_chains + dimension_relations             │
│  作用：检测维度间冲突/一致，为 AI 仲裁提供输入                 │
├─ Layer 3: AI 解读 + 仲裁 (E14+E15) ────────────────────────┤
│  E14: DeepSeek 对五维现状 + 验证链 → 自然语言解读 + 情景推演  │
│  E15: WikiConceptMatcher → LLM Wiki 知识库 → 仲裁意见        │
│  输出：供客户参考，不做自动决策                                │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 关键设计约束

方案 215 号 §2.4 明确规定的约束：

- ❌ **不输出任何数字评分**——评分仅用于选股系统
- ✅ **每个维度输出 `status_text`**——供 DeepSeek 生成叙事
- ✅ **卡5输出维度间关系**——冲突/时序/一致，非综合性评分
- ✅ **每次切换股票重新计算**——无前端缓存

## 三、问题深度分析

### 🔴 P0-1: `trade_date_str` 未定义导致 E12 端点始终 500

#### 问题描述

**文件**：`backend/app/routes/strategy_analyze.py:266`

```python
response_data = {
    'ts_code': ts_code,
    'trade_date': trade_date_str,  # ← 当前作用域从未定义
    'dimensions': dimensions,
    'risk_check': risk_check,
}
```

#### 根因追溯

该行位于 `def strategy_analyze()` 函数体内的 `try` 块中，`trade_date_str` 在整个函数的作用域内从未被赋值。Python 在执行 `response_data = {...}` 时立即求值字典中的所有 value，因此当解释器执行到 `'trade_date': trade_date_str` 时抛出 `NameError`。

此变量被 `except` 捕获，随后函数执行到 `return jsonify({'code': -1, 'message': f'策略分析异常: ...'})`，**每次调用 E12 都返回 500**。

#### 历史来源

此 bug 由提交 `c592b9d`（`feat: 全局数据修复 + 全量策略改进实施`）引入。该提交新增了 `response_data` 字典用于暂存 L1 风控结果等字段，但字典中的 `trade_date_str` 从未赋值。值得注意的是 `response_data` 在此后的代码中**从未被使用**——最终响应使用的是另一个变量：

```python
response = {
    'code': 0,
    'data': {
        'trade_date': _today_str(),  # 此处正确
        ...
    }
}
```

因此 `response_data` 本可完全移除或用 `_today_str()` 替换，但残留的未定义变量引用使得函数在赋值时即崩溃。

#### 影响链

```
E12 500 → loadAnalysis() catch → Promise.all 全链失败
  → finishAnalysisReal() 无法执行
  → renderDimensionCards() 无数据
  → renderVerificationChains() 无数据
  → renderNarrative() 无数据
  → 五维卡片全部显示 "加载中..."
```

#### 修复方向

两种方案：
- **方案A（推荐）**：删除 `response_data` 赋值语句及其后续引用（该变量未被使用）
- **方案B**：将 `trade_date_str` 替换为 `_today_str()`

### 🔴 P0-2: `_compute_chip_signal()` 引用未定义变量导致筹码信号静默失败

#### 问题描述

**文件**：`backend/app/services/signal_computation_service.py:468-470`

```python
# 在 _compute_chip_signal() 方法内
'chanlun_score': chanlun_score,                   # ← NameError
'chanlun_recommendation': score_recommendation,    # ← NameError
'score_details': score_details,                   # ← NameError
```

这三个变量 `chanlun_score`、`score_recommendation`、`score_details` **仅定义在 `_compute_chanlun_signal()` 方法中**（第 516-523 行）：

```python
# _compute_chanlun_signal() 内部
chanlun_score = score_result.get("score", 50)
score_recommendation = score_result.get("recommendation", "HOLD")
```

而 `_compute_chip_signal()` 与 `_compute_chanlun_signal()` 是 `SignalComputationService` 类的两个**独立方法**。变量是局部作用域，不存在跨方法共享。执行到 `'chanlun_score': chanlun_score` 时解释器在当前方法作用域中未找到此名称，抛出 `NameError`。

#### 调用链追踪

```
compute_for_stock()
  ├─ _compute_chip_signal()     ← 先调用（第 186-188 行）
  │    └─ NameError at line 468 → except 捕获 → chip_signal = None
  ├─ _compute_chanlun_signal()  ← 后调用（第 193-199 行）
  │    └─ 正常执行，定义 chanlun_score 等变量
  └─ _compute_factor_signal()   ← 后续策略
```

由于 `_compute_chip_signal()` 在 `_compute_chanlun_signal()` **之前**被调用，这些变量不可能在调用时已存在。外层 `try/except`（第 186-191 行）捕获异常后仅记录日志并返回 None，**筹码信号从此永远为空**。

#### 历史来源

此 bug 自 `_compute_chip_signal()` 方法创建时就存在，看起来是开发者误以为 `chanlun_score` 是类级变量或方法间共享变量，但 Python 的方法局部变量不自动跨方法共享。

#### 影响链

```
chip_signal = None → 卡3（筹码与资金）无数据
  → 卡5冲突检测缺少 chip 信号对比
  → E13 验证链中 chip_volume 链缺少筹码输入
  → 用户看不到筹码分析（集中度/获利比例/主力流向等）
```

#### 修复方向

移除 `_compute_chip_signal()` 输出中的这三行（第 468-470 行），它们是 `_compute_chanlun_signal()` 的输出字段，不属于筹码策略。

### 🟡 P1-1: 验证链匹配机制失效

#### 问题描述

**文件**：`backend/app/services/status_output_service.py:247-254`

`aggregate_v2()` 方法调用四条验证链函数，每条函数遍历 `status_list`（即 `status_recognition` 字典列表），通过 `st.get('strategy_name')` 匹配策略名称：

```python
def _verify_chip_volume(self, status_list):
    for st in status_list:
        name = (st.get('strategy_name', '') or '').upper()
        if 'CHIP' in name or '筹码' in name:
            chip_state = str(st.get('state', '')).upper()
        if 'VOLUME' in name or '量价' in name or '成交量' in name:
            volume_state = str(st.get('momentum', {})).upper()
```

#### 根因：数据结构不匹配

`aggregate_v2()` 传入 `signals` 列表，内部提取其 `status_recognition` 字段形成 `status_list`：

```python
status_list = [
    sig.get('status_recognition', {}) or {}
    for sig in signals
    if sig and sig.get('status_recognition')
]
```

各策略的 `status_recognition` 字典结构如下（以筹码为例，`_compute_chip_signal()` 第 443-451 行）：

```python
chip_status = {
    'state': 'ACCUMULATING',
    'state_label': '买入',
    'trend': {'direction': '', 'strength': '', 'stage': phase},
    'momentum': {'level': action, 'score': 0.50},
    'volume': {'state': '', 'structure': ''},
    'support_resistance': {'support': 0.0, 'resistance': 0.0},
    'risk_level': 'MEDIUM',
}
```

**`status_recognition` 中不含 `strategy_name` 字段。** `strategy_name` 仅在原始信号顶层：

```python
# compute_for_stock() 返回的信号顶层
{
    'strategy_name': '筹码主力分析',   # ← 这里
    'signal': 'bullish',
    'status_recognition': { ... },     # ← 这里没有 strategy_name
}
```

因此所有 `st.get('strategy_name')` 返回空字符串，验证链逻辑中所有策略名匹配均失败，每条链执行到末尾返回默认的 `"insufficient data"` 结果。

#### 影响链

```
所有验证链返回 "insufficient data"
  → chain_passed_ratio = 0/4 = 0
  → ai_mode 始终为 'full_analysis'（而非预期的'summary_only'/'arbitrate_conflicts'）
  → E14 interpret_status 得不到验证链输入
  → 交叉验证条显示全部 "insufficient data"
  → 用户得不到任何有意义的验证信息
```

#### 修复方向

两条路径：
- **路径A（推荐）**：在 `aggregate_v2()` 中构造 `status_list` 时同时保留 `strategy_name`，例如改为 `signals` 整体传入验证链函数
- **路径B（最小改动）**：验证链函数接收 `signals` 而非 `status_list`，或为每个 `status_recognition` 补充 `strategy_name` 字段

### 🟡 P1-2: E14 冗余计算信号

#### 问题描述

**文件**：`backend/app/routes/ai_analysis.py:175-176`

```python
computation_service = SignalComputationService()
signals = computation_service.compute_for_stock(ts_code)
```

前端 `switchStock()` 并行调用的数据流：

```
switchStock()
  ├─ loadAnalysis()     → POST /api/v3/strategy/analyze    → compute_for_stock()  # 第1次
  ├─ loadVerification() → POST /api/v3/strategy/status-aggregate → compute_for_stock()  # 第2次
  └─ loadNarrative()    → POST /api/v3/ai/status-interpret → compute_for_stock()  # 第3次
```

**同一只股票在 1 秒内被计算了 3 次完全相同的信号。**

从 `compute_for_stock()` 的实现看（第 64-314 行），每次调用都会：
1. 从数据管理器获取 K 线数据
2. 从 daily_basic/moneyflow/benchmark 加载扩展数据
3. 依次计算 6 个策略信号
4. 持久化到数据库

单次调用约 500-2000ms（取决于数据源响应速度），三次串行/并行调用造成显著性能浪费。在多个股票切换的连续操作中，此问题会被进一步放大。

#### 设计意图对比

215 号文档 §2.5 明确要求 E14 "基于 Layer1 的输出进一步分析，而非重新计算原始信号"：

> "E14 接收 E12 的五维输出（dimensions + status_text），生成 Layer 1 卡内叙事和 Layer 2 跨维度仲裁"

当前实现中 E14 没有接收 E12 的输出作为输入，而是自行从头计算。

#### 修复方向

- **方案A（推荐）**：E14 接受 `dimensions` 和 `verification_chains` 作为可选请求参数，当存在时跳过 `compute_for_stock()`
- **方案B（最小改动）**：`compute_for_stock()` 添加内存级 TTL 缓存（~1s），避免同 ts_code 的重复计算

### 🟡 P1-3: 前端 `triggerArbitrate()` 未调用仲裁接口

#### 问题描述

**文件**：`_ui-prototype/indicator-ide.html:3294-3316`

```javascript
function triggerArbitrate(){
  showToast('⚡ DeepSeek 仲裁已触发...');
  delete _analysisCache[_currentTsCode];
  delete _verificationCache[_currentTsCode];
  // 仅重刷 E12+E13+E14，从未调用 /api/v3/ai/arbitrate
  Promise.all([
    loadAnalysis(...),
    loadVerification(...),
    loadNarrative(...),
  ]).then(...);
}
```

#### 未调用的后端仲裁能力

后端已有但前端不调用的接口：

| 接口 | 文件 | 功能 |
|:-----|:-----|:------|
| `POST /api/v3/ai/arbitrate` | `ai_analysis.py:312` | `WikiConceptMatcher.match()` 匹配市场状态→知识库概念 |
| `POST /api/v3/uidf/consolidate` | `ai_analysis.py:334` | UIDFEngine 三级决策融合（UPF+验证链+AI仲裁） |

`WikiConceptMatcher` 的实现（`ai_context_builder.py:530` 附近）包含针对不同市场状态的预编码知识库引用：

```python
"MEAN_REV": {"concept": "RSI extreme value reversion", 
             "reference": "Mean reversion strategy / RSI reversal",
             "typical_action": "Contrarian trading, reversal factor weight raised to 0.65"},
```

#### 影响

UI 中的"知识库参考"区（`arbSourcesBody`）始终为空，174 号方案设计的"策略评估结果 → 知识库查询 → AI 综合判读"全链路在此中断。

#### 修复方向

`triggerArbitrate()` 应：
1. 调用 `/api/v3/ai/arbitrate` 传入 `market_state` + `status_recognition`
2. 将返回的 `wiki_references` 渲染到 `arbSourcesBody`
3. 可选：调用 `/api/v3/uidf/consolidate` 获取三级决策融合结果

### 🟡 P1-4: BOCIASI 状态映射逻辑错误

#### 问题描述

**文件**：`backend/app/services/signal_computation_service.py:1468`

```python
'state': 'ACCUMULATING' if result['signal'] == 'BUY' 
         else ('DISTRIBUTING' if result['signal'] == 'NEUTRAL' else 'RANGING'),
```

当情绪信号为中性（`signal == 'NEUTRAL'`）时，状态映射为 `DISTRIBUTING`（出货/看空）。

从 `BociasiQuickLine.evaluate()` 的实现看，`NEUTRAL` 表示"情绪低迷"——既不等于看多也不等于看空，只是市场情绪偏冷。将其映射为"出货"是错误的。

#### 影响

情绪维度在 `status_recognition` 中被标记为 `DISTRIBUTING`，此字段会被 E13 验证链中的 `_verify_emotion_fundamental()` 和 `_verify_tech_fundamental()` 读取。虽然验证链匹配本身已失效（P1-1），但即便修复了验证链，此映射错误会导致情绪信号被错误归类为偏空。

#### 修复方向

```python
# 正确映射：
'state': 'ACCUMULATING' if result['signal'] == 'BUY' else 'RANGING',
```

情绪指标不直接映射为"吸筹/出货"状态语义。`BUY` → 积极/活跃，其他状态 → 中性/低迷。投资语言中"ACCUMULATING/DISTRIBUTING"属于主力行为范畴，不应直接套用在情绪指标上。更合理的方案是使用 `ACTIVE/CALM/DEPRESSED` 等情绪域的状态词。

### 🔵 P2: 展示层问题

#### P2-1: Vibe 策略结果被忽略

**文件**：`_ui-prototype/indicator-ide.html`：`renderDimensionCards()` 函数

E12 返回 `dimensions.vibe`（包含信号方向、置信度、描述文本），但 `renderDimensionCards()` 的 6 个 `setId` 调用只覆盖了 chanlun/volume_price/chip/emotion/factor/conflict 六个维度，没有 `vibe` 的展示逻辑。数据计算后在前端被丢弃。

#### P2-2: `data_availability` 未展示

E12 返回的 `data_availability` 字段携带每个数据源的可用性状态（daily_basic/moneyflow/index/market_state 的 boolean），原型中卡5 C区有 `data-completeness` 区域展示各维度的数据完整度百分比（如"卡1·走势结构：100%"），但当前实现中没有将 `data_availability` 映射到该区域。

#### P2-3: 前端缓存导致数据不刷新

前端 `_analysisCache[tsCode]` 在 `loadAnalysis()` 中缓存策略分析结果，后续同股票切换直接返回缓存数据。但 215 号文档 §5 明确要求"策略分析结果：无缓存，每次股票切换重新计算"。此缓存会导致用户在不同时间点查看同一只股票时看到过期分析。

虽然 `triggerArbitrate()` 会清除缓存，但正常的 `switchStock()` 不会。

#### P2-4: 情绪卡片默认隐藏 + 方向映射不完整

- 情绪维度卡 HTML 自带 `style="display:none"`，依赖 JS 在 `finishAnalysisReal()` 中显示。如果勾选的策略名与 `dimMap` 不匹配（如命名差异），卡片无法显示。
- `direction` 的 `'watch'` 值（来自 `StrategySignal.WATCH`）在前端 `direction === 'bullish'` 判定中无对应显示逻辑，一律归为"⚠️ 待确认"，丢失了"持仓观察"的中性语义。

## 五、修复优先级与建议

### 5.1 修复顺序

```
第一批（P0 — 功能不可用，严重且影响范围小）
  ├─ P0-1: 删除/修复 response_data 中的 trade_date_str
  └─ P0-2: 删除 _compute_chip_signal() 中的 chanlun_score 引用

第二批（P1 — 功能错误，但已有异常兜底）
  ├─ P1-1: 修复验证链策略名匹配（传入原始信号或补充 strategy_name）
  ├─ P1-2: E14 复用 E12 信号而非重新计算
  └─ P1-3: triggerArbitrate() 接入 /api/v3/ai/arbitrate
```

### 5.2 关键建议

1. **P0 问题修复应优先于任何新功能开发**——E12 全量 500 和筹码信号静默失败意味着五维分析页面的核心功能不可用。

2. **修复 P1-1（验证链）前应先确认 191 号方案中的 FMZ 10 态扩展是否有对应的代码实现**，验证链的修复应与市场状态扩展同步进行。

3. **E14 的重复计算修复应改为"接受 E12 输出作为输入"的架构**（而不是简单加缓存），保持与 215 号规格书的设计一致。这样 E14 变成纯解读层而非计算层，职责清晰。

4. **`triggerArbitrate()` 的修复应同时接入 E15 仲裁和 UIDF 融合**，实现 174 号方案的"知识库→仲裁→决策"全链路，而非仅重刷数据。

5. **前端缓存移除后应考虑替代方案**：如果 E12 响应时间 > 2s，可以在前端使用非持久化的 session 级缓存（页面关闭即失效），而不是当前的 `_analysisCache[tsCode]` 导致永不刷新。
