# 374 — 分库数据保留策略与回填规范

> **规范目的**：明确各分库中每张表的数据保留周期、回填要求、清理规则，作为后续存储层运维的唯一参考。任何调整须同步修订本文件。
>
> **适用范围**：data/duckdb/ 目录下6个分库 + stock_cache.db（ECM主库）中的全部表。

---

## 一、分库架构总览

```
data/duckdb/
├── market_cache.db      — 行情数据（采集层写入）
├── compute_cache.db     — 预计算结果（RAW/SIG步骤写入）
├── snapshot_cache.db    — 快照成品（JUD/OUT步骤写入）
├── financial_cache.db   — 财务数据（COL-7写入）
├── history_cache.db     — 历史辅助数据
└── system_cache.db      — 系统元数据
```

路由规则见 `sharding_manager.py`，本文件不重复定义路由，仅定义各表的**数据生命周期**。

## 三、管道依赖与最低数据要求

管道每步对数据的最低要求（低于此值则步骤无法执行）：

| 管道步骤 | 输入表 | 最低数据要求 | 说明 |
|---------|--------|:---:|------|
| COL-1~6 | daily_cache 等 | 当日数据 | 采集层写入 |
| COL-7 | fina_indicator 等 | 当日数据 | 财务同步 |
| **RAW-1** | daily_cache | 当日数据 | 指标计算 |
| **RAW-2** | daily_cache + daily_basic | 当日数据 | 特征提取 → pre_feat_cache |
| **RAW-3** | daily_cache | 当日数据 | 因子计算 |
| **SIG** | indicator + pre_feat + factor | 当日数据 | 策略信号 → strategy_signal_detail |
| **JUD** | strategy_signal_detail + tags | SIG产出 | 判定 → treemap/status_snapshot |
| **OUT** | treemap + status_snapshot | JUD产出 | 成品仓透传 |

**关键依赖链**：`RAW-2 → pre_feat_cache → SIG → strategy_signal_detail → JUD → treemap/status_snapshot`

## 四、回填规范

### 4.1 回填触发条件

| 场景 | 触发 | 回填范围 |
|------|------|---------|
| 首次启动 | `run_integrity_check(backfill_days=25)` | 近25个交易日 |
| 数据缺失告警 | `_query_table` 返回行数 < 阈值 | 缺失天数 × 全量 |
| 手动触发 | `python data_daemon.py --backfill <table> <days>` | 指定表+天数 |

### 4.2 各表回填方式

| 表 | 回填函数 | API | 单次可回填量 | 备注 |
|----|---------|-----|:---:|------|
| daily_cache | `_batch_daily(trade_date)` | `pro.daily()` | 1天/次 | 逐日回填 |
| daily_basic_cache | `_batch_daily_basic(trade_date)` | `pro.daily_basic()` | 1天/次 | 逐日回填 |
| moneyflow_cache | `_batch_moneyflow(trade_date)` | `pro.moneyflow()` | 1天/次 | 逐日回填 |
| stk_limit_cache | `_batch_stk_limit(trade_date)` | `pro.stk_limit()` | 1天/次 | 逐日回填 |
| indicator_* | RAW-1管道步骤 | 内部计算 | 全市场/次 | 依赖daily_cache |
| pre_feat_cache | RAW-2管道步骤 | 内部计算 | 全市场/次 | 依赖daily_cache+basic |
| factor_cache | RAW-3管道步骤 | 内部计算 | 全市场/次 | 依赖daily_cache |
| strategy_signal_detail | SIG管道步骤 | 内部计算 | 全市场/次 | 依赖indicator+pre_feat+factor |
| treemap/status_snapshot | JUD管道步骤 | 内部计算 | 全市场/次 | 依赖signal_detail+tags |

### 4.3 回填优先级

```
P0: daily_cache → daily_basic_cache → indicator_* → pre_feat_cache → factor_cache
P1: moneyflow_cache → stk_limit_cache
P2: SIG → strategy_signal_detail
P3: JUD → treemap_snapshot + status_snapshot
P4: win_rate_cache（依赖P2产出30天数据）
```

## 五、清理规则

### 5.1 清理执行时机

- **每月1日**：执行 `_run_data_cleanup()`，清理超期数据
- **每次日终同步后**：检查管道产出表是否需要清理
- **手动触发**：`python data_daemon.py --cleanup`

### 5.2 清理SQL模板

```sql
-- 通用清理（按 trade_date）
DELETE FROM {table} WHERE trade_date < date('now', '-{days} days');

-- 按 updated_at 清理
DELETE FROM {table} WHERE updated_at < date('now', '-{days} days');

-- 清理后 VACUUM（每月1次）
VACUUM;
```

### 5.3 禁止清理的表

以下表**永久保留**，不参与任何清理逻辑：
- `daily_cache`（历史回测基底）
- `indicator_ma` / `indicator_macd` / `indicator_other`（指标基底）
- `factor_cache`（因子基底）
- `adj_factor_cache`（复权因子）
- `stocks`（股票列表）
- `pipeline_status`（管道状态）
