## 一、背景

### 1.1 问题来源

286号总纲审计发现问题 **P2（板块策略实质缺失）**：系统当前无独立的板块策略分析流程，"板块分析"散落四处且质量不达标。

### 1.2 问题的影响

| 影响面 | 当前表现 | 实际缺陷 |
|:-------|:---------|:---------|
| **五维卡4（情绪环境）** | 显示个股行业名 + 个股自己的涨跌幅 | `sector_pct` 实际上是 `pct_chg`，不是板块涨跌幅 |
| **板块轮动信号** | `SectorRotationModel.evaluate()` 用个股收益率冒充板块指标 | 无法识别"个股强但板块弱"或"个股弱但板块强"的背离信号 |
| **选股系统** | L2/L3 无板块维度过滤 | 无法按行业动量/资金流向筛选股票池 |
| **ECM 板块归档** | `akshare_reader.py` 调用的 `read_as_sector_ranking()` 在 ECM 中不存在 | 实时板块数据重启后全部丢失 |
| **资金流向分析** | `get_sector_moneyflow()` 按 `Stock.industry` 聚合个股 | 聚合准不准取决于 `industry` 字段准确性 |

### 1.3 根因

**所有板块分析问题都可归结为一个根因：缺少真实的行业指数日线数据。** 没有行业指数，所有"板块分析"都只能用个股数据拼凑或伪造。

### 2.2 SectorRotationModel 现状

| 项目 | 说明 |
|:-----|:------|
| 文件 | `backend/app/engine/framework/sector_rotation_model.py`（269行） |
| 功能 | 判断行业板块轮动阶段（LEADING/STRENGTHENING/WEAKENING/LAGGING） |
| 接入状态 | **完全未接入**——无任何 Python 代码导入或实例化 |
| 数据缺陷 | 用**个股自身多周期收益率**冒充板块指数数据 |

## 三、数据源方案

### 3.1 方案对比

| 方案 | 数据源 | 覆盖 | 采集方式 | 数据质量 | 与现有系统的匹配度 |
|:-----|:-------|:-----|:---------|:---------|:-----------------|
| **A. 申万行业指数（推荐）** | Tushare `index_daily` | 31个申万一级行业 | 扩展 `_batch_index_daily` | 最权威 | `Stock.industry` 字段与申万分类对齐 |
| **B. AKShare 行业板块** | `ak.stock_board_industry_index_em()` | 80+ 东方财富行业板块 | 新增采集函数 | 够用 | 板块划分与申万不同，映射成本高 |

### 3.2 方案 A 的前提条件

在实施前必须验证 `Stock.industry` 真实数据分布，确认行业名→申万指数代码的映射可行：

```sql
SELECT DISTINCT industry FROM stocks WHERE industry IS NOT NULL AND industry != '' ORDER BY industry;
```

根据查询结果分三种情况处理：

| 情况 | 特征 | 映射策略 |
|:-----|:------|:---------|
| A（期望） | industry 值 = 申万一级行业名（31个左右），如"食品饮料"、"银行" | 直接字典映射 |
| B（可能） | industry 值 = 申万二级/三级行业名（100+），如"白酒"、"半导体" | 多对一映射（子行业→一级行业指数），需维护映射表 |
| C（不匹配） | industry 值与申万分类无关，如东方财富/同花顺分类 | 降级到方案 B（AKShare 行业板块） |

**实施时先执行 `SELECT DISTINCT industry FROM stocks` 确认情况，再决定最终映射策略。**

### 改动 3：SectorAnalysisService（新增服务层）

```
新增: backend/app/services/sector_analysis_service.py

说明:
  封装板块分析的核心逻辑，供五维卡4和后续所有板块需求共用。

接口:
  class SectorAnalysisService:
      def get_sector_context(ts_code: str) -> dict
          返回单只股票的完整板块上下文：
          {
              "sector_name": "食品饮料",
              "sector_index_code": "801120.SI",
              "sector_daily_return": 2.5,        # 今日板块涨跌幅
              "sector_5d_return": 8.3,            # 5日板块涨跌幅
              "sector_20d_return": 15.2,          # 20日板块涨跌幅
              "sector_rank_1d": 5,                # 今日涨跌幅在31个行业中的排名
              "sector_rank_5d": 3,                # 5日涨跌幅排名
              "excess_return_1d": 0.8,            # 个股超额收益（个股涨跌幅 - 板块涨跌幅）
              "excess_return_20d": -2.1,          # 20日超额收益
              "rotation_state": "LEADING",        # 板块轮动状态（基于动量的5态判断）
              "sector_moneyflow_rank": 4,         # 板块资金流向排名
              "sector_moneyflow_net": 12345678,   # 板块资金净流入
              "top_stocks": [                     # 板块内涨幅前3个股
                  {"ts_code": "000568.SZ", "name": "泸州老窖", "pct_chg": 5.2},
              ]
          }

      内部逻辑:
        - rotation_state 判断（内联版，不依赖原 SectorRotationModel）：
            ret_20d > 10% → LEADING
            ret_20d > 5% and ret_5d > 0 → STRENGTHENING
            ret_20d < -5% and ret_5d < 0 → WEAKENING
            ret_20d < -10% → LAGGING
            其余 → NEUTRAL
        - 资金流向排名复用 DashboardService.get_sector_moneyflow()
        - top_stocks 从 daily_cache 按行业分组查询
```

## 六、风险与对策

| 风险 | 影响 | 概率 | 对策 |
|:-----|:-----|:-----|:-----|
| **Tushare 无 index_daily 权限** | 无法采集申万行业指数 | 低 | 降级到 AKShare 方案 B |
| **Stock.industry 与申万分类不匹配** | 行业映射覆盖率低，部分股票无板块数据 | 中 | 先执行 `SELECT DISTINCT industry` 验证，再选映射策略；若覆盖率 < 80% 切换方案 B |
| **行业指数历史数据不足** | 前 60 天 20 日动量不可用 | 中 | 首次采集回填 60 日，滚动生成 |
| **sector_pct 值变化影响前端展示** | 前端五维卡4数值异常 | 中 | 改动 4 中已有适配说明，前后端协同确认 |
| **阶段三影响选股排序（可选）** | 用户看到不同筛选结果 | 高 | 默认关闭，启用需 UI 中显式开启 |

### C. 与 287 号方案的关系

| 维度 | 说明 |
|:-----|:------|
| 数据采集 | 行业指数由 daemon 日终采集，写入 `daily_cache`，与 287 号日终预计算流程衔接 |
| 预计算 | 行业指数仅作为原始数据采集，板块分析指标（排名/轮动）在读取时实时计算，**不纳入** `strategy_signal_detail` 预计算 |
| 路由 | 板块分析数据合入 E12 响应，无需新增独立 API 端点，与 287 号 DeepSeek 分离设计一致 |
