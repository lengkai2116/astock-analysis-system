# 全局数据体系分层架构方案（规则C修订版）

> **核心原则**：全系统统一由全局数据体系获取数据，禁止 Route/Service/Engine 直调 Tushare/AKShare API。DuckDB 为持久全量存储，PG 为盘中短存 + 业务数据，二者差异化定位，非同步副本。

---

## 一、数据存储层定位

| 存储层 | 定位 | 生命周期 | 写入来源 | 读取使用者 |
|:-------|:-----|:---------|:---------|:-----------|
| **DuckDB** | 持久全量存储 | **永久** | `scheduler_manager` 定时同步 + `akshare_collector` as_* | DataManager（盘后查询）、策略/选股/回测/图表 |
| **InMemoryStateStore** | 盘中实时缓存 | **日内**，日终清理 | `akshare_collector` 5线程 | AkshareReader、WS推送、实时查询 |
| **PG（业务表）** | 并发事务数据 | **永久** | Service 层 ORM 写入 | 策略/模板/通知/账户/日志 |
| **PG（`realtime_*` 表）** | 盘中第二副本 | **日终清理** | `akshare_collector` 5线程 | 盘中降级查询 |
| **PG（`Stock` 表）** | 股票名录索引 | **永久（定期同步）** | `DataManager.sync_stock_list()` | 行业JOIN/名称补全/选股统计 |

## 二、数据获取统一入口规则

### 2.1 读取路径（读哪个数据源）

```
                      ┌── 前端 API 请求
                      │
          ┌───────────┴───────────┐
          │       判断时段         │
          │   (is_trading_time)   │
          └───────┬───────┬───────┘
                  │       │
              盘中是     盘后否
                  │       │
          ┌───────┘       │
          ▼                │
  ┌───────────────┐        │
  │ InMemory       │        │
  │ StateStore     │        │
  │ (实时数据)      │        │
  └───────┬───────┘        │
          │                │
          ▼                ▼
  ┌───────────────┐  ┌───────────────┐
  │ DuckDB        │  │ DuckDB        │
  │ as_* 表       │  │ *_cache 表    │
  │ (盘中归档)     │  │ (盘后全量)    │
  └───────┬───────┘  └───────┬───────┘
          │                  │
          │  统一通过 DataManager 或 AkshareReader 读取
          │  ↓               ↓
          └──────┬───────────┘
                 ▼
        ┌────────────────────┐
        │ Service / Route    │
        │ 不直接调用 Tushare  │
        └────────────────────┘
```

### 2.2 写入路径（谁负责写数据）

```
  Tushare API ──→ scheduler_manager.run_daily_sync()
                      │
                      ├→ DuckDB daily_cache          (日线)
                      ├→ DuckDB daily_basic_cache     (基本面)
                      ├→ DuckDB moneyflow_cache       (资金流)
                      ├→ DuckDB index_cache           (指数日线)
                      ├→ DuckDB adj_factor_cache       (复权因子)
                      └→ DuckDB minute_cache           (分钟 K 线, 保留30日)

  AKShare API ──→ akshare_collector (5 线程)
                      │
                      ├→ InMemoryStateStore            (L1 盘中实时)
                      ├→ DuckDB as_* 表                (L2 盘中归档, 保留30日)
                      └→ PG realtime_* 表              (L3 盘中第二副本, 日终清理)
```

### 2.3 红线规则（禁止）

1. **任何 Route/Service/Engine 代码不得 import `TushareProvider` 并直接调用其方法**
2. **任何 Route/Service/Engine 代码不得在循环中调用 Tushare API**
3. **任何 Route/Service/Engine 代码不得直接调用 AkshareCollector 或 AKShare `ak.*` 函数**
4. **任何代码不得直接往 `PG DailyData` 表写数据**（该表即将废弃删除）

### 2.4 例外清单（允许直调 API 的唯一场景）

| 场景 | 允许方式 | 限制 |
|:-----|:---------|:-----|
| 日终定时同步 | `scheduler_manager.run_daily_sync()` → `DataManager` | 仅同步调度器触发 |
| 盘中采集 | `akshare_collector` 5 线程 | 仅采集器调用 |
| **分钟数据盘后补全** | `DataManager` → via `MinuteDataManager` → Tushare `get_minute_data` | 仅走 DataManager 封装，不暴露到 Route 层；结果写入 DuckDB minute_cache 后，后续读缓存 |
| 实时数据不可用时的降级 | `realtime.py` 中 `_fetch_current_market_data()` 调 Tushare | **必须记录日志**，仅作为最终兜底 |

|:-----|:-----|:-----|

| `get_mini_kline()` → `_try_get_index_daily()` | DuckDB daily_cache 优先 → AKShare 降级 → Tushare API 最终降级 | ⚠️ **Tushare API 降级需要加日志标记** |
| `get_market_volume()` | 同上 `_try_get_index_daily()` | ⚠️ 同上 |
| `get_daily_top()` | InMemory 实时(盘中) / PG DailyData JOIN Stock(盘后) | **❌ 需修改——盘后用 DuckDB + Stock 内存 JOIN** |
| `get_sector_changes()` | InMemory 实时(盘中) / PG func.avg GROUP BY(盘后) | **❌ 需修改——盘后用 DuckDB + Stock 内存 JOIN** |
| `get_dashboard_summary()` | PG COUNT(bullish/bearish) | **❌ 需修改——盘后用 DuckDB COUNT** |

**应改为**：

```
盘后走 DuckDB daily_cache + Stock(PG) 两步法：
  步骤 1: DuckDB daily_cache WHERE trade_date=last_date → 取 pct_chg
  步骤 2: PG Stock WHERE ts_code IN (结果集) → 补 name/industry
  （单天约 5000 行，内存 merge 耗时 < 5ms，无性能问题）

盘中走势：
  get_index_summary / sector_changes / daily_top → 走 AkshareDataReader(InMemory)
  数据不可用时 → 降级走 DuckDB（加日志标记）
```

**需修改的文件**：`dashboard_service.py` 中 3 处 PG 查询 + `_try_get_index_daily` 的 Tushare 降级加日志

## 五、数据质量保障

### 5.1 Stock 表同步机制

**问题**：PG Stock 表需匹配交易所实际上市/退市状态。

**方案**：

```
双重保障:
  ① cron 定时任务（每月 1 日 05:00）— 正常运行时的常规执行路径
  ② startup_data_check() 启动检查 — 弥补关机错过的场景，开机时检测 stock 表是否逾期

  DataManager.sync_stock_list() → Tushare stock_basic API

  执行逻辑：
  1. 新股票 → INSERT（ts_code 唯一约束）
  2. 已退市股票 → 标记 status='delisted'（不物理删除，保证历史数据可查）
  3. 名称/行业变更 → UPDATE

  盘后数据同步时：
  - 仅循环 status='L'（正常上市）的股票
  - 退市股票参与策略回测时仍可查历史日线
```

### 5.2 数据一致性检查

所有 DuckDB 数据表，添加定期检查任务（每周）：

```
- daily_cache 最新日期 = 最近交易日？
- daily_basic_cache 股票数 ≈ 5000？
- moneyflow_cache 最新日期 vs daily_cache 一致？
- as_* 表清理是否按期执行？
```

## 六、系统启动数据完整性检查机制

### 6.1 问题背景

生产环境下，电脑关机导致定时任务错过既定时间是常态，而非例外：
- 日终同步（15:30）错过了→ 当日无盘后数据
- Stock 表月度同步（1日05:00）错过了→ 新股/退市/名称变更未更新
- 周度评估/健康检查等错过了→ 分析报告缺失

**需要统一机制**：系统启动时自动检测各数据类定时任务是否逾期，对关键数据任务执行自动补采，确保系统可用性。

### 6.2 设计原则

| 原则 | 说明 |
|:-----|:------|
| **数据任务 vs 分析任务区分** | 仅补数据采集类任务，不补分析/报告类任务（数据已存在，分析结果可手动触发） |
| **幂等执行** | 补采操作必须幂等，重复启动不产生重复数据 |
| **顺序执行** | 启动阶段多个补采任务串行执行（非并行），避免数据依赖冲突 |
| **日志可追溯** | 每次启动检查的结果记录到 `sync_log`，便于排查 |
| **用户无感** | 补采在后台执行，不阻塞系统启动（通过 APScheduler 提交异步 job） |

### 6.3 任务分类与补采策略

| 任务 | cron 时间 | 类型 | 逾期是否补采 | 检查条件 | 补采策略 |
|:-----|:---------|:-----|:-----------|:---------|:---------|
| **日终数据同步** | 每日 15:30 | **数据** | ✅ **补采** | DuckDB `daily_cache.max(trade_date)` < 最近交易日 | 增量同步（从最新日期至今日） |
| **Stock 表同步** | 每月1日 05:00 | **数据** | ✅ **补采** | PG `stock.updated_at.max()` > 35天或记录数 < 5300 | `DataManager.sync_stock_list()` |
| 周度赢率评估 | 周一 06:00 | 分析 | ❌ 不补 | — | 跳过，记录到日志 |
| 策略健康检查 | 周一 06:30 | 分析 | ❌ 不补 | — | 跳过，记录到日志 |
| 周度报告生成 | 周日 20:00 | 分析 | ❌ 不补 | — | 跳过，记录到日志 |
| 月度参数平原校验 | 1日 05:00 | 分析 | ❌ 不补 | — | 跳过，记录到日志 |

### 6.4 检查流程

```
系统启动
    │
    ▼
scheduler_manager.startup_data_check()
    │
    ├─ ① 非交易日？→ 跳过日终检查（日志记录"非交易日跳过"）
    │   交易日  → 查 DuckDB daily_cache max(trade_date)
    │   ├── = 最近交易日 → 跳过（数据已完整）
    │   ├── < 最近交易日 → 提交异步 job：run_daily_sync()
    │   └── = None（无数据）→ 提交异步 job：全量同步
    │
    ├─ ② 查 PG stock 表
    │   ├── max(updated_at) > 35天 → 提交异步 job：sync_stock_list()
    │   ├── 记录数 < 5000 → 提交异步 job：sync_stock_list()
    │   └── 正常 → 跳过
    │
    └─ ③ 分析类任务全部跳过（仅日志记录）
        └─ "分析任务 <task_name> 已跳过（非关键数据，不补采）"
```

### 6.5 实现要点

**`startup_data_check()` 方法**（`scheduler_manager.py`）：

```python
def startup_data_check(self):
    """系统启动数据完整性检查（替代原 catch_up_if_needed）"""
    if not self._app:
        return

    with self._app.app_context():
        # ── 1. 日终同步检查 ──
        self._check_daily_sync()
        # ── 2. Stock 表检查 ──
        self._check_stock_sync()
        # ── 3. 分析类任务日志 ──
        self._log_skipped_analysis_tasks()
```

**`__init__.py` 调用**（替换原有 `catch_up_if_needed()` 调用）：

```python
# 启动数据完整性检查（替代原 catch_up_if_needed）
scheduler_manager.startup_data_check()
```

**异步 job 提交**：补采任务不阻塞启动流程，通过 APScheduler 提交为异步 job。即使补采耗时较长（日终同步约 3~5 分钟），系统其余部分可正常响应请求。

**Stock 表检查的补充判断**：
- `updated_at` 判断适用于已初始化场景
- 记录数 < 5000 判断适用于全新部署场景（首次启动时无 updated_at 可参考）
- 两个条件任一触发即执行同步

### 6.6 同步日志记录

每次启动检查的结果写入 `sync_log`：

| 字段 | 值示例 |
|:-----|:-------|
| `sync_type` | `'startup_check'` |
| `status` | `'success'` / `'partial'`（部分跳过） |
| `details` | `{"daily_sync": "skipped(up_to_date)", "stock_sync": "triggered", "analysis_tasks": "skipped(non_critical)"}` |
