# 系统定时机制用户可配置设计 + 底盘实施路线修正

> **核心原则：** 所有定时参数必须对用户可见、可配置。后台不保留任何影响用户使用习惯的硬编码定时值。
> **关联文档：** 229号（定时机制分析）、225号（系统管理规格书）、231号（底盘审计）

## 一、APScheduler 现有任务的真实角色

### 1.1 scheduler.py 7 个任务逐项追溯

| 任务 | 功能 | 数据来源 | 写入目标 | 阻塞模块？ |
|:-----|:-----|:---------|:---------|:----------:|
| `run_monthly_backtest()` | 6月信号→价格→赢率评估 | PG(StrategyOutput/Signal) + DuckDB | DuckDB win_rates | **否** |
| `run_t5/t10/t20_checkpoint()` | T+N 回测回调检查 | 委托 BacktestEvidenceService | 同上 | **否** |
| `run_weekly_batch_eval()` | 周度批量赢率评估 | 同上 | 同上 | **否** |
| `run_strategy_health_check()` | 策略健康度巡检 | 委托 StrategyHealthMonitor | 日志 | **否** |
| `run_weekly_report()` | 周度验证报告 | 委托 WeeklyReportService | 报告存档 | **否** |
| `run_monthly_parameter_plateau_check()` | 参数平原校验 | 策略引擎 optimizer | logs/ JSON | **否** |

**结论：7 个任务全部是下游维护分析，不阻塞任何模块的页面功能。** 它们需要的恰恰是先有数据同步管道产出完整数据。

### 1.2 14 模块对定时能力的真实需求分类

| 需求类型 | 模块 | 机制 | 是否需 APScheduler |
|:---------|:-----|:-----|:-----------------:|
| 日内实时数据 | 213, 215, 216 | **前端轮询 + TieredMemoryCache**（230号已实施） | ❌ |
| 日终数据同步 | 213, 215, 216, 218, 221, 224, 226 | daily_close_sync + 事件总线 | ✅ cron 触发 |
| 维护分析计算 | 218, 223 | scheduler.py 已有 7 任务 | ✅ 激活即可 |
| 监控周期扫描 | 224 | 多粒度扫描引擎 | ✅ 独立引擎 |
| 定时配置管理 | 225 | RuntimeConfigManager + API | ✅ 配置读取 |

**关键洞察：日内数据刷新不需要 APScheduler。** 前端轮询 → TieredMemoryCache → 缓存命中返回 / 未命中穿透到 AKShare，这已是被动刷新架构，满足日内实时需求。

## 二、daily_close_sync 完整代码链

### 2.1 当前状态：3 个独立 CLI 脚本

```
sync_data.py（146行）
  └─ sync_stocks() → DataManager.get_stock_list() → PostgreSQL stocks
  └─ sync_daily_data(ts_code) → DataManager.get_daily_data() → PostgreSQL daily_data
  └─ 特点：逐股逐行插入，仅演示 15 只股票

incremental_sync.py（121行）
  └─ get_trading_dates_since(MAX(trade_date))
  └─ 每日期: TushareProvider.get_daily_by_date(date) → 全市场 ~5000 只
  └─ PostgreSQL daily_data（仅插入新行，sleep(1) 频率控制）

bulk_sync.py（197行）
  └─ 遍历 Stock 表 → sync_daily_data(ts_code, use_cache=False)
  └─ PostgreSQL daily_data + DuckDB cache warmup
  └─ 有进度条、速度统计、--skip-existing 选项
```

### 2.2 三个断裂点

| 断裂点 | 现状 | 需要 |
|:-------|:-----|:-----|
| 无统一编排器 | 3 个脚本独立运行 | `daily_close_sync()` 统一函数 |
| 无完成事件 | `print()` 输出，无信号 | `blinker` 信号通知下游 |
| 无自动触发 | `if __name__ == '__main__'` | APScheduler cron 触发 |

### 2.3 7 个等待完成事件的模块

| 模块 | 等待后动作 | 当前替代方案 |
|:-----|:----------|:------------|
| 213 仪表盘 | 刷新 DuckDB 缓存 + 重算涨跌榜 | 前端手动刷新 |
| 215 个股策略 | 增量更新日线/基本面/复权因子 | 前端 switchStock() |
| 216 自选监控 | 重算策略评分 | 前端手动刷新 |
| 218 回测 | 更新历史 K 线 | 手动 bulk_sync |
| 221 复盘中心 | **模拟引擎推进一日**（核心循环） | 无法实现 |
| 224 监控通知 | 日终批量评估 | 无法实现 |
| 226 账户管理 | 更新持仓市价 | 无法实现 |

### 2.4 完整触发链路设计

```
15:30 APScheduler cron 触发（时间来自 RuntimeConfigManager）
  │
  ▼
daily_close_sync() ──── scheduler_manager.py 统一函数
  │
  ├─ 1. config.get('scheduling.daily_sync') → 读取用户配置
  ├─ 2. 检查 enabled? → 否 → 记录日志，结束
  ├─ 3. mode == 'incremental' → 增量同步 / 'full' → 全量同步
  ├─ 4. 按 data_types 拉取:
  │     ├─ daily: pro.daily() → PostgreSQL
  │     ├─ basic: pro.daily_basic() → DuckDB
  │     ├─ moneyflow: pro.moneyflow() → DuckDB
  │     ├─ index: pro.index_daily() × 4 → DuckDB
  │     └─ adj_factor: pro.adj_factor() → DuckDB
  ├─ 5. warmup_cache? → DuckDB 预热
  ├─ 6. sync_log 写入: {task, status, duration, stats}
  │
  ▼
daily_sync_completed.send(date, stats, data_types)  ← blinker 信号
  │
  ├─► 仪表盘: 刷新缓存 + 重算涨跌榜
  ├─► 个股策略: 标记日线已更新
  ├─► 自选监控: 重算策略评分
  ├─► 回测系统: 更新历史 K 线
  ├─► 复盘中心: 模拟引擎推进一日
  ├─► 监控通知: 日终批量评估
  └─► 账户管理: 更新持仓市价
```

### 3.5 API 端点设计

**替代原 P1 待建的简单 sync/schedule 端点，升级为完整配置 API：**

| 端点 | 方法 | 功能 |
|:-----|:-----|:-----|
| `/api/v3/system/schedule/config` | GET | 返回全部调度配置（从 RuntimeConfigManager 内存读） |
| `/api/v3/system/schedule/config` | POST | 保存调度配置 + 通知 APScheduler 更新 Job |
| `/api/v3/system/schedule/sync-now` | POST | 手动触发日终同步（不等 cron） |
| `/api/v3/system/schedule/logs` | GET | 调度执行日志（sync_log 表） |
| `/api/v3/system/schedule/next-runs` | GET | 所有 Job 下次执行时间 |

**关键交互：** `POST schedule/config` 保存后，APScheduler 通过 `reschedule_job()` 立即更新 Job 的 cron 触发器，无需重启服务。

### 3.6 APScheduler 动态配置机制

```
启动流程：
  create_app()
    → RuntimeConfigManager.load()           # DB → 内存
    → APScheduler 初始化
    → scheduler_manager.register_all_jobs(config_manager)
      → 从 config 读取各定时参数
      → 创建对应的 cron trigger Job

用户修改配置：
  POST /api/v3/system/schedule/config
    → RuntimeConfigManager.save()           # 写 DB + 更新内存
    → scheduler_manager.reschedule(new_config)
      → scheduler.reschedule_job('daily_sync', trigger=new_cron)
      → scheduler.reschedule_job('weekly_eval', trigger=new_cron)
    → Response: {"success": true, "message": "调度配置已保存，下次执行时间已更新"}
```

**设计原则：APScheduler 的所有 Job 参数永远从 RuntimeConfigManager 读取，绝不硬编码。**

## 四、底盘-模块关系修正

### 4.1 修正 231号方案的判定

| 底盘缺口 | 231号原判定 | 修正判定 | 理由 |
|:---------|:----------:|:--------:|:-----|
| APScheduler 安装+初始化 | 🔴 前置阻塞 | 🟡 **随225号嵌入** | 安装+初始化仅 2h，在系统管理开发时完成 |
| scheduler.py 7 个任务激活 | 🔴 前置阻塞 | 🟢 **不阻塞任何模块** | 全部是维护分析任务，可最后激活 |
| daily_close_sync 编排器 | 🔴 前置阻塞 | 🟡 **随225号嵌入** | 复用现有 CLI 脚本逻辑，包装为定时任务 |
| 事件总线 (blinker) | 🔴 前置阻塞 | 🟡 **随第一个消费者嵌入** | 50 行代码，221号开发时按需添加 |
| RuntimeConfigManager | 🟡 增强 | 🔴 **225号核心交付** | 配置中心是系统管理自身核心功能 |
| 调度配置 API | 🟡 增强 | 🔴 **225号核心交付** | 用户可配置定时是产品级需求 |

### 4.2 结论

**不存在需要先独立完成的"定时基础设施前置工程"。** 所有定时能力自然嵌入模块开发。

唯一要求：**225号系统管理必须第一个开发，且其定时调度配置功能完整交付。** 后续所有模块开发时通过 RuntimeConfigManager 读取用户配置的定时参数。

### 4.3 实施路线

```
Phase 1: 225号系统管理（最先开发，~3天）
```
