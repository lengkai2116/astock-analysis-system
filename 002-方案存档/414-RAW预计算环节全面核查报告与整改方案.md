# 414-RAW预计算环节全面核查报告与整改方案

> **核查范围**：RAW 环节（原料加工）——采集数据到达后的简单加工计算环节
> **核查目标**：计算正确性、预计算有效性、输出存储正确性、代码集中度
> **核查方法**：4 个并行 explore 子代理 + 主代理直接代码审查

---

## 一、RAW 环节架构概述

### 1.1 在管道中的位置

```
COL（采集存储）→ RAW（原料加工）→ SIG（现状分析）→ JUD（判定整合）→ OUT（输出）
```

RAW 是 SIG 的上游——SIG 消费 RAW 的产出（`indicator_*` 宽表、`factor_cache`、`pre_feat_cache`），同时也直接使用采集层的原始数据（`daily_cache`、`moneyflow_cache` 等）。

### 1.2 RAW 内部三步并行

`data_daemon.py:4664` 编排：

```python
RAW_STEPS = {
    'RAW-1': _precompute_indicators,    # 技术指标预计算
    'RAW-2': _precompute_raw_features,  # 特征提取
    'RAW-3': _precompute_preset_combos, # 因子预计算
}
```

三步并行执行（`ThreadPoolExecutor(max_workers=3)`），读同一源表（`daily_cache` 等）写不同目标表，无数据依赖。

### 1.3 各步职责与产出

| 步骤 | 函数 | 目标表 | 产出内容 |
|------|------|--------|---------|
| RAW-1 | `_precompute_indicators` (L4811) | `indicator_ma` / `indicator_macd` / `indicator_other` | MA5/10/20/30/60、MACD(DIF/DEA/HIST)、RSI14、KDJ(K/D/J)、BOLL(UP/MID/LOW)、VOL_MA5/10 |
| RAW-2 | `_precompute_raw_features` (L2211) | `pre_feat_cache`（JSON） | 10+ 组 54+ 字段：估值/情绪/板块/风格/时间/量价/缠论/筹码/事件/深度 + 扩展字段 |
| RAW-3 | `_precompute_preset_combos` (L2007) | `factor_cache` | 7-10 个量化因子：动量/波动率/RSI/量比/乖离/反转 |

### 1.4 预计算消费链路

```
RAW-1 → indicator_ma/macd/other → chart.py（图表渲染）、SIG dim 引擎（data_context）
RAW-2 → pre_feat_cache → StatusEngine._flatten_pre_feat() → tags → dim1-dim7 engines
RAW-3 → factor_cache → SIG factor 引擎、dim4 筹码引擎
```

### 1.5 分钟 K 线数据链路（RAW 涉及部分）

分钟数据在 RAW 阶段通过 `minute_backfill.py` 和 `kline_resampler.py` 进行补采和频率聚合：

```
mootdx TCP / Tushare → minute_kline_cache（1min/5min）
                      → _resample_minute() → minute_kline_cache（15min/30min/60min）
```

## 三、RAW-1 指标预计算问题

### R1 【HIGH】RSI 使用 SMA 而非 Wilder's EMA

- **文件**：`app/indicators/__init__.py:68-69`，`app/factors/builtin/momentum.py:59-60`，`app/factors/builtin/qlib158.py:1310-1364`
- **现状**：`avg_gain = gain.rolling(window=14).mean()` —— 简单移动平均
- **标准**：Wilder's RSI 使用 `ewm(alpha=1/14, adjust=False)` 指数平滑
- **影响**：`indicator_other` 表中全部 `rsi14` 值与券商终端（同花顺/东方财富/通达信）不一致，14周期 RSI 在波动行情中偏差可达 5-8%
- **范围**：影响 `indicator_other` 宽表 + `factor_cache` 中所有 RSI 因子（两处代码独立但公式相同）

### R2 【HIGH】MA120/MA250 未预计算

- **文件**：`app/indicators/__init__.py:31-40`，`app/data/enhanced_cache_manager.py:349-355`
- **现状**：`calculate_all_indicators()` 只计算 MA5/10/20/30/60，`indicator_ma` 表无 MA120/MA250 列
- **运行时重算位置**：
  - `dim3_vp_engine.py:455`：`periods = [3,5,10,20,30,55,60,120,250]`
  - `volume_price_strategy.py:838-846`：`ma120 = float(np.mean(closes[-120:]))`
  - `signal_computation_service.py:219`：尝试读 `ma120` 但永远不存在
- **影响**：SIG 管道每次运行，5000 只股票各触发 2 次冗余 rolling-mean 计算，拖慢管道

### R3 【MED】BOLL 列名不一致

- **文件**：`app/indicators/__init__.py:98-100`，`app/data/enhanced_cache_manager.py:1115-1116`，`app/routes/chart.py:38`
- **现状**：引擎输出 `boll_middle` 和 `boll_mid`（相同值），但 `cache_indicators_wide()` 只存储 `boll_mid`。`chart.py` 引用 `boll_middle`，从预计算缓存中读不到

### R4 【LOW】KDJ 除零风险

- **文件**：`app/indicators/__init__.py:82`
- **现状**：`rsv = (result['close'] - low_min) / (high_max - low_min) * 100`，当 `high_max == low_min`（停牌/一字板）时产生 `inf`/`NaN`，无防护。RSI 有 `1e-10` epsilon 保护但 KDJ 没有

### R5 【LOW】BBI/ENE/九转预计算未存宽表

- **文件**：`app/indicators/__init__.py:109-145`，`app/data/enhanced_cache_manager.py:1100-1121`
- **现状**：`calculate_all_indicators()` 计算了 `bbi`/`ene_upper`/`ene_lower`/`nine_buy`/`nine_sell`，但 `cache_indicators_wide()` 不写入这些列，也不建表存储

### R6 【LOW】预计算最小数据阈值太低

- **文件**：`app/data/precompute_indicator_manager.py:43`，`backend/data_daemon.py:4821`
- **现状**：阈值 `len(df) >= 30`，但 MA60 需要 60+ 行、MACD 需要 26+ 行才有效。30 行数据时 MA60 全为 NaN、MACD 热身不完整，但仍然写入宽表

## 四、RAW-2 特征提取问题

### R7 【MED】创建 Flask app context

- **文件**：`backend/data_daemon.py:2229-2232`
- **现状**：daemon 进程内为 RAW-2 创建完整 Flask 应用实例（`create_app()`），仅为提供 ORM 上下文（Watchlist），增加 ~200MB 内存开销和启动延迟

### R8 【LOW】`_market_stats_cache` 未持久化

- **文件**：`backend/data_daemon.py:2075`
- **现状**：全市场级统计（MA20占比、换手率分位、涨跌停比等 7 项）存为 Python dict，daemon 重启即丢失。所有其他预计算结果都写 SQLite

### R9 【LOW】异常静默吞没

- **文件**：`backend/data_daemon.py:2360-2800`（RAW-2 循环体）
- **现状**：10+ 组特征计算各自 try/except，失败仅 `logger.warning()`，无聚合统计，全量执行完毕后只知道"succeeded/N 只"，无法区分哪些特征组失败

## 五、RAW-3 因子预计算问题

### R10 【MED】RSI 因子与 indicator_other 的 RSI 代码不共享

- **文件**：`app/factors/builtin/momentum.py:59-60` vs `app/indicators/__init__.py:68-69`
- **现状**：两处都用 SMA 版本的 RSI 但代码不共享。修改一处（如改为 Wilder's EMA）另一处不会自动同步，导致 `indicator_other.rsi14` 与 `factor_cache.QLIB_RSI_14` 可能出现不一致

### R11 【MED】因子 `vol` 列名假设脆弱

- **文件**：`app/factors/builtin/volume.py`（27/53/84 行），`app/factors/builtin/qlib158.py`（81-83），`app/factors/builtin/a_stock.py`（866-868）
- **现状**：所有量因子引用 `data['vol']`，`daily_cache` 使用 `vol`（Tushare 约定），但 `minute_kline_cache` 使用 `volume`。RAW-3 目前只处理日线数据不会触发，但如果未来有分钟因子计算会 KeyError

### R12 【LOW】30s/只超时但串行执行

- **文件**：`backend/data_daemon.py:2043-2065`
- **现状**：5000+ 只股票串行处理，每只 30s 超时保护。RAW-3 分配 1800s（30min）总超时，平均 3.6s/只——实际因子计算 <1s 可行，但慢机器有风险

### R13 【LOW】异常完全静默

- **文件**：`backend/data_daemon.py:2046-2054`
- **现状**：`_factor_one` 的 `except Exception: pass` 吞掉所有错误（包括数据损坏、内存错误），仅有 `precomputed` 计数器，无 per-factor 失败统计

## 六、分钟 K 线数据链路问题

### R14 【HIGH】60min K 线聚合对齐错误

- **文件**：`app/data/minute_backfill.py:149-184`，`app/data/minute_data_manager.py:172-210`
- **现状**：`slot = minute_slot // total_min` 按自然分钟除法分组，不尊重 A 股交易时段边界（09:30-11:30, 13:00-15:00）。09:30-10:29 跨越两个 slot（slot 9 和 slot 10），应为一根 60 分钟线实际变为两根
- **影响**：60min 线每日产出 6 根而非标准 4 根，技术分析和图表渲染全部错误。`minute_data_manager.py:_resample_minute` 有完全相同的逻辑（代码副本）

### R15 【HIGH】mootdx tick 伪造 OHLC

- **文件**：`app/data/mootdx_collector.py:876-892`
- **现状**：`mootdx minutes()` 返回 tick 级数据（price+volume），代码将每个 tick 伪造成 1 分钟 K 线：`high = max(price, open) + price * 0.001`，`low = min(price, open) - price * 0.001`
- **影响**：±0.1% spread 是任意值，对波动性大的股票（A 股日内波动可达 5-10%）完全不准确。1 分钟 K 线的 high/low 为伪造值，聚合到 5min/15min/30min 后传播错误

### R16 【MED】`trade_date` 参数被忽略

- **文件**：`backend/data_daemon.py:5021`
- **现状**：`_batch_backfill_minute_kline(trade_date: str = None)` 接受参数但硬编码 `trade_date_fmt = datetime.now().strftime('%Y-%m-%d')`。当前调用方恰好传 `datetime.now()` 所以未触发，但函数签名误导且历史补采会失败

### R17 【MED】回补跳过部分数据股票

- **文件**：`app/data/minute_backfill.py:206-210`（backfill_5min），`minute_backfill.py:319-321`（aggregate_minute）
- **现状**：检查到有任何已有 5min 数据即跳过整只股票，不补缺失日期。如果一只股票仅有 1 天的 5min 数据（来自实时采集器），其余 29 天缺失不会被补采

### R18 【MED】`per_stock` sync_request 无消费者

- **文件**：`app/data/__init__.py:614`
- **现状**：`_get_minute_data()` 数据缺失时写 `sync_requests(task_type='per_stock')`，但 daemon 的 `sync_requests` 消费者仅处理 `full_daily`/`full_moneyflow` 等批量类型，`per_stock` 可能被静默忽略，异步补采实际不生效

### R19 【MED】`_insert_from_df` 绕过 `_write_lock`

- **文件**：`app/data/mootdx_collector.py:216`，`app/data/enhanced_cache_manager.py:133`
- **现状**：`mootdx_collector` 直接调 `_insert_from_df('minute_kline_cache', ...)` 不经 `cache_minute_kline()`，绕过 `_write_lock`。实时采集（5s）和日终补采并发写入可能导致 "database is locked"

### R20 【LOW】v1/v2 回补同时触发

- **文件**：`backend/data_daemon.py:1897-1909`
- **现状**：`_run_minute_backfill`（Tushare）和 `_run_minute_backfill_v2`（mootdx）同时启动。v1 写 1min（不聚合），v2 写 1min + 聚合 5/15/30/60min。1min 数据可能在两个源之间闪烁

## 七、架构散落问题

### R21 【MED】`condition_evaluator.py` 4 个独立计算器

- **文件**：`app/services/condition_evaluator.py:586-852`
- **现状**：自带完整的 `_calc_macd()`（L586，7 调用点）、`_calc_kdj()`（L679，3 调用点）、`_calc_rsi()`（L747，3 调用点）、`_calc_boll()`（L813，3 调用点），从不读预计算缓存
- **定位分析**：此文件为策略模板提供条件检查（如"MACD 金叉"、"KDJ 超买"）。SIG 管道（dim1-dim7）中的 dim2/dim3 已通过昨天的迁移增加了 `_load_precomputed_macd()` + `precomputed` 参数，属于 SIG 内消费 RAW 产出的正确路径。但 `condition_evaluator.py` 是独立于 SIG 引擎的策略模板条件检查器——其内部的 4 个计算器是**用户自定义策略模板**的运行时计算路径，与 SIG 管道的 dim 引擎不同
- **需讨论**：如果策略模板的条件检查在 SIG 管道内触发，应改为消费 RAW-1 预计算结果；如果是用户自定义模板的独立执行路径（如通过 API 按需触发），可能需要保留独立计算，但建议统一调用 `TechnicalIndicatorEngine` 而非各自实现 EMA/KDJ 逻辑

### R22 【MED】3 个 API 路由实时计算指标（违反红线 #3）

- **红线 #3**："API 路由中禁止实时计算技术指标等数据计算（应当在后台预计算）"
- `app/routes/realtime.py:317-325`：`/api/v3/indicator/realtime` 每次 POST 创建 `TechnicalIndicatorEngine()` 全量计算
- `app/routes/phase3.py:59-76`：`/indicators/<ts_code>/calculate` 实时计算 + 写入 SQLAlchemy `TechnicalIndicator` 模型（与预计算宽表独立，造成双写不一致）
- `app/routes/chart.py:539`：信号生成路径直接调用 `calculate_all_indicators(daily_data)`，未尝试预计算缓存

### R23 【LOW】`calc_macd` 5 个独立副本

| # | 位置 | 支持 precomputed |
|---|------|-----------------|
| 1 | `app/indicators/__init__.py:165` | N/A（引擎本体） |
| 2 | `app/engine/framework/chanlun_strategy.py:14` | 否（SIG 内部） |
| 3 | `app/engine/framework/volume_price_strategy.py:328` | 否（SIG 内部） |
| 4 | `app/engine/patterns/adapters/volume_price_adapter.py:356` | 否 |
| 5 | `app/services/condition_evaluator.py:586` | 否 |

其中 dim2/dim3 已有支持 precomputed 的 `_load_precomputed_macd()` + `calc_macd(closes, precomputed=None)` 版本（正确）。chanlun/volume_price 的版本属于 SIG 引擎内部计算，是否需要迁移由设计决定。

## 十、代码集中度评估

### 集中化的正确部分

- **编排层**：`data_daemon.py`（5470行）是 RAW 的唯一编排者，三步并行架构正确
- **存储层**：ECM（`enhanced_cache_manager.py`）统一管理 4 个 SQLite 数据库，读写分离 + WAL 模式
- **计算层**：
  - 指标引擎 `app/indicators/__init__.py` 是唯一权威计算源
  - 因子引擎 `app/factors/` 通过 FactorRegistry 注册管理
  - 特征提取在 `data_daemon.py:_precompute_raw_features` 中集中执行

### 散落的违规部分

| 散落源 | 位置 | 影响 |
|--------|------|------|
| `condition_evaluator.py` | 4 个独立计算器，13+ 调用点 | MACD/KDJ/RSI/BOLL 重算 |
| `chanlun_strategy.py` | 独立 `calc_macd()`，6 调用点 | MACD 重算（SIG 内部） |
| `volume_price_strategy.py` | 独立 `calc_macd()` | MACD 重算（SIG 内部） |
| `realtime.py` | 路由级实时计算 | 违反红线 #3 |
| `phase3.py` | 路由级实时计算 + ORM 写入 | 违反红线 #3 + 双写 |
| `chart.py:539` | 信号路径实时计算 | 未尝试预计算缓存 |

**集中度评估**：~70%——编排和主路径正确集中，但散落的独立计算仍有 6 处。

## 十一、修改建议与实施计划

### Phase 1：HIGH 优先修复（建议 1-2 天内）

#### P1.1 修复 RSI 公式（R1 + R10）
