# 356 — 第2层 STG 存储层分库实施方案与规则体系

## 一、背景与目标

### 1.1 背景

基于355号方案（第1层COL采集层核查报告）的分析，存储层存在以下问题：

1. **单库多表架构**：52张表共享一个SQLite文件，写入时可能相互阻塞
2. **大表WAL膨胀**：adj_factor_cache（788万行）写入时WAL文件膨胀严重
3. **读写冲突**：写操作串行化，无法并发写入不同表
4. **缺少规则体系**：数据格式、质量、读写管理缺少统一规范
5. **缺少存盘点机制**：无定期盘点，数据质量难以保障

### 1.2 目标

1. **运行稳定**：避免锁冲突、超时、死锁
2. **数据准确有效**：确保数据完整、一致、及时
3. **读写效率提升**：优化读写路径，减少延迟
4. **自查纠正能力**：自动检测和修复数据问题

## 四、大表拆分方案

### 4.1 adj_factor_cache 拆分方案

**当前问题**：
- 总行数：788万行
- 数据范围：2001-2026年（25年）
- 写入时WAL膨胀严重

**拆分策略**：按年份拆分

**拆分后结构**：

```
adj_factor_cache (视图，统一访问)
    ├── adj_factor_cache_2001 (1.9万行)
    ├── adj_factor_cache_2002 (9.7万行)
    ├── ...
    ├── adj_factor_cache_2020 (10万行)
    ├── adj_factor_cache_2021 (56万行)
    ├── adj_factor_cache_2022 (110万行)
    ├── adj_factor_cache_2023 (117万行)
    ├── adj_factor_cache_2024 (121万行)
    ├── adj_factor_cache_2025 (124万行)
    └── adj_factor_cache_2026 (70万行)
```

**拆分实施步骤**：

1. **创建新表结构**
```sql
-- 为每个年份创建表
CREATE TABLE adj_factor_cache_2021 (
    ts_code TEXT,
    trade_date TEXT,
    adj_factor REAL,
    cached_at TIMESTAMP,
    PRIMARY KEY (ts_code, trade_date)
);
-- 创建索引
CREATE INDEX idx_adj_2021_date ON adj_factor_cache_2021(trade_date);
CREATE INDEX idx_adj_2021_ts ON adj_factor_cache_2021(ts_code);
```

2. **数据迁移**
```sql
-- 按年份迁移数据
INSERT INTO adj_factor_cache_2021
SELECT * FROM adj_factor_cache
WHERE trade_date LIKE '2021%';
```

3. **创建统一视图**
```sql
-- 创建视图统一访问
CREATE VIEW adj_factor_cache AS
SELECT * FROM adj_factor_cache_2001
UNION ALL
SELECT * FROM adj_factor_cache_2002
UNION ALL
...
SELECT * FROM adj_factor_cache_2026;
```

4. **删除旧表**
```sql
DROP TABLE adj_factor_cache;
```

### 4.2 其他大表拆分建议

| 表名 | 当前行数 | 拆分策略 | 拆分后最大表 |
|------|----------|----------|--------------|
| daily_cache | 635万行 | 按年份拆分 | ~120万行 |

### 4.3 拆分优势

1. **减少WAL膨胀**：单表数据量从788万行降至最大124万行
2. **提升查询效率**：按年份查询时只需扫描单个表
3. **便于数据维护**：可以按年份归档或清理
4. **降低锁竞争**：写入时只锁定当前年份表

## 五、存储层规则体系

### 5.1 数据格式规则

#### 规则1：日期格式统一

- **标准格式**：`YYYY-MM-DD`
- **适用范围**：所有`trade_date`字段
- **采集层职责**：采集时统一转换
- **验证方式**：写入前验证格式

#### 规则2：股票代码格式统一

- **标准格式**：`XXX.SH/SZ/BJ`
- **适用范围**：所有`ts_code`字段
- **采集层职责**：采集时统一转换
- **验证方式**：写入前验证格式

#### 规则3：表头信息规范

- **列名规范**：小写+下划线（如`trade_date`, `ts_code`）
- **数据类型**：明确指定（TEXT/REAL/INTEGER/TIMESTAMP）
- **必填字段**：ts_code, trade_date, cached_at
- **命名约定**：`{数据类型}_cache`（如`daily_cache`）

### 5.2 数据质量规则

#### 规则4：数据完整性

- **价格字段**：close/open/high/low > 0
- **成交量字段**：vol/amount >= 0
- **涨跌幅字段**：-20% <= pct_chg <= 20%
- **基本面字段**：pe/pb/tot_mv > 0

#### 规则5：数据时效性

- **核心数据**：滞后不超过1天（daily_cache等）
- **补充数据**：滞后不超过7天（margin_cache等）
- **背景数据**：滞后不超过30天（fina_indicator等）

#### 规则6：数据一致性

- **跨表一致性**：daily_cache与daily_basic_cache的ts_code交集
- **时间一致性**：同一股票在不同表的日期对齐
- **逻辑一致性**：high >= close >= low

### 5.3 读写管理规则

#### 规则7：写入管理

- **写入锁**：所有写操作通过`_write_lock`串行化
- **批量写入**：使用`executemany`批量插入
- **幂等写入**：`INSERT OR REPLACE`确保数据一致性
- **事务控制**：每次写入后立即commit

#### 规则8：读取管理

- **读写分离**：读操作走`read_conn`，不与写操作冲突
- **缓存优先**：先查TieredMemoryCache，未命中再查数据库
- **并发安全**：WAL模式下多连接并发读安全

#### 规则9：WAL管理

- **Checkpoint频率**：交易时段1800s，非交易300s
- **WAL大小监控**：超过2GB告警
- **WAL收缩**：非交易时段提示执行收缩

### 5.4 数据清理规则

#### 规则10：历史数据清理

- **日线数据**：保留最近3年
- **分钟数据**：保留最近6个月
- **预计算数据**：保留最近1年
- **复权因子**：保留所有年份（按年份拆分）

#### 规则11：过期数据归档

- **归档条件**：超过保留期的数据
- **归档方式**：迁移到历史分库
- **归档验证**：归档前备份原始数据
- **归档记录**：归档后记录日志

#### 规则12：空表清理

- **清理条件**：长期无数据的表
- **清理确认**：确认无业务依赖
- **清理记录**：清理后记录日志

### 5.5 分库管理规则

#### 规则13：分库命名规范

- **命名格式**：`{业务类型}_cache.db`
- **分库类型**：system/market/compute/financial/snapshot/history
- **表命名**：`{数据类型}_cache`

#### 规则14：分库配置规范

- **WAL模式**：所有分库使用WAL模式
- **同步级别**：NORMAL（性能与安全平衡）
- **缓存大小**：根据数据量配置（8MB-32MB）
- **超时设置**：根据读写频率配置（10s-30s）

#### 规则15：跨库查询规范

- **查询限制**：尽量避免跨库查询
- **关联查询**：通过应用层关联，不使用SQL JOIN
- **数据同步**：确保分库间数据一致性

### 5.6 监控告警规则

#### 规则16：WAL监控

- **监控指标**：WAL文件大小
- **告警阈值**：超过2GB告警
- **处理方式**：执行checkpoint收缩

#### 规则17：锁冲突监控

- **监控指标**：database is locked错误次数
- **告警阈值**：每小时超过10次
- **处理方式**：分析锁冲突原因，优化写入策略

#### 规则18：数据质量监控

- **监控指标**：数据完整性、时效性、一致性
- **告警阈值**：根据业务需求设定
- **处理方式**：触发数据修复流程

### 6.2 盘点内容

```sql
-- 检查各表数据量
SELECT table_name, COUNT(*) as row_count
FROM information_schema.tables
WHERE table_schema = 'main'
GROUP BY table_name;

-- 检查数据时效性
SELECT 'daily_cache' as table_name,
       MAX(trade_date) as latest_date,
       JULIANDAY('now') - JULIANDAY(MAX(trade_date)) as days_lag
```

```sql
-- 检查重复数据
SELECT ts_code, trade_date, COUNT(*) as cnt
FROM daily_cache
GROUP BY ts_code, trade_date
HAVING cnt > 1;
```

```sql
SELECT page_count * page_size as db_size
```
