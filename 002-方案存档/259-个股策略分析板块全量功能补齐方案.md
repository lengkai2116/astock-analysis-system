## 2. 全部缺口清单（9项）

### [G1] 🔴 P0 — 前端未接入E14 AI叙事（卡1-4叙事+情景推演+行动建议）

**症状**：卡1-4下方的DeepSeek叙事文本为硬编码Mock；情景A/B/C推演卡片为硬编码HTML（L1020-1035）；行动建议为硬编码（L1027-1035）。
**后端状态**：`POST /api/v3/ai/status-interpret` V2 已实现，`deepseek_analysis_service.py` 988行代码就绪。
**前端代码**：`loadNarrative()` 已挂接E14调用，但返回数据未渲染到叙事区和仲裁区。
**性能影响**：E14耗时3.04秒（DeepSeek API调用），是switchStock全链路最慢环节。

### [G2] 🔴 P0 — `POST /api/v3/ai/arbitrate` 路由未挂载

**后端**：`WikiConceptMatcher.match()` 已编码（`ai_context_builder.py:525`），功能为"接收验证链冲突项，匹配LLM Wiki知识库概念，返回结构化仲裁意见"。**仅缺路由注册**。
**影响**：Layer 2 仲裁意见中的 `wiki_reference` 字段无来源，数据来源追溯（"知识:xxx"标记）无法生成。

### [G3] 🔴 P0 — `POST /api/v3/uidf/consolidate` 路由未挂载

**后端**：`UIDFEngine.consolidate_with_conflicts()` 已编码（`unified_investment_decision_framework.py:104`），功能为"接收UPF输出+verification_chains+AI仲裁结果 → 三级决策融合输出最终信号"。**仅缺路由注册**。
**影响**：策略最终结论缺少UPF/UIDF的跨维度融合。

### [G4] 🔴 P1 — 盘口五档10行 E8 无路由

**症状**：右侧面板盘口（卖五～买五）为硬编码Mock。
**依赖**：mootdx TCP 实时行情或 AKShare `stock_bid_ask_em()`。
****替代方案**：从 mooktdx TCP 的 InMemoryStateStore 读取（已有 mootdx 实时数据流）。

### [G5] 🔴 P1 — 笼子价格+连续竞价 E9 无路由

**症状**：右侧面板笼子价+连续竞价为硬编码占位。
**数据源**：Tushare `stk_limit` 已有缓存（`stk_limit_cache` 表有数据）。

### [G6] 🔴 P1 — 筹码分布 E11 无API路由

**症状**：筹码面板（红蓝柱+白线）使用 `Math.sin()+Math.random()` 纯前端模拟。
**后端状态**：`ChipDistributionEstimator` ✅、`ChipDistributionService.calculate_chip_distribution()` ✅、`chip_distribution_cache` 表 ✅。**仅缺API路由**。

### [G7] 🟡 P2 — 主力密码/资金仓位 无自定义算法

**症状**：两个副图为灰色占位虚线，无任何数据。需基于moneyflow数据推导算法。

### [G8] 🟢 P3 — 融资融券残留代码清理

**症状**：HTML Tab按钮 + JS `getSeries` 函数 + `updateSubHeaders` 分支共3处留有已取消的融资融券代码。215号§7 D1已标注。

### [G9] 🟢 P3 — LLM Wiki知识库搜索路由未实现

**症状**：数据来源追溯（L1074-1078）的"知识:xxx"标记为硬编码HTML，无法真实搜索Wiki。
**备注**：需 `POST /api/v3/llm-wiki/search` 路由 + LLM Wiki 桌面App运行。

## 5. 性能优化策略

针对E14耗时3.04秒的主要瓶颈：

| 策略 | 说明 | 效果预估 |
|:-----|:-----|:---------|
| **E14异步加载** | switchStock时不等待E14完成，策略分析区先显示骨架屏，E14返回后逐步渲染 | 用户感知等待从3s→0s（异步） |
| **E14结果缓存** | 同一股票30分钟内复用前一次分析结果（`_narrativeCache` 已实现但需延长TTL） | 短时间内切换回同一股票免等待 |
| **E14仅对已展开的卡请求** | 默认折叠的卡不请求Layer1叙事，展开时才请求 | 减少初始请求量约60% |
| **E14并行度** | Layer1 5卡可并行请求（5个独立请求 vs 1个聚合请求） | 视DeepSeek API并发限制而定 |
