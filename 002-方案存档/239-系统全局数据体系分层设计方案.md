# 系统全局数据体系分层设计方案（v2 全模块核对版）

> 基于 GitHub 同类项目实践（pythonstock、AKShare-Stock-Sync、TradingAgents-CN）的核心模式：**集中采集 → 统一存储 → 全局共享**。
>
> 本版新增：① 分钟K线的非覆盖式处理方案 ② 14 个模块数据需求全量核对表 ③ 写入策略分类（覆盖式 vs 追回式 vs 按需缓存）

---

## 零、三点核心澄清

### Q1: 覆盖式写入对分钟K线的影响？

**不影响。** 分钟K线属于"追加式"数据（`appending`），而非"覆盖式"（`overwrite`）。两类数据的区分：

| 写入类型 | 数据类 | 说明 | AKShare 表 |
|---------|--------|------|-----------|
| **覆盖式** (overwrite) | 全量快照类 | 整个数据集一次性替换，只保留最新值 | `as_market_snapshot`、`as_sector_ranking`、`as_concept_ranking`、`as_limit_pool`、`as_top_stocks` |
| **追加式** (append) | 时序积累类 | 追加新数据行，保留全部历史 | `as_minute_kline` |
| **按需缓存** (on-demand) | 个股即时查询类 | 查询时写入，过期（TTL）后下次查询刷新 | `as_quote_cache`、`as_lhb_detail`、`as_news` |

**分钟K线的具体方案：**

```
盘中每 5 分钟采集一次（stock_zh_a_hist_min_em）：
  ┌──────────────────────────────────────────────┐
  │ as_minute_kline 表                            │
  │                                               │
  │ ts_code │ trade_date │ time │ open│high│low│close│volume│
  │ ────────┼────────────┼──────┼─────┴────┴───┴─────┴──────┤
  │ 600519  │ 2026-07-02 │ 09:35│  ...                     │
  │ 600519  │ 2026-07-02 │ 09:40│  ...                     │
  │ 600519  │ 2026-07-02 │ 09:45│  ... ← 每 5 分钟追加一行  │
  │ ...     │            │      │                           │
  │ 600519  │ 2026-07-02 │ 15:00│  ← 收盘最后一行           │
  └──────────────────────────────────────────────┘

  盘后（Tushare 日终同步完成 + DuckDB 有完整日线后）→ 清理当日分钟数据
  （因为盘后不再需要分钟K线，全部用 DuckDB 日线替代）
```

**关键点：**
- 分钟K线**积累的是 240 根K线/天/股**（5分钟线 × 4小时），不是无限增长
- 5000 只股票 × 240 根 = 120 万行/天 → 可以考虑只对**活跃关注股**采集（自选股 ~200 只 × 240 根 = 4.8 万行/天）
- 盘后自动清理当日分钟数据（因为日终后有日线覆盖，不需要分钟级精度）

### Q2: 采集器故障时数据怎么办？

```
采集器离线 → as_* 表定格在最后采集时刻
  ├─ 盘中故障（<3分钟）：as_* 表有最近的快照，数据仍可用
  ├─ 盘中故障（>10分钟）：数据开始明显过期
  │   └→ AkshareDataReader 读取接口检测到 last_updated 离当前 > 阈值
  │       └→ 记录日志 + 前端提示"行情数据可能延迟 X 分钟"
  └─ 盘后故障：不影响（as_* 表定格在收盘值，盘后页面读 DuckDB 预聚合）
```

**不会出现"无数据返回"的情况**，因为 as_* 表永远保存最后一次采集的结果。

### Q3: 系统已有 DataSourceManager 为何还要加一层？

DataSourceManager（`data_source_manager.py`）解决的是**数据源选择与降级**（Tushare vs AKShare vs QMT 的自动切换）。但它的设计前提是**按需调用**——每次请求动态选择数据源并调用 API。

本方案新增的 **AkshareCollector + DuckDB as_* 表** 解决的是**数据供给与消费分离**——采集与存储是独立的后台进程，消费方只读不写 API。两者互补：

```
   ┌──────────────┐     ┌────────────────────┐     ┌────────────────┐
   │ 按需请求层    │     │ 后台采集层(新增)     │     │ 数据源路由层    │
   │              │     │                    │     │ (已有)         │
   │ 模块A → 读   │     │ AkshareCollector   │     │ DataSourceMgr │
   │ 模块B → DuckDB│     │  → 定时采 AKShare  │     │  → Tushare    │
   │ 模块C → as_*  │     │  → 写 DuckDB      │     │  → AKShare    │
   └──────────────┘     └────────────────────┘     └────────────────┘
                              ↑                            ↑
                         盘中使用（新增）            盘后使用（已有）
```

## 二、AKShare 写入策略分类（覆盖式 vs 追加式 vs 按需缓存）

### 2.1 三分类详表

| 表名 | 写入策略 | 采集频次 | 数据量 | 过期清理 | 说明 |
|------|---------|---------|-------|---------|------|
| `as_market_snapshot` | **覆盖式** | 15s | ~5000行 | 每次新写入自动覆盖 | 全市场快照，同代码覆盖 |
| `as_sector_ranking` | **覆盖式** | 5min | ~70行 | 同上 | 行业板块排行 |
| `as_concept_ranking` | **覆盖式** | 5min | ~300行 | 同上 | 概念板块排行 |
| `as_top_stocks` | **覆盖式** | 30s | 10-20行 | 同上 | 涨跌榜 |
| `as_limit_pool` | **覆盖式** | 5min | ~100行 | 同上 | 涨跌停池 |
| **`as_minute_kline`** | **追加式** | 5min | ~4.8万行/天(200股) | **盘后清理当日数据** | 分钟K线保留当日积累 |
| `as_lhb_detail` | **按需缓存** | 30min | ~30行 | LRU/TTL | 龙虎榜，覆盖式按日期 |
| `as_news` | **按需缓存** | 30min | ~50行 | LRU/TTL | 新闻，保留最近50条 |
| `as_quote_cache` | **按需缓存** | 按查询 | 查询个股 | TTL/过期 | 个股盘口，非全量 |

### 2.2 分钟K线详细存储方案

```sql
-- 分钟K线表（追加式，盘中积累，盘后清理）
CREATE TABLE IF NOT EXISTS as_minute_kline (
    ts_code VARCHAR,
    trade_date DATE,
    trade_time VARCHAR,       -- HH:MM 格式
    freq VARCHAR,             -- '1min' / '5min' / '15min' / '30min' / '60min'
    open DECIMAL,
    high DECIMAL,
    low DECIMAL,
    close DECIMAL,
    volume DECIMAL,
    amount DECIMAL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (ts_code, trade_date, trade_time, freq)
);

-- 盘后清理（日终同步完成后触发）：
-- DELETE FROM as_minute_kline WHERE trade_date = TODAY()
-- 理由：盘后已有完整日线，不需要分钟精度
```

**采集建议：**
- 5分钟线覆盖自选股 + 当前查看股（~200 只），每 5 分钟采集一次
- 1分钟线只覆盖当前查看股（约 1 只），每 1 分钟采集一次（仅在个股策略页面打开时）
- 15/30/60 分钟线从 5 分钟线聚合，不需要独立采集

### 2.3 采集频次优先级

```
盘中采集总览（5 个独立线程循环）：

Thread 1: 全市场快照     → 15s  → as_market_snapshot  → 覆盖式
Thread 2: 涨跌榜         → 30s  → as_top_stocks       → 覆盖式
Thread 3: 板块排行       → 5min → as_sector/concept    → 覆盖式
          + 涨跌停池
Thread 4: 分钟K线        → 5min → as_minute_kline      → 追加式
          (自选股 ~200 只)
Thread 5: 龙虎榜+新闻    → 30min→ as_lhb_detail/news   → 覆盖/按需

线程间互不影响，每个线程的间隔固定，不要同步等待。
```

### 3.2 与现有 DuckDB 表的互操作关系

```
现有 DuckDB 表（Tushare 盘后，追加式）：
  daily_cache          ← Tushare daily()
  daily_basic_cache    ← Tushare daily_basic()
  moneyflow_cache      ← Tushare moneyflow()
  adj_factor_cache     ← Tushare adj_factor()
  indicator_cache      ← 指标计算
  chip_distribution_cache ← 筹码计算

新增 DuckDB 表（AKShare 盘中，覆盖/追加/按需）：
  as_market_snapshot   ← stock_zh_a_spot_em()
  as_minute_kline      ← stock_zh_a_hist_min_em()
  as_sector_ranking    ← stock_board_industry_name_em()
  ...

命名空间隔离：
  as_*  = AKShare 盘中数据，纯读取索引（主键查询或全表扫描）
  *_cache = Tushare 盘后数据，历史查询（按 ts_code + date 范围查询）
  agg_* = 预聚合数据（未来），日终同步后自动计算

查询路由规则：
  盘中读 as_*（最新值） → 不需要 WHERE trade_date 条件，直接查最新
  盘后读 *_cache（历史值） → 需要 WHERE ts_code + trade_date 条件
  盘后读 agg_*（预聚合） → 直接查 JSON 字段，零计算
```

### 关键设计决策

1. **AkshareCollector 5线程**：独立 daemon 线程，互不等待，仅 A 股交易时段工作
2. **AkshareDataReader 全局单例**：全局唯一的 AKShare 数据读取接口，所有模块只读不写
3. **DuckDB as_* 表写入策略三分类**：覆盖式（5表） / 追加式（1表） / 按需缓存（3表）
4. **连接泄漏防范**：`_get_ecm()` 模块级单例，避免每次调用创建新 DuckDB 连接
5. **盘后清理链**：日终同步完成 → 清理 as_minute_kline → 清理内存缓存 → 清空采集器关注列表
