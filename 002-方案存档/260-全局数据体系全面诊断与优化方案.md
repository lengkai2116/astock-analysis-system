# 全局数据体系全面诊断与优化方案（v3.0）

## 1. 核心架构原则

### 1.1 五层流水线架构

```
┌──────────┐   ┌──────────────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│          │   │                  │   │          │   │          │   │          │
│  采集层   │──→│     存储层       │──→│  计算层   │──→│  调用层   │──→│  使用层   │
│          │   │                  │   │          │   │          │   │          │
│ Collection│   │  ┌────┐ ┌────┐  │   │ Compute  │   │ API Call │   │  Usage   │
│          │   │  │持久│ │短期│  │   │          │   │          │   │          │
│          │   │  │存储│ │存储│  │   │          │   │          │   │          │
│          │   │  └────┘ └────┘  │   │          │   │          │   │          │
└──────────┘   └──────────────────┘   └──────────┘   └──────────┘   └──────────┘
     │                 │                   │               │              │
  只采集入库        原始数据分层       预计算，存入      只读不写，     消费数据
  不关心谁读        存储+生命周期      计算结果         不负责计算     不关心来源
```

**关键规则**：每层**只与相邻层通信**。采集层只知道存储层，不知道 API 的存在。调用层只知道存储层，不关心数据从哪来。

### 1.2 数据流向规则

```
采集层 (data_daemon)
  │  原始数据（日线/快照/基本面/资金流向）
  ▼
┌─────────────────────────────────────────────────────┐
│              存储层 (ECM SQLite)                      │
│                                                      │
│  ┌────────────┐  ┌────────────┐  ┌───────────────┐  │
│  │ 持久存储    │  │ 短期存储    │  │ 计算结果       │  │
│  │ daily_*    │  │ as_* 表    │  │ factor_*      │  │
│  │ moneyflow_*│  │ minute_*   │  │ indicator_*   │  │
│  │ index_*    │  │            │  │ signal_*      │  │
│  │ fina_*     │  │            │  │               │  │
│  └────────────┘  └────────────┘  └───────────────┘  │
│         ▲                            ▲               │
└─────────┼────────────────────────────┼───────────────┘
          │ 读取原始数据                │ 读取计算结果
    ┌─────┴─────┐                     │
    │  计算层    ├─────────────────────┘
    │ (定时任务) │  写回计算结果
    └───────────┘

调用层 (API / run.py)
  │  只读计算结果（或原始数据的轻量聚合）
  ▼
使用层 (前端 / 后端引擎)
```

## 2. 当前架构的问题映射

### 2.1 现状 vs 目标对比

| 维度 | 当前（有问题） | 目标（应做到） |
|:-----|:-------------|:--------------|
| **数据流** | data_daemon 写自己的内存，API 读不到 | 所有数据进存储层，API 只从存储层读 |
| **实时快照** | 只留在 data_daemon 进程的 InMemoryStateStore | 写入存储层，API 从存储层读取 |
| **实时推送** | data_daemon 的 WsBridge 无法到达前端 | API 进程定时读存储层→SocketIO→前端 |
| **计算位置** | API 端点多处自行计算指标/衍生数据 | 计算层在存储层内部完成，API 直接读取 |
| **API 直调数据源** | 多处 route 直调 TushareProvider | 全部改为读存储层 |
| **存储分层** | 未区分持久/短期，16GB DB 无清理策略 | 明确生命周期，定期清理 |
| **数据质量** | 无监控，出错静默跳过 | 启动完整性检查 + 同步日志审计 |

### 2.2 7个具体问题的分层归属

| 问题 | 症状 | 根因归属 | 修复方向 |
|:----|:-----|:---------|:---------|
| **P0-1** 盘口为空 | 买一~五、卖一~五全 `--` | **采集→存储断裂** | mootdx_collector 写入 as_market_snapshot |
| **P0-2** WsBridge 失效 | 实时推送收不到 | **采集→调用断裂** | API 进程定时器负责推送 |
| **P0-3** data_daemon 崩溃 | launchd 启动失败 | **采集层稳定性** | wrapper 脚本 + launchd 加固 |
| **P1-4** 空表 | margin/concept/index_member 等表无数据 | **采集层任务缺失** | 补齐到 data_daemon 日终同步 |
| **P1-5** 日期格式混乱 | 部分表 YYYYMMDD vs YYYY-MM-DD | **存储层规范缺失** | 统一日期存储格式 |
| **P2-6** DataSourceManager 不完整 | Tushare 降级不生效 | **调用层集成不全** | 数据访问统一走 DataManager |
| **P2-7** 同步方法重复 | DataManager 逐只查 vs data_daemon 批量查 | **历史遗留** | 废弃 DataManager 同步方法 |

## 3. 存储层详细设计

### 3.1 物理存储方案

**关键决策**：将实时快照写入**独立的 SQLite 文件**，与日终数据分离，避免写入锁竞争。

```
数据目录 (DATA_DIR)
├── duckdb/                       ← 名称沿用，内容实为 SQLite WAL
│   ├── stock_cache.db            ← 主力库：日线/基本面/资金流向/财务等（持久）
│   │   ├── daily_cache（持久）
│   │   ├── daily_basic_cache（持久）
│   │   ├── moneyflow_cache（持久）
│   │   ├── index_cache（持久）
│   │   ├── adj_factor_cache（持久）
│   │   ├── stk_limit_cache（近1年）
│   │   ├── lhb_cache（近1年）
│   │   ├── fina_indicator_cache（近3年）
│   │   ├── minute_cache（30日）
│   │   └── 计算结果表（取决于更新周期）
│   │
│   └── market_snapshot.db        ← 新增：盘中实时快照库
│       ├── as_market_snapshot     （覆盖写入，每5s）
│       ├── as_top_stocks          （覆盖写入，每5s）
│       ├── as_sectors             （覆盖写入，每30min）
│       ├── as_limit_pool          （覆盖写入，每5s）
│       ├── as_concepts            （覆盖写入，每30min）
│       └── as_news                （覆盖写入，每30min）
│
└── app.db                        ← 业务库（PostgreSQL→SQLite）
                                   Stock/策略/通知/账户等
```

**分离的理由**：

| 方面 | 合库风险 | 分库优势 |
|:-----|:---------|:---------|
| **写入锁** | mootdx 每5s写 + 日终每15:30写 → 可能互锁 | 独立文件，完全无竞争 |
| **文件大小** | 16GB 单文件，VACUUM 耗时长 | 快照库很小（~500MB），可独立维护 |
| **清理策略** | 复杂 DELETE 影响主库查询性能 | 快照库日终直接 DROP/重建 |
| **故障隔离** | 快照写入异常可能损坏整个 DB | 最多丢失盘中快照，不影响日线数据 |
| **备份策略** | 16GB 全库备份成本高 | 日线库按需备份，快照库不备份 |

### 3.2 存储层生命周期管理

| 表 | 存储位置 | 策略 | 执行时机 |
|:---|:---------|:-----|:---------|
| daily_cache | 主库 | **永久** | — |
| daily_basic_cache | 主库 | **永久** | — |
| moneyflow_cache | 主库 | **永久** | — |
| index_cache | 主库 | **永久** | — |
| adj_factor_cache | 主库 | **永久** | — |

| stk_limit_cache | 主库 | 保留近1年 | 每月1日 |
| lhb_cache | 主库 | 保留近1年 | 每月1日 |
| minute_cache | 主库 | 保留30日 | 每日00:30 |
| as_market_snapshot | 快照库 | **永不持久**，日终清空 | 日终同步后 |

### 3.3 实时快照表设计

`as_market_snapshot` 表结构（与 mootdx_collector 输出字段对齐）：

```sql
CREATE TABLE as_market_snapshot (
    ts_code     TEXT PRIMARY KEY,       -- 股票代码
    code        TEXT,
    name        TEXT,
    price       REAL,
    open        REAL,
    high        REAL,
    low         REAL,
    prev_close  REAL,
    volume      INTEGER,
    amount      REAL,
    bid1        REAL,  ask1        REAL,
    bid_vol1    INTEGER,  ask_vol1    INTEGER,
    bid2        REAL,  ask2        REAL,
    bid_vol2    INTEGER,  ask_vol2    INTEGER,
    bid3        REAL,  ask3        REAL,
    bid_vol3    INTEGER,  ask_vol3    INTEGER,
    bid4        REAL,  ask4        REAL,
    bid_vol4    INTEGER,  ask_vol4    INTEGER,
    bid5        REAL,  ask5        REAL,
    bid_vol5    INTEGER,  ask_vol5    INTEGER,
    cached_at   TEXT DEFAULT (datetime('now','localtime'))
);

CREATE INDEX idx_snapshot_ts ON as_market_snapshot(ts_code);
```

写入方式：`INSERT OR REPLACE INTO as_market_snapshot(ts_code, ...) VALUES (?, ...)`
（覆盖式，每只股票仅保留最新一条记录）

## 4. 计算层详细设计

### 4.1 为什么需要计算层

当前许多"计算"散落在 API 端点和 Service 中：

| 当前位置 | 计算内容 | 问题 |
|:---------|:---------|:-----|
| `market.py:198` | `avg_price = amount / (vol * 100)` | 数据单位错误导致 0.03 |
| `signal_computation_service.py` | 策略信号计算 | 每次请求都重算 |
| `indicators/__init__.py` | 技术指标（MA/MACD/KDJ） | 前端请求时才计算 |
| `strategy_analyze.py` | 五维策略分析 | 每次分析请求都重算 |

**目标**：这些计算前置到存储层，按预定周期执行，结果存表。API 直接读取计算结果。

### 4.2 计算任务清单

| 计算任务 | 输入数据 | 输出 | 更新频率 | 当前状态 |
|:---------|:---------|:-----|:---------|:---------|
| 技术指标预计算 | daily_cache | MA5/10/20, MACD, KDJ, RSI, BOLL 等 | 每日日终后 | ⏳ 实时计算 |
| 资金流向衍生指标 | moneyflow_cache | 主力净额/散户净额/5日趋势 | 每日日终后 | ⏳ 部分实时计算 |
| 策略信号计算 | daily + basic + moneyflow | 5维策略评分 | 每日日终后 | ⏳ 实时计算 |
| 因子值计算 | daily + basic + fina | 因子值 | 每日日终后 | ✅ FactorCalculator 已有 |
| 异常检测 | 全市场日线 | 放量/异动/突破信号 | 每日日终后 | ❌ 尚未实现 |
| 盘中衍生计算 | as_market_snapshot | 主力资金方向/筹码变化 | 每5s | ❌ 尚未实现 |

### 4.3 计算策略：灵活的分级方案

不是所有计算都适合提前算好。采用**三级策略**：

```
┌─────────────────────────────────────────────────────┐
│                  计算分级策略                         │
├────────────┬──────────────┬──────────────────────────┤
│  级别       │  策略         │  适用场景                │
├────────────┼──────────────┼──────────────────────────┤
│  Eager     │ 日终后全量算   │ 因子值、技术指标：       │
│  (预计算)   │               │ 数据稳定，计算量大       │
├────────────┼──────────────┼──────────────────────────┤
│  Lazy      │ 首次请求时算   │ 策略信号、五维分析：     │
│  (按需缓存)  │ + 缓存 N 分钟 │ 计算量适中，用户只查少数股 │
├────────────┼──────────────┼──────────────────────────┤
│  Realtime  │ 每次请求实时算  │ 盘口聚合、涨跌统计：     │
│  (实时)     │               │ 依赖最新快照，无法预计算   │
└────────────┴──────────────┴──────────────────────────┘
```

**Eager 预计算**（每日日终后，data_daemon 执行）：
```
1. 指标计算（~30s）：MA5/10/20, MACD, KDJ, RSI, BOLL, DMA, SAR
   输出表: indicator_values(ts_code, trade_date, ma5, ma10, ...)

2. 因子值计算（~2min）：因子注册表中所有可计算因子
   输出表: factor_values(ts_code, trade_date, factor_name, value)

3. 策略信号计算（~30s）：5维策略评分
   输出表: strategy_signals(ts_code, trade_date, signal_chanlun, signal_vp, ...)
```

**Lazy 按需缓存**（API 进程中计算，但结果缓存 N 分钟）：
```
适用场景：单只股票的策略分析报告
缓存策略：TieredMemoryCache，TTL=30min
缓存键：`analysis:{ts_code}`
```

**Realtime 实时**（每次请求都重新计算）：
```
适用场景：盘中实时数据聚合（涨跌分布、涨幅榜）
数据源：as_market_snapshot（最新快照，不缓存）
```

### 4.4 计算层在哪个进程执行

**Eager 预计算** → data_daemon 进程（日终同步后触发）
**Lazy 按需缓存** → API 进程（响应请求时附带缓存）
**Realtime 实时** → API 进程（响应请求时实时计算）

```
data_daemon 进程:
  ┌─ 实时采集线程 (5s) → 写入快照库
  ├─ 日终同步 (15:30)  → 写入主库
  └─ 日终计算 (15:35)  → Eager 预计算（指标/因子/信号）→ 写入主库

API 进程:
  ├─ APScheduler 定时推送 (5s) → 读快照库 → 实时计算 → SocketIO
  ├─ REST API → 读主库（预计算结果优先，降级到实时计算）
  └─ Lazy 缓存：首次计算后缓存 30min
```

### 5.2 API 实时推送改造

**当前（断裂）**：
```
data_daemon: mootdx 采集 → InMemoryStateStore → WsBridge.emit() → 虚空
```

**改造后**：
```
采集层只管写快照库，不做推送

data_daemon:
  mootdx 采集 → 写入快照库 as_market_snapshot ✅
                                      ↓
API 进程 APScheduler（每5s，仅交易时段）:
  └─→ 读快照库 as_market_snapshot
        ├─→ 涨跌分布    → SocketIO emit('market:summary')
        ├─→ 涨幅榜/跌幅榜 → SocketIO emit('market:top_stocks')
        ├─→ 板块排行    → SocketIO emit('market:sectors')
        └─→ 匹配自选股  → SocketIO emit('stock:quotes')
```

这样每层职责边界清晰：
- **采集层**：写存储，不关心谁读
- **存储层**：存数据，不关心谁消费
- **调用层**：读存储+推送，不关心数据来源

## 6. 性能影响全面评估

### 6.1 逐迭代评估

#### 迭代1：实时快照入库（mootdx → 快照库）

| 因素 | 数据 |
|:-----|:-----|
| 每次写入行数 | ~2000 行 |
| 写入方式 | `INSERT OR REPLACE`（覆盖）|
| 写入耗时 | ~150-300ms |
| 采集间隔 | 5s |
| **写入耗时占比** | **3%-6%**，对采集周期基本无影响 |

**风险点**：SQLite 写入有锁。如果采集线程 A 写入时，采集线程 B 也尝试写入，会等待。解决方案：WAL 模式 + `BUSY_TIMEOUT=5000` + 单线程写入。

#### 迭代2：API 进程每5s定时推送

| 步骤 | 预估耗时 |
|:-----|:--------|
| 读快照库最新数据 | ~50ms |
| 计算涨跌分布（~2000行内存计算）| ~10ms |
| SocketIO emit | ~5ms |
| **总计** | **~65ms / 每5s** |

每5s占用 API 进程 ~65ms，对于响应 HTTP 请求几乎没有影响（APScheduler 任务异步执行，不阻塞 Flask 请求处理线程）。

#### 迭代3：launchd 加固

**影响**：零。只影响启动可靠性，不影响运行耗时。

#### 迭代4：补齐空表同步

| 新增同步任务 | Tushare 调用 | 耗时 |
|:-------------|:-------------|:-----|
| `_batch_margin()` | 1次 API | ~3s |
| `_batch_concept()` | 2次 API | ~10s |
| `_batch_index_member()` | 3-5次 API | ~5s |
| `_batch_win_rate()` | 不调外部API | ~2s |

**当前日终同步耗时**：~30-60s（5类数据）
**新增后总耗时**：~50-80s。15:30触发，最迟 15:32 完成。完全可接受。

#### 迭代5：统一日期格式 + 存储清理

- `_fmt_date()` 格式转换：耗时 <0.001ms，可忽略
- 存储清理 DELETE：每月/每日一次，低负载时段执行（00:30），对用户无感

#### 迭代6：消除 API 直调 Tushare

**这是显著的正向性能提升**——本地 SQLite 读取 vs 远程 HTTP API 调用：

| 端点 | 当前耗时 | 改后耗时 | 改善 |
|:-----|:--------|:--------|:-----|
| `GET /api/v3/watchlist/quotes` | 3-5s（逐只调 Tushare）| 50-100ms（读主库）| **30-50x** |
| `GET /api/v3/market/overview` | 1-3s（调 Tushare 取指数）| 20-50ms | **20-60x** |
| `GET /api/v3/backtest` | 2-5s（取基准数据）| 20-50ms | **40-100x** |

#### 迭代7：计算层落地

前端每次切换 K 线时：
- **当前**：技术指标实时计算 → 200-500ms
- **改后**：读预计算结果 → 10ms（**20-50x 提升**）

代价是日终多花 ~3 分钟做预计算，完全在合理范围。

### 6.2 汇总对比

| 指标 | 当前 | 改后 | 变化方向 |
|:-----|:-----|:-----|:---------|
| **采集周期** | 5s | 5s（+0.3s 写入） | ⚠️ 小幅增加，不影响 |

| **DB文件大小** | 16GB（无清理） | 逐步下降（有清理） | **正向** |
| **计算耗时/请求** | 200-500ms（实时算） | 10ms（读表） | **大幅正向** |

### 6.3 唯一的新增持续开销

写入快照库每5s ~2000行，全天约 4 小时交易时段 → 约 2,880 次写入 → 每次 ~200KB → 全天约 **576MB** 写入量。对于现代 SSD（通常可承受 300-500TBW），年化磨损约为 0.02%，可忽略。

## 7. 架构稳定性与效率深度评估

### 7.1 冷启动问题

**问题**：系统开机后，快照库为空。API 的推送任务立即启动，但读不到数据。

**影响**：开机后前 5-10s，前端推送为空。等 mootdx 完成第一轮采集并写入后，数据恢复正常。

**缓解方案**：
- 推送任务首次启动时，延迟 10s 再执行（给采集层一个采集周期）
- 推送内容携带 `cached_at` 时间戳，前端据此显示"数据加载中"状态

### 7.2 采集层故障隔离

**问题**：如果数据_daemon 进程崩溃，快照库不再更新。但 API 进程还在每5s读快照库→推送给前端"旧数据"。

**影响**：前端看到的是过时行情，用户可能基于过时数据做决策（比没数据更危险）。

**缓解方案**：
- 推送任务检查快照库 `cached_at` 与当前时间的差值
- 如果超过 30s 无更新，推送 `staleness_warning` 事件，前端展示"数据可能延迟"
- 如果超过 5min 无更新，推送 `data_offline` 事件，前端展示黄色警告栏

### 7.3 快照库故障不影响主库

**问题**：快照库 SQLite 文件损坏怎么办？

**缓解方案**：
- 快照库和主库分离，故障完全隔离
- 快照库损坏时，API 的推送任务静默降级（不推送），不影响 REST API 的主库数据读取
- 快照库可随时删除重建（盘中数据无历史价值）

### 7.4 高并发写入注意事项

mootdx_collector 使用多线程采集：
- `collect_market_snapshot()` 主线程分批查询（~26批 × 100只）
- 但写入是单线程的（在函数末尾统一写入）

需要确保写入操作**线程安全**：
- 使用 SQLite `BUSY_TIMEOUT=5000`，避免写入冲突
- 不要拆分写入（每只一条 INSERT），而是批量写入（一次写入全部 2000 行）
- 使用 `executemany()` 或 `pd.DataFrame.to_sql()` 批量方式

### 7.5 ECM 主库 16GB 文件维护

**问题**：16GB 的 SQLite 文件，日积月累后查询性能下降。

**缓解方案**：
- 定期执行 `VACUUM`（每月1日低负载时段），回收删除空间，重建索引
- 日常查询必须走索引（`WHERE ts_code=? AND trade_date BETWEEN ? AND ?`），禁止全表扫描
- 确保 `daily_cache` 有 `(ts_code, trade_date)` 复合索引

### 7.6 数据时序一致性

**问题**：mootdx 每5s写入一次快照库，API 进程每5s读一次。可能读到"半写"的数据吗？

**分析**：SQLite WAL 模式下，写入在一个事务中完成（`INSERT OR REPLACE` 批量语句）。读取不会读到未提交的数据，因为 WAL 模式保证读写隔离。

**结论**：不存在读到半写数据的问题。但可能出现：
- 上一批数据和下一批数据之间，API 读到的是**稳态**（要么全是旧数据，要么全是新数据）
- 不会出现"一半新一半旧"的混合状态

### 7.7 计算层数据时效性管理

**问题**：Eager 预计算在日终后执行。如果用户在日终前查询，读到的是昨天的计算结果。

**原则**：
- 日终前的查询，走 Lazy 路径（实时计算 + 缓存）
- 日终后的查询，走 Eager 路径（读预计算结果）
- API 层根据当前时间自动选择数据源

判断逻辑：
```
if 当前时间 >= 今日日终时间 AND 日终已完成:
    用 Eager 预计算结果
else:
    用 Lazy 实时计算
```

### 7.8 资源占用汇总

| 资源 | 当前 | 改后 | 变化 |
|:-----|:-----|:-----|:-----|
| **API 进程内存** | ~200MB | ~210MB（+推送缓存）| +5% |
| **data_daemon 内存** | ~50MB | ~55MB（+ECM 写缓存）| +10% |
| **CPU**（API 进程）| ~5% | ~8%（+定时推送）| +3% |
| **CPU**（data_daemon）| ~15% | ~18%（+ECM 写入）| +3% |
| **磁盘写入** | ~200MB/日 | ~800MB/日（+快照）| +600MB/日 |
| **磁盘空间** | 16GB | 16GB（清理后下降）| 下降 |

所有增量在桌面应用的正常资源范围内。

1. **ECM 是唯一数据来源**：选股系统所有实时请求路径均从 ECM 读取原始日线/基本面/资金流数据，无直调 Tushare 违规

5. **`factor-combinations` 直连 SQLite**：绕过 DataManager 直接 `sqlite3.connect()`，存在架构一致性风险
