## 一、背景

在策略分析体系全线审计（286号总纲）中，发现两个核心问题：

- **P1**：daemon 日终执行的策略信号全市场预计算写入了 `strategy_signals` 表，但没有任何业务逻辑消费该表，属于"无主代码"
- **P10**：选股系统 L3 和个股策略分析两个渠道调用了不同的评分代码路径（因子两套、缠论选股独有修正），结果不一致

本方案将上述两个问题合并解决：**设计统一的核心策略计算层，评估盘后全市场预计算的可行性，规划对应的实施路径。**

## 二、策略数据源核查

### 2.1 数据源清单

| 数据源 | 缓存表 | 是否盘后 | 15:30同步 |
|:-------|:-------|:---------|:----------|
| 日K线 | `daily_cache` | ✅ | `_batch_daily` |
| 基本面 | `daily_basic_cache` | ✅ | `_batch_daily_basic` |
| 资金流向 | `moneyflow_cache` | ✅ | `_batch_moneyflow` |
| 融资融券 | `margin_cache` | ✅ | `_batch_margin` |
| 指数日线 | `index_daily_cache` | ✅ | `_batch_index_daily` |
| 概念板块 | `concept_cache` | ✅ | `_batch_concept` |
| 龙虎榜 | `lhb_cache` / `lhb_detail_cache` | ✅ | `_batch_lhb` / `_batch_lhb_detail` |
| 分钟K线 | `minute_kline_cache` | ✅ | 日终回填 `_batch_backfill_minute_kline` |
| 十大股东 | `top10_holders_cache` | 盘后/季频 | `_batch_top10_holders` |
| 财务指标 | `fina_indicator_cache` | 盘后/季频 | `_run_financial_sync` |

**结论：全部为盘后数据，无实时行情参与。** 唯一的半实时来源是 `InMemoryStateStore.get_concepts()`（龙虎榜板块效应评分使用），但该数据由 daemon 每 1800 秒刷新，也不属于实时行情。15:30 日终同步后所有数据就绪。

### 2.2 对预计算的约束条件

1. **必须在 15:30 日终数据采集全部完成后触发**。具体而言：daemon 的日终批量采集（`_batch_daily`、`_batch_daily_basic`、`_batch_moneyflow`、`_batch_stk_limit`、`_batch_lhb`、`_batch_concept`、`_batch_margin`、`_batch_adj_factor` 等）和分钟数据回填必须全部执行完毕，确认上游数据就绪后方可启动预计算。预计算不应与数据采集并行执行，避免基于不完整数据产出的策略信号与次日增量数据不一致。
2. **必须在次日 9:30 开盘前完成**（窗口 18 小时）
3. **不得影响交易时段的 daemon 实时采集性能**（30s 主循环优先）

## 三、全市场预计算耗时估算

### 3.1 单只股票的策略计算成本

基于对 `SignalComputationService.compute_for_stock()` 代码路径的分析：

| 阶段 | 组件 | 估算耗时 | 说明 |
|:-----|:-----|:---------|:-----|
| 数据准备 | 加载K线+扩展数据 | ~25ms | SQLite本地读取 |
| L2 | 筹码分析 (`ChipDistributionStrategy.analyze`) | ~50ms | 含筹码分布计算 |
| L3 | 缠论多级别分析 | ~200-800ms | 最耗时，需读分钟数据 |
| L3 | 因子评分 (`FactorRegistry`) | ~50ms | 含多个因子计算 |
| L3 | 量价分析 (`VolumePriceStrategy.analyze`) | ~30ms | |
| L3 | BOCIASI快线+慢线 | ~20ms | |
| 其他 | Vibe/新闻情绪/VAP等 | ~40ms | 可优化(非核心策略) |
| **合计** | **完整策略链** | **~415-1015ms** | 取中值 ~**800ms/只** |

### 3.2 全市场总耗时

| 模式 | 估算 | 说明 |
|:-----|:-----|:------|
| **单线程顺序** | 5000 × 0.8s = **4000s (≈67分钟)** | 当前 daemon 的 `_run_precompute` 方式 |
| 4线程并发(股票级) | 67min ÷ 3 ≈ **22分钟** | SQLite读为主，锁竞争小 |
| 8线程并发 | 67min ÷ 6 ≈ **11分钟** | I/O-bound，线性扩展性好 |
| 仅在L2高分股执行 | ~100 × 0.8s = **80秒** | 选股视角，非全市场 |

### 3.3 窗口可用性

```
15:30  日终同步开始（批量API采集约15-30分钟）
16:00  日终同步完成，所有上游数据就绪
16:00  →  预计算开始
16:00-17:00  (单线程67分钟) 预计算完成
16:00-次日9:30  (共18小时) 可用窗口
```

**结论：即使单线程也完全来得及。** 18 小时窗口内执行 67 分钟的计算任务，CPU 平均利用率约 6%（1核/16核）。

## 四、两渠道计算一致性核查

### 4.1 当前差异全景

| 维度 | 选股系统 L3 | 个股策略分析 | 是否一致 |
|:-----|:-----------|:-----------|:---------|
| **缠论** | `compute_for_stock()` → 取 `chanlun_analysis_detail` → 自打0-10分（含 `_adjust_score_with_context`） | `_compute_chanlun_signal()` → `ChanlunScorer.score()` → 五维格式 | ⚠️ 核心引擎相同(同调MultiLevelChanlunAnalyzer)，但选股额外有市场环境修正 |
| **量价** | `VolumePriceStrategy.analyze()` → `_compute_volume_price_score()` | `_compute_volume_price_signal()` → 内部调同 `VolumePriceStrategy` | ✅ 核心算法相同 |
| **因子** | **`_FACTOR_COMPUTERS`**（函数式映射表，~20个因子） | **`FactorRegistry`**（正式因子系统）+ `FactorCalculator` | ❌ **完全两套代码** |
| **BOCIASI** | 仅快线（内联函数 `_f_bociasi_quickline`，20行） | 快线 + 慢线（跨市场情绪分析） | ❌ 选股缺慢线 |
| **筹码** | 不在L3（已在L2完成 `ChipScorer`） | `ChipDistributionStrategy.analyze()` | ❌ L3不做（合理） |
| **Vibe** | `_compute_vibe_bonus()` 真实代码执行 → 0-10加分 | `_build_vibe_dimension()` 提取 → 第六维度 | ⚠️ 执行方式同但输出格式不同 |

### 4.2 评分方式差异（最需关注）

| 维度 | 选股L3评分公式 | 个股策略评分公式 |
|:-----|:--------------|:----------------|
| **缠论** | `_compute_chanlun_score()` → 0-10分（含 `_adjust_score_with_context` 修正） | `ChanlunScorer.score()` → 0-100分 + signal(HOLD/BUY/SELL) |
| **量价** | `_compute_volume_price_score()` → 0-10分（含RPS+筹码密集加分） | 五维格式中 direction/confidence |
| **因子** | `_compute_factor_score()` → `_FACTOR_COMPUTERS` 函数表加权 | `FactorCalculator` 注册表加权 -> composite 0-1 |
| **综合** | z-score归一化 → 用户权重加权 → 0-10分 + S/A/B/C/D评级 | 各维度独立 direction/confidence → 五维展示 |

## 五、统一方案设计

### 5.1 架构

```
                      UnifiedStrategyCore(ts_code, period)
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
     MultiLevel         VolumePrice          FactorRegistry
     ChanlunAnalyzer    Strategy             (正式因子系统)
          │                   │                   │
     ─────┴───────────────────┴───────────────────┴────
          │                   │                   │
     ChipDistribution    Bociasi(快线+慢线)    Vibe 执行
     Strategy
          │
          └──────────────┬──────────────┘
                         │
                 StandardizedResult
         { 每个策略: {
             raw_score: float,      ★ 0-1 或 0-10 原始分（供选股L3 z-score用）
             direction: str,         ★ bullish/bearish/neutral
             confidence: float,      ★ 置信度
             signal: str,            ★ BULLISH/BEARISH/NEUTRAL/WATCH
             signal_label: str,       ★ 中文标签
             evidence: list[str],    ★ 依据文本
             status_desc: dict,      ★ 现状描述（供个股策略五维渲染）
             raw_detail: dict        ★ 完整策略细节
         }}
                         │
              ┌──────────┴──────────┐
              │                     │
         选股输出适配器          个股策略输出适配器
         · 丢弃筹码维度            · 五维格式组装
         · 丢弃BOCIASI慢线         · NLG/DeepSeek 渲染
         · 提取 raw_score          · 策略建议生成
         · z-score归一化
         · 用户权重加权组合
         · 0-10评分+S/A/B/C/D评级
```

### 5.2 核心原则

1. **一次计算，两路输出**：`UnifiedStrategyCore` 是唯一的策略计算入口
2. **计算不含任何渠道逻辑**：`_adjust_score_with_context` **移入选股适配器**（不进入核心层，保留在选股适配器中作为选股特有的市场环境修正步骤）
3. **因子体系统一**：选股L3废弃 `_FACTOR_COMPUTERS`，统一通过 `UnifiedStrategyCore` 获取因子评分。OHLCV 派生因子走 `FactorRegistry`，ECM 依赖因子走核心内部管线。
4. **选股适配器保留 z-score 归一化**：这是选股"多股票横向比较"的固有需求，不进入核心也不进入预计算
5. **各策略的 raw_score 在 core 产出中自带**：选股适配器直接提取，无需二次计算

## 六、预计算缓存设计

### 6.1 数据流

```
Daemon 日终 (数据采集完成后, 约16:00)
  → UnifiedStrategyCore.compute_batch(所有活跃股票)
  → 逐只序列化为 JSON → strategy_signal_detail(ts_code, trade_date, signal_json)

请求 (次日盘中)
  → 路由/选股 → read strategy_signal_detail
  → 命中 → 反序列化 StandardizedResult → 适配器输出
  → 未命中 → UnifiedStrategyCore.compute(ts_code) 实时计算
          → 写入 strategy_signal_detail → 适配器输出
          → 写 sync_requests('precompute', ts_code) → daemon 异步补算
```

### 6.2 strategy_signal_detail 表结构

新表结构：

```sql
-- 新表：策略信号完整详情（替代现有 strategy_signals 的不足）
-- 每只股票每个交易日一条记录，全部策略信号合并存储在一个 signal_json 中
CREATE TABLE IF NOT EXISTS strategy_signal_detail (
    ts_code TEXT NOT NULL,
    trade_date TEXT NOT NULL,
    signal_json TEXT NOT NULL,         -- 完整 StandardizedResult JSON
                                       -- 包含全部6个策略信号 + market_context + data_availability
    schema_version INTEGER DEFAULT 1, -- 缓存格式版本号，代码升级时校验
    cached_at TEXT DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (ts_code, trade_date)
);
```

`schema_version` 列用于检测代码升级后的缓存兼容性。读取时校验版本号，不匹配则跳过缓存走实时计算。

signal_json 存储完整的 StandardizedResult JSON，SQLite 的 TEXT 列最大支持 2GB，Single JSON ~5-10KB，5000 × 5KB = 25MB/天，无长度问题。

### 6.3 存储增长与清理

| 指标 | 估算 |
|:-----|:-----|
| 每日新行 | 5000 只 × 1 条(JSON 合并存储) = 5,000 行 |
| 每日存储 | 5000 × 5KB ≈ **25 MB**（JSON 序列化） |
| 3个月累计 | ~450K 行, ~2.25 GB |
| 建议清理策略 | 按 `trade_date` 按日分区存储，清理时 DROP 整个分区 |

> **注意**：按 `trade_date` 分区（每日独立 SQLite 表或文件）而非全局 DELETE+VACUUM。分区清理零碎片、零 VACUUM 成本，避免盘中清理影响请求延迟。

| **合计** | **5.5-7天** |

## 八、数据缓存链路设计（核心修正）

### 8.1 关键发现：当前预计算缓存不足以支撑前端五维展示

`cache_strategy_signals()`（`enhanced_cache_manager.py:1480`）当前只存储了：

| 表字段 | 存储内容 | 来源 |
|:-------|:---------|:-----|
| `signal_name` | 策略名称（如"缠论走势分析"） | `strategy_name` |
| `signal_value` | 置信度（浮点数） | `confidence` |
| `signal_level` | 信号方向（如"bullish"） | `signal` |

**丢弃的数据**（恰好是前端五维展示需要的）：

| 丢弃的内容 | 前端消费位置 | 用途 |
|:-----------|:------------|:-----|
| `status_recognition`（嵌套字典，~50个字段） | 五维所有维度 | 方向/趋势/中枢/筹码/资金流向等 |
| `chanlun_analysis_detail` | indicator-ide.html:2802 | 缠论结构、中枢列表、买卖点 |
| `evidence` 列表 | indicator-ide.html:3300-3314 | 验证链冲突详情、关注点 |
| `entry_zone` / `risk_line` / `target_zone` | indicator-ide.html:3285-3295 | 关键价位、止损止盈 |
| `backtest_win_rates` | indicator-ide.html（未直接渲染，策略建议使用） | 历史胜率参考 |
| `signal_source_detail` | indicator-ide.html（调试用） | 信号来源细节 |
| `market_context` 扩展数据 | - | 用于构建信号上下文和 NLG |

**结论：当前 `strategy_signals` 表的设计仅适用于"按策略名取分数"的选股系统场景，完全不足以还原个股策略分析的五维展示。**

### 8.1.2 DeepSeek 九层描述的数据依赖（用户触发场景）

**重要边界**：DeepSeek AI 九层描述不属于策略层功能，不进入预计算。预计算只输出策略信号数据和 NLG 规则生成的现状文本。DeepSeek 的调用由用户操作触发，但所需的策略上下文数据可以从预计算缓存中直接获取。

`strategy_analyze()` 中 `_get_deepseek_status_text(ts_code)` 负责调用 DeepSeek 生成九层股票现状描述，它依赖的数据链路如下：

```
_get_deepseek_status_text(ts_code)
  → AiContextBuilder.build_context(ts_code)
     1. _build_stock_context()     — Stock表查询（name/industry/market_cap）
     2. _build_market_context()    — 大盘环境（固定/占位，非关键）
     3. _build_news_context()      — 新闻数据（当前占位，未接入）
     4. ★ SignalComputationService.compute_for_stock(ts_code)  ← 再跑一次！
        → SnapshotAssembler.assemble(signals, ts_code, data_availability)
          ├─ _extract_environment()    — market_context中的大盘数据
          ├─ _extract_structure()      — 缠论信号 · status_recognition + chanlun_analysis_detail
          ├─ _extract_chip()           — 筹码信号 · status_recognition
          ├─ _extract_price()          — market_context + 缠论支撑阻力
          ├─ _extract_volume_price()   — 量价信号
          ├─ _extract_capital()        — market_context + 筹码信号
          ├─ _extract_sentiment()      — BOCIASI信号
          ├─ _extract_factor()         — 因子评分信号
          └─ _extract_verification()   — MarketSentimentService + FinanceReportService
  → to_prompt_section() → JSON → DeepSeek API
```

**关键问题**：当前每次请求 `strategy_analyze`，`compute_for_stock()` **被调用了两次**：

| 调用位置 | 用途 | 耗时 |
|:---------|:-----|:-----|
| `strategy_analyze()` 主流程（line 451） | 5个 signal dict → 五维组装 | 1-5s |
| `AiContextBuilder.build_context()` 内部（line 159） | 同样5个 signal dict → SnapshotAssembler → DeepSeek prompt | 再做一次同上 |

两次计算结果完全相同，等于 **浪费了一倍的策略计算时间**。

**预计算后的数据流（DeepSeek 用户触发场景）**：

```
用户点击"AI九层解读" → 调 DeepSeek 端点
  → 读 strategy_signal_detail cache → 5 signal dicts（JSON反序列化） ← 5-20ms
  → AiContextBuilder()
     → _build_stock_context()     — Stock表（轻量查询）
     → ★ 跳过 compute_for_stock()，直接使用缓存的 5 个 signal dict    ← 关键改动
     → SnapshotAssembler.assemble(signals, ts_code, market_context)
        → 全部从缓存的 signal dict 中提取，无需额外数据
     → to_prompt_section() → JSON → DeepSeek API
  → 返回给前端
```

**关键确认：SnapshotAssembler 所依赖的数据全部可从缓存的 signal dict 中还原**。

逐项核查 SnapshotAssembler 的 8 个 extractor 的输入来源：

| Extractor | 输入来源 | 是否可从缓存还原 |
|:----------|:---------|:----------------|
| `_extract_environment()` | `market_context`（idx_5d_ret, market_state 等） | ⚠️ `market_context` 需额外缓存，或从 ECM 缓存的 index_daily_cache 轻量重算（5-10ms） |
| `_extract_structure()` | 缠论 signal 的 `status_recognition` + `chanlun_analysis_detail` | ✅ 已完整存储在 signal_json |
| `_extract_chip()` | 筹码 signal 的 `status_recognition` | ✅ 已完整存储在 signal_json |
| `_extract_price()` | `market_context` + 缠论 `status_recognition.support_resistance` | ✅ 支撑阻力在 signal_json 中，bias/分位等可轻量重算 |
| `_extract_volume_price()` | 量价 signal + `market_context` | ✅ 量价信号在 signal_json 中 |
| `_extract_capital()` | `market_context` + 筹码 `status_recognition` | ✅ 筹码数据在 signal_json，大单净额可轻量重算 |
| `_extract_sentiment()` | BOCIASI signal | ✅ 已完整存储在 signal_json |
| `_extract_factor()` | 因子 signal | ✅ 已完整存储在 signal_json |
| `_extract_verification()` | MarketSentimentService + FinanceReportService | ✅ 独立服务，非策略引擎产物 |

**结论：`market_context` 是唯一需要额外处理的依赖项。** 但它包含的数据（指数收益率、乖离率、大单净额等）全部来自 ECM 已缓存的表（index_daily_cache、daily_cache、moneyflow_cache），可在读取时轻量重算（5-10ms），无需实时调用数据源。建议在预计算时将 `market_context` 一并 JSON 序列化存入缓存表，避免读取时重复查表。

### 8.2 缓存存储方案设计

#### 8.2.1 方案对比

| 方案 | 存储内容 | 每日存储 | 读取路径 | 实施复杂度 | 评价 |
|:-----|:---------|:---------|:---------|:----------|:-----|
| **A — 存完整 signal dict JSON** | 每条策略一个 dict：`{strategy_name, status_recognition, confidence, evidence, ...}` → JSON 存入 `signal_detail TEXT` 列 | 5000 × 5 × 5KB ≈ 125MB | 读5条JSON → 反序列化 → 五维组装 | 中 | **推荐**。保留了组装五维的灵活性，NLG 现状文本可在读取时渲染 |
| **B — 存最终 5D 输出 JSON** | 直接存 `{dimensions: {...}, data_availability: {...}}` 完整 JSON，一股一行 | 5000 × 8KB ≈ 40MB | 读1条JSON → 直接返回 | 低 | 最简单，但失去了独立维度的灵活性 |

#### 8.2.2 推荐方案：A + 增量补充

**方案 A 的具体设计**：

```sql
-- 新表：策略信号完整详情（替代现有 strategy_signals 的不足）
-- 每只股票每个交易日一条记录，全部策略信号合并存储在 signal_json 中
CREATE TABLE IF NOT EXISTS strategy_signal_detail (
    ts_code TEXT NOT NULL,
    trade_date TEXT NOT NULL,
    signal_json TEXT NOT NULL,         -- 完整 StandardizedResult 的 JSON 序列化
                                       -- 包含全部6个策略信号 + market_context + data_availability
    schema_version INTEGER DEFAULT 1, -- 缓存格式版本号，代码升级时校验
    cached_at TEXT DEFAULT (datetime('now','localtime')),
    PRIMARY KEY (ts_code, trade_date)
);

-- strategy_signals 不再使用，选股 L3 统一从 strategy_signal_detail 读取
```

**数据流**：

```
Daemon 日终预计算:
  UnifiedStrategyCore.compute_batch(全市场股票)
    → 对每只股票产出 StandardizedResult
       └─ 内含：5个 signal dict + market_context + data_availability
    → ECM.cache_signal_detail()             写入 strategy_signal_detail（完整JSON，单表统一存储）
       └─ signal_json 内容：
          {
            "chanlun": { full signal dict },
            "volume_price": { full signal dict },
            "chip": { full signal dict },
            "bociasi": { full signal dict },
            "factor": { full signal dict },
            "market_context": { idx_5d_ret, bias_ma5, net_lg_amount, ... },
            "data_availability": { ... }
          }
    ↓
盘中请求 POST /api/v3/strategy/analyze:
  → 读 strategy_signal_detail（1条JSON，含全部5个signal dict + market_context）
  → 反序列化
  → 组装五维格式（_build_*_dimension()，输入与实时计算完全相同）
  → NLG 规则生成现状文本（读取时渲染，<1ms）
  → 返回给前端（不含 DeepSeek 文本，DeepSeek 由用户单独触发）
  ↓
用户触发 AI 分析 → POST /api/v3/strategy/deepseek:
  → 读 strategy_signal_detail 缓存获取 5 个 signal dict
  → AiContextBuilder.build_context() 组装 DeepSeek 上下文
  → 调 DeepSeek API 生成九层描述
  → 返回给前端

### 8.4 前端调用适配方案

#### 8.4.0 核心前提

**DeepSeek 不属于策略层功能，不进入预计算**。预计算仅覆盖策略信号数据 + NLG 规则生成的现状文本。DeepSeek AI 九层描述是用户触发的增值功能，由独立的 API 端点提供服务，且所需的策略上下文数据可从预计算缓存中直接获取（消除重复计算）。

前端五维渲染核心代码不变——`_build_*_dimension()` 的输入（5 个 signal dict）和输出（五维 JSON）完全相同，只是来源从"实时计算"改为"缓存读取"。

#### 8.4.1 响应 JSON 结构变化

```
当前（实时计算）E12 响应:
  { code:0, data: {
      dimensions: {...},              // 五维数据（含 NLG 规则生成的状态文本）
      signal_verification: ...,
      strategy_suggestions: ...,
      deepseek_text: "..."            // DeepSeek 九层描述（同步生成）
    }
  }

预计算后 E12 响应:
  { code:0, data: {
      dimensions: {...},              // 五维数据（来自缓存，5-50ms）
      signal_verification: ...,       // 来自缓存
      strategy_suggestions: ...,      // 来自缓存
      nlg_status_text: {...},         // NLG 规则生成的现状文本（读取时渲染）
      deepseek_available: true        // 标记前端可调用 DeepSeek 独立端点
    }
  }
```

`deepseek_text` 字段从 E12 响应中移除。后端不再在策略分析路由中同步调 DeepSeek API。

#### 8.4.2 关键时序变化：E12 大幅加速

**E12 返回时间组成对比**：

```
当前（实时计算）:
  ┌─ 策略计算 1-5s ─┬─ DeepSeek API 1-3s ─┐
  │                                     │
  └────────── E12 总耗时 2-8s ──────────┘

预计算后（缓存命中）:
  ┌─ 缓存读取 5-50ms ─┬─ NLG 文本组装 <1ms ─┐
  │                                          │
  └──────── E12 总耗时 5-50ms ──────────────┘
```

**前端加载时序**：

```
当前:
  Promise.all([
    loadAnalysis(),            ← E12: 2-8s (策略1-5s + DeepSeek 1-3s)
    loadVerification(),         ← E13: 0.5-2s
    setTimeout(1200)            ← 最低等待 1.2s
  ]) → finishAnalysisReal()    ← 全部到位后渲染

预计算后:
  Promise.all([
    loadAnalysis(),            ← E12: 5-50ms (全部缓存)
    loadVerification(),         ← E13: 5-20ms
  ]) → finishAnalysisReal()    ← 点击后 50-70ms 完成全部渲染
```

**重要变化**：E12 从 2-8s 降至 5-50ms，1.2s 最低等待不再必要。五维卡片 + NLG 现状文本瞬间展示。

#### 8.4.3 DeepSeek 调用设计（用户触发）

DeepSeek 作为独立功能，由用户点击触发，通过独立 API 端点调用：

```
用户点击"AI九层解读"按钮
  → GET /api/v3/strategy/deepseek?ts_code=X
  → 后端:
      1. 读 strategy_signal_detail 缓存获取 5 个 signal dict（5-20ms）
      2. AiContextBuilder.build_context()
         - _build_stock_context()     实时查 Stock 表
         - SnapshotAssembler.assemble() 从缓存的 signal dict 提取（无需重复计算）
         - to_prompt_section() → JSON
      3. 调 DeepSeek API 生成九层描述（1-3s）
      4. 返回文本 → 前端更新
  → 前端更新 deepseek_text 区域
```

**关键收益**：DeepSeek 调用时不再需要重复运行策略引擎，直接从缓存获取 signal dict，单次节省 1-5s 策略计算时间。

#### 8.4.4 端点影响清单

| 端点 | 预计算影响 | 说明 |
|:-----|:----------|:------|
| `POST /api/v3/strategy/analyze` | **响应移除 deepseek_text** | 五维数据 + NLG 文本来自缓存，5-50ms |
| `POST /api/v3/strategy/deepseek` | **新增端点** | 用户触发，从缓存读取 signal dict + 实时调 DeepSeek |
| `POST /api/v3/strategy/status-aggregate` | **无影响** | 从缓存信号组装，输出不变 |
| `GET /api/v3/chanlun/chart` | **无影响** | 缠论图独立于预计算，仍实时调用 ChanlunAnalyzer |
| `POST /api/v3/screener/run` | **无影响** | L3 评分从 strategy_signal_detail 提取 raw_score |
| `POST /api/v3/ai/arbitrate` | **无影响** | AI仲裁独立于策略计算 |

#### 8.4.5 前端改动要求

| 改动项 | 说明 |
|:-------|:------|
| E12 响应中移除 `deepseek_text` | 后端不再返回，前端对应字段置为 `null` |
| 新增 DeepSeek 独立调用 | 新增 `loadDeepSeek(ts_code)` 函数，调用 `/api/v3/strategy/deepseek` |
| "AI九层解读"入口按钮 | 根据 `deepseek_available` 标记决定是否显示，用户点击后调用 |
| `setTimeout(1200)` 可移除 | 五维数据 50ms 就绪，不再需要最低等待 |

**零强制改动选项**：若暂时不改前端，E12 返回中 `deepseek_text` 字段设为空字符串、`deepseek_available` 设为 `false`，前端展示和现有行为完全不变。DeepSeek 功能后续通过 UI 迭代独立添加。

### 8.5 全局数据体系合规确认

| 规则 | 预计算模式下的合规情况 |
|:-----|:----------------------|
| **红线1**（禁止非采集层实例化 Provider） | ✅ UnifiedStrategyCore 走 DataManager 只读方法，不涉及 Provider |
| **红线2**（禁止 `use_cache=False`） | ✅ 缓存读取路径无需此参数 |
| **红线3**（禁止路由中实时计算技术指标） | ✅ 路由改为读缓存+组装，技术指标在预计算时已算好写入宽表 |

| **数据存储层唯一网关** | ✅ 全部通过 ECM 读写缓存表，不走其他路径 |

| 大单净买入 | ❌ 不存在 | 需要 moneyflow_cache |
| 资金流向强度 | ❌ 不存在 | 需要 moneyflow_cache |
| 换手率变化 | ❌ 不存在 | 需要 daily_basic_cache |
| 营收增长率 | ❌ 不存在 | 需要 income_cache |
| 净利润增长率 | ❌ 不存在 | 需要 fina_indicator_cache |
| 资产负债率 | ❌ 不存在 | 需要 balancesheet_cache |
| Fama-French五因子 | ❌ 不存在 | 横截面计算依赖全市场数据，core 不纳入，选股适配器自行实现 |

**处理方案**：

**OHLCV 派生因子**（动量/RSI/波动率/乖离率/量比等）已通过 `FactorRegistry`（257个因子）覆盖，`UnifiedStrategyCore` 统一通过 `FactorRegistry` + `FactorCalculator` 计算这些因子。

**ECM 依赖因子**（市盈率倒数/ROE/股息率/大单净买入/资金流向强度/换手率变化/营收增长率/净利润增长率/资产负债率）需要查询 `daily_basic_cache`、`moneyflow_cache`、`fina_indicator_cache`、`income_cache`、`balancesheet_cache` 等 ECM 数据表，不适用于 FactorRegistry 的纯 OHLCV DataFrame 接口。这些因子保留在 `UnifiedStrategyCore` 内部的计算管线中（通过 `SignalComputationService._compute_factor_signal_inline()` 计算），两渠道通过 `UnifiedStrategyCore` 统一入口获得一致的因子评分结果。

**实质效果**：通过 `UnifiedStrategyCore` 的统一入口，两渠道不再有"两套因子代码"的问题——无论因子在 FactorRegistry 还是核心管线中，都是从统一的计算路径获取评分。
