## 一、核心设计原则

### 1.1 预计算是运行原则，不是独立层级

预计算不是系统的一个"层"，而是贯穿整个处理管道的**运行模式**。每个环节都有自己的预计算规则——利用日终到次日开盘的空闲时间，完成后台全量处理，确保次日前端用户体验最优。

```
日终空闲窗口（15:30 ~ 次日 9:00）
  │
  ├── 采集层：日终同步（批量拉取当日数据）
  ├── 原料加工：指标/因子/特征提取
  ├── 策略分析：6引擎信号生成
  ├── 判定及操作建议：12维度状态+操作建议
  └── 成品仓：快照生成+归档
```

### 1.2 环节分离，即插即用

系统按功能划分为**6个独立环节**，每个环节有明确的接口契约（输入/输出/规则）。新增数据源、策略引擎或判定逻辑时，只需在对应环节中添加，管道调度器自动编排执行顺序。

### 1.3 DAG 管道调度

管道执行顺序由**有向无环图（DAG）**声明式定义，而非硬编码步骤列表。调度器自动解析依赖关系，支持并行执行、失败跳过、增量计算。

### 3.4 环节4：策略分析（SIG）

**输入**：**直读STG原始表**（daily_cache / daily_basic_cache / moneyflow_cache 等），不经过pre_feat_cache
**输出**：strategy_signal_detail（5引擎信号JSON + dim_results_json + seven_dim_json）
**执行时机**：日终批量，依赖环节3.FEAT就绪
**执行方式**：串行执行（共享数据读取，避免锁竞争）

> **设计决策演进**：
> - 2026-08-19：SIG策略引擎保持直读STG原始表
> - 2026-08-21（358号）：SIG重定位为"专业分析师"，输出双轨结构
> - **2026-08-30 v3.0确认**：
>   - SIG产出三个JSON字段：`signal_json`（已有）+ `dim_results_json`（JUD消费）+ `seven_dim_json`（直接到OUT，不进JUD）
>   - `seven_dim_json` 由 `build_seven_dim_report()` 生成，包含6维分析的条件/规则/证据整理
>   - `dim_results_json` 包含各引擎的连续强度值+置信度（供JUD消费，可选）
>   - SIG使用Path C（维度引擎路径），通过 `signal_computation_service.compute_via_engines()` 调用dim1-dim6引擎

| DIM-5 因子维 | factor | ⚠️ 无独立引擎，从pre_feat_cache读取 | ✅ |
| DIM-6 估值维 | valuation | dim7 | ✅ |
| DIM-7 财务维 | finance | ⚠️ 无引擎，从pre_feat_cache读取 | ✅ |
| DIM-8 事件维 | event | ⚠️ 无引擎，从pre_feat_cache读取 | ✅ |
| DIM-9 时间维 | time | ⚠️ 无引擎，从pre_feat_cache读取 | ✅ |
| DIM-10 风险维 | risk | dim6 | ✅ |
| DIM-11 位置维 | position | ⚠️ 无引擎，从pre_feat_cache读取 | ✅ |
| DIM-12 信号确认 | signal_confirm | dim1 | ❌ **不参与共识** |

**说明**：
- dim1（信号确认）在SIG预计算，结果供JUD消费，不参与共识计票，仅输出状态+证据+红绿灯
- dim8（状态总结）为纯整理输出，读取dim1-dim7的plain字段和judgment输出
- 旧B组标签维度（factor/finance/event/time/position）当前从pre_feat_cache直接读取，无独立引擎

**操作建议生成**：
- advice_builder 消费 JUD-3 共识 + dirs 方向值
- 输出：opportunity_state（enter/light/wait/avoid）+ 仓位建议 + 止损位

**预计耗时**：~5-10分钟

**双模式执行**：
- **日终批量（主）**：管道自动触发（JUD为独立管道步骤），产出全市场快照
- **实时兜底（辅）**：前端请求时若快照缺失，实时 evaluate（~200ms/只）

### 3.6 环节6：成品仓（OUT）

**输入**：环节5（JUD）的快照 + 环节4（SIG）的七维描述
**输出**：归档表 + 自选股状态变更 + 前端消费数据
**执行时机**：日终批量，依赖环节5就绪

> **2026-08-30 v3.0更新**：
> - SIG产出的 `seven_dim_json`（七维现状描述）**不经JUD**，直接透传到OUT
> - OUT负责将 `seven_dim_json` 写入 `status_snapshot.one_liner_detail` 字段供前端消费

### 4.2 DAG 声明

```python
PIPELINE_DAG = {
    'col':    {'depends_on': [], 'output': 'STG原始表'},
    'stg':    {'depends_on': ['col'], 'output': '分库数据'},
    'ind':    {'depends_on': ['stg'], 'output': 'indicator_*'},
    'feat':   {'depends_on': ['stg'], 'output': 'pre_feat_cache'},
    'fac':    {'depends_on': ['stg'], 'output': 'factor_cache'},
    'sig':    {'depends_on': ['feat'], 'output': 'strategy_signal_detail'},
    'jud':    {'depends_on': ['feat', 'sig'], 'output': 'status_snapshot + treemap_snapshot'},
    'out':    {'depends_on': ['jud'], 'output': 'history表 + watchlist_status_diff'},
}
```

### 4.3 调度规则

1. **拓扑排序**：自动计算执行顺序，ind/fac/feat可并行
2. **依赖检查**：上游未完成时下游自动跳过
3. **失败隔离**：某环节失败不影响已成功的上游
4. **增量计算**：仅处理输入有变更的股票（通过sync_requests判断）
5. **健康度报告**：每环节执行后产出健康度（输入数/输出数/跳过数/失败数/耗时）

### 4.4 日终处理时间预算

| 环节 | 预计耗时 | 可并行 |
|------|---------|--------|
| COL 日终同步 | ~10分钟 | — |
| RAW (IND+FEAT+FAC) | ~15-20分钟 | IND/FEAT/FAC并行 |
| SIG 策略分析 | ~10-15分钟 | — |
| JUD 判定 | ~5-10分钟 | — |
| OUT 成品仓 | ~1-2分钟 | — |
| **合计** | **~41-57分钟** | |

利用15:30~次日9:00空闲窗口（约17.5小时）完全可行。

## 七、自选股监控存储设计

### 7.1 设计原则

自选股状态监控**不需要独立分仓**，而是在成品仓环节增加轻量状态变更检测：

- 数据来源：status_snapshot（成品仓）vs 上日status_snapshot
- 存储：watchlist_status_diff（轻量表，仅记录变更）
- 消费：自选看板（今日操作榜/重点关注/变化提醒）

### 7.2 与opportunity_library的关系

| 表 | 职责 | 数据量 |
|-----|------|--------|
| opportunity_library | 自选股列表+分级+操作建议（CRUD） | 几十~几百行 |
| watchlist_status_diff | 状态变更追踪（日终自动检测） | 几十~几百行/日 |
| status_snapshot | 全市场状态快照（日终批量） | ~5500行/日 |

三表互补：library管理"谁在自选"，snapshot提供"全市场状态"，diff追踪"自选股变化"。
