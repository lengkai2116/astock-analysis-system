**版本**：v1.0（2026-09-29；**只读核查 + 修复方案**，本档**未改任何代码/配置**）
**来源**：2026-09-29 批次5 验证期，stale 看守日志暴露 `scheduler_manager` 中一条真实既存 traceback（`no such table: daily_cache`）→ 用户要求「先只读核查这 4 处」→ 核查中发现同型远超 4 处 → 用户拍板「扩到全 12 处，先出方案」。

## 一、根因（已实证）

`EnhancedCacheManager.read_conn` / `_ecm_local.db_path` 均指向 **总库 `stock_cache.db`**：

```
ecm.db_path = .../data/duckdb/stock_cache.db          ← 总库
read_conn: SELECT ... FROM daily_cache        -> ERROR: no such table: daily_cache
read_conn: SELECT ... FROM daily_basic_cache  -> ERROR: no such table: daily_basic_cache
_query_shard('daily_cache', ...)              -> OK（分库读，正确路径）
```

而 `daily_cache`/`daily_basic_cache` 登记在 **`market_cache.db`**（`sharding_manager._table_to_db:78-79`）。

**项目已有的正确模式（修复模板 3 处，勿新造）**：
- `data_daemon._shard_query_df(table, sql, params)` / `_shard_fetchall(...)`（`:2004/:2024`，356号 §423 验证）；
- `routes/health.py:355-367`——`sharded_tables` 集合 → `sharding_manager.get_db_for_table/get_connection`；
- `EnhancedCacheManager._query_shard(table, sql, params=None) -> DataFrame`（`:515`）。

## 四、修复方案（**已拍板 2026-09-29**）

> **拍板结果**：**Q1＝全 12 处** ✅ / **Q2＝独立 499 号** ✅ / **Q3＝单批全 12 处** ✅。

### 统一改法
将 12 处 `ecm.read_conn` / `_ecm_local.db_path` 直读 `daily_cache`/`daily_basic_cache` 的 SQL，**改用分库读**：
- **DataFrame 路径（11 处）**：`pd.read_sql(sql, ecm.read_conn)` → `ecm._query_shard(table, sql, params)`（返回值同为 DataFrame，调用侧改动最小）；
- **游标路径（#5）**：`_run_signal_checkpoint` 用 `sqlite3` 游标读 `daily_cache`（回算价格），改走 `sharding_manager.get_db_for_table('daily_cache')` → `get_connection(db).execute(...)`；**注意其 `finally` 会 `close(conn, ec)`——不得把共享分库连接赋给 `ec`**，改用局部 helper 取连接，`ec` 保持 `None`。

### 逐处修复点（全 12 处）
| # | 位置 | 改法 |
|---|------|------|
| 1 | `scheduler_manager.py:459` | `pd.read_sql(sql, ecm.read_conn)` → `ecm._query_shard('daily_cache', sql)` |
| 2 | `scheduler_manager.py:527` | 同上（`_query_shard('daily_cache', sql, [min_days, max_stocks])`） |
| 3 | `scheduler_manager.py:601` | `ecm.read_conn.execute(...)` → `ecm._query_shard('daily_basic_cache', sql)` 后取标量 |
| 4 | `scheduler_manager.py:631` | `pd.read_sql(sql, ecm.read_conn)` → `ecm._query_shard('daily_cache', sql)` |
| 5 | `data_daemon.py:7409` | `_sq.connect(db_path=mode=ro)` → sharding `get_connection('market_cache.db')`；局部 helper，`ec` 保持 None |
| 6 | `routes/cache.py:80` | `pd.read_sql(sql, ecm.read_conn)` → `ecm._query_shard('daily_cache', sql)` |
| 7 | `dashboard_service.py:342` | 同上（`get_daily_top` 取最新日） |
| 8 | `dashboard_service.py:352` | 同上（`get_daily_top` 取当日全市场） |
| 9 | `dashboard_service.py:460` | 同上（`get_sector_changes`） |
| 10 | `dashboard_service.py:550` | 同上（`get_dashboard_summary`） |
| 11 | `dashboard_service.py:811` | 同上（`_try_get_latest_trade_date`） |
| 12 | `dashboard_service.py:834` | 同上（`_get_best_trade_date`） |

### 批次（单批全 12 处，依拍板）
- 一次性替换；风险**低**（只换取数路径，SQL/语义不变；`_query_shard` 对未登记表回落总库兼容）。
- 实施前确认：`scheduler_manager:459` 的 `ecm = DataManager().cache` 在循环外已就绪；`dashboard_service` 多处共用 `ecm`。

### 附：#5 暴露并修复的第二处潜伏缺陷（`is_win_*` 列名）
- 修 #5 分库读后，端到端运行报 **`no such column: is_win_t20d`**——代码 `f"is_win_{field}d"`（`field='t5'/'t10'/'t20'`）拼出 `is_win_t5d`，而实际 schema 列为 `is_win_5d`/`is_win_10d`/`is_win_20d`（无 `t`）。**该缺陷一直存在**（此前被分库读失败掩盖）。
- 修复：`f"is_win_{field[1:]}d"`（`'t5'→'5'`）。

### 附2：#2 暴露并修复的第三处潜伏缺陷（`first_date` 类型比较）
- 修 #1~#4 后，新 daemon 启动日志出现 **`启动补采: 数据补齐失败（可忽略）: Invalid comparison between dtype=str and Timestamp`**——`pd.read_sql` 返回的 `first_date` 为 **str**，与 `pd.Timestamp` 直接比较抛 `TypeError`；该异常被 `catch_up_if_needed` 的 `try` 吞（故 #2 修好后「补齐逻辑」仍不生效）。**该缺陷一直存在**（此前被分库读失败掩盖，且因异常被吞而静默）。
- 修复：`_replenish_sparse_stocks` 比较前 `sparse_df['first_date'] = pd.to_datetime(..., errors='coerce')`。
- 实测新 daemon（2026-09-29 18:56）：`daily_basic 历史检查: 1270 天，满足要求`（#3 ✅，原恒「仅 0 天」）+ `启动补采: 数据已最新 (2026-09-29), 跳过`（#1 ✅，原 `no such table` 崩溃）。
- **最终实测（2026-09-29 18:59，含全部 3 处附修）**：`启动补采: 688635.SH 补齐 1 条（现有 88 天）` … **`启动补采完成: 补齐 4/4 只股票（跳过 96 只新股）`**——#1/#2 与 `first_date` 附修**全部生效**（此前崩溃/静默失效；现补齐 4/4、新股过滤正常）。
