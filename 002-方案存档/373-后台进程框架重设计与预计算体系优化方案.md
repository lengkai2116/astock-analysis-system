# 373 — 后台进程框架重设计与预计算体系优化方案

> **方案目的**：基于353号架构和371号核查结论，重新设计后台进程框架，提升采集、存储、预计算的效率及精准度，支撑系统后续平稳运行。
>
> **方案依据**：3个并行探索子代理对实际代码的数据依赖分析、353号/292号方案条款核实、前端需求映射。

---

## 一、现状诊断

### 1.1 当前进程架构

```
进程1: data_daemon（数据进程，launchd自启）
  ├─ 主线程：30s tick驱动 _drive_pipeline()
  │   └─ COL-1~6 → RAW-1→RAW-2→RAW-3(串行) → SIG → JUD → OUT
  ├─ 采集器线程×5：AKShare盘中实时
  ├─ 后台线程×4：财务同步/分钟回填/自选股分钟/信号验证
  └─ 数据库：ECM SQLite WAL（单写者模型）

进程2: run.py（API进程，手动启动）
  ├─ Flask REST :5001 + SocketIO
  ├─ scheduler_manager定时任务
  └─ 读ECM只读 + 写PG
```

### 1.2 核心问题

| # | 问题 | 根因 | 影响 |
|---|------|------|------|
| 1 | **RAW三步串行** | 代码顺序执行，未利用353号设计的并行能力 | RAW阶段~18min，应为~8min |
| 2 | **财务同步覆盖率仅2-10%** | _run_financial_sync在后台线程，每次仅处理100-500只 | 估值特征缺失 |

| 6 | **run_daily_sync与_drive_pipeline重叠** | 两者都执行COL采集，功能重复 | 架构混乱 |

## 二、数据依赖验证（代码核查结论）

### 2.1 RAW三步数据依赖

通过3个并行探索子代理对实际代码的grep/read验证：

| 步骤 | 读取表 | 写入表 | 依赖其他RAW步骤？ |
|------|--------|--------|:---:|
| RAW-1 (IND) | daily_cache | indicator_ma/macd/other | **无** |
| RAW-2 (FEAT) | daily_cache + daily_basic_cache | pre_feat_cache | **无**（17组特征不读indicator表） |
| RAW-3 (FAC) | daily_cache | factor_cache | **无** |

**关键发现**：RAW-2的17组特征全部从daily_cache/daily_basic_cache的原始数据计算，**不读取RAW-1的indicator输出**。353号§3.3明确写道："内部可并行：IND/FAC/FEAT三个子步骤互不依赖"。

### 2.2 JUD写入 contention

| 函数 | 写入表 | 原子性 | 冲突风险 |
|------|--------|--------|---------|
| _build_status_snapshot | status_snapshot | DROP+RENAME | 无（不同表） |
| _build_treemap_snapshot | treemap_snapshot | DROP+RENAME | 无（不同表） |

两函数顺序执行（先status后treemap），treemap读取status_snapshot的consensus_rate等字段。单线程管道内无并发冲突。

### 2.3 strategy_analyze重复计算根因

| 路径 | 字段差异 |
|------|---------|
| 预计算读取(L916) | 有summary_text/one_liner_detail，**缺advice_params** |
| 实时计算(L945) | 有advice_params，**缺summary_text/one_liner_detail** |

**根因**：status_snapshot表**已存储advice_params**，但预计算读取路径未提取该字段。这是代码遗漏，非架构问题。

## 三、重设计方案

### 3.1 设计原则

1. **353号架构合规**：COL阶段负责所有数据采集（含财务），RAW/SIG/JUD/OUT负责计算判定
2. **单写者不变**：SQLite写操作由data_daemon独占
3. **管道内全覆盖**：核心计算纳入pipeline_status管理
4. **RAW真正并行**：三步无依赖，CPU密集计算并行化
5. **EXT步骤不引入**：财务同步作为COL-7纳入COL阶段，不创建管道外EXT概念

### 3.2 新架构

```
进程1: data_daemon
  ├─ 主线程：_drive_pipeline() 30s tick
  │   COL-1~6(采集) → COL-7(财务) → RAW-1/2/3(并行) → SIG → JUD → OUT
  │   每步: pipeline_status + 计数 + 超时 + 重试 + 完整性验证
  │
  ├─ 采集器线程×5：AKShare盘中实时
  ├─ 后台线程×2：分钟K线回填 / 信号验证回算（管道外低优）
  └─ 数据库：ECM SQLite WAL

进程2: run.py（纯读）
  ├─ Flask REST + SocketIO
  └─ 读ECM只读，不参与写操作
```

### 3.3 关键变更

#### 变更1：RAW三步真正并行

**验证结果**：三步读取同一源表(daily_cache)但写入完全不同的表，无数据依赖。

```python
# _drive_pipeline() RAW阶段
RAW_STEPS = {'RAW-1': _precompute_indicators, 'RAW-2': _precompute_raw_features, 'RAW-3': _precompute_preset_combos}

import concurrent.futures
with concurrent.futures.ThreadPoolExecutor(max_workers=3) as pool:
    futures = {}
    for step_id, func in RAW_STEPS.items():
        if status.get(step_id, {}).get('status') != 'done':
            futures[step_id] = pool.submit(func, codes)
    for step_id, future in futures.items():
        try:
            future.result(timeout=1800)
            _ecm.mark_step_done(today, step_id, f"OK parallel")
        except Exception as e:
            _ecm.mark_step_failed(today, step_id, str(e))
```

**写锁说明**：SQLite WAL单写者模型下三线程会串行化写入，但计算阶段(CPU密集)真正并行。计算时间>>写入时间，并行仍有显著收益。

**收益**：RAW阶段从~18min降至~8min。

#### 变更2：财务同步纳入COL阶段（COL-7）

**353号依据**：§3.1将fina_indicator/income/balancesheet/cashflow/forecast列为COL阶段采集表。

```python
# COL阶段新增COL-7
if status.get('COL-7', {}).get('status') != 'done':
    def _col_financial(_codes):
        # 分批500只/轮，循环直到全覆盖
        batch_size = 500
        for i in range(0, len(_codes), batch_size):
            batch = _codes[i:i+batch_size]
            _batch_fina_indicator_for(batch)
            _batch_income_for(batch)
            _batch_balancesheet_for(batch)
            _batch_cashflow_for(batch)
            _batch_forecast_for(batch)
    _run_pipeline_step(today, 'COL-7', _col_financial, codes)
```

**收益**：财务覆盖率从2-10%提升到100%。

#### 变更3：消除strategy_analyze重复计算

```python
# strategy_analyze.py — 预计算读取路径增加advice_params
snapshot = dm.cache.get_status_snapshot(ts_code)
response['status_verdict'] = {
    'opportunity_state': snapshot['opportunity_state'],

# 删除实时 StatusEngine().evaluate() 调用（L945）
```

**收益**：API响应从~400ms降至~50ms。

#### 变更4：watchlist_status_diff接入前端

新增`/api/v3/watchlist/changes`接口。

| 风险 | 缓解 |
|------|------|
| RAW并行写锁竞争 | 三步写不同表+busy_timeout=10s，计算并行>写入串行 |
