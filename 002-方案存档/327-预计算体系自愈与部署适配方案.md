# 327 — 预计算体系自愈与部署适配方案

> **背景**：2026-08-12 用户提出预计算体系"限定时间问题反复出现、超时后无法正常运行"，要求全面问题清查。核查发现核心缺陷链：**running 状态无超时恢复 + 数据到达时间假设 + 无新鲜度自查**——多次故障（P3 卡死致快照陈旧 2 天、价值地图低估值 37 vs 实际 1111 只）的共同根因。且未来**独立部署（非24h开机、开机时间不定、无开发工具）**，体系必须能**自查与实时补救**。
>
> **关联**：292（全局数据体系管道）、305（管道驱动）、325（标签库）、326（前端日期透出）、记忆（P3 failed 重试修复 4bc84b8、Tushare 数据发布延迟 15:30-17:00）

## 一、问题清查结论（实证）

### 1.1 核心缺陷链

```
管道 = 数据驱动 + 时间假设，但无自愈
  ├─ running 无超时 → 任何中断（重启/卡死）→ 永久阻塞 ← 本次 P3 卡死
  ├─ 数据到达时间不确定（Tushare 15:30-17:00 逐步发布）→ 定时触发必错位
  ├─ 非24h开机 → 错过时间窗 → 当日无任何补救
  └─ 无新鲜度自查 → 错误静默传播到前端 → 用户决策受损
```

### 1.2 缺陷清单（按严重度）

| # | 缺陷 | 位置 | 后果 |
|:-:|------|------|------|
| 1 | **running 状态永不超时恢复**（`mark_step_running` 仅接受 pending/failed→running） | enhanced_cache_manager.py:2496 | P3 卡死根因：重启后旧 running 无法重置 → P4/S1 永久阻塞 |

## 二、整改方案（按优先级分阶段）

### 阶段 1（P0）：running 超时恢复（根治 #1，最高优先）

**目标**：任何中断后管道能自愈，不再永久卡死。

**实现**：
1. `mark_step_running` 改造——支持 **running 超时重置**：
```python
def mark_step_running(self, pipeline_date: str, step_id: str, timeout_hours: float = 4.0) -> bool:
    """尝试将环节标记为 running（幂等锁 + running 超时自动重置）

    2026-08-12 修复：running 超过 timeout_hours（默认4h，P2最长1.6h）自动重置
    为 pending——daemon 重启/卡死后旧 running 记录不再永久阻塞管道。
    """
    # 先处理超时的 running（4h 内未完成的环节视为中断）
    self.conn.execute(
        "UPDATE pipeline_status SET status='pending', detail='timeout 自动重置' "
        "WHERE pipeline_date=? AND step_id=? AND status='running' "
        "AND started_at < datetime('now', ?)",
        [pipeline_date, step_id, f'-{int(timeout_hours)} hours']
    )
    rc = self.conn.execute(
        "UPDATE pipeline_status SET status='running', started_at=CURRENT_TIMESTAMP "
        "WHERE pipeline_date=? AND step_id=? AND status IN ('pending', 'failed')",
        [pipeline_date, step_id]
    ).rowcount
    return rc > 0
```
2. `_drive_pipeline` 启动时（开机）**扫描全部 running 残留** → 对超时环节统一重置：
```python
def _recover_stale_running():
    """开机/每 tick：清理超时 running，防止永久阻塞"""
    _ecm.conn.execute(
        "UPDATE pipeline_status SET status='pending', detail='stale running 重置' "
        "WHERE status='running' AND started_at < datetime('now', '-4 hours')"
    )
    _ecm.conn.commit()
```
3. `_drive_pipeline` 每 tick 调用 `_recover_stale_running()`（放在 has_data 检查前，确保即使数据未到也先清理残留）。

**验收**：模拟 running 残留 4h+ → 重启 daemon → 管道自动恢复推进。

### 阶段 2（P0）：开机自愈 + 数据驱动日终（根治 #2/#4/#5/#6/#9）

**目标**：任意时间开机（含错过 15:30、非当日）都能自动补算；日终同步改为数据驱动。

**实现**：
1. **开机数据年龄审计**（新增 `_audit_data_freshness()`）：
   - 查 daily_cache 最新 trade_date → 若交易日且非今日 → **触发"昨日补算"**（用最新数据日期驱动 C1→P4→S1）
   - 记录审计结果到日志 + 健康 API 透出
2. **日终同步数据驱动**（替代 15:30 定时）：
   - `_drive_pipeline` 的 `has_data >= 4000` 门槛已是数据驱动——**补强为"数据到达后触发日终同步"**：
   ```python
   # 数据驱动日终：daily_cache 今日>=4000 且非交易日校验 → 触发 run_daily_sync（若未执行）
   if has_data and not _is_pipeline_complete(today):
       _ecm.ensure_pipeline_steps(today)
       _drive_pipeline()  # 现有逻辑已覆盖
   ```
   - scheduler_manager 的 15:30 定时**保留为兜底**（API 进程无 daemon 时），但 daemon 模式以数据驱动为准
3. **`_get_active_codes` 数据日期透出**：返回 `(codes, data_date)` 元组或全局记录 `_current_data_date`，管道/P4/S1 使用同一日期，避免"今日空回退昨日"混乱。
4. **删除 `_check_precompute_status` 死代码**（其"9:30 前跳过/15:30 后全量"由新审计替代）。

**验收**：模拟"昨日有数据、今日开机（非15:30）"→ daemon 启动 → 自动用昨日数据补算 → 快照更新。

### 阶段 3（P1）：新鲜度自查 + 前端透明度（根治 #3/#11）

**目标**：数据陈旧可察觉，不静默传播。

**实现**：
1. **健康检查扩展**（`/api/v3/health/ready`）：
   - 新增 `data_freshness` 字段：各关键表（daily_cache/strategy_signal_detail/opportunity_tags_cache/treemap_snapshot）最新数据日期 vs 期望交易日
   - 陈旧程度分级：fresh / stale_1d / stale_2d+ → 告警
2. **快照日期透出**（前端）：
   - treemap API 响应已含 `snapshot_date`（现有）→ **前端标注"数据截至 X"**（326 已做 signal_date，扩展至快照）
   - 快照构建时记录 `data_date`（实际数据交易日，非构建日）——区分"构建时间"与"数据时间"
3. **调用层校验**：`get_tags/get_snapshot` 等网关可选择性校验数据日期（若陈旧则日志告警，不阻断）。

**验收**：人为制造陈旧快照 → 健康 API 报 stale → 前端显示"数据截至 08-10"。

### 阶段 4（P1）：单只超时隔离（根治 #7）

**目标**：单只股票计算卡死不拖垮全量。

**实现**：
1. P3/P4 单只计算包 `timeout`（如 30s）：
   - 用 `concurrent.futures.ThreadPoolExecutor` + `future.result(timeout=30)` 包裹单只计算
   - 超时 → 跳过该只 + 记录日志（标记 `timeout_ts_codes`），不中断全量
2. 复用现有 `_safe_compute` 模式（已对异常隔离，补超时）。

**验收**：模拟单只死循环 → 30s 后跳过，其余正常完成。

### 阶段 5（P2）：启动编排 + sync_requests 兜底（根治 #8/#10）

**目标**：非24h开机的完整启动保障。

**实现**：
1. **start.command 强化**：
   - 先启 daemon → 等数据审计完成 → 再启 API（当前已部分实现，补"数据就绪"等待与告警）
   - 若 daemon 未启（API 独立跑）→ 健康 API 报 `daemon_down`，sync_requests 不堆积（标记待 daemon 消费）
2. **sync_requests 持久化兜底**：队列已落库（SQLite）→ daemon 启动后自动消费积压请求（现有 consume_pending_requests 已支持，补"启动时立即消费"）。

## 五、风险与说明

| 风险 | 对策 |
|------|------|
| running 超时误重置（真在计算的环节被重置）| 超时 4h 远大于最长环节（P2=1.6h）；且重置后幂等锁防止并发 |

## 八、审查修正记录（2026-08-12，全面复核）

实施完成后全面审查 5 阶段代码，发现并修正 3 个正确性问题：

### 修正 1（阶段4）：`_run_with_timeout` 超时后仍阻塞主流程（🔴 关键）

**问题**：用 `with ThreadPoolExecutor` 块，超时后 `shutdown(wait=True)` 阻塞等待后台线程——实测超时 2s 但函数耗时 8s（卡死线程跑完才返回），**超时保护形同虚设**。

**修正**：改显式 `ThreadPoolExecutor` + `shutdown(wait=False, cancel_futures=True)`——超时后立即返回（2.0s），后台线程不阻塞主流程。实测验证。

### 修正 2（阶段2）：数据驱动下 C1-C6 用旧日期重复采集（🟡 重要）

**问题**：数据日期已完整（has_data>=4000）时，管道仍执行 C1-C6 采集（用 data_date=旧日期）——重复劳动且可能覆盖。

**修正**：数据日期完整时 C1-C5 标记 done 跳过（"数据已完整，采集跳过"），C6 概念板块独立采集；数据缺失由完整性检查独立补采，不在此阻塞。

### 修正 3（阶段2）：`_audit_data_freshness` 定义未调用（🟡 设计缺口）

**问题**：审计函数按设计应"记录日志"，但无调用点。

**修正**：main() 启动流程接入（run_integrity_check 前调用，日志记录数据新鲜度）。

### 修正 4（阶段5）：start.command 就绪检测可能被历史日志误判（🟢 边界）

**问题**：`grep "进入主循环"` 全日志匹配，旧日志残留可能误判就绪。

**修正**：改 `tail -1` 仅检查日志最后一行是否为本实例"进入主循环"。
