# 事件监控器与 L4 交叉验证仲裁层设计

## 一、事件监控器

### 1.1 核心原则

A 股市场是一个 **事件驱动特征极强** 的市场——财报发布、政策出台、资本运作、行业新闻等事件，常常在短时间内彻底改变一只股票的定价逻辑。纯粹依赖量价指标的系统在面临重大事件时往往表现为"滞后反应"。

事件监控体系的核心是三项能力：
1. **预期差利用**：区分"超预期驱动"和"利好出尽是利空"的本质差异
2. **预判性监控**：将可提前获知的事件（解禁/财报/减持预披露）纳入日历，提前计入评分
3. **事件-仓位联动**：事件综合评分直接参与 L4 操作建议中的仓位比例计算

### 1.2 双通道架构

事件监控拆分为 **已知日历事件**（可预判、提前计入）和 **检测事件**（发生后实时标记）两通道，独立运行后合并进入统一事件评分：

```
已知日历事件通道（预期数天至数月）     检测事件通道（T+0/T+1）
  ├── 限售股解禁日                      ├── 龙虎榜异动
  ├── 财报预约披露日                    ├── 业绩预告超预期
  ├── 减持预披露截止日                  ├── 概念联动
  ├── 分红/除权除息日                   ├── 技术形态突破
  └── 股权激励行权期                    └── 定增破发/资本运作信号

         ↓ 合并 ↓
  事件综合评分 (-5 ~ +5)
         ↓
  L4 仲裁层仓位调整
```

### 1.3 事件监控完整工作流

从数据采集到仓位建议共六步，前后串联：

```
Step 1: 数据采集
  日历通道 → Tushare/AKShare 读取解禁/减持/财报日期等结构化数据
  检测通道 → ECM 缓存表读取每日新增的上榜/预告/概念波动等
  ↓

Step 2: 事件识别
  每个子类事件有独立的检测子函数（命名规范详见 §1.4）：
    _detect_earnings_surprise()       → A1
    _detect_period_report_date()      → A3（日历通道）
    _detect_share_float()             → B1（日历通道）
    _detect_longhubang()              → D1
    每函数返回 {event_type, direction: ±2~±1, confidence, description}
  ↓

Step 3: 新闻质量过滤（仅 D 类事件）
  新闻通道检测到的事件先过五层过滤（详见 §1.11）
  news_quality_score < 0.3 → 丢弃，不进入 Step 4
  通过的新闻 → 方向值按 quality_score 折扣后进入 Step 4
  ↓

Step 4: 评分合并
  同类事件取最高绝对值，不同类合并为综合评分（详见 §1.7）
  同类定义：同一只股票同一天触发多个同一维度（如 A1+A2）→ 取绝对值最高的那个
  不同类合并：综合评分 = max(|A_max|,|B_max|,|C_max|,|D_max|,|E_max|) × 方向
  输出 event_composite_score (-5 ~ +5)
  ↓

Step 5: 仓位联动
  event_composite_score 直接映射仓位建议（详见 §1.7）
  ↓

Step 6: 冲突优先级裁决
  多维度信号方向冲突时（如 A 类看涨 + B 类看跌），以最高优先级维度为准（详见 §1.8）
  优先级：C(监管) > A(财务) > B(资本运作) > D(情绪) > E(特殊)
```

每步的输出是下一步的输入，形成端到端的"数据→信号→决策"管道。

### 1.4 事件检测函数规范

每个子类事件的检测函数遵循统一签名：

```python
def _detect_<event_name>(ts_code: str, **kwargs) -> dict:
    """返回该事件的最新检测结果。
    
    Returns:
        dict: {
            "detected": bool,       # 是否检测到事件
            "direction": int,       # +2(强利好) / +1(利好) / -1(利空) / -2(强利空)
            "confidence": float,    # 0.0 ~ 1.0
            "source": str,         # 数据来源表名
            "description": str,    # 事件描述文本
            "event_date": str,     # 事件日期 YYYY-MM-DD
        }
    未检测到时返回 {"detected": False, "direction": 0, "confidence": 0, ...}
    """
```

### 1.7 事件评分规则与仓位联动

每类事件独立产出 -2 ~ +2 评分，同类事件取最高绝对值，不同类事件按 加权/最高绝对值 合并：

```
事件综合评分 = max(|A_max|, |B_max|, |C_max|, |D_max|, |E_max|) × 方向(正/负)

评分映射：
  +5 ~ +3: 强烈正向事件驱动 → 重仓参与（80%仓位容量）
  +3 ~ +1: 中性偏正向 → 正常仓位（60%）
  -1 ~ +1: 无明显事件驱动 → 仅技术信号操作（40%）
  -3 ~ -1: 中性偏负向 → 降低仓位至20%
  -5 ~ -3: 强烈负向事件驱动 → 清仓规避
```

### 1.8 事件优先级分层（不同维度事件冲突时）

遵循 **分层处理** 原则（来源：知识库"分层处理（方法论冲突）"）：

1. **监管事件（C 类）**：最高优先级，无条件执行（立案调查→清仓，不退市风险标记黑名单）
2. **财务事件（A 类）**：优先级高于技术信号（即将发布利空财报→减仓，即使技术面看多）
3. **资本运作事件（B 类）**：与量价信号并重（量价看多但事件利空→降低仓位但不完全回避）
4. **市场情绪事件（D 类）**：作为权重修正因子，不独立触发买卖
5. **特殊事件（E 类）**：仅作标签展示，不直接触发仓位调整

### 1.11 新闻质量甄别与误导规避

新闻快讯（特别是免费替代的东方财富快讯）存在**误导性、蹭热点、标题党、旧闻重发**等问题，若不加以甄别，事件监控体系将被虚假信号污染，产生"假阳性"事件评分，误导仓位决策。

**问题来源分析**：

| 误导类型 | 表现 | 影响 | 来源频率 |
|---------|------|:----:|:--------:|
| **蹭热点** | 公司发布公告称"关注到XXX题材"，实际与主营业务无关 | 产生虚假催化剂信号 | 高（题材炒作期常见）|
| **标题党** | 新闻标题夸大事实，正文无实质内容 | 误导情绪评分 | 中 |
| **旧闻重发** | 将数周前的已有公告重新包装为"最新"新闻 | 产生重复事件信号 | 中 |
| **公告误读** | 市场/媒体对公告内容的理解偏差 | 信号方向搞反 | 低 |
| **无实质利好** | 签订普通框架协议、日常经营合同被包装为重大利好 | 高估事件影响 | 中高 |

**五层过滤机制**：

```
第一层：来源分级
  ├── 巨潮公告（直接来自法定信披平台） → 权威级，免过滤直接进入事件评分
  ├── 东方财富快讯 / 财联社 → 可信级，需过2-5层
  └── 新浪财经 / 自媒体聚合 → 参考级，降低权重

第二层：内容-股价联动校验（核心反误导手段）
  新闻内容匹配到的股票，如果新闻发布后无明显异常波动（量价无响应），
  则降低该新闻的 news_quality_score。规则：
  - 新闻发布后 30min 内股价变化 < 0.5% → quality × 0.5
  - 新闻发布后 30min 内成交量无异常放大 → quality × 0.8
  极端情况：无任何量价反应的"利好"新闻 → 视为无效新闻

第三层：蹭热点识别（参考知识库"题材炒作"中"大新强顺"框架）
  当公告/新闻涉及热门题材关键词时，检查公司主营业务是否匹配：
  - 检查 Stock.industry 是否与题材行业一致
  - 检查最近一期财报中题材相关业务营收占比（从主营业务构成表获取）
  - 不匹配 → news_quality_score × 0.3，标记为"蹭热点"标签

第四层：旧闻检测
  对比新闻内容与最近 30 日内同一股票的历史事件记录：
  - 事件类型相同（如"签订合同"、"获得资质"等）→ 疑似旧闻重发，quality × 0.5
  - 与上周事件完全重复 → quality = 0（丢弃）

第五层：多源交叉验证
  同一事件在 2 个以上独立来源同时出现 → 置信度提升
  仅 1 个来源且该来源为自媒体级别 → 置信度降低
```

**新闻质量评分在事件监控中的使用规则**：

```
news_quality_score ≥ 0.7: 直接进入事件评分计算（全权重）
0.3 ≤ news_quality_score < 0.7: 事件评分 × quality（折扣计入）
news_quality_score < 0.3: 不进入事件评分，仅做标签展示
```

**实施建议**：
- 第一层（来源分级）和第三层（蹭热点识别）在 P2.1 第一批即可落地（数据已有）
- 第二层（量价联动校验）需要接入实时快照数据，在 P2.1 第二批随新闻快讯通道一起实现
- 第四层（旧闻检测）和第五层（交叉验证）为持续优化项，在 P2.5 迭代完善

## 二、L4 交叉验证仲裁层

### 2.1 定位

Treemap 点击个股方块时触发的深度诊断。核心产出：综合可信度评估 + 操作建议 + 估值跟踪退出信号。

> ⚠ `signal_strength` 衍生标签已在 P0.4 L2标注阶段预计算并写入标签池，L4 层直接读取复用，无需重新计算。详见 295号§3.5 和 294号§三 P0.4。
>
> ⚠ `max_position_ratio` 取值自 **P2.1 事件监控器**产出的事件综合评分（`event_composite_score`），因此 P2.2 必须在 P2.1 完成后才能开始。详见 294号§四 依赖关系图第五梯队。

本层采用 **共识投票** 机制替代传统的 if-else 规则匹配：每个有值标签独立投票（+1 看多 / 0 中性 / -1 看空），按共识率（看多票数/总有效票数）输出最终决策。详见 §2.2。

### 2.2 仲裁逻辑（共识投票引擎）

L4 仲裁分四步串联执行：

```
Step A: 前置估值门禁
  → valuation_level = high/extreme_high 且用户启用"价值低估"预设场景
  → 直接返回 ✗ 不推荐（不进入后续步骤）

Step B: 情绪环境全局加权
  → sentiment_phase = recovery → 所有看多票 × 1.0（正常）
  → sentiment_phase = ebb     → 所有看多票 × 0.7（环境不利，折扣）
  → sentiment_phase = climax  → 短线类标签看多票 × 0.7（过热，折扣接力信号）
  → sentiment_phase = ice     → 看空票 × 0.7（冰点可能反转，降低空头权重）

Step C: 共识投票
  每个有值的标签独立投票（映射规则见下方"标签投票映射表"）：
  ├── 看多票数 = sum(各标签方向值 > 0)
  ├── 看空票数 = sum(各标签方向值 < 0)
  ├── 总有效票数 = 有值的标签总数（中性票计入分母不计入分子）
  └── 共识率 = 看多票数 / 总有效票数（方向为正向时）或 看空票数 / 总有效票数（方向为负向时）

Step D: 结果映射
  ┌──────────────┬─────────────────────────────┬──────────────┐
  │ 共识率         │ 判定                         │ 操作建议       │
  ├──────────────┼─────────────────────────────┼──────────────┤
  │ ≥ 75%        │ ★ 强共识（方向明确）           │ 建仓/加仓     │
  │ 55% ~ 75%    │ ✓ 中等确认                    │ 建议建仓      │
  │ 40% ~ 55%    │ ℹ 分歧（多空接近）             │ 仅做T/持有    │
  │ 25% ~ 40%    │ ⚠ 偏空                        │ 减仓/回避     │
  │ < 25%        │ ✗ 强烈看空                     │ 清仓/不推荐   │
  └──────────────┴─────────────────────────────┴──────────────┘

  兜底：当总有效票数 < 3（标签数据不足时），默认 → ℹ 不推荐
```

**估值跟踪退出联动**（与共识投票并行执行，不受 Step A 门禁影响）：

当用户自选股持仓期间，无论共识投票结果如何，同时检查估值退出条件：

| 开仓时估值 | 触发条件 | 操作 | 说明 |
|-----------|---------|------|------|
| low/extreme_low | `valuation_level` 变为 high/extreme_high + 情绪高潮 | ✗ 建议减仓/止盈 | 估值修复+情绪过热双确认 |
| low/extreme_low | `composite_rating` 上升超过 +1.0 | ℹ 建议部分止盈 | 目标接近 |
| extreme_low | `valuation_level` 回升至 fair | ℹ 估值修复完成 | 目标达到 |
| 任何 | `fina_health` 从 pass 变为 suspicious/fail | ✗ 建议清仓检查 | 基本面恶化 |

> 估值跟踪与共识投票的关系：估值跟踪是**独立于共识投票的并行通道**。即使共识投票结果是"建仓"，如果估值退出条件被触发，`operation_advice.action` 将以退出信号为准。两者冲突时以估值退出优先（因为退出涉及本金保护）。

### 2.3 自选股变更检测（daily_change_summary）

L4 仲裁层每日读取自选库（`opportunity_library` 表 `lib_level != 'done'`）内股票的当日标签，与上日标签比较，产出 `daily_change_summary` 结构体。变更检测在 L4 中执行（因为它已读取全量标签用于仲裁规则，内存中做 diff 无需额外 IO），变更摘要供 L5 自选看板消费。

**8 个监控维度的比较规则**：

| # | 标签名 | 比较方式 | 标记条件 |
|:-:|--------|---------|---------|
| 1 | `main_force_phase` | 值比较（5种枚举） | 任意变化 |
| 2 | `valuation_level` | 值比较（5档枚举） | 任意变化 |
| 3 | `trend_alignment` | 方向比较（up↔down） | 方向反转 |
| 4 | `fund_flow` | 方向比较（inflow↔outflow） | 方向反转 |
| 5 | `phase_confidence` | 数值差值 | ±0.2 以上 |
| 6 | `catalyst_event` | 值比较（none↔有效值） | 从无到有或从有到无 |
| 7 | `fina_health` | 值比较（pass↔非pass） | pass→非pass |
| 8 | `signal_strength` | 数值差值 | ±1.0 以上 |

> **财务数据季频说明**：第 2 维（`valuation_level`）和第 7 维（`fina_health`）依赖的财务数据（`income_cache`/`balancesheet_cache`/`cashflow_cache`）为季频更新。在财报空窗期（每次报告后 2-3 个月），这两个维度通常不会产生变化。这**不是故障或数据断连**，而是财务数据固有节奏。建议：
> - 连续多日无变化时，变更检测的推送分级自动降至 `none`（不推送），避免无效通知
> - 前端展示时标注"财务数据季频更新"

**输出结构体**：

每日仅对自选库内股票产出（非自选股不经过此流程），写入 `opportunity_status_history` 表。

**推送分级**（基于 `change_count` 和具体变化项综合决定）：

| 推送级别 | 触发条件 |
|:--------:|---------|
| `urgent` | fina_health→fail 或 valuation_level→extreme_high |
| `important` | main_force_phase 切换 或 catalyst_event 从无到有 |
| `normal` | signal_strength ±1.0 以上 或 trend_alignment 切换 |
| `none` | 变化仅为 phase_confidence 轻微波动 |

> 变更检测结果同时用于 park 暂存股的唤醒判定（详见 299号§二「park唤醒条件」）。当 park 股票触发任意唤醒条件时，`daily_change_summary` 会额外产出一条 `wake_signal` 字段，notifier（P2.4）据此将股票自动升回 scan 并推送唤醒通知。

| `cross_validation.user_checklist` | **用户自判清单（用户用）** | 弹窗风险提示区 |
| `operation_advice` | 操作建议 + 仓位 + 入场计划 | 弹窗操作区 |
| `risk_warnings` | 行业/公司风险提示 | 弹窗风险区 |
| `valuation_tracking` | 估值变化跟踪（仅自选库展示） | 弹窗估值区 |

**verdict 的写作原则**：
- 先说投票结果：几票看多、几票看空、几票中性
- 再说每个维度的具体指向：主力在做什么、估值在什么位置、趋势方向
- 最后给结论：综合判断是什么
- 语言直白、零术语、用户可以复制给朋友看的程度

**user_checklist 的定位**：
- 系统不替用户做决定，但帮用户列出"你需要额外判断的问题"
- 每一条以 ⚠ 或 ℹ 开头，区分"风险"和"信息"
- 用户浏览后可以快速决定"我信系统建议"或"我觉得××风险太大不参与"

### 2.5 前端展示对接

本层 JSON 输出由 Treemap 点击弹窗（296号方案能力四）消费。仲裁结论（`verdict` + `voting_detail`）、操作建议（`operation_advice` + `max_position_ratio`）、风险提示（`risk_warnings` + `user_checklist`）、估值跟踪（`valuation_tracking`）四块对应弹窗中的四个独立区块。其中估值跟踪区块仅对已在自选库（`in_library != none`）的股票展示。
