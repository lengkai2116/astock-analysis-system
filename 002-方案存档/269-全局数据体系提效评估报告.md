# 全局数据体系提效评估报告

## 核心结论

**全局数据体系需要从架构层面进行修正才能实现操作效率的质变。** 当前的性能瓶颈并非局部问题，而是数据存储模型、预计算策略和索引策略三者叠加的结果。仅做缓存层优化（如 268 号方案第一阶段的 CDN 本地化 + API 缓存）可以改善 20-30%，但要使系统达到商用证券软件的操作感，必须修正数据体系的核心设计。

## 二、需要修正的 8 项架构问题

### 🔴 P0-1：indicator_cache EAV 存储格式导致的 14x 行数膨胀

**现状：** PrecomputeIndicatorManager 使用实体-属性-值（EAV）模型：

```sql
CREATE TABLE indicator_cache (
    ts_code TEXT, trade_date TEXT, indicator_name TEXT, value REAL, ...
    PRIMARY KEY (ts_code, trade_date, indicator_name)
);
```

每只股票每天对 14 种指标每种生成 1 行：
- 当前：5000 只 × 1200 天 × 14 指标 = 84M 行
- 若改为宽表：5000 只 × 1200 天 × 1 行（含 14 列）= **6M 行** → **减少 93%**

**影响：** 仅此项修正即可将 16GB 数据库缩小约 8-10GB。所有 `indicator_cache` 查询直接提速（因为表更小、索引更有选择性）。

**修正方案：**
- 方案 A（推荐）：改为指标垂直分区宽表，如 `indicator_ma_cache(ts_code, trade_date, ma5, ma10, ma20)`、`indicator_macd_cache(ts_code, trade_date, dif, dea, hist)` 等
- 方案 B（更激进）：放弃预计算，改为按需实时计算（从 daily_cache 计算 14 种指标的时间开销约 2-5ms/只）

### 🔴 P0-2：factor_cache 绕过 ECM 连接管理，无索引

**现状：** `FactorPrecomputeManager` 在 `factor_precompute.py` 中通过**独立的 `sqlite3.connect()`** 连接到 stock_cache.db：

```python
self._db_path = os.path.join(...)  # 硬编码路径
conn = sqlite3.connect(self._db_path)  # 绕过 ECM!
```

每个 INSERT 使用逐行方式（row-by-row，行内循环），而非批量插入。`factor_cache` 没有次级索引（仅有 PK）。37M 行插入缓慢、查询更慢。

**影响：** 37M 行的因子数据几乎不可读。这是算力浪费 + 存储浪费的双重问题。

### 🟠 P1-1：indicator_cache 和 factor_cache 缺少与查询模式匹配的索引

已知索引匹配情况（对 86M 和 37M 行表）：

| 查询方法 | SQL | 可用索引 | 是否高效 |
|---------|-----|---------|:--------:|
| `get_indicator_data(ts_code, indicator_name)` | `WHERE ts_code=? AND indicator_name=?` | PK(ts_code, trade_date, indicator_name) | ❌ **indicator_name 是 PK 第3列，只能部分使用** |
| `get_cached_factor(ts_code, factor_name)` | `WHERE ts_code=? AND factor_name=?` | PK(ts_code, trade_date, factor_name) | ❌ **同上的问题** |

两个查询都需要在给定 `ts_code` 后对 `trade_date` 做全扫描来筛选 `indicator_name`/`factor_name`。

### 🟠 P1-2：八张 as_* 常驻表增加不必要开销

ECM 的 `_init_tables()` 中创建了 8 张 `as_*` 表（代码注释写明了"已不再写入但保留表结构避免旧代码报错"）：

- `as_market_snapshot`, `as_top_stocks`, `as_sector_ranking`, `as_concept_ranking`
- `as_limit_pool`, `as_minute_kline`, `as_lhb_detail`, `as_news`, `as_quote_cache`

这些表在应用启动时 CREATE TABLE IF NOT EXISTS，占用建表时间和 schema 空间。同时为其中 5 张表创建了索引（as_snapshot_ts, as_minute_ts, as_minute_date, as_lhb_date, as_news_time），这些索引也会在启动时检查/创建。

### 🟡 P2-1：两张空表（win_rate_cache + strategy_signals）

这两张表已定义、已有索引检查，但**数据始终为空**。启动时有 CREATE TABLE + 索引 SQL 执行，运行时偶有 COUNT(*) 查询。

### 🟡 P2-2：数据保留策略缺失

`invalidate_old_data(days=30)` 只能清理 `daily_cache`，对 `indicator_cache` 和 `factor_cache` 无效。这两张表的行数随每次全量预计算单调递增——已经存在的行被 INSERT OR REPLACE 覆盖，但新的指标或新的股票会不断追加。

### 🟡 P2-3：全量预加载的 Select * 模式

`get_cached_daily_batch()` 和 `preload_all()` 多次执行 `SELECT * FROM daily_cache`（580 万行全量）。在 16GB 数据库上，全表扫描 + pandas DataFrame 构建的时间很长。而且**同样的全量加载在多次调用中重复执行**——没有判断 `_all_daily` 是否已经加载。

### 🔵 P3-1：轻量级 TieredMemoryCache 与实际需求不匹配

`TieredMemoryCache` 最上层只有 100 条/次，不符合仪表盘场景的使用模式。如果一个页面上有 8 个独立 API 调用，第 2 次刷新时命中率几乎为 0（TTL=3s 的实时数据缓存配合不当）。

## 三、修正优先级矩阵

| 优先级 | 问题 | 影响面 | 修正难度 | 预期效果 |
|:------:|:-----|:------|:--------:|:--------|
| **P0** | indicator_cache EAV → 宽表 | 16GB → ~6-8GB | 中（需迁移脚本） | DB 缩小 50%+ |
| **P0** | factor_cache 路径/索引修正 | 37M 行变可读 | 中 | 释放 4-5GB |
| **P1** | 缺失的次级索引 | 查询 100x 提速 | 低（3行 SQL） | 大表查询立即提速 |
| **P1** | 移除 as_* 死表 | 启动加速、schema 精简 | 低（删代码） | 边际改善 |
| **P2** | 数据保留策略 | 阻止持续膨胀 | 中 | 16GB 不再增长 |
| **P2** | preload_all 重复加载 | 内存/时间浪费 | 低 | 减少冗余 I/O |
| **P2** | 空表清理/填充 | schema 简洁 | 低 | 边际改善 |
| **P3** | TieredMemoryCache 扩容 | 热点命中率 | 低 | 次要改善 |

## 四、对 268 号方案优化路线的补充

268 号方案提出的第一阶段 4 项措施（索引 + 缓存 + CDN + VACUUM）可立即见效但不触及数据体系核心问题。

修正数据体系后，优化路线应调整为：

| 阶段 | 措施 | 独立效果 | 叠加效果 |
|:-----|:-----|:--------:|:--------:|
| **A-数据体系修正** | index EAV→宽表 + factor 路径 + 索引 + 保留策略 | DB 缩小 50%，查询 10-100x | 基础 |
| **B-缓存增强** | TieredMemoryCache + API 缓存装饰器 + 聚合 API | 重复请求 0ms | DB 缩小 → 缓存命中率更高 |
| **C-前端加速** | CDN 本地化 + 前端缓存 | 加载快 1-2s | 叠加 |
| **D-SPA 改造** | Vue SPA 构建 | 页面切换即时 | 最终形态 |

**修正数据体系后，整个系统的性能改进空间：**
- 首次仪表盘加载：当前 5-15s → 修正后预期 **1-3s**（DB 缩小 + 索引 + 聚合 API）
- 页面切换：当前 1-3s → 修正后预期 **<300ms**（SPA 构建）
- 重复查询：当前 3-10s → 修正后预期 **<50ms**（缓存命中）

## 五、风险与建议

### 不建议的修正方向

1. **将 indicator_cache 迁移到 PostgreSQL**：当前架构中 PG 用于业务事务，混入大数据量缓存会导致业务查询减慢
2. **使用 Redis/Memcached**：增加运维复杂度，16GB 级数据对内存要求过高

### 建议的修正方向

1. **第一阶段（1-2 天）：** 添加缺失的次级索引（`indicator_cache(ts_code, indicator_name)`, `factor_cache(ts_code, factor_name)`） + 数据保留策略。这是改动最小、收益最大的修正。
2. **第二阶段（3-5 天）：** indicator_cache 格式重构（EAV → 宽表）+ factor_cache 路径统一到 ECM。这是根本性的数据体系修正。
3. **第三阶段（选做）：** 评估是否完全移除预计算，改为基于 daily_cache 的按需计算。随着 daily_cache 缩小，计算 14 种技术指标的开销在 2-5ms/只级别，5000 只全量计算约 10-25s，仅在首次或数据更新时执行一次。
