## 二、问题清单（逐项）

### P1：维度引擎为空壳转发器（严重）

**358号要求**（§10.2-10.3）：
> "每维度一个集中的维度引擎：负责该维度的唯一计算入口、统一输出格式、收敛冗余计算"
> 目标架构：dim1~dim6_engine.py 各自包含完整的维度计算逻辑

**实际状态**：
6个维度引擎文件（dim1-dim6_engine.py）各仅16-17行，全部是转发器：
```python
def evaluate(self, dims, tags, signals=None, lifecycle=None):
    from app.opportunity_atlas.structure_builder import build_structure
    return build_structure(dims, tags)
```

**影响**：
- 358§10.1描述的"零散分布和冗余计算"问题**未解决**
- vol_ratio 仍从6处独立计算，risk_level 仍从10+处独立计算
- 维度引擎的"唯一计算入口"设计目标完全未达成

**需确认**：是否按358§10.5实施路径（Phase 1-8，80h工作量）将builder逻辑整合到维度引擎中？还是保持当前的"引擎→builder"转发架构？

### P2：连续强度值未实现（严重）

**358号要求**（§5.1）：
> "每个维度输出连续强度值（而非离散分类）"
> 结构维：strength × (+1/0/-1) → 连续值
> 量价维：health_score → 0~1
> 筹码维：flow_strength × (+1/0/-1)
> 情绪维：temperature → 0~100 映射

**实际状态**：
维度引擎和builder仍输出离散值：
```python
# structure_builder.py 输出
{'state': '上升/盘整/下降', 'light': 'green/yellow/red', 'confidence': 0.7}

# 358要求的输出
{'strength': 0.82, 'direction': 1, 'continuous_value': 0.82}
```

**影响**：
- 358§4.2"比较和核算为基础"的设计目标无法实现
- 维度间无法进行精确的强度比较
- 共识率计算仍依赖离散投票

**需确认**：是否需要将所有builder的输出从离散(state/light)升级为连续(strength/continuous_value)？

---

### P3：动态权重未实现（严重）

**358号要求**（§5.2）：
```python
MARKET_REGIME_WEIGHTS = {
    'trending_up':   {'structure': 0.30, 'volume': 0.25, 'chip': 0.20, 'factor': 0.15, 'emotion': 0.10},
    'trending_down': {'structure': 0.25, 'volume': 0.20, 'chip': 0.15, 'factor': 0.20, 'emotion': 0.20},
    'ranging':       {'structure': 0.15, 'volume': 0.20, 'chip': 0.25, 'factor': 0.20, 'emotion': 0.20},
    'high_vol':      {'structure': 0.15, 'volume': 0.15, 'chip': 0.20, 'factor': 0.25, 'emotion': 0.25},
}
```

**实际状态**：
- 无 `MARKET_REGIME_WEIGHTS` 常量或配置
- 无市场状态检测器（regime detection）
- 所有维度等权处理

**影响**：
- 不同市场状态（牛市/熊市/震荡/高波动）下维度权重相同
- 358§5.2"不同市场状态的进入/退出阈值不同"无法实现

**需确认**：是否需要实现市场状态检测器和动态权重机制？

### P4：连续共识率未实现（严重）

**358号要求**（§5.3）：
```python
def continuous_consensus(dimensions, regime):
    weights = MARKET_REGIME_WEIGHTS[regime]
    weighted_sum = 0
    total_weight = 0
    for dim_name, dim_value in dimensions.items():
        w = weights.get(dim_name, 0.1)
        continuous = dim_value['continuous_value']  # -1~+1
        conf = dim_value['confidence']
        weighted_sum += w * continuous * conf
        total_weight += w
    return weighted_sum / total_weight if total_weight > 0 else 0
```

**实际状态**：
- `_aggregate()` 方法仍使用旧的12维离散投票逻辑
- 无 `continuous_consensus()` 函数
- 共识率计算基于 +1/-1 计数，不是连续加权

**影响**：
- 358§4.2"置信度加权：强度×置信度=有效强度"无法实现
- 共识率精度不足，无法区分"强共识"和"弱共识"

**需确认**：是否需要实现连续共识率计算替代旧投票逻辑？

## 三、修订方向建议（待沟通确认）

### 方案A：完整落地358方案（80h+工作量）

按358§10.5实施路径，将builder逻辑整合到维度引擎，实现连续强度值、动态权重、连续共识率、regime-aware仲裁。

**优点**：完全实现358设计目标
**缺点**：工作量大（80h+），风险高（改动面广）

### 方案B：务实收敛（20-30h工作量）

保持当前"维度引擎→builder"转发架构，聚焦解决数据通路问题和关键功能缺口：
1. 修复builder的tags key缺失（P11）
2. 统一chip_fund命名（P12）
3. 对齐dim_engine_results输出格式（P13）
4. 更新353总纲（P15）
5. 退役旧路径（P16）

**优点**：风险低，快速收敛
**缺点**：358的连续强度值、动态权重等核心升级未实现

### 方案C：分阶段渐进（推荐）

Phase 1（10h）：修复数据通路 + 格式对齐（P11-P14）
Phase 2（20h）：实现连续强度值 + 连续共识率（P2-P4）
Phase 3（20h）：实现regime检测 + 动态权重 + 仲裁升级（P3-P5）
Phase 4（20h）：维度引擎逻辑整合（P1）
Phase 5（10h）：条件稽核 + 状态总结 + 旧路径退役（P6-P7, P16）

**优点**：分步验证，风险可控
**缺点**：总工作量与方案A相当，但可按优先级裁剪
