### 2.2 问题详细分析

#### 问题1：stk_limit_cache日期格式不一致

**现象**：
- daily_cache的trade_date格式为`YYYY-MM-DD`（如`2026-08-17`）
- stk_limit_cache的trade_date格式为`YYYYMMDD`（如`20260817`）

**影响**：
- `_check_count()`函数使用`trade_date=?`查询时返回0
- 完整性检查误判为数据缺失，触发不必要的补采
- 实际上stk_limit_cache有7744行数据，只是格式不匹配

**验证**：
```
查询 stk_limit_cache WHERE trade_date='2026-08-17': 0 行
查询 stk_limit_cache WHERE trade_date='20260817': 7744 行
```

#### 问题2：margin_cache数据严重滞后

**现象**：
- margin_cache最新数据日期为`2026-07-17`
- 滞后32天

**影响**：
- 融资融券数据不完整，可能影响DIM-10风险维判定
- `_batch_margin()`只在空表时触发补采，非空表不更新

**根因**：
- `run_daily_sync()`中`n = _batch_margin(today)`在有数据时返回0
- `run_integrity_check()`中只检查`margin_cnt == 0`时补采

#### 问题3：adj_factor_cache数据滞后

**现象**：
- adj_factor_cache最新数据日期为`2026-08-06`
- 滞后12天

**影响**：
- 复权因子不完整，影响历史数据复权计算
- `_batch_adj_factor()`只在空表时触发补采

#### 问题4：分钟数据采集三源冲突

**现象**：
- 三个来源同时采集分钟数据：
  1. mootdx_collector.collect_minute_full(): 300s, check_trading_time=True
  2. akshare_collector._collect_minute_kline(): 300s, 无交易时段限制
  3. data_daemon._run_minute_backfill(): 日终触发, Tushare pro_bar

**影响**：
- mootdx与AKShare可能同时采集同一只股票分钟数据
- 写入同一minute_kline_cache表，可能产生重复数据
- 资源竞争：mootdx TCP连接数有限，并发过高可能触发限流

#### 问题5：日终同步触发时机依赖兜底机制

**现象**：
- 日终同步在15:30触发，但daemon可能在15:30-15:35窗口期不在运行
- 依赖`_check_daily_sync_backfill()`兜底机制在15:35后触发

**影响**：
- 如果daemon在15:30-15:35崩溃重启，日终同步可能延迟
- 隔日开机时，由`_drive_pipeline()`自动补算

#### 问题6：concept_cache无trade_date字段

**现象**：
- concept_cache表结构中没有trade_date字段
- 完整性检查中`check_count('concept_cache', today_fmt)`会失败

**影响**：
- `_check_count()`对concept_cache返回0，触发不必要的补采
- 实际上concept_cache数据存在（6053行），只是没有日期字段

#### 问题7：sync_requests队列积压处理（已解决）

**现象**：
- sync_requests表总请求42259条，待处理0条，已完成42256条
- 处理率99.99%，仅3条失败

**评估**：
- 队列处理机制正常，无积压风险
- 启动时立即消费积压，不等主循环首个tick

### 3.3 与其他系统功能冲突分析

#### 3.3.1 SQLite写锁竞争（已缓解）

**冲突场景**：
- data_daemon主循环每30s执行写操作
- P2预计算4 worker并发写strategy_signal_detail
- 完整性检查批量补采写库
- WAL checkpoint执行时需要读锁

**缓解措施**：
- P2改为单连接批量INSERT（354号修复）
- 预计算进行中跳过完整性检查
- WAL checkpoint降频：交易时段1800s，非交易300s

> **357号同步调整（2026-08-19）**：strategy_signal_detail 从 compute_cache.db 迁移到 snapshot_cache.db（成品数据逻辑），写锁竞争从 compute 分库转移到 snapshot 分库。snapshot 分库当前仅低频快照写入（~5,600行/日），新增中频写入（~5,500只/日）后 busy_timeout 需从 10s 提升到 30s 以匹配 compute 分库配置。

#### 3.3.2 Tushare API速率限制竞争（已缓解）

**冲突场景**：
- 日终同步批量调用8+ API
- sync_requests消费
- 完整性检查补采
- 管道驱动C1-C6采集

**缓解措施**：`_ts()`全局速率限制器统一管理

#### 3.3.3 分钟数据采集冲突（未完全解决）

**冲突场景**：
- mootdx与AKShare可能同时采集同一只股票分钟数据
- 写入同一minute_kline_cache表

**缓解措施**：无明确去重机制

#### 3.3.4 与API进程冲突（已缓解）

**缓解措施**：
- `DATA_DAEMON_RUNNING=1`环境变量隔离
- 共享SQLite WAL数据库，通过busy_timeout=30s + WAL模式避免锁冲突

## 四、采集层规则体系

基于本次核查发现的问题，建立完整的数据采集规则体系，确保采集层问题的根本解决和后续稳定运行。

### 4.1 数据格式统一规则

#### 规则1：日期格式统一规则

- **标准格式**：`YYYY-MM-DD`（ISO 8601）
- **适用范围**：所有`trade_date`字段
- **采集层职责**：
  1. 采集时统一转换为标准格式
  2. 写入存储层前进行格式验证
  3. 发现格式不一致时记录告警日志
- **兼容性处理**：
  - 对于历史数据（YYYYMMDD），提供一次性迁移脚本
  - 在`_check_count()`等查询函数中支持两种格式（兼容期）

#### 规则2：股票代码格式统一规则

- **标准格式**：`XXX.SH/SZ/BJ`（Tushare格式）
- **适用范围**：所有`ts_code`字段
- **采集层职责**：
  1. 采集时统一转换为标准格式
  2. 对于纯数字代码，根据交易所规则添加后缀
  3. 写入存储层前进行格式验证

#### 规则3：数据格式修订机制

- **修订位置**：采集层（data_daemon.py）
- **修订时机**：数据采集后、写入存储层前
- **修订内容**：
  - 日期格式转换
  - 股票代码格式转换
  - 列名统一（如`up_limit` → `high_limit`）
  - 数据类型验证（数值字段确保为numeric类型）
- **修订原则**：
  - 不修改实际数值
  - 仅修改格式、标题等元数据
  - 记录修订日志（修订前后对比）

### 4.2 数据完整度审查规则

#### 规则4：数据完整度审查规则（适配分库）

**4.1 数据量审查（基础层）**
- **检查项**：每张表的记录数是否达到阈值
- **阈值标准**：
  - daily_cache/daily_basic_cache: >= 5000行/日
  - moneyflow_cache/stk_limit_cache: >= 1000行/日
  - lhb_cache: >= 20行/日
  - 其他表：根据实际业务需求设定
- **触发条件**：数据量低于阈值时触发补采

**4.2 数据时效性审查（进阶层）**
- **检查项**：数据最新日期与当前日期的差距
- **时效性标准**：
  - 核心数据（daily_cache等）：滞后不超过1天
  - 补充数据（margin_cache等）：滞后不超过7天
  - 背景数据（fina_indicator等）：滞后不超过30天
- **触发条件**：数据时效性不达标时触发补采

**4.3 数据值合理性审查（质量层）**
- **检查项**：
  - 价格字段：close/open/high/low > 0
  - 成交量字段：vol/amount >= 0
  - 涨跌幅字段：-20% <= pct_chg <= 20%（排除新股上市首日）
  - 基本面字段：pe/pb/tot_mv > 0
- **触发条件**：发现异常数据时记录告警日志，不自动修正

**4.4 数据一致性审查（一致性层）**
- **检查项**：
  - 跨表一致性：daily_cache与daily_basic_cache的ts_code交集
  - 时间一致性：同一股票在不同表的日期对齐
  - 逻辑一致性：high >= close >= low
- **触发条件**：发现不一致时记录告警日志

**4.5 分库检查（新增）**
- **检查项**：
  - 各分库的数据完整性
  - 大表拆分后的数据完整性
  - 分库间数据一致性
- **触发条件**：每日盘点时执行

**4.6 独立迁移支持**
- **设计原则**：完整性检查机制应独立于具体数据源
- **实现方式**：
  - 使用配置文件定义检查规则
  - 支持自定义阈值和检查项
  - 提供检查结果报告接口

#### 规则6：数据源对接规则

**6.1 对接标准**
- **接口规范**：所有数据源必须通过统一的Provider接口对接
- **错误处理**：必须实现重试机制（指数退避）
- **速率限制**：必须遵守数据源的速率限制
- **日志记录**：所有数据源调用必须记录日志

**6.2 降级策略**
- **主数据源故障**：自动切换到降级数据源
- **降级数据源也故障**：返回空数据，记录告警日志
- **降级决策**：基于数据源可用性、数据质量、响应时间综合判断

**6.3 数据源健康检查**
- **检查频率**：每次数据源调用前检查
- **检查内容**：连接状态、响应时间、数据质量
- **健康状态**：healthy/degraded/unhealthy
- **故障恢复**：自动检测故障恢复，重新启用数据源

#### 规则7：采集时段管理规则

**7.1 时段定义**
- **交易时段**：9:00-15:30（周一至周五）
- **非交易时段**：15:30-次日9:00 + 周末
- **盘前集合竞价**：9:15-9:25
- **盘后大宗交易**：15:05-15:30

**7.2 时段限制规则**
- **盘中实时采集**：必须支持交易时段限制
- **盘后批量采集**：仅在非交易时段执行
- **后台补采**：优先在非交易时段执行
- **紧急补采**：允许在任何时段执行，但记录告警日志

#### 规则8：数据源配置管理规则

**8.1 配置文件**

- **版本控制**：配置文件必须纳入版本控制

**8.2 配置变更**

- **测试验证**：变更后必须进行测试验证
