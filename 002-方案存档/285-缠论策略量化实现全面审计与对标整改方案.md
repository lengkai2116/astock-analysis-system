# 缠论策略量化实现全面审计与对标整改方案

## 一、背景

在针对 301448.SZ（开创电气）的策略分析中发现三项异常：

1. **环境定位"无可用数据"** — 经排查属 DeepSeek 输出措辞问题，后台数据完整（HS300 5951行、daily_basic 有数据）
2. **主力成本与偏离度不可用** — moneyflow_cache 不含 `amount`/`vol` 列且单位转换错误（已修复，`buy_lg_vol×100` 手转股、`buy_lg_amount×10000` 万元转元）
3. **缠论日线中枢覆盖 33 个月** — 用户指出日K线图中明显可见多个中枢，但算法输出仅 1 个

本方案围绕第 3 项展开系统性审计与整改规划。

## 二、审计结果：当前实现与行业标准的 5 项差异

### 2.1 笔（Bi）的最小 K 线数

| 对比项 | czsc (5.6k⭐) | chan.py (1.9k⭐) | 知识库标准 | 当前代码 |
|--------|:------------:|:---------------:|:----------:|:--------:|
| `min_bi_len` | **6** | **6** | 5（严格笔） | **4** ❌ |
| 计数依据 | 包含处理后 K 线 | 包含处理后 K 线 | 不含包含关系的 K 线 | **原始 K 线 idx 差值** ❌ |

### 2.2 线段 vs 笔中枢的选择

| 对比项 | czsc | chan.py | 当前代码 |
|--------|:----:|:-------:|:--------:|
| 日线级别中枢 | **笔中枢**（跳过线段） | 笔中枢可配置 | 线段中枢（特征序列） |
| 线段使用 | 不使用 | 可启用 | 强制使用 |
| 稳定性 | ✅ 最高 | ✅ 良好 | ❌ 几乎从不触发断线 |

czsc 社区在实践中发现特征序列分型在真实数据中几乎无法稳定触发线段终结，因此默认跳过线段构建，直接用笔做中枢。LLM Wiki 知识库也明确建议："短线级别允许笔中枢"。

### 2.3 中枢演化逻辑

| 对比项 | czsc | chan.py | 当前代码 |
|--------|:----:|:-------:|:--------:|
| 演化方式 | 笔进出判定 | 笔进出+强制闭合 | 特征序列分型+9笔cap |
| 方向交替 | 自然交替（笔本身交替） | 自然交替 | 人工强制（跳过笔） |
| 验证 | ✅ 成熟 | ✅ 成熟 | ❌ cap打断→跳过笔→段数不足 |

### 2.4 线段终结算法的核心缺陷

当前特征序列分型检测条件：

```python
# 上升段的特征序列（下跌笔）：要求中间元素的高>两侧高且低>两侧低
return (f2_high > f1_high and f2_high > f3_high and
        f2_low > f1_low and f2_low > f3_low)
```

在实际数据中，经过特征序列包含处理后，下跌笔序列单调下降，几乎无法形成上述"中间高两侧高"的顶分型结构。**这是 S2 段包含 23 笔却不触发的根本原因**。

靠 9 笔 cap 强制打断后，交替性检查跳过中间笔，导致段数不足、中枢太少。

### 2.5 可视化（制图）能力

| 功能 | czsc plotly 版 | czsc Rust lightweight 版 | chan.py | 当前系统 |
|------|:--------------:|:------------------------:|:-------:|:--------:|
| 分型标记 | ✅ | ✅ | ✅ | ❌ |
| 笔绘制 | ✅ | ✅ | ✅ | ❌ |
| 中枢标注 | ❌ **不渲染** | ✅ 彩色矩形+区间数字 | ✅ | ❌ |
| 买卖点标注 | ❌ | ✅ | ✅ | ❌ |
| 输出格式 | plotly HTML | lightweight-charts 自包含 HTML | HTML/PNG | 仅 JSON |

> **重要发现**：czsc 的 plotly 版 `plot_czsc_chart`（存在于已安装包中）**不渲染中枢和买卖点**。中枢渲染仅在 Rust 版 lightweight-charts 模块中实现，该模块目前未随 PyPI 包分发。这意味着"复用 czsc 出图"这条路连 czsc 自己的中枢都没法画，必须走自建路径。

### 2.6 与 czsc v0.10.12 的实测定量对比

在同一数据（301448.SZ, 747 根日 K 线）上运行 czsc v0.10.12（纯 Python 版，min_bi_len=6）进行实测对比：

| 配置 | 分型数 | 笔数 | 笔方向交替 | 说明 |
|------|:------:|:----:|:---------:|------|
| **czsc v0.10.12 基线** | **234** | **50** | ✅ 交替 | 纯 Python 版，min_bi_len=6 |
| 我们 current（th=0%, mk=5） | 142 | 50 | ✅ | **笔数完全匹配** |
| 我们 current（th=0.5%, mk=5） | 132 | 46 | ✅ | 默认配置 |
| 我们 current（th=0%, mk=6） | 142 | 42 | ✅ | 笔长严格对齐 czsc |

> **th** = `fractal_threshold_pct`，**mk** = `min_klines`

#### 2.6.1 分型数差异的根因：包含处理

| 步骤 | czsc `remove_include` | 我们 `KLineMerger.merge()` | 差异 |
|------|----------------------|---------------------------|------|
| 合并方式 | 新K线与前1根合并，**不与更前一根重比** | 递归至完全无包含，**上限 10 次** | ❌ **我们合并更激进** |
| 合并后 K 线数 | ~600+（估算） | **542**（747→542，72.6%） | ❌ 少了约 60 根 |
| 分形识别 | `strict` 逻辑 | 同一 `strict` 逻辑 | ✅ 一致 |
| 分形数 | 234（占原始K线 31%） | 142（占合并后K线 26%） | 差值 65% |

**根因明确**：`_merge_once` 在新 K 线与前根合并后，合并结果可能与更前一根再次包含——循环直到稳定，这比 czsc 的单次合并更激进，去掉了更多 K 线特征。czsc 只做一次合并，不论结果是否还与更前一根包含。

#### 2.6.2 笔数完全一致（参数对齐后）

当 `threshold=0%`、`min_klines=5` 时，笔数恰好 **50:50**。这说明笔的构建逻辑本身没有本质缺陷。分形多出 65% 但笔数相同，说明我们的 StrokeBuilder 从较少的分形中提取了等量的有效笔。

#### 2.6.3 czsc 有"笔破坏回退"机制，我们没有

```python
# czsc __update_bi 后处理——每笔确认前检查是否被破坏
if (last_bi.direction == Up and bars_ubi[-1].high > last_bi.high) \
   or (last_bi.direction == Down and bars_ubi[-1].low < last_bi.low):
    # 笔被突破破坏，撤回
    self.bi_list.pop(-1)
    # 合并回 bars_ubi，从更前位置重试
```

czsc 在每笔确认前检查最新 K 线是否突破了笔的端点（向上笔突破高点，向下笔突破低点），如果突破则撤回该笔。我们的代码完全缺少这个机制。

#### 2.6.4 K 线计数方式不同

| 项目 | czsc | 我们的代码 | 影响 |
|------|------|-----------|------|
| 笔的 K 线数 | `len(bars_a)` — 通过 dt 范围筛选的包含后 K 线**实际数量** | `f2.idx - f1.idx` — 原始 K 线 **idx 差值** | idx 差值 = 原始位置差，比包含后数量多 → 等价于更宽松的阈值 |
| min_bi_len | **6** | 5（配置值） | czsc 更严格 |

#### 2.6.5 结论：笔的数量本身没有异常

对齐参数后笔数 50:50 完全匹配 czsc。用户感觉"61笔太少"的原因是：

1. **视觉上的"笔"与严格缠论定义不同**——K 线图中肉眼可见的每个小波动不都满足缠论成笔条件（5-6 根不含包含关系的 K 线、顶底分型严格成立、价格方向合理）
2. **包含处理过于激进**（递归至完全无包含 vs czsc 的单次合并），丢失了约 60 根 K 线的特征，减少了分形数量。但笔的层面被补偿，笔数依然匹配
3. **`min_klines=4`（原始值）偏松**，调整到 5 后笔数从 61 降到 46-50（取决于阈值），这是正确方向

#### 2.6.6 分步产量分析：从原始 K 线到中枢的逐级损耗

通过对 301448.SZ（747 根原始日 K 线）的完整链路追踪，确认各步骤的产量变化：

| 阶段 | czsc 产出 | 我们产出 | 差异说明 |
|------|:----------:|:--------:|----------|
| **原始 K 线** | 747 | 747 | 相同输入 |
| **包含处理后 K 线** | ~600+（估算） | **542**（保留 72.6%） | 我们丢失约 60 根（递归合并） |
| **分形** | 234（占原始 K 线 31%） | 142（占合并后 K 线 26%） | 同识别率下，因 K 线少而分形少 |
| **笔** | 50 | 50（参数对齐后） | 产量一致—StrokeBuilder 补偿了 K 线损失 |
| **线段** | **N/A（czsc 无线段层）** | 4（含强制跳过） | 特征序列几乎不断线（架构差异） |
| **中枢** | czsc 笔中枢模式≥1 | 1（33 个月超长中枢） | 线段中枢算法检测+演化双重缺陷 |

**关键推论**：
- 分形差 65%，但笔数一致→我们的 StrokeBuilder 有较强容错性
- 线段层是本系统与 czsc 的**架构性差异**，不是参数调整能解决的
- 即使修复包含处理带来更多分形，线段层瓶颈仍会限制中枢产量

## 三、整改方案

### Phase 1：算法对齐（P0 — 配置调优，不改架构）

| 改动项 | 当前值 | 目标值 | 依据 |
|--------|:------:|:------:|------|
| `min_klines`（默认配置） | 4 | **6** | czsc 标准 |
| K 线计数方式 | 原始 idx 差值 | **包含后 K 线列表位置差** | 已经实现（`merged_klines` 参数） |
| 分形阈值 `fractal_threshold_pct` | 0.5% | **0.5%**（已实现） | 知识库推荐 0.5% |

### Phase 2：架构转型（P1 — 笔中枢模式）

将日线级别的中枢构建从**线段中枢**切换为**笔中枢**：

```
当前：笔 → 线段（特征序列） → 线段中枢 → 中枢演化
                                      ↓
目标：笔 → 笔中枢（直接构建） → 笔进出演化
```

改动要点：

| 改动 | 说明 |
|------|------|
| 新增 `bi_zs_mode` 配置 | `True`=笔中枢（日线默认），`False`=线段中枢（保留现行） |
| 新建 `BiZhongshuFinder` | 基于笔序列直接检测中枢重叠，替代 `ZhongshuAnalyzer` |
| 笔中枢演化 | 笔完全离开中枢区间→闭合→新中枢检测。无 cap、无交替跳过 |

**影响评估**：46 笔将自然形成约 5-8 个笔中枢（3 年周期），交替性天然满足。

### Phase 3：制图系统（P2 — 缠论 K 线可视化）

#### 3.1 设计目标

在 K 线图上叠加标注缠论结构，输出格式为**独立自包含 HTML 文件**（借鉴 czsc 的 lightweight-charts 方案），支持：

| 标注层 | 视觉样式 | 数据来源 |
|--------|----------|----------|
| 分型（顶/底） | 🔺/🔻 三角标记 + 价格标签 | `ChanlunAnalyzer.fractals` |
| 笔（Bi） | 彩色线段 + 方向箭头 | `ChanlunAnalyzer.strokes` |
| 线段（Segment） | 半透明色带（可选） | `ChanlunAnalyzer.segments` |
| 中枢（Zhongshu） | **彩色矩形区域** + 区间高低价标注 | `ChanlunAnalyzer.zhongshu_list` |
| 买卖点 | 买入🟢/卖出🔴 标记 | `buy_points/sell_points` |

#### 3.2 技术方案

| 方案 | 技术路线 | 复杂度 | 中枢渲染 | 数据源 |
|------|---------|:------:|:--------:|--------|
| **A：复用 czsc plot_czsc** | czsc plotly 版 | 低 | ❌ 不画中枢 | czsc 自己 |
| **B：lightweight-charts 自建** | `lightweight-charts-python` 库 | 中 | ✅ `chart.run_js()` | **我们自己的** |
| **C：plotly 自建** | `plotly` + `go.Figure` | 中 | ✅ `add_shape` | 我们自己的 |

**选定方案 B**，理由：

| 维度 | 说明 |
|------|------|
| 数据源 | 使用我们自己的 `ChanlunAnalyzer` 分析结果，与算法修改完全解耦 |
| 中枢渲染 | `chart.run_js("chart.addShape({type:'rectangle',...})")` 调用 JS API |
| 分型/笔 | `chart.marker()` + `chart.create_line()` 原生支持 |
| 依赖 | `pip install lightweight-charts`，纯 Python，无 Rust 依赖 |
| 输出 | `chart.show(block=True)` 或 `chart.save("chart.html")` 自包含 HTML |

**中枢矩形实现细节**（通过 JS 桥接）：

```python
chart.run_js(f"""
    chart.addShape({{
        type: 'rectangle',
        points: [
            {{time: '{zs.start_date}', price: {zs.high}}},
            {{time: '{zs.end_date}', price: {zs.low}}}
        ],
        options: {{
            fill: 'rgba(65, 105, 225, 0.15)',
            borderColor: 'rgba(65, 105, 225, 0.6)',
            borderWidth: 1
        }}
    }});
""")
```

`lightweight-charts-python` 的 `run_js` 方法可以直接注入任意 JS 代码，底层 TradingView 引擎原生支持矩形/线段/标记等全部图形。czsc 的 Rust 版 lightweight-charts 渲染器底层也是通过同样的 JS API 绘制中枢——两者没有本质区别。

**方案 A 的验证用途**：
虽然方案 A 不能用于最终输出，但它可以作为**交叉验证工具**——czsc 的 plotly 版本能渲染分型和笔，可以在同一只股票上：

```
并排对比:
  ┌─ czsc plot_czsc_chart ──┐  ┌─ 我们的 ChartBuilder ──┐
  │  分型位置 ✓  笔连接 ✓    │  │  分型 ✓ 笔 ✓ 中枢 ✓ 买卖点 ✓ │
  │  (标准答案)             │  │  (完整版)              │
  └─────────────────────────┘  └────────────────────────┘
  笔数量一致？位置一致？→ 验证分型/笔算法正确
  中枢范围合理？→ 验证笔中枢和演化逻辑正确
```

#### 3.3 制图核心流程

```
analyze() 输出结构数据
  → 格式化为 lightweight-charts 数据格式
  → 构建 HTML 模板（含分型/笔/中枢/买卖点叠加层）
  → 输出独立 HTML 文件或 base64 内嵌
  → 前端 iframe 或新窗口打开
```

#### 3.4 接口设计（新增 API）

```python
GET /api/v3/chanlun/chart?ts_code=301448.SZ&period=long
返回: HTML content-type: text/html
```

或返回 JSON 结构数据供前端自行渲染：

```python
GET /api/v3/chanlun/structures?ts_code=301448.SZ
返回: {
  "fractals": [...],   # 分型列表 {type, idx, price, date}
  "strokes": [...],    # 笔列表 {direction, start, end, price_range}
  "segments": [...],   # 线段列表
  "zhongshu": [...],   # 中枢列表 {low, high, start_date, end_date}
  "buy_sell_points": [...]  # 买卖点
}
```

## 八、全面修改计划

### 8.1 问题全景一览

根据全文分析，当前系统在缠论实现上存在 **5 个层级、10 项具体问题**，按影响程度排序如下：

| 层级 | 问题编号 | 问题描述 | 严重度 | 对应文档章节 |
|:----:|:--------:|----------|:------:|:------------:|
| **0-包含处理** | P0.1 | 递归合并(上限10次)比czsc单次合并更激进，丢失约60根K线特征 | 🟡 中 | §2.6.1 |
| | P0.2 | `merge_depth` 不可配置，硬编码10次 | 🟢 低 | §2.6.1 |
| **1-分形检测** | P1.1 | `threshold_pct=0.5%` 额外过滤弱势分形，czsc无此限制 | 🟢 低 | §2.1, §2.6.1 |
| **2-笔构建** | P2.1 | `min_klines=4`(已改为5) 比czsc `min_bi_len=6` 宽松 | 🟢 低 | §2.1 |
| | P2.2 | K线计数用原始idx差值，非实际K线数(已部分修复) | 🟡 中 | §2.6.4 |
| | P2.3 | 无笔破坏回退机制，czsc有(新K线突破笔端点时撤回) | 🟡 中 | §2.6.3 |
| | P2.4 | 无价格区间包含检查，czsc有(两分型区间完全包含则不成笔) | 🟢 低 | §2.6 |

#### 8.6.3 BiZhongshuFinder 核心算法

```python
def find(self, strokes: List[Stroke]) -> List[Zhongshu]:
    """笔中枢检测：直接在笔序列上检测中枢，不经过线段层"""
    zhongshu_list = []
    if len(strokes) < 3:
        return zhongshu_list
    
    i = 0
    while i <= len(strokes) - 3:
        # Step 1: 寻找3笔重叠区间
        s1, s2, s3 = strokes[i], strokes[i+1], strokes[i+2]
        
        # 计算3笔的价格重叠区间
        overlap_low = max(min(s1.high_price, s1.low_price),
                         min(s2.high_price, s2.low_price),
                         min(s3.high_price, s3.low_price))
        overlap_high = min(max(s1.high_price, s1.low_price),
                          max(s2.high_price, s2.low_price),
                          max(s3.high_price, s3.low_price))
        
        if overlap_low >= overlap_high:
            i += 1
            continue  # 无重叠 → 前进1笔
        
        # Step 2: 中枢起始
        zs = Zhongshu(low=overlap_low, high=overlap_high,
                      start_idx=i, start_price=s1.low_price,
                      ...)
        
        # Step 3: 延伸检查
        j = i + 3
        while j < len(strokes):
            end_p = strokes[j].low_price if strokes[j].direction == 'down' else strokes[j].high_price
            if end_p > zs.high or end_p < zs.low:
                break  # 笔完全离开 → 闭合
            # 笔在中枢内 → 延伸（不扩展边界）
            j += 1
        
        zs.end_idx = j - 1
        zhongshu_list.append(zs)
        i = j  # 从离开笔开始下一轮检测
    
    return zhongshu_list
```

**关键设计决策**：
- 延伸不扩展中枢区间（vs 原 `_evolve_zhongshu` 允许任意部分重叠都算延伸）
- 闭合条件是笔的**端点完全离开**中枢区间（不是部分离开）
- 方向自然交替（笔本身交替），无需人工强制
- **无 cap、无交替跳过**——笔中枢模式的核心优势

#### 8.6.4 验证标准

| 指标 | 当前（线段中枢） | 目标（笔中枢） |
|------|:--------------:|:--------------:|
| 301448.SZ 中枢数 | **1**（33个月） | **≥4**（每个约3-8个月） |
| 结构合理性 | ❌ 全覆盖价格 | ✅ 窄区间，对应真实支撑阻力 |
| 中线级别中枢 | N/A | 笔数≥9且重叠→中级中枢 |
