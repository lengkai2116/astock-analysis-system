## 四、五大具体差距项

### 差距 1：缺自然语言渲染层

**现状**：5 维输出的 `status_text` 由 `evidence` 数组简单拼接（`_build_chanlun_dimension()` 等函数第 61 行）。

**目标**：每个维度的现状应有独立、连贯的中文描述段落，例如：
- 当前：`"股价站上20日均线; 量能温和放大"`
- 期望：`"从量价关系看，股价已站稳20日均线，成交量呈温和放大态势，短期动能偏正面。但上方4150附近存在前期平台压力，需关注能否放量突破。"`

**涉及文件**：
- `backend/app/routes/strategy_analyze.py` — `_build_*_dimension()` 5 个函数
- 或新增独立的 NLG 服务

### 差距 2：LLM Wiki 知识管道未接入 AI 解读

**现状**：
- `WikiConceptMatcher`（`ai_context_builder.py:525`）已实现，可匹配市场状态+现状识别→返回知识库概念
- `explain_signal()`（`deepseek_analysis_service.py:477`）接受可选 `wiki_context` 参数
- 但 `interpret_status()` 的 prompt 中**从未注入 wiki_context**（第 449-456 行）
- `WikiConceptMatcher` 仅被 `/api/v3/ai/arbitrate` 路由调用，该路由是独立的仲裁端点

**目标**：在 `interpret_status()` 调用 DeepSeek 前，先通过 `WikiConceptMatcher` 获取相关 Wiki 知识，注入 prompt。

**涉及文件**：
- `backend/app/services/deepseek_analysis_service.py:interpret_status()` — 第 449 行 prompt 构建处
- `backend/app/services/ai_context_builder.py:WikiConceptMatcher` — 已有，需接入

### 差距 3：interpret_status 未使用 5 维自然语言格式

**现状**：`interpret_status()` 的 prompt 使用 `state_consensus` + `risk_aggregation` + `momentum_consensus` 等统计聚合数据，格式为：
```
状态共识: ACCUMULATING (共识度: 75.0%)
风险等级: MEDIUM
动量共识: BULLISH
各策略状态:
  - 缠论: 2B买点确认
  - 量价: 拉升期
```

**目标**：将 5 维的自然语言描述注入 prompt，替代/补充当前的结构化统计摘要，使 AI 能基于更丰富的上下文做解读。

**涉及文件**：
- `backend/app/services/deepseek_analysis_service.py:interpret_status()` — 第 431-447 行 prompt 构建

### 差距 4：前端未对接后端路由

**现状**：`_ui-prototype/indicator-ide.html` 未调用以下任何端点：
- `POST /api/v3/strategy/analyze`
- `POST /api/v3/strategy/status-aggregate`
- `POST /api/v3/ai/status-interpret`
- `POST /api/v3/ai/arbitrate`
- `POST /api/v3/uidf/consolidate`

当前后端路由已全部就绪但无前端消费，三个环节的串联需要前端或中间层完成。

**涉及文件**：
- `_ui-prototype/indicator-ide.html`
- 或需要新增前端编排层

### 差距 5：signal 与 status_recognition 的主次关系

**现状**：每个策略输出中 `signal`（bullish/bearish/neutral）是主输出字段，`status_recognition`（现状描述）是嵌套子字段。前端 5 维展示格式中 `direction` 仍以买卖方向为核心。

**目标**：按用户构思，`status_recognition` 应作为主输出，`signal` 作为从现状推导出的辅助属性。但当前所有接口设计以 `signal` 为主线，需要逐层调整：策略引擎 → SignalComputationService → 路由组装 → 前端展示。

**涉及文件**：全链路，从各策略引擎到前端展示。

**📌 跟踪状态（2026-07-20更新）**：272/273号方案通过DeepSeek九层描述框架实现了"现状描述优先"的输出格式——DeepSeek输出以走势结构、筹码成本、价格位置等现状描述为主，signal方向作为辅助信息。此方案在输出层面解决了主次关系问题，但策略引擎内部的 `status_recognition` 与 `signal` 字段结构关系保持不变。当前标记为：**输出层已解决，引擎层保持现状**。

### 8.6 实战验证数据（实测 300750.SZ/002594.SZ）

1. **缠论与量价经常冲突**：20260713 实测 300750.SZ
   - 缠论：`state=ACCUMULATING, trend=up/weakening, 中枢=[140, 610]`（看多）
   - 量价：`state=BEARISH, trend=down/strong, SR=[409, 460]`（看空）
   - 两条最有解析力的策略结论相反 → 共识聚合被迫输出 RANGING → AI 解读保守观望

2. **筹码频率静默失败**：多次实测中筹码均输出"无筹码信号"，直接导致 4 条验证链中的 2 条因 `"insufficient data"` 失败

## 十三、各策略输出调整计划（双路径兼顾）

> 本计划基于以下三个输入制定：
> 1. **§八** 策略解析质量标准（基于 LLM Wiki 知识库）
> 2. **§九** 当前 vs 应有等级差距
> 3. **双路径架构审计**（选股系统批量筛选 + 个股策略分析单票深度）

### 13.1 总体原则

| 原则 | 说明 |
|:-----|:------|
| **同计算不同输出** | 底层分析器（ChanlunAnalyzer.analyze / VolumePriceStrategy.analyze 等）的结果在筛选和个股两个路径间缓存复用，避免重复计算 |
| **筛选路径不加重** | 筛选批处理 100+ 股票，新增字段零计算开销（仅从已有分析结果提取） |
| **个股路径扩深度** | 个股分析单股票执行，可利用分析器的完整输出做更丰富的中文描述 |
| **status_recognition 统一** | 5 策略统一使用同一个 7 字段结构，两路径共享数据格式 |
| **内嵌知识库驱动** | 新增字段的内容指导来自 data/knowledge/concepts/（§十一选定） |

### 13.7 双路径计算缓存策略

当前最严重的问题是**缠论和量价在筛选和个股路径间完全重复计算**（两者在单股票上合计 ~400-700ms）。当个股分析完毕后，筛选系统再次跑同一只股票时完全重算。

| 策略 | 当前重复模式 | 缓存策略 | 预期性能提升 |
|:-----|:------------|:---------|:-----------|
| 缠论 | 双路径均调用 `ChanlunAnalyzer.analyze()` | 以 `(ts_code, length)` 为 key 缓存分析结果文件，TTL=1 交易日 | 消除 200-500ms/只 × N 只的重复 |
| 量价 | 双路径均调用 `VolumePriceStrategy.analyze()` | 同上 | 消除 100-200ms/只 × N 只的重复 |
| 筹码 | 分析器不同，不重复 | 无需处理 | — |
| BOCIASI | 筛选不执行，无重复 | 无需处理 | — |
| 因子 | 分析器不同（注册表 vs FactorCalculator），不重复 | 无需处理 | — |

**缓存边界条件**：
- 同一天内有效（交易日切换时失效）
- 仅缓存分析器结果（`ChanlunAnalyzer.analyze()` 的输出），非最终信号（信号依赖 market_context 变化）
- 首次请求个股分析时写入缓存，后续批量筛选时读取

## 十四、自然语言渲染层实现方式调研

> 本节基于对工业界和开源项目中结构数据→自然语言转换模式的调研，不含具体代码实现。

### 14.1 调研结论速览

| 方法 | 代表作/项目 | 中文支持 | 延迟 | 依赖 | 本项目适用性 |
|:-----|:-----------|:--------:|:----:|:----:|:-----------:|
| **f-string 模板** | 天气/比分报告生成器 | ✅ 原生 | 微秒 | 零 | ✅ **核心方案** |
| **规则句子组合器** | 金融终端（Wind/东财/同花顺） | ✅ 原生 | 微秒 | 零 | ✅ **核心方案** |
| **Jinja2 模板引擎** | 本项目 report_generator.py 已有 | ✅ 原生 | 毫秒 | Jinja2 | ✅ 可选（已在用）|
| **语法实现库** (SimpleNLG等) | 英文形态变化/动词变位 | ❌ 不支持中文 | 毫秒 | Java/Python | ❌ **中文不需要** |
| **LLM 提示生成** | 本项目 deepseek_analysis_service.py 已有 | ✅ 提示可控 | 1-5秒 | LLM API | ✅ **润色增强** |
| **混合：规则+LLM** | 本项目 strategy_ai_interpretation_service.py 已有 | ✅ 两者兼顾 | 微秒/秒级 | LLM API 可选 | ✅ **推荐方案** |

### 14.2 关键洞察：中文不需要语法实现库

SimpleNLG（Java, ~600 stars）和其 Python 移植版（pySimpleNLG 26 stars, pynlg 29 stars）是 NLG 领域最知名的开源库。但它们**对中文无价值**——因为中文没有动词变位、名词性别、冠词、单复数变化。中文的 NLG 只需要：
- **条件逻辑**：`if score > threshold: "强势" else: "弱势"`
- **字符串拼接**：`"，".join(parts) + "。"`

这是纯 Python 可以完美处理的事情，不需要引入任何外部框架。

### 14.3 工业界参照：金融终端的做法

调研了同花顺、东方财富、Wind 等中文金融终端，它们的行情摘要生成模式高度一致：

| 模式 | 示例 | 实现方式 |
|:-----|:-----|:---------|
| **信号触发** | "MACD 金叉"、"突破前高"、"量价背离" | 条件判断 + 固定短语 |
| **状态快照** | "上证指数今日收涨 0.5%，成交量较昨日放大 10%" | 模板填充 |
| **阶段判定** | "处于上升趋势中的回调阶段，支撑位 xx，压力位 xx" | 嵌套条件分支 |
| **对比描述** | "近 5 日主力资金净流入 xx 亿，较前 5 日增加/减少 xx" | 计算 + 比较模板 |

**关键发现**：这些系统不依赖外部 NLG 库，全部是内部实现的 条件分支 + 字符串拼接。核心逻辑是一个**多级条件决定树**：先判定大方向（趋势向上/向下/震荡）→ 再判定具体状态（阶段/力度/一致性）→ 选择对应的中文模板填充。

### 14.4 推荐方案：分层渲染架构

基于调研结论，为本项目设计的自然语言渲染层分为两层：

**层 1：规则句子组合器（同步，零依赖，微秒级）**

```
核心类：ChineseNLRenderer

输入：status_recognition 结构化字典（各策略统一7字段）
处理流程：
  1. 按维度拆分（趋势/动量/量价/关键价位/风险）
  2. 每个维度独立走条件判定树 → 生成中文短句
  3. 句子组合器组装维度段落
输出：每个维度一段中文描述（约 30-80 字/段）

判定树示例（趋势维度）:
  判定 direction=dowtren、strength=strong、stage=DOWNTREND_ACTIVE
  → "下降趋势运行中，空头力量占主导地位。"
  → 若 volume.structure=空头排列 → "均线系统呈空头排列，上方压力重重。"

判定树示例（动量维度）:
  判定 momentum.level=bearish、score=0.72
  → "短期动能偏空，暂无见底信号。"
  → 若存在背驰 → "但需关注底背驰信号的出现。"

判定树示例（筹码维度）:
  若 chip_peak 和 ASR 数据可用
  → "筹码峰集中在 xx-xx 区间，ASR 为 xx%，筹码集中度偏xx。"
  → 若主力集中价可用 → "主力成本价约 xx，当前股价偏离 xx%。"
```

**层 2：LLM 润色（异步，可选，可降级）**

```
核心类：LLMPolishService (可复用现有的 interpret_status 逻辑)

输入：层 1 输出的各维度中文描述
处理：将规则生成的文本发送到 LLM，要求"润色为更流畅的中文，保持所有数字和术语不变"
回退：LLM 不可用时直接使用层 1 输出
```

**两层的定位关系**：

```
层1（规则）               层2（LLM润色）              最终输出
┌─────────────────────┐  ┌────────────────────┐  ┌──────────────────┐
│ 下降趋势运行中，      │  │ 当前处于下降趋势    │  │ 当前处于下降趋势   │
│ 空头力量占主导地位。  │ →│ 运行中，空头力量    │→│ 运行中，空头力量   │
│ 成交量持续萎缩，      │  │ 持续主导。成交量    │  │ 持续主导。成交量   │
│ 未见止跌信号。       │  │ 持续萎缩，暂未      │  │ 持续萎缩，暂未     │
│                      │  │ 出现明确的止跌信号。│  │ 出现明确的止跌信号。│
│                      │  │ 关注 xxx 附近支撑。│  │ 关注 xxx 附近支撑。│
└─────────────────────┘  └────────────────────┘  └──────────────────┘
   零依赖，微秒级             可选，慢，有成本         始终可用
   稳定可预测                   自然流畅               质量保底
```

### 14.5 与现有逻辑的关系

| 现有组件 | 与新的 NLG 层的关系 |
|:---------|:-------------------|
| `_build_chanlun_dimension()` 等 5 个函数 | **被替换**：当前这些函数用 `evidence` 数组的 `.join("; ")` 拼接 `status_text`，新的 NLG 层将取代这个简陋做法 |
| `interpret_status()` | **复用**：该函数仍负责将聚合状态发给 DeepSeek 做最终解读。NLG 层的输出作为 prompt 的输入（替代当前的结构化统计摘要）|
| `strategy_ai_interpretation_service.py` | **参照其分层设计**：该服务已有规则+LLM 的双层结构（规则解释 + LLM 增强），新的 NLG 层可以复用相同的设计模式 |
| `report_generator.py` | **参照其 Jinja2 用法**：如需标准化模板（如固定格式的段落框架），Jinja2 已引入 |

### 14.6 代码组织建议

```
        ├── __init__.py               # 导出 ChineseNLRenderer

        ├── trend_renderer.py         # 趋势维度判定树
```

### 14.7 实现要点总结

| 要点 | 说明 |
|:-----|:------|
| **零外部依赖** | 纯 Python 条件分支 + 字符串拼接，不引入新库 |
| **分层设计** | 规则层保底 + LLM 层可选项，不降低现有可靠性 |
| **判定树驱动** | 每个维度一个独立的条件决策树，易于扩展和维护 |
| **可测试性** | 给定相同输入，规则层输出 100% 确定（单元测试容易）|
| **中文术语集中管理** | 所有金融术语/描述模板集中在 `templates.py` 中，非分散在各维度渲染器里 |
| **增量构建** | 可以先实现缠论+量价两个主力的渲染器，其他逐步补充 |

```
  慢线: 横盘 (RANGING) - 跨市场情绪中性

【验证链状态】                              ← 当前完全缺失
  筹码×成交量:  未通过 — 数据不足（筹码信号缺失）
  缠论×因子:    未通过 — 数据不足（因子信号缺失）
  情绪×筹码:    未通过 — 数据不足（筹码信号缺失）
  技术基本面:   未通过 — 缠论(↑) vs 量价(↓) 方向冲突

【策略间关系】                               ← 当前完全缺失
  缠论(watch) ↔ 量价(BEARISH) = 冲突
  缠论(watch) ↔ BOCIASI(WATCH) = 冲突
  量价(BEARISH) ↔ BOCIASI(WATCH) = 冲突

【知识库参考】                               ← 当前完全缺失
  - 三类买卖点.md：当前无接近的买卖点，处于中枢震荡
  - 量价分析价格形态.md：无明确形态匹配

【风险提示】
  筹码数据不足，无法判断主力资金动向
  因子数据不足，无法获取多因子综合评分
```

### A.3 差距明细

| 数据类别 | 当前 prompt 是否包含 | 来源字段 | 缺失影响 |
|:---------|:-------------------:|:---------|:---------|
| 每个策略的完整 status_recognition | ❌ 只取了 state 一个字段 | `aggregated_status.dimensions` | AI 不知道趋势方向/力度/成交量/关键价位 |
| 验证链详情（通过/失败/冲突描述） | ❌ 未使用 | `aggregated_status.verification_chains` | AI 不知道哪些维度冲突、哪些数据缺失 |
| 策略间方向关系（谁和谁冲突） | ❌ 未使用 | E13 的 `dimension_relations` | AI 不知道策略间一致还是分歧 |
| 内嵌知识库概念 | ❌ 未接入 | `KnowledgeReader.match()`（规划中） | AI 解读缺乏专业知识支撑 |
| 筹码峰/主力集中价等深度数据 | ❌ 未使用 | `status_recognition` 扩展字段 | AI 不知道主力资金动向 |

### A.4 修正后的 prompt 构建流程

```
interpret_status() 被调用
    │
    ├── ① 获取 aggregated_status（已有，不变）
    │
    ├── ② 通过 NLG 层生成五维中文描述
    │     └─ 调用 ChineseNLRenderer.render(five_dimensions)
    │        → 输出每个维度的中文段落（趋势/动量/量价/关键价位/风险）
    │
    ├── ③ 提取验证链冲突信息
    │     └─ 从 aggregated_status.verification_chains 中提取
    │        → 各链通过/失败状态 + 冲突具体描述 + chain_passed_ratio
    │
    ├── ④ 查询内嵌知识库
    │     └─ 调用 KnowledgeReader.match(keywords_from_status)
    │        → 返回 1-3 个匹配概念的中文内容
    │
    └── ⑤ 合并以上全部 → 发送 DeepSeek
          prompt = f'''
          股票: {name}({code})
          最新价: {close}

          【五维现状详述】
          {nlg_descriptions}

          【验证链状态】
          {verification_chain_text}

          【知识库参考】
          {knowledge_context}

          请基于以上完整信息，输出 JSON 格式操作建议...
          '''
```
