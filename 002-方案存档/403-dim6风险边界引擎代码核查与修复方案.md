## 二、BUG清单

### BUG-01（HIGH）：缺少 `import itertools` — CSCVValidator 运行时 NameError

**位置**：行1407（`CSCVValidator.compute_pbo` 内部）

**现象**：调用 `compute_pbo()` 或 `evaluate()` 时抛出 `NameError: name 'itertools' is not defined`

**根因**：文件顶部导入区（行15-23）未包含 `import itertools`，但行1407调用了 `itertools.combinations(split_indices, train_size)`

**影响**：CSCVValidator 整个类不可用，`compute_cscv_pbo()` 模块级函数同样不可用

**修复方案**：在行19后添加 `import itertools`

**工时**：0.1天

---

### BUG-02（HIGH）：缺少 `Callable` 导入 — 类型注解不完整

**位置**：行1450、1461、1572、1588

**现象**：`CSCVValidator.evaluate()` 和模块级 `compute_cscv_pbo()` 的类型注解使用 `Callable[[np.ndarray, Any], float]`，但导入行（行21）为：
```python
, Dict, List, Tuple, Any
```
缺少 `Callable`。由于 `from __future__ import annotations`（行15）的存在，模块加载不会报错，但 `get_type_hints()` 或 IDE 类型检查会失败。

**影响**：类型检查工具报错；若未来移除 `__future__` 注解则立即崩溃

**修复方案**：在行21的导入中添加 `Callable`

**工时**：0.1天

---

### BUG-03（MEDIUM）：EventMonitor 多处数据源访问路径不一致

**位置**：行588-592（`_detect_fraud_sign`）、行945（`_detect_holder_concentration`）、行980（`_detect_margin_risk`）

**现象**：EventMonitor 内部混用两种数据访问路径：

| 函数 | 访问方式 | 示例 |
|------|---------|------|
| `_detect_earnings_surprise` | `self._get_cache()` | 行449 |
| `_detect_fraud_sign` | `self._get_dm().get_cached_xxx()` + `dm.cache.get_cached_cashflow()` | 行588-592 |
| `_detect_delist_risk` | `self._get_dm()` | 行717 |
| `_detect_holder_concentration` | `self._get_cache()` | 行945 |
| `_detect_margin_risk` | `self._get_cache()` | 行980 |
| `_detect_concept_heat` | `self._get_cache()` | 行1077 |

`_get_cache()` 返回 `self._get_dm().cache`（ECM），`_get_dm()` 返回 DataManager。两种路径功能等价但风格不统一。特别是 `_detect_fraud_sign` 内部（行588-592）甚至混用了两种路径：

```python
dm = self._get_dm()
df_fi = dm.get_cached_fina_indicator(ts_code)     # dm 方法
df_cf = dm.cache.get_cached_cashflow(ts_code)      # dm.cache 方法 ← 不一致
```

**影响**：路径不一致增加维护风险；如果 DataManager 统一了缓存访问接口，部分调用会遗漏

**修复方案**：统一为 `self._get_dm()` 一种路径（`_get_cache()` 是其快捷方式，但混用增加认知成本）

**工时**：0.2天

### BUG-04（MEDIUM）：`_assess_risk_level` 的 `risk_sources` 列表是死代码

**位置**：行230-267

**现象**：

```python
risk_sources = []                    # 行230：初始化
risk_sources.append({'name': '缠论风险', 'level': ...})  # 行240
risk_sources.append({'name': '波动率风险', 'level': ...}) # 行245
risk_sources.append({'name': '财务风险', 'level': ...})   # 行250
risk_sources.append({'name': '事件风险', 'level': ...})   # 行255
risk_sources.append({'name': '主力风险', 'level': ...})   # 行260
# ... 后续换手率风险源未 append 到 risk_sources ...
# return 时完全未使用 risk_sources
return {'level': level, 'light': light, 'detail': f'{high_count}个高风险源' if high_count else '无高风险源'}
```

`risk_sources` 列表在函数内构建但**从未被读取或返回**。构建了5个风险源记录，但 return 的 dict 中没有 `risk_sources` 字段，`detail` 也仅使用 `high_count` 数值。

**影响**：
- 5次 `append` 调用完全浪费CPU（每只股票每次调用都执行）
- 换手率风险源（行262-267）未 append 到此列表只是表象，深层问题是该列表本身就是死代码
- 函数无法追溯"哪些风险源触发了高风险"，detail 仅显示计数

**修复方案**：

方案A（推荐）—— 将 `risk_sources` 纳入返回值，供下游追溯：
```python
return {'level': level, 'light': light, 'detail': ..., 'risk_sources': risk_sources}
```
同时补全换手率风险源的 append。Dim6RiskEngine.evaluate() 消费返回值时可读取 `risk_sources`。

方案B —— 如果确实不需要追溯，直接删除 `risk_sources` 相关的5行 append 和初始化，减少无用计算。

**工时**：0.2天（方案A）/ 0.1天（方案B）

### BUG-05（LOW）：涨停阈值硬编码9.5%，不适用所有板块

**位置**：行894、899、915、928

**现象**：`_detect_limit_move` 硬编码 `pct_chg >= 9.5` 作为涨停判定，不适用科创板/创业板（20%）、ST（5%）、北交所（30%）。

**影响**：科创板/创业板的涨停不会被识别为涨停事件；ST股的5%涨停被遗漏；炸板判定同理

**修复方案**：方案A（推荐）—— 根据股票代码前缀判断板块，动态设定阈值：
```python
# 科创板 688xxx / 创业板 300xxx → 20%
# ST 股票名称含ST → 5%
# 北交所 8xxxxx → 30%
# 主板 → 10%
```
方案B（延后）—— 标记为已知限制，后续统一处理

**工时**：0.5天（方案A）/ 0.1天（方案B）

## 三、代码质量问题（6项）

### Q-01（MEDIUM）：`except Exception: pass` 静默吞错

**位置**：行217-218、436-437、1145-1146

三处 `except Exception: pass` 完全吞掉异常。特别是行217的 `_calc_volatility`，如果 `df['close']` 列缺失或类型异常，静默返回默认值（level='medium', atr=0, percentile=0.5），下游无法区分"正常中波动"和"计算失败"。

**建议**：至少添加 `logger.debug` 记录异常。

**工时**：0.1天

### Q-02（MEDIUM）：`_detect_regulatory` 与 `_detect_st_warning` 逻辑高度重复

**位置**：行683-710 vs 行751-779

两个函数都检查股票名称中的 `*ST`/`ST`/`退` 标记，逻辑几乎相同：

| 标记 | `_detect_regulatory` (C1) | `_detect_st_warning` (C3) |
|------|--------------------------|--------------------------|
| `*ST` | direction=-2, confidence=0.9 | direction=-2, confidence=1.0 |
| `退` | direction=-2, confidence=0.9 | direction=-2, confidence=0.95 |
| `ST` | direction=-1, confidence=0.7 | direction=-1, confidence=0.8 |

区别仅在 confidence 数值。

**建议**：提取共享方法 `_check_st_marker(name) -> (direction, confidence, label)`，两个检测函数复用。

**工时**：0.2天

其他所有 logger 调用都使用 `%s` 格式化。f-string 会无论如何都执行字符串插值。

### Q-06（LOW）：`_list_risk_factors` 与 `_assess_risk_level` 覆盖范围不对齐

**位置**：行282-343 vs 行228-279

`_list_risk_factors` 额外包含3个 `_assess_risk_level` 未覆盖的风险源：
- **估值过高**（行325-327）：`valuation_level` in `('high', 'extreme_high')`
- **获利盘过高**（行329-334）：`profit_ratio >= 0.8`
- **L0软风险 low_liquidity**（行336-338）

这3项不参与 `high_count` 计算，不影响风险等级判定，但会展示在 risk_factors 列表中，可能造成"列了风险因素但等级没升"的困惑。

**建议**：要么将这3项也纳入 `_assess_risk_level` 的 high_count 计算，要么在 `_list_risk_factors` 中标注为"参考因素"与"等级因素"区分。

**工时**：0.2天
