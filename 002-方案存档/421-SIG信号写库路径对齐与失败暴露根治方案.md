# 421 — SIG信号写库路径对齐与失败暴露根治方案

> **背景**：2026-09-09 会话观察 20260908 管道重跑时，连续两次出现
> `批量写 strategy_signal_detail 失败: database is locked`（08:05:35 / 08:19:48），
> SIG 步骤仍标记 done（5555/5555），但信号未写入目标库——数据缺失对外不可见。
> 经对照既有方案（356/357/375/377/392/398）核查，确认根因是**写库路径未对齐
> 357 号分库标准** + **失败静默吞错**。本方案制定修订实施计划，**不修改代码**。

---

## 一、根因分析（对照既有方案标准）

### 1.1 方案确立的写库标准

| 方案 | 标准内容 | 状态 |
|------|---------|------|
| **356 号 §3.1** | 分库定稿：strategy_signal_detail（成品）归 **snapshot_cache.db** | 方案 ✅ |
| **357 号**（355 号 239 行注记，2026-08-19） | strategy_signal_detail 从 compute_cache.db 迁入 **snapshot_cache.db**；snapshot 分库 busy_timeout 需 **10s → 30s** | 决策 ✅ |
| **377 号 §1.2** | SIG 输出表 = snapshot_cache.db 的 strategy_signal_detail | 核查 ✅ |
| **375 号 §4.2/§7.1**（2026-08-28 实施） | 读方（OUT/JUD）走 `sharding_manager.get_connection()` 读**分库**；记录"strategy_signal_detail 跨库存储" | 部分 ✅ |
| **398 号 §1.2/§3.2** | 明确缺陷：`_batch_write_signal_detail` 直连 `_ecm.db_path`（主库）**路由不一致**；应改 `WriteGateway.write_batch`；写入后校验 + 失败补算调度 | ⏳ 待实施 |

### 1.2 实际代码偏差（根因链 3 层）

```
┌─ 偏差1：写库目标库 ≠ 357号标准 ─────────────────────────────┐
│  _batch_write_signal_detail (data_daemon.py:5021)            │
│    → _sqlite3.connect(_ecm.db_path)   # _ecm.db_path = 主库   │
│                                            stock_cache.db     │
│  而 sharding_manager 路由已指向 snapshot_cache.db（分库）      │
│  → SIG 信号写入主库残留副本，分库权威副本不被更新              │
└──────────────────────────────────────────────────────────────┘
                            │ 主库与采集线程/主循环写者争写锁
                            ▼
┌─ 偏差2：busy_timeout 10s < 355号注记的 30s ────────────────┐
│  主库写入与 minute_kline_cache 等采集写并发 → database       │
│  is locked（08:05:35 与索引撞锁叠加；08:19:48 无 DDL 复现）   │
└──────────────────────────────────────────────────────────────┘
                            ▼
┌─ 偏差3：失败静默吞错（398号已列缺陷）─────────────────────┐
│  写失败仅 logger.warning → 不抛出 → SIG 仍标 done           │
│  run_integrity_check 无 strategy_signal_detail 补写         │
│  （注释声称"完整性检查兜底"不存在）→ 数据缺失不可见          │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 关键事实核验（2026-09-09 会话实测）

| 库 | strategy_signal_detail | 08-26 数据 | 结论 |
|----|----------------------|-----------|------|
| **snapshot_cache.db（标准分库）** | 33,440 行 | 5,578 行（08-27 写入） | ✅ 权威副本，数据完整 |
| **stock_cache.db（主库残留）** | 33,448 行 | 5,586 行（09-04 写入） | ⚠️ 残留副本，写路径错误目标 |

- 历史写失败：09-07 1 次、09-08 2 次（本会话两次 SIG 重跑均失败），均静默
- 读方（JUD `_load_signals` → `dm.cache.get_latest_signal_detail` → `read_conn`）仍读**主库**
  → 读写目标不一致：读主库残留、标准读法（sharding）读分库

## 二、修订目标

1. **写库路径对齐 357/377 号标准**：SIG 信号写入 snapshot_cache.db（分库）
2. **失败可见 + 自动恢复**：写失败抛出异常 → SIG 标 failed → 管道自动重试（≤3 次）
3. **消除双写不一致**：清理主库残留副本，统一读写目标库
4. **busy_timeout 对齐**：snapshot 分库 10s → 30s（355 号注记要求）

---

## 三、修订实施计划（4 个修复项）

### R1：`_batch_write_signal_detail` 改走 sharding_manager 路由（P0，核心）

**文件**：`backend/data_daemon.py`（函数 `_batch_write_signal_detail`，约 5005 行）

**改动**：
1. 获取分库连接：`sharding_manager.execute_batch_insert('strategy_signal_detail', sql, rows)`
   ——已核实 sharding_manager.py 提供 `execute_batch_insert`(L168)/`execute_insert`(L152)/
   `get_connection`(L104)/`table_exists`(L195)，带分库级 `_write_locks` 串行化
   （R1 可直接复用，无需新增 API）
2. 保留独立短连接 + `INSERT OR REPLACE` + 单 commit 模式（392 号 §2.3 不变）
3. 幂等：写前 `CREATE TABLE IF NOT EXISTS` 检查分库表存在（若分库表缺失则告警+回退主库？——
   实施时决策：**不回退**，直接 failed 由管道重试，避免再次双写）

**验收**：写入后 snapshot_cache.db 08-26 出现新 cached_at；主库不再新增行。

### R2：snapshot 分库 busy_timeout 10s → 30s（P0，355号注记）

**文件**：`backend/app/data/enhanced_cache_manager.py`（分库连接配置区）
        及 sharding_manager 中 snapshot_cache.db 连接参数（若独立建连）

**改动**：snapshot_cache.db 连接的 `PRAGMA busy_timeout` 从 10000 → 30000，
对齐 market_cache.db 的 30s（356 号 §3.2.2 配置）。

**验收**：`PRAGMA busy_timeout` 查询返回 30000。

### R3：写失败暴露——SIG 标 failed 自动重试（P0）

**文件**：`backend/data_daemon.py`

**改动**：
1. `_batch_write_signal_detail` 失败时**抛出异常**（移除内部静默 `except` 降级），
   或返回 bool 由调用方 `_precompute_strategy_signals` 判断并 raise
2. `_precompute_strategy_signals` 异常上抛 → `_run_pipeline_step` 捕获 →
   `mark_step_failed`（既有机制）→ `_drive_pipeline` 对 failed SIG 自动重试（≤3 次，既有）
3. 保留 `_write_factor_signals` 回退仅在 SIG 全量计算失败时（392 号 §2.4），
   与写失败区分：计算失败→回退因子；写失败→重试 SIG

**验收**：人为制造锁冲突（或观察真实竞争）→ SIG 显示 failed → 下一 tick 自动重跑 → done。

### R4：主库残留副本清理 + 读写目标统一（P1）

**文件**：`backend/scripts/`（新迁移脚本）或复用既有迁移模式

**改动**：
1. 新迁移脚本：校验分库数据完整（08-26 ≥ 分库 5,578 行基准）→ 删除主库
   strategy_signal_detail 残留副本（或保留为空表占位——决策：删除数据保留表结构，
   防止读路径 `read_conn` 意外命中旧数据；若 R1 落地后读方已切分库则直接 DROP）
2. 读路径统一：`get_latest_signal_detail`（enhanced_cache_manager.py:2402）与
   `has_signal_detail` 改走 sharding_manager 读分库（375 号 T1 同模式），
   JUD/OUT 消费链全部指向分库
   ——已核实：`EnhancedCacheManager.read_conn` 与主 `conn` 同指 `self.db_path`
   （= stock_cache.db 主库，L99-129），故 `get_latest_signal_detail` 现读主库残留；
   JUD `_load_signals`（status_engine.py:150）经 `dm.cache.get_latest_signal_detail`
   同读主库——**读方迁移（R4a）与 R1 写方迁移必须同批实施**，否则写分库后消费链读不到
3. 幂等可回滚：迁移前备份主库表（`CREATE TABLE ... AS SELECT` 到备份表或文件）

**验收**：全链路（SIG 写 → JUD 读 → OUT 透传）均命中 snapshot_cache.db；
主库无 strategy_signal_detail 数据；前端/API 数据日期正常。

## 四、实施顺序与依赖

```
Phase 1（P0，核心根治）：R1 + R2 + R3
  ├─ R1 写库路由 → snapshot_cache.db
  ├─ R2 busy_timeout 30s
  └─ R3 失败暴露 → SIG failed 自动重试
  └→ 重启 daemon → 观察 SIG 重跑：写失败将自动重试直至成功
      ↓（验证 1：snapshot_cache.db 08-26 cached_at 更新为当日）

Phase 2（P1，收敛清理）：R4
  ├─ 读路径 get_latest_signal_detail 切分库
  └─ 主库残留清理 + 备份
  └→ 全链路验证（验证 2）
```

**依赖关系**：R4 必须在 R1 成功、写路径稳定后执行（先迁移读方再清主库，
避免清理期间读空）。R2 独立可先行。

## 七、风险与注意

1. **写分库后读方未切换**（若只做 R1 不做 R4 读方）：JUD `_load_signals` 仍读主库
   → 信号"看似写入分库但消费链读不到"——**R1 与 R4 读方迁移必须同批实施**
   （R4 拆为 R4a 读方切分库 + R4b 主库清理，R4a 与 R1 同批）
2. **分库表可能已有权威数据**（33,440 行）：R1 后 INSERT OR REPLACE 覆盖当日，
   不破坏历史；禁止 DELETE 全表
3. **daemon 重启窗口**：实施需重启 daemon 加载新代码；重启前先确认管道
   不在 SIG/JUD 关键写窗口（或接受一次 failed 自动重试）
4. **本方案不动 398 号 WriteGateway 大改造**：WriteGateway 是后续中心化方向，
   本方案仅做最小对齐（写库路由 + busy_timeout + 失败暴露），避免大改动风险
