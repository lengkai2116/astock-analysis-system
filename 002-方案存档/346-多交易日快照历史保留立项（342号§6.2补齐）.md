# 346 — 多交易日快照历史保留立项

## 一、背景与必要性

342 号 §6.2（核查发现的基础设施缺口）：opportunity_tags_cache 仅最新快照、status_snapshot 单日快照——**无法跨日核查**，导致：

- **G3.3 共识-市场相关性**（345 号）：consensus_rate 仅 08-14 单日快照，无法做 17 交易日时间序列验证（部分完成，靠 strategy_signals 信号方向代理）
- **G3.1 高共识样本不足**（345 号）：0.67 vs 0.6 门槛区分仅 16/15 条，需多交易日累积（signal_records 回算激活 T20 已部分缓解，但快照横截面仍单日）
- **L1.5 标签时间序列**（342 §3.2）：opportunity_tags_cache 无 trade_date 列，跨日标签核查不可行
- **daily_change_summary**（299 号自选监控 Part B 依赖）：需日度变化比较

## 二、现状机制（实证）

| 表 | 结构 | 写入机制 | 历史 |
|---|---|---|---|
| status_snapshot | 含 `snapshot_date` 列 | **原子表替换**（data_daemon.py:3063-3120：建 `_new` 表 → 填 → DROP 旧 → RENAME） | **仅当天**（08-16: 5571 行） |
| treemap_snapshot | 含 `snapshot_date` 列 | 同上（S1 同管道） | 仅当天 |
| opportunity_tags_cache | **无 trade_date 列**（仅 updated_at=写入时间） | P4 全量覆盖写（456771 行） | 仅最新 |

**根因**：快照表设计为"现状成品"（337 号 §3/§4），原子表替换保证读写一致性但**丢弃历史**。

## 三、改造方案

### 3.1 目标

- 保留每日全市场快照（status_snapshot + treemap_snapshot + opportunity_tags_cache 标签集），支撑跨日核查
- 遵循 292 四层红线：写入在采集层（data_daemon），读取经 DataManager 网关（调用层只读）
- 最小侵入：不改现有表结构/消费端，新增历史归档机制

### 3.2 方案 A（推荐）：独立历史表 + 原子归档

**新增表**（stock_cache.db，ECM 管理）：

```sql
CREATE TABLE IF NOT EXISTS status_snapshot_history (
    ts_code TEXT, snapshot_date TEXT, trade_date TEXT,
    dim_states TEXT, status_bar TEXT, opportunity_state TEXT,
    state_evidence TEXT, conflict_evidence TEXT, consensus_rate REAL,
    direction TEXT, l0 TEXT, lifecycle TEXT, advice_params TEXT,
    PRIMARY KEY (ts_code, snapshot_date)
);
```

**归档时机**：`_build_status_snapshot`（data_daemon.py:3063）**替换前**，将当前 `status_snapshot` 表数据 `INSERT OR REPLACE INTO status_snapshot_history`（当日快照追加历史）。treemap_snapshot 同理。

**写入链**（采集层）：P4/S1 日终 → `_build_status_snapshot` → 原子归档历史 → 原子替换现状。
**读取链**（调用层）：DataManager 新增 `get_snapshot_history(ts_code, start_date, end_date)`（只读查询），禁止 routes/services 直查。

**存储代价**：5571 行/日 × ~200B ≈ 1.1MB/日，年 ~270MB（SQLite 可承受，16.2GB 库）。

### 3.3 方案 B：现状表按 snapshot_date 分区保留（不推荐）

去掉原子替换，改为按 snapshot_date 分区 INSERT——**改动大**（表主键/消费端/treemap 联动），且现有"现状成品"读取假设（`SELECT * WHERE ts_code=? LIMIT 1` 取最新）需改为按日期排序。放弃。

### 3.4 opportunity_tags_cache 历史（可选，二期）

新增 `tag_history` 表（ts_code, trade_date, tag_name, tag_value, confidence, evidence, source），P4 写标签时同步归档——**影响 P4 全量写路径，改动面大**，列为二期（L1.5 时间序列核查依赖，可先满足 G3.3 用快照历史）。

## 四、292 红线合规性

- ✅ 写入仅 data_daemon（采集层）——归档在 `_build_status_snapshot` 内（daemon 管道环节）
- ✅ 读取经 DataManager 网关（调用层只读，禁止直查）
- ✅ 无数据源直调、无 use_cache=False、无 sync_* 绕过
- ✅ 表结构由 ECM 管理（enhanced_cache_manager 或 daemon 建表，统一 WAL）

## 五、实施清单（获批后执行）

1. data_daemon.py `_build_status_snapshot`：替换前归档（方案 A：`INSERT INTO status_snapshot_history SELECT ... FROM status_snapshot`）+ 建表确保
2. treemap_snapshot 归档（`_build_treemap_snapshot` 同步）
3. DataManager 新增 `get_snapshot_history()` 只读方法（数据/__init__.py）
4. 验证：连续 2 次重算后 history 表含 2 个日期；G3.3 用历史快照重跑共识-市场相关性
5. 前端/消费端无改动（读现状表语义不变）

## 六、验收标准

- `status_snapshot_history` 每日归档成功（连续多日 ≥5571 行/日）
- DataManager `get_snapshot_history` 只读可用（routes 不直查）
- G3.3 共识-市场相关性可用多日快照验证（替代单日 + strategy_signals 代理）
- 现有快照读链路无回归（现状表语义不变）

## 七、影响与风险

- **存储**：+1.1MB/日（可控）
- **写时延**：归档 INSERT 5571 行 ≈ 秒级（S1 重建 47s 内）
- **风险**：历史表膨胀（可设保留期，如 180 日滚动清理，默认不清理按需评估）
- **不阻塞**：现状表读取（消费端）不受影响
