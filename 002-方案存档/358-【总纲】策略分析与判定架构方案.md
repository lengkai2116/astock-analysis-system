# 358 — 策略分析与判定架构方案

> 本方案为系统"策略分析"和"判定及操作建议"环节的唯一总纲，整合现状梳理、七维框架分析、架构优化设计。
> 上一次修订：2026-08-20 v3.0（整合七维现状描述框架+LLM Wiki知识库研究）

---

## 一、设计原则

### 1.1 核心理念：描述"现在是什么"，而非"接下来会怎样"

量化系统对出现右侧交易信号的股票，输出重点应放在**"状态刻画"**：信号已经确认，系统的工作是把这个确认后的状态**完整、直观、可核查**地描述出来。

- **只描述不预测**：不出现"目标价""明天涨跌"，只出现"距支撑位X%""突破后第N天"
- **几何化指标优先**：优先输出距离/百分比/天数/比值类指标
- **风险前置**：风险边界维度固定排在倒数第二、综合状态条之前
- **红绿灯化**：每个维度用 ✅/⚠️/🚫 三色标注
- **大白话层**：量化栏＋白话栏双栏输出

### 1.1A 双轨输出原则：结论性判定 + 现状描述性输出（2026-08-21 确立）

> **核心原则**：系统每个维度的分析必须同时输出两项内容——一项用于系统内仲裁和判定，一项用于向用户描述股票现状。两者不可互相替代。

**为什么需要双轨**：

系统分析过程天然包含两类信息：
1. **判定性结论**（系统用）：红绿灯、机会定义、操作建议等——用于仲裁、排序、筛选
2. **现状描述性内容**（用户用）：分析/判定的**条件、过程、规则、逻辑**——让用户知道"系统看到了什么才得出这个结论"

当前系统的问题：**只输出结论，丢掉了条件**。例如：
- 结论："主力在建仓" → 用户只看到一个标签，不知道依据是什么
- 现状："处于建仓阶段（低位涨停+非巨量+大单持续净流入3日+ASR=75）" → 用户清楚知道此刻的具体状态

**条件本身即现状**：判定所依据的条件（如"低位涨停+非巨量+资金净流入"）不是"中间过程"，而是股票此刻**客观存在的事实状态**。用户做决策需要的恰恰是这些事实，而非一个被归纳后的标签。

**双轨输出的结构**：

```
【维度名称】
  ┌─ 现状描述轨（面向用户）
  │   条件1 + 条件2 + 条件3 + ... → 具体事实描述
  │   量化值（距离/百分比/天数/比值）
  │   白话说明
  │
  └─ 结论判定轨（面向系统）
      红绿灯（✅/⚠️/🚫）
      状态标签（流入/中性/流出 等）
      方向值（+1/0/-1）
```

**示例——第四维资金与筹码状态**：

```
【资金与筹码状态】
  ┌─ 现状描述：
  ✅ 大单5日净流入1.2亿（连续3日净流入），超大单占比35%
  ✅ 股东户数较上季度减少4.2%（筹码在集中）
  ⚠️ 龙虎榜近30日上榜2次：机构专用席位买入8000万（真机构），游资席位卖出3000万
  ⚠️ 融资余额近5日增加8%（散户杠杆资金在增加）
  大白话：大资金在慢慢买入，筹码在集中，但散户也在加杠杆追高，需要观察主力能否持续
  │
  └─ 结论判定：
  主力阶段：建仓期（building）
  资金方向：流入（green）
  强度：0.72（强）
```

**实施要求**：358号方案涉及的所有7个维度，每个维度都必须审视其分析/判定的条件及过程规则，同步输出：
- **结论性内容**：用于系统内仲裁（红绿灯、机会定义、操作建议）
- **现状描述性内容**：用于股票现状描述（条件、事实、量化指标、白话说明）

这确保用户既能快速看到系统判定（红绿灯），也能深入了解判定依据（具体条件），从而做出更明智的决策。

### 1.2 输出范式：七维现状描述

基于[[七维现状描述模板]]，右侧信号股的现状描述聚焦"围绕信号做深度刻画"：

| # | 维度 | 核心回答 | 作用 |
|---|------|---------|------|
| 1 | **信号确认状态** | 信号是什么、何时出现、是否已验证 | 判断介入时机的贵贱 |
| 2 | **结构位置状态** | 价格站在哪 | 判断当前空间位置 |
| 3 | **量价健康度** | 涨得结不结实 | 判断趋势健康程度 |
| 4 | **资金与筹码状态** | 谁在买 | 判断主力意图 |
| 5 | **情绪环境状态** | 现在是不是好时候 | 判断市场氛围 |
| 6 | **风险边界状态** | 错了在哪认错 | 判断安全边界 |
| 7 | **状态总结** | 综合状态条 | 一眼掌握全貌 |

## 二、现状问题诊断

### 2.1 输出质量评估

| 问题 | 现状 | 影响 |
|------|------|------|
| **信号粒度过粗** | 6引擎均输出BUY/SELL/NEUTRAL三态 | 丢失强弱信息 |
| **判定逻辑机械** | P0-P7固定优先级链+简单+1/-1投票 | 不适应市场状态切换 |
| **维度间独立性假设** | 假设12维度相互独立 | 量价和筹码高度相关，共识率虚高 |
| **缺少市场状态感知** | 仲裁规则不区分市场regime | 同一规则效果差异大 |
| **操作建议机械** | 固定规则链 | 无法根据强度灵活调整 |

### 2.2 七维框架覆盖度评估

| 七维维度 | 系统现有引擎 | 覆盖度 | 缺口 |
|---------|------------|:------:|------|
| 信号确认状态 | signal_registry（5类信号） | ✅ 80% | 缺少信号验证状态跟踪 |
| 结构位置状态 | 缠论引擎 | ✅ 85% | 缺少几何化距离计算 |
| 量价健康度 | 量价引擎 | ✅ 90% | 缺少50形态量化评分 |
| 资金与筹码状态 | 筹码引擎 | ✅ 85% | 缺少融资余额变化 |
| 情绪环境状态 | BOCIASI引擎 | ⚠️ 60% | 缺少板块热度+龙头状态 |
| 风险边界状态 | StatusEngine L0 | ⚠️ 55% | 缺少盈亏比核算+PIERS排雷 |
| 状态总结 | dim_states红绿灯 | ✅ 80% | 缺少综合状态条派生 |

**总体覆盖度：77%**，风险边界和情绪环境是最大缺口。

## 三、策略引擎重新定位

### 3.1 从"投票者"到"专业分析师"

```
旧：缠论=看多/看空 → 量价=看多/看空 → 筹码=看多/看空 → 融合→方向
新：缠论=结构位置 → 量价=供需健康 → 筹码=资金博弈 → 因子=量化支撑 → 情绪=环境温度 → 综合=全貌
```

每个引擎不再是"投票者"，而是"专业分析师"，各自负责一个维度的深度刻画。

### 3.2 6引擎定位与七维映射

| 引擎 | 新定位 | 核心问题 | 服务维度 | 输出形式 |
|------|--------|---------|---------|---------|
| **缠论** | 价格结构分析师 | "价格站在哪，结构是什么" | 结构位置 | 结构强度(0-1) + 中枢位置 + 关键价位 |
| **量价** | 供需动力分析师 | "涨得结不结实" | 量价健康 | 健康度(0-100) + 形态评分 + 背离 |
| **筹码** | 资金博弈分析师 | "谁在买，筹码如何" | 资金筹码 | 主力行为 + 成本分布 + 资金强度(0-1) |
| **因子** | 量化分析师 | "量化指标是否支持" | 辅助验证 | 因子得分(-1~1) + 各因子贡献度 |
| **BOCIASI** | 情绪分析师 | "现在是不是好时候" | 情绪环境 | 情绪周期 + 温度(0-100) + 板块热度 |
| **复合引擎** | 综合判断器 | "全貌如何" | 状态总结 | 加权融合 + 置信度 |

## 四、从12维判定到7维体检的映射

### 4.1 现有12维 → 新7维的对应关系

| 旧12维（StatusEngine） | **新七维（现状描述）** | 变化说明 |
|----------------------|---------------------|---------|
| DIM-1 结构维 | **结构位置状态** | 保留，增加几何化距离 |
| DIM-2 量价维 | **量价健康度** | 保留，增加形态评分 |
| DIM-3 筹码资金维 | **资金与筹码状态** | 保留，增加融资变化 |
| DIM-4 情绪维 | **情绪环境状态** | 保留，增加板块热度 |
| DIM-5 因子维 | 并入**状态总结** | 因子作为辅助验证，不独立成维度 |
| DIM-6 估值维 | 并入**风险边界** | 估值风险是风险的一部分 |
| DIM-7 财务维 | 并入**风险边界** | PIERS排雷的一部分 |
| DIM-8 事件维 | 并入**情绪环境** | 事件影响市场情绪 |
| DIM-9 时间维 | 并入**信号确认** | 信号生命周期=时间维度 |
| DIM-10 风险维 | **风险边界状态** | 保留并增强 |
| DIM-11 位置维 | 并入**结构位置** | 价格位置=结构位置 |
| DIM-12 信号确认 | **信号确认状态** | 保留，增加验证状态 |

### 4.2 用户强调的"比较和核算为基础"

> "不同维度输出的数据应该代表了不同的强弱度，简单的都+1或者-1，始终认为是不精准的"

**解决方案**：每个维度输出连续强度值（而非离散分类），通过以下方式实现"比较和核算"：

| 机制 | 说明 | 替代的旧逻辑 |
|------|------|-------------|
| **连续强度值** | 每个维度输出0-1或-1~+1的连续值 | 替代+1/0/-1三态 |
| **置信度加权** | 强度×置信度=有效强度 | 替代等权投票 |
| **动态权重** | 根据市场regime调整维度权重 | 替代固定权重 |
| **相关性去重** | 高相关维度降低总权重 | 替代独立性假设 |
| **阈值随regime调整** | 不同市场状态的进入/退出阈值不同 | 替代固定P0-P7阈值 |

### 4.3 信号生命周期阶段划分

基于[[信号生命周期]]框架：

| 阶段 | 含义 | 几何化指标 | 介入含义 |
|------|------|-----------|---------|
| **初期** | 信号刚出现/确认，价格距突破位较近 | 距突破位≤+5% | 远离追高风险区 |
| **中期** | 信号已确认并运行一段时间 | 距突破位+5%~+12% | 需谨慎评估追高风险 |
| **已延伸** | 价格已远离突破位 | 距突破位>+12% | 介入成本较高，盈亏比下降 |

**生命周期天数**：突破后第N天 = 当前日期 - 信号触发日期

**验证状态**：信号是否通过验证期（如"3日收盘不破突破位"）

### 4.4 旧P0-P7仲裁规则 vs 新仲裁逻辑

| 旧规则 | 条件 | **新规则** | 变化 |
|--------|------|-----------|------|
| P0 | right_side_confirm=否决 | **不变**（硬否决优先级最高） | — |
| P1 | 硬否决（监管/ST/退市） | **不变** | — |
| P2 | 深度高估 | 并入**风险边界**维度连续值 | 从独立规则变为维度输入 |
| P3 | bearish+共识≥0.67 | **连续共识率<-threshold** | 从固定阈值变为regime适配 |
| P4 | 未确认 | **连续共识率在中性区间** | 从二元判断变为连续判断 |
| P5 | 基础确认+非强看空 | **连续共识率>0.3但维度协同不足** | 增加协同性检查 |
| P6 | 强确认+bullish≥0.67 | **连续共识率>0.3且≥3维同向** | 增加强度和协同要求 |
| P7 | 无明确信号 | **连续共识率在中性区间** | 统一为中性判断 |

## 五、判定逻辑升级

### 5.1 从离散投票到连续强度核算（核心升级）

> 注：因子维已在§4.1中确认并入状态总结，不再作为独立维度。以下仅列保留的5个核心维度。

| 维度 | 当前输出 | **升级后输出** |
|------|---------|--------------|
| 结构维 | 上升/盘整/下降 | strength × (+1/0/-1) → 连续值 |
| 量价维 | 强健康~严重背离 | health_score → 0~1 |
| 筹码维 | 流入/中性/流出 | flow_strength × (+1/0/-1) |
| 情绪维 | 复苏~退潮 | temperature → 0~100 映射 |
| ~~因子维~~ | ~~看多/中性/看空~~ | ~~已并入状态总结~~ |

### 5.2 市场状态感知的动态权重

```python
MARKET_REGIME_WEIGHTS = {
    'trending_up':   {'structure': 0.30, 'volume': 0.25, 'chip': 0.20, 'factor': 0.15, 'emotion': 0.10},
    'trending_down': {'structure': 0.25, 'volume': 0.20, 'chip': 0.15, 'factor': 0.20, 'emotion': 0.20},
    'ranging':       {'structure': 0.15, 'volume': 0.20, 'chip': 0.25, 'factor': 0.20, 'emotion': 0.20},
    'high_vol':      {'structure': 0.15, 'volume': 0.15, 'chip': 0.20, 'factor': 0.25, 'emotion': 0.25},
}
```

### 5.3 加权连续共识率

```python
def continuous_consensus(dimensions, regime):
    weights = MARKET_REGIME_WEIGHTS[regime]
    weighted_sum = 0
    total_weight = 0
    for dim_name, dim_value in dimensions.items():
        w = weights.get(dim_name, 0.1)
        continuous = dim_value['continuous_value']  # -1~+1
        conf = dim_value['confidence']
        weighted_sum += w * continuous * conf
        total_weight += w
    return weighted_sum / total_weight if total_weight > 0 else 0
```

### 5.4 仲裁规则升级

```python
def arbitrate(consensus, dimensions, regime, risk):
    cs = consensus
    if risk.get('hard_veto'):
        return 'avoid', '硬否决'
    threshold = {'trending_up': -0.5, 'ranging': -0.4, 'high_vol': -0.3}.get(regime, -0.4)
    if cs < threshold:
        return 'avoid', f'强看空共识({cs:.2f})'
    if cs < -0.2:
        return 'wait', f'弱看空({cs:.2f})'
    if cs >= 0.3:
        bullish_count = sum(1 for d in dimensions.values() if d['continuous_value'] > 0.2)
        if bullish_count >= 3:
            position = min(0.6, 0.3 + cs * 0.3)
            return 'enter', f'看多共识({cs:.2f}), {bullish_count}维同向'
    return 'wait', '无明确信号'
```

## 十、维度引擎整合方案（v4.0新增）

### 10.1 现状问题

经全面调查，当前系统中6个维度的分析引擎存在**严重的零散分布和冗余计算**问题：

| 维度 | 分散文件数 | 关键冗余问题 |
|------|:---------:|-------------|
| 第1维 信号确认 | 4+ | right_side_confirm 2版本共存、生命周期2处独立重算 |
| 第2维 结构位置 | 5+ | ma_alignment 3处独立计算（中英文输出不统一）、price_position 3处不同算法、支撑阻力3源无统一输出 |
| 第3维 量价健康 | 7 | vol_ratio **6处独立计算**（10日/20日/100日均量口径不同）、volume_price_fit 2处、divergence 4+处 |
| 第4维 资金筹码 | 9 | 两套并行阶段判定系统、两套并行主力评分系统、moneyflow_cache 6处直接查询 |
| 第5维 情绪环境 | 8 | sentiment_phase映射2处重复逻辑、涨停生态指标分散在2个文件 |
| 第6维 风险边界 | 10 | risk_level **10+处独立计算**、volatility_level 2个独立计算路径、支撑阻力4个独立数据源 |

**典型案例**：vol_ratio（量比）在6个文件中有独立计算，均量基准分别是10日/20日/100日，导致不同模块对"放量"的判定标准不一致。

### 10.2 整合原则

1. **每维度一个集中的维度引擎**：负责该维度的唯一计算入口、统一输出格式
2. **收敛冗余计算**：同一指标只在一处计算，其他模块引用计算结果
3. **消除粗启发式**：data_daemon中的粗启发式计算替换为维度引擎调用
4. **统一输出格式**：每个维度输出统一的双轨结构（status_description + judgment + audit）
5. **保留共用逻辑**：跨维度共用的逻辑（如支撑阻力）定义为共享服务
6. **分阶段实施**：从简单维度开始，按整合难度从低到高推进

### 10.3 目标架构

```
当前架构（散乱）：
  data_daemon.py → 各处分散计算 → tags → status_engine.py → dim_states
  问题：同一指标多处计算、口径不一致、输出格式不统一

目标架构（集中）：
  dim1_signal_engine.py    → 信号确认维度的唯一计算入口
  dim2_structure_engine.py → 结构位置维度的唯一计算入口
  dim3_vp_engine.py        → 量价健康维度的唯一计算入口
  dim4_chip_fund_engine.py → 资金筹码维度的唯一计算入口
  dim5_emotion_engine.py   → 情绪环境维度的唯一计算入口
  dim6_risk_engine.py      → 风险边界维度的唯一计算入口
  shared_support_resistance.py → 跨维度共用的支撑阻力服务
```

每个维度引擎的职责：
1. 读取该维度的所有输入数据（从pre_feat_cache/daily_cache等）
2. 执行该维度的所有计算逻辑（收敛当前分散在多处的计算）
3. 输出该维度的统一结构化结果（status_description + judgment）
4. 提供条件稽核（audit）所需的条件数据
5. 写入pre_feat_cache/dim_states供下游消费
