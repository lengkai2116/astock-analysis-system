# 三元条件驱动框架与闸门体系整体整合方案

## 一、背景与定位

### 1.1 方案层级关系

本方案是 307 号（三元条件驱动框架）与 308 号（闸门2右侧确认信号体系）的**总体整合视图**，回答"如何将现阶段系统内部的细项工作流统一运作"的问题。三个方案的关系：

```
294号总纲（机会图谱五层架构）─── 总体骨架
   │
   ├─ 307号（三元条件驱动框架）── 决策范式（画像→入场→退出）
   ├─ 308号（闸门2右侧确认体系）─ 第二元入场信号的执行细则
   └─ 309号（本方案）────────── 整体工程整合（接线与替换）
```

### 1.2 核心结论（一句话）

**系统的骨架（L2 标签管道 + L4 仲裁引擎 + 标签池 + API）已经全部就位，整合不是重建，而是"三换一接"**：

1. **换**：306号 `_compute_hold_period` → 307号 七维画像 + 机会类型摘要（引擎不动）
2. **换**：VOTE_MAP 扩充 + operation_advice 消费闸门结果（L4 微调）
3. **换**：前端从"持有周期色块" → "四级展示 + 直白表述"（296+307）
4. **接**：EnhancedPatternDetector 接入预计算管道（零成本获得 45+ 形态信号，308号 P0）

## 四、引擎系统调整（3 处，全部是"改"不是"建"）

### 4.1 引擎调整 1：`_compute_hold_period` → 拆为画像+摘要（307号落地）

**现状**：管道 L1626 调用 306号的 `_compute_hold_period(tags)`，输出 `hold_period / hold_period_days / hold_status_type` 三个旧字段。

**调整**：替换为 307号 的两个函数：
- `_build_opportunity_profile(tags)` → 七维画像（风险/价值/趋势/量价/资金/情绪/事件）
- `_classify_opportunity_type(tags)` → 机会类型摘要（复用现有规则树逻辑，改输出字段）

**引擎层不动**——估值/阶段/情绪/板块/量价/缠论/筹码/事件引擎全部保留，只是消费方式从"306分类"变为"307画像"。

### 4.2 引擎调整 2：接入 EnhancedPatternDetector（308号 P0，零成本）

**现状**：管道 L1577 只调 `_add_vp_simple_tags`（简单检测，导致 `pattern_signal` 100% 为 none）。`EnhancedPatternDetector`（45+ 条规则）已存在但只在策略分析路径被调用（volume_price_strategy.py:2671），**未进入预计算管道**。

**调整**：在管道 L1577 处，将 `_add_vp_simple_tags` 升级为调用 `EnhancedPatternDetector.detect_all()`——一次接入获得 45+ 种形态确认信号（预涨/黑马/K线反转）。这是整合成本最低、收益最大的一步。

### 4.3 引擎调整 3：新增"闸门2右侧确认判定器"（308号 P1）

新增纯函数 `_check_right_side_confirm(opportunity_type, tags, kline_df)`，消费三类信号做三档判定：

- **基础确认**（均线/趋势）：从 indicator_ma 或标签读取
- **增强确认**（缠论二买三买 / pattern_signal 形态）：从 buy_sell_point + pattern_signal 标签读取
- **否决条件**（量价背离/空方形态/缠论卖点）：从 volume_price_fit + pattern_signal + buy_sell_point 读取

**关键设计**：产出**三档状态**（强确认/基础确认/未确认/否决），供 L4 投票加权和前端展示使用，不是简单布尔值。

## 六、三元框架与闸门体系的映射关系（确认结论）

### 6.1 确认：闸门体系 = 三元框架第二元的细化执行方案

用户提出的理解经确认正确：**闸门体系是三元框架第二元的入场细化执行方案，与第一元机会画像是同等关系**。

```
三元框架（307号）          闸门体系（308号 + L4）
─────────────────────────────────────────────────
第一元：机会画像 ──────→ 闸门1：机会监控（动态感知）
   "这是一个什么机会"        "当初的理由还在吗？变了没有？"
                              ↑ 这不是一次性判定，是**持续监控**——
                              每次画像刷新即复核，机会类型变化
                              （如 building→distributing）立即告警

第二元：入场信号 ──────→ 闸门2：右侧确认（时机）
   "什么时候可以买"          "股票走出上涨信号了吗？"
                        + 闸门3：L4共识率≥55%（方向可信度）
                              "多数信号都在说买吗？"

第三元：退出条件 ──────→ 技术面退出 + L4估值跟踪退出
   "什么时候必须卖"          "入场依据消失 / 估值修复完成"
```

### 6.2 两个关键澄清

1. **闸门1不是第一元的重复，而是第一元的"时间维"**——第一元描述静态现状，闸门1监控动态变化。机会类型从 `value_bottom` 变成 `danger_zone` 的那一天，就是闸门1触发的时刻。**闸门1的工程实现已经存在**（L4 的 `_compute_daily_change`，即 300号§2.3 的 daily_change_summary 8 维度变更检测），只需把"机会类型变化"纳入监控维度。

2. **闸门2和闸门3都在第二元内部，是 AND 关系**——右侧确认管"时机对不对"，L4 共识率管"方向信不信"。两者都满足才允许入场。不要误解为第二元只等于闸门2。

### 6.3 决策映射表

| 三元框架 | 闸门体系 | 落地位置 |
|---------|---------|---------|
| 第一元：七维画像 + 机会类型 | 闸门1：机会还在（画像复核） | L2 管道 `_build_opportunity_profile` |
| 第二元：入场信号 | 闸门2（右侧确认）+ 闸门3（L4共识率≥55%） | `_check_right_side_confirm` + L4 `consensus_rate` |
| 第三元：退出条件 | 技术面退出 + L4 估值跟踪退出 | `_compute_exit_conditions` + L4 `valuation_tracking` |

## 七、闸门2判定器详细设计

### 7.1 三档判定流程

```
┌─────────────────────────────────────────────────────────┐
│ 闸门2 三档判定流程（每只股票每天评估一次）                 │
│                                                          │
│ STEP 1 否决检查（一票否决，先看有没有危险信号）：           │
│   ❌ 缠论卖点出现（first_sell/third_sell）                │
│   ❌ 量价背离（volume_price_fit=diverging）               │
│   ❌ 放量长阴/空方炮（pattern_signal 预跌型）              │
│   任一命中 → 判定"否决"，无论其他信号多好都不入场           │
│                                                          │
│ STEP 2 基础确认（必选，保证覆盖率）：                      │
│   按机会类型查基础信号（308号§四映射表）：                  │
│     value_bottom → 放量站上MA20（indicator_ma）           │
│     building_watch → 突破建仓成本区（chip_position+MA）    │
│     main_upsurge → 回踩MA10不破                           │
│     wash_hot → 突破洗盘区间上沿                            │
│   命中 → 进入 STEP 3；未命中 → 判定"未确认"               │
│                                                          │
│ STEP 3 增强确认（加分）：                                  │
│   ✅ 缠论二买/三买（buy_sell_point=second_buy/third_buy）  │
│   ✅ 量价形态（pattern_signal 预涨型/黑马型，45+种）        │
│   ✅ K线反转（pattern_signal 锤子线/晨星等）               │
│   ✅ 级别验证（周/月线向上背书）                           │
│   命中 ≥2 项 → "强确认"；1 项 → "基础确认"                │
│                                                          │
│ 输出: right_side_confirm = 强确认 | 基础确认 | 未确认 | 否决 │
│       confirm_evidence = ["二买", "平台放量突破", ...]      │
└─────────────────────────────────────────────────────────┘
```

**识别能力的核心依赖**：STEP 1 依赖 volume_price_fit + pattern_signal + buy_sell_point（其中 2 项待修复）；STEP 2 依赖 indicator_ma（MA60 待加）；STEP 3 依赖 buy_sell_point + pattern_signal + level_validator（其中 2 项待修复）。**四个硬缺口是闸门2识别能力的前提**，缺一不可。

### 7.2 右侧确认的用户表达（三层设计，核心关切）

原则：**"不说术语，说动作"**。

**第一层：状态徽标（L1 浮窗，3 秒看懂）**

```
🔴 右侧未确认："还在蓄势，等它放量突破再动手"
🟡 基础确认中："已出现初步上涨信号，可轻仓关注"
🟢 强确认："上涨信号明确（突破+放量+结构确认），可以行动"
⚫ 否决："出现出货/背离信号，别碰"
```

**第二层：确认清单（L2 详情面板，"还差什么"）**

```
┌─ 右侧确认状态 ──────────────────────────┐
│ 🟡 基础确认中（2/3 条件满足）             │
│   ☑ 放量站上 20 日均线（已满足）          │
│   ☐ 缠论二买出现（还差：回调不破前低）    │
│   ☑ 周线趋势向上（已满足）               │
│   ──────────────────────────────       │

│         回调不破位的确认，再等等"        │
└─────────────────────────────────────────┘
```

**第三层：证据展示（L3 L4诊断区，为什么）**

```
确认信号明细:
  🟢 平台放量突破（今日出现）—— 形态确认
  🟢 MA5 金叉 MA20（3日前出现）—— 均线确认
  🟡 缠论二买 —— 尚未出现（等待回调不破前低）
  否决检查: 无背离、无卖点、无空方形态 ✅
```

**关键设计**：把 308 号的专业信号全部翻译为"动作 + 状态"：
- "二买" → "回调不破前低"（用户在 K 线上一眼可辨）
- "平台放量突破" → "横盘后放量向上突破"（白话+形态）
- "级别向上" → "大趋势（周线）向上，不是逆势抄底"
- "否决" → 直接说"出现卖出信号/量价背离，别碰"

**对用户的价值**：用户不需要懂缠论、不需要懂量价形态，只需要看到：①状态徽标（能不能动）②还差什么（缺哪个确认，怎么等）③为什么（命中了哪些信号，证据透明）。

## 八、五个整合决策点（确认结论，全部接受）

| 决策 | 结论 | 说明 |
|:----:|------|------|
| 1. 机会类型由谁产出 | L2 管道预计算产出（日终） | 与现有"L2 预计算 + L4 读取复用"架构一致，L4 诊断时不重新分类 |
| 2. 闸门2判定在哪个进程执行 | 日终在 L2 管道产出 `right_side_confirm` 三档状态 | 日线确认信号足够；盘中增量一期不做（遵循最小实现） |
| 3. `_advise_action` 放哪里 | **不新建**——由 L4 内部 `_build_operation_advice` 消费闸门结果 | 避免两套建议逻辑（cross_validate.py:604 已有此方法） |
| 4. L4 投票表扩充 | 新增 `pattern_signal`（看涨形态 +1 / 看跌 -1）、`right_side_confirm`（强确认 +1） | 12-13 票，与 294号"12标签投票"对齐且更丰富 |
| 5. 机会类型摘要归属 | 由七维画像推导，不再是独立 if-elif 树 | 保留 306 规则树判定逻辑作为推导映射参考 |

## 九、完整数据流（整合后）

以点击某只股票为例，全链路：

```
① L2 日终预计算（data_daemon）:
   各引擎 → 原始标签 → 七维画像 → 机会类型 → 右侧确认三档
   → evidence_count → 全部落库 opportunity_tags_cache

② 前端加载 Treemap（/treemap）:
   读快照表 → L0 方块着色（机会类型颜色）
   → 悬浮 → L1 浮窗（七维红绿灯迷你条 + 一句话大白话）

③ 点击方块（/diagnose）:
   L4CrossValidator.diagnose(ts_code, tags)
     - 读七维画像 + 右侧确认 + 原始标签
     - Step A 估值门禁（高估直接拒绝）
     - Step B 情绪加权
     - Step C 共识投票（12+ 标签，含 buy_sell_point/pattern_signal 票）
     - Step D 结果映射 → consensus / operation_advice
     - 估值跟踪退出 → 退出条件
   → L2 详情（七维画像 + 入场条件 check + 退出条件 check）
   → L3 L4诊断区（共识率仪表盘 + 投票明细 + 操作建议）

④ 操作建议唯一来源 = L4 operation_advice
   三元框架不再独立生成建议（307号§5.4 修正）
```

## 十三、总结

1. **系统骨架已就位**——L2 标签管道 + L4 仲裁引擎 + 标签池 + API 全部实现，整合是"三换一接"而非重建。

2. **四硬缺口是前提**——MA60 新增列、second_buy 提取修复、pattern_signal 接入、volume_price_fit 调优，前三项约 40 行代码，是闸门2增强确认层生效的必要条件。

3. **闸门体系 = 三元第二元的细化执行**——闸门1是机会动态感知（工程=L4 daily_change_summary 扩展），闸门2+3 是入场双条件（AND），退出并入估值跟踪通道。

4. **右侧确认的用户表达三层设计**——状态徽标（能不能动）/ 确认清单（还差什么）/ 证据展示（为什么），全部"说人话、说动作"。

5. **实施主线 S0-S5**（硬缺口前置修复 + 后端整合，3-4 个工作日）+ S6（前端）+ S7（二期可选增强）。

6. **操作建议唯一来源 = L4 operation_advice**，三元框架只提供条件状态，杜绝两套建议冲突。
