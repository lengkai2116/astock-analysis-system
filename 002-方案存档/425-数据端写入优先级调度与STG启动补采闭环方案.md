# 425 — 数据端写入优先级调度与STG启动补采闭环方案

> **性质**：本方案为**架构设计方案**（尚未修改代码），解决 daemon 单进程串行主循环下，
> "补采/补预计算（紧急）与盘中采集（高频）抢占写锁"的冲突，以及 STG 启动时数据
> 完整性检查未能以高优先级触发补采闭环的缺口。
>
> **前提（业务优先级，用户确认）**：SIG/JUD 核心分析依赖**完整前一日日终数据**；
> 盘中数据仅服务前端展示。因此**补采/补预计算优先级高于盘中采集**。

## 1. 现状核查（2026-09-11 实况，v2.0 更新）

### 1.1 daemon 综合功能（单进程串行主循环，属实）

daemon 是**单进程串行主循环**（`data_daemon.py:main()`，每 30s tick），承担全部职责：

| 类别 | 具体功能 | 位置 |
|---|---|---|
| **盘中采集** | mootdx 快照(5s)+分钟(300s)线程、AKShare 低频线程 | `_start_collectors` |
| **补采** | `run_integrity_check`(回溯3日)、`_consume_sync_requests_batch`(消费积压) | 1417 / 4640 |
| **管道进度** | `_drive_pipeline`：COL-1~7→RAW-1/2/3→RAW-2B→SIG→JUD→OUT→QA-CHECK | 4841 |
| **预计算** | `_precompute_indicators/raw_features/preset_combos/strategy_signals` | 5309 / 2387 / 2092 / 5347 |
| **日终同步** | `run_daily_sync`：指数日线/龙虎榜/量比/形态/融资/胜率/复权/股东/扩展财务 | 1905 |
| **维护** | WAL checkpoint（全分库）、数据清理、定时巡检、历史QA巡检 | 主循环 |

**主循环 tick 顺序**（`data_daemon.py:6023-6043`）：WAL checkpoint → `_consume_sync_requests_batch` → `_drive_pipeline` → 数据清理 → 整点巡检 → `sleep(30)`。补采类任务在主循环内**同步执行**，会拉长 tick。

**429 号修复（已落地，2026-09-11 15:07 commit c0ddae4）**：针对 sync_requests 积压风暴的治标措施——

- `_consume_sync_requests_batch`：`MAX_PER_TICK=50`，finance/stk_holder 按 ts_code 去重、每只只补采一次、跨两类对半分配预算，其余保持 pending 留待下轮
- COL/RAW 网络超时根治 + RAW 并行超时失效修复（消除"网络卡死"级阻塞）

**429 落地后的剩余缺口**：429 只做**限流与超时保护**，未解决以下问题（即本方案目标）：
1. **无优先级调度**：补采/补预计算与盘中采集抢 market_cache.db 写锁时，无高低之分
2. **无盘中让路**：补采期间 mootdx 5s 快照线程照常高频写入，写锁竞争与无谓 IO
3. **无启动高优闭环**：启动发现数据滞后时，`run_integrity_check` 只是普通补采，不设 HIGH、不让盘中让路、无补采后校验衔接

### 1.2 写锁与分库隔离现状（属实）

- **写锁**：`sharding_manager._write_locks[db_name]` 为 **per-db `threading.RLock`（进程内锁）**
- **分库隔离**（`sharding_manager.py:_table_to_db`）：

| 写源 | 目标分库 | 频率 |
|---|---|---|
| mootdx 盘中（minute_kline_cache） | **market_cache.db** | 5s/300s 高频 |
| 补采 daily/资金流/涨跌停/融资 | **market_cache.db** | 低频 |
| 补采财务（4表+finance_report/stk_holder） | **financial/history_cache.db** | 低频 |
| 预计算 indicator/factor/pre_feat | **compute_cache.db** | 低频 |
| 预计算 strategy/status/treemap | **snapshot_cache.db** | 低频 |

**关键结论**：写锁是 **per-db** 的，补采财务（financial/history）、预计算（compute/snapshot）与盘中（market_cache）**不同库，天然无冲突**；**真正同库冲突仅集中在 market_cache.db**：盘中 minute_kline（高频） vs 补采 daily/moneyflow/stk_limit/margin（低频）。因此**降频 mootdx 只需在补采目标含 market_cache.db 时进行**。

### 1.3 STG 启动数据检查现状（v2.0 更新）

| 检查 | 功能 | 是否触发补采 |
|---|---|---|
| `_check_data_timeliness`(1680) | 检查核心/补充/背景数据滞后天数 | **否，仅日志** |
| `_audit_data_freshness`(4821) | 数据年龄审计 | **否，仅返回状态** |
| `run_integrity_check`(1417) | 启动回溯3日/整点巡检补采 | ✅ 有补采，但**无优先级、不让路** |
| `_run_qa_check`(5193) | 423号 QA-CHECK：单轮校验+补算调度（**已实施**） | ✅ 有补算（管道步骤级），事件驱动非阻塞 |
| `RecomputeScheduler` | 423号：问题→管道步骤重跑映射（**已实施**） | ✅ 有补算（RAW/SIG/JUD 步骤） |
| `_is_pipeline_complete` / `_is_precompute_in_progress` | 管道完成/预计算进行判断 | 用于跳过 |

**423 号已建立的能力（v2.0 边界依据）**：QualityChecker（QUALITY_RULES 动态覆盖率）+ RecomputeScheduler（RECOMPUTE_KEYS→置 pending 由管道重跑）+ QA-CHECK 步骤已接入 `_drive_pipeline`（`data_daemon.py:5122`），实现了**"管道步骤 done 后 → 质量校验 → 定向补算 → 多轮核查"**闭环，事件驱动非阻塞。

**425 的核心缺口（v2.0 精确定位）**：423 的闭环在**管道推进过程中**（步骤级补算），且不处理优先级；425 的增量是**管道推进之前**的 COL 数据层——
1. 启动/巡检发现 COL 数据滞后时，以 **HIGH 优先级**立即执行补采（`run_integrity_check`），并让盘中采集让路
2. 补采完成后与 423 QA-CHECK 衔接（复用 `run_quality_round` 校验）

## 2. 架构设计

### 2.1 核心原则

1. **不引入新进程**：所有写入收敛在 daemon 进程内，复用现有 per-db `RLock`
2. **优先级调度**：补采/补预计算 = 最高优先级，盘中采集 = 可让路（前端展示容忍延迟）
3. **分库隔离为主，market_cache.db 优先级为辅**：冲突仅需针对 market_cache.db
4. **与 423 衔接而非重复**：补采后校验复用 423 `QualityChecker.run_quality_round`；管道步骤级补算继续由 423 RecomputeScheduler 负责，425 只做 COL 数据层补采的优先级与触发时机
5. **STG 启动闭环**：数据检查 → 触发 HIGH 补采 → QA 校验 → 恢复管道

### 2.2 写入优先级模型

在 daemon 主循环引入**优先级状态机**（模块级全局变量 `_collect_priority` + `threading.Event` 线程安全控制）：

```
优先级: HIGH（补采/补预计算·核心分析依赖） > NORMAL（日终/巡检） > LOW（盘中采集）
```

| 源 | 优先级 | 说明 |
|---|---|---|
| `run_integrity_check` 补采（启动回溯3日/整点巡检） | **HIGH** | COL 数据层，SIG/JUD 依赖 |
| sync_requests 消费—**核心依赖类**（finance_report/stk_holder/财务4表） | **HIGH** | SIG/JUD 依赖；目标 financial/history 库，天然隔离，无需降频盘中 |
| sync_requests 消费—**前端展示类**（full_* 等） | **LOW** | 前端全量分析请求；沿用 429 `MAX_PER_TICK=50` 限流，不抢占核心 |
| 补预计算（RAW/SIG 重算，423 RecomputeScheduler 触发） | **HIGH** | 管道步骤级，目标 compute/snapshot 库，天然隔离 |
| 日终同步（run_daily_sync） | NORMAL | 15:30 后，非盘中 |
| WAL checkpoint | LOW | 可降频/延后 |
| mootdx 盘中采集 | **LOW（可让路）** | 前端展示，容忍延迟 |

### 2.3 盘中采集让路机制（v2.0 修正实现要点）

补采/补预计算期间，**降频 mootdx 高频线程**（market_snapshot 5s、minute_full 300s）。

**实现要点（修正）**：`_MootdxThread`（mootdx_collector.py:1213）的 `self.interval` 为构造参数、不可变；`_stop_event` 为 **stop 专用**（set 即永久停止，clear 后恢复轮询），**不能用于控制等待周期**。正确做法：

1. 将 `_MootdxThread.interval` 改为**运行时可变属性**（run 循环每次读取最新值计算 `wait`，无需改动等待逻辑）
2. daemon 主循环通过 `mootdx_collector._threads` 直接设置：`thread.interval = 60`（market_snapshot）→ 补采完成恢复 `5`
3. **不 stop 线程**（保留连接），仅降频，避免重建连接开销
4. 降频条件（v2.0 细化）：**HIGH 且补采目标含 market_cache.db** 时才降频；纯财务/预计算补采不降频（天然分库隔离，无谓牺牲前端实时性）

### 2.4 STG 启动高优补采闭环（v2.0 与 423 衔接）

在 `_drive_pipeline` 之前插入**启动补采闭环**（复用现有检查，改为触发式）：

```
STG 启动 / 每 N tick 巡检
  ↓
数据完整性检查（复用 _check_data_timeliness 判定 core_tables 滞后 >1天
                  + run_integrity_check 补采清单）
  ↓ 发现缺失（COL 数据滞后）
进入 HIGH 优先级补采模式（_collect_priority = HIGH）
  ├─ 若补采目标含 market_cache.db：降频 mootdx（snapshot 5s→60s，minute 300s→600s）
  ├─ 高优补采 daily/moneyflow/stk_limit/margin（market_cache.db）
  ├─ 高优补采财务（financial/history_cache.db，天然隔离，不降频）
  ├─ 预计算缺口交给 423 RecomputeScheduler（compute/snapshot_cache.db，天然隔离）
  └─ 补采完成后 QA 校验（复用 423 run_quality_round / 由 QA-CHECK 衔接）
  ↓ 校验通过 / 无缺口
恢复 NORMAL（_collect_priority = NORMAL）：恢复 mootdx 频率 + 继续管道驱动 SIG/JUD
```

**与 423 的时序衔接**：425 管「管道推进前」的 COL 数据补齐（HIGH 补采）；423 管「管道推进中」的步骤质量门禁与补算（QA-CHECK）。两者顺序为：425 补 COL → `_drive_pipeline` 推进 → 423 QA-CHECK 门禁，天然衔接、无重复实现。

### 2.5 关键实现约束

1. **写库**：统一走 `_ecm.cache_*`（已走 per-db RLock + INSERT OR REPLACE），**禁止绕过**
2. **优先级状态**：模块级 `_collect_priority` 标志 + `threading.Event`（跨线程可见），主循环单点设置
3. **mootdx 降频**：`_MootdxThread.interval` 改为可变属性，主循环直接赋值；**不使用** `_stop_event.set()/clear()`（stop 专用）
4. **QA 闭环**：复用 423 `QualityChecker.run_quality_round` 与 `RecomputeScheduler`，**不新建**检查→补算通道
5. **sync_requests 分级**：沿用 429 `MAX_PER_TICK=50` 限流，仅按 task_type 区分优先级，不重复限流逻辑
6. **可观测性**：接入 423 monitor 体系——`monitor.record_metric('collect_priority_mode')`（HIGH/NORMAL/LOW）、`monitor.record_metric('main_loop_tick_ms')`（每 tick 时长，验收量化依据）；HIGH 进出打日志
7. **Windows 兼容**：无新跨进程 API，纯线程内控制（RLock/Event 跨平台）
8. **迁移预留（本机为主，配置外置）**：本方案新增代码**不引入新的硬编码路径/密钥**；DATA_DIR 走环境变量（`data_daemon.py:main()` 已支持）；TUSHARE_TOKEN 等密钥保持 env 文件外置，不进代码/启动器明文（现有 plist 明文 token 待随启动器体检一并整改，属后续独立任务，不在本方案改动范围）

## 5. 验收标准（v2.0 修正）

1. 启动后若 core_tables（daily_cache 等）滞后 >1 天，自动进入 HIGH 补采模式，**mootdx 高频线程降频**（日志可查 `collect_priority_mode=HIGH` + interval 变更日志）
2. 补采完成后 QA-CHECK 通过（复用 423），管道 SIG/JUD 正常推进，核心分析可用
3. **主循环 tick 时长可观测**：`monitor.record_metric('main_loop_tick_ms')` 落点；HIGH 补采期间整体 tick 延迟有量化记录（≤ 合理上限，如 2min），非交易时段基线 tick 不受影响
4. 补采财务/预计算期间，**无 cross-db 写锁冲突日志**（天然分离验证）；降频仅发生在目标含 market_cache.db 的补采（日志可查）
5. `make lint` 通过；`make typecheck` **零新增**（mypy 预存 1181 错误，基线不上升）；`make test` 全通过（含新增 `tests/test_425_priority.py`）

## 6. 决策点（v2.0 更新）

| 决策 | 选项 | 当前建议 |
|---|---|---|
| 进程模型 | 单进程优先级调度 vs 多进程 | **单进程**（D1） |
| 优先级粒度 | 全局 vs per-db | **per-db + 全局模式**（market_cache.db 需要，其余天然分离） |
| 补采触发 | 启动一次 vs 每 N tick | **启动 + 每 N tick 巡检**（复用现有整点巡检） |
| mootdx 降频 | 暂停 vs 降频 | **降频**（保留连接，interval 可变属性；非 `_stop_event`） |
| 降频条件 | 全局 HIGH vs 目标库判断 | **目标含 market_cache.db 才降频**（R5） |
