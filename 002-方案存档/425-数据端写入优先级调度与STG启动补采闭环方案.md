# 425 — 数据端写入优先级调度与STG启动补采闭环方案

> **性质**：本方案为**架构设计方案**（尚未修改代码），解决 daemon 单进程串行主循环下，
> "补采/补预计算（紧急）与盘中采集（高频）抢占写锁"的冲突，以及 STG 启动时数据
> 完整性检查未能触发高优补采闭环的缺口。
>
> **前提（业务优先级，用户确认）**：SIG/JUD 核心分析依赖**完整前一日日终数据**；
> 盘中数据仅服务前端展示。因此**补采/补预计算优先级高于盘中采集**。

---

## 0. 结论速览

| # | 决策 | 结论 |
|---|---|---|
| D1 | 是否需要新进程承载补采/补预计算 | **否**。跨进程 `RLock` 失效，反而引入跨进程写锁复杂度；单进程优先级调度更优 |
| D2 | 补采与盘中采集是否冲突 | **部分冲突**，但仅集中在 `market_cache.db` 一个库（分库隔离已解决大部分） |
| D3 | 是否引入 STG 缓存写入队列 | **不需要全量队列**。现有 `写锁 per-db RLock` + INSERT OR REPLACE 幂等已足够；只需**优先级调度** |
| D4 | 是否建立 STG 启动数据检查→高优补采闭环 | **是，这是核心缺口**。现有 `_check_data_timeliness` / `run_integrity_check` 只告警/记录，不触发高优补采 |
| D5 | 写库方式 | **单进程内**复用现有 `RLock`；不新建跨进程写入通道 |

## 1. 现状核查（2026-09-11 实况）

### 1.1 daemon 综合功能（问题确认属实）

daemon 是**单进程串行主循环**（`data_daemon.py:main()`，每 30s），承担全部职责：

| 类别 | 具体功能 | 位置 |
|---|---|---|
| **盘中采集** | mootdx 快照(5s)+分钟(300s)线程、AKShare 低频线程 | `_start_collectors` |
| **补采** | `run_integrity_check`(回溯3日)、`_consume_sync_requests_batch`(消费积压) | 1381 / 4604 |
| **管道进度** | `_drive_pipeline`：COL-1~7→RAW-1/2/3→RAW-2B→SIG→JUD→OUT→QA-CHECK | 4805 |
| **预计算** | `_precompute_indicators/raw_features/preset_combos/strategy_signals`（RAW三步并行+SIG） | 4940-5000 |
| **日终同步** | `run_daily_sync`：指数日线/龙虎榜/量比/形态/融资/胜率/复权/股东/扩展财务 | 1869 |
| **维护** | WAL checkpoint（全分库）、数据清理、定时巡检、历史QA巡检 | 主循环 |

**核心问题**：主循环 30s 内**串行**执行 sync_requests 消费 → 管道驱动。补采会**阻塞**管道
（09-10 实证：21:09-21:35 一直逐条消费 `_consume_sync_requests_batch`，管道/WAL 全被阻塞）。

### 1.2 写锁与分库隔离现状

- **写锁**：`sharding_manager._write_locks[db_name]` 为 **per-db `threading.RLock`（进程内锁）**
- **分库隔离**（`sharding_manager.py:_table_to_db`）：

| 写源 | 目标分库 | 频率 |
|---|---|---|
| mootdx 盘中（minute_kline） | **market_cache.db** | 5s/300s 高频 |
| 补采 daily/资金流 | **market_cache.db** | 低频 |
| 补采财务（4表+finance_report/stk_holder） | **financial/history_cache.db** | 低频 |
| 预计算 indicator/factor/pre_feat | **compute_cache.db** | 低频 |
| 预计算 strategy/status/treemap | **snapshot_cache.db** | 低频 |

**关键发现**：写锁是 **per-db** 的，所以：
- 补采财务（financial/history_cache.db）与盘中（market_cache.db）**不同库，天然无冲突**
- 预计算（compute/snapshot_cache.db）与盘中（market_cache.db）**不同库，天然无冲突**
- **真正同库冲突仅集中在 market_cache.db**：盘中 minute_kline（高频） vs 补采 daily_cache（低频）

> 分库隔离已解决**绝大部分**写入冲突。剩余冲突窗口远小于直觉预期。

### 1.3 STG 启动数据检查现状（缺口确认）

| 检查 | 功能 | 是否触发补采 |
|---|---|---|
| `_check_data_timeliness`(1644) | 检查核心/补充/背景数据滞后天数 | **否，仅日志** |
| `_audit_data_freshness`(4785) | 数据年龄审计 | **否，仅返回状态** |
| `run_integrity_check`(1381) | 启动时回溯3日补采 | ✅ 有补采，但**无优先级** |
| `_is_pipeline_complete`(4556) | 管道完成判断 | 用于跳过 |
| `_is_precompute_in_progress`(4574) | 预计算进行中判断 | 用于跳过完整性检查 |

**核心缺口**：现有检查**只告警/记录，不触发"高优补采"闭环**。启动发现数据不足时，
没有机制立即以最高优先级补采/补预计算，也没有让盘中采集让路。

## 2. 架构设计

### 2.1 核心原则

1. **不引入新进程**：所有写入收敛在 daemon 进程内，复用现有 per-db `RLock`
2. **优先级调度**：补采/补预计算 = 最高优先级，盘中采集 = 可让路（前端展示容忍延迟）
3. **分库隔离为主，market_cache.db 优先级为辅**：冲突仅需针对 market_cache.db
4. **STG 启动闭环**：数据检查 → 触发高优补采 → QA 校验 → 恢复管道

### 2.2 写入优先级模型

在 daemon 主循环引入**优先级状态机**（模块级全局变量 `_collect_priority`）：

```
优先级: HIGH（补采/补预计算） > NORMAL（日终/巡检） > LOW（盘中采集）
```

| 源 | 优先级 | 说明 |
|---|---|---|
| 补采（run_integrity_check / sync_requests 消费） | **HIGH** | SIG/JUD 依赖，核心分析 |
| 补预计算（RAW/SIG 重算） | **HIGH** | 同上 |
| 日终同步（run_daily_sync） | NORMAL | 15:30 后，非盘中 |
| WAL checkpoint | LOW | 可降频/延后 |
| mootdx 盘中采集 | **LOW（可让路）** | 前端展示，容忍延迟 |

### 2.3 盘中采集让路机制

补采/补预计算期间，**暂停 mootdx 高频线程**（market_snapshot 5s、minute_full 300s）。

**实现要点**：`_MootdxThread`(mootdx_collector.py:1213) 已支持 `_stop_event.wait()`。
新增**优先级感知**：主循环设 `_backfill_mode = True` 时，采集线程 sleep 拉长（如 60s），
补采完成后恢复 5s。**不 stop 线程**（保留连接），仅降频，避免重建连接开销。

### 2.4 STG 启动高优补采闭环

在 `_drive_pipeline` 之前插入**启动补采闭环**（复用现有检查，改为触发式）：

```
STG 启动 / 每 N tick
  ↓
数据完整性检查（复用 run_integrity_check + _check_data_timeliness）
  ↓ 发现缺失（core_tables 滞后>1天）
进入 HIGH 优先级补采模式
  ├─ 暂停/降频 mootdx 高频线程（market_snapshot 5s→60s，minute_full 300s→600s）
  ├─ 高优补采 daily_cache（market_cache.db）+ 财务（history/financial_cache.db，天然隔离）
  ├─ 高优补预计算 RAW/SIG（compute/snapshot_cache.db，天然隔离）
  └─ 补采完成后 QA-CHECK 校验（复用 423 号 QualityChecker）
  ↓ 校验通过
恢复 NORMAL：重启 mootdx 高频 + 继续管道驱动 SIG/JUD
```

### 2.5 关键实现约束

1. **写库**：统一走 `_ecm.cache_*`（已走 per-db RLock + INSERT OR REPLACE），**禁止绕过**
2. **优先级状态**：模块级 `_collect_priority` 标志，线程安全（`threading.Event`）
3. **mootdx 降频**：复用 `_MootdxThread._stop_event.set()` / `clear()` 控制等待周期
4. **QA 闭环**：复用 423 号 `QualityChecker.run_quality_round`，补采后校验
5. **Windows 兼容**：无新跨进程 API，纯线程内控制

## 3. 改动范围评估

| 文件 | 改动 | 工作量 |
|---|---|---|
| `backend/data_daemon.py` | 主循环加优先级状态机、启动补采闭环、sync_requests 消费高优 | 中 |
| `backend/app/data/mootdx_collector.py` | `_MootdxThread` 增降频控制（复用 `_stop_event`） | 小 |
| `backend/app/data/stg_quality.py` | 复用 QualityChecker，无新增（可选：startup_check 封装） | 小 |

**不涉及**：新进程、跨进程锁、新写库通道、分库路由。改动面收敛到 daemon 内部。

## 4. 潜在风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| mootdx 降频后前端展示短暂延迟 | 低 | 补采低频一次，完成后立即恢复；且仅影响展示不影响分析 |
| 补采与管道 SIG/JUD 顺序 | 中 | 明确：先补采完整日终数据 → 再触发管道 SIG/JUD（保证分析输入完整） |
| 优先级标志竞态 | 低 | 线程安全 `threading.Event`，主循环单点设置 |
| market_cache.db 同库写锁（分钟 vs 日线补采） | 中 | 补采 daily 时 minute_full 降频，错开写窗口 |

---

## 5. 验收标准

1. 启动后若 daily_cache 最新日期滞后，自动进入 HIGH 补采模式，**mootdx 高频线程降频**（日志可查）
2. 补采完成后 QA-CHECK 通过，管道 SIG/JUD 正常推进，核心分析可用
3. **主循环不再被 sync_requests 长时间阻塞**（单轮 ≤ 合理上限，如 2min）
4. 补采财务/预计算期间，**无 cross-db 写锁冲突日志**（天然分离验证）
5. `make lint` / `make typecheck` / `make test` 全通过

## 6. 决策点

| 决策 | 选项 | 当前建议 |
|---|---|---|
| 进程模型 | 单进程优先级调度 vs 多进程 | **单进程**（D1） |
| 优先级粒度 | 全局 vs per-db | **per-db + 全局模式**（market_cache.db 需要，其余天然分离） |
| 补采触发 | 启动一次 vs 每 N tick | **启动 + 每 N tick 巡检**（复用现有整点巡检） |
| mootdx 降频 | 暂停 vs 降频 | **降频**（保留连接，复用 `_stop_event`） |
