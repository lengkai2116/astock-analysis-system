## 十六、daemon 锁根因修复（2026-08-15 全面排查）

> **历史症状**：十二节（08-09 指数回填 5088+ 次锁）、十三节（pytest 13 失败=daemon 并发）、08-15 实测"缓存分钟K线失败 database is locked"全天 831 次、daemon CPU 0% 仍持锁（ECM 建表失败）。
>
> **根因（Phase 1-3 排查 + 复现）**：**daemon 进程内双 ECM 实例并存**——`data_daemon.py main()` 直接构造 `EnhancedCacheManager()`（实例 A），而采集器/回填/其他模块用 `get_ecm_instance()` 全局单例（实例 B）。两实例各自独立连接组与 `_write_lock`（实例级，不互斥）→ 并发写同一 stock_cache.db → SQLite WAL 写者互斥 → 一方 busy_timeout=30s 超时 → `database is locked`。
> **复现实证**：双连接并发写（40 次×2）→ **100% 失败**（A=40/B=40）；单实例写正常。
>
> **修复**：`main()` 改 `_ecm = get_ecm_instance()`（统一全局单例，8-15 已实施）。
> **验证**：重启 daemon 后 8+ 分钟 **0 次锁失败**（修复前全天 831 次）；daemon 运行中单实例写 status_snapshot（5571 只）无锁冲突；单例一致性确认（is 同一实例）。
>
> **遗留**：①跨进程写冲突（API 进程 run.py 也用 get_ecm_instance，与 daemon 跨进程双单例）——当前 API 不常写（sync_requests 偶尔），若未来并发写增多需进程级协调（333 项3 单写队列/文件锁）②pytest 与 daemon 并发写测试仍会锁（测试环境纪律：daemon 空闲时跑全量）。
