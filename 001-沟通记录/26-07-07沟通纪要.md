### 003 — 分钟K线数据完整性和延迟检查

**用户输入：** 检查一下分钟K线的数据完整性和延迟

**AI执行内容：**

1. **数据管道现状**
   - **`/api/minute/<ts_code>` 端点**（MinuteDataManager）→ 返回空数据（0条）
   - **`as_minute_kline` SQLite表** → 0行
   - **`_minute_watchlist`（AKShare采集线程关注列表）** → 空列表

2. **三个数据源逐一检查**

   | 数据源 | 状态 | 原因 |
   |--------|------|------|
   | **Tushare stk_mins** | ❌ 限流 | 1次/分钟 → 1次/小时（频繁调用后升级），2000积分需求 |
   | **AKShare HTTP分钟K线** | ❌ 阻断 | Claude代理拦截所有HTTP外发请求 |
   | **mootdx bars() freq=0~8** | ❌ 不支持 | 所有频率代码均返回日线（收市15:00），无真正分钟K线 |
   | **akshare_collector分钟线线程** | ❌ 空转 | 依赖 `_minute_watchlist`（关注列表），但列表为空 |

3. **数据完整性：完全不可用**
   - `as_minute_kline` 表：0条记录（需要外部模块写入）
   - API：`/api/minute/000001.SZ?freq=5min` → 返回空数组
   - mootdx 5分钟K线本应有约48根/交易日/只，实测0根

4. **延迟：N/A（无数据）**

5. **根因分析**
   - **结构性问题**：分钟K线数据需要独立的数据源（Level-2行情或HTTP API）
   - mootdx的 TCP 协议只提供L1快照（最新一档），没有历史分钟K线缓存
   - AKShare HTTP被阻断，Tushare被限流，两个现有通道全部不可用

6. **可行解决方案**
   - **方案A（推荐）**：利用 mootdx 的 L1 快照轮询（每5秒），在内存中自行聚合为分钟K线（open=首笔, high/low/close=区间极值/末笔）
   - **方案B**：配置 AKShare HTTP 代理白名单，解除东方财富 API 的阻断
   - **方案C**：升级Tushare积分并重写限流逻辑（成本高，不推荐）

7. **结论：分钟K线数据当前完全不可用 🔴**
   - 不是配置或代码Bug，是数据源缺失的结构性问题
   - 需要将 mootdx L1快照自聚合方案纳入开发计划
