### 002 — WAL文件膨胀问题

**用户输入**：开机自启动采集后台提示WAL达2059MB（>2GB），询问原因

**AI执行内容**：
1. 定位WAL文件：stock_cache.db-wal 达2.0GB
2. 统计checkpoint失败次数：08-18~08-19共90次全部失败
3. 排查锁持有者：仅data_daemon（PID 1272）持有数据库锁，无其他进程
4. 根因确认：data_daemon自我锁定——wal_checkpoint('PASSIVE')通过self.conn执行，与自身的写事务互相阻塞

**修复措施**：
1. wal_checkpoint()改为使用独立连接（每次创建新连接执行checkpoint，不用self.conn）
2. 添加PRAGMA journal_size_limit=1048576（1GB上限，防止WAL无限膨胀）
3. WAL收缩暂不执行（data_daemon运行中），下次重启后新checkpoint机制生效

**验证**：语法检查通过，355个测试通过（9个预先存在的database locked失败与本次修改无关）

3. 与状态总结维度的区别是什么？
4. 要求研究LLM Wiki知识库和A股同类系统

**AI执行内容**：
1. 分析信号确认状态的定位：确实是派生维度（依赖signal_registry匹配其他引擎输出+日期计算），不是独立引擎
2. 与状态总结的区别：信号确认状态回答"这个信号还在不在、走到哪了"；状态总结回答"这只股票整体好不好"
3. 建议保留为派生维度（方案A），因为右侧交易的核心是"围绕信号做深度刻画"
4. 研究LLM Wiki知识库：信号注册表（触发/验证/生命周期）、信号生命周期（初期/中期/已延伸）、信号冲突处理机制
5. 研究A股同类系统：同花顺BSE（技术评分+多指标共振）、东方财富（信号强度+验证天数）、通达信（选股公式+确认状态）、BigQuant（信号概率+置信度）

**核心结论**：信号确认状态输出三个核心方面——

| 方面 | 核心问题 | 输出字段 |
|------|---------|---------|
| 信号类型 | "触发了什么信号" | signal_type + signal_name + trigger_price + trigger_date |
| 信号强度 | "这个信号有多强" | strength_score(0-100) + confidence + resonance_count + resonance_dims |
| 信号维持 | "信号还在不在、走到哪了" | lifecycle_day + lifecycle_stage + verified + decay_status + distance_to_signal_pct |

**强度评分计算逻辑**：
```
strength_score = structure_score×0.25 + volume_score×0.30 + chip_score×0.25 + factor_score×0.20
resonance_count = 维度中score>0.5的数量
```

**衰减状态判断**：
```
距离扩大 → healthy（信号强化）
距离缩小但未破 → fading（信号衰减）
距离为负且持续 → broken（信号失效）
```

**状态**：待用户确认信号确认状态的三个核心方面和输出规格
