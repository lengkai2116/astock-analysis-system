**弹窗字段来源梳理**：
- 时机行（d-timing-row）：`right_side_confirm`（闸门2，一票否决：缠论卖点/量价背离/预跌形态；基础确认；增强确认）→ 否决=回避(棕)

- 风险提示（d-risk）：`_build_risk_warnings`（只显示第 1 条）

**实证数据（5583 只）**：
- right_side_confirm 分布：否决 2679（48%）/ 未确认 1380 / 基础确认 1162 / 强确认 362
- **冲突1（用户指出）**：否决 + 主力建仓 building = **305 只**
- **冲突2**：否决 + 看多型机会类型（building_watch/steady_rise/build_high 等）= **490 只**（如 000039 否决+building_watch、000338 否决+steady_rise、000004 否决+build_high"建仓在高位，矛盾信号"——类型名自带矛盾）
- **冲突3**：否决 但 L4 看多票>看空票 = **522 只**（其中看多占比>65% = 408 只；如 000505 看多4/看空1 → verdict 会输出"优质机会，建议关注"，与时机行"回避"同屏）
- **冲突4**：否决 但操作建议 max_position_ratio>0 = 部分（实测 000039 max_ratio=0.4、000004=0.16）——label 写"右侧否决"却给仓位上限

**根因归纳**：
1. **引擎解耦无仲裁**：right_side_confirm（闸门2）与 main_force_phase/opportunity_type 是计算层完全独立的引擎，互不通信。313 号 v2 的"解耦原则"（潜力慢/时机快）是设计意图，但弹窗将两者并列展示且无解释层（313 号 C5/C6 认知管理未落地到弹窗），用户视角即为矛盾。
2. **L4 共识与闸门2 覆盖不对称**：VOTE_MAP 中 right_side_confirm 仅 1 票（否决=-1），building(+1)/valuation low(+1)/fina pass(+1) 等可压过；`_build_verdict` 按共识方向输出"优质机会建议关注"，**未被 rsc=否决 覆盖**（覆盖仅发生在 `_build_operation_advice`），导致 verdict 与时机行/操作建议三区块互相矛盾。
3. **max_position_ratio 未随否决归零**：`_build_operation_advice` 中 rsc=否决 只覆盖 action/label，仓位上限仍按共识率映射（仅 event_negative/deep 高估两分支归零），出现"建议不操作 + 仓位0.4"数值矛盾。
4. **机会类型规则树不看时机**：`_classify_opportunity_type` 完全不消费 right_side_confirm，"主力建仓观察/慢牛上涨"可与"右侧否决"同时成立。
5. **快照 vs 实时标签双源**：弹窗初始用 treemap_snapshot（日终），diagnose 用 opportunity_tags_cache（实时），快照未随盘中重算更新时同字段双值、前端本地近似 advice 与异步覆盖会闪变。

**结论**：用户观察准确，且不止一种冲突——共识别 4 类（时机vs主力建仓 305 只 / 时机vs看多机会类型 490 只 / 时机vs L4 看多共识 522 只 / 操作建议 label 与仓位矛盾）。根因在计算层引擎解耦无仲裁 + L4 否决覆盖不对称 + 规则树未消费时机信号 + 展示层无矛盾解释。本次为只读核查，未修改任何代码与方案。
